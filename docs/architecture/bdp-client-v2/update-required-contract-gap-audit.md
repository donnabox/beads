## Conclusion

The current development receiver does not implement an advertised Read+Update service. Its58 bounded row mappings and23 omissions do not measure distance to such a claim. Three concrete integration gates remain: a required discovery/Operation Directory surface connected to the mutable authority; inherited Read qualification on that actual target; and a real executable Read+Update evidence/admission lane. Filling every development inventory row would not by itself satisfy those gates.

Conversely, enabling optional CORS, emitting optional retry hints, providing optional History, exposing a retention promise, or implementing an administrative restore API is not required merely to advertise Read+Update. Configuration-sensitive obligations must be tested when applicable, with honest applicability recorded. They must not be promoted to universal feature requirements because a catalog row exists.

The smallest necessary next qualification slice is **whole-carrier rejection of repeated keys/names and unknown/forward local references, with no effects or key capture**. These are unconditional laws currently underobserved inside an already-bounded row. Existing runtime and request actions suffice; no new mechanism, fixture or policy seam is needed. This improves required evidence without manipulating the omission count.

## Concrete implementation/admission gates

1. **Discovery and directory are absent.** Spec `docs/specs/bdp.md:1998` requires Read+Update discovery with operations and aliases; `:2035` requires a directory with exactly eight singleton targets plus sequence, navigated rather than client-constructed. `packages/server/src/development-runtime.ts:175` serves an explicitly non-attesting development root and development paths, not service-desc discovery or a BDP Operation Directory. Existing mutation implementations are reusable, but their existence is not the discovery protocol. `read-update.discovery.document`, `.aliases`, `.operation-directory` are direct implementation/composition gaps. `.limits` is partly conditional: optional groups need not all be emitted, but emitted bounds must be truthful and diagnostic truncation requires its bounds. The fixed body/sequence/diagnostic limits need reconciliation with the final composed discovery, not blanket advertisement of everything.
2. **Public listener admission is Read-only.** `packages/server/src/index.ts:297` accepts only Read with existing target-bound evidence. This is an intentional guard, not a missing permission to flip an enum. A reviewed cumulative writer composition and evidence path must precede broadening it. The qualified Read target is not automatically evidence for the different mutable development listener. Spec `:73` and `:1990` require inherited Read behavior, including canonical Scope, discovery, inventories, selectors, views, HTTP and authorization semantics on the same advertised Scope.
3. **The write catalog is not executable normative evidence.** `packages/conformance/src/artifact-bundle.ts:115` preserves the ordinary Read catalog lane; its development mode admits only diagnostic write rows. `packages/conformance/src/read-update-catalog.test.ts:15` and `:69` explicitly keep write rows metadata-only. A later reviewed artifact/admission change must bind applicable required write contracts and cumulative Read observations to the actual served target. Current reports correctly stay claimEligible:false.

These are actual blockers to a public write-profile claim. None is solved by copying development report counts into public admission.

## Important remaining obligations inside already-bounded rows

- **Carrier admission:** duplicate key/name, unknown/forward references, malformed later members and invalid patch pointers must reject the whole carrier before any effect/key claim. Existing malformed alias and wrong-kind label observations do not cover these distinctions. `read-update-values.ts:308` and its key/name map at`:320–345` already implement the required parsing.
- **Semantic retry identity:** object member order and creation defaults, array order, changed guards/attribution, reverse cross-carrier direction and reordered independent sequence members/current operationIndex remain separate observations. These are mandatory normalization laws, not new protocol proposals. Some current cross-carrier behavior occurs in newer diagnostic plans without yet broadening the old row's mapping; audit assertions before declaring it wholly absent.
- **Alias semantics:** original target/miss versus fresh locator comparisons at expiry, authorization and alias-subject operations remain partial. Failure expiry may forget recorded misses; do not incorrectly require a failed disposition's witnesses to survive forever.
- **Durability:** startup/replay and between-member process death are good bounded evidence. They do not establish state+disposition atomicity inside a commit, storage fault recovery, power-loss durability or unsupported replica failover. Determine actual deployment/failure model instead of adding infrastructure just for a test count.
- **Method and Problem coverage:** directory absence is a real gap; not every method/Problem code combination is bound. Restrict table claims to actual observed codes. Owned/schema/policy-dependent errors require their applicable fixtures.
- **Optional History and Transactional behavior:** no Read+Update baseline demand for Events, epochs, receipts, atomic batch, replication snapshots or History lookups. Pins and opaque revisions still have ordinary syntax/equality requirements; opaque storage is not historical resolution.

## Recommended next slice: unconditional carrier admission observations

Exact clauses: `docs/specs/bdp.md:2807–2825` / `#sequence-request-envelope`; normative `read-update.sequence.carrier-rejection`, plus corresponding contextual-validation evidence. Existing runtime: `packages/protocol/src/read-update-values.ts:308–345`, preflight at `packages/protocol/src/read-update-preflight.ts:58`, called before lifecycle submit by `development-authority.ts:197`.

Four small diagnostic scenarios, each with a valid prefix before the invalid later relationship:

1. **Repeated key:** two different create requests share a key. Assert direct400/malformed-request and both identities absent. Reuse that exact key for a corrected request matching neither attempted semantic identity; it must create successfully. This catches capture of either duplicate, not merely one side.
2. **Repeated name:** two uniquely keyed creations repeat a name. Assert both identities absent; corrected names under both original keys must create. To distinguish improperly retained failures from a pure refusal, require both created outcomes and direct state.
3. **Unknown label:** valid prefix followed by a member referencing an undeclared label. Assert direct400/no prefix. Correct the request with changed prefix properties under its original key and a valid local reference under the dependent's original key; assert created/updated result and final original Resource state.
4. **Forward label:** valid prefix, a member referencing a later named creation, then that creation. Assert all possible created identities absent. Reorder/correct with all original keys and changed creation properties, then require intended outcomes/state. The corrected key claims must not have been captured by the rejected carrier.

These are direct HTTP status/problem, no-results/no-state, corrected-key and after-state discriminators using existing request actions. No arbitrary clock, policy, fault hook, new operation, public advertisement or shared-store edit. Scope: four diagnostic files (manifest/catalog/coverage/README); existing runner evaluates authored assertions. Preserve explicit limits for invalid key/name grammar, invalid patch pointers, count limits, static wrong-kind variants and other remaining classes; no whole-row claim or count target. Build then matrix/inventory and original carrier/preflight/HTTP tests, checks, evidence verification and both smokes.

After that bounded slice, prioritize a concrete cumulative HTTP/discovery composition plan and required-contract matrix applicability over indefinite row-count expansion. Runtime fault/admission and configurable schema/policy fixtures should be separately scoped against the intended implementation surface.

No new product decision is required for the recommended carrier laws. Choosing which optional capabilities and administrative configurations the initial public Scope supports is a deployment/product scope decision; it must not be silently decided by omission-count pressure.
