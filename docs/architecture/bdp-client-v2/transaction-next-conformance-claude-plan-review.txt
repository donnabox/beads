## Findings

### 1. HIGH — The "no additional change group" oracle has no world-changing discriminator
**Section:** plan line 34 ("Read this route only while the head is pos-1"), controls 1–3 (lines 102–104), line 114 (exclusion rationale)

**Problem.** `changes/?after=genesis` is read only at head pos-1 (actions 3 and 9), so both reads are observationally identical by construction. The runner aborts a scenario at the first failing action (`runner.ts:637-664` rethrows out of the action loop), so controls 1 and 2 — which make the no-op effectful at action 4 — can never reach action 9. Control 3 only flips the expected tuple from `[["pos-1"]]` to `[["pos-1"],["pos-2"]]`, which proves the assertion is not dormant but not that the route reports a real extra group or advance. Net: nothing in the row shows the changefeed oracle is sensitive to an actual second group. The plan's own standard forbids this ("No 'no group' claim may rest only on a dormant assertion or receipt/Event proxy").

The stated reason for excluding a pos-2 read is misapplied. One-group-per-page (`transaction-store.ts:1683-1710`) is a reason not to *expect* two groups; it is not a reason to skip the read. At head pos-2 with `after=genesis` the page is materially different: `transaction-store.ts:1689-1697` sets `next` non-null exactly when `row.position < head`, so the page returns one group at pos-1 **with a non-null continuation** and `observedHeadPosition: pos-2`.

**Impact.** The row's central claim rests on a self-identical repeated read plus an expectation flip. An owner regression that stopped reporting new groups/continuations on this route would leave every assertion in the row green.

**Fix.** Add one action after action 14 that re-reads the *same* allowlisted route `GET https://reference.invalid/acme/changes/?after=genesis` and asserts: exactly one group at pos-1 (same tuple as actions 3/9), `observedHeadPosition` = pos-2, `/groups/0/previousPosition` = pos-0, and `/next` with bare `exists:true` (no literal equality — the checkpoint is epoch/view-bound). This needs no new route, no continuation fetch, and makes no "two groups per page" claim, so the stated exclusion rationale no longer applies. Re-derive the ledger: 15 actions, 166 total, 159 exchanges, 12 raw HTTP (three POST / nine GET), and update the budget arithmetic accordingly.

### 2. HIGH — The proposed budgets are a planning envelope, not a measured guard
**Section:** plan line 81 and the successor table, lines 83–88

**Problem.** The comparator basis is exactly right (I recomputed all twenty raw slices with the test's own `objectSlices` algorithm): zero-match = **36055 B / 1028 nodes / 142 assertions over 17 actions**, and the two proposed new pin rows are byte- and hash-exact (manifest conflict 29772 / `ba93aea8…`, coverage conflict 5188 / `de9b758f…`). But the per-action extrapolation to 14 actions is ≈29.7 KB manifest, ≈846 nodes, ≈117 assertions, against proposed ceilings of 65536 B (**2.21×**), 2200 nodes (**2.60×**), 220 assertions (1.88×), and 16384 coverage bytes (≈2.5× zero-match's 6520 B coverage row, and above the largest existing coverage row — receipt.pagination at 13057 B).

The prior slice was accepted tight: baseline 377449 + 32768 delta, actual landing at 407227 = **90.9% utilization**. The plan's only mitigation is "stop on overrun"; nothing requires the committed guard literals to be tightened to the measured candidate. The plan also inverts the order the operator's framing allows — it asks root to accept *unmeasured* ceilings up front, where root's existing authority covers accepting *reviewed measured* bounds.

Internal consistency note: at zero-match's ratios (254 B and 7.24 nodes per assertion), 220 assertions imply ≈55.9 KB and ≈1593 nodes. So the byte and node caps can never bind; the assertion count is the only live fence. At receipt.pagination's density (17.2 assertions/action) a 14-action row reaches ≈241, so 220 may itself trigger the stop rule. Realistic range is ≈120–240.

**Impact.** If the row lands near the extrapolation, the accepted guard permits a further ≈35 KB manifest / ≈1350 nodes of unreviewed growth against the same fence — the guard stops constraining the artifact it guards, which is the entire function of the live conjunctive guards.

**Fix.** Split acceptance into two stated stages, both inside existing authority: (a) 64 KiB / 2200 nodes / 16 KiB / 220 assertions are accepted **only as the preflight stop threshold**; (b) the literals committed to `transactional-cumulative.test.ts:835-852` must be the **measured** candidate plus a declared margin reproducing prior utilization (e.g. ≤ 8 KiB manifest, ≤ 128 nodes, ≤ 2 KiB coverage, exact action and assertion counts), with measured values and margins recorded in the report. Say in the plan that the realistic assertion range is ≈120–240 so acceptance is not re-litigated mid-authoring.

*On the operator's second question:* execution limits do **not** rise. Verified unchanged: 63000 ms positive (`transactional-matrix.test.ts:431`), 90000 ms cohort budget (110-111), 120000 ms outer (451), 5000 ms exchange (300), 10000 ms prepare/cleanup (298-299), 2048 request octets / 32768 decoded response bytes (412-421, 428), loader 1 MiB / depth 128 / 100000 nodes / 10000 container entries (`artifact-bundle.ts:17,20-22`) with the 4 MiB exception correctly scoped to `read-update` only (159-164). The 472763 B manifest ceiling stays well under the 1 MiB artifact bound. Per-cohort 19 children / 158 exchanges and 76 / 632 across four runs are arithmetically consistent.

### 3. MEDIUM — Stated allowlist insertion position for the new route is wrong
**Section:** plan line 94

**Problem.** `GET .../beads/new` first occurs in `transactional.batch.rollback`, which precedes the new row in catalog order (catalog index: rollback 6, no-op-entries 14, set.mutation 17 — the plan's insertion point is correct). So the new route's first occurrence is position **7**, after `beads/new`, not "after the existing `events/` route" (position 5). I replicated the matrix test's derivation (`transactional-matrix.test.ts:166-195`), which pins an ordered, independently authored array and feeds `exactMode.routes` order into `exactConfigurationDigest`.

**Impact.** An author following the plan literally writes an 11-entry expected array in the wrong order and a wrong digest preimage. The test catches it, but the natural "fix" — reordering manifest rows or sorting the route list — would violate the plan's own catalog-order insertion rule and its byte-for-byte row preservation requirement.

**Fix.** State the corrected position explicitly: insert `{ method: "GET", url: `${scope}changes/?after=genesis` }` at index 7, between `GET ${scope}beads/new` and `GET ${scope}beads/b`. Retain "recompute the digest from the actual canonical configuration; do not reuse `63421454…`."

### 4. MEDIUM — Two positive-run pins unenumerated, and the new row falls outside the wire-bound loop
**Section:** plan line 70 (file 4 scope), line 94

**Problem.** `transactional-matrix.test.ts` also pins `expect(observed.result.scenarios.filter((s) => s.state === "pass")).toHaveLength(10)` (line 338). The plan gives successors for sessions (18) and children (19) — both correct, since current state is 17 sessions + bootstrap = 18 children (line 340-341) — but never states pass count 10 → 11. Separately, the 2048/32768 per-exchange bound loop at lines 406-412 is scoped to `row.id === "transactional.set.mutation" || row.id === "transactional.set.zero-match"`, so the plan's "all new decoded responses <= 32768B" does not cover the new row unless that filter is extended.

**Impact.** An unexplained failing pin at authoring time, and — more seriously — a wire bound the plan presents as an accepted control that would in fact never evaluate against the new row's exchanges.

**Fix.** Add both to the file-4 change list: pass count 10 → 11, and extend the `newRows` filter (or add a parallel filter) to include `transactional.batch.no-op-entries` so the 2048-octet POST and 32768-byte response bounds actually cover its twelve (or, with finding 1, thirteen) exchanges.

### 5. LOW — Each proposed successor guard has one arithmetically dead conjunct
**Section:** successor table, lines 86–88

**Problem.** Every proposed pair sets the absolute cap to exactly baseline + delta (407227+65536=472763; 60069+16384=76453; 10891+2200=13091), so the second inequality can never fail when the first passes. The live guards keep the absolute cap independent (377449+32768=410217 vs 413696).

**Impact.** The plan requires "both sides of each existing conjunctive guard must be reconciled visibly", but the reconciliation yields one informative inequality where two were intended.

**Fix.** Either keep a distinct absolute ceiling with its own rationale, or state plainly that the absolute cap is retained as a redundant restatement — do not present it as a second control.
