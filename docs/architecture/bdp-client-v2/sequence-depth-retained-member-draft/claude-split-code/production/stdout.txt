## Findings

**1. Low — `packages/server/src/transaction-batch.ts:321‑330`.** The member carrier passed to `prepareDepthCarrier` is a bare object literal (`{kind:"singleton", scope, operations:[op], keys:[key]}`); neither it nor its arrays are frozen, unlike `prepareMixedTransaction` (`transaction-batch.ts:180‑185`) and the protocol-frozen singleton carrier (`read-update-preflight.ts:82‑89`). The literal shape is pre-existing, but this patch makes it load-bearing: the depth fact is now recorded against the wrapper only (`depthRefusals`, line 85) while the owner trusts it for fresh-key refusal (`transaction-store.ts:1163‑1167`). Mutating `member.request.carrier.operations[0].input` after preparation would admit a deep member under a stale "shallow" fact. All holders are source-private, hence Low. *Smallest fix:* `Object.freeze({kind:"singleton", scope: carrier.scope, operations: Object.freeze([op]), keys: Object.freeze([key])})`.

**2. Low — `packages/server/src/transaction-sequence.test.ts:576`.** `expect(f.store.receipt("p", original.id)).toStrictEqual(original)` compares a JSON round-trip (`retainedReceipt`→`parseReceipt`, `transaction-store.ts:931‑934`, identity-projected because the default policy is `all-visible`) against the in-memory object returned by `executeClaim` (`transaction-store.ts:1381‑1406`). Every pre-existing instance of this exact comparison uses `toEqual` (`transaction-submission.test.ts:1644`, `transaction-dependencies.test.ts:263`). `toStrictEqual` additionally fails on any explicitly-`undefined` key or non-plain prototype inside `results` entries (built at `transaction-batch.ts:778`). I could not rule that out statically and nothing has executed this file. *Smallest fix:* use `toEqual`, matching precedent; the receipt-unchanged claim does not need the stricter matcher.

**3. Low (evidence) — `transaction-sequence.test.ts:625‑668`.** The oracle's "no claim/creator fact survives" is only indirectly evidenced. `inspect()` (`transaction-store.ts:2290‑2306`) exposes resources/groups/identities/position only — not `receipts` or `creator_facts` — so `toStrictEqual(before)` cannot see them, and residual `creator_facts` rows keyed by the aborted attempt UUID are invisible to all later behavior. The three `created` outcomes in `reused` do genuinely prove key release (a surviving reservation would project `idempotency-in-progress` via `admitSequence:1979` + `admitKey:1144`). *Smallest fix:* either read `creator_facts` directly through the already-imported `DatabaseSync`, or narrow the stated claim to key release.

**4. Low (selection) — ledger `sourceSelections` for `transaction-sequence.test.ts`.** The ten retained titles omit `"preserves committed prefix and another owner while retracting this attempt's tail on an internal fault"` (`transaction-sequence.test.ts:419`), the closest pre-existing regression to this packet's central new claim (a private 500 after a durably committed prefix). New case 3 covers the same ground, so impact is evidential only. *Smallest fix:* add that title to the sequence regex.

The control/provenance oracles belong to the other scope — flagged, not reviewed.
