## Recommendation and alternatives

Use **multiple ordinary version2 manifests**, each bound by the existing source-private cumulative RU factory, with a small source-private artifact-set index and validator. Execute them through unchanged runner calls and retain the separate genuine reports. Add one private progress record that binds the set, configuration and report ownership; it is not a ConformanceRunResult or a qualifying cohort artifact.

| Option | Assessment |
| --- | --- |
| Normal v2 shards plus bounded private index | Recommended. Existing parse limits, fixture-oracle validation, factory WeakSet provenance, exact execution and per-report digests remain intact. New logic only owns set completeness/uniqueness and real-run association. |
| Add `imports`, file references or segments to v2/v3 executable format | Unnecessary first step. `executable-manifest.ts:293` closes root keys to version/catalog/scenarios. Imports would require new parser, resolution/security/cycle rules, digest semantics and every downstream consumer to understand expansion. No current row needs cross-file action execution. |
| Parse shards then fabricate one combined manifest/bundle/report | Reject. It sidesteps the aggregate parser boundary, cannot truthfully use a single source-byte manifest digest, bypasses WeakSet ownership if structurally forged, and blurs actual run boundaries. |
| Further equivalent compression | May recover a small margin; measure first. It does not provide ongoing capacity for remaining required rows. Preserve oracle meaning and controls; do not trim obligations for space. Raising caps is out of scope. |

This is a transport-test artifact layout change, not protocol batching, target configuration or public evidence admission.

## Private validation and identity contract

Add a narrowly scoped source-only helper (suggested `packages/conformance/test-support/read-update-artifact-set.ts`, plus tests), not a public package export. It composes existing factories rather than implementing a second manifest parser. If a set object is consumed later, retain a private factory brand and immutable detached data; structural lookalikes must not acquire evidence authority.

Inputs: canonical RU/no-History selection, exact index bytes, exact shared fixture bytes, exact coverage bytes, exact declared shard source bytes. Capture inputs once; reject proxies/accessors or use the existing hardened data-boundary helper through an internal export. Never validate a caller object and reread it later. Do not duplicate unsafe/coercive digest checks. Reuse `copySourceBytes`, bounded JSON and existing fixture/manifest validation; source descriptors and keyed source maps require closed, detached data.

Validation before launching a child:

- Index IDs/source names unique and valid; required declared files present; no unlisted supplied file, duplicate or empty shard.
- Each shard independently becomes a genuine `createCumulativeReadUpdateArtifactBundle` result for the **same canonical full selection** and shared fixture. Same catalog digest map, v2, RU profile, no History. Each shard's scenario order equals canonical order restricted to its membership.
- Each scenario has exactly one shard owner. Duplicate ownership is rejected even for byte-identical rows; no last-wins merge or double counting.
- Coverage IDs equal the complete canonical selected required-ID list in order, including inherited/companion obligations after retirements. Every bounded-observation row has exactly one owned scenario and exactly one coverage binding containing its full nonempty ordered action/assertion IDs; normalize both actions and legacy requests using existing semantics, never `(actions ?? [])` as a vacuous fallback; every omitted row has no scenario, empty bindings and wholefalse. No unknown/retired row, orphan coverage binding, omitted-but-executed row or executable row absent from coverage.
- Every prerequisite on every action family is earlier in canonical order, implemented and owned in the same shard. Validate the complete selected prerequisite closure before any child starts; reject cross-shard or missing-plan references explicitly. The validator, not the runner selection API, owns this preflight. Do not duplicate prerequisite scenarios or treat another run's success as an executable dependency. Any future need for shared dependency execution is a separate plan.
- Shared fixture identity/capabilities and every applicable fixturePointer remain validated by each ordinary bundle. No target-produced value becomes an authored oracle through this layout.

Compute—not caller-declare—a detached canonical set descriptor and SHA256 from index digest, canonical exact catalog-file digest map, coverage digest, shared fixture digest, and ordered shard entries `{id, manifestDigest, scenarioIds}`. Expose per-shard bytes/digests/budgets in the private progress record. A set digest is additive provenance, never a substitute manifest digest. Individual manifest digests identify exact source bytes. Filenames also occur in the index, so renaming one changes the index/set identity while leaving an unchanged manifest’s digest intact. Preserve original report/artifact digests in every association.

The full required inventory is always canonical. For each required ID, the set gives either one owned plan or an explicit absence. Changing the index or coverage to omit work changes the set binding and cannot yield a full claim.

## Actual execution and reporting

Make the smallest app-test adapter change: parameterize the existing `run` path with an already validated shard source/bundle and common fixture input. Preserve existing single-manifest countercontrol calls and assertions; do not duplicate the installed launcher/exact client/HTTP harness. New controls can select their owning shard. Extract a helper only where necessary to reuse actual execution; no broad harness refactor.

Run the **baseline unfiltered**, preserving today’s genuine report of all applicable catalog rows, including explicit missing-plan harness-error/not-implemented results. Run only the continuation with exact owned IDs through scenarioSelection. This is smaller than changing the baseline’s existing absence assertions. The canonical full catalog still resides in each bundle. The set validator preflights prerequisite closure; unchanged runner behavior then requires same-call prerequisite success. Catalog order remains within each shard. Cross-shard index order is scheduling, never a normative operation ordering assertion.

Association rules are asymmetric and explicit: baseline requested selection is absent, selected/result IDs equal the complete applicable catalog list in order, baseline-owned rows must pass, and every other row must be harness-error/not-implemented with no exchanges in a successful diagnostic run. Continuation requested/selected/result IDs equal its owned canonical subset exactly and each must pass. There must be no missing, duplicate or extra result. Each globally owned required ID has exactly one actual owning report row; C additionally has a baseline not-implemented witness, which is not a contradiction or double credit. Each globally unplanned required ID has its actual baseline missing-plan witness plus coverage omitted/wholefalse, never a fictitious non-not-implemented result. Applicable optional/companion catalog rows are enumerated separately from the canonical required denominator; missing optional rows cannot inflate it. A failed/aborted baseline may contain not-run instead: retain it as failed/unobserved evidence and emit no successful-set summary.

Run the two shards sequentially under one existing90-second cooperative aggregate budget and120-second outer backstop; retain5-second exchanges and30-second focused tests. Do not reset90 seconds per shard or launch concurrent authorities to hide runtime cost. Check abort before each shard’s bootstrap, before every new scenario launch, immediately after a launch completes inside its cleanup-protected block, and after return before writing a successful diagnostic progress record. The existing launcher has a ten-second bound but no AbortSignal; cancellation during launch must await that bounded result, close any acquired child, then fail. Reuse existing prepare/cleanup and drain paths, without launcher redesign or an abandoning race. The90s boundary requests cooperative cancellation; cleanup may consume bounded drain time under the unchanged120s outer ceiling. Record any unrun shard after failure/abort as unobserved, never as absent-but-passed. A slow/failing run fails qualification; measure before proposing scheduling changes.

The set wrapper must compare the second returned bootstrap’s branded configuration and actual configurationIdentity with the first returned bootstrap, not infer equality from common input. One shared served-configuration baseline must also be checked against **every actual scenario instance in both shards**, reusing `bindServedProfileConfiguration`/`assertSameServedProfileConfiguration`. Bind Scope/profile/History/sourceCommit, installed payload/contract/policy/auth identities and the shared fixture digest/capabilities. Also compare the actually observed runtime configuration identity captured today. Stable canonical Scope does not require sharing a mutable database: existing per-scenario fresh authorities and physical listener ports remain legitimate, with actual instance receipts retained. Port/directory are not configuration identity fields (`installed-reference-configuration.ts:175–185`). Do not mix separately observed policy/schema cohorts into this same-config set.

Exact route tables retain the existing bounded construction **per shard**: action-derived raw HTTP and fixed-client GET routes, plus the common nine exact operation POST routes (sequence and eight singletons). Those mandatory directory operation routes are intentionally common even when a shard does not call all nine; this is not a wildcard or a promise that every permitted route was observed. No operation-route derivation refactor is required. Unused fixed fixture GET bindings remain denied. Different shard route sets generally produce different digests, but inequality is not an invariant when the actual configurations are equal. Bind each report to its own captured exactConfigurationDigest; do not force a common union wildcard allowlist or relabel route digests. Same served configuration and same exact client route configuration are distinct facts. Known dynamic Resource captures stay within the existing route validation. Preserve existing digest pins when their inputs remain unchanged; remeasure both baseline pin sites and establish the continuation’s exact pin from its actual captured route table. Comparator6f adds no routes, so it does not itself justify changing the baseline pin. A changed fixture alone also does not necessarily change the exact-route digest. Negative controls must reject a report associated with a different route configuration rather than merely require the two valid hashes to differ.

The new private progress record contains:

- literal claimEligiblefalse, set/index/catalog/fixture/coverage digests, exact source and measured installed configuration baseline;
- per-shard source/digest, selection mode, requested IDs if any, actual selected/result IDs, actual report digest/reference, exact route digest, actual instance receipts, outcome/abort/cleanup state, elapsedMs and budgetRemainingMsAtStart;
- all canonical required IDs, each mapped to its single actual report row or an explicit unobserved/unplanned reason;
- distinct counts for authored, observed pass/fail/not-run, reviewed whole, and currently uncovered. Whole credit needs both a reviewed binding and an actual passing row at the bound source/configuration. Partial rows do not become whole merely because their shard passes.

Do **not** flatten these into a fabricated ConformanceRunResult, add a public report version, or copy old observations into a new run. Exact child reports remain the evidence. The private summary can point into them and machine-check uniqueness/completeness; it cannot manufacture successes or applicability. Unknown/missing reports fail set completion. Before writing any successful set summary, verify all report/source/catalog/fixture/route/configuration associations and every existing supplementary assertion: baseline-specific sequence32/33 and diagnostic bounds remain on its real report; generic authored/serialized body limits, source identity, session cardinality and credential exclusion apply to both. Do not inherit the old optional JSON write-before-assertions ordering. All child cleanup must have completed, all authored rows must pass, and every child/set claimEligible must be literalfalse. Preserve actual child reports; the additional summary contains bounded non-secret metadata/references, never resolved Authorization, tokens or arbitrary child stderr. Failure records can be written separately and clearly labeled. Countercontrols remain diagnostic runs with their own changed source/fixture digest, not mixed into the positive progress record.
