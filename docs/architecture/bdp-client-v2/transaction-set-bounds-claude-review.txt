## Findings

### 1 — LOW · incomplete guard · `packages/server/src/transaction-batch.ts:463-475`

**`receiptProblem` hardens three of the four required receipt fields: `code` is unchecked at runtime and typed as the Read+Update superset, and `status` is range-checked where the receipt form is enumerated.**

`$defs/receiptProblem` requires `[type, code, status, retry]`, restricts `status` to `[400,403,404,409,413,422]`, and restricts `code` to the 13-member `receiptProblemCode`. The guard checks `type`/`retry` for presence and admits any integer `status` in 100–599 — 594 values, 6 of them legal — and never looks at `code`. Statically, branch 1 types `code` as `ReadUpdateProblem["code"] | "cardinality-violated"`, i.e. the 31-member `readUpdateProblemCode`, so 18 codes that are illegal in a receipt (`rate-limited`, `revision-unknown`, `idempotency-conflict`, `resource-pruned`, …) type-check. There is no schema validation on the write path: `transaction-store.ts:1016` puts `problem: result.problem` straight into `json(receipt)`.

**Failure scenario:** an evaluator edit returns a failure with `status: 500`, or with `code: "rate-limited"`, or with `code` absent. All three pass `receiptProblem`, and the terminal receipt is persisted schema-invalid under the idempotency key and replayed from there — the exact outcome the guard exists to prevent. Unreachable through any present path (both evaluators route every failure through `parseReadUpdateProblem` over closed tables), which is why this is LOW — but that is equally true of the three fields the guard *does* check, so the asymmetry has no justification. The progress note's "refuses missing required receipt fields" is literally false for `code`.

**Fix:** add `code` to the guard (membership in the receipt code set) and replace `100 ≤ status ≤ 599` with the six-value enum; narrow branch 1's `code` to the receipt subset so a new return site cannot name a Read-only code either. Extend the probe family from `["type","status","retry"]` to include `code`.

### 2 — LOW · test masks the behaviour it appears to prove · `packages/server/src/transaction-set.test.ts:928-929`

**The malformed-output probes reopen the store before reusing the key, so they cannot distinguish live retraction from startup sweep — and the report attributes the retraction to the reopen.**

The integrity `Error` is a clean non-SQLite rollback, so `atomic` does not fence (`transaction-store.ts:281-303`: `committing` false, `cleanRollback` true, `sqlite` false → plain rethrow) and the `catch` at `:1068-1079` deletes this execution's pending reservation in-process. The key is immediately reusable; `f.reopen()` at `:929` is dead weight. Report F1's "successful valid failure execution with the same key after reopen retracts the interrupted pending claim" misattributes the cause. Separately, `f.owner.inspect()` (`transaction-store.ts:1518-1534`) returns resources/groups/identities/position and no receipts, so `:927` proves only that no graph effect survived; the "no invalid terminal receipt" property rests entirely on the later re-admission succeeding.

**Failure scenario:** a regression that drops the `cleanupThenThrow` delete — stranding the idempotency key until the next process start, i.e. an indefinite `idempotency-in-progress` for that key — passes all three probes unchanged, because the reopen performs the retraction the live path should have.

**Fix:** before reopening, assert the same key is immediately re-admittable (`f.admit(operations)` returns `kind: "owned"`, or run the valid failure directly); keep the reopen afterwards as a separate durable-replay assertion.

### 4 — LOW · test coverage · `packages/server/src/transaction-batch.ts:55, 524-530`

### 5 — LOW · claim wider than the probe · `docs/design/transaction-implementation-progress.md:813-814` (and report F1)

**"Compiler probes require type, status and typed retry on both failure branches" — the five negatives probe only the operation-local branch.**

All five derive from `type Valid` (`transaction-set.test.ts:954-960`), which carries `code: "revision-mismatch"` and `operationIndex: number`, so only branch 1 is a candidate. The property does hold for the limit branch by construction, since both branches now intersect `BatchProblem` — but note branch 2 previously used `ReadUpdateProblem` directly, which already required `type` and `retry`; its one genuinely new constraint is required `status` (it was `status?: number`), and that is precisely what nothing probes.

**Failure scenario:** an edit that reverts branch 2 to `ReadUpdateProblem & {…}` re-admits a `limit-exceeded` problem with no `status`, which `$defs/receiptProblem` requires, with no compiler or runtime objection and a green suite.

**Fix:** add `Omit<WholeLimit, "status"> extends Failure ? … : …` (plus `"type"`/`"retry"`) negatives, or narrow the sentence to "probed on the operation-local branch."

### 6 — LOW · materialization note omits the first reachable ceiling · `docs/design/transaction-implementation-progress.md:826-831`

**The honest gap note states the projection *at* the cap but not the point at which materialization first becomes impossible — which is half the cap, and lives only in the log directory.**

The note gives 4096 × 262,144 = 1,073,741,824 bytes against an unstated SQLite ceiling (a 7% overshoot). It does not mention that `stringifyJsonValue` → `transactionStorageText` → the single `receipts.receipt` string hits V8's `MAX_STRING_LENGTH` of 536,870,888 code units first: 2048 × 262,144 = 536,870,912 already exceeds it, and with the measured 262,196-byte entry overhead the real threshold is below 2048 matches. Both numbers exist in `materialization-limits.log` and `report.md`, neither in the repo.

**Failure scenario:** a future reader sizing against the note treats 4096 as the operative bound and the GiB figure as the ceiling, when a ~2048-match set already throws `RangeError: Invalid string length` inside `atomic` — clean rollback, pending reservation deleted, caller gets an internal error with no receipt and no refusal Problem, repeatably. That is the single most useful number for the separate bounded-delivery design the note defers to.

**Fix:** one sentence in the note recording the V8 string ceiling and the ~2048-maximum-sized-match threshold next to the 4096, i.e. the prior review's "state the reachable receipt ceiling" asked for the *first* ceiling, not the one at the cap.
