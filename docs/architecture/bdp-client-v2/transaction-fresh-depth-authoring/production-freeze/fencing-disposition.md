# Explicit maintenance malformed-receipt fencing disposition

**Recommendation: accept and document the narrow error-class change; no mandatory production repair is established.** This is a source-based technical disposition by the implementation author, not an independent code council or an executed corruption test. All eight production hashes were independently rechecked against production-freeze/source-binding.json (4b240cbe) before this report. The complete actual Claude production output was read; its no-blocking-defect verdict is not the basis for this conclusion.

The change is real. `transaction-store.ts:461–463` parses receipt text with native JSON.parse. The new sweep553 calls it inside maintain560–562 → enter384–393 → atomic407–438. A malformed JSON text produces SyntaxError. If rollback is confirmed clean and COMMIT was not attempted, atomic rethrows that original error: it does not set ownerFailure, close the owner, clear its timer, or revoke its leases. The earlier SQLite JSON predicate raised a non-constraint SQLite error, which atomic432–436 classified as requiring fence. Therefore an explicit maintain() call can now fail while unrelated subsequent owner operations remain possible. Do not describe every malformed-persisted-data path as sticky-fenced, or say that all exception classification was preserved.

The safety boundary retained is transaction outcome certainty, not a universal data-corruption quarantine. atomic433–436 still fences uncertain COMMIT, failed/unconfirmed rollback and non-constraint SQLite failures. All sweep mutations, including prior rows' compaction/deletion and Snapshot expiry, are rolled back together when parsing fails; there is no successful partial sweep, zero-count success, skipped malformed row, key deletion compensation, or receipt replacement. The caller receives the actual failure. This argument does not require a subsequent timer tick.

The timer and startup cases remain stronger. Background maintain failure at1443–1463 sets maintenanceFailure, revokes leases, clears the timer, closes the database and marks closed regardless of error class. Startup sweep623 is inside provisioning/recovery atomic; catch626–630 closes the database and prevents returning an owner. Existing transaction-store.test.ts:889 and3329 test background failure/closed-owner observability. These are source facts and existing tests read here, not newly executed evidence.

There is no existing general invariant that every malformed persisted receipt fences synchronously. disclosedReceipt923, expireRow472, retainedReceipt931, direct admission1142/1157/1167 and execution1224 already use the same parser. Plain application/data-validation errors after confirmed rollback are intentionally rethrown without fence. The parser is a cast, not a complete persisted-receipt schema validator. Accordingly the broader claim “malformed persisted data is uniformly sticky-fenced” was already false. The new filter also is not an opportunity to promise behavior for every valid-JSON but invalid-receipt shape (for example null); those are outside the admitted persisted shape and remain errors where accessed.

The relevant normative requirements are durability and exactly-once retained state, not a prescribed private shutdown policy: spec3367–3401 requires durable disposition/claim recovery;3880–3884 requires serializable Scope outcomes;3896–3903 requires one terminal receipt/replay;3938–3971 binds admission and Resource/group/receipt commit atomically and excludes stale ownership. No inspected clause mandates that a synchronous private maintenance parse error permanently stop all unrelated serving. A malformed stored receipt is not made valid by this change: accesses that need it still fail rather than silently treating the key as unknown or fabricating a receipt. Continuing unrelated reads after a known-clean rollback is not, by itself, evidence of violating those laws. This is not a claim that arbitrary disk corruption preserves all availability/recovery obligations.

Accept a precise clarification of plan-v2 P1: **atomic transaction/rollback boundaries and uncertainty fencing are unchanged; explicit maintain() of malformed receipt JSON now propagates the JS decode error after confirmed rollback without the incidental SQLite-error sticky fence. Background failure and startup closure remain unchanged.** No catch-and-skip is acceptable. Adding a special fence around this filter would restore the incidental historical outcome but introduce a new per-site corruption classification inconsistent with sibling decode paths; it is optional hardening, not required by a demonstrated invariant in this slice. A future uniform corruption policy should be scoped separately rather than inferred from this SQL-to-JS repair.

Informational findings remain accepted separately: sparse arrays are outside both parsed-record operands' dense JSON domain; filtering all owner-null rows and parsing available receipts twice changes constant-factor maintenance cost and requires actual bounded validation observations, not a fabricated performance claim. No new source/test changes, product execution, or user decision is requested.
