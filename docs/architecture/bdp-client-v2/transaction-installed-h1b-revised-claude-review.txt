# Remaining concrete implementation blockers

## F1 · HEAD-receipt observation is unauthorable: the client lane accepts only `json-*` assertions — Blocker

**Location:** `packages/conformance/src/executable-manifest.ts:1300-1309` (`"non-HTTP actions permit only JSON assertions"`), `:254` (`json-schema` is `{id,kind,schema}` — no pointer) · plan §Four partial observations ("Receipt readable: … HEAD bodyless with required context") · plan §Receipt authority item 4 ("Preserve actual status, response headers, body octets/text … in the bounded **internal** observation/ledger").

`parseProgrammaticAction` rejects every assertion whose `kind` does not start with `json-`. So a `client` action can never carry `body-absent`, `header`, `header-tokens`, `media-type`, `status` or `wire-not-contains`. The receipt GET/HEAD must stay on the client lane (its URL is a runtime capture, so an `http` action would hit `prepareExactRequest` → `validateExactRunConfiguration` against the base routes at `runner.ts:1033`/`:1470` and fail `exact-configuration`). The plan's projection is specified as `{status,body,…}` and puts headers/body-octets in the *internal* ledger — which leaves no authored path to assert "HEAD bodyless" or "required context" headers. The same restriction means an unpointered `json-schema` on a receipt GET validates the whole projection, not `/body`.

**Impact:** row 3's HEAD half, and any header/context assertion on a receipt read, cannot be written. Discovered only after the interceptor exists.

**Fix:** pin the projection's closed shape in the plan — `{status, headers: {<lower-case>: string}, body, bodyPresent, bodyOctets}` — and state that receipt assertions are expressed as `json-pointer`/`json-equals`/`json-array-*` into it (`/status`, `/headers/x-bdp-…`, `/bodyPresent`, `/body/status`), with `json-schema` either applied to a projection-wrapper schema or performed internally by the ledger. Keep the existing `/status` and `/body/status` pointers valid unchanged.

## F2 · The private interceptor's dial escapes the target's abort and drain accounting — Blocker

**Location:** `packages/conformance/src/raw-http-scenario-target.ts:72-79` (`active`), `:81-101` (`close` aborts `ending.controller`, then `await Promise.allSettled([...ending.pending])` before `ending.close`), `:256-269` (`dispatch` is the *only* place that ANDs the request signal with `session.controller.signal` and registers the operation in `active.pending`) · plan §Private receipt dispatch ("Preserve current preparation/cleanup abort and pending-operation settlement, **including requests created by this private interceptor**"; snapshot contents = "actual dial route, immutable logical/physical binding, credential resolver and fixed raw executor options").

The plan has the runner build its own executor via `createRawHttpExchangeExecutor(dialRoute, …)`. That bypasses `dispatch` entirely, so the dynamic receipt socket is neither aborted by `session.controller` nor awaited by `close()`. The enumerated snapshot contents carry no session abort signal and no registration hook. The plan's generation/`after close` checks guard request *start*, not an in-flight request; `target.close()` (the emergency path, and `harness.cleanup`) can tear the child down with the receipt socket open.

**Impact:** the stated settlement guarantee is not implementable from the stated snapshot; abandoned sockets and non-deterministic cleanup causes on the abort/timeout controls the plan makes mandatory.

**Fix:** add two items to the private session snapshot and name them: the session's abort signal (to be ANDed into the dynamic request signal, as `dispatch` does) and a `register(operation)` hook that inserts into the same pending set `close()` awaits — or have the holder wrap execution so the runner still owns configuration, observation and recording while the target owns dialing lifetime.

## F3 · Receipt authority cannot be registered where the plan implies; the source wire evidence is gone by then — Blocker

**Location:** plan §Receipt authority items 1 and 6 · `packages/conformance/src/runner.ts:1026-1311` (`runRequest` — `response`, `response.wireResponseBytes`, `capturedExact` are function-local), `:1305-1306` (captures store only the resolved string into `bindings`), `:1307-1310` (`priorResponses` retains only `{status, headers}`), `:840-852` (interception point, which runs on a *later* action).

Item 1 requires the ledger to record "original action/response identity, source JSON pointer, canonical URL, original logical/physical binding and credential/view association"; item 6 requires "the source response's immutable wire identity/digest and pointer link" to be checked before assertions count. None of that survives past the `completed`/`missing` POST's `runRequest` frame. By the time the interceptor sees `input.binding === "receipt"`, only the captured URL string exists. The plan never names the registration seam, and §Owned files only says "runner.ts interceptor/context/ledger/recording".

**Impact:** the countercontrols "wrong source pointer/status/body", "substituted prior response" and "source-response digest mismatch" have nothing to compare against.

**Fix:** name `runRequest`'s capture loop (`runner.ts:1305-1306`) as the TX-branch registration seam and enumerate what is captured there from the live response: action id, canonical response URL, `/id` pointer and value, status, a digest over the decoded body (or over `wireResponseBytes`), the exact-observation reference, and the current session's logical+physical binding and credential handle.

## F4 · The permission-swap control is unsatisfiable as written

**Location:** plan §Installed factory ("Real permission swaps between two tokens of one principal must change actual authentication/policy/runtime identities and observed POST authorization") · `packages/server/src/transaction-runtime-configuration.ts:208-221` (`associations` is the whole sorted credential set; `authenticationIdentity` digests it), `:325-342` (`policyIdentity` and `runtimeConfigurationIdentity` both include `associations`) · `packages/server/src/transaction-http.ts:250-252`, `:287-292`.

In M1 all three identities are functions of the credential *set*, not of which handle a request presents. Selecting a second handle at request time changes only the observed 200/403 — every identity stays equal. Only a *different configuration* (different credential set) moves the digests, and that runtime then fails the bootstrap/prepare expected-versus-actual equality the plan mandates on every prepare and reopen, so it needs its own expected baseline.

**Impact:** as read literally the control can never pass; as read charitably it needs a second baseline the plan does not provide, and the adjacent negative control ("altering only one returned identity while holding the rest fixed is an injected mismatch") depends on which reading applies.

**Fix:** split it. Within one configuration: only POST authorization varies (operator 200 vs read-only 403), identities stay equal — that is the positive policy observation. Across configurations: a swapped credential set must change `authenticationIdentity`, `policyIdentity` and `runtimeConfigurationIdentity` together, validated against its own recorded baseline, with `assertSameServedProfileConfiguration` refusing the cross-pairing.
