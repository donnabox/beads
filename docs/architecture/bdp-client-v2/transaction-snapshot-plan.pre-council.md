Plan only, 2026-10-13. No runtime, spec, schema, public admission or evidence edits. Council review is required before implementation.

## Intended result and limits

Create and durably serve a complete finite Snapshot of the current fixed all-visible Scope, with independent Bead and Link streams anchored to exactly one owner prefix. A client can reconstruct a replica from both streams and resume the existing finite changefeed at the manifest checkpoint without a gap. Captured bodies, identities, revisions, page boundaries, checkpoint and expiry survive mutation and ordinary/crash restart. No second graph owner, all-graph JavaScript array, ordinary collection cursor substitution or Snapshot-dependent write admission.

The first implementation remains source-private and explicitly partial. It does not activate Transactional discovery, optional History, SSE, erasure administration, mutable authorization views or a complete profile claim. Actual empty erasure ledger is valid only for this existing no-erasure installation. Public discovery and complete minimum handling remain separately gated. Minimums on retained Snapshot targets have an unresolved meaning identified below; do not quietly choose it.

## Existing seams and missing work

`transaction-store.ts` owns one locked SQLite connection, resources, identities, durable groups, receipt pages, epoch and current position; synchronous guarded entries reject reentrancy, leaked callbacks and sticky failures. Groups are retained without pruning. Thus a valid capture checkpoint can continue through the entire current retention horizon without per-Snapshot pins or any new replay log. Genesis remains the oldest legal cursor (`minimumReplayPosition` locally `pos-0`), not the most recent Snapshot position. Aliases never enter Snapshot streams or advance its anchor.

`withRead().resources()` builds an entire array and is unsuitable for bounded capture. `transaction-read.ts` ordinary pagination is also unsuitable: query-selected in-memory cursors do not supply this complete durable graph promise. `transaction-changefeed.ts` already provides the actual Scope/epoch/view-qualified checkpoint codec and complete group renderer. Reuse `transactionCheckpoint`, including genesis at zero; do not derive a new token spelling from examples.

`transaction-service.ts` has tracked finite waits/drain and paired owner observations. `transaction-http.ts` supplies trusted credentials, raw method classification, JSON negotiation and conditional response handling. Reuse these rather than adding a new listener. `transaction-runtime.ts` remains the only owner factory. Snapshot persistence/schema/versioning is genuinely missing; no durable installer or capture API already supplies it.

## Minimal private representation and lifetime

Propose a separate private `transaction-snapshot.ts` for target parsing, immutable body types, page URL construction and bounded projection/integrity checks; persistence stays in the existing store. No generic pagination framework and no public exports.

Add locked metadata and captured-row tables, conceptually:

- Snapshot row: random opaque identity, Scope epoch/view, position/checkpoint, fixed creation/expiry instants, recorded per-stream counts/bytes/page boundaries, and the actually projected ledger (empty here).
- Captured Resource rows: Snapshot identity + kind + ordinal + canonical identity + exact bounded wire body; unique identity per Snapshot. Store only the immutable projected records, not a reference to mutable resources.
- Recorded page ranges or equivalent deterministic ranges fixed by the captured configuration. Tokens bind Snapshot/kind/range; do not recalculate ranges from current resources or changed limits on reopen. Initial ranges and absolute next URLs are part of the immutable manifest.

Capture occurs inside one existing owner entry and SQLite transaction, with no await or external callbacks. Obtain context, exact graph rows and checkpoint together. Use a bounded rowwise SQL cursor/keyset traversal confined to that entry; precheck per-row encoded size before loading a potentially corrupt body. Apply the existing lossless JSON/value codec and Resource projection rules; no JSON.parse/stringify replacement that rounds literals. Validate canonical/local identity conversions and inline-owned consistency without confusing the two ID forms. No open SQL iterator or mutable row escapes. Persist the complete capture before returning any usable handle; failed capture rolls back all its rows and leaves graph, receipts, keys, positions and groups unchanged.

No historical preimages, new Resource revisions, group or Events are produced by capture. The Snapshot table is retained read state. Reuse the owner's atomic-failure fencing and original/cleanup-cause preservation. Required SQLite journal recovery precedes configuration comparison; do not reintroduce the defective read-only preflight. A private format bump/refusal is required unless root chooses another reviewed compatibility path; no migration/reseed. Incompatible valid old files remain byte-identical after refusal.

Expiry is fixed at capture, not renewed by HEAD, page reads, manifest refetch or restart. Proposed private lifetime is five minutes, persisted as installation configuration; this is a reference capacity choice, not a normative duration. Expiry cleanup removes bodies but retains sufficient bounded disposition information to distinguish an authorized expired issued handle from a never-issued handle during the documented private retention horizon. **Do not silently turn a known expired handle into unknown while promising a stronger distinction than storage preserves.** Council should approve a concrete disposition retention policy before implementation; no per-client immortal registry. Missing/corrupt recorded rows before expiry are service failure and fence the affected Snapshot/store as appropriate, never truncation or 410.

## Bounded materialization proposal

A complete graph is not bounded by the per-transaction matched-Resource budget. Do not use M32/M64 or Event E256 as a Snapshot resource ceiling. Capacity limits must be explicit private installation limits, not new protocol limits or excuses to publish incomplete streams.

Propose initial development capacity of 4,096 captured Resource rows and 32 MiB total encoded records per Snapshot; at most eight live handles and 64 MiB aggregate captured records. These are conservative testable implementation limits for this private server, subject to council. A larger Scope or exhausted allocation fails creation as an ordinary service limitation before any handle escapes; it must not silently select a prefix, evict an unexpired promise, or invent a mutation/Selector problem. No new 413/503 code is inferred. Bodyless 500 is the existing honest private unsupported/service path until an applicable normative refusal is identified. Capacity and retention cleanup must not become write admission policy.

Use the installed Resource page maximum as a count ceiling and additionally bound encoded bytes per typed stream page, proposed 4 MiB. A page must fit at least one legal installed Resource; prove that inequality from the actual installed representation/source URL bounds, including lossless serialization and inline-owned bodies. Manifest combines two first pages, so bound it independently: at most 8 MiB plus ledger/identity/context/checkpoint/expiry/URL framing under the current empty ledger. Include worst-case escaping of URLs and headers, not just stored JSON lengths. Measure actual final wire bytes before retention and delivery. Show arithmetic below pinned Node 24 string ceiling without huge allocation; parsed object/heap overhead requires small representative measurement, not a universal bound claim.

Capture is rowwise and bounded in total work; no SELECT-all plus later truncation. Ordinal continuity, row counts, kinds, unique identities, page boundaries and all recorded next links are checked. Refetch does not recompute or repair corrupt data. The total captured graph can exceed one page and one transaction, so tests must establish both independently. Page maximum/configuration must be persisted and compared before BDP maintenance on reopen, including retained expired captures.

## Serving context, minimums and unresolved decisions

Creation GET with a complete valid minimum tuple can reuse the existing finite wait loop: each attempt checks that tuple and captures only an eligible owner prefix. HEAD creation makes the same auth/epoch/view/minimum/service decision but returns no usable handle; it may use bounded counts/size checks rather than persist a copy. A HEAD preflight is not a reservation guaranteeing a later independent GET. Waits never hold SQLite entries; existing finite deadline/cleanup semantics apply. Partial/unknown opaque tuples retain current explicit gaps.

For ordinary retained GET/HEAD, authorization and handle disclosure happen before exposing metadata; recorded epoch/view/expiry/integrity fences precede conditionals. Body records, checkpoint and manifest anchor remain original. A same-entry current observation can accompany the retained body internally, as with receipt pages; **wire position semantics must be resolved as follows before implementation claims cover this case.**

**Question S1-Q1:** `:5779–5785` says a minimum read returns a representation at or after its minimum, while `:5899–5931` requires an immutable older manifest/stream anchor. Does a retained Snapshot response use its captured position for `BDP-Scope-Position` and compare the minimum with that anchor, or current serving position after reauthorization with the original anchor in the body? What response is required when minimum is later than immutable anchor but not later than current head? Waiting cannot make that Snapshot newer. Existing Resource-query context machinery and example fixtures are not a normative ruling. Until settled, support creation minima and retained requests without minima only; explicitly refuse unsupported retained minimum controls after nondisclosure and before expiry/conditional shortcut, without inventing catch-up-timeout proof. This is an unqualified private gap, not a full Snapshot contract.

**Question S1-Q2 (implementation policy, not wire semantics):** how long must this private service retain expired issued-handle disposition metadata? The table distinguishes authorized expired from unknown, but does not specify a minimum forgetting horizon for Snapshot identities. Prefer a bounded documented reference policy approved by council, and avoid claiming permanent expired-handle recognition. A root-selected local convention is sufficient if consistent with current law; no new normative text is proposed.

Malformed canonical query mappings also need explicit reference convention (as finite Events/G1), not a universal rule inferred from a fixture. Canonical query namespace should distinguish creation, manifest and stream targets; reject repeated/extra/conflicting parameters without allocation. Tokens are selectors, not credentials. GET/HEAD auth, method-first bodyless 405, unknown/foreign nondisclosure and Accept negotiation reuse existing established routing. Current Origin refusal means CORS remains unimplemented, not implicitly satisfied.

## Executable done-when predicates

1. Empty Scope, multi-page Beads, multi-page Links and uneven stream exhaustion produce schema-valid manifest/typed pages with absolute bound continuations; no transient `links` expansion. Includes compiled owned-Link fixture and legal lossless numeric values.
2. Mutations between creation and every next/refetch leave captured body/revisions/checkpoint/expiry byte-equivalent. Captured deleted Resources remain present; later creates absent. Aliases absent and alias changes do not affect anchor. Both streams are one prefix, not separately captured times.
3. Complete inline-owned/first-class and local-endpoint checks pass. Negative replica controls alter one owned Link, remove an endpoint, duplicate/omit a page/member or mix two valid Snapshot identities: replica rejects without publishing graph/checkpoint. A simulated publication failure leaves old replica generation and checkpoint intact.
4. Stage both streams, publish atomically, then apply finite G1 groups strictly after checkpoint, including a concurrent post-capture commit and owned update/delete. Final replica equals independent canonical live reads after catch-up. Feed checkpoint comparisons use equality/opaque tokens, never client arithmetic. Wrong epoch/view fails; no skipping to head/minimumReplayPosition.
5. Manifest GET/HEAD refetch preserves identity/initial page plans/expiry. Creation HEAD allocates no usable handle or durable graph effect; unsupported methods return bodyless 405 Allow GET, HEAD even for unknown shapes; valid read authentication remains enforced.
6. Expiry, unknown handle, foreign principal/view and corrupted unexpired page take distinct permitted paths. Conditionals cannot bypass fences; 304/412 context and HEAD bodylessness tested. Promise survives ordinary reopen and actual hot-journal crash recovery; pre-expiry corruption is 500/service failure, not 410 or silently empty success.
7. Capture failure before persistence and injected uncertain commit/rollback obey existing owner fencing; no partial handle, leaked capture rows, key capture, revision, group or Events. Successful capture does not alter mutation receipts or positions. Reopen resolves durable capture disposition without auto-generating a replacement.
8. Resource/byte/page/aggregate capacity boundaries fail before handle disclosure; unexpired handles remain usable under pressure. Corrupt oversize persisted lengths are checked before JSON load. Prior-format/config mismatch refuses before BDP maintenance with actual prior-file byte comparison, plus hot-journal incompatible configuration behavior.
9. Creation complete minima use original finite deadline, current attempt context and schema-valid existing problems. Retained minimum Q1 remains visibly unsupported until settled. HEAD and conditional cases have equivalent ordering. HTTP disconnect behavior is reported honestly: current runtime does not propagate all request signals; finite tracked work drains rather than claiming prompt cancellation.
10. Fresh packed installed fixture, after H1 integration, follows actual wire URLs through both streams/feed and durable restart, with bounded observations and negative controls. Workspace-only tests do not count as installed evidence. No row is passed by copying narrative fixtures or synthetic responses; remaining policy/erasure/minimum variants remain missing.
11. Build before emitted tests; focused Snapshot + receipt/Event/feed/owner fault regressions, typecheck/boundaries/format/lint, installed/public smokes and unchanged Read evidence verification. External logs include exact source, tests, exits, time and cleanup. No immutable old evidence reseal.
12. Clean frozen candidate reviewed natively and externally before root integration; no public Transactional claim until all other required routes/Directory/consistency/sets/sequence/policy obligations are met.
