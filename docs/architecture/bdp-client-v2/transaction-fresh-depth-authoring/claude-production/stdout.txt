## Findings

### 1. (Low) Malformed receipt JSON in `sweep` no longer fences the owner

**Location:** `packages/server/src/transaction-store.ts:550-553` (new JS filter), interacting with `atomic` at `transaction-store.ts:415-438`.

**Defect:** The old predicate `json_extract(receipt,'$.detail')='available'` raised `ERR_SQLITE_ERROR` on an unparseable receipt. In `atomic`, `sqlite && !constraint` is true for that error, so the owner was fenced (`fence(cause)` at :436 — `ownerFailure` set, timer cleared, leases revoked). The replacement `parseReceipt(stored.receipt)` at :553 throws a plain `SyntaxError`: not a SQLite error, rollback is clean, so `atomic` rethrows at :437 **without** fencing.

**Impact:** Narrow. The timer path (`:1443-1461`) still closes and sets the sticky `maintenanceFailure`, and the startup path (`:623` inside the provisioning `atomic`, catch at `:626-630`) still closes the db and rethrows. The only changed exposure is an explicit `maintain()` call: a corrupt receipt row now surfaces an error while leaving the store open and usable. Plan v2 P1 asserted "atomic rollback/fencing" would be preserved; this one case changed class. Note the opposite argument is strong: `expireRow`'s own `parseReceipt` (`:472`) and the admission-path `parseReceipt` calls (`:1142`, `:1157`, `:1167`, `:1224`) already throw unfenced `SyntaxError`s today, so the new behavior is *consistent* with the rest of the store and arguably more correct than fencing on a read-side data-corruption error.

**Smallest fix:** None, if accepted — recommend accepting and recording the delta against P1 rather than changing code. If the fence must be preserved exactly, the minimal change is at `:553`: wrap the filter parse and escalate, e.g. `try { … } catch (error) { throw fence(error); }` — `fence` is already in scope. Do not catch-and-skip (plan forbids it; the delta correctly does not).

### 2. (Informational) New Snapshot comparator does not compare array length

**Location:** `packages/server/src/json-value-equality.ts:20-21`, as used at `packages/server/src/transaction-snapshot.ts:408`.

**Defect:** Equality for arrays is decided by own-key count (`Object.keys`), not `length`. `isDeepStrictEqual`, which this replaces at the owned-Link site, compares `length`. Two holey arrays with the same own-index set but different `length` (e.g. `new Array(3)` vs `new Array(5)`) compare equal.

**Impact:** Unreachable in the actual domain: both operands at `:408` originate from `JSON.parse` via `readStoredResource` (inline `ownedLinks` copy vs first-class record), and JSON arrays are always dense. The only guard today is the module doc comment ("admitted dense JSON"). Behavior at the `resource-evaluator.ts:839-840` site is byte-identical to the pre-existing `equal`, so nothing changed there.

**Smallest fix:** Not required. If wanted, one line inside the array branch: `if (Array.isArray(a) && a.length !== (b as unknown[]).length) return false;` — no in-domain behavior change.

### 3. (Informational) Deep available receipts are JSON-parsed twice per sweep, and every owner-null row is now materialized

**Location:** `packages/server/src/transaction-store.ts:550-554` (`parseReceipt` in the filter, then `expireRow` → `parseReceipt` at `:472`).

**Defect/Impact:** This is exactly what plan v2 P1 mandated ("JS-filters `parseReceipt(...).detail === available`, calling **unchanged** `expireRow`"), so it is not a deviation. Two measurable costs for the record: (a) each available receipt — including the 24 KB/depth-12000 witness case — is parsed twice on every maintenance tick and at startup; (b) `SELECT * FROM receipts WHERE owner IS NULL` now crosses full row text for compacted/`expired` rows into JS, where previously SQLite filtered them out (SQLite still parsed them in C to evaluate the predicate, so this is a constant-factor change, not asymptotic). Counts, ordering (no `ORDER BY` before or after), pending exclusion, compact skip, exact-instant expiry, completed compaction, failed deletion and atomic rollback are otherwise identical, including the "invalid terminal receipt retention state" throw remaining reachable for exactly the same row set.

**Smallest fix:** None recommended — threading the parsed receipt into `expireRow` would change its signature, which the plan froze. Flagging only so the authoring measurement step records it.
