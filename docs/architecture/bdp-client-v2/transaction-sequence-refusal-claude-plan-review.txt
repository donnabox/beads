# Findings

**1. BLOCKING — Unsupported normative claim; the 406 half of the plan is not grounded where the plan says it is.**
*Location:* plan line 35 (table row "3579–3592, mutation response negotiation") vs. `docs/specs/bdp.md:3579–3592` @`8c`.
*Issue:* The cited range spans two sections, neither containing the asserted rule. `3579–3583` is `### Read+Update HTTP field support` — CORS exposure of Read response fields (`Retry-After`), nothing about the Scope tuple. `3585–3592` is `### Mutation response media negotiation` — the 406 applies before durable admission/key binding, 415 is distinct, ordinary refusals keep order/non-disclosure. The plan's sentence "A bodyless406 still carries required response headers" appears in neither. The inherited Read-profile 406 rule at `bdp.md:1947–1955` says only "with no BDP problem code, family, or retry member." The *only* place the spec explicitly makes current Scope context required on a bodyless response is `bdp.md:5806` — "Required current Scope context remains required on 304 and 412 responses" — scoped to conditional reads and conspicuously not naming 406.
*Impact:* Root is being asked to accept this as "settled normative contract." It is a derivation from the general sentence at `5768`, not a quoted rule, and the one adjacent explicit rule enumerates 304/412 only — which a reviewer could read as *excluding* 406. Mislabeling it settled is the difference between an acceptable slice and an invented requirement.
*Correction:* Split the mislabeled range (drop `3579–3583`, which is irrelevant). Re-ground the row on `5768` ("Transactional Scope-bounded responses carry: …") as the general law, cite `5806` as the nearest explicit analogue, and state plainly that extending it to a bodyless 406 and a direct 413 is a *derivation* from the general rule rather than quoted text. Keep `3585–3592` only for the ordering claim it actually supports.

**2. BLOCKING — The installed proof cannot detect the exact defect the plan names as the primary hazard.**
*Location:* plan lines 71–82 (exchange table) against plan line 44 ("Capture the context at the serving observation; never synthesize it from a prior successful receipt or cached discovery").
*Issue:* Every sequence refusal in the scenario is observed at `pos-2` (exchanges 3 and 4), which is exactly the position reached by the two seeds. No refusal is re-issued after exchanges 8/9 advance to `pos-3`/`pos-4`. Because `scopeEpoch` and `authorizationView` are owner-lifetime constants (`transaction-store.ts:583–590` — only `metadata("position")` varies), position is the *only* discriminating field in the tuple.
*Impact:* An implementation that captured the tuple once after seeding, or that reused the last successful receipt's context — the named failure mode — passes all 11 installed exchanges. The plan's position-freshness discriminator ("Repeat after an unrelated commit to catch cached context", line 63) exists only in the source tests, and plan line 67 explicitly concedes the controls are "source sensitivities, not installed target observations." So the artifact labelled "actual installed proof" proves header *presence*, not *currency*.
*Correction:* Insert one exchange after request 9 re-issuing the 413 (33 fresh keys; no key reuse needed since exchange 9 already proves non-capture) asserting `pos-4`, then let the final Beads/Events pages follow — they then also re-prove no effects from the second refusal. Revised ledger: **12 exchanges/one child**; expected 12+3+14 = **29**, ceiling 12+12+14 = **38/three**. Route set stays at four static routes plus the receipt URL.

**3. BLOCKING — Converts two currently-infallible refusals into bodyless 500s, undisclosed, and the repo's existing justification for tolerating that does not transfer.**
*Location:* plan line 48; `transaction-service.ts:123–131` (`check()`), `transaction-store.ts:885–897` (`entry-refused` on reentrant / not-accepting / fenced), `transaction-http.ts:585` @`8c` (`else response = empty(500)`).
*Issue:* Today both refusals are decided purely from the parsed carrier's length and the `Accept` header and cannot fail. Adding `run()` + `owner.withRead` makes them fail whenever the service is closing/closed or has a `cleanupFailure`, or the owner is fenced — all of which surface as `empty(500)`. The plan chooses this ("Tests for closed/reentrant entry preserve failure rather than fabricate headers", line 64) but never states that it is a *new* 500 on inputs that currently produce a deterministic 413/406. Critically, `docs/design/transaction-implementation-progress.md:615–618` tolerates a faulting post-runner sequence observation precisely because "replay recovers the original member outcomes" — a refusal commits nothing, so there is nothing to replay and the client simply loses its 413/406.
*Impact:* A silent availability/semantics regression on two wire surfaces, justified by reasoning that applies only to the success path. It is also the kind of change that will read as unintended in review.
*Correction:* State the fault disposition explicitly in the "Minimal implementation boundary" section and justify bodyless 500 against the alternative (emit the uncontexted refusal). Add a test pinning that `transaction-runtime.ts:115` (`if (closing || !handler)` → `temporarily-unavailable` 503) still precedes the handler, so the new 500 is unreachable in the installed server, and record that the source-only 500 is accepted deliberately.

**4. MEDIUM — The strongest anchor for the plan's central design constraint is missing from the table.**
*Location:* plan lines 29–38 (anchor table); `docs/specs/bdp.md:5233–5244`.
*Issue:* "The three Transactional response fields on a receipt or page response are the serving request's own observation, never the body's history … `BDP-Scope-Position` carries the position the read observed" is the normative basis for plan line 44's "never synthesize it from a prior successful receipt" and for the stale-`pos-1` control at line 67. It is not cited. `5786` ("It never reports success with an older position") is likewise uncited.
*Impact:* The plan's single most important implementation constraint and its only value-sensitivity control look like reviewer preference rather than spec compliance.
*Correction:* Add a row for `5233–5244` ("serving request's own observation, never the body's history") and reference it from the implementation boundary and from control #2.

**5. MEDIUM — No assertion pins context *absence* on the sequence route's other refusals, so the "no new disclosure precedence" commitment is unverified.**
*Location:* plan line 65 ("keep their existing paths without calling the new observation") and line 46 ("No generic 'all errors' postprocessing, blanket413 wrapper").
*Issue:* The plan requires only a spy-style check that the new observation isn't invoked. No existing test asserts header absence on this route: the `has("bdp-scope-position")).toBe(false)` assertions at `transaction-http.test.ts:929, 945, 1154, 1302, 1440, 1444, 2370, 2402` @`8c` all cover method-dispatch, read and receipt paths, and the sequence block at `421–443` asserts no context at all.
*Impact:* A later blanket wrapper — exactly what the plan forbids — would attach the tuple to the sequence 401/403/415 and no test would fail. The boundary the plan draws (parsed valid carrier + authenticated authorized principal ⇒ tuple; unparsed/wrong-media/unauthenticated ⇒ none) would be unenforced.
*Correction:* Require header-absence assertions on the sequence route for: carrier-level `Idempotency-Key` 400 (`:304–305`), malformed-body 400 (`:310`), unauthenticated 401 (`:313`), forbidden 403 (`:315`), 415 wrong content-type (`:285–292`), and the `minimum-position` development 500 (`:301`). Record the resulting boundary as a descriptive invariant without settling nondisclosure semantics.

**6. MEDIUM — "Source inspection can check all 33 rejected keys" leaves the no-capture oracle unspecified, and the existing helpers that do it are unnamed.**
*Location:* plan line 66.
*Issue:* The repo already ships the right oracle: the `fixture()` helper in `transaction-http.test.ts` exposes `retainedReceipts()` and `receiptRows(key)`, which read `receipts(principal, key, …)` — the single per-principal key namespace at `transaction-store.ts:209` — directly from SQLite. Direct table inspection is strictly stronger than the replay the plan describes, and it is the only cheap way to cover all 33 keys. The plan's phrasing permits either.
*Impact:* An implementer may choose 33 replay submissions (budget blowout) or no check at all. Also, both helpers close the runtime (`receiptRows` closes *and reopens*), so unordered use will break adjacent assertions.
*Correction:* Name `retainedReceipts()`/`receiptRows()` and the `receipts(principal,key)` table; require the assertion that no row exists for any of the 33 rejected keys nor the 406 member key; state that these calls must come last in the test body because they close the runtime. Note for the record that `transaction-http.test.ts:441–442` already proves cross-reuse of a refused sequence member key on a direct submission returns 200 with no conflict, so that specific oracle is pre-validated.

**7. MEDIUM — The new observation duplicates an existing closure rather than extracting it; no instruction prevents drift.**
*Location:* plan line 44; `transaction-service.ts:244–257` @`8c`.
*Issue:* `discoveryObserved`'s inner `observe()` is already *exactly* the wanted body: one `owner.withRead((_reader, context) => Object.freeze({scopeEpoch, authorizationView, scopePosition}))` plus `entry-refused` → `throw new Error(..., {cause})`. The plan correctly refuses to *call* `discoveryObserved` (it assembles/validates discovery) but then says "choose the smallest existing-style representation," which invites a second parallel `withRead` block. The two can diverge — e.g. one returning a frozen three-field copy, the other the raw `context` object.
*Impact:* Two independent sources of truth for the same tuple on the same owner, with no test tying them together; a future change to one silently skews the other.
*Correction:* Require extracting that closure into one private helper consumed by both `discoveryObserved` and the new refusal observation, and add an assertion that a discovery observation and a refusal observation taken at the same position return an equal tuple. This also likely collapses file 1's footprint to a few lines.

**8. MEDIUM — Budget section omits the hard request-body ceiling, and the overflow failure mode shares the asserted status.**
*Location:* plan line 84 ("measure actual33-member bytes"); plan line 76 (exchange 3).
*Issue:* POST bodies are capped at `TRANSACTION_RUNTIME_LIMITS.requestBodyBytes` = 65536 (`transaction-runtime.ts:65–79`, re-checked at `transaction-http.ts:275–279`), and the installed convention additionally asserts `bodyBytes.byteLength <= 65536` with `exactMode.maximumRequestBodyBytes: 65536` (`transactional-direct-refusal-installed.test.ts:162, 170`). Exceeding it returns `413 request-too-large` — **the same status** as the intended `413 limit-exceeded`. Separately, `TRANSACTION_HTTP_TARGET_BYTES` (8192) bounds the request *target*, not the body (`transaction-runtime.ts:120` tests `request.url`); it is easy to misapply as a body cap.
*Impact:* A status-only assertion would pass spuriously on an oversized carrier while testing an entirely different branch that carries no context. The plan's installed row does name `413/sequence.operations`, but its source bullet ("Verify canonical Problem shape on413", line 65) is looser.
*Correction:* State the 65536 ceiling and that 8192 is a target bound, not a body bound. Require both the source and installed oracles to assert `code: "limit-exceeded"` **and** `limit: "sequence.operations"`, never status alone.

**9. LOW — The plan understates that this is first-ever coverage of the 413 branch.**
*Location:* plan lines 18 and 23 ("Retain those assertions and add the missing context/state distinctions").
*Issue:* `transaction-http.ts:317` is the only `sequence.operations` reference in the server, and no test reaches it: the 413s at `transaction-http.test.ts:259, 1034, 2555` are all `transaction.operations` (direct/batch). The progress doc's "Tests exercise both limits together" (`docs/design/transaction-implementation-progress.md:607–610`) refers to the *configured* direct limit versus the fixed sequence bound (`transaction-http.test.ts:1030–1034`), not to a sequence over-count.
*Impact:* An implementer reading the plan may assume the branch is otherwise exercised and correct.
*Correction:* Say the branch is currently untested and record the verified reachability chain (`sequenceRequest` schema `minItems:1`, no `maxItems`; no count bound in `parseReadUpdateSequenceRequest`; `transactionalProblem.limit` pattern `^[a-z]+\.[A-Za-z]+$` accepts `sequence.operations` with no `additionalProperties` restriction, so the existing `transactionalProblem` validator needs no schema change).
