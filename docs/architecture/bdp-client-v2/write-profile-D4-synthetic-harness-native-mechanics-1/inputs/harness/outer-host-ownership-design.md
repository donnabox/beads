# CLOSED outer host owner design

This is a concrete design for the remaining independent harness-host wrapper. Its executable is **not authored, reviewed, released, or measured** here. `harness.py` is a new per-case launcher with deadline checks; its synchronous authorization and final receipt I/O do not by themselves establish a responsive whole-host cap. Abrupt death can also omit a real-peer creation journal. These are blocking mechanics gaps, not irreducible operator questions. None of the 58 prospective invocations may be evaluated on this preparation's authority.

The separate wrapper must start one monotonic origin before remaining imports, setup, gate reads, hashes, process creation, parsing, results, census, or publication. Keep 120/115/119 for unit invocations and 150/145/149 for real-host variants. There is no new grace period. All callback clocks, when relevant, use the earlier outer origin; a nested `run.main` must never receive a later reset. No estimate is evidence that it fits. The wrapper's parent loop performs only bounded nonblocking control/stdio transport, clock checks, and incrementally bounded census. Every potentially blocking file, JSON/hash, network guard, schema, result, or receipt operation belongs to a registered owned worker. A root guarded invocation immediately precedes launch; an owned authorization worker verifies exact549f before any subject import or peer execution. Supersession stops new work; owned local cleanup/error preservation remains permitted.

The initial worker is a direct `Popen(start_new_session=True)` child. Register its unreaped handle and PID/PGID before any fallible inventory or richer record construction. Keep the handle unreaped until a fresh census shows no other owned member and the leader is terminal/absent, then require a subsequent census of every known PGID to show absence. A zombie is a task, not absence. Previously authenticated terminal executable spelling may differ; PID/start/PGID and prior-live constraints remain exact. An initially terminal-only identity cannot later become a live executable baseline.

Real nested host-peer groups require an explicit ownership handshake. The narrow existing `Popen` argv adapter starts a small control bootstrap in the **same requested PID/PGID/PPID relationship**, which waits on a sealed inherited control channel before executing its bound peer role. The trusted launch adapter retains the actual Popen handle immediately and sends a bounded creation record. The outer owner authenticates the live waiting leader using a fresh bounded census (PID, parent, PGID, start, executable, role/nonce), records the group, then acknowledges peer execution. A lost acknowledgement or closed parent channel makes the bootstrap exit. No `preexec_fn`, broad process matching, forged process identity, arbitrary command role, or product command is allowed. This handshake changes only the new harness's peer adapter, not immutable helper4. Its setup latency is charged to the original outer clock and must itself be tested.

After registration, inspect **every** authenticated PGID on every fresh census, including groups whose leader exited or was reaped. New same-PGID members are included only while the group retains a current authenticated anchor or unreaped owned direct handle. A group once observed empty cannot be silently resurrected. Changed PID start, live executable, PGID, or a terminal-to-live transition becomes sticky UNKNOWN; do not signal a historical numeric group. An escaped group without a fresh anchor cannot be called absent or safely killed. Preserve its unknown result and withhold acceptance. Real peers' finite self-expiry is a secondary backstop, not ownership or cleanup proof.

The parent's census is an owned `/bin/ps` subprocess, registered immediately. Nonblocking stdout/stderr reads are capped as in helper4 (262144/4096, 200ms). A blocked/failed probe becomes explicit failure; dispatch cleanup from retained direct handles/current authenticated anchors. Record attempted versus successful TERM/KILL honestly; a failed inventory/signal cannot suppress later safe escalation. Repeated bounded escalation stays inside TERM115/KILL119 or TERM145/KILL149 and the absolute120/150 boundary. Never signal the supervisor group. At the hard boundary the outside host must actually terminate the wrapper if needed; a Python loop or a precomputed elapsed field is not proof of an enforced wall deadline.

All actual child stdout/stderr are fully drained by owned bounded writer tasks to exclusive raw files. Retain exact bytes, EOF and child terminal observations, write completion, and any failure. No input repair, truncation, source-derived successful substitute, JSON-only filtered log, report union, or reclassification of a failed control as a pass. The current scanner's 256MiB raw, 64MiB selected, 16MiB results and structural limits stay unchanged. Control output must distinguish deterministic modeled scheduling, real kernel/Popen/pipe observations, and product-domain facts that were not exercised.

Successful **control** completion requires: an explicitly expected result on the actual immutable subject; complete output/EOF and all owned helper settlements; fresh whole-PGID absence after required reaping; known ownership; no forced cleanup for a nominal positive control; all postchecks and an owned receipt publisher completed strictly before the applicable terminal deadline. Equality refuses. Expected negative controls may have signaled cleanup, but must still prove absence and preserve the actual failure. A tentative publisher receipt is never a terminal host receipt. Missing/partial/error receipts stay missing/partial/error. A blocked/failed receipt writer receives the same clock and cleanup discipline.

The external terminal receipt must bind: exact harness and helper4 implementation hashes, root release/session/case/variant, whole-host origin and actual duration, raw control exit, all direct creation records and authenticated identities/groups, last fresh census, actual signals and forced-cleanup state, stdout/stderr byte hashes and EOF, actual control-result hash when complete, missing artifacts, and explicit ownership/clock unknowns. No synthetic aggregate acceptance is emitted by the harness. Other-native review of the eventual executable, durable root synthetic-only release, actual receipts, and independent root acceptance precede any product gate. The original helper4 gates remain untouched.

The future entry is a separately named immutable successor's `outer_host.py --case ID --variant VARIANT --release ROOT_RECEIPT`. That file does not exist in this preparation; there is deliberately no executable-looking invented path or runnable wrapper command. The exact final argv, binary/code hashes, peer handshake implementation, actual hard host limiter, terminal receipts, and actual clock fit remain UNRESOLVED. Root can authorize the finite wrapper source successor after reviewing this design and the present concrete controls.
