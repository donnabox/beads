### F1 — High (proven) · `fence()` stops the timer but never releases the connection; the maintenance path does
**File/section:** `packages/server/src/transaction-store.ts:162-170` (`fence`), compared against `:646-660` (maintenance-timer handler), with the open-transaction case at `:183-190`.

**Issue.** `fence()` does `clearInterval(maintenanceTimer)` and sets `ownerFailure`. It does not call `db.close()`. The pre-existing maintenance-failure path at `:646-660` does exactly the opposite and says so in its comment: "stop the timer and release the database instead of silently continuing." After an owner-path fence, the process keeps an open `DatabaseSync` handle on a store documented at `:87` as held "under persistent EXCLUSIVE locking," and in the rollback-failure branch it keeps an **open write transaction**: at `:183-190`, when `db.exec("ROLLBACK")` throws, `cause` becomes the `AggregateError`, `cleanRollback` stays `false`, and control reaches `throw fence(cause)` with the transaction still open. Nothing later rolls it back — `cleanupThenThrow` returns early on `ownerFailure` (diff, `cleanupThenThrow` body) and every entry point throws.

**Trigger.** The delta's own test exercises it: *"preserves the execution and rollback causes, blocks tentative reads, and recovers on reopen"* (`transaction-store.test.ts`) injects a `ROLLBACK` failure, asserts exactly one `BEGIN IMMEDIATE`, then asserts `assertFenced`. At that point the transaction is open and the handle is live.

**Impact.** A fenced owner holds the file lock (and possibly an uncommitted write transaction with a growing journal/WAL) for the life of the process. Any second opener gets `SQLITE_BUSY`. The error message instructs the caller to "reopen before use," but the delta supplies no code path that makes reopening possible.

**Fix/next step.** Close the connection inside `fence()` (mirroring `:646-660`), or add an explicitly fence-exempt release path and assert it in `assertFenced`'s list.

### F2 — Medium (proven, with one question) · the fence is terminal in-process; recovery is performed only by the test fixture
**File/section:** `transaction-store.ts:150-170` (`enter`/`fence`), `:605-616` (`execute` cleanup), `:780-785` region (`nextSequence`'s new `if (ownerFailure) throw error;`). Spec anchor supplied at `docs/specs/bdp.md:3903-3922`.

**Issue.** By design the fence declines to compensate (`atomic`'s comment at `:199-200`: "Reopen determines its durable state; compensation must not guess at it"). That leaves a durable `pending` receipt behind — the tests assert `recoveredPending` of 1 and 3 — and simultaneously stops the maintenance timer and refuses `maintain()`, `inspect()`, `receipt()`, `admit*`, `execute`, `retract`, `nextSequence`, `cancelSequence`. Retraction therefore happens *only* on reopen. The only reopen in the packet is `f.reopen()` in the test fixture.

**Trigger.** Any fenced path: injected COMMIT failure, rollback failure, cleanup `BEGIN` failure, engine-ended transaction — all five new tests reach it.

**Impact.** `bdp.md:3916-3922` places pending-receipt retraction on "restart or failover … within a finite bound," and makes "a `pending` receipt older than the bound … a conformance failure." That bound is now owned entirely outside the store, by a supervisor the packet does not contain. Combined with F1, the fenced process also cannot be succeeded in-place.

**Fix/next step.** Either close in `fence()` and document that the caller must construct a new store, or add a supervision/reopen seam and a test that drives it through the public surface rather than a fixture helper.

**Question:** `openTransactionStore`'s returned object (including any `close`) is in the unsupplied region `:205-569` / `:661-end`. If `close()` routes through `enter`, a fenced store cannot be closed at all — `enter:151` checks `ownerFailure` before `closed || busy`. I cannot resolve this from the packet.

### F3 — Medium (proven behavior change) · `BEGIN IMMEDIATE` moved inside the `try`, so a never-started transaction now fences permanently
**File/section:** `transaction-store.ts:174-175` vs. the removed baseline line (diff: `-    db.exec("BEGIN IMMEDIATE");` above the `try`), with the predicate at `:201`.

**Issue.** If `BEGIN IMMEDIATE` itself throws, the catch runs with `db.isTransaction === false`, so the `if (db.isTransaction)` guard at `:184` skips ROLLBACK and `cleanRollback` remains `false`. `:201` then evaluates `!cleanRollback` as true and fences. Baseline executed `BEGIN IMMEDIATE` outside the `try`: the error propagated, nothing was fenced, and the store stayed usable.

**Trigger.** Any failure to start a transaction — `SQLITE_BUSY`/`SQLITE_LOCKED` at first use against a file another process still holds, or `SQLITE_FULL`/`SQLITE_IOERR` on the journal write. The delta injects precisely this failure in *"preserves %s failure when compensating retraction also fails"* and *"preserves sequence admission and cleanup causes"*, where fencing is the intended outcome because an original failure preceded it; the standalone case has no such precondition.

**Impact.** A transient, fully-known-state condition (no transaction opened, nothing uncertain, retry trivially safe) permanently disables the owner and requires a reopen. This is an availability regression relative to the base commit, in the conservative direction.

**Fix/next step.** Hoist `db.exec("BEGIN IMMEDIATE")` back out of the `try`, or distinguish "transaction never started" from "transaction state unknown" before fencing.

*Baseline note:* the same restructure strictly improves the rollback-failure case — baseline let a thrown `ROLLBACK` replace the original error and continued running un-fenced. F3 is about the newly-fenced BEGIN case only.

### F5 — Medium (question) · correctness now depends on `db.isTransaction`, with no engines pin in the packet
**File/section:** `transaction-store.ts:184-186`.

**Issue.** `db.isTransaction` is a comparatively recent `node:sqlite` addition. If the getter is absent on the deployed runtime it evaluates `undefined` → falsy, so ROLLBACK is **never attempted**, `cleanRollback` is always `false`, and `:201` fences on every single `atomic` failure — including ordinary application errors — while leaving the write transaction open (F1's worst case becomes the default). This degrades silently: no exception, no log.

**Trigger.** Running the built package on a Node without the getter.

**Impact.** First application-level failure permanently fences the owner and parks an open transaction on the exclusively-locked file.

**Why a question, not proven.** The new tests read the real getter (the spy covers only `exec`), and the `before`-COMMIT case asserts exactly one `ROLLBACK`, so CI implicitly pins a sufficient Node. `package.json` / `engines` / the CI matrix are not in the packet, so I cannot establish whether production and CI share that floor.

**Fix/next step.** Add an `engines` floor, or assert `typeof db.isTransaction === "boolean"` once at open and fail provisioning otherwise.

### F6 — Low (proven code behavior; trigger not established) · non-constraint SQLite errors fence even after a proven clean rollback
**File/section:** `transaction-store.ts:191-201`.

**Issue.** The only non-fencing exit for a SQLite-coded error is `constraint` — `(errcode & 0xff) === 19`. Every other primary code fences at `:201` via `(sqlite && !constraint)` **even when `cleanRollback === true`**, i.e. when the durable state is known-unchanged. The mask is correct for extended codes (the test's `1555` → `19`; STRICT-table `SQLITE_CONSTRAINT_DATATYPE` `3091` → `19` likewise lands on the non-fencing path).

**Impact/trigger.** For genuinely storage-level codes (`SQLITE_FULL` 13, `SQLITE_IOERR` 10) fencing is the intended and defensible choice. For deterministic non-constraint codes that *did* roll back cleanly (`SQLITE_ERROR` 1, `SQLITE_MISMATCH` 20, `SQLITE_TOOBIG` 18), the owner is permanently disabled despite known state. **I cannot name a concretely reachable trigger of that second class from the supplied excerpt** — the generation sites are in the unsupplied `:205-569` region.

**Fix/next step.** If this breadth is deliberate, state it in a comment next to `:199-200`, which currently justifies only the uncertainty case. Otherwise narrow the fence to codes that actually imply storage uncertainty.
