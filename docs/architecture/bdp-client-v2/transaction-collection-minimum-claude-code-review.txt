**1. Medium — in-tree progress document now contradicts the frozen source**
*Location:* `docs/design/transaction-implementation-progress.md:623`, `:625`, `:628`, `:648-651`, `:658`.
*Issue:* The commit changes behavior this document asserts in present tense and updates no doc.
- `:648-649` "The private point facet accepts an AbortSignal, but the HTTP path does not pass a signal or connect socket disconnects to a controller." — `transaction-http.ts:231` now passes `request.signal`, and the runtime already bridges Node disconnects (`transaction-runtime.ts:147`, `node-http-disconnect.ts:16`).
- `:650-651` "Actual HTTP point and receipt disconnects **both** drain the remaining finite wait budget, which also bounds their shutdown delay." — point reads no longer drain; they stop at the next loop check (`transaction-consistency.ts:107`), which is exactly what the new test at `transaction-http.test.ts:1896` pins. Receipts still drain (`transaction-service.ts:361` `receiptAtMinimum` takes no signal), so the "both" claim is false in opposite directions.
- `:623`/`:625`/`:628`/`:658` still scope the honored subset to points/receipts ("after captured authorization and **point** materialization"; "Collection continuations and **other nonpoint routes** retain the development gap when controls are supplied"), which is now false for initial Bead/Link collections.
*Impact:* In a repo where this file is the truth record root/council reads, the frozen tree now states that disconnects are not propagated and that collection minimum controls are refused. A reviewer reading only the tree would mis-assess both the abort slice and the serving slice, and the stale sentence is a stronger claim than the code (no-drain vs. drain) rather than a weaker one.
*Fix:* Apply the narrow progress-doc update the plan authorizes at line 75: retitle/extend §"Canonical point and receipt minimum-read subset" to include initial Bead/Link collections and the two named preserved control refusals; replace `:648-651` with the actual behavior (perform-route `request.signal` forwarding only; point and collection waits stop at the next loop check after observable abort, with no instantaneous-cancellation or SLA claim; receipt and changes/events wait behavior unchanged); narrow `:658` to continuations, `types/`, incident Links, aliases and discovery.

**2. Low — the accepted "no allocation" half of the control-failure predicate is unpinned**
*Location:* `packages/server/src/transaction-http.test.ts:1868-1888` and `packages/server/src/transaction-read.test.ts:605-662`.
*Issue:* Root disposition External2 requires "Pin limit33, malformed/complex Selector and parser-invalid controls with behind minimum and **no wait/allocation**" (plan A.4: "without entering a wait or allocating a cursor"). The new HTTP test pins only `expect(wait).not.toHaveBeenCalled()` (`:1888`); the token counter that could prove nonallocation exists only in `transaction-read.test.ts:612-618` and is applied solely to the valid-request behind path.
*Impact:* The preserved-refusal precedence depends entirely on limit/selector admission happening in `materialize`'s `control()` (`authority-read.ts:752-761`) rather than in `finish`'s `control()` (`authority-read.ts:875-896`). If that admission were ever moved or duplicated into `finish` — after `firstPageWithContext` reserves retained state — the refusal would both allocate a cursor and lose precedence to the behind minimum (413 becoming 503), and the current suite would still pass.
*Fix:* In the existing `describe("initial collection minimums")` block, reuse the `generateOpaqueToken: () => \`minimum_${++allocations}\`` plane patch and add: `await plane.minimumFor({kind:"anonymous"}, {...minimum, minimumPosition:"pos-2"}).perform({kind:"collection", collection:"beads", limit: 11})` (over the fixture's `maxPageItems: 10`) and the same with `selector: "$[?"`, asserting each resolves (not rejects) to `{kind:"problem", problem:{code:"limit-exceeded"}}` / `{code:"invalid-parameter"}` and that `allocations === 0`.
