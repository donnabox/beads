## Existing law and current gap

`docs/specs/bdp.md:2532–2575` (`#installed-type-contracts`, `#descriptor-installation-for-mutation`) requires a pinned local descriptor and complete transitive contract closure before admission, exact installed artifacts plus an integrity fingerprint, no refresh at the same Type ID, and offline validation/retry/replay/recovery. Exact artifacts remain while live or retained historical representations reference them; at least Type ID and fingerprint survive for the logical Scope lifetime. Effective contracts intersect inherited schemas (`#effective-type-contracts`, lines562–605). A digest alone is not the required retained local artifact copy.

Current safeguards are real but insufficient:

- `development-contracts.ts:69–145` ingests exact detached descriptor/schema bytes, compiles solely from that capture, brands/freeze-protects the authority, and binds artifact digest, artifact limits, graph limits and evaluator limits into `development-schema5-…`. Its registry accepts only exact canonical installed Type bytes. These prevent caller mutation and implicit network refresh during the process lifetime.
- `installed-reference-configuration.ts:127–164` captures administrator-supplied strings into bounded buffers, compiles the full bundle and retains hosted schema strings **in memory**. `installed-reference.ts:14–87` separately hashes installed package/dependency bytes and starts the actual private factory. Neither persists the raw descriptor/schema capture.
- `development-authority.ts:142–154,180–188` derives installation/lineage from the contract identity plus aggregate policy and passes canonical descriptor text as the store seed. It supplies the matching registry to mutation evaluation and descriptors to the same-owner Read plane. `installed-reference-configuration.ts:172–184` separately binds credentials, policy, profile/history, owner limits and aggregate policy into the served candidate identity.
- `recovery-store.ts:200,550–562` persists `installed_types` descriptor text; for configured authorities this is canonicalized descriptor JSON, not the original descriptor bytes, and there are no stored transitive schema artifacts. `recovery-store.ts:587–595` checks format/Scope/installation/lineage before cleanup. Reopening with changed supplied schema bytes already fails through the changed installation digest, as `development-contracts.test.ts:364` observes. That proves mismatch refusal, not availability of retained exact bytes.

**Ordering trap:** `openRecoveryStore` deletes abandoned claimed keys at line613 and commits startup at617. `development-authority.ts:193–205` checks exact stored Type inventory only **after** that open returns. A new artifact check in that visitor would be too late to preserve pending claims on corrupted persisted artifacts/inventory. The new check must be inside the locked store-open transaction before line613, as root confirmed. Later `store.expire(clock())` and lifecycle maintenance must also remain downstream.

## Minimal design

### 1. Reuse the TX author's shared capture; no second installer

The concurrent author owns `development-contracts.ts` and its immutable branded capture view in `vickie-transaction-contracts`. The current draft exposes artifacts, artifactLimits, graphLimits and evaluatorLimits on the branded authority, with policy constants as witnesses rather than overrides. Treat that draft as provisional: consume the reviewed frozen accessor once available; do not duplicate or edit it in this RU lane.

Capture/configuration compilation remains before store creation/open and before service readiness. Serialize only the accessor's detached primitive reconstruction records: exact kind/retrievalUri/bytesBase64 plus existing integrity/length fields and actual compiler limits/policy identity. Never persist closures, validator functions, mutable typed arrays, paths to source files, live credential/policy state, or an independently supplied registry. Retain the existing compiler identity algorithm; a storage-format change is not a reason to relabel the contract digest.

### 2. Store bytes separately from compact installation identity

Add one exact installation-capture metadata row (or equivalent bounded dedicated row) to the existing recovery store, atomically with explicit creation. Keep `installation`/`lineage` as compact identity, rather than concatenating the base64 bundle into tokens or Read pagination configuration. The row must always exist under the new format: an explicit absence marker for the legacy schema-free development path is different from a missing/corrupted row.

The storage owner need not know JSON Schema. Give it a narrow immutable expected-capture value plus expected canonical installed-Type inventory, supplied by the existing authority after branded compilation. Compare exact expected text and inventory under its locked startup. Avoid an arbitrary caller-supplied startup callback or second compiler inside recovery-store. For the schema-free built-in path, retain its current canonical descriptor seed as the artifact source and explicit compiled-capture absence; do not silently claim original schema bytes existed there.

Bound serialization before file creation/allocation. Reuse the approved capture's artifact/URI/count/limit ceilings; account for base64 expansion and JSON escaping instead of imposing an unrelated1MiB cap that refuses existing valid16MiB bundles. Prefer a measured finite maximum derived from the current capture ceilings. Persist exact raw descriptor bytes in the capture even though `installed_types` remains canonical for registry/Read lookup. Reject unexpected capture fields and invalid primitive values via the shared capture authority, not a new parser.

Retain the whole installation capture for the store/logical-Scope lifetime. No artifact GC is needed: this safely covers live records, retained outcomes and deleted/no-longer-live Resources without introducing lifecycle dependency tracking. Requests, retry, periodic expiry and restart cleanup never remove it.

### 3. Verify before any BDP recovery or maintenance

Inside the current `BEGIN EXCLUSIVE`, after SQLite can read the recovered database and after normal format/identity checks, compare the exact persisted capture and complete expected canonical Type inventory. Check both missing and extra rows, changed bytes, and ID/content mismatch. This must precede claimed-key deletion, allocation writes, startup commit, expiry and owner admission. Pure equality to a prevalidated branded expected capture can reject corrupt saved content without trusting its claimed digest or recompiling unbounded data inside the lock.

Keep SQLite's writable journal recovery. No read-only preflight, sidecar manifest or unsafe file parser. Ordinary incompatible files must stay byte-identical on refusal; an actual hot rollback journal may be restored by SQLite before metadata is readable. After that, the rejected installation must still preserve all committed BDP keys, resources, counters and pending claims. Failed startup must close the database and listeners; no qualification-ready IPC signal may escape.

Administrative configuration may remain required on reopen. Prove the persisted exact capture can reconstruct the same branded compiler offline through existing ingestion; it need not invent an automatic load-from-disk public startup mode. If supplied compiled configuration remains the runtime registry, locked byte/inventory equality establishes that it is the same pinned installation. Type GET/probe/list, mutation validation and hosted schema responses must use those same accepted artifacts. Existing per-reopen live authorization policy changes remain allowed where currently supported; do not accidentally bind ephemeral policy/credentials into immutable Type capture.

### 4. Explicit private compatibility

The store format currently is3 (`recovery-store.ts:191`). A mandatory capture row plus pre-maintenance inventory contract warrants a new private format, chosen at implementation freeze. Reject old files without automatic migration/reseed; do not copy supplied current configuration into an existing format3 file and call it retained history. Preserve exact retained outcome/identity codecs unless independently changed—none is proposed here.

Only one non-test caller currently opens recovery-store: development-authority.ts. Direct recovery-store fixtures and emitted subprocess fixtures also need the explicit absence/current-format behavior. Inventory these first, but avoid broad fixture churn or a compatibility shim. The existing default installation string can remain semantically stable if the format gate supplies the necessary refusal; alter it only if an actual installation identity meaning changes. Never rewrite historical evidence or prior stores.

## Required counterexamples and done predicates

1. **Exact bytes, not digest-only.** A real installed HTTP fixture has a descriptor with noncanonical whitespace, inherited constraints and a transitive schema. Create/update valid and invalid Resources, close, inspect retained artifact bytes independently and reconstruct offline from those saved bytes. Reopen with the same configuration; Type/Resource GET, hosted schema GET/HEAD, validation diagnostics and retained success/failure replay remain consistent.
2. **Before-cleanup refusal.** Provision a disposable store with a live Resource, retained outcomes and an abandoned claimed key. Corrupt one saved artifact byte while preserving the claimed fingerprint, or remove/replace the capture row; separately corrupt/remove/add installed-Type rows without changing installation metadata. Opening with the original administrator config must refuse before clearing the pending key or expiring anything. Compare raw rows and ordinary whole-file bytes before/after; then restore the original disposable test bytes and show valid reopen recovers the original pending claim. This explicitly tests the current post-open inventory-order gap.
3. **Configuration mismatch.** Changed schema bytes at the same URI, missing transitive input, changed compiler/artifact limits, forged capture authority and descriptor/capture mismatch fail closed. Invalid administrative inputs fail before new file creation. Unsupported compiler policy is not an override. No remote resolution or ambient source-file refresh occurs in requests or restart.
4. **Lifetime and detachment.** Caller mutation cannot change captured bytes/limits or the running registry. Delete all live Resources, advance normal retention maintenance, close/reopen: full capture remains unchanged. Preserve exact allocated identities/revisions and retained keys throughout ordinary restart.
5. **Compatibility and crash.** An actual frozen format3 opener/store provides old→new refusal evidence, and where practical new→old refusal for the added metadata format; no migration. Actual child death inside a SQLite transaction leaves hot journal magic, then compatible reopen succeeds. An incompatible-capture open of that hot-journal file refuses before BDP cleanup; a subsequent valid reopen still recovers its pending key and retained facts. State explicitly that SQLite restoration may change interrupted physical bytes.
6. **Same authority and bounded claims.** One accepted contract object supplies storage expectations, validation registry, Type inventory and hosted schema bytes. Keep current profile/history/auth/policy and startup readiness boundaries. No Type lifecycle, new schemas, HTTP mutation vocabulary, profile advertisement or client-side synthetic evidence.
7. **Checks.** Read applicable repository instructions; frozen install, pinned Node24.16/pnpm11.20, typecheck and build before process tests. Run recovery-store/sequence lifecycle, development-contracts, installed-reference/startup/import, and affected installed cumulative regressions; both smokes, boundaries/format/lint and existing evidence verifier. Fresh packed restart/retention observations must record the final clean source/payload and exact configuration. Root handles broader combined checks and publication.
