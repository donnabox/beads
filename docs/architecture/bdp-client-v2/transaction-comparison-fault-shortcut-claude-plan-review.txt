## Findings

**1 — Medium — "Spy only on existing admission functions" is not implementable as written.**
*Location:* plan line 43, against `packages/server/src/transaction-store.ts:1432` (`return Object.freeze({`).
*Issue:* the owner is frozen, so `vi.spyOn(f.store, "admit")` / `"admitObserved"` throws `TypeError` (defineProperty on a non-configurable property).
*Impact:* an author following the step literally hits a wall the plan classifies as a "preflight obstacle," risking either a needless escalation or an improvised injection seam the plan forbids.
*Correction:* name the established spread-adapter precedent instead — `{ ...f.store, admit: vi.fn(f.store.admit), admitObserved: vi.fn(f.store.admitObserved) }`, exactly as `transaction-submission.test.ts:1071–1078`, `:1111–1116` and `:1148–1163` already do. These still delegate to real owner closures, so the "real owner" requirement is preserved.

**2 — Medium — the served 500 is deterministically `http.ts:614`; the "or runtime fallback" disjunction is under-determined and the assertion inventory omits `vary: Accept`.**
*Location:* plan line 35.
*Issue:* the throw originates at `transaction-http.ts:344` inside `handle`'s try (`:584`), so it is caught at `:586` and becomes `empty(500)` at `:614`, then gains `x-bdp-development` (`:616`) and `vary: Accept` for POST (`:617`). The runtime fallback at `transaction-runtime.ts:253–260` is reachable only if `handler.handle` itself throws, and `schemas?.()` returns `undefined` immediately for POST (`transaction-schema-http.ts:42–47`). The two paths differ: only the handler path carries `vary`.
*Impact:* an "exact sanitized 500 properties" assertion written against the disjunction either fails on the unlisted `vary` header or is loose enough to accept a 500 produced by an unintended path — which would pass even if the guard were wrong.
*Correction:* pin the path. Assert `500`, empty body, `content-length: 0`, `cache-control: private, no-store`, `x-bdp-development: non-attesting`, **`vary: Accept`**, plus the stated negatives (no `application/problem+json`, no `Retry-After`, no `Location`, no development-limit, none of the three BDP context headers). Drop the disjunction or record the runtime fallback as explicitly excluded.

**3 — Low/Medium — the new submission fault case must not inherit its neighbours' `dependencies()`/`cancelSequence()` scaffolding.**
*Location:* plan line 43, against `transaction-submission.test.ts:1105–1143` and `:1144–1177`, which both end in `expect(f.store.cancelSequence(attempt)).toBe(2)` — one inside a `finally`.
*Issue:* `cancelSequence` enters the owner, so it throws the retained fault once `maintenanceFailure` is set (`transaction-store.ts:342–344`). In a `finally` it would overwrite the primary assertion failure.
*Impact:* the fault case fails for the wrong reason, or masks its real result.
*Correction:* state explicitly that the fault case opens a plain owner with `maintenanceIntervalMs`/`fault` and **no** sequence reservation — consistent with the plan's own line 13 ("needs neither an unresolved reservation nor deadline timing") — and that its only teardown is the fixture store close, which is safe per `:2088`.
