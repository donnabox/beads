### 1. BLOCKER (High) — TypeScript compile error: `minimumReads: policy` violates `exactOptionalPropertyTypes`

**Location:** `packages/server/src/transaction-service.test.ts:4388` (origin at `:4318` and `:4355`)

```ts
4355  function g09ServiceFixture(policy?: TransactionServiceOptions["minimumReads"]) {
...
4388    { ownerLifetime: "service", read: f.read, minimumReads: policy },
```

**Defect.** `tsconfig.base.json:6` sets `"exactOptionalPropertyTypes": true`, and `tsconfig.check.json` includes `packages/*/src/**/*.ts`, so this test file is typechecked. `TransactionServiceOptions.minimumReads` is declared `readonly minimumReads?: TransactionMinimumWaitOptions` (`transaction-service.ts:71`) — optional **without** `| undefined`. `TransactionServiceOptions["minimumReads"]` resolves to `TransactionMinimumWaitOptions | undefined`, so the object literal supplies a *present* property whose type includes `undefined`. That is TS2379/TS2375 ("Type 'TransactionMinimumWaitOptions | undefined' is not assignable to type 'TransactionMinimumWaitOptions' with 'exactOptionalPropertyTypes: true'").

This is not speculative: every pre-existing fixture in the same file deliberately strips the `undefined` for exactly this reason — `tracked()` at `:1479`, `freshSnapshotOpaqueFixture()` at `:3216`, and `currentObservationFixture()` at `:3769` all use `NonNullable<TransactionServiceOptions["minimumReads"]>`. The G09 fixture is the only site that passes the nullable form through.

**Impact.** `tsc -p tsconfig.check.json` fails; with `noEmitOnError: true` the package build fails too. Since no compiler has been run on this candidate (per the author report), this error is live and blocks the whole six-file slice, including all eight source callbacks (S01–S08 cannot run under a failed typecheck of their own file).

**Smallest correction** (behaviour-identical, matches the house pattern at `:1479`): change both signatures to the non-nullable default and keep the shorthand:

```ts
4318    policy: NonNullable<TransactionServiceOptions["minimumReads"]> = {},
4355  function g09ServiceFixture(policy: NonNullable<TransactionServiceOptions["minimumReads"]> = {}) {
4388    { ownerLifetime: "service", read: f.read, minimumReads: policy },
```

`createTransactionService` does `Object.freeze({ ...options.minimumReads })` (`transaction-service.ts:120`), so `{}` and `undefined` produce an identical frozen policy — S01's default-budget path is unchanged. The alternative minimal fix is a conditional spread `...(policy === undefined ? {} : { minimumReads: policy })` at `:4388` only.

### 2. Low — S01's "caller mutation" assertion cannot fail; it does not discriminate the synchronous capture it claims to prove

**Location:** `packages/server/src/transaction-service.test.ts:4411-4419`

```ts
4416    const captured = f.invoke(supplied);
4417    supplied.scopeEpoch = "changed-after-invocation";
4418    supplied.minimumPosition = "opaque";
4419    expect(await captured).toEqual({ context: f.context });
```

**Defect.** `schemaObserved` → `run(async () => waitForTransactionMinimum(observe, ...))`; `run` calls `start()` synchronously, the async arrow body runs synchronously to its first `await`, and `waitForTransactionMinimum` executes `return await attempt()` with `attempt()` invoked synchronously. The owner read therefore completes **before** `f.invoke(supplied)` returns, i.e. before lines 4417–4418 execute. The assertion would still pass with a hypothetical implementation that re-read `supplied` on every attempt and never snapshotted it. The plan's S01 contract ("captures caller mutation") is satisfied only textually.

**Impact.** The only authored witness for the plan's central production requirement — "capture data-only lexical tuple synchronously before async work" — is non-discriminating. A regression that moved `snapshotCurrentReadMinimum` inside `observe` would go undetected by S01, S02 and S03 alike.

**Smallest correction.** Make the mutation observable across a retry boundary instead of across the synchronous first attempt: give the S01 case an injected policy (`{ budgetMs: 2, now: () => tick++, wait: async () => { supplied.minimumPosition = "pos-999"; } }`), invoke with a satisfied tuple that first fails `behind`, and assert the result still resolves against the captured tuple. No extra direct call is required (the existing 3 calls stay). Alternatively, add no call and instead assert the rejection of an accessor-bearing tuple (`Object.defineProperty(t, "minimumPosition", { get(){...} })`), which only a real `snapshotCurrentReadMinimum` rejects.

### 3. Low — No authored assertion covers abort propagation through a schema minimum wait

**Location:** production contract at `packages/server/src/transaction-service.ts:707-719` and `packages/server/src/transaction-schema-http.ts:62-69`

**Defect.** The plan lists abort propagation among the production obligations for both `schemaObserved` and the shared failure mapper. The implementation is correct — `waitForTransactionMinimum` throws `ScopeServerOperationAbortedError` on `signal.aborted`, `transactionMinimumFailureResponse` returns `undefined` for it, the handler rethrows, and `transaction-runtime.ts:250-255` destroys the response — but nothing in S01–S08 or I01–I02 exercises it. S01 only proves the *no-minimum* path **ignores** a pre-aborted signal (`:4407-4409`); the legacy disconnect test at `transaction-schema-http.test.ts:354` gates *after* `select` resolves, so it never enters the minimum branch either.

**Impact.** A future change that mapped an abort to 503/500, or that dropped the `signal` argument at `transaction-schema-http.ts:64`, would pass the whole new suite. Note this gap is *within* the accepted S01–S08 table (the plan did not enumerate an abort row), so it is a coverage limitation rather than a deviation.

**Smallest correction.** Inside S03's already-injected `wait`, abort a controller passed as the second `invoke` argument on the first wait and assert the next attempt rejects with `ScopeServerOperationAbortedError` — no new callback and no new wire request.

### 6. Low — S07/S08 allocate the full default 1 s minimum-read budget inside a 3 s work bound that also covers runtime startup

**Location:** `packages/server/src/transaction-schema-http.test.ts:603, 658, 683-684/703` (used by S07 `:781` and S08 `:799`)

**Defect.** `startTransactionRuntime` uses `minimumReadBudgetMs: 1000` (`transaction-runtime-configuration.ts:112`), and neither S07 nor S08 injects a `minimumReads` seam. Each 503 row therefore burns ~1000 ms of real time (≈200 owner attempts at the 5 ms `wait` cadence from `transaction-consistency.ts:175`). That 1000 ms, plus `startTransactionRuntime` (SQLite create + Ajv contract compilation + listen), must fit inside the single `g09Bound(…, 3000)` at `:683/703`; the per-request guard at `:658` additionally shrinks to `3000 - elapsedSinceCaseStart`, so a slow startup can make the second request's socket deadline shorter than the server's own catch-up budget and destroy it with `"G09 source request deadline"`.

**Impact.** Flaky failure risk on loaded hosts, attributed to the test harness rather than the subject. I cannot quantify the margin — no execution was performed, and the plan forbids estimate-based widening, so I am not proposing a larger bound.

**Smallest correction** (inside the accepted 3 s budget, no extra wire/retry): start the per-request allowance from the moment the request is issued rather than from case start — replace `3000 - (performance.now() - started)` at `:658` with a fixed `Math.min(5000, …)` relative to the request, or record the actual elapsed startup and surface it in the `:726` report so the margin is observable rather than silent. Flagging the residual risk honestly is acceptable if neither is taken.

### 7. Informational — behavioural exposure change on the exact-schema route (correct per plan, worth recording)

**Location:** `packages/server/src/transaction-schema-http.ts:56-69`

The exact installed schema route was previously constant-time for every minimum-bearing request (early `return undefined` → `developmentGap("minimum-position-route")`, a body-less 500). It now enters `owner.withRead` and can be held for the whole finite budget by any authenticated principal sending `bdp-minimum-scope-position: opaque` or an ahead position. The service registers the task in `active` (`transaction-service.ts:140-155`), which `close()` drains, and there is no per-principal cap on non-stream work. This is exactly the plan-sanctioned reuse of the existing local finite policy and is identical to the exposure already present on Bead/Link/Types/discovery current reads, so I raise no defect — but it is a real cost change on a route previously immune to it, and it is the correct item to re-examine if a future slice adds concurrency limits. No new disclosure: the 200 path already emitted `bdp-scope-epoch/-authorization-view/-scope-position` before this change.
