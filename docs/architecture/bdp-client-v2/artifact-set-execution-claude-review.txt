## Findings

### 1. Continuation shard's exact route table is self-certifying — no independent pin (Medium)

**Where:** `apps/bdptest/test-support/read-update-artifact-execution.ts:20,175,188` · `apps/bdptest/src/read-update-matrix.test.ts:206,954-956,1307-1309`

`run` now configures the harness with `routes: artifactRoutes(bundle, scope)` (`:206`), and `associateArtifactObservations` "verifies" that configuration by recomputing `artifactRoutes(shard.bundle, configuration.scope)` (`:175`) and then digesting the same projection (`:188`). Both sides of the comparison come out of one function, so the check cannot fail on a derivation defect. The runner's own `exactConfigurationDigest` is also computed from the same route array, so that comparison is equally circular. The only non-circular check is the literal `3224c31c…` pin, and it exists **only** for the baseline (the file contains exactly two 64-hex literals, both that value, at `:955` and `:1308`).

**Failure scenario:** `artifactRoutes` over-derives for the continuation shard — e.g. a client-GET binding that C never requests, or a future row whose `target.query` handling widens a URL. The harness allowlist admits the extra route, `equal(exact.routes, artifactRoutes(...))` matches, `routeDigest` matches the runner's digest of that same table, the `routes` negative control (which pops a route from the *observation*, `read-update-artifact-execution.test.ts:213`) still throws, and nothing fails. The handoff requires the opposite: *"Derive exact routes independently per shard"* and *"establish the continuation's exact pin from its actual captured route table"*.

**Fix:** add `expect(progress.shards[1]!.routeDigest).toBe("<measured>")` plus an explicit expected route count/URL list for the continuation; keep the two baseline pins byte-identical. Related: `equal(report.plannedIds, shard.scenarioIds, "owned plans")` (`:133`) is also vacuous — both sides derive from the same `shard.bundle` object — whereas `plannedManifestDigest` (`:146`) is genuine because the planner re-parses the source bytes.

### 2. `observedIds` is a static alias of `authoredIds`; no pass/fail/not-run partition, no uncovered list, no per-ID report mapping (Medium)

**Where:** `apps/bdptest/test-support/read-update-artifact-execution.ts:253-257`

```ts
authoredIds: set.requirements.filter((r) => r.owner !== null).map((r) => r.id),
observedIds: set.requirements.filter((r) => r.owner !== null).map((r) => r.id),
```

Both fields are the *same expression* over static manifest-derived ownership. No field in the summary is derived from `result.scenarios`. `requiredOwnership` is just `set.requirements` (`{id, owner}`) with no report reference, state or reason, and the 99-uncovered figure appears nowhere in the summary — only in each shard's `uncoveredIds`, which `run` computes from the on-disk coverage file (`read-update-matrix.test.ts:776-778`), not from the validated `set.coverage`.

The plan requires *"all canonical required IDs, each mapped to its single actual report row or an explicit unobserved/unplanned reason"* and *"distinct counts for authored, observed pass/fail/not-run, reviewed whole, and currently uncovered"*.

**Failure scenario:** the two lists coincide today only because the helper throws unless every owned row is `pass`. The record itself asserts observation from ownership, so it cannot represent a partially-observed set, and any later relaxation of the row-state assertions publishes unobserved IDs as observed with no cross-check. A supervisor reading `observedIds` is reading the authored list under a different name.

**Fix:** derive observed IDs from the owning shard's `result.scenarios`, partitioned by state (`pass`/`fail`/`not-run`/`not-implemented`); emit `requiredOwnership` as `{id, shardId|null, reportDigest|null, state|reason}`; add `uncoveredIds` from `set.coverage` (required minus `wholeContract` = 99).

### 3. `cleanupComplete` is a hardcoded literal, not a measurement (Low)

**Where:** `apps/bdptest/src/read-update-matrix.test.ts:755` · `apps/bdptest/test-support/read-update-artifact-execution.ts:125,243`

`cleanupComplete: true` is written into the object returned at `:753-784`, i.e. *before* the `finally` at `:785-790` that actually performs `await target.close()` and `rmSync(directory)`. The summary re-emits it as a literal `true` (`:243`), and the guard `if (!report.cleanupComplete) throw` (`:125`) plus the `"cleanup"` negative control therefore exercise a value the producer can never set to false.

Real failures are still caught indirectly: the runner converts a harness cleanup failure into `cleanupError` and downgrades `state` from `pass` (`runner.ts:816-824`), which fails `equal(row.state, "pass")`, and a throwing `target.close()` rejects `run`. So this is a record-honesty defect, not a leak — the record attests to cleanup it never observed.

**Fix:** assemble the payload, run cleanup, then attach the observed outcome (set false / rethrow on failure); additionally assert no report row carries `cleanupError`.

### 4. Budget accounting excludes set construction; no `budgetRemainingMsAtStart`, per-shard outcome, node counts or RSS (Low)

**Where:** `apps/bdptest/src/read-update-matrix.test.ts:840-853,979-998`

The 90 s abort timer is armed at `:841`, but `started` is taken at `:844` — after `installedArtifactSet()` parses the 3,626,922-byte baseline + 114,182-byte continuation manifests and builds both bundles. `timing[].remainingMs` therefore overstates the remaining cooperative budget by that construction time, and `expect(performance.now() - started).toBeLessThan(90000)` measures a shorter window than the timer. (No false pass is possible: `controller.signal.throwIfAborted()` at `:858`/`:977` is the real gate.) The record also omits per-shard `budgetRemainingMsAtStart` and `outcome/abort` state, per-shard source bytes/node counts, and any RSS sample, though the plan requires *"timings/memory must come from the fresh installed run"*.

**Fix:** take `started` immediately before arming the timer; record per-shard `budgetRemainingMsAtStart`/`outcome`; sample `process.memoryUsage().rss` and record per-shard bytes/nodes.

### 5. `reportDigest` does not digest the written child report (Low)

**Where:** `apps/bdptest/test-support/read-update-artifact-execution.ts:239` · `read-update-matrix.test.ts:981-982`

`reportDigest: digest(result)` covers only the `ConformanceRunResult`, while `${filename}.${shardId}.json` contains the whole wrapper (`observations`, `sessions`, `baselineReceipt`, …). A supervisor cannot verify the digest against the file it was handed without knowing to extract `.result` and canonicalize it.

**Fix:** also record the written file's byte digest and length, or write `result` alone and keep the wrapper fields in the summary.

### 6. Set summary is not checked for credential leakage in the live run (Low)

**Where:** `apps/bdptest/src/read-update-matrix.test.ts:963-998`

`expect(JSON.stringify(observed)).not.toContain(token)` is applied to each shard report, but not to `progress` — the artifact actually written to `BDP_CUMULATIVE_REPORT_PATH`. The unit test proves the `readySummary` whitelist drops arbitrary receipt keys (`read-update-artifact-execution.test.ts:160-162`), so exposure risk is low, but the plan's *"never resolved Authorization, tokens or arbitrary child stderr"* has no assertion on the published object.

**Fix:** add the same two `not.toContain` assertions for `JSON.stringify(progress)` immediately before the write.

### 7. 22 association negative controls assert only bare `.toThrow()` (Low)

**Where:** `apps/bdptest/src/read-update-artifact-execution.test.ts:232`

Every discriminator is asserted with `expect(() => associateArtifactObservations(...)).toThrow()`. `equal()` already produces labelled messages (`artifact-set <label> mismatch`), so a control that trips an *earlier, unintended* check passes silently and the intended discriminator goes untested.

**Fix:** assert the expected label per case, e.g. `.toThrow(/catalog source map/)`.
