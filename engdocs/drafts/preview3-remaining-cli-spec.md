# Preview 3 remaining `bd` CLI: contract and staged implementation draft

**Status:** design draft for Donna; no Preview 3 cutline is implied. This covers the CLI outside generic Bead/Link CRUD, `bd link`, `bd dep`, and graph relationship commands. Those have a separate inventory and wave plan. Source baseline is final Preview 2 `graph-preview2` at `703bb13e91aa2cab2092443319139006d74242c8`, tree `98445b7ac964090e00fb134e77e77396d4fcdf88`. A Preview 3 source branch is not yet qualified. Strict compatibility with Preview 1 or 2 and data migration from any prior product are not release goals. Shipping-product behavior is the starting compatibility target, with explicit reviewed exceptions when preserving it would make the product worse or impose disproportionate cost.

## Evidence boundary and scope

The source-only remaining-CLI inventory is a static reading of [the final Preview 2 source](https://github.com/donnabox/beads/tree/graph-preview2) and tests. A local help sweep traversed 303 Cobra paths using the exact installed final binary, but invoked only `--help`; its local matrix correctly marks every behavior cell `not-run`. Those receipts remain local until reviewed for publication. The final Preview 2 14-phase qualification covers its selected suites, not every command/flag combination. No installed command behavior or shipping parity was tested for this draft. In particular, `bd mail --help` attempted a provider/Dolt probe under a deliberately nonexistent HOME; help is not always side-effect free.

`cmd/bd/graph_preview.go` at exact703 has a command-level graph allowlist and a separate `graphPreviewFlags` check. An admitted parent does not imply that all nested children or inherited legacy flags work. An unlisted command is normally refused before the legacy store opens; `duplicate` and `supersede` have explicit early refusals. Store-free commands may be handled before that gate, so do not infer user-visible refusal from absence in the list alone. A future matrix row must distinguish **help-only**, **source-only**, **passing exact-source test assertion**, **observed final binary on embedded**, **observed final binary on ordinary shared server**, and **observed pinned shipping binary**. Record output and exit code as well as success/failure.

The scope is four classes. They have distinct contracts and should not be admitted as a batch:

| Class | Final Preview 2 source-level position | Preview 3 default disposition (proposed) |
| --- | --- | --- |
| Issue workflows: lifecycle, assignment/claim, work selection, shortcuts, comments/todos, hierarchy, Issue discovery | Many named routes admitted; unsupported flags still refuse. `state set` and `gate` are excluded. | Retain Issue meaning. Preserve shipping behavior where feasible, but verify each flag/output path and record graph-specific exceptions. Do not generalize to arbitrary Beads without a designed meaning. |
| Memory conveniences: `remember`, `memories`, `recall`, `forget` | Named routes admitted, with Memory-specific body/search/overwrite/deletion behavior. | Treat as wrappers over canonical Memory Bead operations until Melinda's accepted Memory record/identity design settles exact semantics. Do not fork the writer or History model. |
| History, status and observability: `versions`, graph-mode `history`, `types`, `statuses`, `status`, `children`, epic reads, `setup claude`, `claude-hook stop`, `serve` | Select routes admitted; graph `history` currently aliases `versions`; HTTP BDP History is absent. | Define the local CLI contract after Polly's shared History/Provenance V2 design. Keep BDP protocol readiness a separate gate. Included preview BDP must work directly without an opt-in switch. |
| Everything else: Issue policy, workspace/database maintenance, integrations, imports/exports, tooling | Cobra registration is visible, but graph admission generally refuses or bypasses it; source-only, with per-route exceptions to verify. | Explicitly refuse until each route has a graph backend, side-effect policy, tests and owner. Store-free status/help/version can be checked early; do not blanket-enable a parent family. |

## Contract that every admitted route must meet

These are proposed acceptance rules for implementation and validation, not claims that Preview 2 already satisfies them.

1. **Scope and dispatch.** The command declares whether it operates on an Issue, Memory, any Bead, a Link, or the workspace. Issue workflow commands reject other resources with a clear error before mutation. An admitted command and each admitted child reach a graph-native implementation; no fall-through to a nil legacy store, hidden legacy write, or silent flag ignore. Unsupported flags and omitted journeys produce a named refusal with a nonzero exit code.
2. **Identity and Type.** Accept the documented ID forms, resolve to a canonical graph identity, and distinguish missing ID, wrong resource class, and unregistered Type. Type displays and accepted names follow Trish's Type contract; no new nominal-Type semantics are inferred from the CLI report. Human and JSON output identify the same resource and revision.
3. **Mutations.** A mutation is atomic across native resource state, required Links, History and revision provenance. It honors actor, read-only/frozen policy, accepted `--if-revision`/force semantics and no-op ownership. Conflicts and invalid inputs leave no partial state. Deletion and recovery behavior follow the shared terminal-revision policy once accepted; no command invents a second deletion model.
4. **Reads and output.** Human output remains useful to a person; `--json` has a stable, reviewed shape and exit/error behavior. Filters, pagination/limits, ordering, hidden/deleted behavior and exact-version reads are specified per command rather than borrowed implicitly from the legacy Issue store. Existing JSON clients are protected where feasible; intentional deviations enter the exception ledger.
5. **Topology and authority.** The route works in installed embedded and ordinary shared-server workspaces where advertised, or explicitly refuses one topology. Provider creation, server permissions and BDP HTTP routes are checked separately. An early refusal must not open or mutate a legacy/production store.
6. **Evidence.** Each admitted matrix row has a positive case, representative invalid Type/ID/flag case, output/exit assertion in applicable modes, read-after-write, guarded conflict/no-op/deletion case when relevant, and a source citation. A command-specific test is required; a broad suite pass is supporting evidence, not row-level proof. Refused rows have an exact refusal test. Both engine results are receipted with exact source/binary/Dolt provenance and zero FAIL/SKIP where applicable.

## Family requirements and deliberate boundaries

### Issue work management (candidate early implementation family)

`close/reopen/defer/undefer`, `ready/blocked`, `assign`, claim/unclaim/heartbeat/reclaim/merge-slot, `priority`, `note`, `comment/comments`, `todo`, `q/quick`, and editor-backed `edit` have distinct data and concurrency rules. Keep `ready`, `blocked`, leases and assignment Issue-only unless Donna accepts a separate Memory work-management model. `children` and epic reads are Issue hierarchy projections over native parent-child Links; they must not change the semantics of blocking Links or generic graphs. `comment`/`comments add` currently append native Issue comments without a graph Issue version: decide with Polly whether that is still the intended revision/attribution contract before changing them. `todo` creates/reads task Issues; `quick` creates an Issue and currently does not support `--parent` in graph mode. These are not generic Bead shortcuts by default.

Acceptance should cover ordinary and graph Issue fixtures in the pinned shipping and final-P2 binaries separately: title/status/priority/assignee, deferred/ready/blocked filters, claim ownership and races, parent-child versus blocks, quick/todo identity, comments/notes append behavior, editor cancellation and write, JSON/human shape, and read-only/guarded errors. Use a controlled editor script, never an unattended interactive editor. Keep `gate`, `state set`, label/tag writers and duplicate/supersede refused until their owners have a complete atomic route, including row isolation and edge-plus-close History where needed. A parent command's presence does not authorize a nested writer.

### Issue discovery (candidate early implementation family)

`search`, `count` and `query` in final Preview 2 are Issue-scoped graph routes, not Memory or Link query. Specify each accepted filter, expression, sort, limit, output shape and parse/error behavior in the matrix. Verify title/ID search, lifecycle predicates, parent/hierarchy and blocked predicates, scalar/grouped count, and query expression errors against pinned shipping behavior. Any broadened resource scope or Link query requires a new design and index/ordering contract; do not infer it from generic list/count. Keep a documented refusal for unsupported selectors instead of silently ignoring them.

### Memory conveniences (depends on Melinda and Polly)

`remember`, `memories`, `recall`, `forget` must agree with canonical Memory create/update/list/show/delete, Type constraints, record identity, exact versions, revision provenance and incident-Link policy. `remember`'s overwrite/no-op behavior, `memories`' search bounds and pagination, `recall`'s body-only output, and `forget`'s refusal for referenced Memory are individually reviewed. Do not widen `forget` to cascade Links by accident. The Memory proposal scenarios selected for Preview 3 become the acceptance cases, including mixed Issue–Memory references. Retain convenience names only if they give a clear ergonomic benefit without contradictory semantics; otherwise document their transition rather than silently removing them.

### History, Types and status (depends on Polly/Trish)

Graph-mode `bd history` currently aliases `bd versions`; it does not imply the ordinary History event/commit view or BDP HTTP History. Polly's accepted shared History/revision Provenance V2 contract decides whether it remains an alias or becomes an attribution/event view. Exact version retrieval, ordering, terminal deletion, no-op ownership, and provenance are required tests. `bd types` must list effective user-facing Bead/Link Types from Trish's registry model without exposing confusing internal generic Type names as choices. `bd statuses`, `bd status --graph`, and `state` reads must accurately describe actual capabilities; `state set` remains refused until the state writer/label ownership decision. `serve` only advertises implemented BDP profiles and topologies. Vickie's reference implementation and conformance suite gate a `bd` profile implementation; neither silently upgrades this CLI workstream's cutline.

### Auxiliary and currently refused routes (rolling backlog)

Classify each of the remaining Cobra paths before implementation:

* **Store-free or observational:** `help`, `version`, selected `status`/`types`, `ping`, `context`, `where`, metrics. Verify whether each actually bypasses graph admission and whether even `--help` opens a provider. Keep side effects explicit.
* **Issue policy:** `label`, `tag`, `lint`, `stale`, `orphans`, `duplicates/find-duplicates`, `duplicate`, `supersede`, `human`, `audit`, `rules`, `gate`, `promote`, `prune`, `purge`, `recompute-blocked`, formula/molecule/swarm/mail/ship/onboard. Decide command by command if a graph analogue is useful; refusal is preferable to partial legacy behavior. The label row-isolation blocker and explicit duplicate/supersede atomicity refusal remain visible.
* **Workspace/database:** `config`, `doctor`, `info`, `schema`, `sql`, `dolt`, `vc`, `branch`, `diff`, `conflicts`, `flatten`, `backup`, `restore`, `compact`, `admin`, `gc`, `migrate`, `upgrade`, `sync`, `worktree`, `repo`, `bootstrap`, `preflight`, `prime`, `quickstart`, other setup/hooks. Each requires a backend/topology/permission/authority contract; a graph command should never mutate an unrelated legacy workspace because it was merely allowed through. Respect per-subcommand driver boundaries (including embedded doctor restrictions).
* **Import/export and integrations:** Iris owns `import/export` and package/identity semantics; ADO/GitHub/GitLab/Jira/Linear/Notion/federation need their own mapping contracts. Data migration into Preview 3 is not a release requirement. A passing importer is welcome only if it independently meets its contract and gates.

## Validation harness and matrix deliverables

**Baseline matrix:** Extend `FINAL-P2-COMMAND-MATRIX.csv` without overwriting help evidence. One row per meaningful command/child/flag path and topology, keyed by stable row ID. Required cells: class/scope, graph admission and flags, source line, final-P2 observed outcome or `not-run`, shipping observed outcome or `not-run`, human/JSON output, exit code, mutation and guard effects, Type/ID inputs, evidence receipt, compatibility category, decision owner, candidate wave. Preserve the 303-path help JSON as immutable input, including the `bd mail --help` error. Check nested child routes; do not mark all children supported from a parent allowlist entry.

**Oracle:** Pin a separate shipping source and installed binary. Run ordinary-workspace fixtures there, then comparable graph fixtures on exact final P2. The existing Oracle A catalog has 523 enumerated ordinary-workspace scenarios and defaults its reference to a merge-base; pin `REF_REF` explicitly and add a graph-aware profile and exception ledger before calling it a graph differential. The `cross_mode_parity_harness_test.go` ordinary embedded/proxied oracle and `graph_preview_*workflow_test.go` are useful inputs, not substitutes for the row matrix. Several graph workflow tests skip the server half when `BEADS_GRAPH_TEST_SERVER_PORT` is unset; a skip is not a server pass.

**Installed runs:** Root owns fresh disposable embedded and ordinary shared-server Dolt 2.1.8 workspaces, one active runner/database at a time. Capture exact source/tree, installed binary hash, Dolt version, workspace configuration, command transcript, exit code and structured output, plus server lifecycle. Never run the help sweep under the real HOME merely to fill a cell. Keep failed/old-base attempts separate. No product source edit proceeds based on a source-only or help-only behavior claim.

**PR acceptance:** Each bounded PR cites matrix row IDs, accepted decisions, positive and refusal scenarios, docs/CLI-reference/JSON-corpus fanout, source test selection, two-engine installed results where applicable, and whole exact-current-merge hosted required gates with independent frozen verification. Update generated docs and golden corpus after behavior is accepted; preserve deliberate refusal/compatibility fixtures. If a route cannot pass a complete journey, keep its refusal in the preview and list it for the next wave.

## Morning design questions for Donna (ask one decision at a time)

1. **Scope of Issue shortcuts:** Should `comment`, `note`, `todo`, `quick` and `edit` remain Issue-only, or should any become generic Bead commands? Recommended default: Issue-only until a Memory meaning is designed. This unblocks the Issue mutation wave.
2. **Compatibility priority:** For Issue commands where graph JSON/exit behavior conflicts with shipping, should we preserve shipping by default and enumerate exceptions, with human prose free to improve? Recommended yes. This determines the differential oracle and golden policy.
3. **Memory convenience names:** Keep `remember/memories/recall/forget` as wrappers over canonical Bead operations once Melinda defines the record, or transition users to generic verbs? Recommended provisional wrappers, with no separate state machine.
4. **History UX:** After Polly's model lands, should `bd history` present revision events/attribution while `bd versions` lists retained snapshots, or keep them aliases for one more preview? Defer until Polly's accepted contract; do not preempt her design.
5. **Auxiliary scope:** Which one or two currently refused families matter to the Preview 3 Memory release experience—if any? Recommended selection only after the memory/CLI matrix exposes a concrete missing journey, rather than a general compatibility sweep.

Questions about label writer, `state set`/`gate`, duplicate/supersede atomicity, package import, and BDP profile semantics remain with their named owners. Their current refusals are constraints to preserve, not facts to silently reinterpret in this CLI lane.
