## Findings

**1. Low — `packages/conformance/src/transactional-observation.ts:292`**
- **Issue:** In the `/next` branch of `resolve().validate`, the single-page fixture bound (`page.next !== null` → `TransactionalHarnessError`) is evaluated *before* the retained-facts comparison against `entry.pageBody`. The bound check is a baseline-establishment precondition, but it runs unconditionally on every GET.
- **Impact:** Once a baseline exists, a target that *changes* its page body on a later read in a way that includes a non-null `next` is reported as `state: "harness-error"` / "receipt page exceeds single-page fixture" instead of `state: "fail"` / "retained receipt page differs from original wire facts". The altered-page oracle the acceptance requires ("Test … altered page") never fires for that shape — the page mutation is attributed to a fixture limitation rather than to the target. Severity is capped because the scenario still reports non-pass and `mustStopMatrixAfter` returns false for an uncategorized harness-error, so nothing is silently passed or halted. The path is untested: `runner.test.ts` `changed-page` mutates `results[0].count`, and `transactional-observation.test.ts:430` exercises the nonterminal page only on the *first* GET.
- **Fix:** When `entry.pageBody !== undefined`, compare first and let any deviation be the `TransactionalReceiptFailure`; apply the `page.next !== null` bound only on the baseline-establishing read. E.g. move the bound check inside the `entry.pageBody === undefined` arm, and add a later-read nonterminal case to the `does not initialize a page baseline…` test.

**2. Low — `packages/conformance/src/transactional-observation.test.ts:372`**
- **Issue:** The commit's central capability claim — distinct names grant only their own target — is asserted only for an *unregistered* binding (`resolve("implicit", pageUrl)`) and for a registered page binding pointed at a *different page* (line 440, `${id}/pages/other`). The cross-direction cases are never exercised, even though the test registers both pointer kinds in the same ledger: a registered root binding asked for the page target (`resolve("/id", pageUrl)`), and a registered page binding asked for the root target (`resolve("/next", id)`).
- **Impact:** Both directions are correct today (they fall out of the shared `target !== value` check at `transactional-observation.ts:255`), but the specific "root does not reach the page / page does not reach the root" guarantee has no regression anchor. A future refactor of the `target` derivation at line 253 could reintroduce an implicit grant without failing any test.
- **Fix:** Add two assertions inside the existing capture-order test after both bindings are registered: `expect(() => f.observations.resolve("/id", pageUrl)).toThrow("not authorized")` and `expect(() => f.observations.resolve("/next", id)).toThrow("not authorized")`.
