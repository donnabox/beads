## Must-fix

**1. Validation/publication sequencing permits an ordinary commit before the packed installed phase. (Severity: High — process/evidence)**
*Location:* plan-v2 § "Validation and publication gates": "Run exact25 source callbacks … **Then root may authorize ordinary commit of exact reviewed bytes**; fresh protocol/server archives, bounded external consumer install, measured … equivalence and explicit release **before exact3 installed callbacks and immediate audits**."
*Issue:* the commit of publication-grade bytes is authorized after static + source validation but before any packed/installed evidence. E is the only external witness of the new Bead behavior and the only phase exercising the built artifact; the plan itself makes a fresh build a prerequisite of installed collection (`realpathSync(entry)` is top-level in the installed file, line 62), so an installed-phase failure after commit leaves a committed candidate whose only external witness failed.
*Impact:* a published/committed candidate can carry unproven installed behavior; it also invites either an amendment of recorded provenance or a successor commit, both of which the project's own practice avoids.
*Bounded fix:* restate the gate as: static (typecheck/format/lint) → exact 25 source callbacks → fresh build/inventory → fresh archives/external consumer + measured equivalence → exact 3 installed callbacks + immediate audits + measured cleanup → **only then** root-authorized ordinary commit of the exact reviewed bytes, with a final re-verification that all 679 tracked bytes are unchanged from the reviewed set.
*Factor root must weigh before choosing wording:* the installed file records `declaredSourceCommit` from `git rev-parse HEAD` (lines 67–69) and `workspaceDirty` from `git status --porcelain` (lines 65–66). Running installed callbacks pre-commit therefore records `workspaceDirty: true` and a HEAD that does not contain the tested bytes — which is plausibly why the current ordering exists. Two honest resolutions: (a) run installed on the working tree, record `workspaceDirty: true`, then commit byte-identical bytes and re-verify hashes (the same discipline already used for dirty-d4 → clean-b76); or (b) keep a pre-installed commit but label it explicitly provisional in the plan, forbid relabeling its records, and require post-installed re-verification before it is treated as the reviewed publication. The plan currently does neither. Root owns the final sequencing and disposition.

**2. No control for an authorization-hidden Bead Event source under an opaque minimum; the accepted native correction is only half-discharged. (Severity: Medium — coverage/traceability)**
*Location:* plan-v2 § "New exact source workload", A (items 9–11) and D (31–32, 34–37); against `native-recommendation-review.md` bullet 2 ("Distinguish deleted retained source from **unknown/hidden** identities in the exact tests") and `bdp.md` 5672–5674 ("Unknown identities **and identities outside the caller's authorization projection** always return the same `404 resource-not-found`").
*Issue:* A/D cover *unknown* (`beads/unknown`, `beads/missing`) and *deleted-but-retained*, but nothing covers the hidden branch. `eventSourceKnown` (`transaction-store.ts:693–703`) is a disjunction of two independent terms — `identities` row presence and `authorization.readPolicy === "all-visible"`. The identities-absent tests exercise only the first. This slice newly routes opaque minima *into* `enter` for subject-bearing sources (previously `snapshotTransactionMinimum` threw pre-entry), so the `eventSourceKnown`-before-minimum ordering at lines 1664–1674 becomes load-bearing for an input class it has never seen. I found no existing coverage: the only empty-policy Event assertion in the repo is `transaction-authorization.test.ts:561`, and it reads the subject-less Scope source.
*Impact:* a nondisclosure-ordering regression on the hidden branch (e.g. `Unproved`/503 instead of uniform 404) would ship untested, and it is exactly the disclosure-shaped failure the spec rule exists to prevent.
*Bounded fix:* add one final owner call to A (11 → 12 readEvents, plus one non-read owner call; combined 25/128/146 totals unchanged): after item 11, call `f.owner.replaceAuthorizationPolicy()`, then read the canonical Bead Event source with the opaque tuple and require `{ kind: "missing", context }` carrying the **new** `authorizationView`, with zero `FROM groups` prepares. Feasibility verified: the flip is reachable with existing APIs (`transaction-authorization.test.ts:329–338` proves `replaceAuthorizationPolicy()` after completed `f.run` transactions yields `readPolicy: "empty"` + fresh view); it must be the last call because generation 1 is one-way (`transaction-store.ts:1914`); it requires no owned/pending receipts (line 1911); and its statement does not match `/FROM groups/`, so the spy count stays clean.

**3. The store-local rename/comment is unspecified while the HTTP rename is mandated. (Severity: Medium — specification inconsistency)**
*Location:* plan-v2 § "Precise production edits": HTTP is told to "rename local `initialFiniteScope` to `initialFiniteMinimumSource`", and sentinel #1 is told to adjust its adjacent comment — but the owner edit only says "replace `initialScope` with a predicate" (`transaction-store.ts:1654`, used at 1658 and 1672).

*Impact:* a predictable code-review finding and a successor cycle on an otherwise one-line edit.
*Bounded fix:* one sentence in the owner-edit paragraph: rename the single local (e.g. `initialMinimumSource`) and require that the two adjacent comments state Scope-or-Bead initial selection, with no other text change in 1639–1680.
