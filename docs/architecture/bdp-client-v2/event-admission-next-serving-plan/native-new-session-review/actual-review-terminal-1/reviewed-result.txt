## Findings

**1. [Medium] D's self-imposed timing budget is the tightest in the repo for the largest request count.**
- Location: plan "New source D" ("work abort3000ms and absolute cleanup-inclusive4000ms ceiling", "Callback retains default5000ms"); `workload.bounds.newDWorkMs/newDCleanupInclusiveStopMs`.
- Issue: D must do, inside 3000 ms of work and a 4000 ms absolute ceiling: local `startTransactionRuntime` (dist import, SQLite create, 2 type descriptors, listener bind), 2 `fetch` POST commits, 30 fresh raw socket exchanges, one live SSE register/frame/drain/close, then `runtime.close()` + directory removal. Every comparable runtime+HTTP callback in this repo takes a 60 s callback timeout with a 45 s work deadline (`packages/server/src/transaction-changefeed.test.ts:1028`, `:1895`); the heaviest default-timeout SSE callback (`packages/server/src/transaction-sse.test.ts:145-222`) performs ~12 interactions, not 32. `vitest.config.ts` sets no `testTimeout`, so 5000 ms is the real ceiling.
- Impact: on a loaded worker the abort fires and is recorded as a hard failure ("work deadline") that is indistinguishable from a real regression; the oracles themselves are fine, so this is pure false-failure risk.
- Smallest correction: give the new callback an explicit timeout (`}, 60000)`) and scale its local budgets into the existing HTTP family (work 45000, cleanup-inclusive 10000). No oracle, status vector, or count changes.

**2. [Low-Medium] B's stated step order contradicts B's own derived read counts.**
- Location: plan "New source B" ("commit a; baseline genesis read yields actual CP1; create spread delegate that records real readChanges calls…") vs `workload.newSource.groups.B` (`readChangesCalls 16` = `baselineReads 4` + `serviceAttempts 8` + `positiveServiceReads 4`).
- Issue: if the baseline read is issued on the raw owner before the delegate exists, only 3 calls per case are delegate-recorded. The legacy analogue does the opposite: the pre-service read goes through `delegatedOwner` and `expect(reads).toHaveLength(4)` (`transaction-changefeed.test.ts:1110`, `:1186`).
- Impact: either a failing exact-count assertion or a report whose `readChangesCalls` silently means something other than what was recorded.
- Smallest correction: one clause reorder — construct the delegate first and issue the baseline through it — or relabel the workload field as owner invocations and fix delegate-recorded counts at 3/12.

**3. [Low] F collapses four rows into one callback without a per-row isolation rule.**
- Location: plan "New source F" ("One exact callback containing four isolated fixture/service rows… Four stores/owners/commits/captures/closes;3clocks. Report four real row records"); legacy analogue is `it.each` with one callback per row (`transaction-changefeed.test.ts:1379-1481`).
- Issue: in a single callback, a failing row aborts rows 2–4 unless per-row `try/finally` + aggregation is mandated. Then "four real row records", 4 closes, and the 0+1+1+1=3 clock total are unreachable, and the failing row's store stays open (F registers no global cleanup).
- Impact: the report is least trustworthy on exactly the failure path F exists to police.
- Smallest correction: require per-row `try/finally` (record + close each row, aggregate failures, attempt all four) and state 4/4/4/3 as the all-rows-attempted expectation.

**4. [Low] B/C/F local ownership deliberately drops `fixture()`/`service()`'s unconditional backstop — say so, and note why counts still hold.**
- Location: plan "Fixtures and common controls" vs `transaction-changefeed.test.ts:84-98` (`fixture()` pushes `owner.close()` + `rmSync(force:true)` onto the afterEach `cleanup` array) and `:513-546` (`service()` pushes `instance.close()`).

Avoiding registration is nonetheless necessary for B/C/F specifically, because afterEach would close/remove *after* each report is emitted, making "verified operation/service closure before removal" unassertable.
- Residual: a failed row now retains an open SQLite handle plus a tmp directory for the rest of the worker process — intended per "unknown or failed drainage preserves the directory", but unstated.
- Smallest correction: one sentence declaring retention-on-failure intentional and the report's closure/directory fields as the recovery signal. No helper edits.
