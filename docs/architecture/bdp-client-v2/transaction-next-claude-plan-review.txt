## Verified correct (so the findings below are read in proportion)

- **Every spec citation checks out.** `3664–3705` epoch/position/view bindings ✓; `5766–5807` consistency fields + minimum contract + conditional ordering ✓; `5280–5296` `catch-up-timeout` as a 503/`after-delay` **direct** code (`bdp.md:5301` lists it in the direct set — plan:106 is right that `readProblem`'s union excludes it, confirmed at `packages/protocol/src/index.ts:453-470`) ✓; `6563–6584` token profile ✓; `4618–4624` receipt ordering ✓; `5734–5753`/`5825–5957` snapshot ✓. Only `5757–5763` is off by one (strict-prefix text is `5758–5764`).
- **The Snapshot/changefeed deferral is justified, not conservatism.** `5899–5936` really does require manifest identity/refetch/HEAD lifecycle, joint Bead+Link capture, independent paging to one anchor, expiry-vs-service-failure distinction and checkpoint retention. `inspect()` (`transaction-store.ts:1287`) is a diagnostic dump with no epoch/view binding. Plan:42–46 is accurate.
- **The subset genuinely sidesteps unresolved Q1.** `authority-read.ts:783-794` resolves `kind === "resource" | "properties"` as a point read with no pagination, and `finish` (`:840-891`) — which is where retained pages resolve, *outside* the owner entry — is unreachable for them. So "defer the retained-page anchor question" is structurally sound for exactly this subset, not a dodge.
- **The seam is feasible as described.** `withRead` rejects async callbacks outright (`transaction-store.ts:553-562`), and both the owner's `enter` (`:218-229`) and the plane's `busy` (`authority-read.ts:953-956, 1022, 1083`) are synchronous mutexes released before any await — so "finite wait outside SQLite, writes usable during the wait, concurrent commit can satisfy a waiter" all hold. A typed behind-error thrown from inside the entry does **not** fence the owner (`withRead` uses `enter`, not `atomic`, so no `fence(cause)` path).
- **Conditional ordering is already safe.** `applyReadHttpSemantics` rewrites only status 200/204 (`read-http.ts:12-13`) and runs after `route()` (`transaction-http.ts:316-323`), so no 304/412 can swallow a 409/410/503, and the fixture's `Accept: image/png` refusal cases confirm the barrier also precedes 406. Plan:63's "no bodyless 304/412 may bypass the barrier" is already true by construction — worth saying so rather than re-deriving it.
- **Q3 is a real product question.** `bdp.md:3685-3687` forbids *clients* from ordering position spellings and says nothing about an authority's duty toward a token it cannot decode. There is no located refusal. The plan's refusal to invent a lexical comparison or to call undecodability an exhausted wait is correct.

## Findings

### F1 — MEDIUM-HIGH — Barrier refusals must carry current Scope context; the plan's context contract covers only 200/304/412

- **Location:** plan:60–63 (points 4–5), plan:129. Code: `transaction-http.ts:59-66` (`problem()` sets no BDP context), `transaction-http.ts:70-75` (`context()` is applied only on success paths and on `perform` results carrying an observation).
- **Authority:** `bdp.md:5793-5796` — *every* Transactional Scope-bounded read reports epoch/view/position of the prefix it observed. The narrated fixtures the plan itself cites make this explicit: `refusal-before-conditional-foreign-view` (409), `-expired-epoch` (410) and `-catch-up-timeout` (503) each carry `BDP-Scope-Epoch/-Authorization-View/-Scope-Position`, and `transactional-http-contracts.test.ts:277-287` reads `response.headers["BDP-Scope-Position"]` off the refusal and asserts `observedPosition ===` it. This was also already flagged (review INFO: "T3 should not treat `{200,304,412}` as the exhaustive context list").
- **Impact:** the plan's only context predicate is "Resource/properties and receipt GET+HEAD cover 200/304/412 with same current context." Nothing requires context on the three refusals the slice exists to add, and `problem()` attaches none — so the natural implementation ships context-less 409/410/503 and passes every listed gate. Separately: the 503 must report the **final** attempt's observed position, not the first probe's; "retry the lookup each turn" (plan:84) gets the lookup right but the plan never says which observation the refusal reports.
- **Fix:** replace the one predicate with a status-partitioned one: `401`/`404` carry **no** context (non-disclosure — already pinned by `transaction-http.test.ts:263` `expect(response.headers.has("bdp-scope-position")).toBe(false)`); `409`/`410`/`503` carry the current context, with the 503's `BDP-Scope-Position` equal to the last observation taken before the budget expired; `200`/`304`/`412` carry it as today.

### F2 — MEDIUM — Successor base is pinned to the pre-fix commit, and both successors edit the same gates

- **Location:** plan:114 ("Start new isolated successor from 8844"), plan:135 ("Existing private method/POST admission matrix unchanged").
- **Impact:** F-A/F-B/F-C land first, in `transaction-http.ts` at exactly the lines this slice rewrites: F-A adds a `hasMinimumControls` evaluation on the command branch (before `:252` `service.submit`), F-B rewrites `methodResponse` (`:172-177`), and this plan moves/narrows the same `hasMinimumControls` gates at `:292`/`:295`. Starting from `8844` means textual conflict plus a semantic one: after F-A, `hasMinimumControls` means "refuse" on POST and "honor" on approved GETs, so the single shared helper has to split. And plan:135's "unchanged" predicate is stated against a base that will no longer be the parent.
- **Fix:** pin the base to the F-A/F-B/F-C successor's tip, not `8844`; restate the POST predicate as "the F-A refusal remains in force and is not weakened by the new GET barrier", and name the split helper (e.g. `suppliedMinimumControls()` returning the raw tuple, with per-branch policy) so the two slices don't collide on one boolean.

### F3 — MEDIUM — Narrowing the gate by route class silently drops it for the alias, scope-probe and discovery branches

- **Location:** plan:103–104 ("use point/receipt service path only for approved routes"), plan:136–138 ("Incomplete/unsupported header combinations remain explicitly unqualified"). Code: `transaction-http.ts:295` (gate sits *before* `readRoute`) vs `read-http-routing.ts:28-38` (probe `204`, alias `307`, `discover` all resolve **before** `routes.perform`).
- **Impact:** route class is only known inside `perform(parsed)`, so the obvious implementation moves the gate there — and then `GET …/alias/x` with a minimum control returns `307` while silently ignoring the control (the F-A defect class, reintroduced on a different route), the scope root returns `204` with no context and no gap, and a malformed Read URL returns its `400`/`404` instead of the gap. That breaks the plan's own stated invariant.
- **Fix:** keep a gate ahead of `readRoute` and narrow it by classifying first — `classifyAliasPath` and `requestFromUrl` are both exported from `read-request.ts:142,935`. **Simplification:** plan:107–108's "per-request router closure may pass immutable controls" is unnecessary — `read-http-routing.ts:40` already calls `routes.perform(parsed, request)` (and `routes.alias(aliasPath, request)`), so the raw tuple is reachable per request from one stable route object with zero new state. Dropping the per-request closure removes the cross-request-state hazard the plan then has to rule out.

### F4 — MEDIUM — The `catch-up-timeout` envelope has no protocol-side type or schema path, and the ownership rules foreclose adding one

- **Location:** plan:105–106, plan:113 ("do not edit … schemas … public index/exports"). Code: `read-update-problems.ts:4-17` (`ReadUpdateProblemCode` omits all three Transactional codes), `read-update-values.ts:43` (`problem → #/$defs/readUpdateProblem`), `packages/protocol/schemas/bdp-v0.schema.json` (`$defs/transactionalProblem`, `directProblemCode` **already exist**, with no `READ_UPDATE_VALUE_SCHEMA_REFS` entry and no exported parse).
- **Impact:** `readProblem()` can't produce it and `parseReadUpdateProblem()` will reject it, so the 503 body must be hand-built in `transaction-http.ts`. It is then the one new wire shape in the slice with no schema-backed check anywhere, and the done-predicate matrix (plan:116–141) never asserts its shape. A wrong `type` family suffix, a missing `retry`, or a stray member passes build, typecheck, lint, both smokes and every listed regression.
- **Fix:** cheapest within the stated ownership — assert the emitted body against `#/$defs/transactionalProblem` from the canonical bundle inside `transaction-http.test.ts` (the protocol tests already drive Ajv off that bundle) and add that to the matrix. If a reusable `parseTransactionalProblem` is wanted instead, it needs explicit root approval because it touches the protocol public surface.

### F5 — MEDIUM — The plan silently decides an unlocated ordering question for Resource reads (non-disclosure 404 vs. tuple/behind refusal)

- **Location:** plan:89–90 ("evaluated after captured authorization and **before materialization**"), plan:126–127. Code: `authority-read.ts:789` — the uniform `404` for an invisible/absent Resource is decided *inside* `materialize`, i.e. after the proposed seam.
- **Impact:** for receipts the plan correctly follows `bdp.md:4618-4620` (non-disclosure **before** the minimum check). For Resource/properties reads the plan asserts the opposite order by seam placement and never says so. No authority covers it: `5805` orders epoch/view/minimum only against *conditional shortcuts*, and the Read non-disclosure rules don't mention the tuple. So the slice adopts a semantic the plan's closing sentence ("No new product semantics are adopted by this plan", plan:164) disclaims. There's no disclosure oracle either way — the refusal depends only on Scope-level state — so this is an honesty/record defect, not a leak.
- **Fix:** state the decision and its reasoning as a predicate (the defensible one is tuple-first: a `404` computed from a prefix the client explicitly declared insufficient reports non-existence it hasn't established — cf. `5786` "never reports success with an older position"), and note the deliberate asymmetry with the receipt order at `4618`. Or add it to §Unresolved and keep both surfaces gapped. Don't leave it implied by line order in a file.

### F6 — MEDIUM — Inventory omits `transaction-comparison.ts`, the existing finite monotonic no-restart wait, and the plan adds a second one with no clock/budget seam

- **Location:** plan:9–40 (inventory), plan:76–79, plan:98–101, plan:121–123. Code: `transaction-comparison.ts:29-54` — `budgetMs` (validated finite positive, default 1000), injectable `now` defaulting to `performance.now()`, `deadline = now() + budget` computed **once**, loop with injectable `wait`, `temporarily-unavailable` on exhaustion, and the in-code comment "Same original deadline and no …". It is already in the smoke allowlist (`scripts/smoke-executables.mjs:218-221`).
- **Impact:** the plan's closest existing primitive — which already implements, and already tests, its hardest done-predicate ("no deadline restart per attempt", plan:123) — is absent from an inventory whose stated purpose is to separate existing primitives from missing contracts. Consequence: a second bespoke deadline, and more concretely, plan:103–109 never adds a wait/clock seam to `TransactionRuntimeTestSeams` (`transaction-runtime.ts:35-39`, which today exposes `scheduler`, `clock`, `maximumOperations`, `comparison`). Without one, "exhausts a finite original monotonic budget before 503" is not executable at the HTTP level — it becomes a shape assertion, exactly what plan:123 is trying to avoid.
- **Fix:** add `transaction-comparison.ts` to the inventory; reuse or extract its loop parameterized on the exhaustion outcome rather than writing a second; add an explicit `barrier: { budgetMs, now, wait }` seam to `TransactionRuntimeTestSeams` and say in the matrix that the budget is private and **not** added to advertised `limits` (plan:79 is right, just unlocated).

### F7 — LOW-MEDIUM — `service.receipt` is synchronous and untracked; the wait changes its signature and extends graceful close

- **Location:** plan:98–101, plan:132. Code: `transaction-service.ts:236-249` — `receipt()` returns a value, not a Promise, and is the one public method that does **not** go through `run()`, so it never joins `active`; `close()` awaits `Promise.allSettled([...active])` (`:257`). HTTP calls it synchronously at `transaction-http.ts:285`.
- **Impact:** two unstated changes. (a) `TransactionServiceReceiptResult` becomes a Promise and the receipt branch becomes `await`ed — a signature break the plan's "existing `readReceipt` … paths stay compatible" (plan:86) doesn't cover, because it's the *service* boundary that moves. (b) A waiting receipt read becomes tracked work, so `close()` — which today cannot be delayed by a receipt GET at all — can now block for the full budget, on top of F-E's already-accepted connection destruction. Plan:132 asserts close releases tracked work "within the finite bound" but never says the bound is newly reachable from a read.
- **Fix:** state the signature change explicitly; decide and pin whether `close()` cancels in-flight waits (preferred: cancel at `accepting = false`, return the current observation or 503) or awaits them, and assert the chosen one. Note that a new receipt read during close still throws via `check()` (`:242`), unchanged.

### F8 — LOW-MEDIUM — The plan never says whether HEAD performs the wait

- **Location:** plan:50–52, plan:129 (both say "GET/HEAD" and "GET+HEAD" without distinguishing the barrier).
- **Impact:** `bdp.md:1999-2001` lists the decisions HEAD retains (authorization, query, cursor, negotiation, precondition) and does not name minimum-position; `5809-5813` extends HEAD rules to receipt URLs and insists HEAD acknowledges nothing. An implementer optimizing away a connection-holding wait on HEAD would return current context below the required position — `5786`'s one hard prohibition, reached through HEAD. The reverse reading (HEAD waits) means a HEAD can hold tracked work for the whole budget, which interacts with F7.
- **Fix:** one predicate: HEAD makes the identical barrier decision including the wait, and an exhausted HEAD is a bodyless 503 with the same context and `Retry-After`. `applyReadHttpSemantics` already strips the body correctly (`read-http.ts:40-46`), so this is a statement, not new code.

### F9 — LOW — Per-turn retry is tighter than the existing precedent and makes the receipt wait a write loop

- **Location:** plan:84–85 ("Retry the actual lookup each turn"). Code: `transaction-store.ts:1271-1278` — `readReceipt` runs inside `atomic()` (`BEGIN IMMEDIATE`), and `retainedReceipt` calls `expireRow` (`:300-340`), which issues `DELETE`/`UPDATE` on retention. Precedent: `transaction-comparison.ts:54` waits `Math.min(5, deadline - now())`, not per-turn.
- **Impact:** each retry is a write transaction. A ~1s budget retried per scheduler turn is hundreds-to-thousands of `BEGIN IMMEDIATE` cycles contending with the very commit the waiter needs in order to succeed, so plan:122's "writes remain usable during the wait" is technically true but degraded, and done-predicate 1 ("concurrent real mutation advances a waiting read") becomes cadence-sensitive.
- **Fix:** adopt the existing bounded backoff instead of per-turn retry; keep "re-read every attempt, never cache a receipt across the wait" (which is the correct half of plan:84–85).

### F11 — LOW — Unresolved Q2 understates the authority that exists; two of its three forms are already decided or structurally safe

- **Location:** plan:152–156 ("no tuple-level malformed policy was located").
- **What is actually located:**
  1. **Repeated field is already safe, by construction.** `transaction-runtime.ts:129-131` builds the `Headers` with `append`, so duplicates join as `"pos-2, pos-2"` — a value that cannot match `[A-Za-z0-9_-]{1,256}` (`6565-6570` forbids whitespace and commas). The authority therefore can never "choose an occurrence", which is the specific hazard the directly analogous field rule guards against: `3172-3178` rejects a key outside the profile *and* a repeated `Idempotency-Key` "rather than choosing an occurrence", with `malformed-request`. That precedent is a field-level token-profile rule, not a body-syntax rule, and the plan's sweep for "general header clauses" missed it.
  2. **On receipt URLs a direct `400` is excluded.** `4588-4593` states a row's statuses are **exhaustive** for that target and method, apart from the shared `406`, GET/HEAD `304`/`412`, and the internal-fault bodyless `500`; the receipt row (`4602`) lists `200/401/404/409/410/429/503` and no `400`. So whatever the eventual malformed-tuple answer is, it cannot be `400` on a receipt URL — while point Resource reads have no exhaustive table and inherit ordinary request failures, so `400` is available there. That asymmetry is itself the located normative content, and it constrains any later answer.
  3. Residual genuine question, correctly unresolved: a well-formed token in a *partial* tuple (bare epoch/view with no minimum; minimum with no epoch/view) has no located decision.
- **Impact:** as written, Q2 reads as "nothing found", which risks a later slice re-deriving it from scratch or answering `400` uniformly and violating `4588`. Note also the standing tension the plan inherits: the development gap uses bodyless `500`, which `4591` reserves for "an unexpected internal fault" — acceptable as the existing posture, but it is the carve-out being spent, and plan:156 should say so.
- **Fix:** rewrite Q2 as the three items above — two settled, one open — and record the `4588` constraint as a boundary on the open one.

### F12 — LOW — "Whole minimum-read contract for the subset" needs two inapplicability statements

- **Location:** plan:71–72, plan:116–141.
- **Impact:** `5784` gives the authority three choices — return at-or-later, **wait or route to an eligible replica**, or refuse. This fixture implements only waiting. That is correct and complete, because `3655-3661` assigns one logical mutation authority and defines replication as consuming a snapshot/changefeed, not writable replicas — but the plan never says it, so "whole contract" looks like it's eliding a branch. Similarly `5821-5823` requires the CORS policy to allow the minimum-position fields and expose the three response fields *when cross-origin access is enabled*; this fixture refuses `Origin` outright (`transaction-runtime.ts:155-157`), so the clause is inapplicable rather than unmet.
- **Fix:** two sentences — replica routing is structurally inapplicable under `3655-3661`; the CORS clause is conditional and its condition is off. With those, the whole-subset claim is airtight; the full-profile disclaimer (plan:71–72, 162–164) is already correctly scoped and does not overclaim.

### F13 — LOW/INFO — "Same owner entry" is a mutex for Resource reads and a SQLite transaction for receipts

- **Location:** plan:57–63 (point 5), plan:81–83. Code: `withRead` wraps `enter()` only (`transaction-store.ts:508`) — no `BEGIN`; `readReceipt` wraps `enter(() => atomic(...))` (`:1271-1272`).
- **Impact:** for point reads, `readContext()`'s `metadata("position")` and the resource `SELECT` land in two separate implicit transactions inside one `busy` entry. In-process this is airtight (every writer also goes through `enter`), so the predicate holds — but it holds by single-process serialization, not isolation, which means "captured from the same successful entry" cannot be falsified by an injected interleaving and is asserted by shape. Receipts genuinely get `BEGIN IMMEDIATE`.
- **Fix:** say which guarantee each path has, so the matrix doesn't imply a fault-injection witness that can't exist for the Resource path.

## Bottom line

The plan's judgment calls are sound: the scope cut is real (point reads genuinely can't reach the retained-page question), the citations are accurate, the "don't invent semantics" discipline is honest, and the whole-subset vs full-profile distinction is correctly drawn and not overclaimed.

Two things I'd fix before implementation starts: **F1** (the slice's three new refusal statuses have no context requirement, and `problem()` attaches none) and **F2** (the base is pinned behind the F-A/F-B/F-C successor that edits the same gates). **F3**, **F4** and **F5** are the next three — F3 because the obvious implementation breaks the plan's own unqualified-surface invariant and the fix is also a simplification (`perform` already receives the request), F4 because the one new wire shape would be the only unvalidated one, F5 because the seam placement answers a question the plan claims to leave open.

On your specific asks: the seam design is viable without leaking TX fields or adding global mutable state — `sourceContext` is already a generic source-private slot and the delivery-option whitelist (`authority-read.ts:1026`) is the only thing needing a widening, which is additive and leaves Read/RU behavior byte-identical. The one genuinely unresolved product question is Q3 (undecodable/foreign opaque token), plus the narrowed partial-tuple remainder of Q2; the rest of Q2 has located authority (F11), and Q1 is correctly deferred for this subset but is also correctly *not* claimed as covered.
