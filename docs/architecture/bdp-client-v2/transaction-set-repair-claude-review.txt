## Findings

### 1 — MEDIUM‑LOW · type-safety · `packages/server/src/transaction-batch.ts:462`
**The operation-local failure branch checks only `code` and `operationIndex`; every other problem member is unchecked, because `Omit<ReadUpdateProblem,"code">` collapses to a bare index signature.**

`ReadProblem` declares `readonly [key: string]: unknown` (`packages/protocol/src/index.ts:329`), which `ReadUpdateProblem` inherits. `Omit<T,K>` is `Pick<T, Exclude<keyof T, K>>`; with a string index signature `keyof T` is `string | number`, `Exclude<string|number,"code">` is `string | number`, and `Pick<T, string|number>` is a mapped type that yields `{[x:string]: unknown; [x:number]: unknown}` — the declared `type`, `status`, `retry`, `diagnostics`, `diagnosticsTruncated` members are absorbed and lost. So branch 1's problem type is effectively `{[k:string]: unknown} & {code; operationIndex: number; operationName?: string}`.

**Failure scenario:** a new (or edited) operation-local return site writes `{ ok: false, problem: { code: "revision-mismatch", operationIndex: 0 } }` — no `type`, no `retry`, no `status` — or misspells `retry` as `retryy`. It type-checks. `transaction-store.ts:1016` writes `problem: result.problem` straight into the receipt, where `receiptProblem` requires `type`, `code`, `status`, `retry`; the result is a schema-invalid stored receipt caught only if a test happens to validate that path. This is the exact "a future branch that forgets it now type-checks" hazard F4 was raised to close, and it survives for four of the five required members.

Two secondary consequences: the index signature also admits `limit` (as `unknown`) on branch 1, so an operation-local `limit-exceeded` *with* `operationIndex` and an arbitrary `limit` still type-checks — meaning the `SelectorLimit` probe at `:827-833` is rejected only because it omits `operationIndex`, which is the same property the `MissingIndex` probe already shows, not an independent constraint on `limit` values as the report's F4 wording suggests. And nothing prevents a whole-transaction limit from fabricating an `operationIndex` via branch 1; the no-fabrication invariant is enforced at runtime (`:714-746`) but not at the type boundary.

**Fix:** stop building the branch with `Omit` over an index-signature type. Restate the operation-local problem members explicitly (`type: string; status: number; retry: RetryDisposition; code: ReadUpdateProblemCode | "cardinality-violated"; operationIndex: number; operationName?: string; pointer?: string; diagnostics?: readonly ValidationDiagnostic[]; diagnosticsTruncated?: boolean`), or narrow `ReadProblem`'s extension point so `Omit` stays structure-preserving. One-line confirmation: `type B = Omit<{a: string; [k: string]: unknown}, "b">; const x: B = {}` compiles.

*Pre-existing shape (the `Omit` predates this commit), but it is squarely in F4's scope and it is what makes the "compiler-checked" claim narrower than stated.*

### 2 — LOW‑MEDIUM · diagnostic correctness · `packages/server/src/transaction-batch.ts:686-702`
**The matched-Resource cap is charged before the cardinality check, so a request that explicitly bounded its match count gets a permanent 413 instead of the operation-local 409.**

`matchedResources += selected.length; if (… > matchMaximum) throw` runs at `:686-687`; the `cardinality` min/max comparison is at `:688-702`.

**Failure scenario:** `{"operation":"deleteWhere","collection":"beads","selector":"$[?@.properties.done]","cardinality":{"max":10}}` against a collection where 5 000 Beads currently match. The client's own guard says "fail unless at most 10 match," and the spec's answer is `cardinality-violated` — 409, `retry: "after-state-change"`, with `operationIndex`. Instead the cap fires first and returns a transaction-wide `limit-exceeded`, 413, `retry: "never"`, with no `operationIndex` and no `operationName`. A conforming client reads `retry: "never"` as "the request as written can never succeed" and gives up permanently, although the identical request succeeds once the live match count drops below the guard. The operation that caused the failure is also no longer identifiable in the receipt.

**Fix:** move the cardinality comparison above the counter increment, so a cardinality violation returns its operation-local 409 without charging the budget. The cap still fires for every request that passes its own guard, and the existing F3 probes (which rely on cap-before-cardinality only because a visibility regression would overshoot both) keep working if their asserted code is the one they actually intend.

### 3 — LOW‑MEDIUM · durable materialization · `packages/server/src/transaction-batch.ts:686`
**F2 bounds the number of result entries, not their size, so the prior finding's concrete degradation mode is still reachable — now at ~3 800 matched Resources instead of 500 000.**

Each `updateWhere` result entry carries the full postimage (`:578`, `outcome.resource`), and per-Resource representation is capped at 256 KiB (`transaction-store.ts:991`, `resource-evaluator.ts:1055`), properties alone at 64 KiB. At the new cap: 4 096 × 64 KiB ≈ 256 MiB of receipt JSON in a single `receipts.receipt` TEXT value, re-parsed in full by `parseReceipt` on every `observeReceipt`/`admit` replay (the recursive `freeze` is bounded by `receiptPrefix`, so only parsing is unbounded); 4 096 × 256 KiB = 1 073 741 824 bytes, above SQLite's default `SQLITE_MAX_LENGTH` of 1 000 000 000, so a ~3 815-entry maximal-representation set still trips the value ceiling → `atomic()` abort → pending retraction, exactly the mode the prior review described.

**Failure scenario:** a 200-byte `updateWhere` over 4 000 Beads with large properties completes and writes a ~1 GB receipt (or aborts the owner transaction and leaves the key pending until reopen). The report's own limit paragraph and `transaction-implementation-progress.md:745` do disclose "not a bound on whole-collection scan work, memory or receipt byte size," so this is not a misstatement — but it means F2 reduces the prior MEDIUM finding by ~122× rather than closing it, and the surviving ceiling is not disclosed numerically anywhere.

**Fix:** charge a byte budget alongside the entry count — accumulate `Buffer.byteLength` of each pushed result entry against a private constant well under SQLite's value limit (the same `limit-exceeded`/`transaction.matchedResources` or a `transaction.mutatedResources` sibling needs no new receipt vocabulary). At minimum, state the reachable receipt ceiling in the progress note next to the 4 096.

### 4 — LOW · efficiency · `packages/server/src/transaction-batch.ts:679`
**The F3 visibility traversal runs once per candidate with no memoization, on the full unbounded candidate population, before the F2 cap can fire.**

`isResourceVisible` allocates a fresh `seen` set per call and resolves each local endpoint through `tx.resource` (`resource-evaluator.ts:589-596`), which is an uncached `SELECT * FROM resources WHERE id=?` plus a JSON parse (`transaction-store.ts:725-737, 912`). The previous `options.policy.canRead(record)` was `() => true`.

**Failure scenario:** `deleteWhere` on `links` over a 500 000-row link collection now performs ~500 000 index reads + 1 000 000 extra point lookups and 1 000 000 extra `storedRecord` parses — a ~3× amplification of the scan the report concedes is unbounded — all inside the exclusive `BEGIN IMMEDIATE` owner transaction, blocking the whole authority, and all before `matchedResources` is even computed. Today the Bead branch is free only because `ownedLinks` cannot exist in a transaction store; once owned-Link support lands (explicitly in "remaining scope"), each Bead candidate walks its owned component with a per-candidate `seen` set, making the pre-cap filter super-linear in the collection size.

**Fix:** hoist a `Map<string, boolean>` visibility memo (and a stored-row cache) across the candidate loop and pass it into the traversal, so each Resource is resolved and judged once per operation rather than once per candidate path.

### 5 — LOW · unreachable admitted field / doc precision · `packages/server/src/transaction-batch.ts:577`, `docs/design/transaction-implementation-progress.md:768`
**F1 admits `revisionProvenance` on `deleteWhere` citing spec 4250-4255, but no supported execution path can apply it, and the note attributes that inertness to Beads only.**

Spec 4250-4255 gives `DeleteWhere` provenance exactly one destination: "the fresh source versions of any owned Links it deletes." The evaluator does build that `sourceRecipe` with the supplied provenance (`resource-evaluator.ts:961-978`), but the transaction evaluator rejects the result outright: `if (outcome.sourceRevision !== undefined) throw new Error("unsupported owned-Link transition")` (`:577`) — a bare `Error`, not a Problem, so it escapes the limit catch, aborts `atomic()`, and leaves the key pending until reopen retraction. For unowned Links deletion mints no version, so provenance is inert there too. Net: `revisionProvenance` on `deleteWhere` is currently a no-op in every reachable case, and reachable *only* as a no-op.

The progress note says "Deleting Beads mints no version, so their supplied provenance is inert," which reads as though Links are the case where it is honoured. The four execution receipts (`transaction-set.test.ts:624-712`) use a link type with no `ownsOutgoing`, so there is no evidence either way.

This is not a regression — the owned-Link throw predates this commit and the collection routing at `:704-726` already reached it without provenance — and owned-source fanout is listed in remaining scope. **Fix:** state in the note that set-deletion provenance is inert for both collections in this slice because owned-Link transitions are unsupported, and (separately, outside this slice) convert `:577` from a thrown `Error` into a refusal Problem so an owned-Link selection does not strand the idempotency key.

### 6 — LOW · residual divergence · `packages/server/src/transaction-batch.ts:675-679`
**The *predicate* is now Read-equivalent; the candidate *rows* are not.**

The Read route reaches `isResourceVisible` through `checkedGraph`, whose `accept` applies `validateServerBead`/`validateServerLink` and the Link body-vs-index endpoint agreement check (`authority-read.ts:595-606`) and raises an `integrity` error otherwise. The set path calls `readStoredResource` directly, so under a store whose Link body endpoints disagree with the `source`/`target` index columns, visibility is judged from the body while `incidentLinks`/`outgoingLinks` use the index, and the Read route would refuse to serve the same row. Corruption-only, and consistent with the entire mutation path (no mutation code has ever used these validators — `read-request.ts:798-812` is called only from Read), so this is not newly introduced. Flagged because the report's "Read-equivalent visibility" framing invites the stronger reading. **Fix:** nothing in this slice; record it with the other two policy exclusions in the note rather than letting "shared predicate" stand for "shared projection."

### 7 — LOW · test coverage · `packages/server/src/transaction-set.test.ts:809-821`
