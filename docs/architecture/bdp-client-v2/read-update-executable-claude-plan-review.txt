## F1 — Cumulative bundle has no single catalog source, but a bundle carries exactly one `catalogDigest`

**Severity:** High
**Location:** plan §Concrete scope 1 / Expected files (`artifact-bundle.ts`); `packages/conformance/src/artifact-bundle.ts:35-39,54-58,99-105,162-164`; `packages/conformance/test-support/profile-contract-plan.ts:28,80-109`
**Evidence:** `ConformanceArtifactBundleSources.catalog` is one `ConformanceArtifactSource` documented as "Exact source bytes", and `ConformanceArtifactDigests` has a single `catalogDigest` that lands in the run report (`runner.ts:236-240,379`). The canonical selection is assembled from six classified files and exposes `catalogDigests: Record<file,digest>`; its merged catalog is a synthesized object, `{ catalogVersion: 1, scenarios: [...byId.values()] }` (`profile-contract-plan.ts:109`), never serialized bytes.
**Impact:** Any single `catalogDigest` for the cumulative bundle is either a hash of a re-serialization — an identity no exact source reproduces — or an arbitrary pick of one of six files. Both break the artifact boundary's exact-bytes discipline, and the report would carry a catalog identity that does not denote the contract actually selected.
**Fix:** State in the plan that the source-private factory takes the `ProfileContractSelection` itself rather than catalog bytes, and define `catalogDigest` as sha256 over canonical JSON of `selection.catalogDigests` (a map of exact file → exact-byte digest, reproducible from sources alone). Record the per-file map verbatim in the progress artifact.

## F3 — Three named cases cannot count their rows under the whole-contract rule

**Severity:** High
**Location:** plan §Concrete scope 2; `packages/conformance/catalog/read-update-v1.json`
**Evidence:**
- `read-update.singleton.update-bead` cites both patch application *and* "A semantic no-op update … succeeds with outcome `updated` and the retained revision." The plan's sequence (create/read/guarded update/read/delete/read) has no no-op leg.
- `read-update.singleton.delete-bead` carries four citations, including "`incident-links-exist`: a Bead deletion reached while a live Link is incident upon the Bead" and "After a Bead or Link is deleted, ordinary `GET`, `view=properties`, and, for a Bead, `view=links` return the same `404` `resource-not-found`". "delete/read" reaches at most the ordinary GET; the refusal leg additionally needs `create-link`.
- `read-update.singleton.idempotent-retry` cites "a singleton whose key is retained, in flight, conflicting, or expired answers exactly as the corresponding sequence member would" — a four-state, sequence-comparative obligation. "Duplicate-key exact replay" covers only *retained*.
- `read-update.singleton.create-bead` cites "If `id` is omitted, the authority allocates one"; the plan never says the case omits `id`.

For contrast, `read-update.singleton.expected-revision` *is* fully covered (matching guard applies + stale fails `revision-mismatch` with unchanged state), and `read-update.discovery.document` is coverable provided the default-order leg actually reads a collection and verifies canonical-URI order — note the installed target always emits `limits`, so the "omitted `order`" observation must be an absence check plus an ordering read.
**Impact:** Under the approved rule, these rows must be reported uncovered despite being executed — or the slice over-claims.
**Fix:** Either extend the cases (no-op update; Link-incident delete refusal plus `view=properties`/`view=links` 404s; one `id`-omitted create) or move `update-bead`, `delete-bead` and `idempotent-retry` onto the explicit uncovered list *in the plan*, so the expected selected-ID set is honest before authoring starts.

## F4 — P1's frozen boundary emits three identities; `ServedProfileConfiguration` demands nine fields, three of them unobtainable without parallel calculation

**Severity:** High
**Location:** plan §Concrete scope 3 and §P1 integration dependency ("reuse those values rather than parallel identity calculation"); `vickie-update-installed-repair/packages/server/src/installed-reference-process.ts:48-56`, `installed-reference-configuration.ts:154-176`, `installed-reference.ts:120-126`; `test-support/profile-contract-plan.ts:134-151,216-241`
**Evidence:** `qualification.ready` carries `scope`, `claimEligible`, `configurationIdentity`, `artifactIdentity`, `payloadIdentity`. That supplies `installedPayloadDigest` ← `payloadIdentity` and `installedContractsDigest` ← `artifactIdentity`. But `policyDigest` and `authenticationDigest` are never emitted separately: `access.policy.identity()` and the credential `{principal, tokenDigest}` list are folded *inside* the single `configurationIdentity` preimage (`installed-reference-configuration.ts:154-164`). `sourceCommit` (required `/^[0-9a-f]{40}$/`) is emitted by nothing. `profile` and `history` are likewise absent from the ready message (`history: false` exists only inside the identity preimage).
**Impact:** Three required fields cannot be sourced from the frozen target boundary. The harness must fabricate or recompute them — precisely the parallel identity calculation the plan bars — while the plan asserts all of them are "captured from the actual target/configuration boundary".
**Fix:** Decide in the plan between (i) requesting a P1 successor that also emits `policyIdentity`, `authenticationIdentity`, `profile`, `history` and a build-stamped commit, or (ii) reshaping `ServedProfileConfiguration` to mirror the real boundary — one `configurationIdentity` replacing the policy and auth digests — and declaring `sourceCommit` a caller-asserted launcher input, not a target observation. Then stop describing the whole set as boundary-captured.
