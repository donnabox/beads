## Findings

**1. Medium — the new freeze's non-`available` branch is never asserted.** `transaction-store.ts:912-920`: when `projection.detail !== "available"` or `results` isn't an array, `projected === projection` (and under `all-visible`, `=== receipt`), so `freezeReceiptValue` receives the whole parsed receipt rather than a fresh spread wrapper. The new fixture calls `assertDeepReceiptFrozen` only on completed/available receipts (`singleRead.receipt`, `root.receipt`) and on pages. The failed and expired receipts are read via `store.receipt()`, which bypasses `observeReceipt` entirely (`:2180-2189`).
Fix: after the failure step, `assertDeepReceiptFrozen(store.readReceipt("p", failed.id).receipt)`; after expiry, `const r = store.readReceipt("p", seed.id); expect(r.receipt?.detail).toBe("expired"); assertDeepReceiptFrozen(r.receipt); expect(store.readReceiptPage("p", pageUrl)).toMatchObject({ kind: "expired" })`. The last also covers `:2251`, the one page branch the delta leaves untested.

**2. Medium — `accepts byte-bounded singleton and wrapped set content across the former depth boundary` is now degenerate.** `transaction-submission.test.ts:708-732`: both table rows are `"receipt"`, so `kind` is constant and the 27/28 distinction asserts nothing; worse, `toMatchObject({ kind: "receipt" })` passes for `status: "failed"`. The claim this edit encodes — depth 28 is accepted *and executed* — is unasserted.
Fix: `toMatchObject({ kind: "receipt", receipt: { status: "completed", results: [{ outcome: "matched", count: 0 }] } })` and drop the now-meaningless `kind` column.

**3. Low/Medium — `finishes %s synthetic syntax before admission` dropped `position`/`identities` from its oracle.** `:861, :882-883`. Splitting `expect(f.store.inspect()).toEqual(before)` into `resources`/`groups` comparisons was necessary (the deep 0-match `updateWhere` now commits and binds `deep_key`), but it silently stops asserting that a 0-match commit does not advance `position` — the exact invariant the new deep test asserts for its own noop step.
Fix: add `expect(f.store.inspect().position).toBe(before.position)` and `expect(f.store.inspect().identities).toHaveLength(before.identities.length + 1)`.

**4. Low/Medium — the `noop` step cannot detect a key-order-only resource rewrite.** It asserts `position`/`groups` unchanged and compares the receipt resource with `assertDeepSubmissionValue`, which sorts keys — so a no-op that re-persisted properties as `{copy, deep}` (exactly what the root `replace` supplies) instead of `{deep, copy}` would pass. The `failed` step does assert `resources` unchanged; the noop step does not.
Fix: `expect(JSON.stringify(store.inspect().resources)).toBe(JSON.stringify(beforeNoop.resources));`.

**5. Low — `sweep` parses each available receipt twice.** `:565` `parseReceipt(stored.receipt)` then `:484` inside `expireRow`. On the 40 KB/12000-deep rows this doubles the cost the change exists to make affordable. Fix: pass the parsed receipt into `expireRow` as an optional third argument.

**6. Low — `SELECT *` now materializes full deep receipt text for rows it immediately discards** (already-`expired` compacts), so maintenance cost scales with total retained keys. Disclosed by the new comment and accepted per the brief; noted only for the `SELECT *` column cost. Durable fix would be a `detail` column — out of scope.

**7. Informational — cycle behavior changed shape.** The recursive versions overflowed the stack; the iterative one would spin indefinitely. All inputs are `JSON.parse` output or freshly built wrappers, so acyclic. Neither old nor new has an `isFrozen` short-circuit, so "traverses already-frozen parents" is preserved, not newly introduced. No action required.

**8. Execution-dependent risk to confirm on first run:** 12000 is the first depth this suite actually *stores* (prior deep bodies were parsed then refused), so it is the first exercise of `JSON.stringify` at that depth in `json(receipt)` and resource serialization.
