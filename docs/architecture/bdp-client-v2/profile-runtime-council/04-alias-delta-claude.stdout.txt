**1. HIGH — Repoint and delete preconditions are never observed, so the "across repointing and deletion" half of the reference-idempotency observation is not established**

- **File/section:** `packages/conformance/development/read-update-manifest-v1.json`, scenario `development.read-update.alias-recorded-targets` actions `repoint` (snapshot L1896–1918), `delete-original` (L2019–2040), `original-reassigned` (L2400–2422); scenario `development.read-update.pinned-references` actions `repoint` (L3150–3172), `delete-alias` (L3238–3259). Also `read-update-coverage-v1.json` row `read-update.alias.reference-idempotency` (L526–586).
- **Issue:** Every alias-mutating precondition step in these two scenarios asserts only `/status == 200`. No assertion — not an alias-result `outcome`/`target`, not a read-back, not a fresh-key resolution — establishes the alias's intermediate value. The retention assertions that follow (`recorded-after-repoint`, `cross-slot`, `retry-recorded`, `changed-external`) return `beads/a` whether the repoint happened or not.
- **Reachable trigger:** A receiver whose `put-alias` repoint or `delete-alias` is a silent no-op passes **all** assertions in `alias-recorded-targets` and `pinned-references`. I walked both hypotheses action by action: under "repoint no-ops," `recorded-after-repoint`, `cross-slot`, `recorded-after-delete`, `original-still-recorded` and `new-request-current` all still pass (the later `original-reassigned` put re-establishes `beads/b` and its outcome is not asserted). Under "delete-alias no-ops," the same set passes.
- **Impact:** The row that was flipped to `bounded-observation` claims "Recorded targets and transient fresh-locator comparison are observed across repoint/delete/reassignment"; the *reassignment* leg is genuinely discriminated (`original-still-recorded` vs `new-request-current`), the *repoint* and *deletion* legs are not. The prose in `README.md` L162–163 and `update-implementation-progress.md` L86 both assert the repoint/delete legs.
- **Fix/next step:** Assert the alias result on `repoint`/`delete-original`/`fresh-repoint`/`delete-alias` (`outcome: updated`/`deleted`, absolute `target`), or insert a fresh-key probe of the new state before each retained replay. Both are already in the packet's vocabulary: `new-request` (L1645–1674) asserts a put-alias `/body/outcome`, and `alias-absent`/`still-absent` (L1552, L1626) show alias GET read-backs work.

**1b. MEDIUM (same class, narrower trigger)** — `alias-recorded-misses` action `assign` (L2674–2696) and `unassign` (L2819–2840) likewise assert only `200`. Nothing establishes that `alias/missing` was live at `recorded-miss`/`absolute-miss`/`direct-is-different` time, which is precisely the clause under test ("An originally recorded miss remains a miss even if that alias is later assigned", spec L3208–3209). **2. MEDIUM — `read-update.alias.allocation-avoids-aliases` flipped `omitted` → `bounded-observation` with no assertion that can detect a violation of the row's obligation**

- **File/section:** `read-update-coverage-v1.json` L435–458 (status flip and bindings); manifest scenario `development.read-update.alias-allocation` L626–857.
- **Issue:** The row's obligation is "An authority never allocates a Bead id whose segment is a live alias path" (spec L2947–2948). The bound assertions observe allocation *shape* (`canonical`, `in-scope`, `root`, `single-segment`, `nonempty`), read-back of one property, `alias-path-taken` on an explicit create, and alias survival. **No assertion compares the allocated segment to the live alias path** (`alias/reserved`). The limits field says collision skipping "is NOT exercised or qualified," and the revised next-steps text (`README.md` L182–184) says "live-alias allocation sampling does not establish that behavior" — i.e., the packet itself states the binding does not bear on the row.
- **Reachable trigger:** An allocator that minted segment `reserved` would produce an id colliding with the live alias path. Whether `reserved-bead` would then still return `alias-path-taken` is unspecified in the supplied excerpt (precedence between `identity-taken`, spec L2945, and `alias-path-taken`, L2946, is defined only for alias puts at L2951–2955, not for Bead creation), so detection is incidental at best.
- **Impact:** The headline count moves to "48 rows have bounded observations" with one row whose status is carried by adjacent, non-probative evidence. A reader scanning statuses rather than `limits` strings draws the wrong conclusion.
- **Fix/next step:** Add one cheap assertion that the allocated id is not `{scope}beads/reserved` (single-sample, but it makes the row's obligation at least falsifiable), and either revert the status to `omitted` with category `needs-controlled-fixture` or retitle the evidence as allocation-shape-only. Longer term, the controlled allocation fixture the README already schedules.

**3. MEDIUM — `allocate.canonical` observes WHATWG URL serialization idempotence, not BDP canonical-segment grammar; the limit does not say so**

- **File/section:** `apps/bdptest/src/development-matrix.test.ts` L54 of the diff (`canonical: new URL(identity).href === identity`); manifest assertion `allocate.canonical` (L724–730); coverage limits L454–456.
- **Issue:** `new URL(x).href === x` catches dot-segments and some malformations, but not percent-encoded octets, uppercase hex, or unsafe characters that the URL parser leaves untouched. An allocated segment such as `A%2Fb` satisfies `canonical`, `inScope`, `root == "beads"`, `childSegments == 1`, `emptySegments == 0`.
- **Reachable trigger:** Any allocator emitting a percent-encoded or non-safe-segment local ID; the observation reports it as canonical.
- **Impact:** The spec's canonicality rule (L2108–2111: "a noncanonical encoding — is rejected, never normalized") and the safe-segment grammar are not observed, while the assertion id reads as if they are. The assertion name is the only description a reader of the inventory gets.
- **Fix/next step:** Add a safe-segment regex observation on the child segment, or rename/limit the assertion to "URL-serialization-stable" and state the grammar as an explicit limit on the row.

**4. MEDIUM — The packet encodes a normative reading of pin participation in semantic identity that the cited spec section arguably excludes, and omits the conflicting sentence from its citations**

- **File/section:** `read-update-catalog-v1.json` row `development.read-update.pinned-references` L330–366 (cites §Sequence-local Resource references "The pin is provenance, not a constraint…" and §Idempotency keys "Opaque external URIs and Pinned References are compared byte-exactly as written"); manifest `changed-pin` (L3390–3427) and `removed-pin` (L3429–3463) assert `idempotency-conflict`.
- **Issue:** The cited §Sequence-local block also contains (spec L2430–2431) "It does not participate in Link identity or Reference comparison." The catalog row quotes the surrounding sentences but not that one, while the manifest pins the behavior that changed/removed pin bytes produce `idempotency-conflict`. The reconciliation — that "Reference comparison" means denotation equality, distinct from a member's *semantic identity* under §Idempotency keys — is nowhere stated in the packet.
- **Reachable trigger:** Any reviewer or implementer reading the row's citations concludes the opposite behavior is required.
- **Impact:** A diagnostic-only packet is asserting an interpretation of a contested boundary. That is the "no new product decisions" risk, in the one place where two cited clauses pull apart.
- **Fix/next step:** Either cite the excluding sentence and record the reconciliation in the row's `limits`, or treat this pair of assertions as a spec question before binding them. I am flagging the interpretation, not asserting the implementation is wrong — under §Idempotency keys alone the asserted behavior follows.

**5. MEDIUM — The asserted `validation-failed` diagnostic is byte-identical across five distinct causes, while the cited clause requires a diagnostic "that names the cause"**

- **File/section:** manifest `alias-invalid-targets` actions `local-alias` (L946–956), `absolute-alias` (L1016–1026), `link` (L1084–1094), `external` (L1152–1162), `opaque` (L1220–1230), `retained-invalid` (L1312–1322) — all assert `/body/diagnostics` deep-equals the single message *"an alias put's target must be a canonical in-Scope Bead reference; an alias, a Link, or an external URI is not admitted"*. Catalog citation at L236 and spec L2961–2962.
- **Issue:** The message restates the rule and enumerates all three rejected categories; it does not name which applies. Five materially different inputs (local alias, absolute alias URL, Link path, external `https` URI, opaque `urn:`) are pinned to the same string. The row's limit (L484–486) says only "One fixed development diagnostic message is asserted; no authority-specific wording is proposed for other implementations" — it does not disclose that cause-naming is unobserved.
- **Reachable trigger:** Any of the five actions; the observation cannot distinguish a cause-naming receiver from a constant-string one.
- **Impact:** The bounded observation for `read-update.alias.non-canonical-target` reads as covering the diagnostic obligation; it covers presence and shape only.
- **Fix/next step:** Either have the development receiver name the specific category and assert per-case messages, or extend the limit: "diagnostic presence and shape only; cause-naming is not observed."

**9. LOW — Dead, misleading `target` placeholder in `allocated-live`**

**10. LOW — Identity observation is coupled to the trailing-slash spelling of `execution.scope`**

`development-matrix.test.ts` diff L48: `identity?.slice(execution.scope.length).split("/")`. With a scope lacking a trailing slash, `root` becomes `""` and `emptySegments` becomes 1. It fails loudly rather than silently, but `root`/`childSegments`/`emptySegments` are computed before `inScope` is known, so an out-of-Scope id yields meaningless values that are nonetheless reported. **Fix:** derive segments from `new URL(identity).pathname` relative to the scope path, or compute only when `inScope`.

### Checks that came back clean (stated so the gaps above are not read as the whole picture)

- All 59 `scenario.assertion` references in the new coverage bindings resolve to assertion ids that exist in the corresponding manifest actions; no dangling references.
- Action ids are unique within each new scenario; idempotency keys do not collide across different operations within a scenario (including the sequence-member keys `pin-creator`/`pin-dependent`, which share the namespace per spec L3168–3170).
- The retention/conflict logic of `alias-recorded-targets`, `alias-recorded-misses` and `pinned-references` matches §Idempotency keys L3193–3212 clause by clause for the *fresh-locator* legs: `new-locator` (unrecorded locator resolved anew → equal → replay), `new-locator-rechecked` (repointed → conflict), `new-locator-missing` (deleted → locator-specific unresolved identity → conflict), `new-locator-restored` (resolved anew again → replay, proving retry-time witnesses did not mutate retained state), `cross-slot` (recorded locator in another reference slot, equivalent absolute spelling), `direct-canonical` (direct reference compares without alias resolution), `distinct-miss` (two misses not equal), `direct-is-different` (recorded miss ≠ live canonical). Each of these is discriminating against the plausible wrong implementation.
- `changed-pin` isolates pin bytes with an NFC/NFD pair (`past:\u00e9/%2F` vs `past:e\u0301/%2F`); `changed-external` isolates external-URI case. `retained-state` establishes that the three conflicting retries left the Link untouched.
- `renamed-local` cannot pass vacuously: re-execution of `createBead` on the existing `beads/made` would fail, so the retained replay plus `@renamed` → `beads/made` resolution is established, as is `operationName` repositioning per spec L3258–3260.
