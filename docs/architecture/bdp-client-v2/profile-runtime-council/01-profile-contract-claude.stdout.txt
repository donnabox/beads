### F1 — High — Transactional admission of `historicalResolution` lost — **REGRESSION**

**Where:** `docs/specs/bdp.md` §Discovery profile membership, lines 3714–3743 (table 3734–3743); with §Scope discovery line 1048, §Historical resolution 1580–1583, §Read discovery 1087–1093, §Read+Update discovery 2002–2006.

**Issue:** Base `a9bcf9ed:2137-2140` read: *"All three discovery definitions optionally admit the closed `historicalResolution: { "version": 1 }` member. It describes Historical resolution, **distinct from the Transactional `history` Scope-history member**."* Head retains admission only for Read (1089) and Read+Update (2005). §Transactional discovery (3678–3712) states no closed member list, and the one exhaustive per-profile membership statement — the table at 3734–3743 — has **no `historicalResolution` row**. The disambiguating clause was deleted too, leaving prose at 3720–3721 (*"The history, receipt, snapshot, changefeed, and Event members are required only in Transactional and prohibited in both lower profiles"*) with nothing to distinguish `historicalResolution` from those members.

**Reachable trigger:** Build a discovery validator or generate closed discovery types from §Discovery profile membership. A Transactional Scope that implements the inherited History capability (1580–1581: *"A cumulative profile inherits it without requiring it"*) MUST advertise `historicalResolution` (1582: *"Discovery advertises it only as…"*) but has no admitting rule. Symmetrically, reading `historicalResolution` as one of the prohibited "history members" contradicts 1089 and 2005.

**Impact:** Cumulative-boundary contradiction on the single member that carries the optional History capability across all three profiles. Transactional + History discovery is unspecified; a generated closed `transactionalDiscovery` type could reject a required member.

**Fix:** Add `historicalResolution | optional | optional | optional` to the table at 3734–3743, and restore one clause distinguishing it from the Transactional Scope-history fence members.

**Provenance:** narrowing happened inside `a9bcf9ed..e9361d77` (`e9361d77:1101` reads *"The Read discovery definition optionally admits…"*); head then dropped the paragraph entirely. Unverified: whether `schemas/bdp-v0.schema.json` still admits it — schema not in this packet.

### F2 — High — Permanent tombstones for operations that commit nothing — **BASELINE**

**Where:** `docs/specs/bdp.md` §Outcome retention, lines 3311–3321.

**Issue:** The Scope-lifetime tombstone class includes `updated` *"including a semantic no-op"*, while the same sentence asserts *"tombstone storage is therefore bounded by the committed effects, as identity tombstones already are, and no principal can grow it with requests that commit nothing."* A semantic no-op commits nothing: 2122 (*"retains the existing revision"*), 2165–2166 (*"mints no revision and records no attribution"*), 3589 (*"No-ops retain the old revision and context"*), 5557 (*"emits no `updated` Event"*). The analogy also fails for effectful updates: identity tombstones are one per identity ever allocated; key tombstones are one per committed **operation**, unbounded over a fixed Resource population.

**Reachable trigger:** An authenticated principal repeatedly submits `update-bead` with the Resource's current `properties`/`metadata` and a fresh `Idempotency-Key`. Each returns an `updated` disposition → "committed state" → MUST retain a compact tombstone for the lifetime of the logical Scope.

**Impact:** Unbounded permanent durable-storage growth per principal with zero committed effect — exactly what the paragraph claims is impossible. The stated bound is also unverifiable in conformance.

**Fix:** Exclude semantic no-ops from the committed-state tombstone class (re-executing a no-op under a forgotten key is harmless, so nothing is lost), and restate the bound as one tombstone per committed effect rather than claiming parity with identity tombstones.

**Baseline:** identical at `a9bcf9ed:4386-4395`. Section diff of §Idempotency keys → §Durability and recovery shows only provenance-label removal plus one cross-reference removal between base and head — the idempotency/retention/recovery normative text is otherwise unchanged.

### F3 — Medium — Boundary test exempts all shared sections — **NEW CODE**

**Where:** `packages/conformance/src/profile-catalog-boundaries.test.ts:32` and `:70`.

**Issue:** `owner = 0` for every `##` heading that is not one of the three Part titles, and `expect(owner).toBeLessThanOrEqual(rank[scenario.requiredProfile])` always passes when `owner === 0` (minimum rank is 1). At head, `## Conformance index and informative end matter` (`bdp.md:6536`) and all its subsections are owner 0: `### Normative conformance matrix` (6538), `#### Owned-Link wildcard conformance rows` (6565), `#### Numeric-model conformance rows` (6582), `#### History conformance rows` (6596), `#### Read+Update conformance rows` (6640), `#### Transactional conformance rows` (6732), `### Deferred model features` (6907). The entire preface (`bdp.md:1-209`) is owner 0, exempted only by the one hard-coded check at test line 72.

**Reachable trigger:** A scenario with `requiredProfile: "read"` whose `requirement.anchor` is `#transactional-conformance-rows` satisfies both assertions.

**Impact:** The guard cannot detect mis-profiled citations into shared end matter — which is where the per-profile obligation row tables actually live — so it delivers less than its comment at lines 10–11 claims (*"A valid quote/anchor alone cannot establish profile applicability"*). Secondary: inserting any new `##` heading inside a Part silently resets owner to 0 for the remainder of that Part, and the three spot checks at lines 57–59 anchor near each Part's start, so they will not catch it.

**Fix:** Treat owner 0 as "not part-owned" and fail unless the anchor is on an explicit shared-anchor allowlist; separately assert the exact expected set of `##` headings so an inserted `##` breaks the test instead of silently widening it.

### F4 — Medium — Test's anchor universe diverges from the document's — **NEW CODE**

**Where:** `packages/conformance/src/profile-catalog-boundaries.test.ts:12-43` (`headingOwners`, slug at 34–37).

**Issue:** The ownership map is built from ATX headings only, so the document's two explicit anchors are invisible: `bdp.md:362` `<a id="references"></a>` — which has **no heading at head** (no `References` heading exists) — and `bdp.md:2370` `<a id="batch-local-resource-references"></a>`, preserved across the rename to `### Sequence-local Resource references` (2372). Both resolve: the spec links to the second at `bdp.md:2471`, and `spec-present-contract-map.md:44` links to `#references`. Separately, the local slugger collapses whitespace runs (`.replace(/[ \t]+/g,"-")`) where GitHub emits one hyphen per space, so `## Part I — Read` registers as `#part-i-read` while the rendered anchor is `#part-i--read`.

**Reachable trigger:** A catalog requirement citing `#references` or `#batch-local-resource-references` fails `expect(owner, label).toBeDefined()` — reported as an unknown anchor, not a boundary violation — though the anchor resolves. Conversely a citation of the non-resolving `#part-i-read` is accepted and mapped to Part I.

**Impact:** The test's notion of a valid anchor diverges from the document's; the two preserved compatibility anchors carry no part ownership at all, so profile applicability for that material cannot be established by this guard. Plausibly the cause of the "two citation migrations" at `spec-present-contract-map.md:85-86` — i.e. catalogs moved off resolving anchors to satisfy the test.

**Fix:** Index `<a id=>`/`<a name=>` anchors with their enclosing part's ownership, and use the repo's shared slugger (or `github-slugger`) rather than a local approximation so ownership and link resolution agree. Restore a real heading for `#references` or retarget its citers.

### F5 — Medium — Undisclosed alias existence oracle in key comparison — **BASELINE**

**Where:** `docs/specs/bdp.md:3199-3204` (§Idempotency keys), with 3292–3299 and 3489–3491.

**Issue:** A previously unrecorded alias locator is resolved for key comparison *"through a store lookup, without filtering the alias by the principal's Authorization View"* (3200–3202). The comparison outcome is observable: equal → retained disposition replayed; not equal, including a miss → `idempotency-conflict`. The defense at 3294–3297 addresses only Resource disclosure, not the existence bit of the alias→target mapping, while 3489–3491 asserts *"aliases are not an enumeration oracle"* and 3452–3454 admits exactly **one** deliberate exception to that posture (`identity-taken`).

**Reachable trigger:** A principal whose original member recorded locator `A` → canonical Bead `X` retries the same key with locator `B`. `B` is resolved now, unfiltered; replay vs. `idempotency-conflict` reveals whether `B` currently resolves to `X`, for a `B` the principal's Authorization View need not project.

**Impact:** A second, undisclosed exception to the no-enumeration-oracle posture — one bit per probe, bounded to the principal's own key namespace. Not a Resource-content leak.

**Fix:** Either acknowledge it as an accepted exception in the same explicit terms as `identity-taken`, or state that the only distinguishable fact is "does locator L resolve to the target this key already recorded."

**Baseline:** identical at `a9bcf9ed:4275`.

### F6 — Medium — `changeContext` admission on `deleteLink` is Type-dependent or inert — **BASELINE**

**Where:** `docs/specs/bdp.md:3577-3579`, with 3580–3581 and 3590–3591.

**Issue:** *"The member appears on create/update Bead and Link, **owned-capable deleteLink**, including their sequence forms"* reads two ways. (a) `deleteLink` always admits it. (b) Only `deleteLink` on a Link whose Type is owned by its source admits it — which requires a generic client to consult a Type Descriptor to know whether a request member is admitted, contradicting the uniformity principle at 183–185 (*"A generic client does not need a Type Descriptor to make a request or parse a response"*). Under (a), `deleteLink` on a non-owned Link mints no version, so the context is recorded nowhere (3590–3591) yet is preserved in semantic mutation identity (3580–3581).

**Reachable trigger (reading a):** Delete a non-owned Link with `changeContext: {"message":"x"}`; a retry that omits the member is a different semantic identity → `idempotency-conflict`, whose retry disposition is `never` (3394), for an input with no recorded effect.

**Impact:** Either a uniformity violation or a permanently unrecoverable retry caused by an inert input.

**Fix:** State admission in Type-independent terms, and either exclude context from semantic identity where the operation mints no version, or say explicitly that inert context still binds the key.

**Baseline:** identical at `a9bcf9ed:3423`.
