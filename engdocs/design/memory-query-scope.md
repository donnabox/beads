2. **Result-specific contracts and pointer roots.** Default complete Resource JSON applies to Resource results, not automatically to search hits, graph views, reference-only endpoints, computed/grouped rows or ephemeral assessment graphs. Hit/aggregate rows require explicit access to their own non-Resource fields; graph output must distinguish per-Resource masks from protected graph context. Target Resource bodies remain opt-in; exact target references do not. Evidence and provenance may be explicitly projected out, but their omission cannot create an attestation or imply absent evidence. Field masks do not change the assessed group, judgment or claim population. Auto-retain mandatory context for inclusions; refuse omissions that would corrupt it. These requirements protect meaning, not every optional field or an entire assessment transcript.

Melinda finds this compatible with the query model. It is a declared array-valued projection, not preservation of cardinality or original indexes. Within an assessment result, the complete subject array and required reference revisions remain protected. ## Accepted query-language decisions

### Population selection

Donna accepted explicit population flags, with Beads as the default when neither is supplied. Working spelling:

```sh
bd query --beads 'type is Constraint'
bd query --links 'type is Conformance'
bd query --beads --links 'metadata.reviewed = true'
```

The flags select candidate populations; selecting both takes their union, not an intersection. They do not add a stored field or declare a new universal root Type. With neither flag, the population is Beads; `--beads` alone selects Beads, `--links` alone selects Links, and both select their union. Existing Issue-query compatibility remains explicit rather than redefining the pure population model. A proposed `bd link query EXPRESSION` wrapper supplies Link-only selection to the common operation; this is an intended wrapper, not a command currently implemented in the inspected source. Its empty/conflicting population overrides must be defined rather than silently broadening Link-only scope.

Resource result shape/rendering is Cleo's workstream. Donna asked to settle population and relationship semantics here first, then compare with Cleo; the examples below do not select a competing result envelope or output grammar.

### Relationship capabilities; spelling under review

Donna endorsed correlated directional relationship-existence predicates and explicit bounded walks, while remaining neutral on spelling. A relationship match binds one actual Link and its corresponding neighbor so predicates on the two apply to the same pair. Incoming/outgoing direction is explicit; Link Type tests retain exact versus refinement-family meaning. Negation tests for absence within the declared authorized read context, not global absence of hidden state.

Repeated traversal is an explicit bounded query operation. It does not declare every traversed Link semantically transitive. Depth/resource limits, cycles/shared nodes, reference resolution and incomplete-read behavior need precise rules. Domain-specific implication (such as Requires closure) remains defined by its Type contract; arbitrary References, Subject To and conformance claims do not inherit those implications.

Before choosing grammar, Donna requested a [primary-source survey of graph query approaches and relevant standards](graph-query-language-survey.md). The research compares Cypher/openCypher, Gremlin, SPARQL, ISO GQL, SQL/PGQ and GraphQL, with a short recursive-rules comparison. It is informative input, not a language or conformance selection. Compare pattern matching with traversal composition; keep output contract work with Cleo. The prior `this -[r]-> p` existence example is illustrative, not adopted syntax or an implemented command.

The follow-up [backend portability proposal](query-backend-portability-proposal.md) weighs SPARQL explicitly and examines PostgreSQL and SQLite execution. Donna accepted the recommendation on 2026-10-19: a shared typed query model, the accepted predicates, and a small Cypher-style relationship fragment. Full SPARQL is deferred as a possible facade. This selects the design direction, not a complete grammar, implementation, output envelope or BDP amendment. SQL sketches and representative wrapper mappings should test it before grammar freezes.

Donna accepted the proposal's [first relationship cases](query-backend-portability-proposal.md#first-relationship-cases) on 2026-10-19: candidate existence returns each candidate once, Link results retain parallel identities, reachable-Bead sets deduplicate, and individual path enumeration is explicit. Flat requirement views return reachable Constraints; explanatory graph views preserve shared descendants and cycles. Seed selection, traversal pruning and post-walk filtering are distinct. These select result semantics rather than syntax or an output envelope. An isolated SQLite check exercised eight SQL cases; PostgreSQL execution and Beads wrapper equivalence remain unverified.

### Exact Type and refinement-family selection

Donna accepted these predicate forms during the query-language review:

```text
type = Policy
type is Constraint
```

`type = T` matches exactly the candidate's declared Type identity. `type is T` matches T itself and the transitive family of Types refining T, including future refinements. These are Type tests for both Bead and Link candidates; they do not change the candidate collection or imply graph traversal. `type is Conformance` therefore includes concrete Addresses, Satisfies, Violates and their refinements; abstract Conformance has no direct instances.

Type names in examples stand for explicitly resolved Type identities. Ambiguous names fail rather than selecting an arbitrary Type; arbitrary property strings are not rewritten as identifiers. Canonical spelling, name-resolution mechanics, precedence and the remainder of the grammar still need design. Neither accepted form silently reinterprets shipping Issue-query syntax. Existing BDP exact-Type/family filtering provides the semantic reference; adopting CLI spelling does not rename a wire parameter or add a portable Selector operator without shared-contract review.

For discussion, ordinary predicate composition can look like:

```text
type is Constraint and properties.status = "ratified"
```

The explicit property path remains valid under the accepted field-resolution rule below. Boolean spelling, missing-value behavior and status conventions remain open. A recorded status remains an authored value, not verified approval.

### Field resolution and property shorthand

Donna accepted bare property names, reserved Resource names, and explicit metadata/property qualification:

```text
type is Decision and status = "ratified"
metadata.team = "platform"
properties.type = "internal"
```

A bare ordinary name resolves to the candidate's property of that name. Resource fields use reserved names, including `id`, `type`, and Link `source`/`target`; the complete reserved-name set must be defined before the grammar is finalized. `metadata.…` explicitly addresses metadata. `properties.…` remains an equivalent explicit form for property access and is required to disambiguate a property colliding with a reserved Resource name. Thus `status` and `properties.status` address the same property; `type` and `properties.type` address different values.

Resolution does not fall back between properties and metadata according to which happens to exist, and does not depend on a candidate's Type-specific schema or field presence. A property with a reserved name remains accessible through explicit qualification. Nested paths, quoting/escaping of unusual keys, missing/null semantics and case rules remain to be specified; this decision does not adopt the legacy metadata parser's treatment of dots as literal key characters.

The inspected Issue query uses bare predefined fields plus explicit `metadata.…`; it does not yet implement generic Type-property lookup. The new design must explicitly preserve the agreed shipping compatibility boundary. Some current field operators have special semantics, such as title equality meaning substring matching. The accepted pure equality/contains rules below replace that ambiguity in the new model; legacy compatibility stays separate.

### Equality and explicit text matching

Donna acknowledged explicit substring matching as a capability of the new query model and directed that the pure model not support legacy field-dependent equality. `=` means equality consistently; `contains` expresses substring matching explicitly:

```text
title = "Export"
title contains "export"
type is Decision and status = "ratified"
```

The equality form compares the complete property value under the shared value-comparison contract; it does not become substring matching for particular field names. The `contains` form is a separate predicate that can be composed with ordinary selection. Donna selected literal substring matching for `contains`: `%`, `_`, `*` and other pattern characters have no wildcard or regular-expression meaning. An expression such as `title contains "100%"` searches for the literal substring `100%`. A possible `value matches regex` predicate is deferred unless needed. Donna selected case-sensitive `contains` by default, with an explicit case-insensitive option; `bd search` uses that option by default. The option's concrete spelling and Unicode case-folding/normalization rules, plus treatment of non-string/missing values, still need specification. `bd search` should reuse the selected text-matching semantics rather than define another text engine. No SQL-LIKE wildcard behavior is implied by these examples.

Shared BDP text support must be designed as a justified new query capability with Trish; it is not an extension solely to preserve legacy CLI equality. The current BDP Selector has no substring operation, so this decision does not itself select an amendment, wire spelling or implementation.

### Lumen defaults for value expressions

Donna directed us to follow Lumen by default after reviewing missing/null and explicit conversion behavior. Use the inspected intended-design corpus described below as the reference for value operations; this does not adopt the entire Lumen language or its runtime. She subsequently clarified that Lumen's prohibition on exceptions from functional expressions need not apply here: query expressions may report explicit evaluation errors. Previously accepted Beads Type-family tests, population selection and graph semantics remain explicit Beads constructs.

For ordinary optional property reads, absent and present-null yield null. Preserve physical Resource JSON and permit explicit key-presence tests to distinguish the stored forms. `??` is short-circuit, right-associated and null-only: it preserves false, zero and empty strings. No `undefined` value or missing-field three-valued predicate model is introduced. Consequently, ordinary `status = null` matches absent or present-null status, `status != "ratified"` includes absent status, and grouping by the read value combines absent/null. Presence plus value can distinguish the groups. This supersedes the earlier proposed missing-value unknown behavior and the earlier distinct missing/null group default.

Reuse Lumen's established expression vocabulary where applicable, such as `in` for array membership/physical record-key presence and `??` for explicit defaults. Its nullable `number(text)`/`bool(text)` parsers are reference behavior, not a required Beads error model. Recommend explicit strict conversions that report an evaluation error on invalid input; do not silently turn conversion failure into null, a skipped row or a nonmatch. A separately named error-tolerant conversion may be added if needed. `??` handles null and does not catch evaluation errors. Exact query function names, conversion tables, error scope and typed lowering still need specification; no query runtime support or general exception-handling syntax is claimed.

Lumen itself distinguishes required dynamic access, which can fail, from optional/safe access. Beads' convenient optional-property shorthand must be documented as such; it does not make every required/index access safe. Lumen also rejects statically disjoint comparisons and rejects `??` on unconstrained `any`. How query schemas, heterogeneous populations, narrowing and dynamic values provide equivalent checks is a design task. Do not silently turn those errors into nonmatches, introduce truthiness or import Lumen's optional-record equality into arbitrary raw Resource JSON. Any required Beads adaptation must be called out explicitly.

CLI partial-result flags, exit statuses and output envelopes are separate from these language-value defaults. Their remaining choices stay provisional.

### Open compatibility issue: legacy text matching

The existing Issue query interprets `title=…`, `description=…` and `notes=…` as case-insensitive substring matching; the corresponding `!=` forms negate that match, with additional field-specific conventions such as empty-description values. This differs from BDP Selector's exact value comparison. Compatibility handling must account for that existing behavior explicitly rather than silently change existing queries. It does not belong in the pure query model, whose equality is consistent across fields.

Donna directed us to log this as a compatibility issue, not extend BDP solely to preserve the legacy product behavior. A legacy mode for local-only Dolt users is a candidate solution, not an adopted mode, flag, default or backend restriction. [Compatibility item recorded in7656](https://github.com/gastownhall/beads/issues/7656#issuecomment-6280729620). Janet's existing shipping compatibility register owns the disposition; no separate tracker or compatibility waiver is created here.

“Portable substring matching” meant a new query capability with shared BDP-server and CLI semantics. It did not mean the legacy `title=…` behavior. Donna subsequently accepted explicit substring matching in the new model and excluded legacy field-dependent equality from it. Literal substring interpretation and the case-sensitivity split are selected; case-option spelling, Unicode rules, other value semantics and the corresponding BDP mechanism remain design work. Any legacy local-Dolt mode stays outside the pure semantics; no such mode, default, compatibility waiver or release allocation has been adopted.

An unimplemented expression is a coverage gap, not automatically an exception.

Design examples must become a common acceptance corpus for wrapper and general-query paths. Rendering follows Cleo's norms. No passing implementation tests are claimed by this design requirement.

### Batched design questions for Donna

**Reviewed by Donna, 2026-10-19; remaining choices below.** Donna requested a substantial batch before going AFK. The numbered list preserves the proposals she reviewed. Her explicit responses accept binding/scope (1), zero-hop behavior (3), nested paths (4), Unicode matching (8), stable ordering/pagination (11), and aggregation (12). Simple-path default (2) is accepted subject to explaining its consequences. Typed equality and no implicit coercion (6) are accepted; conversion operations need design. Array membership/any/all (7) are accepted; Donna remains open to overloading `contains` for arrays. Complete-or-explicit-partial behavior (9) and distinct revision nodes (10) are accepted; partial-result flag semantics and an optional identity-grouped view remain open. Missing/null/unknown behavior (5), including the unknown behavior proposed for mismatched types in (6)/(7), is **not yet accepted**. These decisions extend the accepted architecture and relationship results above; shared BDP changes require Trish's reconciliation. Output rendering remains Cleo's responsibility.

1. **Binding names and scope.** Recommend `$this` for the candidate and `$r`/`$p` for named Link/neighbor bindings. Bare properties continue to mean the candidate's properties, including inside existence blocks; use `$p.status` for the neighbor's status. Outer bindings are visible inside a nested block; new inner bindings stay local; redeclaring an existing binding is an error. This avoids property/variable-name collisions and implicit changes of subject. Illustrative shape: `exists { ($this)-[$r]->($p) where $r.type is Requires and $p.type is Policy }`.
2. **Individual paths and cycles.** Recommend that an explicit path request defaults to simple paths: no repeated selected Bead edition within one path. Parallel Links still produce distinct paths. Traversed graphs retain cycle Links. Repeated-vertex walks require an explicit option and finite depth/work/result limits. Reachable-set and graph queries do not enumerate paths merely to produce their answers.
3. **Zero hops and returning the root.** Recommend a default minimum of one hop. Include the seed via a zero-hop result only when explicitly requested. A positive-length cycle back to the seed may still return it in a reachable set, with the cycle visible in graph explanations; do not secretly remove that reachable node.
4. **Nested properties and unusual keys.** Recommend dot notation for nested objects and quoted brackets for literal keys: `metadata.team.name` versus `metadata["team.name"]`. Explicit array indexing is permitted; no implicit array flattening. Property prefixes remain available for reserved-name collisions.
5. **Missing versus null.** Recommend distinct missing/present tests. `status = null` matches a present JSON null. Comparing a missing value produces unknown; both `status = "ratified"` and `status != "ratified"` exclude missing status, and negation preserves unknown. Only true selects a row. Users include missing status explicitly when desired. This would be a new-model rule to reconcile with BDP selectors, not a claim about their current behavior.
6. **Typed comparison.** Recommend no implicit string/number/boolean coercion: `"3"` differs from `3`, and `true` differs from `1`; numeric `3` and `3.0` compare equal. Array equality is ordered; object equality ignores key order. Unsupported ordering between value types yields unknown for that candidate; statically invalid expressions are errors. This supports heterogeneous populations without making one differently shaped Bead fail the entire selection.
7. **Array predicates.** Recommend a distinct membership operation such as `tags has "security"`; reserve the already accepted `contains` for literal string substrings. Explicit `any`/`all` bindings support arrays of objects. `all` over an empty array is true; require nonempty separately when intended. Missing/non-array values yield unknown. Exact production spelling is provisional.
8. **Unicode and case-insensitive text.** Recommend locale-independent Unicode case folding for the explicit insensitive mode, with a specified Unicode version shared by backends. Exact equality and sensitive substring matching perform no implicit Unicode normalization; insensitive matching only folds case, without removing accents. Do not inherit PostgreSQL locale or SQLite ASCII-only defaults. A backend must implement the shared behavior or report unsupported capability.
9. **Incomplete reads.** Recommend ordinary queries return a complete answer to the requested bounded question or fail explicitly. A separate opt-in permits marked partial results. Never turn an unfinished negative-existence test into an absence assertion, or a partial count into a total. Requested hop bounds define the question; exhausting an execution budget before answering it is different. Pagination is not a license to compute aggregates from one page.
10. **Multiple revisions in one graph.** Recommend honoring explicit endpoint pins and resolving floating endpoints under the declared read context. If traversal encounters two revisions of one Bead, retain them as distinct graph nodes; never silently replace a pin with the current head. General identity matching and exact-revision matching remain distinct operations. This does not introduce new pins or decide the Memory-wide pinning policy; unsupported pinned/history reads report that limitation.
11. **Stable ordering and pagination.** Recommend deterministic identity-based ordering by default, with exact revision as a tie-breaker when needed; explicit sorts add stable identity tie-breakers. Revision-token ordering is not chronology. Page cursors bind to the query and read context; a provider that cannot preserve that context must reject stable continuation rather than silently resume against changed data. Unordered presentation and tree layout remain separate concerns.
12. **Aggregates and grouping.** Recommend count/group/aggregate over the selected input before output pagination; count is zero on empty input. Count units stay explicit: Resources, Links, distinct neighbors or paths. Missing and null remain distinct group keys. Array values do not automatically multiply groups; unnesting is explicit, and label-based wrappers request it deliberately.

Follow-up explanations and proposals, not additional accepted decisions:

- **Simple paths:** A→B→A→C is excluded as an individual simple path because A repeats. A→C remains a path; the graph still retains A→B and B→A, and a reachability query can still find C. Cycle witnesses and loop-sensitive analyses need graph/cycle operators or explicit repeated-node walks. Default simple paths do not limit graph extraction or erase cycles; they avoid repeated laps being enumerated as additional paths. Bounds are still needed because even simple paths can be numerous.
- **Unknown is a predicate result, not stored data:** the proposal adds no JSON value, public `undefined` sentinel or `unknown` literal. It distinguishes inability to evaluate a comparison on an absent field from false. For missing status, both equality and inequality with a concrete string are unknown; negation stays unknown. Explicit missing/present tests remain ordinary true/false. This truth model and its operator tables remain pending Donna's clarification; it must not be conflated with an incomplete graph read.
- **Explicit conversion:** recommend a narrowly defined `cast(expression as TYPE)` form with a documented conversion table. Example: `cast("3" as number)` produces 3, whereas `cast("3x" as number)` fails instead of accepting a prefix. Invalid conversions fail explicitly; an error-tolerant conversion form is deferred unless required. Missing/null conversion behavior depends on settling (5). No function spelling, full conversion table or runtime support is selected yet.
- **Partial-result opt-in:** recommend `--allow-partial`. It permits returning only conclusively established findings with mandatory completeness information and a reason for incompleteness. It cannot label unfinished negative tests as absent, estimate a total as exact, or make page-local ordering a global top-N answer. Exit status and the distinction between complete rows, unresolved candidates and graph-only partial output require coordinated design; the flag alone does not settle them. Cleo owns representation.
- **Optional coalescing:** Donna suggested a possible flag. Treat identity grouping as a presentation/projection option over revision-distinct records, not an in-place merge of revisions, automatic head selection or retargeting of pinned Links. Whether that option is needed, its spelling and the preservation of underlying revision-specific edges remain open.

**Subsequent response:** Donna accepted the simple-path explanation, the strict explicit-conversion approach, proceeding with distinct array membership, and the proposed partial-result and revision-grouping directions. Conversion grammar/table, partial exit status and any revision-grouping flag remain unspecified. She asked to minimize invention and examine Lumen before choosing missing/null semantics, specifically whether ordinary Bead property reads should distinguish absence from explicit null and whether `??` should be supported. The earlier unknown-result proposal is still not selected.

**Lumen comparison, inspected locally at `formula-language` commit `94c0344e43afad8fb5b52819909f2b00995f2093`:** active intended-design sources `docs/spec/types.md` (Records), `docs/spec/syntax.lumen` (member/index access, membership, nullish coalescing) and `docs/spec/expressions.md` distinguish physical key presence from read values. Declared optional fields read as `T | null`, with absent and explicit-null reads coalescing. Safe access to an absent dynamic/open-record field also yields null, while required dynamic access fails. `??` is short-circuit, right-associated and null-only; it does not unwrap a Result. Record membership tests physical key presence; array membership uses deep value equality. Lumen's static `??` restrictions do not automatically transfer to a heterogeneous Beads query. These are design-source observations, not a runtime conformance claim; the inspected files were clean.

With ordinary value equality, a missing status then satisfies `status != "ratified"`. **Error-model clarification:** Donna explicitly said Lumen's rule that functional expressions cannot throw exceptions does not need to apply to this query language. Strict-conversion behavior above is the current recommendation, while exact error propagation/recovery remains design work.

These are new acceptance obligations if selected, not executed conformance evidence. Provider support for cross-call consistency is an explicit shared-contract dependency, not a guarantee created by CLI cursors.

## Four questions to make useful

Names below are sketches already raised by the Memory draft, not adopted command grammar. `SUBJECT` and `CONSTRAINT` are illustrative selectors.

| Candidate view | Question | Result to preserve |
| --- | --- | --- |
| `bd memory constraints SUBJECT` | Which declared Constraints govern this subject, and why? | Subject To roots, their Requires-family closure, and explanation paths. State whether implicit applicability was examined. |
| `bd memory requires CONSTRAINT` | What is necessary for satisfying this Constraint? | Requires closure, with Defines edges identified as the defining structure; shared targets and cycle markers remain visible. |
| `bd memory coverage SUBJECT` | What claims exist about these obligations? | Recorded Conformance-family claims bound to the selected subject scope, actual Link Types, evaluation identity where present, evidence/provenance, assessed revisions/context, conflicts, and obligations with no visible relevant assessment. |
| `bd memory explain SUBJECT CONSTRAINT` | Why is this an obligation, and what supports the assessment? | An applicability witness, dependency edges, relevant claims, and reasons a stronger conclusion or composition is unavailable. |

The same query foundation should support generic resource/Link selection, exact Type versus refinement-family matching, and reusable bounded walks. A Memory view applies the typedef's domain rules to those primitives. Extending the existing Issue-filter grammar is a separate decision; these examples require no new `bd query` syntax yet.

## Priorities after Donna's review

The four questions above are starting points, not a closed command inventory. Recommended design order:

| Priority | Capability | Boundary |
| --- | --- | --- |
| 1 | Enumerate transitive requirements as a linear list or tree, starting from a Constraint or a subject's declared roots. | Traverse the Requires family, including Defines and future refinements. Show all necessary Constraints, not just Beads whose exact Type is Requirement. |
| 2 | `bd memory assess ...`: gather assessment inputs and support reporting or saving findings about one or more subjects and selected Constraints. | One full collective subject group per evaluation. Define inputs and the report first; judgment may come from an agent, checks, or a person. Design saved and unsaved modes together. |
| 3 | Tree views for discovery and inspection, using the same selected graph. | Treat list/tree/JSON as presentations over shared query results. `bd list` participates in the complete shared design; additional `bd show` adaptations remain a later decision. |
| Deferred | Type-specific create/update/delete shortcuts and version-management operations. | Preserve selected revisions in every read and assessment now; defer authoring/version-management UX. |

### Transitive requirements and tree presentation

A linear view should list each selected Constraint once and retain the dependency edges and reasons for inclusion. A tree view should unfold the same graph from its selected roots, label Defines versus other Requires links, and mark repeated/shared nodes and cycles with references. The graph need not be a tree; tree formatting must not invent a single owner or discard additional parents. Stable sibling ordering is presentation, not Procedure execution order or dependency priority. Bounds and incomplete expansion remain visible in every format.

This extends the proposed `requires` and `constraints` views rather than creating another traversal model. The query foundation selects resources and edges; the Memory facade interprets the Requires-family semantics and supplies useful presentation.

### Assessment execution and persistence

Assessment has three distinct jobs:

1. **Gather:** select the full subject group and Constraints, expand the Requires family as requested, and collect relevant content and existing evidence. Preserve the selected revisions, reasons for inclusion, read context, and completeness limits. This is deterministic query and CLI work.
2. **Judge:** examine the material and produce reasoned claims. An agent, automated checks, or a person may do this; some assessments combine them. The CLI does not decide that arbitrary prose has been satisfied merely by gathering it.
3. **Report:** display the findings or publish an evaluation owning its claim Links. This is deterministic validation and persistence work; structural validity does not establish that the judgments are correct.

Donna agreed to define the **assessment inputs and report first**, using an agent assessing a code change against a Specification and its required Policies as the first example. This supersedes the earlier scope wording that described `assess` as running an explicitly chosen evaluator inside `bd`. The agent can use `bd` to gather material and submit findings; automated checks can contribute evidence. Whether one command coordinates all three jobs remains open. No evaluator registration or plugin interface is selected.

The report preserves the full subject group and observed revisions, Constraint revisions, assessor provenance, relevant assessment context and method/tool versions where available, evidence, and proposed Addresses/Satisfies/Violates claims. These are semantic requirements, not adopted JSON field names or new stored properties. Failure to assess a Constraint is an unresolved result, not automatically a Violates claim. Declared applicability, closure completeness, execution failures, and claim contradictions must remain visible; the findings remain claims under the consumer's acceptance policy.

Provide two persistence choices over that same report:

- **Saved assessment:** create an evaluation record owning its claims, with provenance identifying the actor. Publishing the result must bind the subjects and Constraints actually assessed; changes during assessment must not silently retarget it to newer revisions. Persistence failure must be reported distinctly from assessment completion, with no success claim for a partially saved evaluation. Atomic publication and revision-binding mechanisms need the shared write/batch design.
- **Unsaved assessment:** print the findings or write JSON representing the ephemeral assessment Bead graph to an explicitly requested destination, without persisting evaluation Beads or claim Links. Do not create then delete temporary graph records. The evaluation and its owned claim Links exist in the output graph; their representation must distinguish ephemeral graph identities from stored identities. Exact identity/reference encoding remains shared design work. Ephemeral evaluation/Link references must not invent live canonical store URLs, retained revisions, or a selected installed Evaluation Type identity. Persisted subject and target identities/revisions retain their existing meaning. Writing the graph to JSON does not assign stored identity; a later save/admission requires explicit mapping and publication semantics. The graph is not automatically an import-ready export package. Ordinary execution logs or side effects of any checks need their own disclosed contract; unsaved means no assessment records persisted to the Bead graph.

### Ephemeral assessment graph and projection

Unsaved JSON is a Bead graph representing the assessment, rather than only a separate findings table. Preserve the ephemeral evaluation root, its full assessed subject group, and the concrete claim Links it owns. Scope emitted Links by selected Link Types, with explicit exact-Type versus refinement-family selection. **Default: the Conformance family**, including Addresses, Satisfies, Violates, and applicable concrete refinements. The abstract Conformance base is never the actual Type of a claim Link.

Default target presentation is the target ID/reference, preserving assessed revision selection. Titles are a proposed optional readability addition; they never replace identity or justify fetching complete target bodies. Target-ID filters may narrow the displayed graph. Requires/Defines, Subject To, or other explanatory Link families require explicit expansion; an evaluation's declared subject group remains essential context even when those Links are omitted.

Selection of assessed Constraints and projection of the result are different operations. Filtering out a Link Type or target must not change the underlying assessment, manufacture a claim, or conceal the fact that this is a selected view. Carry scope, bounds/completeness and unresolved findings alongside the graph, including obligations for which no claim was produced. Preserve parallel claims and the full collective subject group. A target reference or ID/title projection is not a partial object presented as a complete BDP Resource. Coordinate its graph framing and ephemeral identities with Cleo and Trish; coordinate any export of it with Iris. Concrete JSON shape and flags remain open. A complete selected graph view, a complete assessment, and a complete transferable package are different completeness claims.

Do not choose the default persistence mode yet. Both modes use the same assessment inputs, claim meanings, evidence requirements, and graph projection semantics; persistence adds stored identities and provenance. Saved mode requires implementation of the selected Evaluation Type and exact subject-reference representation, plus the publication lifecycle still under review. This expands the design scope beyond read-only inspection; it does not select a built-in agent runner, evaluator plugin system, or release prerequisite.

## One example and its expected answers

Use these labels as an illustrative graph, not assigned Bead identities:

```text
Release --subject-to--> Export Specification
Export Specification --defines--> Export selected rows
Export Specification --requires--> Protect customer data
Protect customer data --defines--> Redact logs
Export Specification --subject-to--> Review Specification documents
```

`constraints Release` reports the Specification, row Requirement, data Policy, and redaction subpolicy. It does not report the document-review Policy: Subject To is nontransitive. `requires Export Specification` shows its necessary dependencies and distinguishes Defines from ordinary Requires.

Suppose an evaluation of Release alone owns a Satisfies claim for the row Requirement and an Addresses claim for the Specification. Its full subject group is Release; the claims belong to the evaluation, not the release build. The row has a complete-satisfaction **claim**; the Specification has a contribution claim; the Policy and subpolicy have no visible relevant assessment. None of this establishes verified compliance or changes Issue readiness. A Violates claim concerning the same row, subject, revisions, and context must coexist with the Satisfies claim as a contradiction. A claim concerning another revision must be shown separately, not merged into that conflict.

### Worked assessment: a code change against its Specification

Suppose a Bead identifies an export code change at a particular code revision. It is Subject To the Export Specification in the example above. The code reference and test artifacts must identify the material examined; a Bead revision alone does not freeze mutable external code or evidence.

1. **Gather with `bd`:** resolve the subject revision and Specification revision, expand Requires/Defines to the row Requirement, customer-data Policy, and redaction subpolicy, and retrieve relevant bodies and existing claims within the selected read boundary. Exclude the document-review Policy from the code change's inherited obligations because Subject To is nontransitive. Report inaccessible content or incomplete traversal.
2. **Assess through the agent:** read the code and obligations, use permitted checks, and explain findings against individual Constraints. A passing selected-row test can support a Satisfies claim for that Requirement. An observed log exposing customer data can support a Violates claim for the redaction subpolicy. Neither the passing test nor completion of the review establishes satisfaction of the whole Specification. Missing evidence stays unresolved; it does not automatically become an Addresses or Violates claim.
3. **Report or save through `bd`:** validate the report's references and structure, then print it/write JSON or publish the evaluation and its claims. All claims concern the same full subject group. Unsaved JSON contains the ephemeral evaluation and its selected claim Links, with target references by default; evidence and unresolved obligations remain available in the selected result context. Saving adds stored identities and provenance without changing the claims' meanings.

A code change assessed together with a configuration Bead forms a different collective subject group. Its result must not be attributed to the code change alone. Existing conflicting claims remain visible; this workflow does not overwrite them, close an Issue, or choose a consumer's gate outcome.

This is a workflow example, not executable command syntax, an evaluator implementation, or a claim that the current CLI supports it. The next contract work is the precise gather inputs/report representation and their relationship to `assess`.

The first inspection slice does not evaluate prose or applicability predicates, run tests, author claims, reconcile evidence, or derive indirect Satisfies claims without established revision/context compatibility. ## Truthful results and read context

A result must distinguish **recorded findings**, **assessment compatibility**, and **query completeness**. None is a stored Memory status or a new claim-kind enum.

- Preserve selected subject/Constraint identities and revisions, evaluation identity and full assessed subject scope, actual Link identities/Types, evidence, provenance, and supporting edges. Missing evidence is not verification; missing claims are not violations.
- Bound depth, visited resources, claims, and explanation size. Deduplicate repeated visits; represent shared nodes and cycles. A finite witness/edge graph avoids pretending to enumerate infinitely many walks. Distinguish an incomplete obligation set from abbreviated explanations.
- Define completeness relative to the selected question, authorized view, and read context. A visible result cannot certify the absence of hidden obligations or assessments. Do not reveal hidden endpoints, counts, or reasons.
- Report exhausted budgets, unsupported capabilities, unresolved revision/context compatibility, and unestablished read consistency. Never present a bounded or inconsistent read as an exhaustive “nothing unmet” answer.

Coordinate a structured result envelope with Cleo so completion, scope, and limits travel with the selected rows or graph. Keep query observations separate from any consumer's pass/fail decision. Do not silently replace existing `bd query --json` arrays with a different shape. Defaults, exact fields, pagination, and exit behavior remain facade decisions.

### Accepted multi-subject assessment direction

An evaluation-owned claim about a Web app and an API concerns the combination: they satisfy the Requirement together. It does not establish that either component independently satisfies the whole Requirement. A query for the Web app can show its participation in that collective assessment, but must preserve the full assessed scope rather than label the Web app individually satisfied. Conflicting-claim and composition reasoning must respect the assessed group and its selected revisions; overlapping groups are not automatically equivalent scope.

Each evaluation owns claims for one full subject group. A claim about a different group belongs to a separate evaluation; two evaluations may still independently assess the same group. The query obtains the assessed scope from the evaluation rather than applying a per-claim subset selector.

The main draft selects Evaluation refining Memory as the concrete carrier; Assessment was the earlier working name. Required nonempty exact `{uri, revision}` subject references are selected, with floating subjects refused. Detailed cleanup and ephemeral identity/framing still need review. Every Addresses, Satisfies, or Violates claim must belong to an evaluation, including self-authored or unattested claims; direct unowned claims are not retained in the successor model. Any Bead can still be an assessed subject. Queries resolve a subject to its evaluations, then inspect the claims owned by those evaluations, preserving their complete subject groups. This proposal selects neither a join nor a generic third-party owner field.
