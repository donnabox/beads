## Concrete authority and transaction sketch

A proposed common catalog/ledger owns canonical path, resource kind, fixed Type, current opaque revision and allocation state. Every live allocation selects exactly one backing row/provider; no second editable graph copy of an Issue or Dependency. Specialized Issue scalar columns and normalized labels remain authoritative payload; generic records own their canonical payload bytes. The catalog must not duplicate independently editable domain fields. Current `row_lock` is a domain CAS token, not the canonical revision; any retained local revision ordinal is a third, explicitly mapped value, not portable identity. Exact placement remains a schema decision, including the open immutable Type versus mutable Issue classification distinction.

For Dependencies, preserve pair uniqueness **as an Issue-domain rule**. Migration 0050 deliberately derives the legacy row ID from `(source,target)`, excludes Type from uniqueness, and handles Issue/wisp/external target columns. That key cannot be canonical nonreusable Link identity: deleting and re-adding the pair would reuse it. Allocate a separate stable canonical Link identity/mapping, treat the deterministic key solely as legacy/domain storage identity, and never regenerate canonical identity on a legacy rename/plane move. Generic multiedges cannot enter this table unchanged. A generic parallel Link must remain distinct from a Dependency; pair-addressed Dependency commands keep their semantics, while generic operations use Link ID and refuse ambiguous shorthand. Reclassification into/out of Dependency constraints needs an explicit rule, not a silent upsert. Evidence: `schema/migrations/0050_dependencies_deterministic_id.up.sql`, `issueops/dependencies.go:267` (pair lookup), `:299` (insert), `:924` (removal), and `graphops/types.go:60` (allocation states/nonreuse).

For either layout, one write transaction must validate Scope/selected workspace and expected state; reserve nonreusable identities; change authoritative payload/labels/Links; compute source-owned revision effects; record complete retained snapshots and required events; then commit. No-op detection precedes version minting. An owned-Link change records the whole source-owned set, not just a changed edge. All generic and Issue entry points must use this same path. A catalog is insufficient if generic writes bypass domain validation or Issue writes bypass canonical effects.

**Shared-server direct path:** `internal/storage/dolt/transaction.go:194–230` normally opens separate regular/ignored SQL transactions; journal-enabled mode already shares one. `finishDoltTransaction:259` commits regular SQL, then Dolt staging/commit, then separate ignored SQL where applicable. Evaluate and qualify the existing one-SQL-transaction path for graph mode; do not infer atomicity from `RunInTransaction`. **Embedded:** `embeddeddolt/transaction.go:42` completes SQL mutation before a later Dolt history commit. Retained content versions must live inside SQL commit, with later history failure reported honestly. **UOW:** `uow/doltserver_tx.go` owns one connection, pending-change/DOLT_COMMIT versus plain COMMIT behavior, rollback and indeterminate handling. Both direct and UOW require the same mutation/history coverage; preserving one does not establish the other. Concurrency/conflict/partial-failure tests are necessary on both backends; no extra flock or homemade retry proposed.

## Migration and Jim History delta

**Specialized migration:** create admitted Scope/catalog/allocation and generic backing; register existing Issue/wisp rows and Dependency rows with collision-free canonical identities; preserve labels, comments/events, typed targets, blocking behavior and persistence traits; enforce one live backing per allocation. Add canonical mapping to existing Dependency records rather than dual-write them into another authoritative Link table. Generic enumeration must union/select every backing in one snapshot, and generic mutation must dispatch back to the owning specialized domain. Existing private readers hardcode `graph_beads`/`graph_links` (`read_body.go`, `read_page.go`, `read_bead_page.go`), so this adaptation is real work, including global limit/order and owned-set budgets.

**Universal migration adds:** copying the complete Issue aggregate into generic representation; converting the 20-file query family and scalar-write paths; preserving supported SQL reads with explicit compatibility views/projections; reworking indexes, Issue/wisp routing, history/compaction/import/moves and existing foreign keys. Keeping authoritative legacy rows plus editable JSON to avoid those changes would simply be dual authority. A normalized label/index projection can be legitimate, but its ownership and transactional maintenance must be explicit.

For both, retain the source database; validate conversion before enabling graph writes, and use forward recovery afterward. Do not invent historical versions during backfill. Existing ephemeral/no-history Issue behavior must survive without making required Memory History optional. Scope restore/clone continuity and alias mapping are admission gates, not incidental IDs.

**Verified Jim gap at this exact baseline:** `0067_add_versioned_beads_schema.up.sql` creates `issue_versions` and `current_revision`, but a production-Go search for those names finds only `schema/cli_migrations.go` literals. There is no retained-version writer wired at 99f7. `issueops/journal.go` provides same-transaction Issue snapshots/event sequencing; `issueops/history.go` queries `dolt_history_issues`; neither is Jim’s retained-version implementation. `git cat-file` cannot resolve delivery-plan Jim pin `64becbc335cd754efa1f68effcbd5ca3f33873db` in this object store. The plan’s writer/census findings are therefore attributed prior evidence, not independently verified here.

Next prerequisite: obtain and review the pinned contributor implementation (`version_history.go` and direct/UOW callers), then extend its existing recording seam instead of writing another Issue-history system. Required generic delta: Type-independent canonical state/identity, complete owned Links/pins, durable portable version addressing, no-op suppression, removals/restoration rules, mandatory Memory recording and concurrent allocation/CAS. An Issue-shaped snapshot plus optional switch is insufficient under either layout. Do not freeze a generic retained schema based solely on the current migration scaffold.

The baseline also selects `github.com/donnabox/mysql v1.10.1-0.20260920194038-ca53f9bcb727` through `go.mod:298`. Both layouts inherit this client dependency until separately qualified otherwise; an ordinary shared Dolt server does not establish stock-client support. This comparison does not propose an engine fork or claim old paired-engine fixture qualification proves installed C0 behavior.

**Decision to take now:** specialized backing with shared canonical authority, retaining existing query layouts; implement C0 generic non-Issue create/read/reopen through ordinary initialization while designing the common writer once. Gate Issue adoption on canonical mapping, direct/UOW coverage, contributor History review, and migration/concurrency proof. Do not declare complete A from that early generic slice.

## C0 decision boundary

Janet selected this hypothesis before implementation on September 23. C0 is restricted to fresh disposable preview workspaces with non-Issue Memory payloads. Existing Issue/Dependency tables remain the sole future owners of their specialized data; Issue commands refuse in the preview until canonical coupling exists. No existing Issue is copied into editable generic payloads. This is not a migration approval or a production descriptor/History ABI. The compiled preview bootstrap will use the same ordinary Dolt database and migration machinery, not an extra Memory database. A new random coordination token on the authority row in every SQL write transaction provides the existing Dolt optimistic-conflict pattern; the installed two-process and cancellation checks must prove it. Commit errors remain uncertain and are never automatically replayed.
