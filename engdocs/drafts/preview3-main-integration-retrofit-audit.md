## What the boundary actually does today

The ordinary missing `graph_mode` config value resolves to `dependency` (source `internal/configfile/graph_mode.go:10-22` at the exact source root above). The graph path is selected by a fresh `bd init` with `--graph-mode link`, persists `graph_mode`, workspace/scope/authority metadata and a `graph-preview-format` generation sentinel, and rejects mismatched/corrupt/unknown/newer markers before ordinary opening (`cmd/bd/graph_preview.go:40-47,68-101,231-371`). The graph init refuses an existing `.beads` directory (`:304-315`) and writes a separately named graph database (`:458`); there is no implicit existing-data migration. Each admitted graph command dispatches to graph code; unadmitted commands/flags refuse before opening the legacy store. `cmd/bd/main.go:1299-1301` invokes admission ahead of ordinary store discovery. This is a meaningful capability boundary, **not** a compile-time boundary: graph flags and command dispatches are registered in the same `bd` binary (`cmd/bd/graph_preview.go:72-102`; `show.go:38`, `update.go:113`, `memory.go:411,605,668,725`).

The BDP Read server is enabled only when a graph workspace is admitted and ordinary shared-server Dolt is selected (`cmd/bd/graph_preview_serve.go:19-41`). `httpapi.Config.GraphRead` then selects the separate read route; normal listeners have nil `GraphRead` (`internal/httpapi/graph_read_gate.go`, `server.go:821,1716,1801,1901`). There is no BDP HTTP writer in the selected source. `graphops` is a public Go package but has no general existing-Issue activation path; publishing its API still imposes API-quality obligations.

Graph tables are created by the graph initializer (`internal/storage/graphstore/schema.go:24-49,227-240`), and `OpenExisting` explicitly performs no DDL (`internal/storage/graphstore/backend.go:158-160`). **Shared History is different:** the Preview line adds numbered ordinary-store migrations `0070`–`0072`, including nullable columns on `issue_versions`, `issues` and `wisps`, and a new `epoch_minted_addresses` table. The `versioned-history.enabled` default is false (`internal/config/config.go:266-275`); its write activation is per opened store/provider and also honors store setting/environment (`cmd/bd/versioned_history.go`, `internal/versionedhistory`). Shared Issue writers and storage operations were changed even when graph mode is not selected, e.g. `internal/storage/domain/db/issue.go:84-112` distinguishes create from upsert before recording a version. Source comments claim flag-off byte-identical behavior, but that is a **claim to verify on the actual shipping merge**, not a substitute for comparison tests. These shared migrations/writers cannot be isolated solely by the graph workspace marker.

## Minimal pragmatic shipping-protection sequence

1. **Pin and partition.** Keep qualified `b9e` and final Preview 2 frozen. Choose an upstream integration target/merge candidate explicitly. Confirm whether shared History is included in the first upstream PR or isolated into a separate preparatory PR. Do not reassign old source qualification to a rebase or new merge.
2. **Prove default-off compatibility where it matters.** Add normal shipping workspace/CLI/server/data-format parity tests first. Audit shared History writers and ordinary-store migrations as non-graph-gated changes, including old-client database opening. These are release-quality tests, not flag documentation.
3. **Keep graph mode a coherent boundary.** Preserve explicit fresh-workspace admission, independent graph tables, read-only BDP route and refusals. Do not add one global Memory opt-in to the first supported release; when a feature becomes supported, its default and any named individual experimental exception need their own test.
4. **Requalify the exact upstream PR merge.** Run complete selected two-engine tests, no-skip scenarios, applicable protected CI (including Bazel/Docker), public API/CLI compatibility and binary/client/Dolt provenance on the actual merge source. Human review/merge queue and release decision remain independent.

Bounded incremental retrofit estimate for the selected `b9e` source: **~25–45 engineer-days** across parallel owners with overlapping matrix rows, low confidence overall because the shared History/migration and upstream-interface behavior need real tests and upstream review. This excludes implementing any missing Memory V2 scenario, import/export completion, Preview 3 data migration, and release operations. A *coherent first shipping-protection tranche* might be 8–15 days if History is split out and the graph mode/default-off proof is clean; that does **not** imply the full candidate is safe to merge. The **comprehensive cleanup** option (centralize the 50-file command routing, stabilize public Go API, factor graph/server modes and document all supported surfaces) adds roughly **15–30 days** and should follow the minimal safety proof rather than block every small slice.

## Open audit limits and decisions

This was a bounded source/status scan, not full semantic diff review of 700+ Preview paths, a complete API compatibility compile, or installed behavior. Costs carry that uncertainty. Most crucial remaining factual question: whether ordinary workspaces with versioned History disabled and upgraded schema behave identically to shipping main across direct, proxied and older-client writes. That requires an isolated runtime matrix owned by root, not another static assertion. The upstream `4a67d0d0` two-commit drift was not qualified. The exact applicability/cost of Iris source after rebase, Trish F0, and later Memory/History/Type slices must be reviewed on their own heads. A policy should permit named exceptions only with explicit owner, proof and review; it must not equate a feature flag with quality or backward compatibility.
