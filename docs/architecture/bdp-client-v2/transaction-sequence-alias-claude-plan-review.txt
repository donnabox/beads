## Findings

**1. High — Deferred-template eligibility is computed twice and the plan requires it only once; disagreement aborts a valid carrier with an unhandled error.**
*Plan:* §A line 33 ("creator dependencies **or** eligible alias operands"), §B lines 38–41, ownership line 69.
*Source:* `packages/server/src/transaction-store.ts:1736-1738` (`admitSequence`) and `:1802-1804` (`nextSequence`) each independently compute `member.dependencies.length ? dependencyTemplate(...) : undefined`.
*Issue:* The plan states the new predicate in prose but never says it exists at two store sites that must agree, nor proposes a single source. If `admitSequence` reserves an alias-only member with a template — row inserted with `identity=""`, `witnesses=""`, `dependency` set, `claims.normalized === undefined` (`:1096-1102`) — while `nextSequence:1802` still sees `dependencies.length === 0`, the turn skips the fenced normalization at `:1826-1850` and falls straight to `executeClaim(claim)` at `:1874`, which throws `"unresolved execution"` at `:1119` (`!normalized || current.dependency`).
*Impact:* `executeClaim`'s `cleanupThenThrow` (`:1296-1310`) deletes the row, `nextSequence`'s catch (`:1905-1909`) calls `cancelSequence` and rethrows, the stepper rethrows (`transaction-sequence.ts:103-111`), and neither `transaction-service.ts:419-435` nor `transaction-http.ts:336` catches it — a *valid* alias sequence becomes an unhandled 500 that destroys the carrier after a committed prefix. No existing test exercises an owned claim whose `dependency` is still set at execution.
*Fix:* In §A, require `prepareTransactionSequence` to publish the deferral fact on the prepared member (e.g. `readonly aliasOperands: readonly { field: string; locator: string }[]`); in §B, require `nextSequence` to derive "needs turn normalization" from the durable row (`row(principal, member.key).dependency !== null`) rather than recomputing from the member, so the two sites cannot diverge. Add a store assertion/test that no owned claim with `dependency != null` reaches `executeClaim`.

**2. High — §C's pending rule has no mechanism for an alias-only template: `compareDependencyTemplate` returns `equal` and hands a direct caller the owner's *pending* receipt.** *(This is the requested explicit assessment: pending alias-template handling as written does **not** follow existing law.)*
*Plan:* §C bullets lines 49–51.
*Source:* `transaction-dependencies.ts:52-72` sets `unresolved` **only** from `fact(d.creator)`; `:80` returns `different ? "conflict" : unresolved ? "pending" : "equal"`. `transaction-store.ts:1063-1067` maps `"equal"` to `{kind:"existing", receipt: parseReceipt(prior.receipt)}`, and for an unresolved reservation `prior.receipt` is the owner's pending receipt.
*Issue:* An alias-only member's template has `dependencies: []`, so the creator loop never runs, `unresolved` stays `false`, and a spelling-compatible candidate (both sides masked in the same slot) falls through to `equal`. §C asks for `comparison-pending` "if any required original alias target/miss remains unresolved" but never names the flag that produces it.
*Impact:* Violates `docs/specs/bdp.md:3999-4002` ("Until equality is established, this caller MUST NOT receive the owner's pending receipt") and `:3885-3887` ("handing a duplicate a receipt presupposes established semantic equality"). Concretely: a sequence reserves key `k` for `deleteBead(bead: alias/work)`; a direct singleton `deleteBead(bead: alias/work)` under `k` gets 200 plus the owner's pending receipt before the turn, is joined to a mutation whose target it never agreed to, and never receives the 409 it is owed if the turn resolves `work` differently.
*Fix:* State in §C that while the `dependency` row is present every recorded alias slot is unresolved **by definition** (the owner has not had its turn) — i.e. seed `unresolved = template.aliasSlots.length > 0` before the creator loop at `transaction-dependencies.ts:51`, so the only reachable results for an alias template are `conflict` or `pending`. Promote observation #7's "a wrong currently matching target must not prematurely obtain pending receipt" to a required assertion.

**3. Medium — §C does not forbid resolving the *template's* locators, and the existing `resolveAlias` argument makes that the path of least resistance.**
*Plan:* §C bullet 3 line 51; diagnosis item 5 line 27.
*Source:* `transaction-dependencies.ts:41` (`resolveAlias` parameter), used only on the candidate at `:49` and `:74-79`; `transaction-store.ts:1054` passes the live store resolver.
*Issue:* "If any required original alias target/miss remains unresolved" invites an implementer to call `resolveAlias(templateLocator)` to decide unresolvedness — which is exactly the admission-time snapshot this slice exists to remove, and makes a currently-matching target yield `equal`.
*Impact:* Reintroduces admission-time alias semantics into the comparison decision, contradicting `docs/specs/bdp.md:3066-3070` ("resolves it to the alias's current target when the member is reached"), while passing a naive happy-path test. It also risks recording a current lookup as the owner's future witness, which `transaction-batch.ts:386-389` and `docs/specs/bdp.md:3238-3240` forbid.
*Fix:* Add an explicit prohibition to §C: `compareDependencyTemplate` MUST NOT invoke `resolveAlias` for any locator recorded in the template; `resolveAlias` is reachable only for the candidate's own reference slots. Pair with a unit test that passes a `resolveAlias` which throws for template locators.

**4. Medium — §D leaves the compatibility boundary open when the source already proves the additive form is safe; the offered bump is a hard refusal, not a migration.** *(This is the requested safe compatibility recommendation.)*
*Plan:* §D line 61 ("prefer a tagged additive pending form with proof that recovery retracts it before interpretation; if old reader safety cannot be established, bump the private store compatibility identity").
*Source:* `transaction-store.ts:198` (`format = "bdp-private-transaction-snapshot-10"`), `:201` (`identityPolicy`), `:207` (`dependency TEXT` column already exists), `:530-535` (byte-exact `configuration` gate), `:552-556`, `:499-503`, `:421-492`, `:830-843`, `:1052-1053`.
*Issue/impact:* Because `configuration` is compared byte-exactly at `:534`, bumping `format` or `identityPolicy` does not migrate anything — it makes every pre-existing store unopenable (`"transaction installation mismatch"` / `"transaction identity policy mismatch"`), which the plan's own line 61 also forbids as "an unrelated migration". Leaving the choice to review invites that outcome for no benefit.
*Recommendation:* Keep `format` and `identityPolicy` unchanged. Carry the deferred alias representation **only** inside the existing `dependency` TEXT JSON; add a required discriminator member to that JSON (e.g. `form: "transaction-deferred-member-1"`) and have the parse at `:1053` treat an unrecognized `form` as an owner fault; preserve today's invariant that an unresolved row stores `identity=""` and `witnesses=""` (`:1096-1097`) so no path that bypasses the dependency branch can mistake a masked identity for a final one. The old-reader proof §D asks for is already in source: startup deletes **every** `owner IS NOT NULL` row and all `creator_facts` inside the provisioning transaction and *before* the first `sweep` (`:552-556`); `sweep` selects only `owner IS NULL` (`:499-503`); `expireRow` never reads `dependency` (`:421-492`); `disclosedReceipt`/`retainedReceipt` read only `receipt` (`:830-843`). So no `dependency` value written by one process is ever interpreted by another. Required evidence: extend the existing crash fixture (`transaction-sequence.test.ts:469`) with an alias member so `recoveredPending` counts the alias reservation and the reopened store admits a fresh carrier; plus a negative test that `maintain()` over a store holding an unresolved alias reservation neither reads nor retracts it.

**5. Medium — The "Existing law" anchors omit the one paragraph that states turn-time resolution, the link-subject wrong-kind rule, the admitted slot set and the put-target refusal.**
*Plan:* line 15 cites `docs/specs/bdp.md` "lines 2354ff and 3202–3243; table rows 6760–6761".
*Source:* `docs/specs/bdp.md:2351-2356` is only a forward pointer ("Which mutation members admit an alias spelling, and when the authority resolves it, is defined under [Alias targets]"). The operative text is `docs/specs/bdp.md:3062-3080`: "admitted wherever a canonical in-Scope Bead reference is: as the `bead` subject of an update or a deletion and as a Link endpoint `source` or `target`, bare or as the `uri` of a Pinned Reference, in a singleton and in a sequence member alike. The authority resolves it to the alias's current target when the member is reached … a `link` subject spelled by alias is of the wrong kind and fails with `resource-not-found` … A put's own `target` admits no alias spelling". (`:3202-3243` and rows `6760-6761` are correct as cited.)
*Impact:* §A line 35 and observations #2/#5 rest entirely on `:3062-3080`. A reviewer following the given anchors cannot confirm the admitted slot set — notably that a **pinned** alias `uri` is admitted, which is what `transaction-batch.ts:441-444` and `:978-982` must preserve byte-exactly — so the removal of `transaction-batch.ts:264-268` could widen or narrow the slot set against an approved plan. (The current slot set is already correct: `aliasFields` at `transaction-batch.ts:310-316` admits `source`/`target` for `createLink` and `bead` for `updateBead`/`deleteBead`, and deliberately excludes `link` and `putAlias.target`; `putAlias target:"alias/..."` passes the parser and fails `validation-failed` in `alias-evaluator.ts:67-94`, confirming plan lines 35 and 84.)
*Fix:* Cite `docs/specs/bdp.md:3062-3080` as the normative basis (keep `:2354` as the pointer) and restate the exact admitted slot list in §A so the refusal removal cannot change it.

**6. Low — §B's asynchronous-seam fallback is not implementable without touching the shared direct-carrier execution path §D freezes.**
*Plan:* §B line 43 ("if an implementation introduces any asynchronous seam here, move capture into the execution transaction instead") against §D lines 60–61.
*Source:* `transaction-store.ts:1118-1119` — `executeClaim` requires `owned.normalized` set and `current.dependency` already cleared, and the same `executeClaim` serves the direct singleton/batch route (`:1915`).
*Issue/impact:* Adopting the fallback means restructuring `executeClaim`'s precondition and the `claims` `normalized` field, i.e. a change to the direct-carrier path the plan otherwise declares untouched — a larger blast radius than the ownership section permits.
*Fix:* Drop the fallback and state the invariant the source already supplies: `nextSequence` is fully synchronous between `:1826` and `:1874`, the store holds one connection under `PRAGMA locking_mode=EXCLUSIVE` (`:518`), and `enter()` (`:339-350`) refuses reentrancy — so capture and evaluation cannot be separated by external work. Keep the existing `after-dependency-resolution` fault stage (`:182`, `:1848`) test from observation #9 as the proof that a crash between capture and execution retracts both.
