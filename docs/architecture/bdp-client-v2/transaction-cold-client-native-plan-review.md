# Native review: Transactional cold-client C1 plan

## Findings and recommendation

No High or Medium blocker found in the proposed C1 serving change. Approve the bounded initial Bead/Link collection minimum implementation, with the two evidence/lifetime clarifications below. This is approval of a plan boundary, not implementation correctness, whole-contract credit, cold-discovery readiness, or public profile admission.

1. **Low — distinguish deterministic owner-retry proof from installed concurrency evidence.** Plan lines 75 and 81 ask for controlled actual owner progression and an installed negative control. The deterministic seam exists in `packages/server/src/transaction-http.test.ts:946–978`: an injected `minimumReads.wait` commits through real HTTP before allowing the next attempt. The installed process has only initial configuration and a subsequent `close` control (`transaction-installed-process.ts:1–3,31–47`), not a behind-attempt notification or injected wait. Runtime test seams and installed identity must not be conflated (`transaction-runtime.ts:50–61,324–329`). A request-write completion or short sleep does not prove that the installed owner observed a behind attempt before a concurrent mutation. **Disposition:** keep deterministic retry/re-entry and pre-retention controls in existing direct runtime/owner tests; separately run genuine packed minimum success, no-progress timeout, wrong-context, conditional, pagination and concurrent-commit observations. Describe the latter only as concurrent success unless there is an actual behind-attempt witness. A packed source-condition mutant can be discriminated by the no-progress timeout case without adding IPC or changing installed configuration. No new production observation hook is needed.

2. **Low — existing finite wait does not currently imply HTTP disconnect cancellation.** Plan lines 65 and 82 reuse the existing lifetime and require child cleanup. `transaction-http.ts:222–227` calls `facet.perform(parsed)` without `request.signal`, whereas `transaction-service.ts:236–245` forwards only `receiving?.signal` to `waitForTransactionMinimum`; `transaction-runtime.ts:147–148` does create the request signal. Therefore this exact path currently finishes through the bounded wait after a disconnect rather than promptly cancelling its retries. **Disposition:** either explicitly retain this limitation and prove bounded drain/child cleanup, or make the narrow already-owned HTTP forwarding change with focused pre-abort/disconnect regression. Do not claim prompt cancellation solely because the service supports a signal. This does not require a new timeout, service framework, store edit, or product ruling.
