## Findings

**1. [High] Two pre-existing control-cohort bounds break, and the plan's "preserve all existing controls" instruction makes that invisible.**
Location: plan §"Four-file ownership and preservation" (`Preserve … all existing assertion IDs/pins/controls`) and §"Measurement gates" (`New positive + three controls: at most 20 children/180 exchanges each`) vs. `apps/bdptest/src/transactional-matrix.test.ts:1312` and `:1314`.

Issue: the manifest is shared by every cohort, so the three existing matching-no-op discrimination controls (`it.each(["bead-property","link-metadata","group-inventory-and-head"])`, `:1264–1341`) will also run the new 12th row to completion. Those cohorts assert `expect(children.length).toBeLessThanOrEqual(19)` and `expect(exchanges).toBeLessThanOrEqual(159)`.

Impact (computed): children become `1 bootstrap + 12 scenario + 7 reopen = 20` (> 19). Exchanges: the mutated no-op row stops at `n-noop` (index 3 → 4 exchanges) or `n-noop-groups` (index 8 → 9), so other rows contribute `159 − 15 = 144`; totals become `144 + 4 + 21 = 169` and `144 + 9 + 21 = 174` (> 159). Both assertions fail. The plan budgets "20 children/180 exchanges" only for the *new* positive and its *three new* controls, and nowhere states that the three existing controls must be re-pinned — a reader following "preserve all existing … controls" literally lands on a red suite.

Fix: state the complete re-pin inventory explicitly. Hard breaks the plan currently omits: `transactional-matrix.test.ts:1312` (→ ≤20) and `:1314` (→ ≤180). Items the plan does cover but should be enumerated at line granularity so none is missed: `:184–196` route inventory; `:330`/`:477` "eleven" labels; `:339` (11→12); `:341` (18→19); `:342` (19→20); `:347` + `:1216–1237` digest/preimage; `:407–412` 2KiB/32KiB filter list; `:473` (159→180); and in `packages/conformance/src/transactional-cumulative.test.ts`: `:189` (239→238), `:805` title, `:812–824` ID list (insert at index 2), `:826–838` per-row action table, `:847` (166→187), `:853–856`, `:861` (1539→1539+A), `:873–874`, `:691–796` `originalObjectPins`, `:1317` (`toHaveLength(10)`→11).

**2. [Medium] Installed control 3 mutates only an expectation that duplicates an oracle the row already carries, so no installed control makes the rolled-back prefix observably different on the wire.**
Location: plan §"Three meaningful installed controls" item 3, against plan §"Fixture, mutation inputs and independent oracles" (`every complete item must equal its independently validated seed capture`).

Issue: the row already binds `complete-b` to the independently captured seed record (the `equalsBinding` pattern at `transactional-cumulative.test.ts:1536–1537`). Control 3 changes the *literal tuple* expectation for b's metadata from `{}` to `{phase:"incoming-prefix"}`; the whole-record binding still passes and only the redundant literal fails. It proves the duplicate is metadata-sensitive, not that the oracle set detects a genuinely different served state. Controls 1 and 2 both mutate operation *order*, so all three controls leave the rollback-of-b fact itself un-probed on the wire. The installed precedents this mirrors (`transactional-matrix.test.ts:1264–1311`, `bead-property`/`link-metadata`) mutate the **request body** and are strictly stronger.

Impact: the row's central destructive claim ("failed prefixes must leave full b unchanged") rests only on static expectation pins plus a same-expectation sensitivity check; a regression that committed the prefix would have to be caught by an oracle no installed control has demonstrated to be live.

Fix: replace control 3 with a wire-side control — e.g. delete the `delete a` operation from `d-incoming` so the batch *completes* ( `[update b, delete l, delete r]` ), making b genuinely carry `{phase:"incoming-prefix"}` and l,r genuinely absent; then require the named `complete-b` binding and the beads/links inventory assertions to fail on real served state. Keep the current expectation-only case as one of the static weakening guards the plan already lists.

**3. [Medium] The 2× planning stop is justified by a second "incidence direction" partition that this runtime cannot fail asymmetrically; the plan does not disclose that.**
Location: plan §"Measurement gates" (`This deliberately budgets two destructive-refusal direction partitions plus an ordered comparator`) and §"Exact law and coverage gap" (`test both incident directions`).

Issue: the refusal is a single direction-agnostic predicate. `resource-evaluator.ts:1028–1029` calls `tx.incidentLinks(id)`, implemented at `transaction-store.ts:1148–1152` as `SELECT id FROM resources WHERE kind='link' AND (source=? OR target=?)`. Both of the plan's partitions traverse the identical predicate, the identical `fail("incident-links-exist")`, and the identical `ROLLBACK TO effects` path (`transaction-store.ts:1240`). Nothing in the reference implementation can refuse one direction and admit the other.

Impact: by the plan's own measured analogues, the second partition is ~5 of 21 actions and ~80 of the expected assertions, and it is the stated reason the planning stop is 2× (162106 B / 4256 nodes / 21186 B / 446) rather than ~1.2×. Root is being asked to approve a doubled budget on a rationale that reads as implementation coverage. The partition is defensible as *spec*-level coverage for an arbitrary authority (the clause says "any live Link is incident upon"), but that is a different argument. Note also what the doubled row still does not reach and the plan correctly excludes: out-of-Scope/external endpoints, self-Links, hidden incidence.

Fix: restate the justification as a spec-partition choice rather than an implementation discriminator, and give root the single-direction variant explicitly (≈13 actions, one-no-op-cost stop: ~81053 B / 2128 nodes / 10593 B / ~223) so the budget decision is informed.

**4. [Medium-low] Ledger action 19 asserts a context header on a 404 with no installed precedent in this suite, and the plan does not name it as a measurement risk.**
Location: plan §"Exact 21-action ledger" row 19 (`GET beads/a; 404, authored request and present current context pos-2`).

Issue: this is the only action in the row that pins `bdp-scope-position` on a non-200 response. The code path supports it — `authority-read.ts:797` returns `observed(notFound(), observation)`, `transaction-http.ts:235–237` wraps it with `context(...)`, and `applyReadHttpSemantics` (`read-http.ts:10–39`) does not touch a 404 `application/problem+json` response — but no installed Transactional row observes it today: the closest precedent, `transactional.batch.rollback`'s `absent` action (`GET beads/new` → 404), asserts only status plus authored request/headers. The plan's reason for avoiding `response-metadata-equals` here is correct (`runner.ts:2195` compares `response.status === expected.status`, so a 200 baseline would fold the status), which makes a literal `pos-2` pin the only option.

Impact: action 19 sits after all four POSTs and every destructive observation. A wrong assumption here stops the row at action 19 of 21 in a packed run, after the budget has already been spent.

Fix: flag it in §"Done when and remaining uncertainty" alongside the wire/page-size risks, with a named fallback (presence-only on epoch/view/position, literal status, no equality) to be applied by root disposition rather than discovered mid-run.

**5. [Low] The Event tuple drops `subjectType`, weakening the installed precedent on the one row where it carries the most signal.**
Location: plan §"Scope Events and change groups" (`check complete ordered type/source/subject/ordinal tuples`) vs. `transactional-cumulative.test.ts:1463` (`["/source","/type","/subject","/subjectType","/ordinal"]`).

Issue/impact: the no-op row projects five fields. In this row `subjectType` is what distinguishes `deleted` on `links/l` (`types/relationship`) from `deleted` on `beads/a` (`types/task`) *by type*, and it is the field that catches an authority mislabelling a tombstoned subject's kind. Dropping it loses that for exactly the facts the row is about. Fix: keep the five-projection tuple.

**6. [Low] "15 finite Events fit installed 32 limits" conflates two distinct, separately configurable caps.**
Location: plan §"Measurement gates" (`Maximum 4 operations per new batch and 15 finite Events fit installed 32 limits`).

Issue: the Event-page item cap is `receiptMaximumItems` (`transaction-store.ts:1575`), which only *defaults* to `TRANSACTION_MAXIMUM_OPERATIONS` via `transactionReceiptMaximum()` (`transaction-store.ts:217`) and is a runtime seam (`transaction-runtime-configuration.ts:294`). The 4-operations bound is `TRANSACTION_RUNTIME_LIMITS.maximumOperations = 32` (`transaction-batch.ts:63`). They coincide at 32 only because the installed reference configuration does not set `receiptMaximumItems`. Impact: the `next:null` expectation on a 15-fact page is pinned to a default the plan describes as a single enforced limit. Fix: cite the two caps separately and record that `next:null` depends on the default receipt item maximum.

**7. [Low] "restored" misdescribes savepoint rollback.**
Location: plan §"Exact 21-action ledger" row 7 (`full l,r restored/unchanged`), echoed in §"Fixture…" (`restore the deleted Link`).
Issue/impact: `transaction-store.ts:1240` issues `ROLLBACK TO effects`, so the staged `delete l` never commits — nothing is restored and no compensating write is observable. The wording invites a later reader to believe the row witnesses a restoration event. Fix: "never committed / unchanged".

**8. [Low] "Incoming-only"/"Outgoing-only" name the surviving Link, not the deleted one, and the ambiguity is baked into artifact identifiers.**
Location: plan §"Fixture, mutation inputs and independent oracles" bullets 3–4, ledger IDs `d-incoming*`/`d-outgoing*`, metadata values `{phase:"incoming-prefix"}`.
Issue/impact: in the "incoming-only" batch the operation *present* is `delete l` (a's outgoing Link) and the Link that survives is `r` (incoming to a). The prose disambiguates, but the action IDs and the literal metadata values become permanent artifact bytes that read the other way. Fix: name by what is proven, e.g. `d-incoming-survives` / `d-outgoing-survives`.

**9. [Low] Two citation drifts, and the ordered-success precedent is a self-Link case the row's own exclusion list excludes.**
Location: plan §"Exact law and coverage gap".
Issue: (a) `transaction-store.ts:1236–1247` — the rollback is at `:1240` and the failed-receipt literal closes at `:1248`; the accurate range is 1239–1248. (b) `Spec2303–2306` — the quoted law is 2303–2305; 2305–2306 is the separate *sequence* interleaving sentence, which this atomic-batch row deliberately does not test, so citing it as support for the batch case overreaches slightly. (c) `transaction-store.test.ts:625–670` is titled "deletes a **self-Link** before its Bead with ordered unlink facts and final tombstones", while the plan's exclusion list excludes self-Links; so the 7-fact distinct-endpoint expectation is derived from that self-Link ordering plus `transaction-batch.ts:756–769`, not from an existing distinct-endpoint precedent. Fix: correct (a) and (b); say (c) plainly so root does not read the precedent as covering the distinct-endpoint case.

## Limitations

My own feasibility estimate for the new row (~128 KB manifest growth, ~350 assertions, ~3400 nodes against the 162106/446/4256 stop) is a per-action extrapolation from the no-op row's measured per-action bytes and is not a measurement; the plan is correct that actual M/N/C/A are unmeasured until implementation.

The analogous bead case is proven by the installed no-op row (`complete-a` binds `beads/?limit=32` `/items/0` to a receipt capture and passes) and `bdp.md:1470` forbids embedding incident Links, so the risk is low but unobserved for links.
- I did not evaluate whether two opposite Relationship Links between the same pair trip any aggregate/endpoint-multiplicity path; the installed descriptors (`transactional-matrix.test.ts:52–63`) declare no multiplicity or `owned`, and `maximumEndpointMultiplicity` is empty in the inspected store path, but no installed row creates two Links today.

- I reviewed only the plan file at the stated SHA256 (verified `f99e40c7…`) against repo source. I did not read PR114's review threads, the `bdp-client-v2/design.md` ledger, or any council/CI state, so I take no position on whether these candidate bytes survive that review — which the plan itself also disclaims.
