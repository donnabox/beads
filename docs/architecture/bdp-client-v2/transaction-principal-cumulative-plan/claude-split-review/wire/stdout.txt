**1. HIGH [O] — `HANDLE_ID` is never exhibited, yet all three new credential handles are hyphenated.**
Location: plan §"One truthful default configuration" ("expose exact handles operator,reader,anonymous,principal-a,principal-a-rotated,principal-b"); proof JSON `configuration.credentials[*].ref`; manifest `credentialRef` on all seven actions — against `packages/conformance/src/http-executor.ts:681` (`if (typeof ref !== "string" || !HANDLE_ID.test(ref) || ref.length > 128) return configuration();`).
Issue/impact: the only handle ids attested anywhere in supplied evidence are `operator`, `reader`, `anonymous` — none containing `-`. `HANDLE_ID`'s pattern is not supplied, so there is no evidence that `principal-a`, `principal-a-rotated`, `principal-b` are accepted. If the pattern excludes `-`, every one of the seven new dispatches takes the `return configuration()` refusal branch before `resolveCredentials` is ever called; the row fails wholesale for a reason unrelated to namespace isolation, and the control's expected `[200,409]` is unreachable too. Length (max 19 ≤ 128) is fine; the character class is the unknown.
Smallest correction: exhibit the `HANDLE_ID` literal from `http-executor.ts` and show the three refs match. If it rejects `-`, rename the three handles/refs to an accepted spelling and update the manifest `credentialRef` values and the closed resolver map accordingly; no other change is needed.

**6. MEDIUM [P] — actions 6 and 7 drop the standalone's epoch equality, and the Event-ID projection absorbs whatever epoch/view the server returned.**
Location: plan §"…complete oracles" (collection/event paragraphs; "GET7 supplies its own validated serving view") versus `transactional-principal-key-installed.test.ts:551–674`, which asserts `collectionWire.headers["bdp-scope-epoch"] === a.receipt.scopeEpoch` *and* `eventsWire.headers["bdp-scope-epoch"] === a.receipt.scopeEpoch`.
