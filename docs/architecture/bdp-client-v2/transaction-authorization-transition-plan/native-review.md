## Required corrections

**N1 — high: distinguish rolled-back administration from an uncertain commit.** Required behavior2 says failed commit leaves the old snapshot/leases active. transaction-store.ts:370–402 deliberately treats a throwing COMMIT, failed rollback or non-constraint SQLite failure as an uncertain owner fault. Keeping old delivery alive in that state could disclose under a revocation that actually committed. Amend: only a confirmed pre-commit rollback preserves old policy/leases. Uncertain commit fences admission and aborts affected delivery leases; reopen reads the durable policy before resuming. A post-commit notification failure must also fail closed, never roll the visible policy back. Preserve the existing atomic failure discipline.

**N2 — high: lease registration must reject a stale initial observation.** Aborting only currently registered old-view streams is insufficient. transaction-runtime.ts:176–193 awaits handler selection, then registers through service.stream; service.ts:282–302 accepts no view argument. A transition between selection and registration leaves an old materialized packet outside the cancellation set. Require an owner-serialized acquireDeliveryLease(expected immutable snapshot/view) that both validates the expected snapshot and registers the abortable lease before releasing the owner entry. A stale acquisition cannot write headers/frames. Cancellation and registration share this boundary; no arbitrary user callback runs inside the owner transaction. Existing pump write() checks AbortSignal immediately before sink.write (transaction-sse.ts:63–99), so its signal can enforce queued-frame exclusion without a second independent mutable policy lookup. Add a deterministic zero-HTTP stale-selection/acquisition case alongside the backpressure case. Already accepted socket writes remain outside the recall claim.

**N3 — high: freeze all receipt-delivery and admitted-work paths, not just root GET/new POST.** Root projection alone leaves concrete exits:
- transaction-store.ts:2069–2099 calls observeReceipt but discards its return, then slices original receipt.results for a page.
- transaction-service.ts:564–579 freezes the previously accumulated sequence response rather than reprojecting it under the final observation.
- store executeClaim:1140–1155 executes a previously acquired claim; sequence reserves claims at1792–1830 and resolves/executes them at1888–1955. An entry-only HTTP permission check does not cover those turns after a transition.

Specify one retained-receipt projection primitive used by root, legitimate retained pages, duplicate/synchronous delivery and sequence-member projection. Preserve execution-body epoch/view and positions; response context is current (spec5234–5273). Do not erase matched/deleted/alias/failed execution facts merely because read policy is empty. For mutation permission, check current policy at each owner execution turn as well as admission; an already committed transaction is not undone. Define safe cleanup of unexecuted owned reservations and preserve sequence committed-prefix facts. Pin direct-owner, page and sequence cases in the CPU/source inventory. This is necessary fanout of the existing promise, not an additional public feature.

**N4 — medium: Snapshot durable validation must be independent of serving-view validity in maintenance too.** The plan correctly requires known live old-view handles to fail409. Do not implement that by changing disposition() to throw foreign-view whenever d.view differs. disposition is also called by expire at snapshot.ts:273–296 and liveLedger at299–318, which capture uses at607–624. That would prevent fresh empty Snapshots or expiry of old-view handles. Separate integrity validation against the persisted disposition/recognized policy lineage from request authorization fencing in resolve (545–575), after issued-token legitimacy and before body loading. Keep old live handles in real storage/capacity accounting; revocation is not expiry or permission to discard durable promises. A fresh empty capture must not enumerate/copy raw authority records as current capture does at617–640; project its inventory first while retaining the same bounded integrity rules.

## Concrete architecture recommendation

Use one durable **Scope-wide immutable policy snapshot** initially, resolved through a principal-aware internal capture interface. This matches the actual owner’s shared policy today and avoids prematurely implementing principal provisioning/retirement/defaulting. State explicitly that the administrative replacement affects every authenticated principal in this Scope, while receipt ownership remains principal-specific. A small CPU second-principal check should prevent accidental caller-only revocation. This is a routine implementation choice, not a ruling that all deployments must share a view.

The snapshot should separate stable installation/authority facts from a current read policy identity/view and mutation permission. Version the private durable policy envelope with an explicit binding kind (Scope now; an explicitly bounded principal binding can be added later) and monotonic generation/opaque view. Do not encode live policy into retained graph/group identities, rewrite receipt bodies, or use credentials as the generation. Keep authentication and credential canMutate as an upper bound: effective mutation permission is credential permission AND current owner permission, never a replacement that elevates read-only credentials. Trusted direct owner entry enforces the owner restriction too.

Reuse authority-read's existing synchronous capture(reader, principal, intent) within withRead (authority-read.ts:471–500). Replace transaction-read's lifetime-captured policy at131–137/162–170 with the same-entry snapshot; do not recreate the entire Read plane and lose its actual issued cursors. For future principal mappings, this capture seam and independent fact validation avoid a retained-fact rewrite. Do not claim that this first policy proves arbitrary partial ACLs, owned closure, grant/regrant, or installed administration.

Migration should accept only the exact old configuration preimage, atomically add a bounded policy record and new private storage revision, and preserve the initial development-all-visible view. Existing old-binary exact configuration comparison (store.ts:540–547) then rejects the migrated format. Missing/corrupt records in a new-format store must fault. Validate historical group views against recognized retained policy/fact context, not merely against a caller-supplied group.view; preserve epoch/position/ordinal/framing checks (events.ts:190–210; changefeed.ts:119–160). Empty-view Changes legitimately emit projectionAdvance with no transaction and empty arrays (spec6135 onward); all-visible retained bytes remain unchanged.

## Sound parts and proof limits

The plan correctly uses Snapshot manifest's real initial bead page/next; no extra first-page request is needed (snapshot.ts:488–542,585–602). Old-view checkpoints, Event IDs and collection tokens must fail via their existing context fences; no S1/G2 or unknown-minimum decision is inferred. Request13 uses the actual Snapshot checkpoint; reconnect precedence remains real. The second Event stream without after plus the backpressured real-packet case is materially stronger than elapsed silence.

The negative suppress-publication/cancellation control must suppress one coherent publication step without independently changing persisted facts or response expectations; its first named generation/lease failure establishes sensitivity only. Exact mutation and failure inventory remain preflight work. Complete schema/body checks, durable reopen/rollback tests, real lease milestones, bounded cleanup and primary+cleanup retention remain required. Metadata must describe the actual current policy; ready-time configuration metadata alone must not be advertised as a permanently live authorization attestation.

Freeze exact production/type/caller footprint and the CPU cases above before authoring. No remote policy endpoint, credential grammar, new transport seam, arbitrary partial policy engine, public profile claim or expanded product-question scope is needed.
