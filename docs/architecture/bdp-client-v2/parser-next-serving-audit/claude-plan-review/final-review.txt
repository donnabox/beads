# Blockers (correct before authoring)

### BL1 — Medium. C's two refusal observations are synchronous throws, not rejections
**Plan:** ¶48 ("Separately one post-close real-owner.readEvents call **must reject**") and ¶52 ("call service.events once while closing; that call is refused before owner entry").
**Source:** `transaction-service.ts:139-154` — `run()` calls `check()` synchronously, so `service.events(...)` **throws** rather than returning a rejected promise; `transaction-store.ts:396-407` — `enter()` throws `"transaction store closed or reentrant"`, and `readEvents` (`:1637`) is a synchronous function. Both shapes are already pinned by the existing callback: `transaction-service.test.ts:1036` `expect(() => service.events(...)).toThrow("closing or closed")` and `:1039` `expect(() => f.owner.readEvents(...)).toThrow()`.
**Impact:** a test authored to the plan's wording (`await expect(...).rejects...`) fails or swallows the exception, and C's "exact" observation claim is wrong at the observation layer — the one layer the plan says must be exact.
**Smallest correction:** in ¶48/¶52 state: "both refusals are synchronous throws asserted with `expect(() => …).toThrow(…)` — the while-closing `service.events` throws `transaction service is closing or closed`, the post-close direct `owner.readEvents` throws `transaction store closed or reentrant`; neither yields a promise. Only the two admitted requests are observed as rejections."

### BL2 — Medium. "The parser source remains untouched" is unsatisfiable as written, because the frozen parser bytes are inside a nominated file
**Plan:** ¶32 nominates `transaction-http.ts`; ¶73 ("Earlier parser successor and PR150 bytes remain preserved") and ¶79 ("The parser source remains untouched until its validation is complete").
**Source:** the parser-successor production change is in `transaction-http.ts:578-591` (`if (isReadProblem(parsed) && parsed.status === 400) return problem(parsed);` ahead of the `minimum-position` / `minimum-position-route` labels), and its evidence is `transaction-http.test.ts:5361-5562` (`withParserRefusalOwner`, logged as `observation: "parser-refusal-source"`) plus the three callbacks at `:5564-5610`.
**Impact:** the freeze statement is file-scoped but the edit is file-scoped too, so the later "parser untouched" verification cannot be made as stated; it also leaves open the risk of an author re-flowing or renumbering those lines while editing the Event branch in the same file.
**Smallest correction:** replace ¶79's sentence with byte scope: "No change inside `transaction-http.ts:574-591` (the canonical-Read current-minimum gate) and none in `transaction-http.test.ts`; the Event edit is confined to the branch at `transaction-http.ts:502-536`. The authored diff must be taken against `b76c3b7` and must show those parser lines byte-identical."

### BL3 — Medium. E's cleanup rule does not exclude the historical unconditional store deletion
**Plan:** ¶67 ("Bound cleanup attempts jointly, preserve primary/cleanup errors, close child before removing owned store, and fail on unknown ownership/deadline/late exit").
**Source:** the historical `finally` at `transactional-event-missing-context-installed.test.ts:356-370` removes the owned directory with `rmSync` **unconditionally**, i.e. also after `child.close()` threw; `scripts/transaction-installed-observation.mjs:48-60` only SIGKILLs and rethrows on an unclean exit, so the child may still hold the SQLite file.
**Impact:** an author copying the historical prefix (which ¶67 instructs) deletes the owned store under a possibly-live child, destroying the survivor evidence the plan says it must report.
**Smallest correction:** add to ¶67: "remove the owned directory only after a verified clean child close; if close failed or the deadline fired, record `directory`, `childPid`, `childExitCode`, `childSignalCode` and `directoryAbsent:false` as survivors and fail — do not copy the historical unconditional `rmSync`."

### BL4 — Medium. E's three exchanges cannot be dispatched without declaring its own exact-mode routes and bound
**Plan:** ¶67 ("Exactly3 HTTP exchanges: finite Scope Event setup GET …, matched opaque GET, matched opaque HEAD … Reuse … existing raw executor … Retain existing5s exchange bound … and callback bound from that fixture").
**Source:** `packages/conformance/src/http-executor.ts:560-567` rejects any exchange whose `(method, url)` pair is absent from `exactMode.routes` with a `configuration` failure before any wire write; the historical routes list (`transactional-event-missing-context-installed.test.ts:150-159`) declares only `GET ${scope}events/` (no HEAD), and the historical dispatch bound is `expect(++attempted).toBeLessThanOrEqual(11)` (`:193`).
**Impact:** the matched-opaque HEAD — the bodyless-metadata half of the E oracle — fails as a harness configuration error, not as a wire observation.
**Smallest correction:** in ¶67 state: "the new callback constructs its own executor with `routes: [{GET, `${scope}events/`}, {HEAD, `${scope}events/`}]`, `requestTimeoutMs: 5000`, its own `attempted <= 3` bound, and its own response-fingerprint array; module-level `entry`/`sourceCommit`/`binding`/`validPage` are reused unchanged."

# Optional improvements

1. **Cite the conditional-ordering MUST.** ¶64's `If-None-Match: *` / `If-Match: "wrong"` pairs rest on `bdp.md:5876` ("Scope epoch/view, minimum-position and erasure/expiry checks MUST precede any conditional shortcut") and `1986-1989` ("An ordinary refusal is not replaced by `304`"). ¶9's normative paragraph cites neither. Adding them turns those six exchanges from preservation preference into a cited obligation. (Behavior itself is already correct: `read-http.ts:10-14` only rewrites `200`-JSON/`204`, so the `503` cannot become `304/412/406`.)
2. **C's "delegate count before close is 5" is misleading.** Two of the five delegated attempts (drained #2 and #3) occur *after* `service.close()` is invoked, during drain. Restate as "5 delegated attempts in total for C, asserted after `await closing`; exactly 3 have occurred at the moment `close()` is called."
3. **Pin B's clock seam.** `transaction-consistency.ts:155,170,176` calls `now()` once at start plus once per failed attempt and waits `min(5, deadline-current)`. The stated 0/5/10 schedule therefore requires `now` to read a mutable variable advanced by the gate; a `() => tick++` generator (used at `transaction-service.test.ts:936,1158,1195`) would shift it because the setup call also consumes a `now()`. Say which form B uses.
4. **Name where the service capture sits.** ¶28 says "before run/wait starts". Placing `snapshotCurrentReadMinimum` *outside* `run()` (as `changes()`/`beginEvents()` do at `transaction-service.ts:451-458,489-492`) converts today's rejected-promise TypeError for a malformed tuple into a synchronous throw and moves it ahead of `check()`. Capturing inside the `run(...)` callback but before `waitForTransactionMinimum` keeps delivery shape and the closing check unchanged while still preceding the first attempt. Either is defensible; pick one explicitly.
5. **"Keep source existence first" is inaccurate about current layout.** In `transaction-store.ts:1649-1655` the source parse *and* the tuple snapshot both run **before** `enter()`; only the comparison order (`eventSourceKnown` → sentinel → `readContext` → check, `:1659-1666`) is inside the entry. Reword ¶29 to "inside the owner entry, keep source existence and the sentinel return ahead of the minimum comparison; tuple capture stays outside the entry as today."
6. **A's no-scan oracle is vacuous for two of its six refusals.** The `after`-bearing and Resource-source opaque tuples throw from `snapshotTransactionMinimum` before `enter()` (`:1652-1655`), so zero prepares is trivially true there; the real evidence is for Unproved/Unsupported/behind, where the owner is entered, `readContext()` runs, and `retainedGroupReader()` (`:1677`) is never reached. Also state that the setup page must be read before the spy is installed (as the model at `transaction-events.test.ts:614-636` does), or the setup scan contaminates the zero-group count.
7. **Build-prerequisite precision.** ¶75 says the build must precede *collection* of `transaction-events.test.ts`; in fact its `../dist/transaction-runtime.js` import is inside the callback (`:396-398`), i.e. execution-time. The collection-time dist dependency is the installed module (`realpathSync(entry)` at module level, installed test `:57-64`). If `transaction-dependencies.test.ts` is selected as a regression it also needs dist (`:518-531`). Restate accordingly; the ordering requirement is unchanged.
8. **D needs a problem validator.** `transaction-events.test.ts:122` compiles only `validPage`. The `503` assertion needs `$ref: #/$defs/transactionalProblem`; the bundle already constrains `catch-up-timeout` to `.../problems/unavailable`, `503`, `after-delay` (`schemas/bdp-v0.schema.json:4260-4283`), which matches `transaction-http.ts:628-633` with protocol's `temporarily-unavailable` family. Worth naming so the schema step isn't improvised.
9. **State the retained gap honestly in ¶7.** After this change, Event reads with an unknown minimum that carry `after`, select SSE, target a Resource `view=events`, or negotiate non-JSON still return the private `500` + `x-bdp-development-limit: minimum-position`, which is not among `5841-5843`'s permitted outcomes (representation / wait / route / foreign-view / cursor-expired / catch-up-timeout). The plan preserves that deliberately (S1-adjacent, `5850-5851`), but ¶7/¶64 should record it as a known preserved gap rather than leaving it to inference.
10. **D's per-test bound.** No explicit vitest timeout is used by the 394 model and `vitest.config.ts` sets no `testTimeout`, so the new callback inherits the 5 s default while deliberately burning six 80 ms budgets (~16 × 5 ms real sleeps each, `transaction-consistency.ts:176`) plus runtime start/close — roughly 1 s. Fine, but state the expectation; if headroom is wanted, lower the new runtime's `minimumReads.budgetMs`, do not widen the bound.
11. **Catalog hygiene (one line).** The new behavior is the subject matter of `transactional.changefeed.catch-up-timeout` (`packages/conformance/catalog/transactional-v1.json:1186`). The plan already leaves catalog/manifest bytes alone; add an explicit "no catalog selection or coverage claim follows from D/E" so the counts cannot later be relabeled as conformance evidence.
