# D4 administrative erasure and restore: next realization plan

The next useful implementation design is an owner-private administrative boundary integrated with the existing serialized TX store, every retained carrier and its publication fence. A method that appends an erasure record alone cannot close these requirements. The recommended restore option imports validated logical history into an **intact current identity/erasure store**, rather than replacing that store with an old SQLite image. This preserves newer allocation and erasure evidence while the history moves to a new epoch. Both recommendations remain CLOSED design options, not supported APIs or adopted source.

The existing seams are concrete. `transaction-store.ts` owns exclusive SQLite entry, atomic commit and ambiguous-commit fencing. Its format11 stores current resources, identities, aliases, receipts/page plans, creator facts, groups and snapshot records/pages, but no permanent erasure ledger or original-version commitment inventory. The service's policy-replacement drain is a useful lifecycle pattern; it only changes all-visible to empty and does not erase data, track per-view erasure floors or coordinate queued frames.
