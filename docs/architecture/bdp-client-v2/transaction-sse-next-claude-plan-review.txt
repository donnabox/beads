# Findings — plan G2a (changefeed SSE) vs. frozen dfcf

## 1. HIGH — `stringifyJsonValue` rationale is factually wrong; done-when 13 specifies a test that cannot mean what it says

**Plan**: §"One owner, one frame at a time" (line 54); §"Executable done-when" item 13.

**Evidence**
- `packages/protocol/src/json-values.ts:93-96`: "Primitive escaping/number formatting is **exactly JSON.stringify's**"; line 114 emits every scalar via `JSON.stringify(item)`.
- `json-values.ts:31-33`: "Numeric values here have **lost their original spelling**: raw write requests still require lossless numeric admission before reaching this boundary."
- `transaction-store.ts:557`: retained group bodies are `JSON.parse(body)` — spelling is already gone before projection.
- Losslessness is an *admission-time* property: `json-admission.ts:211-218` `isAdmissibleJsonNumber` **refuses** any literal whose exact decimal differs from `exactDecimal(JSON.stringify(nearest))`.

**Impact**: The plan's stated reason for preferring `stringifyJsonValue` ("so exact numeric literals survive") is false — it is numerically identical to `JSON.stringify`. An implementer writing done-when 13's "numeric literal frame test" either asserts something false (`1.0e2` surviving as `1.0e2`) or writes a vacuous assertion and files it as evidence of "lossless serialization" the system does not provide.

**Bounded fix**: Restate the rationale as the two properties the helper actually supplies — (a) byte-identity with the finite JSON page and with `deliver()`'s Content-Length serializer (`transaction-runtime.ts:76-78`), and (b) immutable-snapshot / accessor-swap and unpaired-surrogate safety. Rewrite done-when 13 to assert the SSE `data` field is byte-identical to that group's encoding inside the corresponding finite page, and cite admission-time numeric admissibility as the real lossless guarantee.

## 2. HIGH — finite-HTTP preservation: two pinned `406` assertions are affected, one inverted, and the plan calls its test work "bounded additions"

**Plan**: §"Exact file ownership and predecessor gate" (Tests paragraph); §"Admission and representation selection" step 3.

**Evidence**
- `packages/server/src/transaction-changefeed.test.ts:676-680`: GET `changes/?after=genesis` with `Accept: text/event-stream` → **406, empty body** (today's pinned behavior). G2a inverts this.
- `packages/server/src/transaction-events.test.ts:472-476`: `events/` with `Accept: text/event-stream` → **406 for both GET and HEAD**. G2a must *preserve* this (G2b is unimplemented).
- Both are produced by the same single gate: `read-http.ts:26-33` inside `applyReadHttpSemantics`, applied once for every GET/HEAD at `transaction-http.ts:448-450`.

**Impact**: If the extracted media helper is wired into `applyReadHttpSemantics` rather than only into the `changes/` branch at `transaction-http.ts:322-332`, the Event routes either start returning `200 text/event-stream` for transport that does not exist, or lose their honest 406. Separately, "bounded additions to service/HTTP/runtime tests" hides a mandatory *change* to an existing pinned assertion — exactly the kind of silent rewrite the plan's own discipline forbids.

**Bounded fix**: Name both assertions in the plan. Require SSE selection to be reachable only from the changefeed branch, with `applyReadHttpSemantics` left byte-behaviour-identical for JSON/204. Add a done-when that `events/` and `?view=events` still return bodyless 406 for `Accept: text/event-stream` under G2a.

## 3. MEDIUM-HIGH — `Last-Event-ID: genesis` has no disposition and bypasses the epoch/view binding

**Plan**: §"Real ambiguities" item 2; step 1; done-when 3.

**Evidence**
- `transaction-changefeed.ts:56-62`: `parseCheckpoint` returns `{position: 0}` for `"genesis"` **before** any tag comparison; `checkpointPosition` (74-86) returns `0` immediately, so the epoch check (81-82) and view check (83-84) never run.
- `genesis` is never emitted as an SSE `id`: `transactionCheckpoint` yields `"genesis"` only at position 0, and groups occupy positions ≥ 1.
- Spec `#event-id-and-checkpoint-character-profile` 6572-6573 reserves genesis and says it is "never assigned to an Event or later position".
- `transaction-changefeed.test.ts:674-675` already exercises `last-event-id: genesis` on the finite path.

**Impact**: Under the plan's rule "a positive Last-Event-ID overrides `after` for SSE", a client or intermediary sending `Last-Event-ID: genesis` to a `start=now` stream silently gets a complete-history replay with **no epoch/view validation** — precisely the case the mandatory erasure fence (6464-6473: "a read whose `after` precedes P fails with `cursor-expired`") must reject. The plan's ambiguity #2 covers only empty/whitespace/malformed/repeated headers.

**Bounded fix**: Add an explicit disposition for a reserved, never-emitted checkpoint arriving in `Last-Event-ID` — refuse as local-reference `invalid-parameter`, or record it as a named private gap — and add the case to done-when 3.

## 4. MEDIUM — ambiguity #1's "no query intent" limb is already settled by frozen code and a pinned test

**Plan**: §"Real ambiguities" item 1 ("Last-Event-ID with original start=now, **or with no query intent**").

**Evidence**
- `transaction-changefeed.ts:99`: `if ((after === null) === (start === null)) throw new TransactionChangefeedParameterError()` — exactly one intent required, evaluated before any Accept or header inspection.
- `transaction-changefeed.test.ts:669-673` pins `changes/` + a valid `last-event-id` → `400` `invalid-parameter`.
- Spec 5974: "Omitting both is an error. It never means 'start at whatever history remains.'"

**Impact**: The only implementable G2a behavior for header-without-query is the inherited 400. Presenting it as an open combination invites an implementer to relax the one-intent parser to "support EventSource", which breaks the pinned 400 and contradicts 5974. This conflates a routine settled case with genuine normative ambiguity.

**Bounded fix**: Split item 1 — keep only "header + original `start=now`" as genuinely unresolved; state that "header with no query intent" is settled as 400 by 5965-5975 plus `transaction-changefeed.ts:99`, and that the parser must not be relaxed.

## 5. MEDIUM — an existing client-disconnect seam is overlooked, and installing one changes two existing finite call sites

**Plan**: §"Actual code, reusable seams and missing transport" (line 38); step on disconnect/cleanup (line 58); done-when 10.

**Evidence**
- `packages/server/src/index.ts:443-455` `createNodeHttpDisconnectSignal` already folds `incoming 'aborted'` and `outgoing 'close'` (when `!writableFinished`) into one `AbortSignal`; `index.ts:479-481` passes it through `new Request(..., { signal })`; `index.ts:496-499` already maps `ScopeServerOperationAbortedError` to `outgoing.destroy()`.
- `transaction-runtime.ts:130` builds a signal-less `Request`, while `transaction-http.ts:329` and `:345-350` **already** pass `request.signal` into `service.changes`/`service.events`.
- `transaction-consistency.ts:107` throws `ScopeServerOperationAbortedError` when the signal is aborted; `handle`'s catch (`transaction-http.ts:420-444`) has no branch for it → bodyless `empty(500)`.

**Impact**: (a) "Request currently has no client-disconnect signal" overstates the gap repo-wide and risks duplicating a seam the plan's own "do not duplicate policy machinery" rule forbids; `index.ts` is absent from the ownership list. (b) Wiring a real signal silently reclassifies an existing finite behavior: a client disconnecting during a minimum wait on `changes/`/`events/` now produces an abort routed through the internal-fault branch instead of a completed-then-discarded read.

**Bounded fix**: Name `createNodeHttpDisconnectSignal` as the pattern (export it with root coordination, or declare the ~10-line duplication deliberate). Add a `ScopeServerOperationAbortedError` branch that destroys the socket rather than synthesizing 500. Add a done-when pinning that finite `changes/`/`events/` minimum-wait behavior is unchanged for non-disconnecting clients. Drive slot release from the `response` `'close'` event (fires on destroy as well as FIN), not FIN detection, so the one-slot cap cannot leak for the 10s socket timeout.

## 8. MEDIUM — stream registration vs. `service.close()`'s one-shot `active` snapshot is left ambiguous; ordinary shutdown is indistinguishable from an owner fault

**Plan**: line 33 ("An indefinite stream cannot simply remain in that active set forever"), line 58, line 59, done-when 10.

**Evidence**: `transaction-service.ts:82-97` `run()` calls `check()` and registers one promise per call. `close()` (394-411) sets `accepting = false`, then evaluates `Promise.allSettled([...active])` **once, synchronously** when the async IIFE starts — nothing registered afterwards is awaited. Any later `run()` throws the plain `Error("transaction service is closing or closed")` from `check()` (line 80).

**Impact**: Registering the pump as one long-lived `run()` task makes `close()` block indefinitely — a direction the plan's warning ("do not await service.close from a stream task that service.close is itself waiting on") does not cover. Registering per-poll means shutdown surfaces as a plain `Error`, which the plan's rule at line 59 ("an owner fault or gap after stream headers closes the stream") would record in retained diagnostics as an owner fault, making done-when 10's "original+cleanup diagnostic causes are retained" untruthful about cause.

**Bounded fix**: Pin a separate `streams` registry that `close()` cancels **before** it snapshots `active`, leaving mutation drain semantics untouched; require ordinary-shutdown cancellation to be a distinct retained cause from an owner fault in done-when 10.

## 9. LOW-MEDIUM — only one of four captured transport deadlines is analysed; the 5s heartbeat is sized against an unverified assumption

**Plan**: line 55 ("fit the current10s idle timeout"); done-when 11.

**Evidence**: `transaction-runtime-configuration.ts:102-111` captures and hashes `requestTimeout: 10000`, `headersTimeout: 10000`, `timeout: 10000`, `keepAliveTimeout: 1000`. `transaction-runtime.ts:180-193` installs all four and asserts them; `:193` destroys the socket on `'timeout'`. **Impact**: Whether `server.requestTimeout` continues to govern after the request has been fully received decides whether a >10s idle stream is achievable at all. **Bounded fix**: Enumerate all four deadlines, record as an observed evidence fact which of them apply after response headers are sent, and derive the heartbeat interval from that observation rather than from `timeout` alone. Also pin the raw SSE recorder's own deadline relative to the 10s server deadline (the existing exact-mode helpers use 5000ms: `transactional-execution-binding.ts:187`, `raw-development-http.ts:52`).
