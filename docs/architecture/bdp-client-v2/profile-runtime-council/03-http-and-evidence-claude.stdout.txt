## A. Proven defects (decidable from the supplied source)

### 1. Medium — `targetProcess` binding for `bdpbd` is a per-run nonce, not a recipe digest
**File/section:** `scripts/generate-read-cohort.mts:519-524` (bdpbd `baseEnv`) and `:590-607` (`targetProcess: canonicalJsonDigest({... environment: plan.baseEnv ...})`); consumed by `packages/conformance/src/cohort-verification.ts:327-334`.

**Issue:** `bdpbd`'s `baseEnv` spreads `bdEnvironment` (`:450-458`), which carries `HOME: path.join(temporaryRoot, "home")` and `GIT_CONFIG_GLOBAL` under a `mkdtemp` root, plus the inherited `PATH`/`TMPDIR`, plus `BDP_BD_EXECUTABLE: bdExecutable` (an absolute resolved path, `:393`). The digest therefore changes on every run and every machine, independently of any source or recipe change.

**Reachable trigger:** run `generate-read-cohort` twice from the same clean tree — bdpbd's `targetProcess` differs both times (the artifact summary's `2562c874…` is not reproducible). Conversely, materially change the launch recipe and the digest moves no more distinguishably than normal churn.

**Impact:** the binding the verifier demands as the packaged launch recipe conveys no recoverable information for bdpbd: it cannot detect recipe drift and cannot be re-derived by a reviewer, contrary to the stated convention at `:320-329` ("so a reviewer can re-derive every value from the run head").

**Fix/next step:** normalize before digesting — substitute stable placeholders for per-run temp paths, exclude inherited `PATH`/`TMPDIR`, and reference bd by the content digest already recorded as `bdExecutable` instead of its filesystem path.

### 2. Medium — the verifier's documented anti-relabel guarantee does not hold
**File/section:** `packages/conformance/src/cohort-verification.ts:323-340`; comment at `:325-326` reads "Relabeling an in-process segment as packaged therefore fails here: the bindings it could not honestly carry are exactly the ones now demanded." Related claim: `packages/server/src/read-conformance-capability.ts:5-10`.

**Issue:** the three `PACKAGED_ONLY_BINDING_KEYS` are only checked against `SHA256_HEX` (`:330`). None is recomputed: `installedPayload` digests `apps/*/dist/main.js` (build output, not committed, so the gate cannot re-derive it), and `targetProcess`/`workspace` are generator-internal canonical-JSON digests with no committed byte source.

**Reachable trigger (walked end to end against every check in `verifyReadCohortEvidence`):** take the committed artifact's bdptest in-process segment, set `admission: "packaged"` on the segment and its 11 rows, add three arbitrary 64-hex strings for the packaged-only bindings, update `packagedRows` 36→47 and `selfCertifiedRows` 11→0 (`:539-551` stays consistent, `scores.pass` stays 47), keep canonical formatting, recompute the constant, and commit the artifact plus `read-conformance-capability.ts`. Every remaining check passes: the `in-process ⇒ selfCertifiable` rule (`:474-478`) no longer applies, and there is **no** `packaged ⇒ ¬selfCertifiable` rule.

**Impact:** the honest packaged/in-process split rests entirely on the generator, not the gate. The forged artifact would present 11 rows as black-box packaged conformance while its own derived `selfCertified` list (`:214-219`) still names them — an internally contradictory artifact that verifies green, directly against `selfCertifiedNote` ("must not be presented as black-box conformance"). Severity is Medium under the "detect drift/sloppiness" reading of the gate; High if the evidence model is intended to resist a committer, which the comment's wording asserts.

**Fix/next step:** (a) refuse `admission === "packaged"` for any id in `input.derivedSelfCertifiable` — consistent with the existing derivation semantics, not a new product decision; and (b) soften the `:323-326` comment to what is actually proved (shape only), or bind `installedPayload` to a committed build-provenance digest the gate can re-derive.

### 3. Low — the non-attesting marker is missing on 405/406/500 and alias 307 responses
**File/section:** `packages/server/src/development-runtime.ts:76-84` (`empty`) and `:200-205` (307); the marker is set only in `json` (`:57`) and `readJson` (`:95`).

**Reachable trigger:** `OPTIONS /development/create-bead` → 405 (`:168`); `Accept: text/plain` on a mutation POST → bodyless 406 (`:239`); `GET /alias/x` → 307 (`:201`); any non-`ReceivingError` throw → 500 (`:249`).

**Impact:** the one invariant this server advertises (`:1`, "Explicitly non-attesting") is not uniformly present on captured responses; a 405/406/500/307 from this server is header-indistinguishable from a production server's.

**Fix/next step:** set `x-bdp-development: non-attesting` in `empty()` and on the 307 path.

### 4. Low — unknown `/development/*` mutation targets answer 405 `Allow: GET, HEAD`; the `resource-not-found` branch is dead
**File/section:** `packages/server/src/development-runtime.ts:164-166, 209-213`. Line `:213` (`if (!operation && name !== "sequence") throw new ReceivingError("resource-not-found")`) is unreachable: anything that reaches it already satisfies `method === "POST" && mutationTarget`.

**Reachable trigger:** `POST /development/does-not-exist` → 405 with `Allow: GET, HEAD`. Also `POST /development/create-bead?x=1`: `:164` slices the **raw** target, so `name` becomes `create-bead?x=1`, `mutationTarget` is false, and a valid operation URL with a query string gets the same 405.

**Impact:** misleading refusal (advertises GET/HEAD on a nonexistent target) and a dead admission branch; a diagnostic probing "unknown operation" records 405, not `resource-not-found`.

**Fix/next step:** route on the parsed `url.pathname`, and refuse unknown `/development/*` names with `resource-not-found` before the method checks.

### 5. Low — limit incoherence makes three configured refusal boundaries unreachable over HTTP
**File/section:** `packages/server/src/development-authority.ts:28-34` and `:112-126`, against `development-runtime.ts:110-121`.

**Issue:** `propertiesBytes: 64 KiB` equals `requestBodyBytes: 64 KiB`, and `diagnosticBytes: 512 KiB` / `representationBytes: 256 KiB` both exceed the HTTP body cap, so `request-too-large` always trips first. Separately, `:120` draws `diagnostics` from the raw `DEVELOPMENT_LIMITS` while `:121` draws `diagnosticBytes` from the snapshotted `bounds` — sibling budget fields with different provenance, so any normalization inside `snapshotReadUpdateRuntimeLimits` applies to one and not the other.

**Reachable trigger:** submit a 64 KiB `properties` document → `request-too-large`, never the properties-bytes refusal.

**Impact:** the configured values are dead over the HTTP lane; any diagnostic row claiming to observe the properties/representation/diagnostic-byte boundary would in fact be observing the body cap. (I cannot check whether such a row exists — the dev manifest is not supplied.)

**Fix/next step:** set `propertiesBytes`/`representationBytes` strictly below `requestBodyBytes` or document them as in-process-only bounds; source both numeric-budget fields from `bounds`.

### 6. Low — `normalizationSafeRawRequestPath` returns a path for authority-form targets
**File/section:** `packages/server/src/node-http-target.ts:11-25` (and `:38-51`).

**Issue:** for `"//evil.example/x"`, `authorityStart = 2`, `pathname = "/x"`, and the final WHATWG equality check at `:30-32` compares against `/x` (protocol-relative resolution) — so the function returns `"/x"`, silently discarding the authority. The returned value is not a substring of the supplied target.

**Reachable trigger:** any caller that does not independently reject `//`. `development-runtime.ts:158` does reject it, so the dev server is unaffected; **other call sites are not in the packet.**

**Impact:** the helper's name and contract ("normalization-safe raw request path") invite use as a single admission check, where it would silently collapse an authority-form target to a local path.

**Fix/next step:** return `undefined` for authority-form input, or return the authority so callers must handle it explicitly.

### 7. Low — a legal empty query is refused as malformed
**File/section:** `packages/server/src/node-http-target.ts:6-8, 29-32`.

**Issue:** for target `/x?`, `search = "?"` while `parsed.search === ""`, so the equality check fails and the function returns `undefined`. In the dev server that becomes `malformed-request` (`:159-161`).

**Impact:** a syntactically valid request target is rejected. Possibly deliberate fail-closed strictness; flagged because `read.http.raw-request-targets` is a required cohort row and the production call sites are not in the packet.

**Fix/next step:** compare normalized query presence (`queryIndex !== -1 && search === "?"`) as an allowed case, or state the exclusion where the helper's contract is documented.

### 8. Low — `scenario.actions ?? scenario.requests` skips oracle validation for an empty `actions`
**File/section:** `packages/conformance/src/artifact-bundle.ts:186`.

**Issue:** `[] ?? x` evaluates to `[]`, so a scenario declaring `actions: []` suppresses validation of its `requests` assertions entirely; a scenario carrying both validates only `actions`.

**Reachable trigger:** depends on whether `parseExecutableScenarioManifest` permits either shape (not supplied).

**Impact:** unresolved fixture oracle pointers in `requests` would reach run time rather than being refused at the artifact boundary — the exact failure this function exists to prevent.

**Fix/next step:** `(scenario.actions?.length ? scenario.actions : scenario.requests) ?? []`, or validate both lists.

### 9. Low — `jsonPointer` accepts non-conforming pointers
**File/section:** `packages/conformance/src/artifact-bundle.ts:271-286`.

**Issue:** no check that a non-empty pointer begins with `/`. Pointer `"foo"` → `slice(1).split("/")` → lookup of key `"oo"`. (The `~1`→`/` then `~0`→`~` order at `:276` is correct.)

**Impact:** a malformed oracle pointer resolves to the wrong member (or silently "does not resolve"), so a mis-typed pointer can bind an unintended expected value instead of being rejected.

**Fix/next step:** reject non-empty pointers not starting with `/`.

### 11. Low — unhandled rejection path in the dev server's request bookkeeping
**File/section:** `packages/server/src/development-runtime.ts:252-256` (`void task.finally(...)`).

**Issue:** `handle`'s catch-all (`:245-249`) covers the normal paths, but a throw *inside* that catch (e.g. a `writeHead` on an already-sent response, or an invalid header value while reporting an error) rejects `task`; the `.finally(...)` chain's rejection is `void`ed, so it surfaces as an unhandled rejection and terminates the process under Node's default.

**Trigger not proven:** I could not identify a concrete reachable double-response path in the supplied excerpt; reporting it because the process owns admitted work and the lifecycle observations (`development/README.md:76-93`) turn on exactly how this process dies.

**Fix/next step:** `void task.catch(() => {}).finally(...)`.

### 12. Low — per-process random Scope epoch doubles as the Authorization View
**File/section:** `packages/server/src/development-authority.ts:142`, `:152`, `:171-181`.

**Issue:** one `randomBytes(24)` value is used for both `scopeEpoch` and `authorizationView`, regenerated on every process start while the store is durable.

**Impact:** across the restart/SIGKILL observations the dev composition cannot exhibit any distinction between an Authorization-View change and a Scope-epoch change, and all outstanding cursors are invalidated by restart (consistent with in-memory retained state at `:155-170`). Any dev diagnostic touching epoch/view identity is therefore vacuous rather than negative. Whether the Read profile requires the two to be independent is not in the supplied spec excerpt.

**Fix/next step:** derive the epoch from durable store lineage/state and use distinct values for the two roles, or record the conflation as an explicit limit on the affected inventory rows.
