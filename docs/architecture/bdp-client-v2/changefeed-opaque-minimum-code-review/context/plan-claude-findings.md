## Findings

**1. HTTP: the required statement reorder is never stated (Medium — close before authoring)**
*Plan:* §"Exact production seam", item 1. *Source:* `packages/server/src/transaction-http.ts:470–481`.
The new predicate reads `media` and `effective`, but today `minimum` is computed **first** (470–472), `media` at 473, raw `fields` at 476–478, the repeated-SSE throw at 479–480, `effective` at 481. The plan prescribes "for selected paths choose `currentReadMinimumHeaders`; otherwise `transactionMinimumHeaders`" without saying the `minimum` computation must move below `effective`. *Impact:* an author following the text literally cannot choose the helper; whoever reorders silently also moves `minimum` **after** the repeated-Last-Event-ID throw, which the plan elsewhere pins ("preserve … repeated-SSE refusal/effective-after precedence"), so the reorder looks like a deviation under review. It is in fact behavior-preserving — both header helpers swallow their own errors (`transaction-consistency.ts:63–84`) and `hasMinimumControls` cannot throw (`transaction-http.ts:152–156`). *Correction:* add one sentence — "Compute media, raw reconnect fields, the repeated-SSE refusal and effective intent first, then eligibility, then minimum; this is a pure reorder because both header helpers catch internally."

**2. The implementation-progress record is left contradicted and is outside the five-file maximum (Medium — root scope decision)**
*Plan:* §"Exact production seam" first paragraph ("Maximum five existing files") and §"Outcome … exclusions". *Source:* `docs/design/transaction-implementation-progress.md:1273` ("Remaining unsupported minimum forms stay explicit development gaps", inside the changefeed slice at 1249–1275) and `:722–725` ("unknown opaque position spellings also retain that gap").
Those statements become partly false once fresh start-now opaque minima wait and return 503. Sibling slices in this same family did amend this file (alias minima at `:701–718`, fresh Snapshot creation at `:730–735`). The plan excludes documentation without naming the omission. *Impact:* either the five-file freeze is breached at authoring time, or the repo ships a record that contradicts the code. *Correction:* one explicit sentence choosing (a) add `docs/design/transaction-implementation-progress.md` as a sixth owned file with a short appended paragraph, or (b) name the record amendment as a separate successor so the contradiction is deliberate.

**3. "Install counting delegates" is not realizable as phrased; the owner is frozen (Medium — close before authoring)**
*Plan:* §"Exact source callbacks", A/B/C/X ("install counting delegates", "Callback-local spies/delegates"). *Source:* `transaction-store.ts:1551` (`return Object.freeze({…})`); existing helper `transaction-changefeed.test.ts:508–542` passes `f.owner` directly and the plan pins it byte-identical.
`vi.spyOn(owner, "readChanges")` and property assignment both fail on a frozen owner — which is exactly why the one existing instrumented callback spies on `DatabaseSync.prototype` instead (`transaction-changefeed.test.ts:414–425`). The established idiom is a spread delegate at construction: `createTransactionService({ ...owner, readReceipt: countedReceipt }, …)` (`transaction-service.test.ts:3544–3545`). *Impact:* a wasted authoring/execution cycle, and B's "actual owner close" plus the post-close raw probe depend on the wrapper forwarding `close()`; service construction also calls `owner.readConfiguration()` (`transaction-service.ts:111–116`) and `owner.close()` on shutdown (`:745`). *Correction:* state that new callbacks build the service over a callback-local spread delegate (`{ ...f.owner, readChanges, captureChangesStart }`), passed either through the unchanged helper via a fixture-shaped literal or an inline `createTransactionService`, and that the spread preserves `close`/`readConfiguration`.

**6. "Returns … Unproved" should be "throws" (Low)**
*Plan:* §3 "A direct selected owner call returns actual TransactionMinimumUnproved". *Source:* `transaction-consistency.ts:129` throws it; A correctly says "must throw". *Impact:* risks an author implementing a returned sentinel (which would bypass `waitForTransactionMinimum`'s catch at `:164–169`). *Correction:* change "returns" to "throws".

**7. B's "without capture" is imprecise (Low)**
*Plan:* B, "A valid post-close service call fails synchronously without capture". The lexical tuple snapshot still runs before `run()`/`check()` (`transaction-service.ts:477–481`, `140–141`); only the admission capture is skipped. *Correction:* "without admission capture".

**8. Optional: state that the selected opaque path can never succeed, and what that costs (Low, optional)**
`position()` of an unrecognized token is permanently undefined (`transaction-consistency.ts:26–31, 120–131`), so every attempt throws Unproved and the outcome is always 503 after the full budget. In the installed cohort there is no seam: budget defaults to 1000 ms with 5 ms sleeps (`:144, 176`) ≈ 200 real owner entries per opaque request, two such requests. That is the actual basis for the plan's 5 s installed request deadline. One sentence would make the margin explicit instead of implicit. (Precedent exists: `apps/bdptest/src/transactional-minimum-receiving-installed.test.ts:502`, `transactional-collection-minimum-installed.test.ts:1139`.)

**9. Optional: pre-empt the council question on caller-asserted leniency (Low, optional)**
Sibling slices expose leniency either via a dedicated method (`receiptAtMinimum`, `transaction-service.ts:609–632`, with `readReceipt` unconditionally lenient at `transaction-store.ts:959–971`) or via owner-side re-derivation (`readEvents` recomputes `initialMinimumSource`, `transaction-store.ts:1685–1693, 1704–1707`). This plan is the first where the owner trusts a caller flag. It is well justified — a start-now admission checkpoint is textually indistinguishable from a client `after=` continuation, and spec 5850–5851 excludes retained continuations from waiting — and the plan already disclaims a capability boundary. A one-line note that the owner *deliberately cannot* re-derive this (unlike `readEvents`) would close the obvious reviewer question.

## Verified accurate against source (not findings)

- **Waiter preflight and C's clock counts.** `waitForTransactionMinimum` validates policy → `started = now()` → deadline → loop-top abort check (`transaction-consistency.ts:144–161`). So budget 0 → 0 clock calls; already-aborted → 1; throwing/nonfinite clock → 1. C's "1,0,1,1" is exactly right, as is "zero readChanges and waits".
- **Anchor capture before preflight, fixed across retries.** `transaction-service.ts:481–487`: `run` → `check` → synchronous `start()` → `captureChangesStart()` → waiter. Capture is already outside the retry callback; the plan's "do not move capture into the retry callback" preserves, not changes, this.
- **Owner ordering.** `transaction-store.ts:1841–1856`: after-string check → tuple capture → `enter` → unsupported return before `readContext` → context/head → `checkpointPosition` → future refusal → missing-retained-row corruption → **then** minimum. The plan's sequence matches byte-for-byte in intent.
- **A/B schedules.** Budget 2 / clock 0 yields `wait(Math.min(5, 2-0)) = 2` ("records requested 2"), second attempt at clock 2 hits `current >= deadline` → catch-up-timeout with the pos-2 context. Abort is only observed at loop top, so "abort must precede release, and release must precede cleanup awaiting close" is necessary, not decorative. `close()` is memoized (`transaction-service.ts:732–733`), drains `active` via `allSettled` (`:737`) and closes the owner (`:745`) — so "memoized repeated close is not a new owner lifetime", synchronous post-close refusal (`:138`) and the raw closed-owner probe all hold.
- **503 never degrades to 304/406/412.** `applyReadHttpSemantics` only transforms 200-JSON or 204 (`read-http.ts:10–39`) and HEAD content-length is the serialized GET body (`:42–45`); the catch-up-timeout mapping with `retry-after: 1` is `transaction-http.ts:640–653, 112`. - **JSON ignores Last-Event-ID.** `transaction-http.ts:476–481` consults raw fields only when `media === "sse"`; spec 6043–6045 and 6185–6189 condition precedence on SSE. Correct, and correctly *not* copied from the Event path's header-absent fence (`:505–514`).

- **Spec citations.** 5819–5832 (lexical receiving; MUST NOT become 304/412/406/SSE; HEAD metadata), 5841–5851 (general remaining-read law; the narrower MUST really is scoped to "current Bead or Link Resource or properties view"; 5850–5851 excludes retained continuations), 6036–6053, 6149–6153 ("the head checkpoint the authority observed when it admitted the request"), 6185–6189, 6994–6995 all read as the plan describes.
