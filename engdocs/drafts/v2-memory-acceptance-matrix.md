# Memory V2 acceptance matrix — proposed scope

Donna and Trish's October 16 direction: V2 is a replacement with deliberate, reviewed regressions where needed. Previews are increments toward V2; no row below is automatically a Preview 3 gate. This is a planning interpretation of [Chris's Memory proposal](https://github.com/gastownhall/beads/issues/5877), not an amendment to that proposal or a conformance claim. The baseline is final Preview 2 `703bb13e91aa2cab2092443319139006d74242c8`; Janet's [source-only report card](https://github.com/donnabox/beads/pull/110) is the evidence inventory. Its grades do not constitute executed scenario tests. Narrow installed Preview 2 embedded/shared-server CLI observations cover only creation, basic links, counts, show and selected refusals. A **source-only** Preview 3 integration base is qualified in draft [PR113](https://github.com/donnabox/beads/pull/113) and the matching dedicated branch is local-only; the Memory V2 product acceptance suite remains pending. The public [implementation status issue #7656](https://github.com/gastownhall/beads/issues/7656) tracks each requirement and S1–S16 scenario through merge, release-quality coverage, protected CI and default-on activation gates.

## V2 decision boundary

The V2 objective is the **selected Memory workflows** below, alongside the existing Issue/Dependency model and an Activity model for work provenance. Minimum capabilities are `--type` selection, a fixed Memory/Link/Issue/Dependency/Activity catalog, the constraints those workflows require, retained revisions with exact pinned References, revision provenance on accepted mutations, and Activity provenance for recorded work. A fixed catalog may be compiled into the binary; it needs discoverable inventory/details and stable historical meaning across upgrades. V2 does not require user-defined/installable Types, `bd type` management, federation, a BDP client/server, cryptographic signing, or the Rust reboot. Attribution supplied by a writer must remain distinguishable from authenticated or verified identity.

BDP stays an independently general protocol effort under Trish. If a preview includes BDP functionality, it remains directly usable without an opt-in switch and experimental in contract maturity. Neither BDP publication nor a Go-backed bridge is V2 product support by itself. Hardening existing `bdpbd` versus advancing the Go BDP implementation is an unselected comparison, not a V2 gate or presumed cost ranking. The Rust service/client transition is separate.

## Requirements not silently closed by this subset

| Requirement / workflow | V2 treatment and necessary decision |
| --- | --- |
| R17's user-defined, non-workflow Link Types | **Intentional exception requiring proposal reconciliation.** A fixed built-in catalog plus a low-enforcement generic informational Link Type may support selected workflows and an off-ramp from ad hoc links. Its vocabulary/upgrade meaning and unknown historical Type handling still need a reviewed contract. Do not claim full R17 as written. |
| R18–R20 cross-Scope behavior | Local exact pins, local integrity, deletion and truthful unavailable/gone distinctions are required for selected workflows. Live federation/remote target resolution is deferred. Decide whether carrying an unresolved fully qualified Reference remains required for format stability. |
| R13/R16 project-wide feed and removed-version reasons; S16 | Polly's packet currently treats these as selected Preview 3 outcomes. The new V2 scope requires exact retained history and provenance for chosen workflows, but **does not yet decide** whether an ordered all-project feed, retention/erasure producer and S16 mirror workflow are V2 gates. If omitted, explicitly narrow the Memory proposal claim; do not relabel a per-Memory version list as the ordinary feed. |
| R24 legacy conversion; S11 | A safe export/import cycle may be the upgrade path. Shipping/preview data migration is already excluded from Preview 3. Whether V2 replacement needs a supported conversion/offramp before launch is a product decision; absent that, do not claim S11 or existing-data continuity. Never invent historical authorship. |
| R27/R27a connected interchange; S13 | Iris's graph-mode→graph-mode `link→link` path is a Preview 3 **or** 4 candidate. Full R27 needs connected Task/Memory/Link identity and meaning, atomic publication/refusal, and no key/similar-ID retargeting. `dependency→link` helps broader migration; `link→dependency` is out of scope. If excluded from V2, call S13/R27 deferred rather than passed. Independently enumerate bulk Memory exposure and keep `bd export` excluded by default with explicit body-carrying choice when supported. |
| R8/R21 no implicit body acquisition | P2 summary output alone does not meet the proposal's stronger storage-acquisition language. Decide and test the selected V2 retrieval boundary; avoid asserting R8/R21 from output shape only. |
| R25/R26/R29/R31 supported surfaces | Define the actual V2 CLI, Go and HTTP surfaces, enumerate deliberate breaks, and test identical canonical semantics on supported embedded/shared-server paths. BDP client/server can be excluded; do not describe an unsupported surface as conformant. |
| Fixed Type history semantics | Catalogue entries need stable identifiers/versions or another explicit way for old revisions and pins to retain their original meaning after a binary upgrade. A changed built-in definition must not silently reinterpret old affiliation. Trish/Melinda/Polly to settle storage/read/validation behavior. |

## Gate and next decisions

For each selected row, freeze the exact Type/operation/constraint/revision/provenance contract, expected CLI and structured output, and refusal behavior before claiming support. Exercise complete scenarios on one exact qualified source with installed Dolt 2.1.8 embedded and ordinary shared-server modes; include no-op, conflict, deletion, pin, historical-read and source-attribution assertions. Janet owns that product qualification and release ledger. Source inspection, BDP publication and a passing narrow CLI slice are not substitutes.

Donna's decisions needed before a V2 cutline: (1) whether the project-wide feed and actual retention/erasure removal are mandatory for the selected Memory workflows, (2) whether an existing-data offramp is required at V2 launch, (3) the fixed catalog's generic Link Type and historical-definition rule, (4) the exact Activity provenance workflow and owner, and (5) the supported CLI/Go/HTTP surface set and curated shipping-product exceptions. These are open; no preview allocation is implied by this matrix.
