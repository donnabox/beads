### HIGH — locked-metadata capture lands inside `configurationIdentity`, which is `.trim()`ed per read
**Location:** `transaction-store.ts:191-197,467`; `authority-read.ts:269,486-492`; plan:98-99 vs plan:75-76
`configuration` is the whole locked JSON text, and `readConfiguration.scopeConfiguration.configurationIdentity` is set to *that entire string*. `authority-read.ts:269` validates it with `value.trim().length === 0` on every read-entry capture (`:486-492`), and reopen does `JSON.parse` plus a full byte compare (`transaction-store.ts:436-442`).
**Impact:** Putting the base64 capture in the same metadata row makes `configurationIdentity` a multi-megabyte string — bounded only by `CONTRACT_ARTIFACT_CEILINGS.totalBytes` (16 MiB raw → ~22 MiB base64, `installed-contract-artifact.ts:19-34`) — allocating a full copy per read request. The plan's "No changes should be needed to AuthorityReadPlane" is false under its own storage choice.
**Action:** Require the capture in a *separate* metadata row, keep `configurationIdentity` a bounded digest, and add a done predicate naming an explicit TX-side byte bound (`stringifyJsonValue` imposes none by design — `json-values.ts:99`).

### HIGH — the branded object cannot cross the fixture seam that produces restart evidence
**Location:** `transaction-runtime.ts:22-34,228-239`; `transaction-runtime.test.ts:13,20-28`; `development-contracts.ts:60-63`; plan items 1 and 4, predicate 6
`TransactionRuntimeOptions` is `JSON.stringify`ed into a child process, and `types` is plain `TypeDescriptor[]`. Branding is a module-level `WeakSet`, so a compiled `DevelopmentContracts` survives neither JSON transport nor a second module instance — and that test loads `../dist/transaction-runtime.js` while unit tests load `src`.
**Impact:** "Accept only the existing branded DevelopmentContracts" (plan:57-59) is incompatible with threading the bridge through this fixture (plan:77-79) to prove predicate 6. Compiling in `src` and passing to `dist` throws `assertDevelopmentContracts` even in-process.
**Action:** State that the *runtime fixture* seam accepts a plain artifact bundle and compiles inside the runtime (child side), with the branded-only rule applying at `openTransactionStore`; pin one module instance for the compile.

### MEDIUM — scope-local Type IDs and compile-after-scope ordering are unstated

### MEDIUM — enabling validation activates a retained-diagnostic obligation with no step for it
**Location:** `docs/specs/bdp.md:2607-2614`; `transaction-batch.ts:58-63`; `transaction-store.ts:191-197`; `read-update-runtime-limits.ts:62-80` vs `development-authority.ts:205-206`
Spec: a still-replayable retained diagnostic list "constrains subsequent configuration: the authority must refuse an incompatible lower bound or retain a sufficient bound through lawful expiry." TX's bounds are the module constant `TRANSACTION_RUNTIME_LIMITS`, which is **not** in the locked configuration, and TX has no analogue of RU's `assertReadUpdateRuntimeCompatibility` / `visitRetainedOutcomes`.
**Impact:** Dormant today (TX can never emit `validation-failed`); this slice is exactly what wakes it. A build lowering `diagnosticBytes`/`diagnosticCount` would reopen a store holding oversized retained diagnostics without refusing.
**Action:** Add a step/predicate — fold the diagnostic/properties bounds into the locked configuration, or scan retained receipts after the installation check and before pending retraction.
*Already satisfied, worth recording as such:* joint feasibility **is** qualified — `transaction-batch.ts:64` calls `snapshotReadUpdateRuntimeLimits(TRANSACTION_RUNTIME_LIMITS)` at module load; 512 KiB ≥ the 283,906-byte first-diagnostic requirement, matching the 16384/1024 metadata allowances enforced at `development-contracts.ts:108-112`.

### MEDIUM — predicate 6 credits the new capture with a refusal the digest already delivers

### MEDIUM — "compiler limits/policy identity" has no parameter to be restored through
**Location:** plan:96; `development-contracts.ts:17-18,89-94,128-137`; `installed-contract-artifact.ts:42-46`
`compileDevelopmentContracts` accepts only `{descriptors, schemas, limits}`. `SCHEMA_GRAPH_CEILINGS` and `EVALUATOR_CEILINGS` are module constants, already folded into `identity`.
**Impact:** Recorded ceilings cannot be fed back into reconstruction — it always uses the running build's constants. Consequence (unstated): any ceilings change fails *every* persisted installation closed with no migration path.
**Action:** Say the recorded ceilings are a comparison witness only, and fold "ceilings change ⇒ fail-closed reseed" into the format-compatibility paragraph (plan:107-112).
