**Finding 1 — Low. `packages/conformance/matrices/read-update-reference-continuation-v1.json:2209` (`att-subject-noop`), and the guard set of `read-update.singleton.attribution` generally.**

Concrete issue: accepted plan A step 3 requires, after the full-envelope no-op, that "a retained current guard succeeds." No guard in the attribution row ever binds a revision that was retained *across* a no-op. The complete guard inventory for that row is `att-subject-stale` → `att-subject-after-properties-rev` (stale), `att-subject-noop` → `att-subject-after-metadata-rev` (minted by the immediately preceding effectful edit), `att-subject-context-noop` → `att-subject-absence-3-read-rev`, `att-unowned-context-noop` → `att-unowned-absence-3-read-rev`, `att-owned-noop` → `att-owned-properties-link-rev`. Each of the three no-ops (`att-subject-noop`, `att-unowned-context-noop`, `att-owned-noop`) is the *last* guarded action on its plane, so the token they retain is never re-submitted. The numeric row does carry this witness (`num-subject-current-noop`/`num-link-current-noop` guard with `num-*-initial-rev` after four raw no-ops retained it).

Impact: in row A, "mints no revision" is observed only from the mutation result and the independent GET record (`att-subject-after-noop` postimage, which does include `revision`). A realization that reports the prior revision in both the result and the afterstate read while treating a different token as current for guard purposes is not discriminated in A. The attribution catalog clause under council review ("mints no revision and records no new provenance and retains the existing version's entire envelope") is therefore observed one step weaker in A than the equivalent clause is in B.

Correction: add one guarded action per plane — or at minimum for the Task subject — whose `expectedRevision` binds the revision captured *after* the no-op (`att-subject-after-noop-rev` etc.) under a fresh Idempotency-Key, and assert it is admitted; the row has 6 actions of headroom under the authorized 75. Otherwise state explicitly in the coverage `reason` and in `report.md` §"Deliberately bounded conclusions" that A's retention evidence is afterstate-only and that the guard witness for retained revisions is carried by B, so council does not read A as having observed guard-level retention.

**Finding 2 — Low. `apps/bdptest/src/read-update-matrix.test.ts:456-466`.**

Concrete issue: the `refusal-success` control captures the record it will forge into the fake 200 response by positional client-action selection (`?.actions?.filter(action => action.family === "client")[retryClientIndex++]` then `clientAction?.id === "num-subject-restored-read"`). Unlike the `retryControl` branch 8 lines below, which guards positional selection with `expect(clientAction.input).toEqual(execution.input)` (line 473), this capture has no check that the positionally selected action is the one actually executed.

Impact: if the numeric row's client-action order changes, or a client action is skipped, `numericControlRecord` is silently taken from a different GET and the forged body carries the wrong resource — yet the test still passes, because `status`, `body-schema` and `complete-problem` fail for any non-Problem body regardless of which resource is embedded. The control's stated property, "refusal response replaced with a **plausible** success" (report.md line 18; plan §B controls), would then no longer hold while the assertion still reports green. The only failure mode that surfaces is the all-or-nothing `throw Error("missing independently observed prior Resource")` when nothing was captured at all.

Correction: apply the same `expect(clientAction.input).toEqual(execution.input)` guard before the capture, or assert `numericControlRecord` deep-equals the independently authored restored postimage (the literal `properties`/`metadata`/`actor-only` values pinned on `num-subject-restore`) before substituting it.

**Finding 3 — Low. `apps/bdptest/src/read-update-matrix.test.ts:3668`.**

Concrete issue: the accepted ≤16 sensitivity-control ceiling is enforced as `expect(attributionNumericControls.length + 3).toBeLessThanOrEqual(16)`. The `12` comes from the named table, but the `3` is a literal standing in for the raw-mode cases, which are declared as an anonymous inline array inside `it.each([...] as const)` at line 3524-3531 and are not counted from source.

Impact: adding a fourth raw control mode (the natural next step — the plan's follow-on round-trip-admission/nested-refusal slice "preserving these exact raw-byte techniques") raises the real control count to 16 and then 17 without the budget assertion noticing, silently breaching a ceiling root fixed in `read-update-action-budget-disposition.md` ("at most 16 controls"). The assertion that is supposed to bind that cap stops binding half of it.

Correction: hoist the raw-mode table to a named `const attributionNumericRawControls = [...] as const`, pass it to `it.each`, and assert `attributionNumericControls.length + attributionNumericRawControls.length` against 16.
