## Findings (all low)

**1. Low — `apps/bdptest/src/read-update-matrix.test.ts:2220`**
Issue: `harnessCategory` is the one projected field the new test never exercises — the fixture exchange (:2255-2260) has no `harnessError`, and because `JSON.stringify` drops `undefined`, the expectation at :2297-2302 passes whether that field works or not.
Impact: `harnessError` is reachable in this path (exact mode yields `exact-configuration` / `exact-observation`, runner.ts:1287, 1402) and is the error channel closest to credential-bearing material. A future typo like `harnessError?.message` would both break the diagnostic and leak a message, with no test failing.
Fix: add `harnessError: { category: "exact-observation", message: secret }` to the fixture exchange and `harnessCategory: "exact-observation"` to the expected exchange object.

**2. Low — `apps/bdptest/src/read-update-matrix.test.ts:2219`**
Issue: `writeState` is dropped while `transportError.category` is kept.
Impact: `RequestWriteState` (`packages/conformance/src/http-executor.ts:41`) is a three-value enum — `not-started` / `started-completion-unestablished` / `complete` — and for a *retained-retry* failure it is the decisive fact: whether the original request was fully written before the transport error, i.e. whether a replay should have been idempotent at all. Without it, a `transportCategory: "connection"` line can't distinguish an unsent request from an unacknowledged completed write.
Fix: in the exchange projection add `writeState: exchange.transportError?.writeState ?? exchange.harnessError?.writeState`. Bounded enum, no credential exposure.

**3. Low — `apps/bdptest/src/read-update-matrix.test.ts:2228-2233`**
Issue: when `row` or `last` is absent the diagnostic collapses to four keys and says nothing about what *was* present — exactly the case the second expectation at :2316-2331 pins. Relatedly, `scenarioCleanupFailed: row?.cleanupError !== undefined` yields `false` for a missing row, reading as "cleanup succeeded".
Impact: for the likeliest real CI failure here — `counterfactualApplications` is 0 because the client stopped early — the operator can't tell "zero client exchanges" from "observations present but route projection empty", nor which scenario ids the runner actually produced.
Fix: add two credential-free fields: `observedClientExchanges: report.observations.length` and `observedScenarios: report.result.scenarios.map((s) => s.id)` (catalog constants). Optionally make the cleanup flag honest with `scenarioCleanupFailed: row === undefined ? undefined : row.cleanupError !== undefined`.

**4. Low (latent) — `apps/bdptest/src/read-update-matrix.test.ts:2207-2209, 2229`**
Issue: `report.observations.at(-1)` is an `as` cast, so `last.observation.route.method` is unchecked by the compiler, and the helper is called eagerly at :2351 before any oracle assertion.
Impact: accurate today, but if the exact client's observe payload ever drops `route`, the diagnostic throws a `TypeError` *before* the three oracles run — turning a real conformance failure into an unrelated stack trace in CI. That is the one way this observability-only change could obscure the failure it exists to explain.
Fix: either optional-chain the deep reads (`last?.observation?.route?.method`), or make the helper fail-soft as a whole — wrap the body in `try { ... } catch (error) { return JSON.stringify({ diagnosticUnavailable: error instanceof Error ? error.name : "unknown" }) }` (name only, never `message`). Dropping the cast in favour of the client's own return type would also restore compile-time coverage.
