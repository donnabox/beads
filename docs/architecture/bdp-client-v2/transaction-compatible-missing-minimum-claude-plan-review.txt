## Verdict

**Yes — returning the existing 404 for a compatible, already-satisfied source context is correct**, and the mechanism the plan picks (one `checkSourceCondition` edit, no HTTP/service/store change) is the right one. I verified the failure-class discrimination is exhaustive for the route subset, the context propagation is genuinely same-entry, the conditional/HEAD claims hold against the real helper, and the ledger arithmetic (pos-1/pos-2, 9 URLs, delete ordering) is sound. ### 1. MEDIUM — `sourceCondition` is forwarded by the ordinary `readFor` facet, so the new 404 branch is reachable outside `minimumFor`'s subset
**File/section:** `packages/server/src/transaction-read.ts:96-99` · plan §Source trace item 3, §Precise implementation boundary

The callback signature is `(condition, observation, refusal)` — it carries **no request**, so the new branch cannot discriminate route. Meanwhile `composed.readFor(...).perform/resolveAlias` forward caller `options` verbatim, and `authority-read.ts:1056` reads `sourceCondition` out of them; `transaction-service.ts:274-275` forwards too. Today every out-of-subset missing result (alias, Type, `bead-links` anchor, continuation) throws the Gap — that *is* the "alias minimum is wholly refused" behaviour the rulings audit row 16 and plan line 22 rely on.

**Impact:** after the repair, an in-process caller passing a satisfied tuple through `readFor` gets `404 + context` for a missing alias/Type/incident anchor. Not reachable over HTTP today (`grep` confirms line 121 is the *only* site in the repo that sets `sourceCondition`), so no wire regression — but it directly contradicts "The proposed repair does **not** widen this route predicate" and "Alias 307/alias absence … remain unchanged."

**Bounded correction:** in the same owned file, have `composed.readFor` forward only `signal` and drop `sourceCondition`, so the source-condition callback stays reachable solely through `minimumFor`. Strictly a narrowing; no new abstraction, option, or interface; nothing currently depends on the forwarding. Add one read-test asserting a `readFor`-supplied `sourceCondition` is not honoured.

### 3. MEDIUM — "No remaining normative ambiguity" rests on a negative inference; the affirmative mandate is omitted
**File/section:** plan §Settled contract, lines 18-22 · `docs/specs/bdp.md:5781-5786`, `:1445-1448`, `:5793-5798`

`:5781-5786` enumerates exactly three authority outcomes for a complete tuple — "a representation at that position or later", wait/route, or "the normative foreign-view, cursor-expired, or catch-up-timeout problem". A nondisclosing 404 is literally none of the three. So "there is no remaining minimum failure to arbitrate" is an *interpretation* (reading "eligible observation" to cover a problem representation of the observed prefix), and declaring "no remaining normative ambiguity" overstates it.

**Impact:** the plan simultaneously under-uses its two strongest clauses. `:1445-1448` **mandates** the uniform 404 for a deleted/unknown/non-visible identity, and `:5793-5798` says **every** Transactional Scope-bounded read reports epoch/view/position — which today's bodyless, header-free 500 does not. The rulings audit states this outright ("ordinary 404 remains dictated"); the plan paraphrases it only as permission. The strongest available argument — that the status quo is *non-conformant* and this is defect repair — is never made.

**Bounded correction:** restate the basis affirmatively (current 500 violates `:1445-1448` and `:5793-5798`), and say explicitly that `:5781-5786`'s enumeration is read to include a problem representation of the satisfied prefix — naming that as the one interpretive step taken.

## Verified correct (no change needed)

- **Failure-class discrimination is exhaustive and no broader.** Within `minimumFor`'s predicate the only refusal codes reaching the callback are `invalid-parameter`/`limit-exceeded` (`authority-read.ts:752-761` via `readControlProblem`, and `read-request.ts:954-965` can produce only those two) and `resource-not-found` (`authority-read.ts:797,801`). Request-validation `invalid-parameter` is a `preContext` refusal and never reaches the callback (`:983`, `:1084-1091`). `checkTransactionMinimum` emits exactly `cursor-expired`/`foreign-view`/`behind` (`transaction-consistency.ts:69-77`), so the three-reason allowlist is tight and excluding `catch-up-timeout` is right — only `waitForTransactionMinimum:117` manufactures it, above the callback. The plain `Error("invalid owner minimum position")` at `:76` is not a `TransactionMinimumFailure` and propagates.
- **No wait introduced.** `waitForTransactionMinimum` retries only `TransactionMinimumFailure` with `reason === "behind"` (`:111`); the Gap is a distinct class, so missing+behind still fails immediately.
- **Same-entry context is real, not reconstructed.** `observed()` (`authority-read.ts:509-515`) retains the observation on the materialized Problem; the callback runs inside the single owner entry with that same `context.observation` (`:981-992`) and is skipped for a pre-context refusal (`:983`); `transactionReadContexts` re-validates epoch/view against the observation rather than trusting the owner (`transaction-read.ts:154-165`).
- **No HTTP production change needed.** `readRoute.perform` already attaches `transactionReadContexts(result.observation).current` whenever `"observation" in result`, true for an observed refusal (`transaction-http.ts:220-234`); `problem()` yields `application/problem+json`, `cache-control: private, no-store`, no ETag (`read-http-routing.ts:44-52`, `transaction-http.ts:89-106`).
- **Conditionals/HEAD hold.** `applyReadHttpSemantics` transforms only `status===200` with `content-type: application/json`, or 204 (`read-http.ts:10-39`) — a 404 is never turned into 304/412 under `If-None-Match: *` or a mismatching `If-Match`. The HEAD branch (`:42-46`) drops the body and sets content-length from the serialized problem; precedent for a nonzero-content-length HEAD problem exists at `http.test:1256-1259` (503) and installed`:504`.
- **Deletion oracle sound.** `deleteResource` hard-deletes (`transaction-store.ts:1199-1203`), so a deleted target hits `graph.point() === undefined` → `notFound()`. Retained history is off in the installed fixture (`expect(child.ready.history).toBe(false)`, installed`:213`), correctly excluding the optional 410.
- **Ledger arithmetic checks out.** One transaction = exactly one position increment regardless of operation count (`transaction-store.ts:1123-1130`, `:1264-1270`), and for an effective batch `requiredPosition === effectPosition === position` (`:1275-1276`) — so literal pos-1/pos-2 is a sound independent expectation. Delete order l-then-a is *required*: `incident-links-exist` → 409 otherwise (`resource-evaluator.ts:1028-1029`), and intra-transaction `tx.incidentLinks` sees the earlier delete (effects applied inside `SAVEPOINT effects`, `:1205`). 9 distinct URLs and 2 Beads + 1 Link max live both hold. 32-op cap confirmed (`transaction-batch.ts:63`). Bounds confirmed unchanged: 5000 ms/request, 32768 body, 16384/65536 exact caps (installed`:259-284`), 80-response ceiling (`:317`), 90 s/120 s (`:158`, `:594`), 10 s launcher deadline (`scripts/transaction-installed-observation.mjs:30-31`). Per-scenario `observations` and `snapshot_${key++}` are `start()`-closure-scoped, so the two scenarios cannot splice counts or reuse keys.
- **Five-file ceiling holds for existing fallout.** Repo-wide, `TransactionMinimumVisibilityGap`/`minimum-position-visibility` appear only in `transaction-read.ts`, `transaction-http.ts`, and **one** test assertion (`transaction-http.test.ts:1227`) — inside the owned set. Other minimum-bearing HTTP tests target present resources or receipt pages. `docs/specs/bdp.md` is byte-identical at aebf and b20, so the normative citations are pin-safe. C3's HTTP/service deltas (operations constant moved to `transaction-discovery.ts`; scope-mismatch guard) leave the readRoute, catch chain and gap mapping untouched.
- **The seams the oracles depend on exist:** owner-entry interception with reentrancy assertions and *scoped* SQL counters (`transaction-read.test.ts:560-594`, including the present-target `{reason:"behind"}` expectation at `:588`), and the injectable `minimumReads.wait` counter (`http.test:1240-1249`).
- **Scope-priority question resolved favourably.** The rulings audit's §"Next safe serving implementation" prefers *fresh Snapshot creation minimums* over this slice — but that work already landed as the plan's own parent (`aebf656`, PR #105 `vickie-tx-snapshot-minimum`), so this is the legitimate successor. Worth one disclosing sentence in the plan, since a reviewer reading the audit alone would flag it.
