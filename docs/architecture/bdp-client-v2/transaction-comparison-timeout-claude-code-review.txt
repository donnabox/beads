### 1. Medium — `closed`-shortcut guard terms have no committed coverage, and a documented scoping claim rests on them

**`packages/server/src/transaction-store.ts:1731-1732`**

```ts
if (closed && !ownerFailure && !maintenanceFailure)
  return Object.freeze({ kind: "owner-stopped" });
```

**Issue.** The two negation terms are what keep the new operation from swallowing a fault: with `ownerFailure` or `maintenanceFailure` set, control must fall through to `enter()` so the fault throws. No committed test exercises either term. The three fault/stop tests cover disjoint states — `transaction-store.test.ts:3267` is closed *without* a failure, `:3289` fences with `closed === false` (`fence()` only sets `ownerFailure` and clears the timer), and `:3315` never closes.

**Impact.** Simplifying the guard to `if (closed)` compiles, passes lint, and passes all eighteen selected cases, while converting a fenced or maintenance-failed owner into a benign `owner-stopped` → bare 503. That is precisely the masking the plan forbids adding (§46: *"no broad catch converts them to an owner-stopped outcome"*) and it would silently falsify the progress note at `docs/design/transaction-implementation-progress.md:1782-1784`, which scopes the masking to *"before final observation"* — i.e. asserts the fault is **not** masked inside this operation. Severity is held at Medium rather than High because the production comparison loop reads `comparisonEpoch()` first, which returns `undefined` for any closed owner and short-circuits to `comparison-owner-stopped` before `observeComparisonDeadline` is reached; the guard is defense-in-depth for direct store callers.

**Fix** (both in-footprint, using facilities already in the file):
- Extend `:3289` after the fence is confirmed: `f.store.close(); expect(() => f.store.observeComparisonDeadline(f.store.scopeEpoch)).toThrow(failure as Error);` — `close()` is reachable post-fence (`busy` is false, `db` is still open).
- Add a maintenance case modelled on `transaction-store.test.ts:889-907` (`vi.useFakeTimers()`, `maintenanceIntervalMs: 25`, `fault("before-maintenance-commit")`, `advanceTimersByTime(25)`), then assert `observeComparisonDeadline` throws `"maintenance failed"` rather than returning `owner-stopped`. This also turns the doc's scoping sentence into a tested claim.

**Fix.** Optional. If coverage is wanted without a new seam, the submission-level double at `transaction-submission.test.ts:1070-1078` can be extended with an `observeComparisonDeadline` stub returning `{ kind: "owner-stopped" }` at a reached deadline, asserting the `comparison-refusal`/`owner-stopped` shape. The HTTP branch would need a stub `service`, which has no precedent in `transaction-http.test.ts` and is not worth introducing for this.

## Known accepted limitations (not defects)

- **Epoch-stop and closed-owner 503s carry no context headers.** A deliberate disposition (plan §34) — a mismatched persisted epoch cannot yield a coherent tuple from owner-lifetime constants. It is a narrowing of spec `bdp.md:5768-5774` for a defensive path.
- **The maintenance-failure closed shortcut still masks that fault** at `transaction-store.ts:1724`, before `observeComparisonDeadline` is ever reached. Correctly scoped in the doc and correctly *not* claimed as repaired. See finding 1 for the untested half of that scoping.
- **Default installed timeout sensitivity is unobserved.** Named as such in the doc. I did not infer any result from the pending installed direct-14/1 and sequence-13/1 regressions, and treated the Event 0→1→5 finite-page substitution as the explicit substitution it is, not as change-group pagination proof.
- **`atomic()` adds a new fencing surface on the timeout path** (a `BEGIN IMMEDIATE` failure fences the owner, where a pre-change timeout could not). Plan-directed (§33), identical in kind to every existing `atomic` read, and benign under single-connection exclusive ownership. Noted, not flagged.
