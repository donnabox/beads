## Findings

**1. Low — test coverage, `packages/server/src/transaction-service.test.ts:1766`.** No test pins that the captured options reach the *attempt*; only that live caller options are not re-read. A mutant passing `undefined` as the per-attempt options while still using `captured?.signal` for the wait would pass every new test: invalid shapes still reject at capture, pre-aborted signals still abort in the wait loop, and the replacement comparator still succeeds. **Impact:** the attempt-level signal is load-bearing — `waitForTransactionMinimum` checks only the overridable `signal?.aborted` (`transaction-consistency.ts:107`), whereas the authority additionally samples the intrinsic getter (`authority-read.ts:934-939,1068-1070`) and the post-work state (1106–1107). Losing it would silently drop native-abort precedence. **Fix:** in the success branch, use a real `AbortSignal` carrying an own shadowing `aborted` getter that returns `false` while the signal is natively aborted, and require `ScopeServerOperationAbortedError`; or abort the original from inside the wrapped `withRead` on the second entry. Both are within the authorized test file and need no new production seam.

**2. Low — latent, `packages/server/src/transaction-read.ts:231` (and symmetrically 246).** The bare `catch {}` fallback forwards raw options to the authority **without `sourceCondition`**, so plan §22's invariant is enforced only by two independently maintained copies of the descriptor logic plus an enumerated test list. **Impact:** no current failure — the predicates match exactly — but any future loosening of `ownData` or tightening of `ordinaryDeliveryOptions` would turn a minimum read into a silent unconditioned read that returns data with no consistency check, with no error anywhere. **Fix:** make the fallback self-enforcing by treating a *fulfilled* fallback attempt as an integrity error (every capture-rejected shape makes the authority reject, never fulfil). Note the frozen alias branch must stay behaviorally intact under plan §37, so the symmetric change belongs in a follow-on rather than this slice.

**3. Low — latent/unreachable, `packages/server/src/transaction-read.ts:189-212`.** The ordinary `readFor` branches retain the wide-`try` shape the new `perform` corrects: `facet.perform(...)` sits inside the `try`, so a synchronous throw from it would re-invoke it from the `catch`. **Impact:** currently unreachable — `deliver` routes every fault through its observed promise and never throws synchronously — so this is a structural asymmetry, not a live double-entry. **Fix:** none in this slice; `readFor` is outside the authorized change surface. Worth narrowing the `try` to the capture call in a follow-on for consistency with 228–235.

**4. Low — maintainability, `packages/server/src/transaction-read.test.ts:1956-1983`.** The new describe re-declares `principal`, `prepared()` and a byte-identical `serviceFor()` already present in the alias describe (1580–1603), including the duplicated 32-item page/`maxPageItems` coupling to the owner's `receiptMaximumItems`. **Impact:** the two copies must be changed together; if the owner receipt maximum moves, one copy drifts and `createTransactionService` throws "receipt page maximum differs from installed owner" in only one block. **Fix:** hoist the shared `prepared`/`serviceFor`/`principal` helpers to module scope alongside the existing `fixture()`.

Also noted, not a finding: in `service` mode the standalone `plane` and its counter seam at `transaction-read.test.ts:2026-2027` are dead setup (a second authority plane over the same owner, never used), which could mislead a reader about which plane the `entries`/`nestedCall` seams observe. It is harmless — the unused plane retains no cursors, so its post-close `releaseAll()` touches no SQLite.
