## Underlying semantics verified

- **Iterative serializer equivalence.** I hand-traced the LIFO ordering for arrays, objects, nesting, and empties: output is byte-identical to the retired recursive version. Number lexemes come from `JsonNumberLiteral.literal`, keys from `Object.entries` (unchanged, so no reordering), strings from `JSON.stringify` — and the `{value}` boxing correctly disambiguates separator strings from JSON string payloads (a bare `""` payload still serializes as `""`, not as a separator). `transaction-set.test.ts:1024-1030` pins all of it exactly: `1e+30`, `9007199254740993`, `-0`, an escaped quote, and `z` before `a` (insertion, not sorted). The implementation mirrors the already-proven `stringifyJsonValue` in `packages/protocol/src/json-values.ts:101-140`.
- **Deep inputs cannot reach a recursive frame.** With depth now checked last, 20 000-level bodies traverse `decodeJsonDocument` (iterative, `json-admission.ts:98-193`), `mapLosslessJson` (iterative incl. freeze, `:231-291`), the new serializer, `parseReadUpdateShape` (iterative, `read-update-values.ts:160-181`), and `snapshotJsonValue` (frame-based, `json-values.ts:41-91`). I checked Ajv's exposure directly: the bundle's 158 `$defs` contain **no** reference cycle, and `properties` is `{type:"object",additionalProperties:true}` while `propertyChange.items[].value` is `true` — so validator recursion is bounded by schema depth, never by data depth. No path can turn a deep body into an unlabeled 500.
- **Depth coverage is complete.** All four prepare entries assert it: batch/`prepareTransactionSetCore` → `:169`; set singleton → the wrapper at `:169`; non-set singleton → `:208`; sequence → `:238`.
