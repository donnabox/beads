## Recommended relationship between commands

`bd query` should expose the general query operation. Commands such as list, search, children, and Link listing should translate their arguments and convenience defaults into the same structured query model and invoke a shared library/provider operation. They should not shell out to another `bd` process, mutate another command's flags, or have to print and reparse query text. A parser and a flag-based wrapper should be able to construct equivalent requests.

Wrappers can supply named selections, projections, ordering, bounds and presentation. Those choices must be visible enough to explain differences: search currently includes closed Issues while ordinary list has exclusions; children deliberately includes closed children. One common operation does not require identical wrapper defaults or preserve legacy field-dependent equality in the pure model.

Several commands combine queries with domain analysis, external data, or mutations. They should share the query foundation for their reads. The extra operation still needs its own contract: an ordinary query must not claim work, run an AI assessment, consult Git without disclosure, or change records as an incidental read.

## Existing convergence worth building on

The product is not starting from independent command implementations everywhere:

- `bd children` already delegates to a non-emitting list core with explicit parent/all-status defaults in the native path.
- `bd search` already lowers through a shared `ListRequest.Query` and reader role.
- `bd gate list` already constructs a query through `issueops.ListGates`.
- Current list/query providers share filter, predicate and page helpers, while readiness, graph walks, counts and other views still have distinct typed roles. Reuse those contracts and preserve contributor work; don't equate “one operation” with one giant function or one backend scan.

Evidence: [children](../../cmd/bd/children.go), [search request](../../issueops/search.go), [gate query](../../issueops/gates.go), [query provider](../../internal/workapi/storequerier/querier.go), [list provider](../../internal/workapi/storereader/reader.go), [tree provider](../../issueops/treewalker.go), [graph reader](../../graphops/reader.go).

## Observable differences to keep explicit

- **Different default sets:** search and children include closed Issues; ordinary list and several named views exclude selected states or kinds. Shared semantics should expose those wrapper defaults, not accidentally make all commands return the same set.
- **Walk filters versus display filters:** the current tree role preserves the ancestor chain of matching descendants after walking. Its depth counts the root as level one. A generic traversal must specify this instead of silently interpreting every filter as a traversal prune.
- **Different kinds of limits:** the current tree request documents that a depth cutoff is not marked in its answer; cycle reporting caps text display while retaining the complete JSON report; current graph views may read a full snapshot before testing/refusing a row cap. These are coverage and compatibility inputs, not behaviors to import uncritically into the new truthful-completeness contract.
- **Legacy inferred structure:** native list trees have a dotted-ID hierarchy fallback. It is not an actual stored Link and must not become an implicit edge in the pure graph model.
- **Text and identity affordances:** search's SQL-LIKE wildcards and ID-like special cases, query's field-dependent equality, and partial-ID/Memory-key resolution need explicit facade/compatibility treatment. They are not automatically primitive string semantics.
- **Unsupported is not empty:** missing version-history support, inaccessible neighbors and unavailable graph capabilities must not masquerade as no matches, no blockers, or full conformance.

These findings come from [tree request semantics](../../issueops/treewalker.go), [cycle reporting](../../cmd/bd/dep_cycles.go), [preview graph reads](../../cmd/bd/graph_preview_dependency_views.go), [list hierarchy](../../cmd/bd/list_tree.go), [search](../../cmd/bd/search.go), and [version outcomes](../../cmd/bd/versions.go). They are source observations; no new installed execution was run.

## Requirements to carry into language review

1. One explicit candidate population and identifier-resolution boundary; actual declared Type versus family membership; named wrapper defaults that can be explained.
2. Typed value/existence/array/text predicates, consistent equality and explicit substring semantics; legacy matching is P3-CLI-005, outside pure semantics. Contains is a literal substring predicate, case-sensitive by default; an explicit case-insensitive option serves search, which selects that option by default. Regex matching is deferred. Option spelling, Unicode rules and non-string/missing-value details are still open.
3. Directed Link/neighbor correlation and reference identity versus exact-revision tests; witnesses retain edge identity, concrete Type, direction, ownership and parallel claims.
4. Bounded walks and graph projections, with the distinction between selecting roots, expanding the graph and filtering presentation made explicit. Tree layout cannot change membership or hide necessary intermediates without disclosure.
5. Projection, counts, grouped counts and distinct values; define aggregation inputs, overlapping groups, missing/empty results and whether pagination applies before or after each operation.
6. Ordering before pagination, aggregate/witness limits, body acquisition, authorization and consistent read context; completion means the requested selected question was answered, not that every connected fact is known.
7. Domain views such as ready/blocked/completion use generic primitives plus explicit application rules. Exact/current records, history/events and external analyses have declared capability boundaries.
8. Wrapper equivalence cases: equivalent normalized requests produce the same members, edges and aggregates under the same read context; rendering is Cleo's concern. Different documented wrapper defaults remain intentional differences.

Suggested first coverage examples are: list versus search with an explicit matching predicate; children including closed children; ready versus blocked on the same dependency graph; an incoming/outgoing Link selection with parallel exact-revision claims; a graph with shared children and a cycle; count/group-by before page slicing; distinct label values; current versus exact historical read; and an ephemeral evaluation graph preserving a collective group through Link/target projection. These are proposed acceptance cases, not tests that have been run.

## Expressibility and equivalence acceptance

Donna requires all inventoried read surfaces to be expressible as wrappers over the generic query operation, modulo explicit exceptions. Maintain a disposition per surface: an equivalent query/request plus wrapper defaults, an unresolved language gap, or a named exception with a reason and the query portion it can reuse. The analysis/external/mutation boundaries identified above are candidate exception boundaries to confirm; the scan is not blanket approval for skipping difficult views.

For the common corpus, hold population, authorization and read context fixed, then compare wrapper and generic-query execution on:

- Resource identities and exact revisions; edge identities/Types/directions, parallel edges, subjects and witnesses.
- Property values, projections, counts/group keys, ordering, pagination and empty/missing outcomes.
- Bounds, truncated walks or explanations, consistency/completeness disclosures, unsupported capabilities and errors.
- No incidental mutation or hidden content acquisition. Mutating compound commands separately prove that their selection and guarded write remain atomic where required.

Cover closed versus default-filtered populations; a shared descendant and a cycle; literal `%`, `_`, `*` text; sensitive versus insensitive case matching; a nonmatching intermediate node on a path to a match; incoming/outgoing exact-revision claims; an aggregate larger than its display page; inaccessible/unretained data; and a collective ephemeral assessment graph. Read-only domain views need semantic equality, not merely matching output text. JSON and human rendering checks are additional to request/result equivalence.

Every surface remains unproven until its concrete mapping or explicit exception is reviewed and its relevant acceptance evidence exists. This is design/implementation acceptance planning, not a report of executed tests or a release allocation.
