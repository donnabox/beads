## T2b plan review — `bdp-integration-logs/transaction-http/plan.md`

Scope: plan text only, against frozen T2a `bddc448` and `docs/specs/bdp.md` (6969 lines). I did not review the in-progress `transaction-http.ts` / `transaction-runtime.ts` code in the T2b worktree; where I cite those worktree files it is only to confirm that a helper the plan names exists and is prior reviewed work.

**Spec citations in the plan check out.** `4485ff` → the ordered pre-admission list at `bdp.md:4490-4520`; `4600ff` → the mutation-surface table rows at `bdp.md:4602-4605`; `4618ff` → `bdp.md:4618-4623`; `5758ff` → `Transactional HTTP consistency` / `Transactional conditional reads` at `bdp.md:5766-5804`. The precedence restatement in plan §"Required wire matrix" (conflict before negotiation; duplicate negotiates before capacity; unknown key checks count before negotiation) matches both the spec and T2a's actual behavior. The expiry-ordering call (minimum-position check precedes cursor expiry, per `bdp.md:4618-4621`) is correct and is the kind of thing that is usually gotten backwards.

---

### HIGH

**1. Loopback origin vs. the scope baked into the store file — done-when 1 and 5 are not jointly satisfiable as written.**

- *Evidence:* `transaction-store.ts:153-158` embeds `scope` in the persisted `configuration` string; `:394-399` refuses reopen unless that string matches **byte-exactly**. Receipt identities are minted as `${scope}receipts/${randomUUID()}` (`transaction-store.ts:654`), and `createReadHttpRoute` 404s anything whose `url.origin !== scopeUrl.origin` (`read-http-routing.ts:28`). P1a's existing pattern binds first and *derives* the scope from the ephemeral port (`development-runtime.ts:272-281`: `scope = http://127.0.0.1:${address.port}/`). Plan line 8 says only "explicit owner provisioning"; line 28 requires "reopens exact retained key/receipt state"; line 32 requires process restart tests.
- *Failure scenario:* runtime copies the P1a bind-then-derive pattern with port 0. First start provisions with `scope=http://127.0.0.1:51234/`. Restart binds 51889 → `configuration` mismatch → store open refused before recovery, so done-when 1/5 fail. If instead the scope is pinned to a non-loopback canonical URL (e.g. `https://beads.example/acme/`), then `read-http-routing.ts:28` 404s every request to the loopback origin, and the receipt body's `id` and the `202` `Location` point at an authority that is not serving them — and "unchanged original body" (done-when 3) forbids rewriting them.
- *Fix:* add an explicit rule: the runtime takes a **fixed** listen port and derives the canonical scope from it *before* opening the owner, provisioning and restart use the same port, and a bind conflict on restart fails loudly rather than reprovisioning. State that no URL in a retained receipt is ever rewritten at projection time, and that the restart test asserts the receipt `id` returned after reopen is byte-identical to the one returned before.

**2. No admissible status exists for the plan's "unsupported development category", and the plan forbids the only one it could reach for.**

- *Evidence:* plan line 24: "Set operations and sequence Resource-alias operands remain unsupported before effects. Raw unsupported development categories must not be mislabeled protocol malformed syntax." But `updateWhere`/`deleteWhere` are members of the closed `batchOperation` union (`bdp.md:4461-4466`), so a batch body carrying one is a *valid* `batchRequest`. The POST row at `bdp.md:4600` is exhaustive: `200`, `202`, direct `400/401/403/409/413/415/429/503`, plus only the bodyless `406` and bodyless `500`. `advertisedLimits` has no JSON-depth group (`bdp.md:1058-1068`), so the 32-level depth refusal has no `limit` name for a `413 limit-exceeded`. T2a already surfaces this as a *statusless* result kind: `{ kind: "development-limit", message }` (`transaction-submission.ts:34, 72-73`) — every other kind carries a status, this one deliberately does not.
- *Failure scenario:* `POST batch` with `{"operations":[{"operation":"updateWhere",…}]}` and a valid `Idempotency-Key`. Not malformed (plan forbids 400), not a limit (no advertised limit), not transient (not 503), not a media problem. The implementer picks something — most likely `400` in contradiction of the plan's own rule, or `501`, which is outside the exhaustive row.
- *Fix:* decide it in the plan. Recommended: do not route the two set targets at all (so `POST .../update-where` is an ordinary `404 resource-not-found` for an unimplemented target), and for the irreducible case — a schema-valid `batch` containing `updateWhere`/`deleteWhere`, and the depth bound — emit the **bodyless `500`** and record it in the progress note as a knowing development-gap response, not a protocol ruling. Add a done-when assertion that no such request binds a key or creates a receipt.

**3. The three Transactional response fields are required on receipts but deferred on Read routes — including on the `304`/`412` the plan itself tests.**

- *Evidence:* plan line 18 requires receipts to carry "current serving epoch/view/position" (correct per `bdp.md:4572-4576`). Plan line 20 defers to T3 the "current epoch/view and original retained-page context ordering … and 304/412 current context". Meanwhile done-when 3 (plan line 30) requires receipt `304`/`412` tests *in this slice*, and `bdp.md:5802-5804` is unconditional: "Required current Scope context remains required on 304 and 412 responses." `bdp.md:5781-5786` ("Every Transactional Scope-bounded read reports the Scope epoch, Authorization View token, and position") covers Resource reads too. T2a already captures exactly this and separates the two cases: `transactionReadContexts(observation) → { current, snapshot? }` (`transaction-read.ts:77-79`).
- *Failure scenario:* a receipt GET with `If-None-Match: *` returns a bodyless `304` carrying `Cache-Control: private, no-store` but no `BDP-Scope-Epoch` / `BDP-Authorization-View` / `BDP-Scope-Position` — tested and recorded as passing. Separately, a canonical Resource GET returns `200` with no Scope context at all, leaving T2a's context plumbing unexercised by the first slice that could exercise it.
- *Fix:* split the deferral. In T2b: emit `current` context on every Read and receipt `200`, **and** on `304`/`412`. Defer to T3 only (a) the continuation current-vs-`snapshotSourceContext` choice and (b) positive barrier/wait outcomes. If instead Read-route context really is deferred wholesale, say so in one sentence and justify why a receipt-only context surface is not a half-built wire surface — right now the plan reads as if both are covered.

### MEDIUM

**4. "Fail closed" never names a status, and the candidate set is constrained.**

- *Evidence:* plan line 20: "any supplied minimum-context controls fail closed as source-private unavailable behavior". The receipt-URL row (`bdp.md:4602`) is exhaustive — `200/401/404/409/410/429/503` — and `bdp.md:4620-4622` names `409 foreign-view`, `410 cursor-expired`, `503 catch-up-timeout` as *the* consistency failures.
- *Failure scenario:* implementer picks `400 malformed-request` (plausible: an unsupported request field) or `501`. Both are outside the exhaustive row, so a refusal intended as "safe" becomes a new non-conformance in a row the plan otherwise honors.
- *Fix:* pin `503` + `Retry-After` with a non-`catch-up-timeout` code, or `503 catch-up-timeout` labelled as borrowed-not-qualified. Also pin **which fields** trigger it: `BDP-Minimum-Scope-Position` only, or also a bare `BDP-Scope-Epoch`/`BDP-Authorization-View` pair. Per `bdp.md:5776-5779` epoch+view are only meaningful *accompanying* a minimum position, so failing closed on them alone over-refuses. State explicitly that even a trivially-satisfied minimum (`pos-0`, or the current head) is refused, so T3 does not inherit refusal as the expected behavior in tests.

**5. `applyReadHttpSemantics` is method-agnostic; reusing it on POST receipt responses can suppress the receipt.**

- *Evidence:* `read-http.ts:10-48` keys only on `status === 200 && content-type === application/json`; `conditionalReadStatus` (`:50-56`) consults `If-Match`/`If-None-Match` with no method check. Plan line 18 says "HEAD and conditional decisions reuse existing applyReadHttpSemantics"; done-when 4 asserts only that "Conditional request fields on POST cannot prevent execution". `bdp.md:4595-4598` scopes the conditional exception to **GET/HEAD**; `bdp.md:3565-3577` says conditional fields on command targets do not guard anything.
- *Failure scenario:* `POST batch` with `If-None-Match: *`. Execution commits, receipt is produced, the response passes through `applyReadHttpSemantics`, and the caller gets a bodyless `304`. Done-when 4 passes (execution did happen) while the client has lost its receipt and a `304` has been emitted on a row where it is not admissible. A second-order version: post-hoc `406` on a POST response, when `bdp.md:4525-4527` requires negotiation *before* admission — which T2a already handles by taking `acceptsJson` as an admission control (`transaction-store.ts:57-60`, `transaction-submission.ts:59, 93-96`).
- *Fix:* state that POST responses never enter the conditional/negotiation branch — media acceptability reaches the owner only as `TransactionReceivingControls.acceptsJson`, and the only post-processing applied to a POST response is header/body serialization. Strengthen done-when 4 to assert the receipt is **still returned** with `200`/`202` and its correct body in the presence of `If-None-Match: *`, `If-Match: "x"`, and `If-Modified-Since`.

**6. Router composition order and per-target `Allow` are unspecified, and the Read helper's defaults are wrong for command targets.**

- *Evidence:* `read-http-routing.ts:23-24` returns a blanket `405` with `Allow: GET, HEAD` for any non-GET/HEAD method **before** any routing, and `:28`/`:40` return `404` for unmatched paths. `bdp.md:4601` requires `405` with `Allow: POST` on command targets; `bdp.md:4604-4605` requires `405 Allow: GET, HEAD` on receipt URLs and the `receipts` root, with the root answering `404 resource-not-found` for GET/HEAD.
- *Failure scenario:* the transaction handler delegates to `createReadHttpRoute` first; `POST .../batch` returns `405 Allow: GET, HEAD`. Or: `DELETE .../receipts/<unknown>` — unpinned precedence yields `404` for unknown tokens and `405` for known ones, which is a disclosure oracle on a row the plan elsewhere insists is uniform.
- *Fix:* specify the order — command targets and the `receipts` tree are matched (and their method tables applied) *before* the Read route is consulted; the method check on a `receipts/{token}` **shape** precedes existence and principal checks so `405` is uniform; and a token outside `[A-Za-z0-9_-]{1,256}` (`bdp.md:6580-6584`) is a `404`, never a `400`, since `400` is not in that row.

**7. Shutdown, close-racing, and owner fencing have no HTTP mapping, and close ordering is unstated.**

- *Evidence:* `transaction-service.ts:63-69` — `check()` throws a plain `Error` in two distinct situations: `cleanupFailure` (fenced; "close and reopen") and `!accepting` (closing). `transaction-service.ts:184-197` makes `receipt()` synchronous, so it *throws* rather than returning a typed refusal during close. `transaction-service.ts:201-221` snapshots `[...active]` once. T2a also fences the owner from a failed background maintenance sweep on an unreferenced ~1s timer (progress doc, "Receipt retention in a live owner"). Plan line 8 says only "graceful accepted-work drain"; done-when 5 covers durability but has no case for either state.
- *Failure scenario:* `close()` is called while a request is between socket-accept and its first `run()`; the handler throws "transaction service is closing or closed" and the client gets a bodyless `500` instead of `503` + `Retry-After`. Separately, a background sweep failure fences the owner mid-serving and every subsequent route returns `500` with no way to distinguish it. Separately again, if `close()` is awaited before the listener stops accepting, an in-flight response write can be cut.
- *Fix:* pin three things in the plan: (a) `!accepting` → `503 temporarily-unavailable` + `Retry-After`; fenced/`cleanupFailure` → bodyless `500` (per `bdp.md:4596`), both labelled as such; (b) shutdown order — stop accepting connections → let in-flight handlers finish writing → `service.close()`; (c) a done-when case for "owner fenced while the listener is live", asserting routes refuse rather than the process crashing.

**8. Two body/target bounds are layered without a stated relationship, and a target bound on GET routes sits outside their exhaustive rows.**

- *Evidence:* `transaction-submission.ts:61-62` enforces `TRANSACTION_RUNTIME_LIMITS.requestBodyBytes` = 64 KiB (`transaction-batch.ts:42-47`). Plan line 8 adds independent runtime "finite body/raw-target bounds". No `targetBytes` constant exists anywhere in the server package — the runtime invents one. Spec order is bounds (`413`) **then** carrier syntax including `415` (`bdp.md:4493-4499`). The receipt and Read GET rows (`bdp.md:4602-4605`) do not list `413`, and `bdp.md:4618` says authentication is decided **first** on a receipt read.
- *Failure scenario:* the runtime's read bound is set above 64 KiB, so a 100 KiB `text/plain` body gets `415` before `413` — inverted against `bdp.md:4493`. And `GET .../receipts/<token>?<very long query>` returns `413` on a row where `413` is not admissible, before authentication.
- *Fix:* require the runtime body bound to equal `TRANSACTION_RUNTIME_LIMITS.requestBodyBytes` (reuse the constant rather than restating 64 KiB), so the `413` fires in the transport and the submission check is a defensive duplicate; name the chosen `request.targetBytes` value; and state that the target bound applies to command targets only, with over-long GET targets on receipt/Read routes answered inside their own exhaustive rows.

**9. Refusal responses have no source of serving context, because the service discards it on a miss.**

- *Evidence:* `transaction-service.ts:119-124` — the private `receipt()` helper returns `undefined` when `observed.receipt === undefined`, dropping `observed.context`, which `owner.readReceipt` returned regardless (`transaction-store.ts:1196-1202`). `transaction-service.ts:193-196` therefore builds the `404` with no context, and the `401` at `:191-192` never touches the owner at all.
- *Failure scenario:* if the plan's "current serving epoch/view/position" is read as applying to refusals too, there is no way to produce it without a second (non-atomic) observation. If it is read as `200`-only, an unauthenticated `401` correctly leaks nothing but the decision is accidental rather than stated.
- *Fix:* state the rule: the three fields appear on `200`/`304`/`412` only; `401`, `404`, `405` and the bound refusals carry none, specifically so an unauthenticated or non-disclosed caller learns no Scope epoch. If any refusal is to carry them, say that the narrow `transaction-service.ts` addition must preserve `observed.context` on a miss.

**10. The `503` path T2a built explicitly for this boundary is absent from the wire matrix and the done-when.**

- *Evidence:* `transaction-submission.ts:109-115` already returns `{ status: 503, code: "temporarily-unavailable", retry: "after-delay" }`; the T2a progress note says in terms that unresolved comparison "yields an internal `temporarily-unavailable` result **for future direct 503 mapping**". `bdp.md:4530-4549` also requires the transient-abort rule: direct `503` SHOULD carry `Retry-After`, and the retracted receipt's URL then answers the uniform `404`. Done-when 2 enumerates "oversized/malformed/media/auth/key conflict/capacity/Accept" — no `503` case anywhere in the plan.
- *Failure scenario:* two concurrent unequal-but-unproven requests under one key; comparison hits its finite deadline; the handler has no mapping and emits `500`. T2b is the "future" T2a was deferring to, and the slice closes without it.
- *Fix:* add `503` + `Retry-After` to the matrix and a done-when case: unresolved comparison under a short injected deadline returns `503` with `Retry-After`, binds no key, creates no receipt, and the same key subsequently admits normally.

### LOW

**11. Stray carrier `Idempotency-Key` on `sequence`: "no carrier Idempotency-Key" (plan line 16) is ambiguous between *not used* and *rejected*.** `bdp.md:2764-2766` is explicit — "a sequence request that carries the field is rejected before execution with `malformed-request`" — and `bdp.md:3161` lists it among the direct carrier failures. *Fix:* say "a stray carrier `Idempotency-Key` is a direct `400 malformed-request` before admission, and nothing executes", and add it to the done-when 2 sequence list.

**12. "prior-epoch" receipt `404` is not testable in this slice.** `transaction-store.ts:391` writes `epoch` once at provisioning; there is no rotation path, so a genuine prior-epoch receipt cannot be produced. Done-when 3 claims "unknown/foreign/prior receipt paths share 404". *Fix:* relabel as a fresh-store proxy (a token minted in a previously provisioned store, presented to a new one), or drop "prior" from the done-when so the external report does not overclaim.

**13. Reuse is named for the Read helpers but not for the transport helpers that already exist.** The plan credits `read-http-routing`/`read-http` (correctly — `read-http-routing.ts` is prior reviewed work from `fc2c708`/`3edba21`, arriving via the PR86 merge, not new T2b code). It does not mention `node-http-target.normalizationSafeRawRequestPath`, the Host/absolute-target origin check (`development-runtime.ts:153, 163-164`), `acceptsJson`, or `TRANSACTION_RUNTIME_LIMITS`. *Fix:* name them as reused, and acknowledge in one line that the listener/body-reading/problem-projection shell is knowingly duplicated from `development-runtime.ts` (which the plan correctly declines to edit) with extraction deferred — otherwise two private runtimes silently diverge on raw-target normalization, which is precisely the class of bug `normalizationSafeRawRequestPath` exists to prevent.

**14. Two sequence entry points invite divergence.** The root-approved additive `sequenceObserved` leaves `sequence()` in place (`transaction-service.ts:153-180`) with its own abort/`cleanupFailure` path, which T2a's tests pin. *Fix:* have `sequence()` delegate to `sequenceObserved` and drop the observation, so the drain/abort/fencing semantics cannot fork. The "same runner" requirement in the plan is right and worth keeping explicit: the final context read must happen *inside* the same `run()` task, or a `close()` racing the final read will throw `check()` after the work already committed.

**15. State the monotonicity assumption behind "serves canonical afterstate from the same service" (done-when 1).** It holds only because one process holds one SQLite `EXCLUSIVE` connection, so a read after a committed POST cannot observe an earlier prefix. Saying so prevents done-when 1 from being read as evidence that the T3 barrier is optional — the plan already insists the barrier is required next, and this is the sentence that keeps that honest.

**16. Say that an original submission never yields `202` in this composition.** `submitTransaction` executes to terminal in-process (`transaction-submission.ts:119`), so no synchronous wait bound is advertised and `202` arises only from a concurrent equal duplicate joining a pending owner. `bdp.md:4557-4563` allows both sources; stating which one T2b actually exercises keeps done-when 2's "equal retries do not execute twice" from being confused with wait-bound behavior. Also pin `Location` = the receipt's own absolute `id`, not a rewritten URL (ties to finding 1).

### Not findings — checked and sound

- Receipt validator omission: `conditionalReadStatus` with `etag === null` yields exactly the `bdp.md:1989-1996` matrix (`If-None-Match: *` → `304`; specific `If-Match` → `412`; `If-Match: *` passes; specific `If-None-Match` cannot match). Date conditions are unevaluable for want of a modification date, consistent with `read-http.ts:4-8` and `bdp.md:1998-2001`. Reuse is correct; "no synthetic ETag or Last-Modified" implies receipts use `jsonResponse` (`read-http-routing.ts:44-53`, which already sets `private, no-store`) rather than `scopeDataResponse` (`:55+`, which sets ETags) — worth one sentence in the plan, but the intent is right.
- `page.maximumItems >= 32`: matches `transaction-service.ts:49-52` and `bdp.md:5068-5074`; the plan's refusal to infer a protocol minimum is the correct reading.
- `403 forbidden` exists in T2a (`transaction-submission.ts:19, 85-86`) and is simply unreachable under fixed all-writable policy; absence from the plan is fine, though one clause saying so would close the row.
- Sequence envelope shape: `TransactionSequenceResponse = { results }` (`transaction-sequence.ts:8-10`) already matches `bdp.md:3137-3148`, and the three Transactional fields are HTTP fields rather than body members — so `sequenceObserved` returning `{ response, context }` is the right shape.
- "No public admission / no on-wire discovery", the out-of-band URL fixture, and keeping cold schema-valid TX discovery as an unfinished done-predicate (plan line 22) are all consistent with the absent `updateWhere`/`deleteWhere`/snapshot/changes implementations. No fake-directory risk in the plan as written.
