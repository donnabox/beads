### 2. HIGH — Installed `encoded` negative row cannot be dispatched: the public exact executor rejects percent-encoded unreserved octets at construction

**Location:** `apps/bdptest/src/transactional-discovery-installed.test.ts:1558-1572` (specifically `:1561`), against `packages/conformance/src/http-executor.ts:402-419` (`canonicalHttpUrl`) reached from `:543` via `snapshotExactRoutes` ← `snapshotExactHttpMode` ← `createRawHttpExchangeExecutor` (`:169-170`), called in `send` at `:668`.

**Defect:** The row builds `.../operations/create-bea%64` (`leaf = "d"`, `charCodeAt(0).toString(16).toUpperCase() === "64"`). `canonicalHttpUrl` rejects any `%XX` whose decoded octet matches `/^[A-Za-z0-9._~-]$/` (`:416`) by `return configuration()`, which **throws** `HttpTransportError("configuration", …)` (`:365-367`). `d3Safe` does not decode `%64` (`new URL` preserves it), so the throw happens inside `send` before any socket is opened. Note every character of `create-bead` is unreserved, so *no* percent-encoded respelling of that target can pass this guard; encoding the separator (`%2F`) is independently rejected at `:421`.

**Impact:** The `private installed discovery methods auth and transport` callback aborts with a configuration error instead of observing the required `404`; `counts.scheduled`/`exact` are incremented at `:658-659` but `completed` is not, so the `26/26/0/25/1` inventory assertion at `d3Installed:506-512` can never be reached. One of the 11 installed callbacks fails deterministically. (The source-side analogue at `transaction-http.test.ts:7235` uses a direct `new Request`, bypasses the executor, and is fine — so this is an installed-lane-only defect.)

**Smallest correction:** Keep the row anonymous and allowlisted but encode an octet outside the unreserved set, e.g. target `` `${nav.targets.createBead}%2C` `` (decodes to `,`, passes `canonicalHttpUrl`, still refused by `methodResponse` at `transaction-http.ts:268-272` as a noncanonical operation target). This changes the witness from "alternate spelling of the same name" to "noncanonical encoded suffix" and should be recorded as such.

### 3. HIGH — TypeScript compile error: readonly tuple elements passed to a mutable-tuple array parameter

**Location:** `apps/bdptest/src/transactional-discovery-installed.test.ts:1742`, against the declaration at `:743`.

**Defect:** `fields?: readonly [string, string][]` parses as `ReadonlyArray<[string, string]>` (mutable element tuples). The argument
```ts
d3Tuple(nav, "opaque-minimum").map(({ name, value }) => [name, value] as const)
```
has type `(readonly [string, string])[]`. `readonly [string, string]` is not assignable to `[string, string]` → TS2322 at the call site. This is independent of `strict`.

**Impact:** `tsc`/`vitest --typecheck` fails; all three `private installed discovery close pending *` callbacks are in the failing file. Since no compiler has run on this candidate, this is unflagged.

**Smallest correction:** either widen the parameter to `fields?: readonly (readonly [string, string])[]` (`:743`), or drop `as const` and annotate: `.map(({ name, value }): [string, string] => [name, value])` (`:1742`). The second is the smaller behavioural no-op.

### 6. LOW — (confirms native N3, and extends it to the source file) Local-raw header bound omits the 4-byte terminator

**Location:** `apps/bdptest/src/transactional-discovery-installed.test.ts:818-824` and the same expression in `packages/server/src/transaction-http.test.ts:7126-7132`.

**Defect:** Both use `split > 16384`, where `split` is the index of `\r\n\r\n`; the complete header block is `split + 4`. The canonical executor enforces `end + 4 > maximumHeaderBytes` (`http-executor.ts:1119-1123`). The local helpers therefore admit 16388 header octets — 4 more than the pinned 16384 cap, violating plan4's "All local raw exchanges enforce the same or stricter header/body/derived-wire caps". The body bound (`bytes.length - split - 4 > 131072`) is strictly tighter than the executor's, and the derived-wire bound `163840` matches `maximumBodyBytes + 2 × maximumHeaderBytes` exactly, so only the header term is off. Unreachable with the actual responses under test.

**Smallest correction:** `split + 4 > 16384` in both files. Native flagged only the installed copy; the source copy has the identical defect.

### 7. LOW — Scope 204 carries owner context headers without `cache-control: private, no-store`

**Location:** `packages/server/src/transaction-http.ts:599-605`.

**Defect:** The 204 projection sets only `link`; `context()` (`:122-127`) then adds `bdp-scope-epoch`, `bdp-authorization-view`, `bdp-scope-position`. Every other response in this handler (`empty()` `:87-96`, `jsonResponse()` `read-http-routing.ts:44-53`) sets `cache-control: private, no-store`. 204 is a heuristically cacheable status, so an intermediary could retain and replay an authorization view and scope position. The shape is byte-identical to the existing Read probe emitter (`read-http-routing.ts:31-37`), which is why it is plausibly intended — but the Read probe carries no owner-state headers.

**Impact:** Minor disclosure/staleness risk in a private loopback development service; no test asserts the header's absence, so the fix is non-breaking.

**Smallest correction:** add `"cache-control": "private, no-store"` to the `new Headers({...})` literal at `:602-604`. Flagging rather than asserting a defect, since "exact existing service-desc Link … preserving the existing URL emitter" is ambiguous on this point — root's call.
