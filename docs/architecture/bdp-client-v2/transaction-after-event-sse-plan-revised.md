## Recommendation

**S2a: serve valid, supported `updateWhere`/`deleteWhere` singleton and atomic batch requests through the existing Transactional owner.** The core is already implemented and tested; this increment should retire the normal preparation/HTTP exclusion without adding another evaluator, owner, receipt model or Selector language.

The full negative Selector admission contract remains a genuine product/spec question. A schema-valid Selector string with invalid/out-of-profile grammar, or one exceeding `selector.bytes/depth/nodes`, is currently a private development refusal. This proposal does **not** choose its normative status or admission phase. A bounded private serving increment may accept the settled valid subset and retain explicit unsupported behavior for those categories, with no profile claim. Root explicitly permits isolating this work while leaving the question visible. Full set-serving qualification cannot be declared until the question is resolved and its precedence matrix is executable.

A separate preexisting limitation also matters: the32-match cap bounds effects/results, not candidate enumeration. Identify and instrument that boundary in S2a; do not advertise an examined-work bound or invent a new public limit. A behavior-preserving streaming enumeration follow-up is described below and needs explicit shared-seam approval before inclusion.

## Existing seams and bounded change

### One preparation/identity path

`prepareTransactionSetCore` already preserves lossless values and original outer operation indices, composes RU syntax-only validation for ordinary operations, refuses set labels/body keys, and creates a branded private transaction. `prepareSetCore` uses existing Selector evaluation on an empty collection to accept valid bounded grammar and currently wraps every ReadSelectorError as a development limit. It does not execute or bind a key during preparation. The existing selectReadResources parses and bounds the complete Selector before the candidate loop (read-selector.ts:162–185); the candidate evaluator does not raise ReadSelectorError. With immutable identical input/limits, this makes the supported-grammar decision candidate-independent. It justifies safely separating the private supported subset, not a new normative error phase.

Refactor the current normal/core split into one internal dispatch, rather than maintain two parsers that gradually differ. Normal batch preparation may delegate to the existing mixed set path; ensure its ordinary-operation recursion terminates in the ordinary parser and preserves label/witness indices. Keep the private set-only helper only if a real test seam still needs it, with identical machinery. No fake protocol brands.

Add a **source-private singleton-operation union** extending the current ReadUpdateOperation with exactly updateWhere/deleteWhere; use it in batch singleton preparation and TransactionSubmission. Do not widen the public RU operation enum or sequence grammar. Singleton validation must first apply the same depth-2-equivalent operation-content walk as the existing Resource singleton (transaction-batch.ts:178–179), making its private depth limit equal to the one-operation batch wrapper. It must reject illegal discriminator/name/body-key before wrapping: never silently strip an illegal field or let spreading body.operation override the route-selected operation.

Keep complete closed shape checks (including later operations), key grammar and label checks before any key access. Preserve exact lossless cardinality values and patch/provenance input, original singleton/batch pointers, label normalization and exact Selector string identity. Numeric spelling equality applies to numeric JSON members; it does not normalize numeric-looking text within Selector strings. Do not impose new restrictions on @ text inside ordinary Selector strings.

Unsupported negative Selector categories remain separately recognizable development gaps, not silently converted into malformed-request, invalid-parameter or a failed receipt. For this partial private composition, record the preflight unsupported category without consulting durable keys; after completing unambiguous closed-shape/key syntax checks and trusted authorization, return the existing bodyless development500 before key/effects. This is explicitly an unfinished private execution boundary, **not** the settled protocol phase for those inputs. An unauthenticated/read-only unsupported request will instead receive401/403 without the development-limit header. ### Numeric admission and original-request failures

Keep three phases distinct. Negative/fractional bounds and an empty/extra-field cardinality object violate the closed shape and receive pre-key400 with no receipt. An exact nonnegative integer can pass shape validation and still fail numeric admission: `9007199254740993` becomes a retained failed receipt, HTTP200 with embedded422 validation-failed, no graph effects, correct original outer index and a diagnostic locating the bound. Conversely `1e30` is numerically admissible: `isAdmissibleJsonNumber` compares the exact decimal to the shortest binary64 serialization's decimal, not the exact binary fraction. `1e30` and `1e+30` both normalize to coefficient1/exponent30. On a small fixture `min:1e30` therefore yields cardinality409, while `max:1e30` does not block matching; neither is a numeric422 example. No max-safe-integer rule is introduced. `{min:5,max:2}` passes shape/numeric admission then yields retained cardinality409. Cardinality checks remain before the matched count charge, after numeric admission.

The receipt clause at5258–5262 conditionally requires `problem.pointer` whenever the cause can be located in the submitted request. Schema optionality does not waive that obligation. A diagnostic message containing a relative path is not the same field; numeric-admission diagnostics still name the offending member under their own contract. S2a must add bounded known-location mapping at the existing set failure construction: numeric failure uses the first offending occurrence, cardinality failure identifies the failing supplied bound, and other set failures use an exact known original field/location only when available. Audit translated patch/evaluator diagnostics against the original `change` input; do not emit the synthetic `propertiesChange` path or claim a stored Resource's schema instance path is a request pointer. If additional shared evaluator location machinery proves necessary, report that scope before editing it rather than fabricating a path or declaring the row qualified.

For a numeric bound, the original singleton points at `/cardinality/min`; an original batch operation at index2 points at `/operations/2/cardinality/min`. The existing prepared carrier kind and original outer index are available during execution. Persist that original pointer in the original failed receipt; equal cross-carrier retries and reopen must preserve it verbatim, not rebase it to the retry body. Never include the carrier spelling in semantic identity merely to make the pointers easier. This is a narrowly identified existing-contract repair in transaction-batch.ts and its tests, not a general Problem redesign. Whole-transaction limit failures keep their existing no-fabricated-operation-index framing.

## Bounds: output is bounded; examined work is not

Current enforced tuple: request64KiB,32 outer operations, matched32 across repeated sets/no-ops, induced Events256, complete representation256KiB, properties64KiB, diagnostic512KiB/count16. Selector core bounds are4096 decoded UTF8 bytes/depth32/nodes256. The same persisted receiptMaximumItems knob is32 at actual installed defaults and bounds both receipt inline/continuation entries and finite Event page entries. It does not count whole changefeed groups. Owned fan-out uses the accepted one-Link+one-source/maximum-four-Event facts, without source preimage bodies. Reuse current materialization proof; do not reintroduce4096-Event historic assumptions or count bytes as Resources.

At `transaction-store.ts:1131–1138`, staged resources uses SELECT id .all().map(requiredResource). At `transaction-batch.ts:804–819`, the evaluator materializes/parses/filters/selects the complete collection before checking32 matches. A selector matching zero can therefore read/allocate an arbitrary collection. The32-match cap proves no bound on candidate count, scan time, or visibility-closure traversal. Installed bounded fixtures prove only their actual workload. This remains a public-readiness gap. The current resources(kind) implementation is an ID query plus one requiredResource lookup per row, repeated once per set operation (up to32 outer sets), with visibility traversal per candidate. Every selection must observe the effects of preceding operations; a single frozen candidate snapshot cannot be hoisted across operations. This does not prove32 physical full scans are universally irreducible: a future correct index or maintained staged representation could improve the work. S2a does not introduce one.

The smallest behavior-preserving memory follow-up would keep the scan within the synchronous owner entry, stream one frozen stored row at a time, retain only up to the existing32 selected records plus a total match count, and still evaluate the whole collection before cardinality then matched-budget decisions. If matches exceed32, do not retain more postimages but keep counting so cardinality409 still precedes matched413 when the complete match is known. Apply no mutations until selection/cardinality/budget finish. Do not silently truncate the matching set, claim an examined-resource cap, or change ordering to database UTF8 collation (canonical code-unit ordering still applies after bounded selection).

That follow-up needs a guarded owner visitor/iterator with no escaped SQLite lifetime and a parse-once predicate from the existing Selector implementation. A narrow shared-selector seam would require root arbitration; do not copy the parser or add a second evaluator. It must perform logically fresh selection at each operation turn. Streaming retention alone does not reduce the candidate count, repeated selection work, total CPU or recursive owned-visibility work. A real examined/duration bound needs its exact count/configuration/failure/replay contract, not an invented limit here. **Do not automatically include this follow-up in S2a or pretend S2a closes it.** Root can order it before wider qualification after reviewing the code/impact. No new public limit or storage-configuration change is proposed by this plan.
