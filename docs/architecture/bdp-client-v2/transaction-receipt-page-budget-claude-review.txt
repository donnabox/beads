## Findings

**1 · MEDIUM — the 16 KiB coverage fence is asserted but never measured; no coverage candidate exists**
*Location:* `budget-amendment.md:5` ("Coverage +16KiB unchanged"); `author.py:47-57`
*Impact:* `author.py` iterates manifest first, writes `manifest-v1.json.candidate` at line 50, then trips the line-55 assert (`<=320*1024`) — so the loop never reaches `coverage-v1.json`. The directory contains no coverage candidate and the amendment states no coverage byte figure. One of the two fences the root reviewer is asked to leave unchanged is therefore unverifiable from the submitted set. I reconstructed it in memory: growth **12992 B**, total **54804**, headroom 3392, and Biome formatting leaves it byte-identical. So the claim is true — but it is currently an unevidenced assertion.
*Fix:* generate and hash the coverage candidate, or state the measured 12992 / 54804 in the amendment.

**2 · MEDIUM — the generator installs into the source tree, so approving the fences also arms an unreviewed artifact write**
*Location:* `author.py:57` (`path.write_text(out)` → `packages/conformance/test-support/transactional/{manifest,coverage}-v1.json`)
*Impact:* "No source artifact/fence change has been made" (`budget-amendment.md:19`) is true only because the line-55 assert fired first; git confirms both files still at 238693 / 41812. But the script conflates candidate generation with installation. Raising lines 55-56 to 128 KiB/360 KiB and re-running immediately writes both artifacts into the tree — contradicting line 3's "artifact authoring/execution remains held pending independent root review."
*Fix:* delete line 57 or gate it behind an explicit opt-in flag; the generator should only emit `*.candidate`.

**3 · MEDIUM — 2019 B of total headroom silently forecloses the root-approved 18→20 action expansion**
*Location:* `budget-amendment.md:5`; root acceptance line 11 ("Up to 20 new/141 total only with a specific documented seam need")
*Impact:* the amendment offers node headroom (157) as the scope bound, but the binding constraint under the proposal is the 360 KiB **total**, at 2019 B. Measured formatted action sizes in the candidate: cheapest are reopen 396, p-seed-read 1853, p-final 1884, p-page-head 2047. A single additional HEAD read (2047) already breaches 368640; the two cheapest realistic additions (1853 + 396 = 2249) also breach it. Nodes would fit (13-58 for light reads); bytes would not. So granting 360 KiB quietly converts "up to 20/141" into "18/139 final," and a later documented seam need forces a second amendment.
*Fix:* state this explicitly so the root decides now — either accept 18/139 as final for this row, or set the total fence with room for the two reserved actions.

**4 · LOW — per-action decomposition is measured on an undisclosed pre-format candidate**
*Location:* `budget-amendment.md:9`
*Impact:* line 3 names `manifest-formatted.json` as the exact candidate, but the decomposition is measured on `manifest-v1.json.candidate` (SHA `01de14e7…`, never named or hashed in the amendment). The discrepancy shows only on the largest line item: p-update is **36888 B** in the named exact candidate, not 38616 — Biome's entire 1728 B action-level saving sits in that one `outcomes` tuple. The other four figures are identical on both bases. Consequently the five-action sum is 95712 B (93.5 KiB), not 97440, and the remaining 13 are 31628 B (30.9 KiB). Separately, both "~97KiB" and "~32KiB" label raw byte counts as KiB in a document where every fence is exact KiB (80 KiB = 81920, 360 KiB = 368640). A reviewer measuring the named artifact cannot reproduce the table.
*Fix:* restate on the formatted basis (p-update 36888; five actions 95712 ≈ 93.5 KiB; remaining 13 ≈ 30.9 KiB), or name and hash the pre-format candidate and label the basis.
