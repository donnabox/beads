## M1: actual immutable metadata and physical routing

At the basis, `transaction-runtime.ts` requires explicit Scope for compiled artifacts, but rejects Host unless it equals the loopback listener authority. The exact raw executor always derives Host from the canonical request URL and forbids an authored Host override. A stable `https://reference.invalid/acme/` Scope therefore cannot currently execute this cohort. M1 must solve the actual runtime gate; the harness must not fake Host or rewrite canonical identities.

M1 introduces a narrow **private configured authority mode**, used by the installed candidate, that validates Host against the configured canonical Scope authority while listening on loopback. No arbitrary Host allowlist or routing plugins. Keep ordinary development defaults unchanged. Origin-form targets resolve under that Scope; canonical path, wrong Host/port, duplicate Host, alternate authority and out-of-Scope target checks remain real. This is not a claim of public TLS/proxy deployment or complete absolute-form/CORS support. Those untested cumulative Read branches remain missing, not ruled out of the protocol.

Use port **0** for the private listener; emit its actual `listenUrl` after binding and successful owner/service/handler construction. Validate exact plain-loopback form, explicit port, no userinfo/query/fragment, and expected pathname. Bind the raw dial route to that value before resolving credentials or issuing requests. Canonical request URL/Host and physical plain-loopback endpoint are recorded separately. Reopen may obtain a new port; validate a new actual listening endpoint from the same child startup rather than silently following an arbitrary returned address. Do not put the ephemeral port into persistent store compatibility identity.

M1 captures closed own-data inputs and freezes the exact values consumed by runtime/owner/service/transport. Metadata comes from this real capture and is emitted only after startup succeeds:

- `artifactIdentity`: return `contracts.identity` unchanged (`development-schema5-<64hex>`). H1 requires plain descriptor/schema bytes and the real compiler, never a bare Type inventory shortcut. H1 uses existing `installedContractsDigest` to validate/decode the prefix; no rehash or alternate contract digest.
- `policyIdentity`: canonical digest of fixed all-visible Resource policy, actual empty aggregate policy and the actual permission associations. **Permissions are per credential**, not a principal→boolean map. Associate each token digest with principal and canMutate; two tokens for the same principal may differ. No raw tokens leave capture.
- `authenticationIdentity`: digest of the captured authentication scheme and exact credential/token-digest/principal/permission associations. Permission changes can affect both identity digests; independent variability is not promised. Tests swapping canMutate across same-principal credentials must change the binding. Separate injected mismatch tests check each digest field's enforcement.
- `configurationIdentity`: digest of the actual canonical Scope, compiled closure, effective fixed limits/defaults, receipt bounds, selector/pagination/retention/maintenance configuration, policies/authentication, configured transport authority mode, profile transactional and history false. Hash what the runtime consumes; avoid a second parallel list of defaults. Derive from the tuple on the approved integration base, including any accepted materialization changes, rather than hard-coding the older source's capacity.
- `profile:"transactional"`, `history:false`, `claimEligible:false`, real `scope`, actual `listenUrl`, and a closed handler-generated operation-target map. These are private candidate metadata, not Service Description/capability advertisement.

Keep store installation compatibility separate from the live runtime configuration and per-start listener binding. Do not add credentials or ephemeral port to persistent identity as a side effect. This change must not create clocks, scheduler hooks, store access, synthetic positions/outcomes, policy redesign or a Type lifecycle.

The existing `ServedProfileConfiguration` **does not retain configurationIdentity**. H1 needs a source-private immutable TX execution binding containing (a) the existing served binding, (b) the actual full configurationIdentity, and (c) that start's physical listenUrl/dial binding. Compare expected versus observed capture at bootstrap, every scenario start before setup/actions, and durable reopen. For a reused child, this checks its immutable startup binding and live child identity; there is no policy-change control or invented metadata-refresh IPC. A restarted child requires a new actual ready observation. Changing only configurationIdentity must fail before the first request even when every shared served field matches. The live logical identity must remain stable across an intended same-configuration reopen; the new physical endpoint is separately validated/rebound. Child-reported actual identity is mandatory; expected calculations may check it but cannot replace it.

`sourceCommit` is launcher-verified build/pack metadata, not a child claim. Fixture digest/id/capabilities are bound exact harness inputs. Equality checks establish consistency of observations, not cryptographic deployment attestation.

## Dynamic receipt reads: separate, auditable raw observation path

Public frozen-route behavior in `http-executor.ts` and the ordinary runner stays unchanged. A receipt UUID cannot be predeclared, so merely adding a capture does not make it an admissible exact HTTP action. The private TX adapter is an explicit reviewed H1b component, not a transparent relaxation of the ordinary exact configuration digest.

1. Use explicit Resource IDs for every initial create. Predeclare operation POSTs and Resource/collection/Event GETs in the normal frozen route list; batch receipt assertions initially use the actual POST body. All default reads, including Events/receipts, use the operator credential handle. Anonymous TX read controls expect 401, unlike RU anonymous reads.
2. Wrap actual raw execution for these fixed requests with a source-private observation ledger. Preserve the original returned status, header lines, body bytes/text and exact request observation without rebuilding a response. Admit a receipt target only from the validated receipt `id` of a successful actual completed/failed POST observation (or a directly linked actual receipt observation). Store originating action/response identity, exact source pointer, canonical URL, method role and credential/view association. A caller-supplied string or synthetic fixture binding cannot create authority to follow a URL.
3. A private `transactional.receipt-read` action names that prior observed binding and GET or HEAD. Require same canonical Scope/origin, exact receipt path grammar with one identity segment, no userinfo/query/fragment, no alias/operation/Resource substitution, no encoded traversal, and exact equality to the previously observed value. Validate source response shape/status using unchanged normative receipt definitions. Reject unobserved, foreign, malformed or cross-scenario captures before dialing or resolving credentials. Receipt reads use the same allowed credential handle as their source observation in this slice; no arbitrary credential switch or host override.
4. For this one route only, instantiate the existing raw executor with a separately snapshotted exact mode containing that single canonical method/URL, bound to the already validated physical listener and immutable TX execution binding. Keep the public base frozen-route set and its digest unchanged. Record the per-route exact configuration/digest, original raw request observation and original received response plus the prior-response linkage. Reports must distinguish this dynamic action's per-route provenance from the base run's fixed-route digest; do not claim the dynamic URL was in that original list. Keep original exchanges in the bounded private observation path and apply existing credential redaction/fingerprint rules to exported request evidence; do not print raw authorization fields or change response bytes to make an assertion pass.
5. Feed a bounded observation envelope to the existing assertion engine, retaining original wire observations as the evidence source. Parsing its received JSON for assertions is allowed; constructing synthetic successful HTTP replies is not. Any action-output projection must identify its original raw exchange and preserve response bytes, not substitute a new response serialization. If existing runner output cannot retain that linkage, propose the narrow private recorder addition before implementation rather than dropping the raw evidence.
6. Counterfactual response mutations are test-only negative controls, never accepted target observations. Test an unobserved receipt URL, same-Scope wrong path/UUID, changed source response, cross-row binding, foreign origin, credential substitution, changed dial endpoint and altered exact observation; each must fail before a credential-bearing dial or at the specified evidence assertion.

No receipt-page adapter is implemented initially. Direct HTTP carriers have at most 32 operations/entries and production receiptMaximumItems is 32, while this cohort uses at most eight operations; HTTP set preparation remains closed. Thus no receipt continuation is reachable here. `transactional.receipt.pagination` and the paginated branch of readable/restart observations stay explicitly missing. No bound lowering, hidden skips or zero-page-success claims.
