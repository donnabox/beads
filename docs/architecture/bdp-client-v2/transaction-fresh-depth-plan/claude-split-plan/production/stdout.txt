## Findings

**1. Blocking — SQLite `json_extract` over receipt text becomes a depth-sensitive traversal the plan never inventories.**
*Plan location:* plan.md §3 ("transaction-store.ts removes only the depth-specific branch/union variant … leaving authoritative retained/pending/expired comparison … unchanged") and §New source witnesses A ("Close/reopen actual store once and re-read genuine retained receipt/page/current Resource").
*Source:* `packages/server/src/transaction-store.ts:554` — `SELECT * FROM receipts WHERE owner IS NULL AND json_extract(receipt,'$.detail')='available'`, inside `sweep()`, which runs at store open (`transaction-store.ts:626`, within the startup transaction whose failure closes and may unlink the file at `629‑633`) and on the maintenance timer (`1451‑1468`), where a throw is sticky: it revokes leases, closes the database, and surfaces on every later owner entry. Completed receipts carry result Resource postimages (`1375‑1396`, `json(receipt)`), so this column begins carrying depth‑12000 text exactly when the gate at `1163‑1166` is removed. It has never done so: fresh deep keys are refused today, and the affected existing installed fixtures are depth 41.
*Defect/impact:* the repo already records this hazard — `recovery-store.ts:561` "SQLite's built-in JSON parser rejects otherwise admitted deeply nested text", which is why format 4 replaced `json_valid` with the JS predicate `bdp_json_syntax_v2` (`recovery-store.ts:564‑577`) and why its own deep fixture is depth 12000 (`recovery-store.test.ts:1314`). After one deep completed receipt, the next maintenance tick or reopen either raises a SQL error (Scope‑wide sticky failure; installed requests 10–13 and witness A's reopen fail as private faults, not the planned 200s) or evaluates false (deep receipts silently never compact/expire, breaking retention). This is independent of fixture choice: a 64KiB body admits ~32k nesting.
*Smallest correction:* in the already‑owned file, drop the SQL JSON dependency — scan `SELECT * FROM receipts WHERE owner IS NULL` and test `parseReceipt(stored.receipt).detail === "available"` in JS (`expireRow` already parses each row), preserving the row set and ordering; add a required regression (deep completed receipt → `maintain()` + reopen). Do not lower the fixture instead.

**2. Low–Medium — durable semantic‑identity expansion is outside the plan's byte accounting.**
*Plan location:* plan.md §2/§"Actual 413 request bounds…" and pre-review-audit.md §Response-cap audit (request/response/receipt/Snapshot bytes only).
*Source:* removing the branch at `transaction-store.ts:1163‑1166` lets fresh deep keys reach `normalizeTransaction` (`transaction-batch.ts:479‑557`), whose `identity` is `encodeSemanticValue` output; per nesting level it emits `["array",[` … `]]` (12 bytes) where the body has 2, i.e. ≈6× expansion, stored unbounded in `receipts.identity` (schema `transaction-store.ts:231`, no CHECK, no byte limit) for the retention window. The ledger's 48363B sequence body implies ≈290KB of durable identity.
*Impact:* no limit or refusal path is crossed, but "capacity bounded by existing bytes" is incomplete for durable rows.
*Correction:* one sentence stating the expansion factor and that no new limit is added; measure actual identity bytes for the `sequence` body during authoring.

## Verification supporting the four scope questions

**1. Extraction.** `equal` is exactly `resource-evaluator.ts:383‑408`, iterative, and used only at `865‑866`. Its semantics match the stated domain: `a === b` makes −0/0 equal; `Array.isArray` parity separates arrays from objects; key count plus `Object.hasOwn` enforces key presence and null‑versus‑absent; object key order is irrelevant; dense arrays compare by index keys. `equal(link, undefined)` returns false, so the missing‑owned‑data case still rejects before issuance. Substituting it for `isDeepStrictEqual` at `transaction-snapshot.ts:407` loosens only ±0 and prototype identity, neither observable: stored bodies round‑trip through `stringifyJsonValue` (so −0 serializes as `0`) and both operands come from `readStoredResource`/`JSON.parse` plain data. The prohibitions are grounded — `encodeSemanticValue` throws on native numbers (`semantic-identity.ts:137‑140`), and serialization equality would make key order integrity‑significant. The sorted‑ID check (`399`, flat string arrays) and endpoint checks (`411‑423`) are shallow and unaffected. Nothing in these modules is exported from `packages/server/src/index.ts`, so the new helper can stay source‑private.
