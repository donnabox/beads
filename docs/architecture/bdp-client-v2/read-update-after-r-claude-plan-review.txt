## Finding 1 — Medium: Catalog 61's Type/properties-schema conjunct has no Property-Change witness, and the plan does not disclose it

**Location.** Plan §"All five selected obligations" Catalog 61 cell (line 24) and §"Why the Type/schema sample is sufficient for this row" (lines 27–33); proposed coverage reason, plan line 51. Evidence: `packages/conformance/matrices/read-update-reference-continuation-v1.json` R row — the only Type/schema witnesses are `nr-{bead,link}-schema-create-refused` / `-absent` / `-create-corrected` / `-read`. There is no `nr-*-schema-patch-*` action.

**Impact.** The selected text is list item `bdp.md:2658–2659`, inside the list introduced at `2648–2649`: "When each operation is reached, the authority validates **its resulting state** before evaluating the next operation. It checks: …". R executes 24 effectful update operations, and none of them can exercise that check:

- `nr-schema` (bead and link) is created and read, never updated.
- Every resource R *does* update is typed `types/task` / `types/relates`, and `packages/conformance/fixtures/read-update-reference-v1.json` contains **zero** occurrences of `propertiesSchema` — the only schema-bearing Types in R's configuration are the four injected by `withSchemaCohort` (`apps/bdptest/test-support/installed-schema-cohort.ts:12–53`). R's own `task`/`relates` descriptor GETs assert only `/id`, `/describes` and (for relates) endpoint `conformsTo`, so the row does not even establish whether its update targets are under a schema contract.
- The update-path numeric refusals cut the other way: their diagnostics name **request** locations (`/propertiesChange/0/value/items/0/a~1b~0c`, `/metadataChange/1/value`), which evidences input-time admission, not resulting-state validation.

Net: a runtime that applies effective-Type/properties-schema validation on create and skips it entirely on update passes all 619 R assertions. The plan's exclusion list names only keywords, child/base combinations, descriptor graphs, installation, wrong-kind, endpoint policy, cycles and Type lifecycle — not operation form. Since the plan deliberately partitions whole vs. change for both the numeric and the metadata conjuncts, confining the schema conjunct to the whole/create form is an asymmetry in its own standard, not an exhaustiveness limit. The native review disposes of it with a single word ("every keyword, Type graph, **operation** and failure permutation"), bundling a partition the plan treats as material elsewhere with genuinely unbounded matrices.

Context root should weigh: the discriminating behaviour does exist and is observed — `read-update.singleton.update-bead`'s coverage reason records "a row-local child-declared effective parent-schema refusal" — but that is another row's evidence, that row is itself `wholeContract:false`, and R's standard is explicitly row-local.

**Fix (either, root's call).**
1. *Keep zero-action.* Say so explicitly: add to plan §Why-sufficient and to the proposed coverage reason that the Type/properties-schema conjunct is represented by whole-document creates only, on the stated ground that the per-operation preamble (`bdp.md:2648–2649`) is not selected text — i.e. carry it as a second named residual beside the revision-linkage one. This fits the 768-byte cap only if the reason stays terse; measure before freezing.
2. *Treat it as a distinct conjunct.* Then the zero-action premise fails. Minimum bounded closure is one row-local pair per kind: `nr-<kind>-schema-patch-refused` replacing `/n` with `-1` on the admitted `nr-schema` resource — expect 422 naming base Type `…/types/schema-<kind>-base`, `schemaLocation …/schemas/schema-<kind>-base#/properties/n/minimum`, then full-record `equalsBinding` against a captured `nr-<kind>-schema-read` body — plus an admitted one-leaf correction. This invalidates "zero manifest bytes/nodes/actions/assertions", the 768-byte coverage cap, the 18-entry refusal map count, the 88/619 pins at matrix test:4031/4847, and the `addedIds`/5460-byte ledger at :4839–4846, and needs its own action and byte budget.
