## Verdict

It can produce real installed-service observations without enabling public Transactional admission or pretending launcher-provided operation targets prove cold discovery. **Make the full live-configuration comparison explicit before implementation accepts observations.** Two additional bounded plan details need to be stated; none requires a product ruling or changes to current runtime semantics.

## M1 — existing served-configuration binding drops the new live configuration identity

Plan lines 15–16 reuse `bindServedProfileConfiguration` / `assertSameServedProfileConfiguration`; line 27 correctly requires an actual runtime `configurationIdentity` covering effective limits, pagination, retention and transport defaults. However, `packages/conformance/test-support/profile-contract-plan.ts:35–69` has no corresponding field. Its closed own-data capture rejects extras, and its equality function at 171–179 compares only the captured existing fields. Two ready messages with identical payload/contracts/policy/auth/Scope but different runtime configuration identities therefore map to the same existing served binding. Merely returning the new digest in IPC does not enforce it.

This is a **plan enforcement gap**, not a demonstrated defect in an unimplemented H1 runner. The existing RU matrix compensates with explicit configurationIdentity assertions at `apps/bdptest/src/read-update-matrix.test.ts:261,310–313`; H1 must not assume the shared binder already does that.

Minimal repair: require a source-private TX bound execution record that retains and compares the actual runtime configuration digest on bootstrap, every scenario start and durable reopen, before setup/actions. Either retain an explicit parallel immutable equality check as RU does, or introduce a narrowly scoped private TX binding wrapper; no broad public input widening is necessary. Include a counterfactual changing only configurationIdentity while every existing ServedProfileConfiguration field remains equal, and require failure before the first request. Preserve expected-versus-observed checks and recorded readiness; a launcher-side independent expected calculation may verify, but must not replace, the child-reported actual binding.

## L1 — reconcile the promised cumulative byte cap with the planner's actual gate

Plan lines 14,16,69 promise reuse of the cumulative 4 MiB manifest budget for TX. The artifact factory can be extended as proposed, but `profile-contract-plan.ts:236–240` currently selects that budget **only** for baseline Read+Update. A TX manifest is still capped at the ordinary 1 MiB limit in the reused planner. The proposed shared-files list at plan line 63 does not include this helper.

Either explicitly keep the initial small TX manifest within 1 MiB and report that current planning limit, or add the narrow baseline-TX selection case with boundary controls proving public Read, History, fixture and catalog budgets remain unchanged. Do not globally raise `parseBoundedJson` or ordinary artifact limits. This need not delay the initial four-row authoring if its manifest stays below 1 MiB.

## L2 — choose and record an unambiguous physical listener binding

Plan line 28 requires the actual listener binding; line 40's ready-field list includes Scope and optional canonical targets but no listenUrl. At the basis, `transaction-runtime.ts:96–97` accepts port zero and `:274–280` assigns the actual loopback port; the returned `listenUrl` at 338–342 is distinct from the stable configured Scope. Canonical receipt/Event URLs cannot themselves identify that physical endpoint.

Choose one bounded arrangement explicitly: require a known nonzero configured port and bind the raw executor to that exact input, or emit/validate the actual loopback listenUrl when using port zero. The latter avoids reservation races. In either case record the route translation and reject a changed/foreign physical endpoint before credentials or actions are sent. Do not place an ephemeral listener port into persistent store compatibility identity. This is a harness wiring clarification, not a new protocol field or mandatory public routing convention.

## Accepted boundaries and concrete acceptance notes

- The canonical selection/factory plan is sound: all 250 selected required rows remain visible, exact catalog-digest map/order/retirements are bound, and the distinct WeakSet/brand may authorize only the source-private entry. Keep ordinary runner rejection even for a genuinely branded TX bundle, plus structural-lookalike and RU-factory negatives. No user-controlled bypass flag.
- Existing runtime options compile exact artifact bytes before listener startup (`transaction-runtime.ts:119–153`); compiled identity binds artifact digest and all three compiler-limit witnesses (`development-contracts.ts:137–152`). Capture only plain artifact input in H1, not an alternate bare types inventory. Current store identity alone is insufficient for live transport/auth/defaults; the plan correctly requires metadata derived from the actual consumed detached tuple.
- Current authorization is **per credential**, not purely per principal: credentials capture canMutate at `transaction-runtime.ts:102–114`, then the matched credential provides it at 196–204. The plan's permission-bearing association clause must include that fact. A negative control swapping canMutate between two tokens for the same principal should change the bound auth/configuration identity; never collapse it to one ambiguous principal boolean.
- Separate persisted installation identity from live payload/auth/listener identity. Do not add auth or ephemeral listener identity to store compatibility as a side effect. Stable Scope/compiled closure already have durable compatibility gates. Payload hashing remains actual installed dependency bytes, not Git source identity or a proof of external deployment/TLS.
- Closed IPC, import inertness, post-start close-only control and readiness after actual service/handler availability are appropriate. The existing TX pre-ready handler returns unavailable (`transaction-runtime.ts:158–162`), and the runtime returns only after handler construction. Test disconnect/close during startup as well as after ready; no ready event after stopping, no leaked owner/listener, nonzero cleanup failure. Log only bounded nonsecret metadata.
- The four row IDs exist with the stated normative requirements. Literal intermediate receipt postimages versus final GET, rollback absent-Resource/Event witnesses, failed-retained replay after changed state and completed replay after independent mutation are discriminating observations. Keeping all four wholeContract flags false is honest. Add explicit HEAD only if claiming it; the initial GET-only readable witness does not establish the catalog title's full GET/HEAD behavior.
- Actual production receipt maximum is 32, while the planned initial carriers have at most eight operations and HTTP set preparation remains closed. Initial receipt pagination should therefore be recorded missing unless a real supported carrier produces enough results. Do not lower the bound, silently skip page assertions, or count zero page GETs as pagination success. The plan already permits this omission.
- Finite Events establish only the available final-effect/order witness. They do not establish atomic transient invisibility, complete change groups, replication, SSE or metadata-only incident semantics. Failed receipts have no committed result list; context can be current while retained receipt disposition/postimages remain original. Avoid comparing fresh response-context headers to the original receipt as if they must be identical.
- The actual transport's Origin/absolute-form limitations remain explicit; inherited Read gaps stay missing, not inapplicable. Exact captured URL allowlisting must preserve canonical Scope confinement, verb and role, use original HTTP observations and reject foreign targets before any credential-bearing dial.
- Shared payload extraction is appropriate if its traversal/preimage remains unchanged for the same package bytes. Newly emitted files naturally change payload hashes. Preserve package-root/deep-import denial, internal-symlink refusal, and no workspace resolution fallback. No reseal follows from this plan.
