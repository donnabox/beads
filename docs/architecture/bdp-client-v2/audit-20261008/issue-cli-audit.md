# Issues-pack CLI feasibility over generic BDP

Audit date: 2026-10-08. This is a source-and-test-contract audit, not executed runtime qualification. No database, build, source snapshot, Preview 2 artifact, or role launch was changed. Current `gastownhall/beads` main is `5126de8c1a02d01db2481e4fd5e78dd41010e25f`; normative BDP main is `182f1fcf8a01d896976bff3c9e3fb87c596c6ca6`. The Preview 2 snapshot was available but this report deliberately establishes the current Issue command obligations from main and tests them against normative BDP, not the temporary Preview implementation.

## Conclusion

**Most Issue mutations can run as an Issues pack over generic BDP, with Transactional as the required profile. Current BDP does not provide an efficient stateless implementation of all existing reads or compact support for several existing transaction policies.** This is not a reason to retain Issue-specific endpoints. It identifies generic protocol additions or an explicit client replica requirement, plus a few compatibility decisions.

The strongest gaps are: priority/search/count/graph queries; compact race-safe assertions over joined or traversed state; partial-success close batches with an atomic claim-next; and current ephemeral/lease behavior that intentionally avoids history. Simple claims, scalar patches, metadata keys, create-with-links, and bounded cascade deletion are positive examples, not gaps.

Do not label every graph policy impossible: `deleteWhere` with cardinality `max:0` can assert no visible matches, while an `expectedRevision` same-value update can guard known resources. These mechanisms can carry surprisingly much policy in a generic batch, but can require large read sets and selectors, broad write permission, and retries. They do not magically provide joins, ordered selection, conditionals, or authority enforcement of arbitrary Issue invariants.

## Reading the request costs

`B` = Beads relevant to a candidate query; `E` = relevant Links; `P` = negotiated page size; `K` = command output size; `D` = traversed graph depth; `W` = resources written. Costs count HTTP requests after discovery/authentication. Parallel requests reduce latency but not response volume. Receipt polling/pagination may add requests; one mutation request does not guarantee a synchronous one-response outcome. A warm client replica changes the cost to local work plus changefeed catch-up, but initial bootstrap, local storage, retention recovery, view changes, and consistency must be part of the product contract.

## What BDP actually supplies

- A Selector evaluates one Resource at a time, over `id,type,properties` and Link endpoints. Scalar paths, literal comparisons, existence, and Boolean operators are available. Joins, traversal, functions, regex, aggregation, recursive descent, and nested filters are expressly absent. [docs/specs/bdp.md:781–842](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L781-L842)
- All collection pages contain complete records in authority-advertised order; only canonical-URI ordering is mandatory, and callers cannot request another order. There is no projection, embedded per-Bead incident Links, or relevance ranking. Structural endpoint filters and selector filters are combined before pagination. Each cursor continues one logical projected snapshot. [docs/specs/bdp.md:5367–5455](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L5367-L5455)
- Transactional batches are one-Scope, all-or-nothing, ordered, and staged. No interactive transaction or nested transaction exists. Creation labels bind only identities, not query results, timestamps, revisions, or computed properties. [docs/specs/bdp.md:1246–1284](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1246-L1284) [docs/specs/bdp.md:970–1043](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L970-L1043)
- Set mutations select the complete match set at serialization, enforce cardinality, and never truncate to a page. Operational limits can reject a transaction even if not pre-advertised. Chunking sacrifices whole-job atomicity. [docs/specs/bdp.md:1586–1661](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1586-L1661) [docs/specs/bdp.md:2310–2371](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L2310-L2371)
- Patches have add/replace/remove only; JSON Patch test, move, copy, arithmetic, string append, and general expression evaluation are absent. Same-value patches are no-ops. Explicit mutations accept revision guards. [docs/specs/bdp.md:955–968](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L955-L968) [docs/specs/bdp.md:698–754](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L698-L754) [docs/specs/bdp.md:4912–4953](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L4912-L4953)
- A first-class Scope snapshot binds both Beads and Links to one consistent position. Independent collection queries are not a replica bootstrap. Strict reads give a consistent prefix per request; a minimum checkpoint is a lower freshness bound, not a multi-query immutable read transaction. [docs/specs/bdp.md:2035–2065](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L2035-L2065)

## Priority findings and concrete counterexamples

### 1. Efficient top-K, string search, counts, and graph predicates are not guaranteed

`ready` is not “status=open.” It uses derived blocked state, custom active statuses, excludes infra and ephemeral kinds by default, inherits deferred-parent exclusion, handles descendants, and sorts by policy. Hybrid order places recently created work in a separate bucket and uses priority and age; BDP cannot ask for this order. Existing main tests pin labels, label-AND/OR, globs, case-insensitive contains and date filters. Existing `--max-rows` tests expect explicit overflow rather than silently presenting an incomplete result. [internal/storage/sqlbuild/ready.go:47–67](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/sqlbuild/ready.go#L47-L67) [internal/storage/issueops/ready_work.go:48–74](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/ready_work.go#L48-L74) [cmd/bd/list_test.go:576–698](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/list_test.go#L576-L698) [cmd/bd/ready_max_rows_test.go:21–145](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/ready_max_rows_test.go#L21-L145)

Counterexample: 100,000 eligible Issue records sorted by canonical URI, requested `ready --limit 1 --sort priority`; the best-priority oldest winner can be on the final URI page. A client that stops after its output-size page is wrong. The general guaranteed strategy fetches all eligible candidates and relevant graph state, regardless of K=1. Priority equality queries can split finite P0–P4 buckets and improve some cases, but oldest/hybrid ordering and readiness still require scanning the winning candidate bucket; they do not establish an efficient general implementation. No claim is made that providers cannot index scalar selectors—only that the wire lacks needed query shape.

Blocked state is particularly deep: waits-for can mean all children or any child, optionally also requiring the spawner itself to close. Source already documents a 50k-Issue/100k-edge case where poor joins made one close take ~39 seconds. Shipping all this work over HTTP per invocation is a material regression. [internal/storage/issueops/blocked_state.go:23–120](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/blocked_state.go#L23-L120)

Recommendations to compare: (a) generic ordered/projection/count/string query capabilities and bounded graph predicates; (b) a mandatory client replica/query engine consuming transactional snapshot+changefeed; (c) both, with explicit small-scope fallback. Do not implement Issue-only search/readiness endpoints. A warm replica solves data access and repeat-query latency, not mutation race guards.

### 2. Atomic batches help, but readset validation needs explicit design

Closing a parent checks both open children and live direct blockers. Existing main uses dependency-coordination writes to conflict with a concurrent new child edge; the target Issue revision alone cannot prove the child set stayed fixed. BDP likewise says an ordinary new Link does not change either endpoint revision, and an owned Link changes its source only. An incoming child->parent edge therefore does not update the parent's revision. [internal/storage/issueops/close.go:131–173](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/close.go#L131-L173) [docs/specs/bdp.md:1038–1043](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1038-L1043)

Counterexample: client reads “no open children,” another client attaches open C to P, first client performs only `updateBeadProperties(P,expectedRevision=P_old,status=closed)`. The guard can pass. Atomically batching that one update with unrelated writes does not repair the missing predicate.

A bounded BDP-native plan is possible:

1. Read relevant relationship set and endpoint state, evaluate policy locally.
2. At the start of batch use `deleteWhere` with cardinality `{max:0}` selecting newly appeared prohibited relationships (e.g. incoming child Links not in the observed known-ID set). Zero selected means no deletion; a nonzero set fails the whole transaction.
3. Guard observed resource revisions with same-value explicit updates where authorized, or use zero-match assertions against changed relevant scalar properties; ensure missing/deleted counterparts are also handled by required cardinality/liveness, not only negative predicates.
4. Apply close patch with expectedRevision. Keep all guards before dependent writes.

The zero-match guard is an inference from normative set-selection/cardinality semantics, not a dedicated advertised assertion feature. A conformance vector should test it before using it as the SDK foundation. Exact-member validation requires more than just matching the old count: replacement/removal can preserve cardinality. Pin-transparent endpoint matching is available as collection parameters, but `deleteWhere` has only Selector; selectors must explicitly account for string and pinned-reference endpoint representations if the chosen pack admits both. [docs/specs/bdp.md:1586–1661](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1586-L1661) [docs/specs/bdp.md:4955–5032](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L4955-L5032) [docs/specs/bdp.md:803–824](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L803-L824)

For a large traversal this expands into O(readset) revision operations and/or O(readset) selector clauses; limits may make the atomic plan inadmissible. Same-value updates require write authorization on read-only dependencies. Negative selectors observe the Authorization View, not hidden graph state. A client cannot enforce a global Issue policy it cannot observe. This is a **compact predicate/assertion and visibility contract gap**, not proof that every small graph operation is impossible. [docs/specs/bdp.md:904–953](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L904-L953)

A model mapping may intentionally orient a relationship so the guarded aggregate is the source and owns those Links; then a source revision guard covers its outgoing membership. That can eliminate the incoming-child phantom for that chosen mapping. It does not automatically guard the changing status of independently mutable target Beads, transitive reachability, unrelated competing queue candidates, or an arbitrary legacy child-to-parent representation. Treat ownership direction as an architectural input, without deciding Type lifecycle in this audit.

A pack-owned “graph generation” Bead can serialize cooperative graph writers: everyone guards and bumps it in each batch. This is a useful implementation option but a hot spot, broad retry source, and only safe when every writer follows the discipline. Generic clients bypassing it can still create Links. Whether Issue constraints are pack-client guarantees or authoritative scope invariants is a product boundary decision; no Issue-specific provider code should be needed in either case.

### 3. `ready --claim` is two separate problems: one winner and choosing the right winner

An expectedRevision update or exactly-one scalar set update gives one winner for a known candidate. It does not choose the first ready candidate with the full current graph predicate. `updateWhere` with cardinality `{max:1}` on a pool does not choose one—if two match, it fails; there is no mutation limit/order. Batch labels do not bind query results. Current ready-claimer contracts explicitly require front-row selection, filter parity, correct counts/dependencies, lease behavior, and one history entry. [internal/storage/dolt/ready_claimer_contract_test.go:10–76](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/dolt/ready_claimer_contract_test.go#L10-L76) [internal/storage/issueops/claim_next.go:45–72](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/claim_next.go#L45-L72) [docs/specs/bdp.md:997–1017](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L997-L1017)

Candidate scan + guarded claim + retry can preserve single ownership and eventual progress; strict front-of-queue-at-commit semantics require guarding competing candidates and predicate dependencies, or a generic ordered conditional selection facility. Contending workers choosing the same cached first row can cause O(workers) conflicting attempts and stale scans. Test both selection semantics and contention, not merely final assignee uniqueness.

### 4. Multi-ID close has partial failure *inside* an atomic unit

Main `ExecuteCloseBatchWithPolicy` records each per-ID error, continues successful closes, then claims next in the same SQL transaction if any close landed. It also uses close-policy/savepoint machinery. BDP batches abort on any failed operation; sequences commit each separately and cannot bind a next candidate query. [internal/storage/issueops/close_batch.go:123–175](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/close_batch.go#L123-L175) [internal/storage/issueops/close.go:68–138](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/close.go#L68-L138) [docs/specs/bdp.md:1246–1284](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1246-L1284)

Client preflight can exclude known failures and batch successes, but a race can invalidate the accepted set and force a whole retry. It cannot atomically discover and report arbitrary policy failures, skip them, and choose the next task without representing the conditions. Possible decisions: preserve semantics through generic conditional/assertion primitives; accept guarded preflight with bounded retries and carefully specified per-item outcomes; or intentionally change command atomicity. A sequence is not a transparent replacement.

### 5. Notes and labels show why representation matters before adding operations

`--set-metadata a=1` maps directly to JSON Patch add on `/metadata/a` once the object exists; independently added keys survive. String `--append-notes` cannot use array append `/-` while keeping current scalar notes shape. It needs guarded read/modify/write. Existing concurrency tests specifically assert every successful append remains and every successful metadata key survives. [cmd/bd/update_proxied_integration_test.go:1518–1648](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/update_proxied_integration_test.go#L1518-L1648)

For labels, `{"labels":{"bug":true}}` permits exact Selector membership and independent key changes. Array labels require read/modify/write for removal/deduplication and cannot push arbitrary membership through singular-path selectors. Link labels scale representation separately but turn common label filtering into a join and need duplicate protection. Current tests demand idempotent duplicate add and no-op absent removal. None of these forces an Issue endpoint; these are pack model choices with measurable tradeoffs. ### 6. Dependencies and deletion expose bounded-operation and invariant limits

Bulk dependency tests require applying hierarchy edges before blocking edges, rolling back a newly induced scheduling cycle, and allowing unrelated additions despite an already existing cycle. A blanket generic “graph must be acyclic” rule would itself be incompatible with the third case. BDP only defines optional endpoint maximum multiplicity; acyclicity and tuple uniqueness are explicitly deferred. Client preflight + guarded atomic create is viable at bounded scale; the exact policy is nuanced and belongs in the pack unless generalized as declarative constraints. [cmd/bd/dep_bulk_role_test.go:24–182](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/dep_bulk_role_test.go#L24-L182) [docs/specs/bdp.md:563–614](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L563-L614)

Deletion is more than cascade Link cleanup: current code traverses all dependents for cascade, discovers neighbors before removing relationships, rewrites their descriptions to mark deleted references, and commits it together. BDP supports guarded client-generated patches and links-first deletion. It cannot compute textual replacements or traversal in the batch, and it cannot split a transaction above limits without changing semantics. Never report a dry-run plan as protected merely because the eventual operation is atomic. [internal/storage/issueops/delete_role.go:13–186](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/internal/storage/issueops/delete_role.go#L13-L186) [docs/specs/bdp.md:1057–1081](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1057-L1081) [docs/specs/bdp.md:1633–1650](https://github.com/gastownhall/bdp/blob/182f1fcf8a01d896976bff3c9e3fb87c596c6ca6/docs/specs/bdp.md#L1633-L1650)

## Recommended portable Issues-pack acceptance matrix

These are proposed future executable conformance scenarios derived from existing tests; they were not run during this audit.

1. Two independent providers load the same pack with no Issue-specific server code. All scalar CRUD, parent/dependency creation, comments and exact labels agree.
2. Eight clients claim one task: one winner; same-actor retry preserves first started_at; pool and custom-status rules match.
3. Concurrent append notes / set metadata: every successful writer's result survives; exhausted contention is a loud error.
4. Concurrent attach-child versus close-parent: no close accepted from a stale empty-child read; repeat for reopening a blocker and for incoming unowned Links.
5. Bulk hierarchy plus reverse scheduling dependency rolls back; unrelated pre-existing cycle remains allowed.
6. Late-canonical-URI top-priority item, deep parent descendants, any/all-child gates, and hidden incident Links challenge read correctness.
7. Label AND/OR, absent labels, idempotent adds/removes, and glob/contains searches return identical semantic results across representations.
8. Multi-ID close with one refused target and claim-next: pin intended atomic and error semantics explicitly before implementation.
9. Delete cascade plus neighbor text rewrite rolls back together on an injected guard or limit failure; dry run never mutates.
10. Formula instantiation creates all references atomically; over-limit plan fails before claiming success; no silent atomicity downgrade.
11. Wisp squash preserves identity and makes root durable; heartbeat history/log volume has an explicit accepted contract.
12. Cold and warm performance at 50k/100k and 1M/2M Beads/Links: measure bytes, request count, latency, local disk, conflict retries, replay recovery, and authorization-view reset. Publish a target budget, rather than accepting “it can be done” as efficiency evidence.

## Supplementary duplicate and command-root contract pass

### Exact duplicate grouping, fuzzy scoring, and auto-merge

`duplicates` fetches all Issues, uses non-closed Issues as duplicate candidates, and groups by exact `(title, description, design, acceptanceCriteria, status)` values. It uses all fetched Issues for regex text-reference counts, including closed Issues: description, design, acceptance and notes are scanned for the current numeric-suffix ID pattern. The actual winner ranking is **3 × dependent count + dependency count**, then text-reference count, then lexical ID; command help's shorter reference-count description omits the structural first criterion. Tests explicitly preserve the Issue with children even when an alternative has more text references. [cmd/bd/duplicates.go:46–82](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/duplicates.go#L46-L82) [cmd/bd/duplicates.go:196–330](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/duplicates.go#L196-L330) [cmd/bd/duplicates_test.go:89–226](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/duplicates_test.go#L89-L226)

Generic plan: retrieve full Issue pages, hash the exact tuple locally, scan text locally, and retrieve incident dependency Links for duplicate-group members to compute the existing count semantics. Let `T` be total text bytes, `G` duplicate-group members, and `E_G` their relevant edges. Network cost is `ceil(B/P)` Bead pages plus approximately `ceil(E_G/P)` Link pages when bounded OR endpoint selectors fit; otherwise multiple selector batches or per-member endpoint requests. Local grouping/reference extraction is O(B+T), graph counts O(E_G), group winner selection O(G). Exact tuple selector queries can answer “find matches for this known Issue,” but do not discover all duplicate groups without scanning because BDP has no grouping/aggregation. A pack-maintained content-hash property can improve targeted matches but requires every writer to keep it current and does not provide all-groups aggregation.

Auto-merge is a graph transform: reparent each source's children to the target (delete old parent Link, create replacement), close source with duplicate reason, and add `related` Link. Current code records per-step errors and continues; it is not one all-or-nothing group transaction. A bounded atomic BDP batch is possible after graph/policy preflight, but intentionally strengthens current failure semantics. Alternatively preserve per-source partial results with separate batches. Immutable Link endpoints require delete/recreate, already the current logical operation. [cmd/bd/duplicates.go:374–452](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/duplicates.go#L374-L452) [cmd/bd/duplicates_test.go:352–430](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/duplicates_test.go#L352-L430)

`find-duplicates`/`find-dups` compares title+description only. Tokenization lowercases Unicode, separates on nonletter/nondigit characters except hyphen, drops tokens with byte length ≤1, and retains frequency. The actual mechanical score is **the average of multiset Jaccard and cosine similarity**, not plain Jaccard. It pretokenizes then compares every unordered pair, accepts score ≥ threshold, sorts pairs by descending score, and only then applies output limit. Tests cover duplicate token counts, case/punctuation, hyphens, single-character filtering, empty sets, both similarity functions, thresholding and insufficient input. Generic plan: push status to a Selector, page complete Beads, and run exactly the same algorithm in the Rust pack. For B Issues and average U unique tokens, local comparison is O(B²U); pair storage and sorting can be O(B²) and O(B² log B) respectively in dense-match cases. `--limit 20` does not bound comparison work. Required BDP requests are `ceil(B/P)`, with no server pairwise/fuzzy computation needed. A local inverted index or bounded exact top-K heap can reduce work/memory, but candidate pruning must preserve the existing threshold contract; do not call an approximate nearest-neighbor replacement equivalent without a product decision.

AI mode mechanically prefilters at `max(threshold/2,0.15)`, keeps at most the top 100 candidates, sends groups of 10 to an Anthropic-compatible client, and filters returned scores at the requested threshold. It truncates descriptions to 500 bytes in the prompt and falls back to mechanical candidates on request/format failures. This means at most 10 AI batch calls at the application layer, in addition to BDP reads; SDK/network retries are additional. AI is a client integration with its own credentials and data-sharing policy, not a BDP provider feature. This audit read the code and tests; it sent no AI request. ### Creation identity contract

BDP explicitly supports both client-supplied and authority-allocated IDs. `CreateBead(id?,type,...)` omits `id` for allocation; a supplied ID's canonical URL must never previously have been committed for any Resource in the logical Scope. Deletion does not permit reuse. The normative schema `createBeadMembers` requires `type` and has optional `id: durableResourceReference`. This enables batch creation of known hierarchical child IDs with a separately guarded counter, subject to collision/nonreuse handling.
