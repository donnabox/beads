## Findings

### 1. Duplicated capture-bound formula and length-probe SQL across the two private stores — no shared constant
**Severity:** Medium (maintainability / silent divergence)
**Location:** `packages/server/src/development-authority.ts:186-191` vs `packages/server/src/transaction-store.ts:205-211`; probe SQL `packages/server/src/recovery-store.ts:643-645` vs `packages/server/src/transaction-store.ts:470-474`
**Impact:** The 142,610,432-byte ceiling is written out twice as `8 * CONTRACT_ARTIFACT_CEILINGS.totalBytes + 1024 * CONTRACT_ARTIFACT_CEILINGS.submittedArtifacts + 4096`, under two local names (`maximumCaptureBytes` / `captureMaximumBytes`), with two refusal messages, and neither site cross-references the other. The identical `SELECT length(CAST(value AS BLOB)) …` string is likewise duplicated. The arithmetic is sound today (worst case ≈ 6× URI escaping + 4/3× base64 + ~154 B/entry ≈ 124.3 MB against a 142.6 MB bound), but the 8× / 1024-per-entry factors encode an *assumption* about JSON escaping and entry overhead. A future correction to that assumption applied in one lane leaves the other with a stale, possibly unsound bound, and nothing fails. The two protocols also already differ in substance: TX compares the stored length against the ceiling (`> captureMaximumBytes`), RU against the exact expected length (`!== captureBytes`) — so "the same check" is not the same check.
**Fix:** Export the bound (e.g. `CONTRACT_CAPTURE_MAXIMUM_BYTES`) from `installed-contract-artifact.ts`, which already owns the ceilings and is already imported by both authorities, and consume it in both. If the one-line TX edit is outside this lane's ownership, at minimum add a cross-reference comment at `development-authority.ts:183` naming `transaction-store.ts:205` as the twin, and file the consolidation.

### 2. Missing `contractCapture` row is reported as `store-mismatch`, not corruption
**Severity:** Low-Medium (operator misdiagnosis; deviates from the plan's own wording)
**Location:** `packages/server/src/recovery-store.ts:643-647`; oracle at `packages/server/src/development-retention.test.ts:160-161,188`
**Impact:** The plan states "missing row is corruption, not absence" (`read-update-artifact-retention-plan.md:21`). Every other mandatory metadata row behaves that way — `meta()` raises `RecoveryStoreError("integrity", "missing store metadata: <name>")` at `recovery-store.ts:368-372`, and `meta("format")` at `:632` inherits it. The capture row instead short-circuits on `storedCaptureBytes === undefined` and reports `store-mismatch` / `"installation capture mismatch"`, which tells an operator their *configuration* does not match the store when in fact the store is missing a mandatory row. That misroutes the response (re-point configuration / re-provision vs. restore from backup). The row-present vs. row-absent cases are trivially distinguishable here, and the new test bakes the mismatch classification in.
**Fix:** Split the probe: `if (storedCaptureBytes === undefined) throw new RecoveryStoreError("integrity", "missing store metadata: contractCapture")`, keeping `store-mismatch` for a present-but-different value. Assert the two distinct reasons in the `missing-capture` vs `capture` subcases.

### 3. `openRecoveryStore` has no absolute ceiling on `contractCapture`; the bound lives only in its single caller
**Severity:** Low (residual, deliberately chosen by the plan)
**Location:** `packages/server/src/recovery-store.ts:296-301, 643-647`
**Impact:** `requireText` imposes no byte bound, and the stored-length check is *relative* (`storedCaptureBytes !== captureBytes`). It rejects mismatched sizes but not oversized ones when the expectation is itself oversized — so "bounded metadata serialization before load" rests entirely on `development-authority.ts:190`, the one production caller. The sibling `transaction-store.ts:477` guards the same property at the store layer with the same constant. A second production caller, or a caller-side regression, would have the store insert and later materialize an unbounded metadata value. This matches the plan (H3/M5: "the expected capture is already bounded by the authority"), so it is a residual rather than a deviation — but it is an asymmetry with the twin store that costs one comparison to close.
**Fix:** Add `if (captureBytes > CONTRACT_CAPTURE_MAXIMUM_BYTES) throw …` in `openRecoveryStore` once the constant moves per finding 1 — no compiler import needed.

### 4. No committed test opens a real format-3-shaped store; the only real predecessor check is an out-of-tree script
**Severity:** Low (coverage, not a live defect)
**Location:** `packages/server/src/recovery-store.test.ts:1084, 1121`; evidence `bdp-integration-logs/read-update-artifact-retention/predecessor.mjs`
**Impact:** Both in-repo format fixtures synthesize `format='1'` / `'2'` on a **format-4-shaped** store, which retains the `contractCapture` row. The distinguishing shape of an actual format-3 store — format row `'3'` **and no capture row at all** — is never opened by any committed test. Meanwhile `STATUS.md:48-50` now carries a user-facing compatibility claim ("Format 4 … also rejects existing nonattesting development-facade stores"). The real bidirectional verification exists and passes (`predecessor.log`: `actualFormat3To4/4To3`, `byteIdentical`, `pendingPreserved`, exit 0), but `predecessor.mjs` hardcodes absolute paths into two sibling worktrees' `dist/` and can never run in CI, so the next format bump has no in-repo guard.
**Fix:** Add a fixture alongside the `'1'`/`'2'` cases that sets `format='3'` *and* deletes the `contractCapture` row, asserting `store-mismatch`, byte-identical main file, and the pending claim intact.

### 5. Stale format reference left in source after the bump
**Severity:** Low
**Location:** `packages/server/src/member-identity.ts:387-388`
**Impact:** Still reads "Recovery-store format 3 is the compatibility boundary for those bytes: prior formats are refused before recovery, never reinterpreted or rewritten." Format 3 is now itself refused; format 4 is the boundary. Both `STATUS.md` mentions were updated, this one was missed — it is the only remaining stale reference in tracked source. A maintainer reading it would conclude format-3 stores still carry the `revisionProvenance` bytes forward.
**Fix:** Change "format 3" to "format 4".

### 6. `STATUS.md` byte-preservation claim is unqualified where the progress doc qualifies it
**Severity:** Low (doc consistency)
**Location:** `STATUS.md:46-47` (paragraph edited by this commit) vs `docs/design/update-implementation-progress.md:627`
**Impact:** STATUS.md says "The refusal preserves existing bytes and cannot silently reseed an existing database." The progress doc correctly carries the qualification: "a recovered journal can restore physical bytes before refusing BDP startup" — exactly the case the new `recovery-store.test.ts:1642` test exercises. As edited, the top-level claim surface promises byte preservation on *every* refusal, which the code cannot provide once SQLite rolls back a hot journal before metadata is readable.
**Fix:** Carry the one-clause qualification into the STATUS.md paragraph the commit already touched.

### 7. Corruption-test oracle cannot tell which gate fired
**Severity:** Low (weak oracle)
**Location:** `packages/server/src/development-retention.test.ts:188`; same pattern in `native-same-length.mjs`
**Impact:** All 14 corruption subcases accept `/capture mismatch|inventory mismatch/`. A regression in which a Type-row corruption reported a capture mismatch (or vice versa) passes. The ordering assertions (pending row preserved, bytes identical) are the test's real value and are sound; only the message discrimination is loose.
**Fix:** Map each corruption key to its expected message.

## What I verified as correct

- **Bounded serialization before load** — `recovery-store.ts:643-645` probes `length(CAST(value AS BLOB))` and `||` short-circuits before `meta("contractCapture")` materializes the text. UTF-8 byte accounting is right (SQLite UTF-8 DB, `CAST … AS BLOB` yields encoded bytes), and the `"é"` vs `"x"` test with a `StatementSync.prototype.get` tripwire genuinely proves the fetch is not reached. No capture JSON CHECK was added, so `quick_check` does not parse the payload; `expectedTables` is unchanged.
- **Explicit null absence** — `"null"` sentinel on both the built-in authority path (`development-authority.ts:185`) and the store default (`:297`); the row is always written at creation (`:592`). No collision with a real capture, which always serializes to `{…}`. Captured-store-without-expectation refuses, so the default is not a bypass.
- **Complete supplied inventory including built-in** — `expectedTypes` is passed unconditionally at `development-authority.ts:194`; the built-in `types` map is now frozen at `:108-110`, configured `contracts.types` was already frozen. `count(*)` equality plus per-expected-id body compare is exactly set-and-bytes equality (PRIMARY KEY makes duplicates impossible), so missing / extra / ID-swap / changed-body are all caught — `native-same-length.mjs` covers the equal-count ID-swap case. `Object.keys(installedTypes).length === installedDescriptors.length` holds by construction (`descriptor.id !== uri` refuses at `installed-contract-artifact.ts:378`, URIs are unique map keys), so replacing the removed `visitInstalledTypes` loop with `new Set(Object.keys(installedTypes))` loses nothing.
- **No mutable policy changes** — capture holds only `artifacts` + the three limit witnesses (`development-contracts.ts:138-143`); no access, authentication, credential or principal identity. Confirmed by grep that the only `metadata` writes are the parameterized `nextRevision`/`nextIdentity` updates and the `format` touch, and `installed_types` has no post-creation write path, so neither is reachable from a member transaction. Policy writes stay in the `policy` table (`recovery-store.ts:870`). Installation/lineage identity stays compact.
- **Option snapshotting** — `isProxy` on both the options object and the inventory, own-data-descriptor checks, symbol/non-string rejection, `Object.create(null)` snapshot then freeze, all at `:288-327` — **before** `mkdirSync`/`openSync` at `:348-355`. The test's `hooks === 0` plus `existsSync === false` assertions are real.
- **Ordering** — capture/inventory gate at `:641-656` sits inside `BEGIN EXCLUSIVE`, after the format/Scope/installation/lineage check, and before `DELETE FROM key_state WHERE state='claimed'` at `:674`, the `format` touch, and `COMMIT`. Hot-journal rollback necessarily precedes it (first page read is the `journal_mode` pragma at `:578`, after function registration). Refusal path closes the DB, rolls back, and only unlinks a file this invocation created uncommitted. The new `mode==="hot"` child harness (tiny cache + 40 × 18 KB spill + SIGKILL at the COMMIT barrier) produces a verified rollback-journal magic, and the test confirms SQLite recovery happens *without* a BDP claim sweep on refusal, then two claims recovered on the valid open.
- **Residual post-open checks** — the Resource-Type scan (`development-authority.ts:207-212`) and `assertReadUpdateRuntimeCompatibility` (`:215`) remain after `store.expire(clock())` (`:213`). Code comment, progress doc, and report all say so explicitly and do not claim a universal startup-ordering repair. The authority's `catch` (`:341-344`) closes the owner or the store; `development-runtime.ts:551-554` closes the listener before any `ready`, so the new refusal class leaks nothing.
- **Determinism** — capture text is stable across restarts: artifacts are deduped and sorted by URI bytes (`installed-contract-artifact.ts:405`), limit objects are fixed-order frozen literals, and `stringifyJsonValue` preserves `Object.keys` order with `JSON.stringify` scalar formatting. `snapshotJsonValue` rejects unpaired surrogates, so `requireText(…).isWellFormed()` can never fail on a legitimate capture. Reordering the input bundle changes neither identity nor capture.
- **Offline reconstruction** — genuinely proven twice: `development-retention.test.ts:233-259` reconstructs from the persisted base64 through `compileDevelopmentContracts`, asserts identity equality, confirms raw whitespace-preserving bytes differ from canonical `installed_types`, and reopens the authority with the reconstructed contracts; `packed/retention-probe.mjs` repeats it against the packed install over real IPC-launched HTTP, verifies `format='4'` on disk, checks hosted schema GET/HEAD bytes, restarts on a different listener port under a stable Scope, and replays both the success and failure dispositions. Capture is unchanged after deletion and receipt expiry (`:266-270`).
