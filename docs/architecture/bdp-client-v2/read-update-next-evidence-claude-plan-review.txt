## Findings

### 1. HIGH — The plan's own constraints make the independent-GET oracle and its negative control mutually unsatisfiable

**Location:** plan lines 53, 75, 78, 87 · `packages/conformance/src/runner.ts:801-817` · `apps/bdptest/src/read-update-matrix.test.ts:375-376` · `apps/bdptest/test-support/read-update-exact-client.ts:51-56`

`runner.ts:801-817` dispatches `family:"http"` to `runRequest(..., execute, ...)` and only non-http families reach `actionExecutor`. In the app test, `actionExecutor` (`:375-376`) is the *only* place the counterfactual layer wraps anything — it wraps `executeClient`. So every GET authored as `family:http` is structurally unreachable by the response-corruption layer.

Plan line 53 prefers exactly that form ("fixed `family:http` actions with `target:{binding:"beads",path:"..."}` for authored IDs") and in the same sentence forbids the alternative ("do not add fixture bindings solely for these paths"), while line 78 forbids editing the raw executor. The three available mechanisms each violate one constraint:

- `family:http` + `{binding:"beads", path:"…"}` — works, but control line 75 ("corrupt one independent final GET to the replay's old postimage") cannot be applied, and it mutates the route set.
- `family:client` + new fixture binding — the only counterfactual-reachable form (the shipped `w2ReadControl` dispatches on `targetBinding === "w2.beads.w2-independent"` / `"w2.beads.w2-count-0"`, both fixture bindings), but forbidden by plan line 53.
- `family:client` + captured ID — reachable and route-free, but **cannot express a provably-absent Bead**: `targetBinding` must name an existing binding (`read-update-exact-client.ts:51-56`), and a never-created F has nothing to capture.

Row A step 5 ("Prove absence first") and step 6 therefore have no satisfying form at all. The repo's established idiom for this is a dedicated fixture binding — `http.absent → beads/http-never-created`, `w1.missing-link`, and 13 more `w2.beads.w2-{missing,unknown-*}` entries — used precisely by `family:client` 404 reads.

**Impact:** Row A steps 5-6 are unauthorable as written; the line 75 control and row B step 4's GET assertions are undiscriminated. An author following line 53 literally ships GET oracles with no sensitivity control, which is the exact failure mode the controls section exists to prevent.

**Fix:** Drop the "do not add fixture bindings solely for these paths" prohibition. Declare the handful of bindings for the authored A/B/F paths (following the `w2.beads.*` naming), author every independent GET as `family:client` so it lands in the counterfactual layer, and add `packages/conformance/fixtures/read-update-reference-v1.json` as a fourth expected-edited file. The fixture digest is computed dynamically everywhere (no literal pin), so this is mechanically safe.

### 2. HIGH — Row B step 3's headline assertion is not expressible in the assertion vocabulary

**Location:** plan lines 59, 62 · `packages/conformance/src/runner.ts:2111-2141` (esp. `:2113-2114`)

`json-array-tuples` throws `"array tuple projection was absent"` if **any** projected pointer is missing from **any** array item. Row B deliberately mixes named and unnamed members and success and failure members, so neither `/operationName` (optional — `sequenceMemberResult.required` is `["operationIndex"]` only) nor `/outcome` vs `/code` (mutually exclusive) can be projected across the results array. "Assert **the entire ordered index/name/outcome-or-code array**" as one assertion cannot be written.

Whole-array `equalsBinding` — the mechanism that makes the shipped `retained-results` control catch an injected `detail` — is also unavailable here, because row B's positions, order, and length all lawfully differ from the original. The shipped precedent confirms the shape of the workaround: `retained-bindings/indices` projects `/operationIndex` *alone*, and `sequence.member-problem-shape` uses per-member `json-pointer` assertions (`name-0`…`name-4`, `index-1`, `index-5`) for exactly this reason.

**Impact:** The plan's assertion design for its primary novel observation is unimplementable without a runner change, which plan line 87 forbids. It also leaves plan line 62 ("compare every actual non-positional field … do not silently narrow equality to `code` alone") with no available mechanism for the retained *failure* member, whose positional and non-positional fields are siblings — leaving field enumeration (`code`/`status`/`type`/`retry` + `detail exists:false` + `outcome exists:false`) as the only route, which is weaker than deep equality.

**Fix:** Restate step 3 as the decomposition that actually exists: one `json-array-tuples` with `ordered:true` projecting `/operationIndex` only (this also pins exact length, `runner.ts:2163-2165`), plus per-member `json-pointer` assertions for each `operationName` presence/absence, each `outcome`-or-`code`, each retained `resource` via `equalsBinding` against the step-1 capture, and an explicit `/detail exists:false` on the failure member. State that `detail` is accounted for by asserted absence — the installed authority never emits it (`member-executor.ts:116-131`), though `readUpdateProblem` permits it.

### 3. MEDIUM — The evidence-gap statement is factually wrong; installed cross-carrier evidence already ships

**Location:** plan line 14 · matrix `read-update.sequence.local-bindings` actions `retained-bindings`, `dependent-key-conflict`, `conflict-unchanged`

The plan asserts "Existing installed evidence only exercises same-carrier singleton replay and some retained failed local bindings." It does not. Key `blocked-dependent` is presented as a **sequence member** in `retained-bindings` (retained `binding-unavailable` failure) and then re-presented as a **singleton** in `dependent-key-conflict` with a different operation record, asserting HTTP `409` and `code: "idempotency-conflict"`, with `conflict-unchanged` proving the live record was untouched. That is cross-carrier outcome 2 (`bdp.md:3289-3291`) over installed HTTP, with negative controls already attached.

**Impact:** Row A steps 3 and 4's changed-input-conflict halves substantially duplicate shipped evidence, so the slice's actual novelty is narrower than claimed: cross-carrier *replay* (outcome 1), cross-carrier retained-*failure* replay, and positional reprojection. Worse, the plan's own anti-credit discipline (line 40) is violated in the opposite direction — the new coverage `reason` prose, written from line 14, would overstate the delta. The existing omitted `reason` ("cross-row observations do not award this required ID whole-contract credit") is in fact the accurate framing and the plan contradicts it.

**Fix:** Rewrite line 14 to name `sequence.local-bindings/dependent-key-conflict` as existing installed cross-carrier conflict evidence, and restate the gap as cross-carrier retained-success replay, cross-carrier retained-failure replay, and positional reprojection. Carry that wording into the new coverage `reason` fields.

### 5. MEDIUM — Two `exactConfigurationDigest` pins must move together, not one

Both pin `bdffd6f957401222f6e5ffc928c7769d23976e8a8a8d5eb16dfa1bb7ce836a07`; those are the only two occurrences in the repo. `exactConfigurationDigest` hashes `routes` (`runner.ts:1362-1379`), and `readRoutes`/`clientReadRoutes` are derived from `bundle.manifest.scenarios` — the full matrix, independent of `scenarioSelection` (which is why the single-scenario test at `:1191` yields the same digest as the 43-scenario run).
