**2 — Blocker. C's post‑close probe is unsatisfiable as written.**
Plan C step 4: *"then one post-close **real owner** probe rejects"*, with step 3 forbidding `inspect()` and a delegate probe.
Source: `transaction-store.ts:987‑993` — after close, `withRead` **returns** `{kind:"entry-refused", reason:"not-accepting", cause}`; it does not throw or reject. Only `inspect()` throws (`:2342‑2343`, used that way at `transaction-service.test.ts:1719`), and the plan bans it.
Smallest correction: state the post‑close oracle as `owner.withRead(() => true)` returning `kind:"entry-refused"` with `reason:"not-accepting"` (symmetric to the live `kind:"read"` probe), or explicitly permit the rejection to come from a post‑close *service* call instead.

**3 — Blocker. Installed cohort accounting omits an existing sibling callback in the owned file.**
Plan: *"Installed validation is two separate supervised cohorts: amended historical22 and new37 =59HTTP,2 owned stores/2 sequential children"*; `workload.json` repeats `cohorts:[22,37], http:59, stores:2, children:2`.

I verified `:634` is *unaffected* by the production change (receipt **root** only, opaque + current context → already 503; no page row, no foreign‑opaque row), so this is an accounting/reporting defect, not a behavioural one.
Smallest correction: say the installed runs are title‑filtered to the two cohorts, and record that the unchanged 5‑exchange sibling (same file, bytes changed by the append) is covered only by the later full exact‑head CI.
