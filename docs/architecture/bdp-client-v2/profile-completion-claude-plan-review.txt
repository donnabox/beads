# 2. Findings

### F1 — BLOCKER: no slice produces an installed configuration that can advertise a write profile

- **Location/evidence:** `apps/bdptest/src/server-composition.ts` composes `createReferenceFixturePort` (immutable, `@bdp/adapter-in-memory`) and calls `admitReadServerProfile(config.server.advertisedProfile, "bdptest")`. `packages/server/src/index.ts:271` types `AdmittedReadProfile.profile` as the literal `"read"`; `index.ts:307` refuses any other value. The mutable SQLite owner is `packages/server/src/development-authority.ts`, reachable only through `development-runtime.ts` — a *separate* `node:http` server with its own routing, a 32–256-char bearer token on every request, `x-bdp-development: non-attesting` on every body, mutation targets at `/development/<name>`, and the explicit comment at `development-runtime.ts:186` "No service-desc or BDP discovery profile".
- **Impact:** U1→U3 and T1→T4 can each satisfy their Done-when predicates in full and still leave zero installed services able to advertise `read-update`. The plan's own goal sentence (design.md:11) is unreachable from the slice list. The paused U1 branch makes this concrete: the authorized composition plan builds canonical discovery "only in a disposable source-test receiver" (design.md:124).
- **Fix (required implementation, root-owned, must precede U1):** add a slice "installed mutable reference payload" — durable `recovery-store` seeded from `@bdp/protocol` `reference-domain.ts` with the ten `https://work.example/types/*` descriptors passed through `create: { types }`; `operations/` and `alias/` mounted inside `createReadServer`'s routing (not a second listener); `advertisedProfile` plumbed from `@bdp/config` (which already accepts all three profiles, `packages/config/src/index.ts:376–379`) into `discoveryFor` (`index.ts:1527`); admission widened to a per-profile record. Then retarget U1 at that composition.

### F2 — BLOCKER: the cumulative Read+Update required set contains a Read row the profile contradicts, and a passing test pins it

- **Location/evidence:** `read.discovery.document` cites "These are the only members admitted by the closed `readDiscovery` definition". `schemas/bdp-v0.schema.json` → `readDiscovery` has `profile: {"const":"read"}` and `additionalProperties: false`. `docs/specs/bdp.md:3779` marks `operations` *prohibited* in Read and *required* in Read+Update. `read-update-v1.json` declares **zero** `retires` members, while `transactional-v1.json` declares 12 — including `transactional.discovery.document → read-update.discovery.document`, i.e. the exact analogous retirement one level up. `packages/conformance/src/transactional-catalog.test.ts:170` asserts `[...retiredScenarioIds(combined, "read-update")]` equals `[]`.
- **Impact:** against a genuinely RU-advertised target this row must fail. `pass` is the only admissible state for an applicable row and `fail` closes the cohort for all targets (`matrices/README.md` §"Required set and admissible state"). It cannot honestly be N/A — discovery is always served. Read+Update is therefore unqualifiable as the catalogs stand, independent of any runtime work.
- **Fix:** add `retires: ["read.discovery.document"]` to `read-update.discovery.document`; audit `read.discovery.optional-limits` the same way (RU's `limits` validates against the different closed `readUpdateAdvertisedLimits`); update `transactional-catalog.test.ts:170` to the new expected set. Leave `read.alias.absent` alone — it is already gated by `alias-absent-v1` and correctly recorded N/A for bdptest in the committed artifact.

### F3 — BLOCKER: five required Read+Update obligations are dropped by the only documented composition rule

- **Location/evidence:** `read-update.owned-wildcard.explicit-precedence`, `read-update.owned-wildcard.undeclared-type-versions-source`, `read-update.numeric-model.same-value-no-op`, `…round-trip-admission`, `…nested-refusal` exist **only** in `owned-wildcard-v1.json` / `numeric-model-v1.json`. `matrices/README.md` §"Write-profile catalog composition" says to combine "the Read, Read+Update and Transactional scenario arrays"; `transactional-catalog.test.ts:164–167` combines exactly those three. Meanwhile those two companion files duplicate six Read-profile IDs already in `read-v1.json`, so naive concatenation throws on the unique-ID check in `catalog.ts` (`scenario identifier … must be unique`). `development/read-update-coverage-v1.json` inventories "all 81 current normative catalog rows" — the real delta is 86.
- **Impact:** a composed RU/TX bundle silently omits five required obligations, and the one documented inclusion path cannot be executed literally without a parse error. The coverage denominator ("58 of 81", design.md:115) is wrong by construction.
- **Fix:** move the five RU rows into `read-update-v1.json` and make the companions pure views of the canonical files (or publish a dedup-and-include composition rule with a test that builds all three cumulative bundles). Re-base the coverage inventory on 86.

### F5 — HIGH: the evidence gate cannot detect a changed installed configuration, and its allowed delta is a hole for write constants

- **Location/evidence:** `cohort-verification.ts:101` — `installedPayload`, `targetProcess`, `workspace` are `PACKAGED_ONLY_BINDING_KEYS`, format-checked as SHA-256 hex and never recomputed. `scripts/generate-read-cohort.mts:589` records `installedPayload` as the digest of uncommitted built entry bytes and `targetProcess` as a digest of the launch recipe including `baseEnv` (where `BDP_SERVER_ADVERTISED_PROFILE` lives). `scripts/read-cohort-evidence.mjs:23` sets `ALLOWED_EVIDENCE_DELTA_PATHS` to the artifact plus `packages/server/src/read-conformance-capability.ts`, and `evidenceCommit` is the last commit touching either.
- **Impact:** (a) flipping bdptest's composition to a mutable RU payload leaves `pnpm evidence:verify` green on Read evidence observed against the immutable Read-only payload — the "same actual installed configuration" rule is honour-system, not mechanized; (b) a write-profile admission constant added to `read-conformance-capability.ts` (the natural home — it owns `ReadServerTarget` and `hasReadConformanceEvidence`) lands *inside* the Read gate's allowed delta with no write cohort behind it, and the Read gate still passes.
- **Fix:** put write admission in its own module with its own gate and its own allowed-delta pair; add a verified `advertisedProfile` field to the artifact root and per segment; recompute a composition digest over **committed** sources (`apps/*/src/server-composition.ts`, the launch config) instead of dist bytes; extend `VERIFICATION_INPUT_PATHS` to each claimed profile's catalog/manifest/fixture.

# 3. Genuine product decisions (not derivable from the current spec or source)

- **D-1 — Installed authentication/authorization model for a public write profile.** Eight required RU rows need ≥2 authenticated principals and a view that hides a live Resource *on the installed service*. The spec supplies no credential scheme and only says "an anonymous principal counting as one principal". Options: (a) ship a startup-config principal/credential/view-policy surface (new security-review scope, secrets in config); (b) record those rows as self-certified in-process under the existing Read precedent, with the artifact saying so; (c) don't advertise RU. **Blocks U2b only** — U1, F2/F3 catalog repairs and F1 payload work proceed either way.
- **D-2 — Single-target write evidence.** bdpbd cannot serve aliases and has no mutation surface, so RU/TX evidence can only be bdptest. Is a one-target cohort acceptable for a public advertisement, given the Read cohort was deliberately two-target and `bdp.md:6616` asks for cross-implementation combinations? **Blocks the verifier generalization shape (F6), not its timing.**
- **D-3 — Erasure administration.** `bdp.md:6372`: "erasure is not a BDP operation" — it is an administrative act. Observing the 19 erasure rows black-box needs an operator surface the reference service does not have. Ship an operator erasure command, accept self-certified erasure evidence, or don't advertise Transactional.
- **D-4 — Scope of this run.** Given F7, drive **Read+Update** to a real installed advertisement and keep the T lanes as private-owner implementation with no advertisement claim. This is the one decision I'd ask for first; it changes T3/T4's predicates.
- **D-5 — Re-sealing Read.** Making the installed payload mutable means the current sealed Read cohort and constant must be regenerated against the new configuration for the cumulative rule to be true. Confirm that retiring the present seal by ordinary re-generation (new run head, new constant, no relabeling) is accepted.

# 4. Sequencing correction

The plan runs U1 and T1 first from preserved branches. That ordering puts runtime work ahead of two classes of blocker that invalidate it.

- **P0 — root, metadata/tooling only, no runtime risk:** F2 + F3 + F12 catalog repairs; F6 verifier generalization; F5 gate split; F9 partition update. Everything downstream is unqualifiable until these land, and none of it needs a worker or a decision.
- **P1 — root:** F1/F4/F11 installed mutable payload with profile-plumbed discovery and per-profile admission.
- **P2 — U1, retargeted:** canonical `operations/` + `alias/` on *that* composition, not a disposable receiver. Preserve the preserved `96ae78e` work as the extraction it is.
- **P3 — U2a then U2b:** installed Types/schema/ownership (reuse `installed-contract-artifact.ts`, `installed-schema-*.ts`); principals/authorization gated on D-1.
- **P4 — U3:** cumulative RU manifest (~133 rows after retirements), fixture capabilities, generator segment, per-profile gate.
- **T lanes:** continue `transaction-read` / direct-carrier work as private-owner implementation with no advertisement claim; TX advertisement stays blocked on D-2, D-3 and new T5/T6.

The absence window is not a reason to compress P0 — it is the cheapest, most independent work on the list and it is the part that currently makes the stated goal unreachable.
