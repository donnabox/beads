## Required

**1. Severity: medium — `docs/specs/bdp.md:5972-5973` — the new clause is readable as the inverse of the ruling, and introduces an undefined term.**
The clause is appended inside the list introduced by "A client supplies exactly one explicit starting intent", so its plain reading is a *grammar* restriction — `start=now` is an admissible starting intent only when no reconnect checkpoint is supplied — rather than the intended *semantics* qualifier. That is the opposite of the operator ruling and of the shipped behavior. Separately, "selected-SSE" appears exactly once in the whole specification and nowhere in the design docs; everywhere else the spec uses "selected" for Resources/sets/representations (1419, 1516, 4243, 5578), and media negotiation is phrased as "an endpoint selects an acceptable supported…" (1954) or "Accepting `text/event-stream`" (6110).
*Impact:* an implementer reading only the bullet can conclude `start=now` + `Last-Event-ID` must be refused — the behavior this commit removed. The disambiguating sentence is two paragraphs away at 6113-6115, and no catalog row cites the bullet, so nothing guards the misreading.
*Fix:* keep the bullet a pure intent definition and qualify with the spec's own idiom, e.g. "`start=now` to deliberately observe only future groups; when `text/event-stream` is the accepted media type and the request also carries a reconnect checkpoint in `Last-Event-ID`, that checkpoint governs instead." Leave 5974-5975 byte-identical, then re-run the catalog citation check.

**2. Severity: medium — `packages/server/src/transaction-sse.test.ts:879-907` — the minimum-wait test cannot distinguish header-honored from header-ignored.**
`f.create("before")` puts head at pos-1, and the supplied `Last-Event-ID` is pos-1's checkpoint — the same value `captureChangesStart()` would return at open time. Under a build where `effective` ignored the header for `start=now`, `after` would still be `cg_…_1`, the minimum would still retry, and the test would still observe pos-2 with `previousPosition` pos-1 and `bdp-scope-position: pos-2`.
*Impact:* the test's name, the plan row ("saved checkpoint remains effective and intervening group is delivered") and `report.md:9` ("controlled minimum retry") all claim coverage the test does not provide; the header × minimum-wait interaction is unguarded, and only `:848` discriminates at all.
*Fix:* put the saved checkpoint strictly behind head before opening — create two groups (pos-1, pos-2), send pos-1's checkpoint with `BDP-Minimum-Scope-Position: pos-3`, commit pos-3 during the wait, and assert the first delivered group is **pos-2** (`previousPosition` pos-1). Head capture would deliver pos-3 there, so the case becomes a real old-guard/ignored-header discriminator with no new minimum semantics.

**3. Severity: low-medium — `apps/bdptest/src/transactional-sse-installed.test.ts:462,484` — `directoryRemoved: true` is asserted rather than observed, and a cleanup fault discards the whole evidence log.**
`directoryRemoved: true` is a literal, unlike the adjacent computed `childClosed` (482-483). It is also unverifiable in principle as written: `rmSync(directory, { recursive: true, force: true })` is the last statement of `finally`, `force` only suppresses missing-path errors, and `maxRetries` defaults to 0 — so an `EBUSY`/`EPERM` from a file the installed child still holds throws out of `finally`, skipping both the `console.log` and the `AggregateError`.
*Impact:* the reported evidence carries a cleanup claim no observation backs, and in the one case the evidence matters most — the pending ignored-header derivative, which is expected to fail — a cleanup race would destroy the stream bytes, hashes, `phase` and named-oracle message entirely. Root acceptance requires "preserve every failure and cleanup."
*Fix:* wrap `rmSync` in `try/catch` pushing to `failures`, and set `directoryRemoved: !existsSync(directory)` computed after removal.
