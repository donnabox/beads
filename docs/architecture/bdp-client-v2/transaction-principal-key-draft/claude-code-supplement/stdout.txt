### 4. Containment compares the raw `mkdtemp` path, not its realpath — Informational (pre-existing)

**Location:** `outsideStore` at lines 275–282, against `directory = mkdtempSync(path.join(tmpdir(), …))` at line 400

`path.relative(directory, …)` uses the unresolved temp path. On darwin `tmpdir()` sits under the `/var` → `/private/var` symlink, so a path expressed in the realpath form of the store directory would produce an escaping `..` relative and be judged *outside* — a false negative in the containment guard, not a false failure. Unreachable for the argv case this delta touches (relative values resolve from the repo cwd, nowhere near the store) and unreachable in practice for the env case given the random `mkdtemp` suffix. Noted only because `realpathSync` is already imported in this file, so `outsideStore(path.resolve(filename), realpathSync(directory))` would be a one-token close if the guard is ever meant to be adversarial rather than hygienic.

### 5. Whether the argv scan sees the flags at all is still unvalidated — Informational

**Location:** the `process.argv` loop, lines 403–413

Under Vitest's `forks` pool (default) the test body runs in a tinypool child whose `process.argv` is `[execPath, workerEntry]`, and under `threads` the worker's `process.argv` likewise does not carry the CLI flags. If that holds for this repo's pool configuration (`vitest.config.ts` was not supplied, and no runtime validation has been performed yet), then neither the containment check nor the two new missing-value throws fire from inside the worker — which also means F1's original failure mode was never reachable. This does not affect the correctness of the repair either way; it is the cheapest thing to confirm during the pending runtime validation, since it determines whether the guard is doing any work. Worth settling before the "positive actual validation will use relative output path" step, because a passing run proves nothing if argv is empty.
