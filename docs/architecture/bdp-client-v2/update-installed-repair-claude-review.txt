The packed path is also covered: `pnpm smoke` spawns the tarball's `dist/installed-reference-process.js` as the entry and it still completes the full IPC lifecycle. Both halves of M4 — bare-import inertness including inherited IPC, and the no-IPC refusal on real execution — hold.

### Finding 2 (H3, HIGH) — **CLOSED**, including the un-demonstrated consequence (b)

`development-runtime.ts:298` (`let serving = false`), `:303` (first predicate in `handle`), `:544` (set as the final statement of the startup `try`, after the full per-credential discover/route loop), `:565` (cleared in `close()`).

Two things worth recording about how I got evidence:

1. **Unmocked raw-socket races cannot land a request in the window — on either commit.** I ran out-of-process racers that connect the instant `server.listen` binds, with 1 and with 32 credentials. On both `dea6f9e` and `4078ca7` the TCP connection is accepted inside the window (`connectMsAfterStart` 51–65 vs `startupMs` 58–71) with request bytes already queued, yet the response is always produced after readiness. The reason is structural: **the `listen` → `serving = true` phase makes no poll-phase yield** — `openDevelopmentAuthority` and the 32 `await view.discover()` calls all resolve on the microtask queue. So the exposure is narrower in practice than the finding implied, and a barrier is required to observe the gate at all.

2. **With a barrier, the differential is decisive.** I wrote my own ESM loader hooks (`module.register`, `/private/tmp/bdp-probes/gate-hooks.mjs`) that wrap the real `openDevelopmentAuthority` and suspend the **second** principal's `discover()` — the same class of instrumentation as the author's `vi.mock`, written independently, driving the real `startInstalledReferenceCandidate` and real HTTP. Same probe, both commits:

| During startup (`startupSettled:false`, 1 route built) | `4078ca7` | `dea6f9e` |
|---|---|---|
| valid-credential `GET` scope probe | **204** | **503** `temporarily-unavailable`, `retry:"after-delay"` |
| valid-credential `POST operations/create-bead` | **200 `created`**, resource `…/beads/early` | **503** |
| **no** credential | 401 `unauthenticated` + `www-authenticate` | **503** |
| bad credential | 401 | **503** |
| unknown path | 404 | **503** |
| after a startup that then **fails**, durable reopen: `beads/early` | **200 — the write survived a failed startup** | **404**, and the same idempotency key yields a fresh **200** |

The last row is consequence **(b)**, which the original review could only report as a structural mechanism ("I lost the connect race twice"). It is now an observed outcome on the baseline and observably absent on the repair. Consequence **(a)** is closed too: during startup *nothing* gets 401 any more, so a conforming retrying cold client sees only a retryable 503.

**Shutdown implications — checked, no regression.** `close()` sets `serving = false` alongside `closing = true`; `close()` is idempotent (same promise object); the listener is released on both the success and the failure path (port rebindable in every run); on the success path the store reopens with the resource durable (`beads/early` 200 after reopen), on the failure path it reopens empty with the key unclaimed. Requests arriving after `close()` begins get `ECONNREFUSED`/503, never a served response.

The window between `serving = true` and the caller holding the handle is closed by construction: there is no `await` between `:544` and the `return` at `:562-576`, and `startInstalledReferenceCandidate` computes `payloadIdentity` *before* starting the runtime and does only synchronous work after it — so the caller's continuation runs as a microtask, before any I/O callback.

Two of the four items on the finding's prescribed fix list were not implemented — see N5.

## Residuals in the bounded changed code

### N1 — LOW · The entrypoint test reads a mutable global; `import.meta.main` is available on the pinned runtime

`packages/server/src/installed-reference-process.ts:63-71`

**Impact.** `process.argv[1]` is writable. Probe H: a host that assigns `process.argv[1] = "<module path>"` and then merely imports the module re-opens the full M4 hijack — observed host `exitCode:2` plus the stderr line, from an import alone. This is deliberate action by the host rather than the bare import M4 named, so the finding stays closed, but the check is softer than it needs to be.

**Fix.** `if (import.meta.main)`. I confirmed `import.meta.main === true` under the pinned Node 24.16.0. It is unforgeable, removes two `realpathSync` calls from every import, and preserves scenarios D/E (verified behaviour there is the correct refusal, not inertness).

### N2 — LOW · Inertness is pinned against the workspace `dist`, never the packed tarball

`apps/bdptest/src/installed-reference-import.test.ts:7-10`

**Impact.** The new probes target `../../../packages/server/dist/installed-reference-process.js`. The original finding's reachability argument was specifically `files: ["dist"]` shipping the module in the tarball. `scripts/smoke-executables.mjs:352-371` still only asserts that the **exports map** denies `@bdp/server/installed-reference-process` and `…/dist/installed-reference-process.js` — the two specifiers the finding showed are bypassed by file-path and `--import` resolution. So the artifact that actually ships has no inertness assertion.

**Fix.** Add one bare-import assertion to the smoke against `installedReferenceEntry`'s directory (the smoke already computes that path at `:390-396`). I verified by hand that the packed copy is inert, so this is a coverage gap, not a defect.

### N3 — LOW · Two new spread sites can silently shadow validated or advertised bounds

`packages/server/src/development-authority.ts:214-217` and `:257-266`

**Impact.** `limits: { ...bounds, ...DEVELOPMENT_OWNER_LIMITS.member }` — `bounds` is the output of `snapshotReadUpdateRuntimeLimits`, which validates feasibility (`read-update-runtime-limits.ts:22-44`). A future key added to `member` that collides with `requestBodyBytes`/`propertiesBytes`/`diagnosticBytes`/`diagnosticCount`/`maximumFirstDiagnosticBytes` would win over the validated snapshot and bypass that validation. Symmetrically, `pagination: { defaultPageItems: readLimits.page.defaultItems, maxPageItems: …, cursorTtlMs: …, ...DEVELOPMENT_OWNER_LIMITS.pagination, … }` places the spread *after* the three values derived from `readLimits` — a key named `maxPageItems` added to the `pagination` group would silently enforce a page bound different from the one `advertisedLimits: readLimits` publishes. Before this change all of these were sibling literals in one object, where a collision is a visible duplicate key.

**Fix.** Put the spreads first (`{ ...DEVELOPMENT_OWNER_LIMITS.member, ...bounds }` is wrong — `bounds` must not win either), or simply assert after construction that the pagination page bounds equal `readLimits.page.*` and that `member` shares no key with `bounds`. Same shape as finding 8's "nothing enforces that" observation.

### N4 — INFO · `DEVELOPMENT_RETENTION_MS` is now a dead export with a narrowed meaning

`packages/server/src/development-authority.ts:77`. It was the sole retention constant; it is now an alias for `lifecycle.minimumRetentionMs` specifically, and after `installed-reference-configuration.ts` stopped importing it, it has **zero** consumers anywhere in the repo and is not re-exported from `index.ts` or `development.ts`. Either drop it or point it at the tuple so the name stops implying "the retention".

### N5 — INFO · Two of finding 2's four prescribed items were not implemented (both now moot)

- The startup `catch` at `development-runtime.ts:545-558` still does not drain `pending`, unlike `close()` at `:568`. This is now harmless *because* of the gate: a task admitted before `serving = true` can only reach `refused(…, "temporarily-unavailable")`, which never touches `authority`. The reason it is safe is the gate, not the catch — worth recording so a future edit before `:544` does not quietly reintroduce the race.
- The post-body admission re-check at `:452` is still `if (response.destroyed || closing)`, not `|| !serving`. Equivalent today because the only transition that clears `serving` also sets `closing`, in the same statement.
