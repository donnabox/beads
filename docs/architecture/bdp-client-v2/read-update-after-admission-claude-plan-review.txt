## F1 — High — Row A's pinned correction is not expressible through the existing client contract, and the already-noted fix is inverted

**Where:** plan §Row A item 2 and line 37 ("preserving any opaque pin") · `apps/bdptest/test-support/read-update-exact-client.ts:105-115` · `packages/server/src/resource-evaluator.ts:724-738` · `docs/specs/bdp.md:2449-2460`

**Evidence.** The exact client's `bodyBindings` substitutes **strings only, into top-level fields** from the whitelist `["type","bead","link","source","target","expectedRevision"]` (`body[field] = string(...)`, line 110-114). There is no mechanism to place a captured canonical Bead URL inside a `{uri, revision}` object, and `id` is not substitutable at all. So the corrected `{uri: <canonical>, revision: <pin>}` cannot be authored from a capture.

Separately, the premise behind the already-noted correction does not hold. Spec 2449-2460: *"The pin is provenance, not a constraint: an authority stores and echoes it byte-identically, compares it only for equality, and performs no semantic validation…"* The runtime agrees — `resource-evaluator.ts:736` passes `reference.revision` straight through, and nothing in `packages/server/src` ever compares an endpoint pin against a stored revision. A literal `"fixture-pin"` on the corrected request therefore returns 200, not a failure.

**Impact.** (a) As written the vector cannot be authored on the client lane. (b) Switching to "an independently observed actual revision" is strictly weaker evidence: a real revision cannot distinguish *pin-unvalidated* from *pin-validated-and-happened-to-match*. The opaque literal is the stronger choice and additionally witnesses the byte-identical echo the spec requires.

**Bounded fix.** Keep the literal opaque pin. Give the replacement Bead a **supplied literal creation id** (e.g. `beads/ra-pin-target`) so both the bad and the corrected body are fully literal, and author the pair either on the raw lane (`{binding:"operations", path:"create-link"}` + explicit `idempotency-key`, exactly as existing `read-update.singleton.*` rows do) or as a client action with a literal body and no `bodyBindings` for `source`/`target`. Add one assertion that the stored Link echoes `revision` byte-identically.

## F4 — Medium — Row A's slot-inventory rule is applied asymmetrically

**Where:** plan §Row A items 1-4 and line 39

**Evidence.** The complete `@name`-capable slot inventory is exactly seven: `updateBead.bead`, `deleteBead.bead`, `createLink.source`, `createLink.target`, `updateLink.link`, `deleteLink.link`, `putAlias.target` (`$defs.{updateBead,deleteBead,updateLink,deleteLink}Members` → `resourceReference`; `createLinkMembers.source|target` → `inputReference`; `putAliasMembers.target` → `resourceReference`). Each is overridden by a `durable*` variant in its singleton request definition. The plan covers all seven — the inventory is complete, no missed slot.

But `putAliasMembers.alias` and `deleteAliasMembers.alias` are **already** `durableResourceReference` at the shared members level — the same situation as `createBeadMembers.id` and `createLinkMembers.id`, which the plan deliberately excludes as "not sequence-local reference slots". The plan includes the two alias-member vectors and excludes the two creation-id vectors on identical facts. (Rejection for all of these comes from the schema: `read-update-values.ts:262-263` explicitly skips `@`-prefixed values; `validateAliasSyntax` at 291-306 additionally fires for `alias`, and runs identically for sequence members at line 317.)

**Impact.** The "whole candidate after a reference-slot inventory" claim rests on a rule the inventory does not apply consistently.

**Bounded fix.** State the rule. If it is *every slot a singleton request definition constrains*, add `createBead.id` and `createLink.id` bare-`@made` vectors (13 total; both are `durableResourceReference`, both give the expected 400). If it is *only slots whose singleton definition differs from the shared members definition*, drop the two alias-member vectors and attribute them to the `#alias-targets` grammar sentence (spec 2963-2965), which this requirement does not select.

## F6 — Medium — Row B's first retry probe cannot discriminate, and is guaranteed inert by the identity model

**Where:** plan §Row B "Retry discriminators", first sentence · `packages/server/src/member-identity.ts:88-91` · `packages/server/src/member-executor.ts:751-768` · `packages/server/src/alias-evaluator.ts:156-159`

**Evidence.** The field-rule table gives `putAlias` exactly `{field:"alias"}` and `{field:"target", binding:"bead"}` — **neither carries `alias: true`**, so no alias witness enters `identityJson` for an alias put. Changing the live resolution of the alias named by the put's wrong-category `target` therefore cannot change the semantic identity, and the retry is a verbatim retained replay. Re-execution would also yield the same 422, since the category check at `alias-evaluator.ts:158-159` fires before any resolution.

**Impact.** The probe's outcome is identical under both hypotheses — it is a control, not a discriminator. The plan concedes this two sentences later but still presents it first under "Retry discriminators".

**Bounded fix.** Relabel it as a no-effect control. If an alias-resolution-change discriminator is wanted, site it on a slot that does carry an alias witness — `updateBead.bead` or `createLink.source|target`, both `alias: true` in the same table. The load-bearing discriminators remain the changed-input same-key 409 and Row C's create-then-replay retained 404, both of which check out against `member-executor.ts:764-780`.

## F7 — Low — ledger discipline the plan half-states

**Where:** plan §Wire/capacity bullets 2 and 4 · `apps/bdptest/src/read-update-matrix.test.ts:1824-1859`, `204-212`

**Evidence.** The live-identity ledger does `live[collection].add(operation.id)` for every successful create (1850) and compares a collection GET's `identities` assertion against the accumulated sorted set (1836-1838) — a create without a supplied `id` inserts `undefined`. Collection GETs on `beads`/`links` must carry `query: {limit:"100"}` plus a `complete` assertion (`/next` = null) and an `identities` assertion (1831-1838) — the plan states this part correctly. The enforced per-row ceilings are `peak.beads <= 64` and `peak.links <= 16` (1858-1859); `limit=100` is the page request, not a live-identity bound, so "all under actual page maximum 100" names the wrong constraint for the 24/12 budget (which is inside 64/16 regardless). Also: client GETs only resolve `targetBinding` against runner bindings and `clientReadRoutes` only whitelists bindings present in the fixture, so every Link/Bead/alias a row inspects needs a fixture binding in file #3 (unused bindings are harmless — verified by the test at 1224-1236, which shows they leave the digest unchanged).

**Bounded fix.** Require every row create to supply a literal row-owned `id`; add each new row to `ledgers` with measured `actions/raw/client/peak`; restate the live bound as 64 Beads / 16 Links per row with `limit=100` as the page request.
