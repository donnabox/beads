## Findings

**1 — MEDIUM · `packages/server/src/development-runtime.ts:487-492` · pre-existing, now on the claimed-complete and newly-exercised path**
The CONNECT socket gets no `error` listener before `socket.end(...)`. Node's HTTP server removes its own `socketOnError` from the socket before emitting `connect`, so the socket is handed over with zero `error` listeners; the sibling implementation at `index.ts:530` guards exactly this with `socket.on("error", () => undefined)`, and `transaction-runtime.ts:186` additionally guards the socket type. `installed-reference-process.ts` installs no `uncaughtException`/`unhandledRejection` handler (grep over `packages/server/src`, `apps/bdptest/src`, `scripts` finds process-level handlers only inside test files).
Impact: a loopback client that sends `CONNECT` and immediately resets makes the server-side write fail (ECONNRESET/EPIPE) with no listener, which is an uncaught exception that terminates the installed candidate process. Secondary and more likely in practice: the new probe's own `bound` and `deadline` branches (`installed-reference-observation.mjs:312`, `:305`) destroy the client socket *with* an error, so a slow run sends an RST toward that unguarded server socket — the resulting child exit surfaces as a failure at `:358-359` (`exit code 0` / empty `stderr`) rather than as the socket assertion that actually timed out. That is a flake channel with a misleading failure mode, introduced by this commit's own test.
Fix: `server.on("connect", (_request, socket) => { socket.on("error", () => undefined); socket.end("HTTP/1.1 405 …\r\n\r\n", () => socket.destroy()); })` — matching `index.ts:530-534`. The completion callback also removes the lingering-socket question, since `server.closeAllConnections()` at `:502` does not reach a CONNECT-detached socket.

**2 — LOW · `scripts/installed-reference-observation.mjs:320-322` · assertion strength**
The three raw-header assertions use `/i`, which makes the header **values** case-insensitive, not just the names. Header field names are case-insensitive so `/i` is right for `X-Bdp-Development`, `Allow`, `Content-Length`; the values are not. Every other marker assertion in the repo is case-exact (`:251`, `:297`, `development-server.test.ts:306` all use `assert.equal`/`toBe` against `"non-attesting"`), and HTTP method tokens in `Allow` are case-sensitive.
Impact: a regression to `Allow: get, head` or `X-Bdp-Development: Non-Attesting` passes the only observation that covers this path, in both emitted and packed runs. The marker's value is a byte literal in source (`:490`), so there is nothing to tolerate.
Fix: assert the value exactly while leaving the name tolerant, e.g. `assert.ok(connect.includes("\r\nX-Bdp-Development: non-attesting\r\n"))` and `assert.ok(connect.includes("\r\nAllow: GET, HEAD\r\n"))`, or keep `assert.match` with the name alternated and the value anchored case-sensitively. `Content-Length: 0` is already pinned by the `:323` terminator assertion.

**3 — LOW · `docs/design/update-implementation-progress.md:587-596` and `review.md:11` · scope precision of the "seven paths" claim**
The enumeration is a **union across two configurations** of one shared module, not seven paths of one receiver, and "These statements cover responses written by the candidate receiver" reads as a single exhaustive list. Statically: the installed candidate reaches five of the seven (`:88`, `:113`, `:361`, `:397`, `:490`) — `:143` and `:431` are both unreachable there because `composedRead` is always populated (`:533-546`) and `:381` returns on every method; the ordinary development receiver reaches four (`:88`, `:113`, `:143`, `:431`) — it has no schema artifacts (`schemaArtifacts` is `[]` without `transport`, `:203-206`), no composed read from the public facade, and no `connect` listener at all, so an ordinary-server CONNECT is destroyed by Node with no response written.
Impact: an auditor checking the claim against the installed candidate alone finds five marked paths and two listed paths they cannot reach, and may read the discrepancy as a gap. The substance is correct; only the framing is.
Fix: one clause — "across the ordinary and installed configurations of the shared receiver, the response paths are …", naming which configuration reaches which. No code change.
