## Findings

**1. "Opaque unknown minimum" is never pinned to a non-`pos-` position token — Medium**
- **Location:** plan-v2.md:34, 36, 38, 47 (A/B/C and installed tuple construction).
- **Issue:** The gap being reordered is keyed on `!transactionMinimumHeaders(request.headers)` (`transaction-http.ts:583-587`), and `transactionMinimumHeaders` differs from `currentReadMinimumHeaders` only by `position()` (`transaction-consistency.ts:26-31,57-62`): it is `undefined` only when `minimumPosition` is neither `genesis` nor `^pos-(0|[1-9][0-9]*)$`. The plan says "complete opaque unknown minimum tuple" but never states this.
- **Impact:** If authored with a lexically valid unknown position (e.g. `pos-999`), A's third matrix column collapses onto the "actual current minimum" control and exercises nothing new, and C's four valid-excluded controls become wrong: `types/` with a known-but-unproven position is `isCurrentTransactionMinimumRead === true` (`transaction-read.ts:48-54`), so it reaches the owner instead of returning 500/`minimum-position`.
- **Correction:** State that the unknown tuple is the setup GET's actual epoch/view plus a non-`pos-`, non-`genesis` position token (existing spelling `minimumHeaders(seed, "opaque")`, `transaction-http.test.ts:4840`), and that the A/B/C oracles depend on that spelling.

**2. Spec attribution for "validation before target existence" is overstated — Medium**
- **Location:** plan-v2.md:11 (and the framing of :20, B's `beads/missing?view=bogus`).
- **Issue:** Spec 5819-5824 orders only the *lexical tuple* refusal "after ordinary transport, target/method, and authentication/authorization checks, but before any owner read or target-existence lookup." Spec 5834-5839 requires uniform 404 for ordinary unknown/hidden targets and then only says "Ordinary request validation and the lexical receiving rule above still apply" — it does not rank query validation ahead of existence.
- **Impact:** Reads as a normative oracle for 400-over-404 on hidden/missing targets, which the cited text does not supply.
- **Correction:** Keep spec 1552-1555 as the normative anchor for unsupported/repeated collection parameters; justify 400-before-existence as parity with behavior that already exists on known minima (`transaction-http.ts:588`) and absent minima (`read-http-routing.ts:39-40`), labeled reference parity. The non-disclosure argument stands independently: the 400 is URL-derived and identical for existing, missing and hidden targets.

**3. `limit=0` carries no normative anchor in the cited ranges — Low-Medium**
- **Location:** plan-v2.md:11 and 34 (A's uniform oracle), :28 (predecessor sentinel update).
- **Issue:** Spec 1552-1555 covers unsupported/repeated parameters only; a "positive integer `limit`" is normative only for retained-version pages (1775-1776). `limit=0` → 400 comes from `read-request.ts:258-263`.
- **Impact:** Grouping limit0 under the 1552 rule presents a reference choice as spec-mandated, including in the draft sentinel rewrite.
- **Correction:** Same oracle values, but label limit0 explicitly as parser parity (`parseOptionalLimit`), distinct from the normative unsupported/repeated rule.

**4. A's HEAD oracle "zero body" is ambiguous and false if read as `content-length: 0` — Low-Medium**
- **Location:** plan-v2.md:34.
- **Issue:** `applyReadHttpSemantics` (`read-http.ts:42-46`) removes the body and sets HEAD `content-length` to the serialized GET problem length; the existing direct-handler pattern asserts GET `content-length === null` and HEAD `Number(content-length) === directGetBytes` (`transaction-http.test.ts:4557-4563`).
- **Impact:** A literal `content-length === "0"` assertion at the direct-handler boundary is unsatisfiable.
- **Correction:** Phrase A's HEAD oracle as "`body` undefined, `content-type: application/problem+json`, `cache-control: private, no-store`, `content-length` equal to the GET problem byte length".
