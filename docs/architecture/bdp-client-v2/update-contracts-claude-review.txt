## A1 — High — Evaluator-side diagnostic truncation is converted into a 500, although the receiver's bound is 32× tighter

**Location:** `packages/server/src/development-contracts.ts:87-89`

**Evidence**
- The adapter faults before emitting anything: `if (outcome.kind !== "evaluated" || !outcome.diagnosticsComplete) throw new Error("installed schema evaluation did not complete")`.
- `diagnosticsComplete: false` is a *normal* evaluator outcome, not a fault: `installed-schema-evaluator.ts:1081-1089` sets it when an invalid instance yields `>= limits.diagnostics` failures or exhausts `limits.diagnosticBytes` (only the *first*-diagnostic-doesn't-fit case refuses).
- Evaluator bounds are `EVALUATOR_CEILINGS.diagnostics = 1024`, `diagnosticBytes = 1048576` (`installed-schema-value.ts:17-18`), passed verbatim at `development-contracts.ts:84`.
- The receiver's bounds are 32× / 2× tighter: `DEVELOPMENT_LIMITS.diagnosticCount = 32`, `diagnosticBytes = 512 * 1024` (`development-authority.ts:43-44`), enforced by `collectDiagnostics` (`resource-evaluator.ts:180-215`).
- The protocol already has an exact representation for this state: `PropertyValidationResult = {valid:false, diagnosticsComplete:boolean}` (`property-validation.ts:21-27`), and the receiver's law is `complete === !stopped` (`resource-evaluator.ts:304`).

**Failure scenario**
The pinned test at `apps/bdptest/src/development-contracts.test.ts:466-490` proves the schema compiles: `allOf` of 1025 `{required:[pN]}` branches. Over real HTTP against that Type, `POST .../create-bead` with `{"id":"beads/x","type":<base>,"properties":{}}` → evaluator returns `kind:"evaluated"`, `valid:false`, 1024 diagnostics, `diagnosticsComplete:false` → `throw` → escapes `validateProperties` (`resource-evaluator.ts:292-296`) → `runMember` fault → `sequence-executor.ts:492-497` rejects `submission.completion` → `development-authority.ts:301` rethrows → `development-runtime.ts:356-360` `empty(response, 500)`.

**Impact**
An administratively accepted, successfully compiled schema makes *every* create/update on that Type answer `500` instead of `422 validation-failed` with 32 diagnostics. Store state is correct (`finish` → `store.abandonAttempt`, no effects, no retained disposition, so retries legitimately re-run) and the owner is not shut down (`fatal` stays false), so this is availability + wire-conformance, not corruption. It is reachable purely through configuration the compiler admitted — a self-DoS. The design note in `docs/design/update-implementation-progress.md` only requires that incomplete evaluation "cannot become successful validation or invented complete diagnostics"; emitting the 1024 diagnostics the evaluator *did* produce and returning `diagnosticsComplete:false` invents nothing and is not success, so the throw is stricter than the stated law and the 500 is gratuitous.

**Fix** — move the completeness check after the emit loop and fault only when the receiver did *not* already stop. This preserves the pinned test at `:466` exactly (its emitter always returns `true`, so `stopped` stays false and it still throws "did not complete"):

```ts
if (outcome.kind !== "evaluated") throw new Error("installed schema evaluation did not complete");
if (outcome.valid) return { valid: true };
if (!outcome.diagnostics.length) throw new Error("invalid schema result lacks diagnostics");
for (const diagnostic of outcome.diagnostics) {
  /* ...existing bound checks... */
  if (!emitter.emit(diagnostic)) return { valid: false, diagnosticsComplete: false };
}
// The receiver's tighter bound did not stop us, so our own truncation is unrepresentable.
if (!outcome.diagnosticsComplete) throw new Error("installed schema evaluation did not complete");
return { valid: false, diagnosticsComplete: true };
```

Because `diagnosticCount (32) < diagnostics (1024)` and `diagnosticBytes (512 KiB) < 1 MiB`, the residual throw becomes unreachable for count-driven truncation and narrow for byte-driven truncation (only when the evaluator's *next* entry alone would have exceeded 1 MiB while the accepted prefix stayed under 512 KiB). `kind:"refused"` has no protocol representation, so keeping that as a local fault is correct — I'm not disputing that half.

## A2 — Medium — `max: 0` aggregate policy is admitted by installed configuration, rejected by the Read plane, and unrepresentable on the wire

**Location:** `packages/server/src/development-authority.ts:127-131`

**Evidence**
- Admin admission: `!Number.isSafeInteger(item.max) || item.max < 0` — accepts `max === 0`.
- Read plane refuses it: `authority-read.ts:421-426` uses `max <= 0` → `AuthorityReadError("configuration", "invalid aggregate policy")`.
- Normative wire schema forbids it: `schemas/bdp-v0.schema.json:1114-1115`, `"max": {"$ref": "#/$defs/positiveInteger"}`.
- The Update plane *does* implement it: `resource-evaluator.ts:985-992` starts `count = 1` for the link being created, so `count > 0` always fails → every such link gets `aggregate-constraint-violation`.

**Failure scenario**
`configuration.maximumEndpointMultiplicity = [{endpoint:"source", linkConformsTo:<edge>, max:0}]`. `openDevelopmentAuthority` accepts it and provisions the store (`recovery-store.ts:304-312` creates the directory and `reference.sqlite` with `openSync(..., "wx")`). The new startup loop then calls `await view.discover()` (`development-runtime.ts:404`), which reaches `captureContext` → `aggregateSnapshot` → throws. `perform` rejects (`read-sequence-lifecycle.ts:378-379`), startup's `catch` closes and rethrows.

**Impact**
Fail-closed, so no runtime authorization hazard — but the operator gets an opaque `AuthorityReadError` from the Read plane instead of the intended `TypeError("invalid installed aggregate policy")`, *after* `reference.sqlite` has been created. Retrying is then blocked both ways: `create: true` hits `EEXIST` at `recovery-store.ts:310`, and `create: false` with a corrected `max: 1` hits `store-mismatch` at `recovery-store.ts:586-595` because the aggregate hash is folded into `installationId`. **Fix** — align the admin bound with the normative schema and the Read plane: `item.max < 1` (or `!(item.max >= 1)`). If `max: 0` is genuinely wanted as "forbid this endpoint type", that needs a `positiveInteger` relaxation in `schemas/bdp-v0.schema.json` and `authority-read.ts` first — which is out of this slice's scope.

## A3 — Medium — `installationIdentity` hashes the aggregate array in caller-supplied order with no canonicalization

**Location:** `packages/server/src/development-authority.ts:141-143`

**Evidence**
`installationIdentity = \`${contractIdentity}-${sha256(stringifyJsonValue(aggregate))}\``, where `aggregate` preserves the caller's array order (`:115-139`) and permits duplicate `(endpoint, linkConformsTo)` pairs. Contrast the deliberate canonicalization applied to the access policy's id lists: `development-contracts.ts:160`, `Object.freeze([...new Set(values)].sort())`.

**Failure scenario**
`[{t,L,5},{s,L,5}]` and `[{s,L,5},{t,L,5}]` are semantically identical and enforced identically by `resource-evaluator.ts:980` (which iterates all entries, so order and duplicates are immaterial to enforcement), yet they hash differently → reopening an existing store after a cosmetic reorder (a config-file refactor, a `JSON.parse` of a reordered list, a `Set`-to-array change upstream) throws `store-mismatch` at `recovery-store.ts:586-595`. Adding a redundant duplicate entry has the same effect.

**Impact**
Permanently strands the dev store's data on a no-op configuration edit. The design note's law is *"Fixed aggregate policy changes require a new installation"* and the test at `development-contracts.test.ts:386-391` pins that for a real change (`[] vs [one]`) — a reorder is not a change, so this is unintended breakage of the "exact-config durable reopen" observation at `:361-385`.

**Fix** — canonicalize before hashing, mirroring `access()`: dedupe and sort the normalized entries, e.g. `[...new Set(entries.map(stringifyJsonValue))].sort()`, and hash that. Optionally reject exact duplicates with the existing `TypeError("invalid installed aggregate policy")`.

## A5 — Medium — `DevelopmentContracts.identity` does not cover `receipt.limits`, which does feed compilation

**Location:** `packages/server/src/development-contracts.ts:63` and `:112`

**Evidence**
`identity: \`development-schema5-${captured.sha256}\`` (`:112`), while the ingester documents exactly what the digest covers: *"URI bytes enter the digest; this measured counter and limits do not"* (`installed-contract-artifact.ts:93-95`). ## A6 — Low — `policyIdentity` is a global hash over every principal's snapshot, not the acting principal's

**Location:** `packages/server/src/development-authority.ts:145`

**Evidence**
`policyIdentity: configured?.access.identity() ?? installation`, where `identity()` hashes `[...snapshots.entries()].sort()` across *all* principals (`development-contracts.ts:191-195`). **Impact**
Two separable issues, both minor here:
1. **Mislabeled field.** `ReadObservation.policyIdentity` reads as "the policy this observation was authorized under", but it changes when an *unrelated* principal's policy is replaced. **Related, same function (Low):** `capturedConfiguration()` now returns a fresh **unfrozen** object per call, where the previous code returned the shared frozen `configuration` singleton (`:55-59`, old `scopeConfiguration: { capture: () => configuration }`). `authority-read.ts:453-463` re-validates and re-freezes defensively, so nothing is exploitable today, but handing a mutable snapshot across the capture seam drops a guarantee the rest of this file maintains everywhere else. `Object.freeze` the return.

## A7 — Low — Read access is default-allow and deniable only by enumerating up to 1000 existing ids

**Location:** `packages/server/src/development-contracts.ts:139-166`

**Evidence**
`DevelopmentAccess` exposes booleans for `create` and `write` but nothing for read; readability is expressed solely as the `hidden` deny-list, capped at `administrativeArray(v, 1000)` (`:151`) with no wildcard.

## A8 — Low — `hidden`/`readOnly` cannot name most legal local resource ids

**Location:** `packages/server/src/development-contracts.ts:152`

**Evidence**
The policy regex is `^(beads|links)\/[A-Za-z0-9_-]+$` — a single segment from a restricted charset. Legal local ids are far broader: `assertCanonicalPathSegments` / `validateCanonicalIdSegment` (`packages/protocol/src/read-values.ts:428-462`) permit multiple segments and any canonically-encoded segment that is not `.`, `..`, or control-bearing — so `beads/a.b`, `beads/team/a`, and percent-encoded ids are all creatable in this authority.

**Impact**
Such a resource can never be hidden or made read-only. It is a capability gap — a dev store containing dotted or multi-segment ids cannot be partially restricted at all.

**Fix** — validate entries with the protocol's own predicate instead of a local regex: require the `beads/`/`links/` root, then run `assertCanonicalPathSegments` on the remainder (the same pairing already used by `resource-evaluator.ts:340-348`).
