### Findings

**1. LOW — regression-guard asymmetry: the N row's distinguishing partitions have no static pin**
`apps/bdptest/src/read-update-matrix.test.ts:4086` (end of the `roundTrip` literal loop, 4066–4086)

The static ledger pins R's three lexical classes against the manifest (`"value":9007199254740993` / `0.12345678901234567891` / `1e309`, the corrected and effectful literals, and the `one`/`zero`/`expanded` corpus). There is no equivalent block for N. Nothing in any test asserts that `nn-bead-metadata-create-refused` carries `1e-400`, that `nn-bead-metadata-patch-refused` carries the twenty-digit decimal, or that the deep leaf sits at depth 16 under `/deep/d0…/d13/a~1b~0c`.

*Failure scenario:* a later edit shortens the chain to `d0/d1` and correspondingly rewrites the expected `instanceLocation` in `complete-problem`, or swaps `1e-400` for `9007199254740993`. The row still returns 422 with a matching diagnostic, all 254 tests still pass, and the slice silently stops sampling the depth/underflow/precision-in-metadata classes the plan committed to — while the coverage `reason` text continues to claim "finite depth 16" and the catalog row still cites "at any depth".

*Partial mitigation already present:* control 8 pins the two-diagnostic shape at runtime (`toHaveLength(2)`), control 5 implies `/shallow` is `diagnostics[0]`, and client control 9's path pins the `metadata.outer[0]["a/b~c"]` escaped-key shape. Depth and the two refused literals are unguarded.

*Fix:* add an N-side loop mirroring 4066–4086 — assert `nn-<kind>-properties-create-refused` body contains `"shallow":9007199254740993` and a `/deep` chain of exactly 14 `d<n>` segments terminating in `"a/b~c":9007199254740993`, that `nn-<kind>-metadata-create-refused` contains `"a/b~c":1e-400`, and that `nn-<kind>-metadata-patch-refused` contains `"a/b~c":0.12345678901234567891`.

**2. LOW — catalog denial controls can pass for the wrong reason**
`packages/conformance/src/numeric-model-catalog.test.ts:120` and `:123`

```ts
expect(() => assertBindings(entry, { ...manifest, catalogId: "read-v1" })).toThrow(
  /read-update-reference-continuation-v1.json/,
);
expect(() => assertBindings(entry, { ...manifest, manifestVersion: 1 })).toThrow(
  /read-update-reference-continuation-v1.json/,
);
```
`entry` is interpolated into *every* failure message `assertBindings` can produce, including `` `${entry} binds ${row.id}` `` (line 84). The matcher therefore does not distinguish the intended catalog-binding refusal from an unrelated ownership failure. It is correct today only because the spread keeps `scenarios` approved; the plan's rule for the app controls ("fail its exact intended assertion IDs, not merely any schema/harness failure") is not honoured here. The unescaped `.` in the regex is a secondary nit.

*Failure scenario:* if `approvedBindings` later drifts so the continuation also trips a binding check, both assertions keep passing while the `catalogId: read-update-v1` / `manifestVersion: 2` guard is no longer exercised at all.

*Fix:* match on the discriminating text instead, e.g. `.toThrow(/read-update-v1/)` and `.toThrow(/\b2\b/)`, or assert on the thrown `expected`/`actual` — or split the catalogId/manifestVersion checks into a named helper whose message is unique.
