This tracker covers the release plan and its execution. The active first phase is establishing a qualified Preview 3 integration branch. The integration-base milestones below are only what we need to begin producing Preview 3 builds; they are not the complete release plan. The Memory outcomes below are candidates to stage across previews toward V2, not a claim that every one is a Preview 3 cutline or has passed qualification; workstreams enter a preview cutline only by explicit decision.

## Why we are releasing previews

Each preview may make progress toward one or both goals:

1. Satisfy the requirements of [Chris's Memory proposal](https://github.com/gastownhall/beads/issues/5877). This has somewhat more time pressure.
2. Develop the Beads Data Protocol (BDP) specification and reference implementation toward a stable, interoperable protocol.

Memory functionality is intended to merge into fork `main` when qualified. BDP remains experimental until its protocol is stable, but preview builds expose the BDP functionality they include directly, without an opt-in switch. Experimental describes its evolving contract, not an availability gate. BDP client/server support is not a Memory V2 release requirement. The broader BDP specification can remain general while V2 implements a fixed local subset; protocol publication alone is not product support. The potential Rust service/client reboot and either Go-backed BDP bridge candidate are separate from the V2 release gate. No bridge implementation was chosen.

## Compatibility policy

Strict compatibility with Preview 1 or Preview 2 is **not a Preview 3 goal**. Those previews can inform the design, but they do not freeze their CLI, data or protocol choices. Record intentional changes and their user impact in the Preview 3 release material.

Compatibility with the shipping `bd` product **is a goal**. Inventory and validate existing behavior before adapting it. When preserving a shipping behavior is unusually difficult or would make the resulting product awkward, make a deliberate, reviewed exception and document the changed behavior rather than silently treating compatibility as either absolute or irrelevant.

Data migration from the shipping product or earlier previews into Preview 3 is **not a release goal**. Shipping-product behavioral compatibility does not imply an upgrade path for existing data. Iris's import/export work could supply a migration path if it is ready and explicitly accepted into the cutline; otherwise, plan it as a Preview 4 candidate. Document the actual supported path when the Preview 3 release is frozen.

Preview 2 demonstrates partial end-to-end Memory journeys. Donna and Trish have now proposed a **Memory V2 objective**: selected workflows from the [Memory proposal](https://github.com/gastownhall/beads/issues/5877), with `--type` selection, fixed Memory/Link/Issue/Dependency/Activity Types, enough constraints for those workflows, retained revisions and pinned References, revision provenance on mutations, and Activity provenance for recorded work. Previews can deliver those slices incrementally. V2 need not expose user-defined/installable Types, `bd type` management, federation, BDP client/server support, or cryptographic signing; a compiled fixed catalog with inventory/details is sufficient if historical Type meaning remains stable across upgrades. Writer-provided attribution must not be presented as authenticated identity. This proposed V2 boundary supersedes treating all four earlier Memory slices below as mandatory together in Preview 3; their detailed outcomes remain candidates until Donna sets each preview cutline. The [V2 workflow and requirement matrix](v2-memory-acceptance-matrix.md) records evidence, owners, candidate staging and explicit exclusions. Trish owns BDP and Type specifications, coordinating with Melinda on Memory and Vickie on implementation semantics. Donna works directly with Melinda; Polly owns the History/Provenance packet; Trish owns Link constraints/References.
