## Verification basis

`git diff 581bad0de6f5e… HEAD -- packages/server packages/protocol docs/specs/bdp.md` is **empty**, so the audit's "identical server/protocol runtime and normative text" claim is confirmed. Every normative citation I checked resolves to text that says what the documents claim: `:5758–5764`, `:5770–5787` ("never reports success with an older position"), `:5805–5807` ("minimum-position … MUST precede any conditional shortcut"), `:5831–5840` (HEAD on the creation target returns "metadata and decision without a usable snapshot handle"; "internal allocation is an implementation detail"), `:5915` ("ordinary … consistency … failures"), `:5916`, `:5919–5921`, `:5234–5244`, `:5293–5296`. Existing-law support for **fresh creation only** is real and does not require a product ruling. No new mutation barrier or retained-Snapshot semantics is proposed; audit row 3's de-scoping is grounded in the verified text (`catch-up-timeout` is defined for "a read"; `:5238` defers minimum to "a later read").

Scope is genuinely narrow: `service.snapshot` has exactly two production callers (`transaction-http.ts:421`, `:426`), no public `index.ts`/`development.ts` export touches these types, and `transaction-store.ts:339–350` shows `enter()` does **not** fence on a plain thrown error (fencing lives in `atomic`/`cleanupThenThrow`), so throwing `TransactionMinimumFailure` once per attempt out of the owner entry is safe and matches `readEvents` at `:1531`. `transaction-consistency.ts` truly needs no change: epoch→view→position already matches `:5805`, the deadline never renews (`:103`), and the abort check at `:107` precedes the first attempt at `:109`, satisfying §16's "pre-abort must prevent an owner attempt". Placing the check before `snapshots.expire` is safe — independent maintenance still runs at `maintenanceIntervalMs: 1000`, and `liveLedger`'s "capture requires completed expiry at its instant" (`transaction-snapshot.ts:314`) is only reachable on paths that do run expire.

## Findings

**1. HIGH — Negotiation (406) vs. the minimum wait is unspecified, and the plan silently changes an observable status.**
*Location:* plan §17/§19/§37; `transaction-http.ts:416–424`; existing control `apps/bdptest/src/transactional-snapshot-installed.test.ts:548`.
*Impact:* The create branch enters preflight whenever `candidate.status !== 200`, which includes 406 from `accept: text/plain`. Forwarding the tuple there means a GET with an unacceptable Accept **plus** a behind minimum burns the full 1000 ms budget and returns `503 catch-up-timeout` instead of 406; with a satisfied minimum it returns 406 only after a full real capture pass. Spec `:5805` mandates minimum-before-*conditional*; `:5915`/`:5919` do not order 406 against consistency. The plan lists "negotiation ordering" in its own focus and never resolves it, so the choice gets made by accident in the installed run.
*Fix:* State the choice in §17. Recommended: return 406 from `candidate` **before** any tuple forwarding or preflight (it is a pure receiving-side media decision needing no owner observation), keeping 304/412 after the minimum per `:5805`. Add one discriminating row: behind minimum + `accept: text/plain` → assert the chosen status explicitly.

**2. HIGH — `behind` is *not* convertible by "existing outer error handling"; it lands on a bodyless 500.**
*Location:* plan §17; `transaction-http.ts:565` (`error.reason !== "behind"`) falling through to `:591 empty(500)`.
*Impact:* The plan's sentence "Minimum failure is converted by existing outer error handling with actual context" is false for `behind`. It is unreachable today only because every minimum read is wrapped in `waitForTransactionMinimum`, which rewrites `behind`→`catch-up-timeout` at the deadline. §17 instructs forwarding the tuple through *both* creation branches while only §16 adds the wait; if either branch reaches `observeSnapshot` with a tuple outside the wait, the client gets a contextless 500 with no `x-bdp-development-limit` marker, and no test in §33–§38 would catch it.
*Fix:* Add a source-level assertion that no create/preflight path can emit `behind` to HTTP, and either extend the `:565` branch to map `behind` to the same 503 shape or make it a loud internal error instead of `empty(500)`.

**3. HIGH — "One finite monotonic deadline per minimum operation" is not expressible through `service.snapshot`'s per-call API.**
*Location:* plan §16, §19; `transaction-http.ts:421` and `:426`; `transaction-service.ts:252–256`; `transaction-consistency.ts:85–121`.
*Impact:* Each `service.snapshot(...)` call starts its own `budgetMs`. The create path calls it twice whenever `candidate.status !== 200` **and** `decision.status === 200`. That is unreachable today only because `eligible` is also "200 + `content-type: application/json` + no etag", so `decision.status` always equals `candidate.status` — an unasserted invariant living in a different function (`read-http.ts:10–48`). Any later etag/content-type change on the eligible response yields two independent 1000 ms budgets (2 s worst case) and two separately-authorized owner entries. §19 asks the implementer to "prove it cannot reset the wait budget" and supplies no mechanism.
*Fix:* Pin the invariant with a test that the preflight branch always returns — i.e. `:426` is unreachable for `target.kind === "create"` — or thread one deadline (a single already-started wait state, or one service entry doing preflight-decision-then-capture inside one `waitForTransactionMinimum`). Prefer the test; do not leave it as prose.

**4. MEDIUM-HIGH — The no-allocation oracle does not discriminate: both failure modes are 503 with `retry-after`.**
*Location:* plan §35, §47, §49.
*Impact:* If the check lands after `snapshots.capture` — the exact mutant this slice exists to exclude — each of the ~200 retries in a 1000 ms budget allocates a handle, the 8-live-handle cap at `transaction-snapshot.ts:613–633` trips inside the same request, and the owner **returns** `temporarily-unavailable` rather than throwing. The wait loop never sees a `TransactionMinimumFailure`, so HTTP answers **503 + `retry-after`** — indistinguishable by status or `retry-after` from correct `503 catch-up-timeout`. §49's "503 catch-up-timeout rather than 200/304/412" omits the one neighbour that actually collides.
*Fix:* Assert the Problem `code === "catch-up-timeout"` and its `type` family on every behind observation; assert `bdp-scope-position` is strictly below the supplied `minimumPosition` (precedent: `transaction-http.test.ts:1315`); assert a later eligible capture still returns 200 with a fresh handle id. Also state in §35 that one behind request drives ~budget/5 ms owner entries, so reviewers read the capacity claim correctly.

**5. MEDIUM-HIGH — The named installed budgets do not exist in the named fixture.**
*Location:* plan §47 ("existing 5s exchange/90s aggregate/120s outer/10s lifecycle") vs. `transactional-snapshot-installed.test.ts:152` (`withDeadline` default **45000**), `:526`/`:585` (`it` timeout 60000), `:241` (requestTimeoutMs 5000), `test-support/transactional-execution-binding.ts:190` (`cleanupTimeoutMs: 10000`). The 90 s/120 s figures belong to `transactional-set-installed.test.ts:107,454`.
*Impact:* The plan's exclusions forbid new launchers and limits, yet a ~35–40-exchange, two-launch, two-reopen observation with two real ~1 s waits must fit **45 s**, not 90/120 s. Either the ledger is under-budgeted or the implementer quietly raises the fixture's deadlines.
*Fix:* Restate the real ceilings (5 s exchange / 45 s fixture deadline / 60 s per-`it` / 10 s cleanup) and either show the ledger fits 45 s or explicitly authorize a new `it` with its own stated deadline and that number.

**6. MEDIUM — "nominal 2 s real wait floor" contradicts the unchanged 1000 ms budget.**
*Location:* plan §47 vs. `transaction-runtime-configuration.ts:112` (`minimumReadBudgetMs: 1000`) and `transaction-consistency.ts:90`.
*Impact:* Read per-request — the natural reading, since it qualifies "2 fixed-head no-progress requests (GET and HEAD)" — any ≥2 s assertion fails deterministically against a 1 s budget. Read as the pair's total it is correct, but it is also the only ledger number setting a per-exchange wall-clock expectation near the 5 s exchange timeout.
*Fix:* Write "≈1 s per request, ≥2 s combined for the GET+HEAD pair", and assert a lower bound with margin (≥900 ms) plus an upper bound below 5 s, not an exact floor.

**7. MEDIUM — No requirement to copy/revalidate the request and tuple at the owner boundary, breaking the established mutation-during-wait discipline.**
*Location:* plan §15 ("optional *already-captured* minimum parameter"), §16. Compare `transaction-service.ts:263–271` (`changes` freezes `copied` before `run`), `:238`, `transaction-read.ts:96`, `transaction-store.ts:1518–1521` (`readEvents` re-snapshots at the owner), and the existing discriminator `transaction-service.test.ts:717–737` + `:724` which mutates `supplied.minimumPosition` after the call.
*Impact:* `owner.observeSnapshot(request)` re-reads the caller's object on every retry. A mutable request lets `request.kind` flip `create`→`manifest` mid-wait, defeating §15's "allowed only for create/preflight" if the service validates once and the owner trusts it; an unfrozen tuple lets the required position move between attempts. "Already-captured" is also the only place in this store where a minimum would skip owner-side `snapshotTransactionMinimum` (which is idempotent on its own frozen output).
*Fix:* In `service.snapshot`, freeze a `{kind}`-only copy and call `snapshotTransactionMinimum` synchronously before `run` (matching `changes`/`readAtMinimum`); in `observeSnapshot`, re-snapshot the tuple and reject a tuple with a non-create/preflight kind **per attempt**; add the mutate-after-call test mirroring `:724`.

**8. MEDIUM — The counterfactual can bind a mutated payload to a clean source commit.**
*Location:* plan §50; `transactional-snapshot-installed.test.ts:31–41`; `test-support/transactional-execution-binding.ts:74–84`.
*Impact:* `sourceCommit` defaults to `git rev-parse HEAD`, an entry override requires only *some* declared commit, and `workspaceDirty` is computed from the test's root rather than the mutant's build tree. A mutant built from an uncommitted edit elsewhere gets reported under a clean commit id — precisely the "label a source-only mock as installed" failure §50 forbids, reached by accident.
*Fix:* Require the bypass to be committed on a throwaway branch so `BDP_TRANSACTIONAL_SOURCE_COMMIT` names a commit that contains it, and require the counterfactual report to assert `served.installedPayloadDigest !== <calibrated digest>`. The mechanism already exists and is used for the opposite assertion at `:532`/`:540`.

**9. MEDIUM — Missing the one oracle the HEAD/preflight and conditional paths actually have.**
*Location:* plan §33, §37.
*Impact:* HEAD, 304 and 412 carry no body, so the manifest/afterstate oracle of §34 cannot detect a missing or bypassed check on those paths — only the response context can. The plan asserts "HEAD/preflight is eligible" and "actual current context on successful conditional responses" but never states the inequality to assert, leaving the HEAD mutant unguarded.
*Fix:* On every non-failure response to the create target carrying a tuple (200 GET, 200 HEAD, 304, 412), assert `Number(bdp-scope-position.slice(4)) >= Number(minimumPosition.slice(4))` and that epoch/view echo the supplied values. (Reachability check passed: `view = "development-all-visible"` at `transaction-store.ts:240` and a UUID epoch both satisfy the private token grammar at `transaction-consistency.ts:13`, so a client can actually form the tuple from echoed headers.)

**10. LOW-MEDIUM — The retained-target exclusion is stated more broadly than the uncertainty it rests on.**
*Location:* audit row 5 ("One genuine conflict"), plan §11/§17/§27; `docs/specs/bdp.md:5916` and `:5903`; `transaction-snapshot.ts:206–208`.
*Impact:* Only the *position* comparison (retained anchor vs. current serving observation) is unsettled. Epoch and view are determined under either reading, because the retained disposition's epoch/view are integrity-asserted equal to the current context, so a foreign epoch/view is incompatible with both candidates — and `:5916` already admits "ordinary epoch/view, minimum-position … failures" on that row. Telling council the whole retained row needs a ruling overstates the blocker and parks an unambiguous conformance gap (blanket 500) indefinitely.
*Fix:* Name the position comparison as the sole unsettled subcase in both documents, and note that retained epoch/view refusal is a separately implementable slice. Keep it out of this patch; stop describing it as blocked.

**11. LOW-MEDIUM — "Pinned existing controls" partly do not exist yet.**
*Location:* plan §37; the only existing installed minimum control is `transactional-snapshot-installed.test.ts:566–570`, a **partial** tuple (`bdp-minimum-scope-position` alone) on the **create** target.
*Impact:* There is no existing retained-target minimum control to "keep". After this patch `:566` legitimately stays 500 (partial tuple remains the gap), but complete-tuple refusal on `?snapshot=<id>` and on `?snapshot=<id>&stream=&page=` is a *new* assertion; described as pre-existing, it may simply not get written, leaving the accidental-enablement risk unguarded.
*Fix:* List it as an addition — assert 500 + `x-bdp-development-limit: minimum-position` for a complete tuple on both retained targets — and state explicitly that `:566`'s partial-tuple control must stay green and unmodified.

**12. LOW — Code citation drift against an unbuilt base.**
*Location:* plan §19 cites `transaction-http.ts:409–426` (actual create branch `412–426`, `candidate` at `416`); audit row 1 cites `transaction-store.ts:1425–1464` (actual `observeSnapshot` `1426–1466`); audit row 4 cites `transaction-consistency.ts:20–67` (parser `20–55`, failure class `56–63`, `checkTransactionMinimum` `65–78` — the cite ends mid-function).
*Impact:* Small in itself, but §7 instructs reconciling "the named source seams" against a base that does not exist yet (root's reviewed C1+alias successor), and drifted anchors make that reconciliation unverifiable.
*Fix:* Cite by symbol name plus range, and re-anchor on the supplied base before authoring.

## Assessment

The core design is sound and well-matched to existing law and existing seams: owner same-entry check before allocation, reuse of the unmodified finite wait, request-signal forwarding, and the existing `run`/`active` drain all work as the plan assumes, and the armed-wait fixtures it proposes to reuse exist (`transaction-service.test.ts:706–737`, `transaction-http.test.ts:1302–1317`). The gaps are concentrated in the error contract (#1, #2, #4), one API-shape mismatch against the plan's own deadline rule (#3), and evidence precision (#5, #6, #8, #9). #1, #2 and #3 should be resolved in the text before authoring; the rest can be folded into the acceptance plan. No files written, no tests or builds run.
