## Findings

**1. P3 — beads collection row does not observe absence of the `links` plane in collection items**
Location: `packages/conformance/matrices/read-update-v1.json:1127–1177` (the `beads` action's five assertions); claim text `packages/conformance/test-support/read-update-coverage-v1.json:205`.
Impact: `currentBeadRecord` permits an optional `links: currentLinkCollection` (and `ownedLinks`), and the tuple projects only `id`/`type`/`properties`/`metadata`. A response-only counterfactual adding `"links":{"items":[],"next":null}` to each item is schema-valid, order-preserving and tuple-identical, so it passes all five assertions — yet `docs/specs/bdp.md:1409` states the default Bead `GET` does not include Links and `include=links` is valid only on a Bead URL, never on the collection. The `wholeContract:true` reason now says "complete … records", so a narrow presence-side hole remains in the same class as the closed P2s (though far lower impact: extra optional member, not wrong stored values). Note this exposure is specific to beads — `linkRecord`'s only optional extra is the spec-legitimate `revisionProvenance` — so it is *not* inherited from the already-accepted links row. Verified statically only; not executed (no writes permitted).
Fix: add `{"id":"default-bounded-links","kind":"json-pointer","pointer":"/items/0/links","exists":false}` (and `/items/1/links`; the fixture is fixed at two Beads) to the `beads` action, plus a matching proxy control that injects the plane — or, if you prefer zero new assertions, narrow the coverage `reason` to the record's required members. Treat `ownedLinks` separately: for a non-owning Type like `types/task` its absence is expected, but assert it only after confirming the ownership semantics the existing `read.resource.default-bounded` row already bounds.

**2. P3 — "forwards real bytes / raw integrity is not bypassed" overstates what the proxy does**
Location: `apps/bdptest/src/installed-read-oracles.test.ts:75–110` (esp. 106–109); claims at `read-update-oracle-root-review.md:7` and `read-update-oracle-repair-report.md:9`.
Impact: the proxy decodes *every* response to a UTF-8 string and re-serializes head and body — header names are lowercased, `transfer-encoding` is dropped and `content-length` is always recomputed. On the Scope prologue the authority returns 204 with no `content-length` (`packages/server/src/read-http-routing.ts:33`), and the proxy injects `content-length: 0` (confirmed: Node emits it on a 204), which RFC 9110 §8.6 forbids; the exact decoder ignores `content-length` for 204 (`http-executor.ts:1182`), so the prologue still passes. None of this affects either closure — no authored assertion in those two rows observes framing or casing, and the `unchanged` controls prove transparency at the assertion level — but the counterfactual demonstrates *assertion sensitivity over a real socket*, not octet-transparent forwarding, and the reports should not be read as the latter.
Fix: one-sentence amendment in both reports ("re-serializes each forwarded response head/body with recomputed framing"), or pipe the upstream response through verbatim and re-frame only the mutated collection response.

**3. P3 — test hygiene nits in the new file**
Location: `installed-read-oracles.test.ts:58–61` and `82–110`.
Impact: `mkdtempSync` and `launchInstalledReference` sit outside the `try/finally`, so a launch failure leaks the temp store directory — the production test guards exactly this (`read-update-matrix.test.ts:232–236`). Separately, a throw inside the proxy's `end` handler (e.g. a non-JSON 200 body) never completes the response, so the failure surfaces as a 5 s transport timeout instead of the real parse error. Both are diagnosis-quality only.
Fix: move the two statements inside the `try`, or wrap them in the same catch+`rmSync` pattern; wrap the mutation block in `try/catch` and reply 502 with the error text on failure.
