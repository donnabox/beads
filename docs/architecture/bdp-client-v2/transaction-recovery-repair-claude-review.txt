**F2 (Low–Medium) — CLOSED for roots; residual for one page branch (finding 1).** `readReceipt` (621–647) now orders it correctly: `disclosedReceipt` (principal scan + id match + epoch filter) → `unsupported` return → `readContext()` → 404 for undisclosed → `checkTransactionMinimum` → `expireRow` → `observeReceipt`. **F3 (Low) — CLOSED as scoped.** `String(undefined)` → `JSON.parse("undefined")` is gone with the preflight; an absent `configuration` row now reaches `metadata()` (317–321) and its "missing transaction metadata". ## Findings

### 1 — Low. A page read still disposes of a failed, expiry-eligible parent before answering 404, so the progress document's blanket "unsupported root/page controls … do not trigger retention" is wrong for pages.

**Location** `packages/server/src/transaction-store.ts:1452–1457` (the `!saved` branch), against the `unsupported` gate at `1466` and the doc claim at `docs/design/transaction-implementation-progress.md:723–724`.

Only completed receipts get a durable plan (`transaction-store.ts:1055`), so for a failed or pending parent `SELECT * FROM receipt_pages …` finds nothing and line 1454 calls `retainedReceipt(principal, parentId)` — which, after the refactor, is exactly `disclosedReceipt` + `expireRow(stored, instant())` (606–610). That `expireRow` runs *before* the `condition === "unsupported"` gate at 1466 and before any minimum check, and for `status:"failed"` past `expiresAt` it executes `DELETE FROM receipts …` (350–353).

**Failure scenario.** `GET ${scope}receipts/<failed-id>/pages/anything` with `BDP-Minimum-Scope-Position: junk`, on a failed receipt past `expiresAt`. It routes to the page branch (`transaction-http.ts:321`), the owner forgets the receipt, and the response is 404 — a request the server has declared it cannot process has advanced retention state, which is the precise shape F2 named and which the root path no longer does. The same holds for a *supported but behind* minimum (the receipt is forgotten before `checkTransactionMinimum` ever runs, so no 503 is possible) and even for a plain no-controls page GET. The 404 itself is correct — page-level nonexistence precedes the gap, matching the `index < 0` → `missing` rule at 1465 — only the write is wrong.

**Impact.** Small and bounded (the row was disposal-eligible and the 1 s sweep would reach it anyway), but it leaves root and page disagreeing again and makes two shipped sentences inaccurate: line 723–724 asserts unsupported root/page controls "do not trigger retention", and line 699 extends the "private gap after disclosure and before read-triggered expiry" ordering to "both roots and pages".

**Repair.** In the `!saved` branch, decide the "a visible completed parent must have its durable plan" invariant without expiry: use `disclosedReceipt(principal, parentId)` and test `parseReceipt(stored.receipt).status === "completed"`, returning `{kind:"missing"}` otherwise. This is behaviour-preserving — `expireRow` never forgets a completed receipt, and a completed-but-compacted parent still has its plan row so it never reaches this branch — and removes the only write on the path. Either tighten the doc to name the exception or drop the "for both roots and pages" / "do not trigger retention" generalizations.

### 2 — Low. The one composite the repair newly discloses — incompatible installation *with* a hot journal — has no committed regression.

**Location** `packages/server/src/transaction-recovery.test.ts` (no such case) against `docs/design/transaction-implementation-progress.md:690–692`.

The report and doc now promise that a hot-journal file may be restored by SQLite and *then* refused "before any BDP recovery/maintenance". My reading says that holds — recovery happens in the PRAGMA at 425, the config check at 436–443 throws a non-SQLite error, `atomic()` rolls back cleanly and rethrows "installation mismatch", and the retraction/sweep at 444–448 never execute — but nothing in the repo witnesses it. The two committed byte-identity regressions use cleanly closed files, and the real-predecessor probe (`old-format-and-partial-insert.mjs`) hard-codes a sibling worktree path, so it is not reproducible in CI.

**Failure scenario.** A future change that moves the refusal after the retraction, or that lets journal recovery fence the owner (`fence()` would replace "installation mismatch" with "transaction storage failure; owner fenced"), would ship green: no test opens a hot-journal store with a mismatched installation.

**Repair.** Extend the existing `after-terminal` case, which already leaves a hot journal plus one pending row: before the good reopen, assert `openTransactionStore({...options, create: false, receiptMaximumItems: 3})` throws `/installation mismatch/`, then reopen correctly and assert `recoveredPending === 1` and the 60 receipts are still `detail:"available"` — proving the refused open recovered the journal yet retracted nothing and swept nothing. Roughly five lines, no new fixture.

### 3 — Low. The new root `unsupported` result is discriminated structurally against an untagged type, diverging from the page API it was modelled on.

**Location** `packages/server/src/transaction-service.ts:267–271` (`if ("kind" in observed) return observed;`) and `packages/server/src/transaction-store.ts:611–620` (`ReceiptRead` has no discriminant; two overloads).

`readReceiptPage` takes `TransactionMinimum | "unsupported"` in a single signature and returns a 4-way tagged union (1421–1430). `readReceipt` instead keeps an untagged `{receipt, context}` and bolts `{kind:"unsupported"}` beside it, so the service must detect the variant with an `in` test. It is correct today — `ReceiptRead` has no `kind` — but the invariant is unstated and unenforced: adding any `kind` field to `ReceiptRead` (or to a future sibling result) silently reroutes every successful read into the 500 gap, and TypeScript would not complain. Relatedly, the exported `TransactionServiceReceiptResult` (39–42) does not carry the new variant, so it is only visible in `receiptAtMinimum`'s inline return type.

**Failure scenario.** A later change adds `kind: "receipt" | "missing"` to `ReceiptRead` for symmetry with the page reader; `"kind" in observed` becomes true for every read, `receiptAtMinimum` returns the read object as if it were the gap, and `transaction-http.ts:342` answers 500 + `x-bdp-development-limit` for ordinary minimum reads. No type error; only the HTTP tests catch it.

**Repair.** Give `readReceipt` one signature returning a tagged union (`{kind:"read", receipt, context} | {kind:"unsupported"}`), drop the overload pair, and switch on `result.kind` in the service; or, minimally, fold `{kind:"unsupported"}` into the exported `TransactionServiceReceiptResult` and replace the `in` test with an explicit tag comparison.

### 4 — Low. The new HTTP test's retention assertion races the 1 s background maintenance sweep.

**Location** `packages/server/src/transaction-http.test.ts:1319–1343`, against `packages/server/src/transaction-store.ts:1101–1120` and `TransactionRuntimeTestSeams` (`transaction-runtime.ts:35–43`).

The fixture starts the runtime with the default `maintenanceIntervalMs` of 1000 (`transaction-store.ts:199`), and the unref'd interval calls `maintain()` → `sweep(instant())` against the *seam clock*. After `f.setTime(86401001)` at 1319 the test performs eight loopback round-trips and then asserts `retainedReceipts()` equals both original receipt bodies. Nothing holds the sweep off.

**Failure scenario.** If fixture startup plus the eight requests exceed one second of wall time (plausible under `maxWorkers 2` contention or a loaded CI box), the sweep compacts `completed` to `detail:"expired"` and deletes `failed`. The `failed` + `token` expectation then flips from 500 to 404 (`disclosedReceipt` returns `undefined`), and the final `toEqual([failed, completed])` fails regardless. The test would fail for a reason unrelated to the ordering it exists to pin.

**Repair.** Add a `maintenanceIntervalMs` passthrough to `TransactionRuntimeTestSeams` (it already forwards `clock`, `minimumReads`, `receiptMaximumItems`) and set a large interval in this fixture, so the assertion depends only on read-triggered retention. Failing that, drive the clock inside a `minimumReads.wait` seam as `transaction-http.test.ts:1292–1311` does, rather than advancing it for the whole test body.

### 5 — Low. The new independent namespace guard is untested and is keyed on `id` rather than `parentId`; the service's surviving `next`-prefix check is still tautological.

**Location** `packages/server/src/transaction-store.ts:1445`; `packages/server/src/transaction-service.ts:245–247` and `141–144`.

Two small shortfalls in F4's repair. (a) No regression exercises the guard: `transaction-receipt-pages.test.ts:117` covers an unknown token on a real receipt (the `index < 0` path), not a `…/pages/…` URL outside the receipt namespace, so the clause that replaced the tautology has no witness. (b) The guard tests `id`, so `${scope}receipts/pages/<token>` passes it — `lastIndexOf` yields `parentId === ${scope}receipts`, the collection URL, which is *not* in the receipt namespace — and is rejected only by the `receipt_pages` lookup failing, i.e. exactly the lookup-dependence F4 asked to remove. Not reachable over HTTP (`transaction-http.ts:321` slices after `receipts/`, so `"pages/<token>"` does not contain `/pages/` and never routes to the page branch), so this is a strength-of-invariant point, not a leak. (c) `result.page.next.startsWith(\`${result.page.receipt}/pages/\`)` is still unconditionally true, since the store builds `next` as `pageUrl(parentId, …)` and sets `page.receipt = parentId` (1490–1493); same for `checked()` at 141–144. Only the `results.length !== maximum` pair in those conditions validates store output.

**Failure scenario.** A later refactor that derives `parentId` differently (say, a fixed `indexOf`) reintroduces a cross-namespace page id; the guard still passes on the `id` prefix and the only backstop is a `receipt_pages` miss, which is the behaviour the independent check was added to stop relying on.

**Repair.** Test `parentId.startsWith(\`${scope}receipts/\`)` instead of `id`, and add one line beside `transaction-receipt-pages.test.ts:117` asserting `readReceiptPage("p", \`${scope}other/x/pages/${token}\`)` is `missing`. Leave (c) as declared defence-in-depth, or state in the comment that the `next` prefix is construction-guaranteed and only the length pairing is load-bearing.

## Residual qualification limits

- **Unverified by me:** I ran nothing. The 523/523 green, the two reds, the smoke runs, the evidence verification and the predecessor-format probe are all author-produced logs that I read rather than reproduced; the `pnpm test` → `dist` coupling above means a reviewer who reruns them must build first. My code reasoning is independent of those logs, but the *passing* status is not independently confirmed.
- **Crash shape, not durability.** SIGKILL plus injected SQL failures witness application-crash and SQLite rollback-journal behaviour. They say nothing about power loss, fsync/filesystem durability, torn sectors, failover, or `synchronous=FULL` actually reaching stable storage. The report states this; it remains true after the repair.
- **Byte identity is now conditional, by design.** A normal incompatible or bound-mismatched file is refused with the whole file unchanged (two committed regressions). A file with a hot journal may be physically altered by SQLite recovery before the refusal. Per your instruction I did not treat that as a defect; it is a real narrowing of the previously unconditional guarantee and is now disclosed in the doc, but see finding 2 for the missing witness.
- **Concurrency.** The new page drain test is a deterministic two-waiter interleaving with an injected clock and wait policy. It is lifecycle evidence; it is not a concurrency, contention or load qualification, and the 5 ms `BEGIN IMMEDIATE` + full-chain-validation poll remains the more expensive waiter.
- **Error-surface normalization is explicitly out of scope.** A zero-byte or non-SQLite file, and a concurrently-locked store, still produce raw `ERR_SQLITE_ERROR` text rather than the owner's documented refusals (F3 residual).
- **Suite breadth.** 15 of 129 test files ran. That is complete with respect to every non-dist importer of the changed modules plus the executable smokes, but no full workspace suite was repeated; cross-package integration remains root's to confirm.
- **Review breadth.** I checked the four focus areas, the diff, and the surrounding open/read/page paths. I did not audit the unchanged paging, submission, sequence or Read-plane logic beyond what these paths touch, and I made no assessment of spec conformance beyond the ordering clauses the prior review already pinned.
