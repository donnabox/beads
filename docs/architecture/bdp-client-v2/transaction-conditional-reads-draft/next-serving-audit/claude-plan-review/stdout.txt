I verified the plan against the pinned sources rather than the reviews. Summary first, then numbered findings.

## Verdict

**No blockers.** The five-request / two-child witness is feasible and protocol-correct on the pinned source. Nine corrections follow, five of which I'd want fixed before authoring.

## What I confirmed (do not re-litigate)

- **Header precedence is real and discriminating.** `transaction-http.ts:519–528` passes `fields.length === 1 ? fields[0] : eventRequest.after` to `beginEvents`, so `Last-Event-ID: E0` wins over `?after=E1`. `transaction-store.ts:1752–1765` → `eventPacket` (`:745–802`) starts at `{position:1, ordinal:0}`, cursor-matches E0 via `eventProjection` (`:736–741`), skips `ordinal <= 0`, emits `[E1]`, `caughtUp`. Query-only would emit nothing; a full replay would emit E0 *first*. The plan's "first id-bearing frame must equal E1, drained list must be exactly [E1]" therefore excludes all three wrong hypotheses. Correct as written.
- **Recorder hazards are exactly as the native condition states.** `until` returns at `raw-sse-recorder.ts:138` without consulting `failure`/`destroyed`; `failure` (`:24`) is never exported; `ready.reject` at `:108` is a no-op once `:95` resolved; `close()` (`:153–156`) resolves on socket `close` regardless of `failure`. The synchronous `destroyed === false` gate is the only available health signal, and `timeoutMs` default is 25 000 (`:34`), so pinning 5000 is required, not cosmetic.
- **Launcher close is 10 s + 10 s, not 10 s.** `scripts/transaction-installed-observation.mjs:48–60` → `bounded(exited)` (10 s, SIGKILL) → on failure `drainFailure` (`:38–46`) SIGKILLs and runs `bounded(exited)` again. `close()` is memoized, so an abort-triggered close (`:61–65`) and a later explicit `await` observe the same promise — the plan's tracked-handle design is compatible.
- **Restart IDs are stable.** `epoch` is written only under `create` and re-read on reopen (`transaction-store.ts:583–630`); `authorizationView` is the constant `INITIAL_TRANSACTION_VIEW` (`transaction-authorization.ts:5`, store `:274`, `:627`); checkpoint is `pos-<persisted position>`. `renderTransactionEvent` (`transaction-events.ts:100`) hashes exactly those plus source and ordinal.
- **Request 5 yields contextual 400, not 404.** `readEvents` checks `eventSourceKnown` first (`:1659`), then `checkTransactionEventCursor` (`:1668`) → source-tag mismatch → `TransactionEventParameterError(undefined, context)` (`transaction-events.ts:139–140`) → `transaction-http.ts:640–644` → `transactionHttpProblem("invalid-parameter", context)`, which sets all three context headers (`:122–127`).
- **Frame fields, schema, paging.** `transaction-sse.ts:43–45` emits `id`/`event`/`data` per spec `bdp.md:6345–6356`. `event`, `eventPage`, `mutationReceipt`, `transactionalProblem` all exist (`schemas/bdp-v0.schema.json:3075, 3191, 3896, 4179`); the completed receipt branch requires `transaction` and permits `effectPosition` (`:3960–3962`). `receiptMaximumItems` defaults to `TRANSACTION_MAXIMUM_OPERATIONS` (`transaction-store.ts:249`), so two events fit one page with `next:null`.
- **Binding comparison across restarts works and excludes the ephemeral address.** `installedTransactionBinding` returns only `{served, operationTargets, runtimeConfigurationIdentity, authorityMode}` (`transactional-execution-binding.ts:85–91`); `port: 0` (`transaction-installed-configuration.ts:62`) makes same-port reuse legal. Reopen with changed artifacts/config is *rejected by the store* (`transaction-store.ts:592–611`), so byte-identical artifacts are a hard precondition, not hygiene.
- `maximumStreams: 1` (`transaction-sse.ts:17`) is satisfied by one stream at a time.

## Findings

**1. Medium — the witness has no sensitivity control.** *plan-v2, "Proposed finite witness", steps 2–4.* Every expectation is a `toEqual`/`toBe` against a value the test itself saved, and nothing demonstrates the comparators can reject a near-miss. The adjacent installed callback treats this as mandatory: `transactional-alias-installed.test.ts:339–342` and `:357–360` deliberately mutate a clone and assert the comparator throws, recording `localSensitivityControls`. Recent history (`1ba65f2`, `b021380`) is the same discipline. **Fix:** add two request-free, lifetime-free local controls — (a) clone the restored E1, mutate `data.revision` (or `ordinal`), assert the same comparator rejects it; (b) assert the frame comparator rejects the saved E0 record against the observed E1 frame. Report them as `localSensitivityControls`. Zero cost in HTTP requests or process lifetimes.

**2. Medium — the 45 s / 10 s / 60 s envelope does not cover the launcher's worst case.** *plan-v2, "Use 45s work/10s final cleanup/60s callback"; `scripts/transaction-installed-observation.mjs:22–60`.* If the work deadline aborts at 45 s, `onAbort` starts `close()`, whose worst case is 20 s → 65 s, past the 60 s Vitest timeout. `boundedDrain` caps *reporting* at ~55 s, leaving ≈5 s for report assembly and the preserve/remove decision; and the launcher's internal SIGKILL path can land at 55–65 s, i.e. after the callback has already returned. The historical callback carries the same latent gap (`transactional-event-sse-installed.test.ts:83, 316`), so the plan inherits rather than introduces it, but plan-v2 asserts the 10 s budget as a property. **Fix:** either raise the callback timeout to 75–90 s (outer supervision stays 120 s, as the alias callback does with 90 s/120 s at `:106, 485`) or lower the work deadline to ≤35 s; derive the cleanup deadline as `min(10_000, hardStop - elapsed)`; and state explicitly that the 10 s bound is a reporting bound, not a termination bound, so the supervisor must tolerate a late child exit even on a reported pass.

**3. Medium — no in-child diagnostic is capturable, so "preserve the actual trace" is unachievable for the most likely failure.** *`scripts/transaction-installed-observation.mjs:13–18`; `transaction-installed-process.ts:71–77`.* The launcher attaches `data` handlers that only *count* stdout/stderr bytes and discard them; the child writes a single fixed string `"installed transaction qualification failed"` with `exitCode = 2` and never echoes the cause. A failed `create:false` reopen — the plan's riskiest step — therefore surfaces as `"installed transaction exited before ready"` with no reason, and plan-v2's "preserve the actual trace and scope a source repair from the observed failure" cannot be honoured. **Fix:** capture the child's stderr bytes test-locally in the new callback (bounded, e.g. last 4 KiB) and include them in the preserved failure record; or state in the plan that reopen failures are diagnosable only by inspecting the preserved store, and make store preservation mandatory on *any* second-launch failure. Do not claim trace preservation you cannot produce.

**4. Medium — the pre-handle launch-failure branch cannot supply PID evidence, and process-group cleanup is unsafe.** *plan-v2, "Test-local lifecycle mechanics" and "The outer120s supervisor owns final PID/process-group inspection"; `scripts/…observation.mjs:9–12, 87–93`.* `launchInstalledTransaction` returns `{child, ready, close}` only on success; on startup failure it runs `close()` and throws, exposing neither handle nor PID. So "retain PID evidence / supervisor owns forced cleanup" is unimplementable in exactly the branch that needs it. Worse, the child is spawned **without `detached: true`**, so it shares the runner's process group — a supervisor process-group kill would kill Vitest itself. Separately, "even if the helper attempted cleanup" is vacuous: the helper never touches the directory (it only `mkdir`s under `create`, `:7`). **Fix:** restrict supervisor forced cleanup to PIDs the callback actually captured; record the pre-handle branch as `stop: "unknown-no-handle"` plus unconditional store preservation; have the supervisor identify survivors by runner `ppid` + entry path, never by process group; drop the process-group wording.

**5. Medium — installed attribution will record live HEAD and a dirty workspace.** *`transactional-event-sse-installed.test.ts:27–31, 278–279`; `profile-contract-plan.ts:135`.* `source` falls back to `git rev-parse HEAD` at module load and is embedded in `served.sourceCommit` (validated as 40-hex). The plan itself says HEAD may advance through the unrelated CI repair during this window, so the report can attribute to a commit that is not the pinned baseline. The code permits `BDP_TRANSACTIONAL_SOURCE_COMMIT` *without* an entry override (`:27–28` only constrains the converse), i.e. a pinned commit over local dist — a false installed attribution. And with the two CI-repair files still modified, `workspaceDirty` will be **true**. **Fix:** make the new callback refuse the local fallback for installed attribution (require both env vars present and assert the recorded `source` equals the pinned baseline); record the dirty-path list (names only) and assert it is a subset of `packages/server/src/transaction-set.test.ts` and `transaction-submission.test.ts`, so `workspaceDirty:true` is self-evidently the known CI repair rather than contamination.

**6. Low/Medium — the post-drain "precisely [E1]" assertion is a bounded-window claim, not exhaustive.** *`raw-sse-recorder.ts:55–100, 125–127, 153–156`.* `body` is recomputed only inside the `data` handler, and `close()` calls `socket.destroy()`, discarding anything not yet surfaced; `frames` additionally drops the trailing incomplete segment (`:126`). The exhaustiveness direction is conservative (extra frames could be missed, not fabricated), and ordering already excludes a from-the-start replay, so the check is still useful — but plan-v2 words it as absolute. **Fix:** word it as "every complete id-bearing frame observed in the bounded window", and add the cheap live-getter checks that cost nothing: `status === 200` re-read after drain, and `elapsedMs` well under the pinned 5000 ms, so a deadline-destroy cannot be mistaken for a clean intentional close. This is the same discipline the plan already applies to elapsed-sleep absence claims.

**7. Low — the plan asserts cross-restart ID stability without naming its source basis.** *plan-v2 step 3.* The witness stands entirely on persisted `epoch` (`transaction-store.ts:583–630`), the constant view (`transaction-authorization.ts:5`, store `:274/:627`), persisted `position`, and reopen's configuration/capture rejection (`store:592–611`). Without those citations, a step-3 failure cannot be scoped to one of epoch persistence, policy persistence, position persistence, or artifact drift. **Fix:** pin those four ranges in the plan's source-reasoning section alongside the existing `transaction-events.ts:95–141` citation.

**8. Low — pin literals, not only equality-to-saved.** `effectPosition` is permitted but *not required* by the completed receipt branch (`schemas/bdp-v0.schema.json:3962`), so "validate effectPosition" must assert presence and value. With no second mutation, every post-commit response must carry `bdp-scope-position: pos-1`; the alias callback pins such literals explicitly (`:239–247`). Pinning catches a saved-value capture bug that equality-to-saved cannot.

**9. Low — request 5's two preconditions should be pinned.** The contextual 400 holds only because `beads/a` exists as an identity and `authorization.readPolicy === "all-visible"` (`transaction-store.ts:691–701`); under a generation-1 empty policy the same request becomes 404. State both as preconditions so a future policy change surfaces as a precondition break rather than a protocol finding.
