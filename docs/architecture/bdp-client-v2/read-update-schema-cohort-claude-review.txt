## Findings

### 1. MEDIUM — both new coverage rows carry a verbatim-identical `reason` that misdescribes each row
**Location:** `packages/conformance/test-support/read-update-coverage-v1.json:6674` and `:6824`
**Impact:** The two reasons are byte-identical. Neither states what its own row observes. `validation.diagnostics` (180 assertions: failing-Type identity, exact keyword URIs, instance pointers, observed 32/524288 bounds) is described as "no implicit network installation … not established" — a `validation.type-contract` clause with no bearing on it. `validation.type-contract` (137 assertions: `type-not-installed`, `validation-failed`, absent supplied identity, positive create controls) never mentions `type-not-installed`. Plan lines 29–30 give each row a distinct clause map and credit boundary, and the progress doc's third new paragraph describes them distinctly — the coverage `reason` is the row-local record a promotion reviewer reads, so a generic duplicate defeats the mechanism the plan relies on.
**Fix:** Write per-row reasons from the plan's clause map: type-contract → both-kind inadmissible-property refusal with absent-ID GET, one missing Type per category returning `type-not-installed` with no allocation, positive controls; partial on cause inventory and no-implicit-network. diagnostics → exact failing Type, authored schema `$id` + keyword pointer, properties-relative instance location, canonical Problem tuple, observed discovery bounds; partial on truncation, evaluation order, retained-list compatibility, non-Type causes.

### 2. MEDIUM — the progress doc retains a W1 invariant sentence that this same commit falsifies
**Location:** `docs/design/read-update-executable-progress.md:133`
**Impact:** The paragraph still asserts "no fixture, Type, installed contract or policy changed … the admitted route set is identical. Both digest pins reflect that order-only change." At 2c10d19 the fixture changed (id renamed, both Type oracles 13→17), the installed contract changed (17 descriptors + 4 schemas), the route set gained 8 exact GET routes (`types/schema-*`, `schemas/schema-*`), and both digest pins were rewritten `be0e83fb…`→`bdffd6f9…` **for that reason**, not for an order-only change. A reader auditing the digest movement is pointed at the wrong cause, in the one document whose purpose is honest evidence accounting.
**Fix:** Scope the sentence to its historical pin ("at `39dd934`/`ededc12` …") or restate: the pins now also carry the cohort's new route and configuration identity.

### 3. MEDIUM — the "thirteen byte-identical shipped descriptors" claim rests on a tautological assertion
**Location:** `apps/bdptest/src/installed-schema-cohort.test.ts:35-37`; helper at `apps/bdptest/test-support/installed-schema-cohort.ts:58-62`
**Impact:** The test compares `withSchemaCohort(...).contracts.descriptors.slice(0, 13)` against `shipped.map(d => ({retrievalUri: d.id, utf8: stringifyJsonValue(d)}))` — literally the expression `withSchemaCohort` itself evaluates. Its only informational content is "`referenceTypeArtifacts` returns exactly 13"; it cannot detect divergence from what the empty-descriptor shipped path installs. Over HTTP, the 13 pre-existing `read.types.descriptor` actions assert only `status`, closed-schema validity and `/id` (`normalize: scope-relative-url`) — not `conformsTo`, `source`/`target` or `ownsOutgoing` — and the fixture tuple oracle adds only name/describes. So nothing in this cohort compares the 13 shipped descriptor *bodies* against the shipped-set configuration, which is exactly the claim the progress doc's new section leads with. (By construction both capture branches run the same `referenceTypeArtifacts` + `stringifyJsonValue`, so this is a missing oracle, not a suspected mismatch.)
**Fix:** In the same test, also capture `{...base, contracts: {descriptors: [], schemas: []}}` and assert the shipped capture's artifact entries equal the cohort capture's first 13 (by `retrievalUri` + bytes) — one call, genuinely independent of the helper. Alternatively give the 13 the same full-object `exact` assertion the 4 new descriptor actions use.

### 4. MEDIUM/LOW — `installed-schema-cohort.test.ts` asserts far less about the capture than its name claims
**Location:** `apps/bdptest/src/installed-schema-cohort.test.ts:16` (title) and `:48-49`
**Impact:** The title says it "pins the complete schema cohort closure", but the capture step is `expect(captured.profile).toBe("read-update")` only. `captureInstalledReferenceConfiguration` returns `schemas` (the 4 hosted URIs/bytes), `configuration.contracts.descriptors` (17) and `artifactIdentity` — none are asserted. The closure claim is carried entirely by the capture not throwing, so a future change that silently dropped a schema from the hosted set (leaving `propertiesSchema` resolvable only via `$id` aliasing, per `installed-schema-graph.ts:517`) would pass this test; it would be caught only downstream by the matrix run's schema-document GETs.
**Fix:** Assert `captured.schemas.map(s => s.uri)` equals the four `$id`s and `captured.configuration.contracts.descriptors.length === 17`, or rename the test.

### 5. LOW — the four schema-rejection diagnostics never pin `document`
**Location:** `packages/conformance/matrices/read-update-v1.json`, actions `schema-{validation,diagnostics}-{bead,link}-{base,child,complete}` and `schema-update-bead-base`
**Impact:** They assert `diagnostics/0/{type,schemaLocation,instanceLocation}` but not `diagnostics/0/document`, while the pre-existing generic probe in the same row does (`bead-metadata-array` → `document: "metadata"`, plus `document-root`). `document` is precisely the field that distinguishes a properties diagnostic from a metadata one, and the metadata-exemption credit turns on that distinction; `instanceLocation: "/n"` alone is ambiguous between the two documents. The progress doc's "document-relative instance pointers" is therefore not fully pinned.
**Fix:** Add `{"id":"document","kind":"json-pointer","pointer":"/body/diagnostics/0/document","exists":true,"equals":"properties"}` to the schema-failure probes. Free, and it strengthens both the intersection and exemption claims.

### 6. LOW — `read-update.validation.type-contract` has no assertion-input sensitivity control
**Location:** `apps/bdptest/src/read-update-matrix.test.ts:385-397` (all 6 new controls target `validation.diagnostics` and `singleton.document-patch-validation`)
**Impact:** Plan line 46's done-criterion is "all newly credited laws have meaningful negative sensitivity controls". Its `type-not-installed` vs `validation-failed` pair and the positive create controls do discriminate by construction, so this is a missing proof rather than a wrong claim — but it is the one promoted row where no control demonstrates the assertions can fail.
**Fix:** One control, e.g. rewrite `problem-code` to `validation-failed` on the `schema-contract-bead-uninstalled` response (must fail `problem-code`), or make `after-schema-contract-bead-invalid` return a 200 record (must fail `status` + `absent`).
