### 1. Stale "unowned" claims contradict shipped behavior — Low (documentation/comment accuracy)

**Location** `packages/server/src/transaction-service.ts:10`; `docs/design/transaction-implementation-progress.md:754`, `:791-793`, `:802`

The plan required dropping stale "and unowned" wording. That was done for the store's guard string (`transaction-store.ts:191`) but three in‑scope occurrences survive, all phrased in the present tense:

- `transaction-service.ts:10` — "Only the existing fixed all-visible, schema-free/unowned configuration applies." The service is composed by `transaction-runtime.ts:276-289` directly over the store, and the new owned HTTP test (`transaction-owned.test.ts:624`) drives `startTransactionRuntime` with a compiled **owning** bundle through this exact path. (The "schema-free" half was already stale from the compiled‑contract slice; "/unowned" is made stale by this one.)
- progress doc `:793` — "Owned-Link transitions remain unsupported," directly contradicting the new §"Atomic owned-Link projection" in the same document. `01e2d54` reflowed that very paragraph (formatter rewrap) without correcting the sentence.
- progress doc `:791-793` — "Deletion mints no version for either supported collection (Beads and unowned Links), so supplied provenance is inert in both." Now wrong for owned Links: `deleteLink` carries `MintInput` (`read-update-values.ts:92`), `deleteWhere` forwards it (`transaction-batch.ts:829-831`), and `noOp` is false when `deleting` — so `needsContext` is true for an `agent`/`message` input and the owning source's new version records that native attribution.
- progress doc `:754`, `:802` — "The supported installation remains all-visible, schema-free and unowned", "owned-source fanout … remain outside this slice."

**Impact** The progress document is the handoff/review record for this slice. A later integrator reading §"Bounded set-core review repairs" concludes owned transitions are refused and deletion provenance is inert — the opposite of what ships. Note the direction is *under*-claiming, so there is no profile over‑advertisement risk here.

**Fix** Update `transaction-service.ts:10` to drop "schema-free/unowned". In the progress doc, either mark the superseded sentences as historical or correct them: delete `:793`'s sentence, qualify `:791-793` to "unowned Links" only, and qualify `:754`/`:802`'s "unowned" to the slice in which it was true.

### 2. Owned transitions never exercise native (`agent`/`message`) attribution — Low (test coverage)

**Location** `packages/server/src/transaction-owned.test.ts` (whole file); projection at `transaction-batch.ts:730`, `:739`

`grep` over the owned test file returns zero occurrences of `agent`, `message`, or `committedAt`. The store sets `recordChangeContext: false` (`transaction-store.ts:1023`), and every owned provenance assertion uses actor‑only input (`provenance = { actor: {...} }`, `:148`). Because `needsContext` requires `agent` or `message` (`resource-evaluator.ts:869-873`), the owned path never reaches `makeContext`/`observeCommitTime`, and no test observes a `committedAt`‑bearing provenance on either the nested delta or the Event level. This is also precisely the case the doc in finding 1 declares inert for deletion.

**Impact** The batch is the new code and is what copies `subject.revisionProvenance` into the nested delta and `source.revisionProvenance` into the Event. Spec 5437‑5508 requires these be the same value ("An operation that mints both a Link version and a source version records its one attribution on both"). A regression that dropped, swapped, or stale‑copied native attribution on owned creation/update/deletion would pass the entire 15‑test owned suite. Mitigated — not eliminated — by evaluator and `development-contracts.test.ts` ("revision/provenance fanout") coverage at the layer below, which does not assert the Transactional Event projection.

**Fix** Add `revisionProvenance: { agent: "a", message: "m" }` to one owned create, one update, and one delete (plus the `deleteWhere` member path), and assert the Event‑level `revisionProvenance` deep‑equals the nested delta's for create/update, equals the source record's for delete, and carries a `committedAt` in the `present` state.

### 3. Three redundant full `readStoredResource` parses per owned operation — Low (efficiency / simplification)

**Location** `packages/server/src/transaction-batch.ts:598`, `:606-610`, `:644-652`, `:704-706`

Within one owned operation the same rows are parsed and schema‑validated repeatedly:

- `:606-610` parses the preimage of **every** write, including the direct subject — which `:598` already parsed into `before` — while only the owning source's `.revision` is ever read.
- `:704-706` re‑parses the source **postimage** that the `changed` loop already parsed at `:647` and stored in `changes` under the identical key `outcome.source`.

An owner's body inlines its entire owned set, so each owner parse is O(owned‑set size). Net: ~3 owner‑sized parses where 1 suffices, on the hot owned path.

**Impact** Constant‑factor cost on every owned mutation, scaling with the owner's owned‑set size. This is adjacent to the report's own disclosed INCONCLUSIVE 80 s+ run at 32 self‑Links per owner — the fixture was reduced to one Link per source specifically to avoid that cost. I am **not** claiming this is that slowdown (the report correctly notes graph shape and helper work changed together, so it isn't isolated); it is the cheap, obviously‑safe reduction in the same region.

**Fix** Two independent one‑liners: store the raw `EvaluatorStoredResource` in `previous` and parse once at the point of use in the owned block; and replace `:705-706` with `changes.get(outcome.source)?.resource`, which the `changed` loop is guaranteed to have just set with the canonical postimage. The `:707-715` invariants run unchanged against either.

### 4. Set‑path gaps against the accepted plan's predicate 7 — Low (test coverage)

**Location** `packages/server/src/transaction-owned.test.ts:424-461`, `:503-513`, `:528-540`, `:582-589`, `:734-736`

Every `updateWhere`/`deleteWhere` in the owned suite is the **sole** operation of its transaction. Three specifics of predicate 7 are therefore unreached:

- *"Later set or explicit operation sees final staged owned state"* — no test places two set operations, or a set followed by an explicit owned operation, in one transaction. (The explicit‑only interleave at `:289-327` does cover staged visibility for explicit operations.)
- *"No-op members have no source fact"* — `:426-431` selects `n == 0` and writes `1`, so both members are effectful; `:450` and `:735` are deletions. No set mixes no‑op and effectful owned members. The explicit mixed case at `:346-347` is covered.
- *"retains per-member sourceRevision"* — `:438` maps results to `count ?? resource?.id` only; unlike the explicit chain assertion at `:312-316`, no set test asserts that each member's `sourceRevision` equals its own source Event's `revision`.

**Impact** A defect in staged‑state visibility across set operations (stale candidate snapshot, or a selector re‑scanning after an earlier member re‑versioned the shared source), a spurious source fact on a no‑op set member, or a receipt reporting the final source revision on every member, would all pass. Low likelihood given the batch derives each from evaluator output per member, but these are the plan's named predicates and the report implies them under "Staged canonical set updates/deletes of owned Links, per-member sourceRevision."

**Fix** One added transaction covering all three: `updateWhere` over owned Links whose `change` is a no‑op for one selected member and effectful for another, followed in the same batch by a second set operation and an explicit owned update; assert the no‑op member yields an `updated` entry with unchanged `sourceRevision` and no source fact, that the later operations observe the staged state, and that each member's `sourceRevision` matches its own source Event.

And the group's `changes` entries now derive from re‑parsed stored bytes rather than the evaluator's in‑memory postimage (receipt `results` still use the latter); since `properties`/`metadata` are open objects in the bundle and every record member is evaluator‑produced, the re‑parse cannot fail, and the change moves the group toward agreement with what Read actually serves.
