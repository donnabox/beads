## Direct answer on removing both control guards

**Yes — it achieves the claimed concrete result, with no added requests.** With `expectedRevision` omitted from the `updateBead` in *both* contenders, whichever request the server admits first commits at pos-2, and the second applies to current state per spec 2159–2160 and evaluator 1022–1024 (the `"expectedRevision" in input` predicate is simply not entered) and commits at pos-3. The failed-contender count is therefore 0 under either arrival order, so the named one-failure oracle must fail. That is strictly stronger than removing one guard, which — exactly as the plan states — still yields one failure whenever the unguarded contender executes first, making the control scheduling-dependent. The cost stays at rows 1–3, three HTTP requests, `[200,200,200]`, matching `control.maximumHttp: 3`.

Two qualifications on what it licenses: the control establishes *input sensitivity of the oracle to the guard field*, which the plan states correctly and does not inflate into a production mutant; and because both contenders are required to be completed before the oracle is set (L8), the evidentiary content lives in the preconditions rather than the named assertion. Its practical weaknesses are not in the design but in readout (M4) and artifact collision (M5) — fix those two and the control does what it claims.
