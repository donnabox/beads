## Existing law and the decision boundary

The bounded Selector language is specified at `docs/specs/bdp.md:849–860`; set selection, atomicity, provenance and limits at `:4246–4289`; projected cardinality and no silent unwritable filtering at `:4905–4918`. Admission orders bounds, carrier syntax, principal, key, fresh capacity, negotiation and durable admission at `:4493–4539`. Equal retained/pending outcomes precede fresh admission controls. Current owner code already expresses that ordering at `transaction-store.ts:1050–1084`.

However, embedded Selector grammar is not explicitly assigned to carrier step2, and Selector bytes/depth/nodes are not explicitly placed in step5 or in the postadmission execution-limit list (`:5246–5265,5303–5319`). Read query mapping does not settle the Transactional phase. Relabeling every parser exception as400 or every limit as a retained413 would choose new observable semantics. The saved proposal correctly identifies the missing decision.

Recommended question for the operator:

> Should invalid set Selectors be rejected before key lookup, and valid but over-limit Selectors be refused only for a new key? I recommend yes: `updateWhere` or `deleteWhere` with `$..*` returns400 `malformed-request` without a receipt or key binding, even if that key already exists. For valid grammar, a new key exceeding Selector bytes/depth/nodes returns413 `limit-exceeded` before execution, without binding the key; an equal retained/pending retry follows its existing receipt/comparison rules before those current Selector caps, and a conflicting key still returns409. Existing body bounds, authentication and receipt negotiation still apply. The alternative admits valid over-limit requests and retains a failed receipt, consuming the key while that failure is retained. Which behavior should we implement?

Clarification accompanying the recommendation: static complexity is checked across the whole fresh carrier, so an over-limit Selector in operation2 produces direct413 even if operation1 would have failed during execution. Both choices commit nothing. Invalid grammar remains whole-carrier400 under either proposed choice. `limit-exceeded` retains `retry: never`; an unbound key is not permission to automatically repeat an unchanged request. Equal retry protection bypasses only Selector operational caps, not framing/body bounds or authentication. No new error code or receipt-union variant is proposed.
