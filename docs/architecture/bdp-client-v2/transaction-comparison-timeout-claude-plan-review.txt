## Findings

**1. High — the epoch-change condition the plan is organized around is unreachable in this store; the one reachable residual is a masked storage fault, not an authority transition.**
Plan lines 7, 15, 18, 34, 38, 48. Source: `transaction-store.ts:528` writes `epoch` exactly once, under `options.create`; the reopen branch at 530–553 only *reads* it (`epoch = metadata("epoch")`); there is no `UPDATE … epoch` anywhere in the repo. Line 520 sets `PRAGMA locking_mode=EXCLUSIVE; busy_timeout=0`, so no second process can write metadata while an owner is open. `transaction-service.ts:566–580` awaits `active` (which holds the pending submit) before `owner.close()`, so orderly shutdown cannot close mid-comparison.
Impact: `comparisonEpoch() !== epoch` can only fire via `closed`, and the only way `closed` becomes true during a live comparison is the maintenance-failure handler at `transaction-store.ts:1340–1357`, which sets `closed = true` *after* closing the database — so a background storage fault silently returns a bare 503 instead of surfacing. That is precisely the "fabricated 503 for a storage fault" plan step 3 forbids. So the plan (a) spends step 2's recheck, step 3's residual, and required-test bullet 3 on a condition that cannot occur, and (b) mislabels the one reachable case as an ownership/authority-transition gap worth preserving, when it is a fault-masking defect.
Smallest correction: state in §Exact source that the epoch is created once and never rotated and that the owner holds an exclusive lock, so the recheck is a defensive assertion rather than a live race; re-describe the residual as "owner closed by background maintenance/storage failure" and either scope it out explicitly as a pre-existing defect for a separate slice or require `closed` to be distinguished from `maintenanceFailure`/`ownerFailure`. Demote test bullet 3 to a one-line defensive assertion reusing the `{ ...store, comparisonEpoch: () => epoch }` double that already exists at `transaction-submission.test.ts:467` and `transaction-dependencies.test.ts:641`.

**2. High — the normative obligation the plan rests on does not exist; this is a new semantic and needs an actual product ruling.**
Plan lines 5 ("currently lacks the **required** Scope context"), 7 ("No human product ruling is needed"), 26 ("The general Scope-response requirement at 5766–5774 supplies the tuple obligation"). Source: `docs/specs/bdp.md:4004–4009` enumerates what this 503 must carry — code, `retry: after-delay`, SHOULD `Retry-After`, no receipt, no state change — and the tuple is not in that list. The generalizations are read-scoped: line 5793 says "Every Transactional Scope-bounded **read** reports…"; 5233–5244 is scoped to "a receipt or page response"; the only explicit extension to non-200 responses is line 5805, "Required current Scope context remains required on 304 and 412 responses," i.e. conditional reads. Line 5768's "Transactional Scope-bounded responses carry:" is declarative with an undefined subject, and the sole conformance row is `transactional.changefeed.consistency-fields` (6922).
Impact: attaching the tuple to a direct POST refusal is an extension of a *local* convention, not a spec repair — and the repo's convention is a deliberate split (409/406/413-limit carry context; 400/401/403/413-too-large/415 deliberately do not, asserted at `transaction-http.test.ts:2590–2603`). The governing question is which non-read refusal classes count as Scope-bounded responses, and the answer decides the plan's fate both ways: rule "reads/receipts/pages only" and the plan is unnecessary; rule "all authorized known-Scope responses" and test bullet 4's instruction to "keep earlier malformed/auth/size exclusions intact" preserves bugs. This also contradicts the plan's own "no new semantics" framing.
Smallest correction: rewrite §Recommendation to present this as a proposed extension rather than a required repair; delete "No human product ruling is needed for the healthy same-epoch subset"; add a gate asking root to rule on which direct refusal classes carry the tuple, naming the consequence for the existing 400/401/403/413/415 exclusions.

**3. High — the "seam-controlled packed-runtime observation" is not a distinct evidence class, so file 9 and the whole 11-exchange ledger buy nothing.**
Plan lines 42, 56–57, 59–71, 73. Source: `transaction-http.test.ts:12–14` already imports `../dist/transaction-runtime.js` — the emitted module, not source; `:76–91` starts a real listener on `port: 0` and passes seams through; `:126–145` `get`/`post` issue real `fetch` calls; `transaction-runtime.ts:94–97` already takes `seams` as a second parameter, and `captureSeams` already accepts `comparison.{budgetMs,now,wait}` (`transaction-runtime-configuration.ts:138–174`).
Impact: the existing source HTTP cohort *is* emitted-dist plus real loopback HTTP under a controlled comparison clock — the tests the plan itself cites at `802–847` and `2605–2660` are exactly that. A new `apps/bdptest` file loading the same emitted module by explicit path would run the same code over the same transport with the same seams, so the distinction the plan asks root to adjudicate as a new evidence class does not exist at this tree. The costs are real and recurring: a ninth file, a new app cohort, a root acceptance gate, an 11-exchange ledger, a 22-exchange maximum, and the special package-installation cost the plan itself flags at line 73.
Smallest correction: drop file 9, the controlled-runtime ledger and its acceptance gate; add the multi-position assertions (two observable positions, final `pos-3`) to the existing `transaction-http.test.ts` cohort at 2605–2660. Keep §Honest feasibility's genuinely correct conclusion — the default installed child has no comparison seam, so the shipped 1000 ms budget stays unobserved, recorded as a sensitivity with no qualification claim.

**4. Medium — nine files is disproportionate; the defensible slice is seven.**
Plan line 42. With finding 3 removing the app test and finding 1 removing the dedicated epoch-race cohort, the slice is: `transaction-comparison.ts`, `transaction-store.ts` (one narrow observation method — still needed, since `comparisonEpoch()` and `readContext()` each call `enter` and cannot be nested), `transaction-submission.ts`, `transaction-http.ts`, plus `transaction-submission.test.ts`, `transaction-http.test.ts`, plus `docs/design/transaction-implementation-progress.md` = 7. The plan's own instruction "if an implementation can safely use fewer files, prefer it" should be resolved to that number before assignment rather than left to the author, since the ninth file carries a root gate and recurring suite cost.
Smallest correction: restate §Proposed ownership as seven files with the app test removed.

**5. Medium — the opt-in mechanism is unspecified, and the natural reading of step 2 breaks exact-shape assertions on the unobserved path.**
Plan lines 32–33. Source: `transaction-comparison.ts:15–23` takes a structurally narrowed store with no `observed` flag; `transaction-submission.ts:103–109` builds the observed adapter. But `transaction-dependencies.test.ts:212–220`, `629–638`, `641–654` and `transaction-sequence-alias.test.ts:342`, `365`, `709` call `compareAndAdmitTransaction(f.store, …)` with the **full** store and assert `.toEqual({ kind: "temporarily-unavailable" })`.
Impact: step 2's "Reuse existing enter/readContext authority rather than exposing SQL or accepting a caller-supplied tuple" most naturally reads as detecting the new store capability. Capability detection would make those full-store unobserved call sites start receiving context and fail exact-shape assertions — and since `transaction-dependencies.test.ts` and `transaction-sequence-alias.test.ts` are not in the plan's file list, the slice would silently grow to eleven files.
Smallest correction: add to step 2 that the observation is reached only through an explicit option supplied by `submitTransaction` when `observed` is true, never by store-capability detection, and clarify that a caller-supplied observation *callback* is permitted while a caller-supplied *tuple* is not.

**6. Medium — HTTP needs a positive discriminator; an `&& result.context` fallback reproduces the concealment step 3 forbids and the proposed presence tests cannot detect it.**
Plan lines 34–35. Source: `transaction-http.ts:348`, `354`, `368` throw when same-entry context is missing on 406/409/413-limit; `transaction-submission.ts:120–127` asserts the same, but only for conflict/operation-limit/not-acceptable.
Impact: the 503 is the first refusal where absent context is *legitimate* (the preserved stop path), so the existing throw-if-missing guard cannot be reused unconditionally. Without a discriminator carried on the result, the obvious implementation — `if (result.context) return context(problem(...), result.context)` — silently degrades a healthy same-epoch timeout whose capture was skipped or lost into a bare 503 indistinguishable from the stop path. Step 3 names the hazard but the plan never says how HTTP asserts against it, and a boolean header-presence test passes either way.
Smallest correction: require the discriminator on the submission refusal result (e.g. `stop: "deadline" | "owner-stopped"`), and require `transaction-http.ts` to throw `"comparison-timeout refusal lost same-entry context"` when `stop === "deadline"` and context is absent, matching lines 348/354/368.

**7. Low — "same synchronous owner entry" understates the invariant, and the observation's position in the stack is unpinned.**
Plan line 33. Source: `enter` (`transaction-store.ts:341–352`) is a per-instance JS mutex, not a DB transaction; `metadata` (`407–411`) is one statement, so two reads inside one `enter` are two implicit SQLite transactions. The established read pattern is `enter(() => atomic(() => … readContext() …))` (`868–880`).
Impact: the stated invariant is necessary but not sufficient as written. It is currently harmless only because of finding 1, which is exactly why it should be written down rather than relied on silently. Separately, the plan does not pin whether the observation runs in the comparison loop's synchronous deadline branch or in `submitTransaction` after the await — only the former has no interleaving boundary where the maintenance timer could close the owner and turn a clean 503 into a 500 from `enter`.
Smallest correction: say "in one `enter(() => atomic(...))` read transaction", and require the observation to be invoked in `transaction-comparison.ts`'s deadline branch with no intervening await.
