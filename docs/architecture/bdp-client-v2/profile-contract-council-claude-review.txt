## N1. LOW — an unsupported carrier fabricates `blockedPrerequisites` entries
**Location** `packages/conformance/test-support/profile-contract-plan.ts:391` (`|| carrierBlocker` inside `dependencyReady`), consumed at `:399-401`.
**Repro (executed)** Plan profile `read-update` with the real `matrices/read-v1.json` restricted to RU-selected rows — the exact scenario the repair's own test `:332-349` uses:
```
carrierBlocker: current normative artifact/runner carrier does not support read-v1 version 1 on read-update
read.discovery.canonical-navigation => carrier-unsupported blockedPrerequisites: ["read.discovery.scope-service-desc"]
read.discovery.optional-limits      => carrier-unsupported blockedPrerequisites: ["read.discovery.scope-service-desc"]
rows with nonempty blockedPrerequisites: 11
control at profile read (no blocker): same two rows => ready-unexecuted, blockedPrerequisites: []
```
11 rows are reported blocked; 9 are genuine (retired `read.discovery.document`), 2 name `read.discovery.scope-service-desc`, which is selected, planned and otherwise ready.
**Impact** The record attributes dependency failures that do not exist, inverting the doc's claim that "A carrier reason is also recorded at plan level, so unsupported carriers do not hide dependency failures" (`docs/design/profile-contract-planning.md`) and weakening report claim 5's "blocked prerequisite IDs remain visible". At a cumulative RU/TX plan every row with a prerequisite would carry a non-empty list, making the field useless exactly where it was added to be informative.
**Fix** Drop `|| carrierBlocker` from `dependencyReady`; readiness precedence at `:407-417` already surfaces `carrier-unsupported` first. The nine genuine blocks survive (they fail `required.has`), so the existing `toHaveLength(9)` assertion still passes.

## N2. LOW — the carrier rule over-blocks `manifestVersion 2` at Read+Update, which is the next declared slice
**Location** `packages/conformance/test-support/profile-contract-plan.ts:346-349`.
**Repro (executed)** `catalogId: "read-v1"`, `manifestVersion: 2`, profile `read-update`:
```
carrierBlocker: current normative artifact/runner carrier does not support read-v1 version 2 on read-update
histogram: {"carrier-unsupported":43,"unplanned":86}
```
But the real gates admit that combination today: `createConformanceArtifactBundle` requires `manifest.catalogId === \`read-v${catalog.catalogVersion}\`` (`artifact-bundle.ts:115-117`) and `catalogVersion` **must equal 1** (`catalog.ts:110-111`), so every ordinary normative bundle is `read-v1`; the factory applies no `manifestVersion` gate (1 or 2 both parse, `executable-manifest.ts:465-467`); and `validateRunOptions` blocks only v1-at-non-Read and v2-at-Transactional — it explicitly admits **v2 at `read-update`** with a matching exact configuration (`runner.ts:2560-2586`).
**Impact** The emitted reason is factually wrong about the runner, and report claim 4's "support is limited to read-v1 on Read" is inaccurate as a statement about the runner (it is accurate only about the absence of a cumulative RU *catalog/manifest* artifact). Because any future cumulative RU bundle is forced to `catalogId: "read-v1"` by the rules above, the planner will mark the entire next slice `carrier-unsupported`, and since carrier takes display precedence, every real `applicability-unresolved` / `setup-unavailable` / genuine prerequisite verdict is masked (and N1 fabricates blocks on top). Direction is fail-closed, so nothing false is claimed ready.
**Fix** Mirror the actual gates: treat `catalogId === "read-v1"` as supported when `profile === "read"`, or when `manifestVersion === 2 && profile === "read-update"`; or key the blocker on the factory's `expectedCatalogId` rule and the runner's two explicit refusals rather than on profile alone. Reword the reason to name what is actually missing (no normative cumulative RU artifact) instead of asserting a runner refusal.

## N3. LOW — `dependencyReady` is unmemoized, so prerequisite traversal is exponential in caller-supplied manifest bytes
**Location** `packages/conformance/test-support/profile-contract-plan.ts:388-401` (recursion with a fresh `ancestors` set per call site, no result cache).
**Repro (executed)** Manifest where row *k* has one prerequisite action per earlier row (valid: prerequisite actions precede the owned action, prerequisites earlier in catalog order), built from real Read rows:
```
n=12 actions=78  elapsed=4.6ms
n=16 actions=136 elapsed=14.0ms
n=20 actions=210 elapsed=197.1ms
n=22 actions=253 elapsed=843.4ms
n=24 actions=300 elapsed=3759.0ms      (~4.4x per +2 rows)
```
Extrapolating, n≈30 is minutes and n≈36 is hours. A 44-row dense chain (~990 actions, ~150 KB) sits well inside `parseBoundedJson`'s 1 MiB / depth-128 / 100k-node / 10k-entry bounds.
**Impact** Unbounded CPU / an effectively hung planner on a hostile or merely dense manifest — inconsistent with the rest of this module, which goes to considerable length to bound exactly this input (intrinsic byte copies, JSON complexity limits, iterator-free capture). Confined to source-private test support: a CI/test hang, not a service DoS.
**Fix** Three-colour DFS with a per-id memo: cache the boolean once computed, and treat a node already on the gray (in-progress) stack as the cycle sentinel. O(V+E), and it preserves every current verdict including the cyclic case pinned at `:392-397`.
