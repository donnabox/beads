## Findings

**1. Low — `apps/bdptest/src/transactional-sequence-depth-installed.test.ts:543-561` — cleanup-overrun error is recorded twice.**
The 10 s cleanup timer does `failures.push(cleanupReason)` (545) *and* `cleanupReject?.(cleanupReason)` (547); the rejection is caught at 560-561 and pushed again. On overrun the `AggregateError` carries the identical `Error` instance twice and the safe report's `failureCount` is inflated by one. The timer can only fire while the race is pending (if `child` is undefined the `finally` clears it immediately), so the rejection path always records it. Smallest fix: delete line 545. (Compare the deliberate dedup used for the work deadline at 577.)

**2. Low — same file, `565-575` — mandated directory retention is itself reported as a failure.**
`stopped` is correctly made conservative for a pre-ready launch failure (`!launchAttempted || (child !== undefined && …)`), so the directory is deliberately kept — which then trips `if (!directoryAbsent) failures.push(new Error("…directory remains"))` at 575, plus "child remains active" at 568. A deliberate retention is recorded as a defect, contradicting the stated `startupLimitation`. Smallest fix: `if (stopped && !directoryAbsent) failures.push(…)`. (The sibling `transactional-depth-key-order-installed.test.ts:640-649` does not hit this because its `stopped` treats a missing child as stopped; the new, stricter rule is the right one — only the oracle needs to follow it.)

**3. Low — same file, `268` — dead disjunct in the depth gate.**
`row.label.endsWith("fresh-depth")` matches no row (labels are `seed`, `retained-deep`, `original-replay`, `original-resource`, `fresh-deep`, `fresh-key-reuse`, `retained-deep-negotiation`, `fresh-deep-negotiation`). `includes("deep")` already covers all four deep bodies, so the 41-object oracle is complete today, but the dead clause implies a selector that does not exist and would silently let a renamed row skip the depth check. Smallest fix: drop the second disjunct.

**4. Low — same file, `223` — title claims "over packed bytes" while the default entry is the workspace build.**
`entry` defaults to `packages/server/dist/transaction-installed-process.js` (57-59), i.e. a diagnostic workspace artifact, not a fresh pack; only `BDP_TRANSACTIONAL_INSTALLED_ENTRY` (with a declared commit) binds an external consumer. The phrasing matches an existing house idiom (`transactional-snapshot-installed.test.ts:422,796,959`) and the report stays honest via `entry`/`entrySha256`/`workspaceDirty`/`claimEligible:false`, so this is naming, not an oracle defect. Smallest fix (optional): "over the installed entry", leaving packed attribution to the separately bound consumer.

**5. Low (adjudication note, no code change) — control header shape.**
`source-dispositions.md` §1 attributes the control's generic 500 to `transaction-runtime.ts:260-267`. In the real code the strict-preparation throw at `transaction-http.ts:328` is caught first by `handle`'s catch (`:642 empty(500)`), which then sets `x-bdp-development` and, for POST, `vary: Accept` (`:646-647`) — the runtime fallback sets no `vary`. `selection.json` already states this correctly in `markerMeaning`, and the named oracle only requires 500/empty/no marker/no context, so no oracle breaks; an adjudicator comparing an exact header set should expect `vary: Accept` present.

No actionable finding against the docs paragraph (`docs/design/transaction-implementation-progress.md:1996`) beyond style: it is a single unwrapped line with a double blank separator in an 80-col hard-wrapped document, which Biome does not format (`package.json:18-19`, Markdown unformatted), so `format:check` passing is consistent.
