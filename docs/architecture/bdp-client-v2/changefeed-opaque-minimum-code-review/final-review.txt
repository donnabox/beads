### 4. Member-chain formatting likely non-canonical — LOW confidence, gate risk

### 5. Duplicated deadline failure in the new source HTTP callback — OPTIONAL
`packages/server/src/transaction-changefeed.test.ts:1609-1614` pushes the deadline error into `failures` inside the timer, and `:1849-1850` (`catch (error) { failures.push(error); }`) pushes the *same object* again when `controller.signal.throwIfAborted()` rethrows the abort reason. Smallest correction: in the catch at `:1850`, use `if (!failures.includes(error)) failures.push(error);`.

### 6. Owner `admission` marker is unvalidated and has no defense in depth — OPTIONAL (defensive)
`packages/server/src/transaction-store.ts:1834,1845`. `readChanges` relaxes the position grammar purely on a caller-supplied string, with no rejection of other values and no in-entry cross-check. The existing analogue, `observeSnapshot` (`transaction-store.ts:1558-1590`), *derives* `unrecognizedMinimum` from the tuple itself and additionally re-checks `request.kind` before `checkCurrentReadMinimum(..., true)`. The source comment at `:1843-1844` correctly acknowledges that an admission checkpoint is textually indistinguishable from an `after` cursor, so the owner cannot verify the claim; the only guard is `transaction-service.ts:478-479` (`"start" in copied && copied.start === "now"`), which the new boundaries test does pin.

Failing closed on unknown marker values means this is safe today, not a bug. Smallest hardening: add `if (admission !== undefined && admission !== "finite-start-now") throw new TypeError("invalid changefeed admission provenance");` next to the existing `after` type check at `:1842`.

### 11. Observation: the opaque wait is futile by construction, and HEAD doubles its cost — OPTIONAL
On this single-owner authority an unrecognized position token can never become recognized, so every finite `start=now` opaque request burns the whole budget before the mandated 503. At the installed default (1000 ms, `Math.min(5, …)` sleeps) that is roughly 200 extra owner entries per request — each re-running `snapshotCurrentReadMinimum` on the already-frozen tuple, `readContext()`, `checkpointPosition`, and the retained-group probe — and `transaction-http.ts` applies the same loop to HEAD. This is explicitly required by `docs/specs/bdp.md:5847-5849` ("MUST use its bounded minimum-read wait") and matches the already-shipped fresh-Snapshot and current-Resource behavior, so it is not a defect; it is a cost worth stating in the progress note.

## What I verified as correct

**Spec alignment (read in `docs/specs/bdp.md`, not taken from the summaries).** `5841-5851` is the governing text: the general rule at `5841-5843` admits "waits … or returns the normative … catch-up-timeout problem" for all remaining reads, and the explicit MUST at `5845-5849` is scoped to current Bead/Link/properties views with the disclaimer that it does not extend to retained continuations, Snapshots, or incident-Link lists — it does not forbid the changefeed extension. `6994-6995` independently names `transactional.changefeed.consistency-fields` ("honor minimum positions") and `transactional.changefeed.catch-up-timeout` ("A minimum-position read that cannot be served within the wait bound fails with catch-up-timeout"), which the draft now satisfies for this subset. `6149-6151` ("for `start=now`, the head checkpoint the authority observed when it admitted the request") is exactly the single-anchor invariant preserved by capturing inside `run()` before the waiter. `6043-6045` and `6186` confine `Last-Event-ID` precedence to accepted `text/event-stream`, matching the `media === "sse"` gate. `5828-5832` (lexical 400 must not become 304/412/406/SSE, HEAD keeps GET metadata) still holds: `malformedTransactionMinimumHeaders` fires at `transaction-http.ts:404`, and `applyReadHttpSemantics` only transforms status 200/204.

**Precedence consistency.** The "minimum refusal before unsupported-Accept negotiation" rule is not new project behavior: `transaction-http.test.ts:5776-5791` already asserts 503 for a fresh-Snapshot opaque minimum under `{}`, `if-none-match: *`, `if-match: '"absent"'`, and `accept: "text/plain"`. The changefeed extension matches it.

**Selection correctness of the finite path.** `media !== "sse" && "start" in effective && effective.start === "now"` is equivalent to gating on `changefeed` (for non-SSE, `effective === changefeed`), and narrows correctly for TypeScript. With `media === undefined` the request still takes the finite path and negotiation is applied afterwards (200 JSON → 406; 503 passes through). JSON ignores `Last-Event-ID` including repeated/malformed values, because `effective` only switches on `media === "sse"`; the runtime always supplies `lastEventIds` (`transaction-runtime.ts:153-156,174-179`), so the `?? ` fallback never masks repetition. Moving the `minimum` computation after `media`/`fields`/the repeated-ID throw is behavior-preserving since both header helpers are pure. For the finite branch the `?? "unsupported"` is unreachable (all three fields are present and token-valid by the time `:404` has passed), i.e. harmless dead defense.

**Exclusions hold.** `after=`/genesis (no `start` key), SSE (any accepted `text/event-stream`), reconnect-overridden SSE, and foreign epoch/view opaque tuples all keep the strict `transactionMinimumHeaders`/`snapshotTransactionMinimum` path or the explicit `minimum-position` gap. Store-level `minimum === undefined` with the marker set skips the check entirely, so the existing `start=now` JSON cases (`transaction-sse.test.ts:316-329`) are untouched.

**Synchronous capture and frozen retries.** `copied` is frozen before any await and `finiteStartNow` is computed from `copied`, not `intent`; the tuple is snapshot-frozen before `run()`. Test A's post-dispatch mutation of both `intent` and `minimum` is therefore a genuine witness, and `anchors == [anchor, anchor]` with `reads[1].after == reads[2].after == anchor` pins the single admission anchor across the wait while `reads[1].context.scopePosition == "pos-1"` / `reads[2] == "pos-2"` pins per-attempt context recapture. The final `catch-up-timeout` context is the last observation (`pos-2`), matching `waitForTransactionMinimum`'s `error.context`.

**Owner ordering.** The new branch sits exactly where the old minimum check sat, so `readContext` → head → `checkpointPosition` (cursor-expired/foreign-view/parameter) → `start > head` → committed-row corruption probe → minimum → row read → corruption checks is unchanged. Corruption therefore still dominates and cannot be masked by a 503.

**Preflight/lifecycle.** The capture precedes the waiter's policy validation and abort check, which the four preflight rows assert exactly: `captures: 1` always, `reads: 0`, `waits: 0`, `clocks: 0` for `budgetMs: 0` (thrown before `now()` at `transaction-consistency.ts:147-154`) and `1` for the aborted/throwing/NaN rows (`:155-156`, `:161`). The abort callback's ordering expectation `["wait-entered","abort","wait-released","owner-close","close-resolved"]` is reachable: `close()` flips `accepting` synchronously and then blocks on `Promise.allSettled([...active])`, so the drain cannot precede the abort-driven rejection. Post-close probes behave as asserted — `check()` throws "transaction service is closing or closed" for a valid tuple, while a malformed tuple throws "unsupported minimum tuple" first because the snapshot precedes `run()` (same ordering as `snapshot()`/`beginEvents()`), and `enter()` yields "transaction store closed or reentrant" on the raw owner. `store.close()` is idempotent, so the per-test `instance.close()`, the `service()` helper's `cleanup.push`, and `fixture()`'s `owner.close()` can all run.

**HTTP body/length/conditional semantics.** `jsonResponse` sets no `content-length`; the GET length comes from the node delivery boundary (`transaction-runtime.ts:93`) and the HEAD length from `applyReadHttpSemantics:42-46` — both `Buffer.byteLength(stringifyJsonValue(body))`, so `head == get` and `get == String(bytes)` are consistent, and HEAD carries metadata with no body per `5832`. The 503 carries `application/problem+json`, `cache-control: private, no-store`, `retry-after: 1`, no `etag`, no `x-bdp-development-limit`, and the three context headers via `context(problem(...), error.context)`. `if-none-match: *` / `if-match: '"missing"'` are never evaluated on a 503, and the 400 keeps its JSON body under `accept: text/plain`.

**Test D clock discipline.** With `budgetMs: 2`, `now: () => tick`, `wait: ms => tick += ms`, each refusal consumes exactly two attempts and leaves `tick` monotonically increasing across the ten sequential exchanges, so the waiter's `current < previous` guard never trips. The asserted status vector `[200,200,200,503,503,503,503,500,500,400]` matches the dispatch order I traced through the handler for all ten requests, and `attempted` reaches the declared bound of 10.

**Installed callback.** `profile`/`history`/`claimEligible`/`authorityMode` come from `metadata()` (`transaction-runtime-configuration.ts:388-401`) and are non-`undefined` only because the installed child supplies no seams; `startInstalledTransactionCandidate` additionally requires `authorityMode === "canonical"`, which `installedTransactionBinding` re-checks. The three granted routes cover all four exchanges (one grant serves the eligible GET, the opaque GET, and the opaque HEAD on the same URL). The header set passes the raw executor's guards: `HTTP_FIELD_VALUE` admits the spaces in `"malformed reconnect ignored"`, and `bdp-authorization-view` is the one `auth`-substring name explicitly exempted from `isSecretHeaderName` (`http-executor.ts:343-344`) — this callback is the first to send it through `raw.headerLines`, so that exemption is load-bearing here. Abort precedes drain on every exit path, `child.close()` is launcher-memoized so the abort-triggered close and the explicit close share one promise, both `exit` and `close` are required for `cleanClose`, and the directory is preserved whenever closure or drainage is unknown. The ~1 s default budget per 503 fits inside the 5 s executor timeout, the 10 s transport timeouts, the 45 s work deadline, and the 10 s cleanup deadline.

**Typing.** Under `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, and `verbatimModuleSyntax` (both files are inside `tsconfig.check.json`'s `include`), I traced the risky constructs and found none failing: the added parameters are positional optionals, so every existing caller and any narrower owner double stays assignable; `{ ...owner, … }` is safe because `openTransactionStore` returns a frozen plain literal with no side-effecting getters; `{ ...f, owner: delegatedOwner }` spreads the fixture's get-only `owner` into a mutable, override-compatible literal with no excess properties; `Parameters<typeof owner.readChanges>` gives a tuple whose index 0 is required (so `noUncheckedIndexedAccess` does not apply) and whose optional tail spreads back cleanly; the optional-chain `throw` guards narrow `response.wireResponseBytes`, `response.bodyOctets`, and `processEvents.exit`/`close` as the code relies on; `{ ...firstContext }` over a possibly-nullish value is permitted; and `groups[0]?.changes[0]?.resource.id` has an exact precedent at `:576`. All four new imports are used and none is duplicated.

**No regression in neighbouring suites.** `transaction-http.test.ts`'s `gapPair` is only invoked for `types/`, `types/task`, `beads/a/`; its only changefeed route is bare `changes/` (400 malformed). `transaction-sse.test.ts`'s `start=now` minimum cases (`:389-414`, `:879-909`) all use recognized `pos-N` positions on the SSE path, and `:316-329` sends no minimum at all. There are no conformance scenarios combining `changes/` with a minimum (`changes/?start=now` and changefeed+minimum both return no matches under `packages/conformance`). The six-file scope holds, with the documentation change append-only.
