## Findings

### 1. High — `packages/conformance/src/executable-manifest.test.ts:607-641` — `manifestVersion: 1` × `actions: [{ family: "http", … }]` is unverified, and the negative branch is undifferentiated

Problem: the loop at `:608-611` crosses `version ∈ {1,2}` with `actions ∈ {false,true}`. Nothing in the supplied context establishes that a v1 scenario accepts an `http`-family action: the only v1 action fixture in this file (`actionManifest()`, `:41-64`) uses `family: "client"`, and the only `family: "http"` fixtures (`exactManifest`, `:1469-1497`) are v2. `executable-manifest.ts:927-928` only admits `"family"` as a known request key when `version === 2`. Separately, the mixed-case branch at `:627-630` asserts only `toThrow(ManifestValidationError)`, so it cannot distinguish the intended lowercase rule (`:1475-1476`) from a re-regressed secret rule (`:1477-1478`) or from an unrelated v1-action rejection.

Consequence: if v1 does not support http-family actions, `parseExecutableScenarioManifest(source)` at `:632` throws and the test fails on the first gated run — the candidate is frozen and unexecuted, so this burns the authorized validation cycle. Independently, 8 of the 16 branches (the mixed-case ones) pass on *any* throw, which is the weakest possible assertion for a test whose purpose is to prove the lowercase rule was not changed.

Correction: pin issues per branch instead of `toThrow` alone — capture `error.issues` and assert the mixed-case branch contains `"must be a lowercase HTTP field name"` and does **not** contain `"secret headers are not allowed in a scenario"`; for the lowercase branch keep the `toMatchObject`. Then either confirm v1 admits `family: "http"` actions or restrict the `actions` arm to `version === 2` (v2 actions are already covered by the raw test at `:1536-1553`), keeping `requests` across both versions.

No `!` appears anywhere in the ~1,500 supplied lines of source or test; the surrounding code uses `.at(0)` plus an explicit `undefined` throw (`:644-648`, `:665-669`) or optional chaining (`:1521-1522`), and production code reaches for `as string` (`runner.ts:1786`) and `as ScenarioConditionalHeader["form"]` (`runner.ts:1499`) where `!` would be shorter. ### 3. Medium — `packages/conformance/src/runner.test.ts:5587-5598, :5612` — the request-side compatibility projection is never populated, so the leak path the fix actually opens is untested
