### Actionable Findings

#### Finding 1: Cause preservation and sticky fence omitted on sequence cancellation failure in `nextSequence`
* **Severity**: Medium
* **File and Exact Section**: [`packages/server/src/transaction-store.ts`](file:///packages/server/src/transaction-store.ts#L780-L795) (diff chunk around lines 780–795)
* **Concrete Issue**:
  When a sequence member turn encounters an error in `nextSequence`, it attempts compensating cancellation via `cancelSequence(attempt)`. If `cancelSequence` throws, `nextSequence` directly throws `new AggregateError([error, cleanup], "transaction sequence cancellation failed")` without passing the combined error to `fence(...)`:
  ```ts
  } catch (error) {
    state.busy = false;
    if (ownerFailure) throw error;
    try {
      cancelSequence(attempt);
    } catch (cleanup) {
      throw new AggregateError(
        [error, cleanup],
        "transaction sequence cancellation failed",
      );
    }
    throw error;
  }
  ```
  Unlike `execute`, `admit`, and `admitSequence`—which route through `cleanupThenThrow(error, ...)` to fence `combined = new AggregateError([error, failure])`—`nextSequence` does not update `ownerFailure` with the combined aggregate error:
  1. If `cancelSequence` fails due to an SQLite storage failure inside its `atomic` block, `atomic` sets `ownerFailure` to only the storage failure (`cause`). The original sequence execution failure (`error`) is never recorded in `ownerFailure`. Subsequent owner entries (`store.inspect()`, `store.admit()`, etc.) via `enter()` throw `ownerFailure`, which reports only the cleanup failure, dropping the root trigger (`error`).
  2. If `cancelSequence` throws any non-storage failure (where `atomic` does not set `ownerFailure`), `ownerFailure` remains unset. The owner is not fenced despite failed compensating sequence cancellation and abandoned uncancelled pending reservations.
* **Reachable Trigger**:
  An execution error occurs during `nextSequence` (e.g., transaction evaluation failure or injected fault), and the automatic sequence rollback in `cancelSequence` fails during receipt deletion (e.g., storage fault or unexpected state error).
* **Impact**:
  Violates cause preservation across subsequent owner entries. Callers inspecting the fenced owner receive an incomplete error chain missing the root sequence failure. If cancellation fails outside of an engine storage fault, the owner remains unfenced in an inconsistent reservation state.
* **Fix / Next Step**:
  Align `nextSequence` with `execute`, `admit`, and `admitSequence` by routing cancellation through `cleanupThenThrow(error, () => cancelSequence(attempt))` or explicitly invoking `fence(new AggregateError([error, cleanup], "transaction sequence cancellation failed"))` before throwing.

#### 2. Transactional SQLite Failure Hardening
* **Guarded Rollback**: `atomic` verifies `if (db.isTransaction)` before issuing `ROLLBACK` and confirms `cleanRollback = !db.isTransaction`. If `ROLLBACK` itself fails, it aggregates the original error with the rollback failure (`new AggregateError([error, rollback])`).
* **Ambiguous `COMMIT` Sticky Fence**: `committing = true` is set immediately before `db.exec("COMMIT")`. Any error thrown during commit—whether the commit took effect on disk or failed beforehand—triggers `fence(cause)`. `ownerFailure` sticky-fences all subsequent `enter()` and `atomic()` calls until reopen.
* **Clean Rollback Retry**: When `run()` fails due to an actual SQLite constraint violation (`(errcode & 0xff) === 19`), `sqlite && !constraint` evaluates to `false`. If rollback is verified clean, `atomic` re-throws the constraint error without fencing, permitting clean idempotency/caller retry.
* **Acyclic Persistent Error Chains**: When compensating cleanup fails in `cleanupThenThrow`, `fence` creates a new `ownerFailure` wrapping `AggregateError([error, failure])` rather than mutating existing error instances, preventing cycles.
* **No Partial Publication**: Resources, change groups, position metadata, and terminal receipt status commit in a single SQLite transaction. Ambiguous commits fence the owner, preventing tentative reads or partial receipt disclosure.
