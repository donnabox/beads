### Finding 2 — `Object.fromEntries(... .map(...))` silently produces `any`, making two guards vacuous (optional)

**Severity:** low.
**Sites:** `apps/bdptest/src/transactional-alias-installed.test.ts:678–684` (`current`), `700–704` (`currentHeader`), `652–654`; `packages/server/src/transaction-http.test.ts:3103`, `3119–3128`.
**Defect:** the map callbacks return `[name, value]`, which TypeScript infers as `string[]`, not a tuple. That misses `Object.fromEntries`' first overload and selects `fromEntries(entries: Iterable<readonly any[]>): any`. So `current` is `any`, `ReturnType<typeof context>` (used as the `responses[].context` field type at `transaction-http.test.ts:3103`) is `any`, and `currentHeader`'s `value === undefined` guard is not type-driven. Under `noUncheckedIndexedAccess` (`tsconfig.base.json:16`) this is precisely the check the author intended to get.
**Impact:** no compile error and no runtime bug — `current` is provably fully populated by the `if (!value) throw` at line 681 — but the declared typing discipline is lost at exactly the places the review asked to verify, and `assertContext` compares `any` to `string | undefined`.
**Smallest fix:** `return [name, value] as const;` in each callback (and in the module-level `context()` helper at `transaction-http.test.ts:181–188` if that file is touched again), which selects the typed overload.

### Finding 3 — GET/HEAD `content-type` parity is asserted but never anchored (optional)

**Severity:** low.
**Sites:** `packages/server/src/transaction-http.test.ts:3197` + `3207`; `apps/bdptest/src/transactional-alias-installed.test.ts:747–748`.
**Defect:** `getType` is captured from the GET and only compared to the HEAD's value; no assertion pins it to `application/problem+json`. If the header were absent on both, `null === null` / `undefined === undefined` passes. By contrast `content-length` *is* anchored (`transaction-http.test.ts:3198`, installed `736`) and `cache-control`/`retry-after` are anchored to literals, so the rest of the metadata parity check is meaningful.
**Impact:** one oracle in the HEAD-metadata group is vacuous in the failure mode it is meant to catch. The adjacent unselected witness does anchor it (`transactional-collection-minimum-installed.test.ts:1150`).
**Smallest fix:** add `expect(getType).toBe("application/problem+json");` after line 3197, and `expect(get.response.headers["content-type"]?.split(";", 1)[0]).toBe("application/problem+json");` before installed line 747.

### Finding 4 — the live-alias foreign-opaque `Unsupported` path has no source-level (non-HTTP) oracle (optional)

**Severity:** low.
**Sites:** `packages/server/src/transaction-read.test.ts:2287–2355` (row set B); the only coverage is `packages/server/src/transaction-http.test.ts:3240–3258`.
**Defect:** all four B rows (`absent`, `deleted`, `dangling`, `hidden`) resolve to a *missing* alias, so the foreign-view conditioned read at line 2320 always takes the `resource-not-found` bypass at `transaction-read.ts:216` and never reaches `checkCurrentReadMinimum`. Consequently the claim "foreign opaque on a live alias stays `Unsupported`/private 500" rests solely on the four HTTP rows, with no direct assertion that `minimumFor.resolveAlias` on a *visible* target with a foreign epoch/view rejects with `TransactionMinimumUnsupported`.
**Impact:** correct behavior, thinner than it appears; a regression that made the alias branch waitable on foreign tuples would be caught only through HTTP.
**Smallest fix:** add two `await expect(service.readAtMinimum(principal, { ...f.minimum("unknown"), scopeEpoch: "foreign" }).resolveAlias(url("alias/work"))).rejects.toBeInstanceOf(TransactionMinimumUnsupported)` lines (and the view variant) to the F fence test, which already imports the class.

### Finding 6 — outer-deadline cleanup abandons `cleaning`; late events cannot reach the report (accepted limitation)
