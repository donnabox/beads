## Current defects

**1. MEDIUM — Replay/restart claims rest entirely on body equality; `bdp-scope-position` is never checked**
*Location:* `packages/server/src/transaction-http.test.ts:434-464`, `491-524`
*Issue:* `transactionalSequenceResponse` is `additionalProperties: false` over `{results}` only, and `sequenceMemberResult` / `sequenceMemberAliasResult` carry no position field. For a sequence, the `bdp-scope-position` response header is therefore the *only* effect-count evidence available, and neither new test reads it — even though the existing suite establishes the convention at `:184`, `:402` and `:988`.
*Impact:* "already committed prefix members stay committed… replay after listener reopen" is proven only by two identical JSON bodies. A regression that re-executed a member whose re-execution is body-identical would pass. That is not hypothetical: it is exactly the class the installed test guards against at `transactional-alias-installed.test.ts:314` with the comment "A retained prefix must not rerun its alias write" — a re-run `putAlias` returns the same result. HTTP test 2 has that same member (index 1) and no equivalent guard beyond the post-replay `alias/work` read.
*Correction:* alias writes do not advance the scope position (confirmed at `:662`: one create + one `putAlias` ⇒ `pos-1`). So in test 1 assert `pos-2` on the first sequence response, unchanged after `put`, unchanged on both `replay` and `recovered`, then `pos-3` after `fresh`. In test 2 assert `pos-2` after the sequence (create + createLink), `pos-3` after `create("other")`, unchanged by the repoint and by the post-reopen replay.

## Optional hardening

**7.** `exchange()` asserts only `x-bdp-development` (`transactional-alias-installed.test.ts:214`). The set cohort additionally requires `bdp-scope-epoch`, `bdp-authorization-view` and `bdp-scope-position` to be non-empty on every 200 (`transactional-set-installed.test.ts:177-179`); collection-minimum has a full `minimum()` helper. Adding the three-header presence check costs one line and covers the same envelope gap as finding 1 at the installed layer.

**8.** `bodyOctets: response.bodyOctets` is recorded unguarded (`:209`). The field is optional on `HttpExchangeResponse` (`packages/conformance/src/http-executor.ts:90`) and `JSON.stringify` silently drops an `undefined` property, so a future executor change would emit log entries missing the octet count with no test failure. The raw socket executor always supplies it today (`:225`, `:1200`), so this is defensive only; collection-minimum guards it explicitly.

**9.** `sessions` proves two clean exits (`:411-412`) but not two distinct processes. `expect(sessions[0].pid).not.toBe(sessions[1].pid)` pins the restart rather than inferring it from the launcher.

**10.** `transaction-http.test.ts:546` (`f.post(batch([create("b")]), "a")`) is now vestigial. Before this commit it proved the refused alias sequence captured no member key; the alias sequence moved to test 1, where key `"a"` is legitimately claimed, so in test 3 the line posts under a key nothing ever claimed while the test name still says "without key capture". The equivalent sequence-route check survives at `:966-981` (`deep_sequence`). Drop it or re-point it at a key actually claimed earlier in test 3.

**11.** Test 2 replays only after reopen; test 1 replays both before and after (`:457`, `:462`). The plan's done-when asks for comparison-only retry proofs "before and after reopen". One extra pre-reopen replay in test 2 would prove the allocated-id and pinned-endpoint identity stable within a single session too.

**12.** Neither test schema-validates the replayed or recovered bodies (only the first response, `:438`, `:495`). `toEqual` against a validated body covers shape transitively; a direct `validateSequence` call on each makes every response independently checked.
