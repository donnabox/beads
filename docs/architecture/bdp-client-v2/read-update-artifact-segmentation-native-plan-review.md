## Required implementation details within the approved approach

1. **Cross-shard configuration equality must be observed, not inferred from common input.** Current `run` creates its own bootstrap, `baseline` and `sessions` (`read-update-matrix.test.ts:271–309,326–342`). Calling it twice unchanged gives two separate within-run checks. The wrapper must compare each returned bootstrap's branded served configuration and actual `configurationIdentity` to the first shard's baseline, and retain that same comparison for every scenario instance. A negative that changes only the second shard's actual readiness/configuration receipt must fail. Compare neither physical listener ports nor per-scenario database directories as configuration identity. This is a concrete implementation of the plan, not a request for a new binding field or runtime option.

2. **One cooperative budget, with explicit startup boundaries.** Current `run` passes the signal into the runner but not its bootstrap (`146–167,271–304,375–376`); `scripts/installed-reference-observation.mjs:18–85` has bounded ten-second launch/close behavior but no AbortSignal. Put abort checks before starting either shard, before a new scenario launch, and immediately after a launch completes inside the cleanup-protected block. If cancellation occurs during launch, await the bounded launch and close the acquired child before returning failure. Do not start work merely because readiness arrived after the budget expired. One90-second controller plus the existing120-second outer ceiling remains appropriate; it is cooperative cancellation with bounded drain, not a guarantee that all cleanup ends at exactly90 seconds. A real second-shard abort test must leave no child/store owner and no passed summary; a pre-aborted test must launch no second child. No launcher/runner redesign is required.

3. **Migrate all aggregate verification before publishing a successful summary.** The current aggregate contains evidence beyond manifest pass/fail: actual request body lengths, sequence32/33 and diagnostics ceilings, exact route digest, session counts, and credential exclusion (`read-update-matrix.test.ts:832–925`). Keep baseline-specific checks attached to its original genuine report, and apply generic body/credential/session checks to both reports. Do not silently drop those checks because C lacks the baseline's named rows. Existing source writes its optional diagnostic JSON at826–827 before those later assertions; the new successful set summary should be written only after report association, all supplementary checks and cleanup succeed. Failure records may be emitted separately and labeled as failures. Assert literal `claimEligible:false` at set and child report levels; never copy raw credentials, resolved Authorization headers, or arbitrary child stderr into the additive safe summary. Keep genuine reports separate; references/digests plus bounded non-secret metadata suffice.

4. **Close the association boundary, not just source validation.** Check report requested/selected IDs and result IDs exactly against its owned canonical subset, including no missing, duplicate or extra result. Check matching source/artifact/fixture/catalog/exact-route bindings and the actual common installed configuration. Every authored result must actually pass for successful set observation; skipped, blocked, not-run or absent results do not count. Whole credit additionally requires the independently reviewed binding. The new summary should give each canonical required ID either exactly one genuine result reference or an explicit unobserved/unplanned reason. The planned negatives cover this; retain them when factoring the helper.

These are concrete acceptance conditions already consistent with the plan's intent, not reasons to redesign or widen its scope.
