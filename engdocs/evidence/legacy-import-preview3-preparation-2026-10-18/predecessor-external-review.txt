**`internal/storage/graphstore/legacy_import.go:213` (also `:216-218`; doc `docs/reference/graph-legacy-import.md:43`)**

**Issue.** The freshness inventory is `{9 explicit graph/journal/lease/counter tables} ∪ DeleteCascadeTables(false) ∪ DeleteCascadeTables(true)` + `bd_events_seq` + the `config` memory prefix — 26 planes, which the 27 matrix cases cover exactly 1:1. **`docs/reference/graph-legacy-import.md:82-87` vs `internal/storage/graphstore/legacy_import.go:62`**

**Issue.** The doc promises: "If commit or rollback cleanup is uncertain, import conservatively reports `outcome_unknown` (exit 6)… An unsuccessful rollback, including an already-ended driver transaction, does not provide a verified rollback acknowledgment." Line 62 passes `!dryRun` as `withTx`'s `write` flag, so a dry-run takes the read-only cleanup path: `backend.go:226-230` returns `tx.Rollback()`'s error bare, and the deferred rollback at `:214-222` only joins `ErrOutcomeUnknown` when `write` is true. A dry-run is not read-only — it executes the `config issue_prefix` `UPDATE` (`:80`), every native issue/comment/dependency insert, and every graph catalog/payload/version insert.

**Impact.** A dry-run whose rollback fails (driver-level cancellation at the 5-minute CLI budget is the reachable trigger, since the conn is already dead) returns an unclassified error. `graphStorageError` falls through every case to the `default` branch and renders `graph_not_initialized`, exit 5 — telling the operator the graph isn't initialized while a workspace whose entire contract is "must be empty and fresh" may have just been populated behind an unverified rollback. **Fix.** Stop encoding "dry-run" as "read-only": separate `withTx`'s commit decision from its cleanup-classification flag (e.g. `withTx(ctx, staged bool, commit bool, fn)`, or have the dry-run path explicitly `errors.Join(ErrOutcomeUnknown, rollbackErr)`), so a rollback-only transaction that staged writes still demands a verified rollback. Extend `legacy_import_test.go:483-521` over `[]bool{false, true}` for `dry` as well as `deadline`.

**`internal/storage/graphstore/legacy_import.go:247`**

**Issue.**
```go
"SELECT COUNT(*) FROM config WHERE LEFT(`key`,?)=?", utf8.RuneCountInString(kvkeys.MemoryConfigKeyPrefix), kvkeys.MemoryConfigKeyPrefix
```
This is correct, but only incidentally. `MemoryConfigKeyPrefix` is `"kv.memory."` (`internal/storage/kvkeys/kvkeys.go`), pure ASCII, so code-point count, byte count and SQL character count all coincide — byte-wise and rune-wise `LEFT` implementations agree, and the boundary behaves (the `ordinary-config` case at `legacy_import_test.go:416` pins it: `LEFT('kv.memoryx.retained',10)` is `'kv.memoryx'`, correctly not a Memory). The Go side also computes a length that `LEFT`'s result is then compared under the column's *collation*, which the Go side knows nothing about.

**Impact.** No live defect, and the ASCII assumption is independently pinned by `kvkeys.TestMemoryConfigKeyPrefix`, so a non-ASCII rename fails loudly elsewhere rather than silently miscounting here. It is a clarity/robustness item: `RuneCountInString` reads as if the mismatch had been reasoned about when the two semantics simply cannot diverge for this constant.

**Fix.** Derive the length engine-side so Go and SQL cannot disagree at all, and drop the parameter:
```go
"SELECT COUNT(*) FROM config WHERE LEFT(`key`, CHAR_LENGTH(?)) = ?", kvkeys.MemoryConfigKeyPrefix, kvkeys.MemoryConfigKeyPrefix
```
If the computed length is kept, use `len(...)` with a comment naming the ASCII precondition. Optionally add an `ordinary-config` sibling key whose leading bytes overlap the prefix multi-byte-wise, to pin the boundary against either `LEFT` implementation.
