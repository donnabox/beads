# Findings

## 1. BLOCKER — the service-capture discriminator does not discriminate

**Severity:** blocker (test plan; invalidates a done-when gate)
**Location:** plan line 46 (Service capture bullet), line 48 counterfactual #2, done-when #3; source `transaction-service.ts:309–315`, `transaction-read.ts:230`, `transaction-consistency.ts:107`

**Issue.** The plan's experiment is "mutate caller options to a different signal/sourceCondition after admission. Abort the originally captured signal, release the held wait and require no second owner attempt." Both halves already hold on the old code:

- `receiving?.signal` at `transaction-service.ts:314` is an **argument expression**, evaluated once, eagerly, before `waitForTransactionMinimum` is entered. The wait signal is therefore already captured by value for the loop's lifetime. Mutating `receiving.signal` afterwards cannot change it, and aborting the original still trips `signal?.aborted` at `transaction-consistency.ts:107` on the next iteration, before attempt 2.
- A mutated `sourceCondition` is already defeated because `transaction-read.ts:230` appends `sourceCondition: minimum` **after** the spread, overriding any caller value at any enumerability.

**Impact.** The control passes against candidate *and* counterfactual. Done-when #2 ("each bounded old-code counterfactual fails its intended test") cannot be satisfied by it, and done-when #3's "captured original signal" claim would rest on a test that proves nothing — precisely for the slice's most important service-side property, per-attempt option immutability.

**Correction.** Make the mutation observable only through the per-attempt options handed to the authority. Either:
- (a) while the finite wait is held, define an extra own key on the live caller object (`receiving.unknown = 1`) and require the read to still complete — old code re-spreads the live object and rejects `invalid-input` on attempt 2; or
- (b) replace `receiving.signal` with a second, **pre-aborted** signal (or `delete` it) and require completion via an independent satisfying commit — old code passes the mutated signal and rejects `ScopeServerOperationAbortedError` on attempt 2.

Keep the `get signal()` control as the separate (and genuinely discriminating) witness for the eager `receiving?.signal` read, and restate counterfactual #2 as covering the getter *and* the per-attempt re-read, not abort timing.

## 2. Optional (medium) — fallback safety rests on an unstated cross-module invariant

**Severity:** optional, but worth one plan sentence plus one named test case
**Location:** plan lines 22, 44; source `transaction-read.ts:81–93, 235–242`, `authority-read.ts:304–311, 1054`

**Issue.** On capture failure, both the facet and the service hand the **raw** caller options to the authority with **no** `sourceCondition: minimum`. That is safe only because capture's rejection set is a subset of the authority's. I verified it currently is, for every shape — but one case is held together non-obviously: for an own **non-enumerable unknown key**, `ordinaryDeliveryOptions` rejects via `Reflect.ownKeys` (`:81–93`), while the authority rejects only because `ownData` re-publishes every own data property as *enumerable* (`authority-read.ts:310`) before `Object.keys(receiving).some(...)` at `:1054`.

**Impact.** If that normalization ever changed, the fallback would deliver a **successful read that ignores the configured minimum** — the exact "unconditioned fallback" the plan forbids. Latent, not live.

**Correction.** State the invariant explicitly ("capture must reject only shapes the authority rejects, else the fallback serves an unconditioned read"), and require the witness discriminator by name on the `perform` path rather than the ambiguous "unknown": `Object.defineProperty({}, "unknown", {value: 1})` and `Object.defineProperty({}, "signal", {value: <not a signal>})`, asserting `invalid-input` and zero owner entries. `transaction-read.test.ts:1659` already carries the first for alias; say the perform mirror must retain it.

## 3. Optional (low) — lifecycle precedence differs by mode; the plan overstates "the authority's"

**Severity:** optional
**Location:** plan lines 26, 45; source `transaction-service.ts:123–131`, `transaction-read.test.ts:1725` vs `:1732`

**Issue.** After `service.close()`, a previously obtained guarded facet rejects through the **service's** synchronous `check()` (`Error("transaction service is closing or closed")`), not through the authority and not through an observed Promise — capture is never reached. The existing alias test pins exactly this asymmetry: synchronous throw in service mode (`:1725`), `code: "server-closed"` through a Promise in direct mode (`:1732`). The plan's lifecycle bullet asks for "the authority's existing closed/reentrant precedence" without distinguishing modes.

**Impact.** An implementer mirroring the bullet literally for the service writes a failing test, or "fixes" `run`/`check` and changes service admission semantics outside the stated scope.

**Correction.** Split the bullet: direct facet → authority `ScopeServerClosedError`/`reentrant` through the observed Promise; service → unchanged synchronous `"closing or closed"` admission throw with capture unreached.

## 4. Optional (low) — route gate pre-empts receiving precedence on `perform`; state the precondition

**Severity:** optional
**Location:** plan lines 44–45; source `transaction-read.ts:226–227`, `:32–56`

**Issue.** Unlike `resolveAlias`, `minimumFor.perform` evaluates `isCurrentTransactionMinimumRead` **before** any capture or authority lifecycle check and rejects with a bare `TypeError`. Every receiving/lifecycle discriminator on the perform path must therefore use an in-subset request or the TypeError pre-empts the expected `invalid-input`/`server-closed`/`reentrant` outcome. Line 44 says "valid literal requests"; the lifecycle bullet (line 45) does not repeat it. Separately, that gate reads `request.kind`/`.resource`/`.collection`/`.continuation` as plain property accesses (`:32–56`) — only `id` is descriptor-read (`:38`) — so caller accessors on those keys still execute before the authority sees the request.

**Impact.** A literal reading yields either a confusingly failing test or pressure to broaden request classification, which the plan forbids.

**Correction.** Add "in-subset request required" to the lifecycle bullet, and scope line 44's "no getter/trap invocation" assertion to the **delivery-options object**, naming `transaction-read.ts:32–56` as a known deferred residual of the same class.
