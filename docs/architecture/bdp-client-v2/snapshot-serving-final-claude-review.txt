## Findings

### 1. LOW-MEDIUM — the only pinned repeated-decision evidence runs under vitest's default 5 s timeout
**Location:** `packages/server/src/transaction-snapshot-http.test.ts:665-713`.

`vitest.config.ts` sets no `testTimeout`, so this test gets the 5000 ms default. Its work: 4,000 inserts of ~1 KiB bodies, **three** runtime close/reopen cycles (`f.offline` for the insert, then `f.state()` twice), and 8 full bounded passes — decode + `validateServerBead` + `checkGraph` + SHA-256 page packing over ~4 MB each, externally measured at ~90 ms per decision on this exact record shape.

The sibling core file budgets every comparable near-ceiling test explicitly: `transaction-snapshot.test.ts:569` (15 s), `:590` (30 s), `:652` (15 s), `:819` (15 s). The existing offline-4097 test in this file (`:450-491`) does pass under the default, but it inserts *empty-properties* records and both its requests refuse at the O(1) count check before any decode — it never performs the pass this test performs eight times.

**Impact.** `transaction-snapshot-serving-progress.md` cites this test as the pinned-Node-24 repeated-decision witness. A timeout on a loaded runner destroys the measurement and the `repeated-nonallocating-snapshot` `console.info` record instead of producing evidence. I did not run it (per the instruction to stay clear of the author's final runs), so this is a budget-margin finding, not an observed failure.

**Bounded fix.** `}, 15000);` on `:713`, matching the file-set convention.

### 2. LOW — prior installed finding 8's tautology was replaced with a different tautology, and the doc now claims a control that cannot fail
**Location:** `apps/bdptest/src/transactional-snapshot-installed.test.ts:67-68`; doc claim at `docs/design/transaction-snapshot-installed-observations.md:68-69`.

```ts
if (response.headers["content-length"] !== undefined)
  expect(Number(response.headers["content-length"])).toBe(response.bodyOctets);
```

`decodeResponseBody` (`packages/conformance/src/http-executor.ts:1217-1235`) throws `disconnect` when `framed.byteLength < expected` and `invalid-body` when `framed.byteLength > expected`, then returns `framed`; `parseRawResponse:1200` sets `bodyOctets = body.byteLength`. So whenever a content-length-framed response parses at all, `Number(content-length) === bodyOctets` holds **by construction** — exactly as unfalsifiable as the `Buffer.byteLength(bodyText)` comparison it replaced. And when `content-length` is absent (the chunked branch at `:1212-1215`), the guard is skipped, so there is no body-framing assertion at all.

**Failure scenario.** A server regression that framed manifest bodies with `transfer-encoding: chunked` passes this test silently with zero framing coverage; a genuine length/body mismatch is caught by the executor's own transport error, not by this assertion. Either way `"Declared body length is checked against actual framing"` names an observed control the test does not contribute.

**Bounded fix.** Make the declaration mandatory and compare against the wire instead of against a derived value: `expect(response.headers["content-length"]).toBeDefined()` plus `expect(response.wireResponseBytes!.length).toBeGreaterThan(response.bodyOctets)` — or delete the line and the doc sentence.

### 3. LOW — the independently measured identity covers one module, not the closure that executes, and Limits does not say so
**Location:** `apps/bdptest/src/transactional-snapshot-installed.test.ts:37-38`; doc `:11-13` and Limits `:74-88`.

`entrySha256` hashes only `realpathSync(entry)`. The installed process's behavior comes from its whole package closure, which the entry merely imports. The closure identity remains `child.ready.payloadIdentity` — the subject's own computation over its own closure, which prior finding 7 correctly characterized as self-attestation. The doc's `"the realpath entry's independently measured SHA-256"` is literally accurate but the Limits section, which does enumerate every other non-claim, omits it.

**Failure scenario.** A packed run whose tarball entry file is byte-identical while a sibling module in the installed closure differs: `entrySha256` matches, `declaredSourceCommit` matches, the ledger reads as pinned, and nothing the test measured distinguishes the two artifacts.

**Bounded fix.** One Limits sentence: the measured SHA-256 covers the entry module only; the executing package closure identity remains the subject's self-attested `installedPayloadDigest`.

### 4. LOW — the explicit-commit guard is file-local, but the doc states it as a property of packed-run mode
**Location:** test `:35-36`; doc `:8-15`; sibling `apps/bdptest/src/transactional-matrix.test.ts:36-38` and `:79-81`.

Separately, `"The external packed-run supervisor separately checks clean source, builds that exact commit, packs/installs it, and supplies both environment values"` (`:14-15`) is stated in the present tense about a process that exists nowhere in the repository — nothing sets those variables in `scripts/`, CI, or any manifest.

Editing the sibling is out of scope per the disposition ("do not edit shared launcher/binding/runner"), and root accepted the supervisor split. The **disclosure** is in scope: because this commit deliberately chose not to fail fast on a dirty worktree, the supervisor is the only enforcement, and the doc asserts its behavior rather than requiring it.

**Bounded fix.** Scope the doc sentence to this test file, note that the sibling installed matrix observation retains the inherited default, and phrase the supervisor line as a requirement on an external packed run with nothing in-repo enforcing it.

### 5. LOW — the new seeded oracle is a recursive subset match, so added members escape it
**Location:** `apps/bdptest/src/transactional-snapshot-installed.test.ts:406-423`.

`toMatchObject` permits extra properties at every nesting level, so `properties`, `metadata` and the row itself are only subset-checked. Prior finding 1's bounded fix used `toEqual` on `properties` for this reason.

**Failure scenario.** A projection that *adds* a member uniformly — `properties: { title: "café 🦉 b00", injected: 1 }` on every snapshot bead *and* every point read — passes `assertSeeded`, and also passes `assertReplica` (`:348-351`) because both surfaces agree. The doc's `"A consistently wrong seeded postimage fails even if all server projections agree"` (`:27-28`) is true for wrong and missing values — the dropped-`properties` and mojibake cases that motivated the finding are genuinely caught — but not for added ones.

**Bounded fix.** Inside `assertSeeded`, add `expect(row.properties).toEqual({ title: … })` and `expect(row.metadata).toEqual({ seeded: … })`, keeping `toMatchObject` for the row-level fields that legitimately vary (`revision`, `ownedLinks`). `metadata` is an admitted create-operation field (`packages/protocol/src/read-update-values.ts:69,84`), so the exact comparison is well-defined.

### 6. LOW — no ledger is emitted when the fixture fails to start
**Location:** `apps/bdptest/src/transactional-snapshot-installed.test.ts:147-155`; failure paths at `:179-183` and `:190-199`.

`withInstalled` calls `start()` *outside* `finishObservation`, and `report` is unreachable before `baseline` exists. A launch failure or a ready-metadata validation failure therefore yields correct AggregateError causes and **zero** `private-installed-snapshot` records on stdout.

**Failure scenario.** A harvester scanning observation logs cannot distinguish "the installed child never launched" from "the test file never ran" — on a commit whose stated purpose is a sound evidence artifact. The doc's `"ledger explicitly says passed or failed … including on cleanup failure"` (`:64-66`) is correctly scoped and does not overclaim, so this is an undisclosed gap rather than a false statement.

**Bounded fix.** Emit a minimal record from both `start()` failure paths — `{ observation, outcome: "failed", stage: "startup", declaredSourceCommit, workspaceDirty, entry, entrySha256, claimEligible: false }`, omitting `binding` — or add one doc sentence stating that a startup failure produces causes but no ledger.

### 7. LOW / informational — the ledger now records issued continuation URLs, including HMAC page tokens
**Location:** `apps/bdptest/src/transactional-snapshot-installed.test.ts:264`, logged at `:319-320`.

`observations[].url` for continuation reads is the server-issued `…snapshot?snapshot=<uuid>&stream=…&page=sp_<n>_<43-char HMAC>`. The adjacent comment commits to never logging credentials, and a page token is a per-snapshot capability component derived from the secret disposition seed (`transaction-snapshot.ts:115-120`). Mitigations are real: the route refuses unauthenticated requests before any token lookup (`transaction-http.ts:322`), and the child plus its temp store are destroyed in cleanup, so the token is dead before the record is read. The prior review explicitly asked for route identifiability, so the addition is sanctioned — recording it so the tension with the comment is visible rather than discovered later.

**Bounded fix, only if a stricter reading is wanted.** Record `pathname` + `stream` + the token ordinal, or substitute the token's length for its value.
