## Findings

**1. Transactional unapplied-`metadataChange` diagnostics are now request-pointer-proportional against a budget equal to the request cap, so a legal in-cap request raises an internal error instead of `validation-failed`. Severity: medium.**

Location: `packages/server/src/transaction-batch.ts:442-452` (`diagnosticBytes: 65536` + the new pointer-bearing message), with `packages/server/src/transaction-submission.ts:60` (65536-byte request cap) and `packages/protocol/src/json-admission.ts:350-354` (the throw).

Impact: JSON Pointer escaping doubles `/` to `~1`, so a pointer can be ~2× the body bytes it came from. Measured against the built `dist`:

| case | body bytes | first-entry outcome at HEAD | at `b0a6bca` |
|---|---|---|---|
| `metadataChange`, 32,727-char key | 32,808 | `JsonDiagnosticBudgetError` | 66-byte entry |
| `propertiesChange`, 32,810-char key | 32,811 | `JsonDiagnosticBudgetError` | same throw |

Nothing catches `JsonDiagnosticBudgetError` on this path, so it escapes `evaluateTransaction` → `executeClaim`. `cleanupThenThrow` (`transaction-store.ts:735-746`) does retract the pending reservation cleanly, so there is no state corruption and no poisoned idempotency key — but the request is permanently un-refusable: every retry yields the same internal error instead of the `validation-failed` Problem that `docs/specs/bdp.md:3442-3473` and the `read-update.numeric-model.round-trip-admission` row require. The repo already encodes the rule being broken: `read-update-runtime-limits.ts:36-42` requires `diagnosticBytes >= 2*(requestBodyBytes+propertiesBytes)+2 + 21760` precisely so the first diagnostic always fits, and the transactional path is the one budget that never passes through `snapshotReadUpdateRuntimeLimits`. (The development authority *is* safe: 512 KiB vs a 283,906-byte computed floor — I checked.) Secondary effect: metadata diagnostics went from a constant 66 bytes to pointer-sized, so metadata updates can now hit `diagnosticsTruncated` where they previously returned the complete list — legal, but a reporting regression.

Scope honesty: the `propertiesChange` and both create paths had this exposure at `b0a6bca` (via the retained `instanceLocation`) at the same threshold. The delta newly extends it to `metadataChange`.

Fix: route the transactional budget through `snapshotReadUpdateRuntimeLimits` (or size `diagnosticBytes` to its floor for a 65536-byte cap), or omit the pointer label when the resulting entry would not fit — an unlabelled message is strictly better than an internal error. Test gap: `transaction-store.test.ts:2670-2724` nails the truncation boundary exactly (2 entries at exactly 65536, 1 on overflow) but never covers first-entry-cannot-fit, which is the case this change makes reachable.

**2. `instanceLocation: pointer` in both new default callbacks is dead on every reachable path, and reads as the defect under repair. Severity: low.**

Location: `packages/server/src/development-authority.ts:130` and `packages/server/src/transaction-batch.ts:450`.

Impact: for `createBead`/`createLink` the shared formatter recomputes the location from `occurrence.pointer` and ignores the caller's (`member-numeric-diagnostics.ts:24,30`); for `updateBead`/`updateLink` both branches discard it. Since the schema admits number literals only under `properties`/`metadata` and their `*Change` `value` subtrees (I checked `revisionProvenanceInput`/`revisionActor` — all string/null, and carrier validation runs with numbers replaced by `0`), there is no operation where that member survives. So both authorities still *look* like they emit request pointers as document locations, with the only protection living in a separate module. If a future operation kind is added that `memberNumericDiagnosticBudget` does not wrap, the raw `instanceLocation: pointer` reaches the wire and the closed defect returns silently. Related latent edge: the update branch's `!startsWith("/metadataChange/")` else-branch means any future numeric position outside the two change lists inherits the properties treatment and emits a bare `"unsupported number"` with no location at all.

Fix: delete `instanceLocation` from both callbacks (the formatter supplies it where it is meaningful), or guard it with the same prefix test used for the message.

**3. Numeric update diagnostics retain caller `type`/`schemaLocation`, which `bdp.md:3459` says must be absent — and the delta's new tests now enshrine that shape. Severity: low.**

Location: `packages/server/src/member-numeric-diagnostics.ts:45-50`; codified by `packages/server/src/member-identity.test.ts:1439-1441` and `:1486`.

Impact: `docs/specs/bdp.md:3451-3459` splits diagnostics into effective-Type-contract failures (which carry `type` + `schemaLocation`, plus `instanceLocation` when the failure lies within `properties`) and "every other cause", for which "`type` and `schemaLocation` are absent". A numeric admission refusal is always the latter — it happens before any Type contract is evaluated. The formatter strips `document` and `instanceLocation` mislabels but passes `type`/`schemaLocation` straight through, and the two new tests assert `expect(admission.diagnostics).toEqual([{ message, type, schemaLocation }])`, locking in an entry that is simultaneously Type-contract-shaped and missing the `instanceLocation` that shape requires. Not reachable through either shipped authority (neither callback supplies them), so the exposure is to embedders of `prepareMemberExecution`. The field retention itself predates the delta; the tests asserting it do not.

Fix: drop `type`/`schemaLocation` in the update branch the way the metadata branch already does, and amend the two tests — or, if caller-supplied contract framing is intentional here, say so in the spec paragraph rather than leaving it contradicted.
