## Findings

**1. Medium — the reopen-provenance gate can be silently bypassed by the new rows.**
Location: `apps/bdptest/src/transactional-matrix.test.ts:300–305`; plan lines 62, 68, 70(c), 70(e).
Issue: the only machine check that post-reopen receipt reads carry advancing generation provenance is filtered by `e.request.id.startsWith("reopened-")` and pinned at exactly 2. Currently exactly two actions (`reopened-completed`, `reopened-failed`) in `transactional.receipt.readable` match. The plan's update list names manifest counts, readiness, pass count and session count, but never this assertion or the `reopened-` id convention.
Impact: two bad outcomes. If the new post-reopen reads are named `reopened-*`, `toHaveLength(2)` fails for a non-defect reason. If they are not, the assertion still passes at 2 and the new scenarios' generation provenance is never asserted at all — while done-when (c) ("completed/failed GET/HEAD plus reopen carry intact source/generation provenance") reads as satisfied. That is a weakened gate hidden behind a naming accident.
Correction: state in the plan that every post-reopen `transactional.receipt-read` action id in both new rows must begin with `reopened-`, and pin the new expected count explicitly — 5 on the plan as written (2 existing + 2 from scenario 1's "reread both receipts" + 1 from scenario 2's single retained compare). Do not relax `:301` to `toBeGreaterThan`.

**2. Medium — the plan's row numbering contradicts the canonical catalog order it mandates, and insertion position is load-bearing.**
Location: plan lines 9, 27, 39, 62; `profile-contract-selection.ts:61–89`; `transactional-cumulative.test.ts:92–95` and `:99–101`; `transactional-matrix.test.ts:353, 375–377`.
Issue: in the merged selection, `transactional.set.cardinality` is at index 149 and `transactional.set.singleton-targets` at 150 — both between `transactional.batch.rollback` (136) and `transactional.receipt.readable` (154). The plan numbers singleton-targets "1" and cardinality "2" and says "The first… the second…", while line 62 requires "canonical catalog order". `:92–95` hard-requires manifest order to be the catalog-order subsequence and `:99–101` requires coverage rows in manifest order.
Impact: following the plan's narrative order, or appending at the end, fails the first cumulative test. Prepending additionally breaks the existing cross-wire control, which reads `value.scenarios[0]!` at `:353` and then asserts on `transactional.batch.atomic-commit` at `:375–377`.
Correction: state the insertion explicitly — manifest and coverage positions 3 and 4, after `transactional.batch.rollback` and before `transactional.receipt.readable`, cardinality before singleton-targets — and renumber the two plan sections to match so narrative order is not mistaken for manifest order.

**3. Medium — coverage-artifact obligations are far stricter than "all six coverage flags remain false".**
Location: plan lines 60, 62; `transactional-cumulative.test.ts:102–113`.
Issue: each coverage row must carry `wholeContract:false`, a `reason` containing the literal substring `"Whole contract remains unqualified"`, and `bindings` **strictly equal** to `[{ scenario: <id>, assertions: [<action.id>:<assertion.id> for every action and assertion in manifest order] }]`. The plan commits only to "All six coverage flags remain false" and lists coverage as an owned artifact.
Impact: the two new coverage rows are the bulk of the increment's mechanical content (existing rows enumerate 25+ ids each). A single missing, extra or misordered id, or a reason missing that substring, fails the first cumulative test with nothing in the plan explaining the contract — and any later assertion-id edit must be mirrored.
Correction: add to the plan that each new coverage row carries `wholeContract:false`, a reason containing `"Whole contract remains unqualified"`, and `bindings[0].assertions` enumerating `${action.id}:${assertion.id}` for every action/assertion in manifest order, with coverage row order equal to manifest order.

**4. Medium — the installed cohort deadline has zero headroom and cannot be raised, yet the plan roughly doubles the workload while declaring bounds unchanged.**
Location: plan line 68; `transactional-matrix.test.ts:105–107, 288, 311`.
Issue: the current cohort is 36 manifest actions and 5 installed child launches under a default `budgetMs` of 90000 with a hard rejection of `budgetMs > 90000` at `:106`, inside a 120000 vitest timeout. The plan permits "at most 40 new actions" and adds four more launches (5→9) while asserting the aggregate 90s / outer 120s bounds "apply without increase". The two scenarios as described land at roughly 35–38 actions, i.e. near the ceiling, not well under it.
Impact: a ~2× workload inside an unraisable deadline. Overrun surfaces as `"installed cohort deadline"`, indistinguishable from a genuine target defect, and the only escapes are editing the `:106` guard (forbidden by the plan's own "without increase") or re-scoping the rows after authoring.
Correction: before freezing the two rows, measure the current four-row installed run's wall clock and record the measured headroom in the plan; derive the per-scenario action budget from that measurement instead of a nominal 40. If six rows do not fit inside roughly 70% of 90s, record it as a concrete root decision (raise the cohort guard or split the cohort) rather than leaving the conflict implicit.

**5. Low-Medium — control 5 and the second half of control 3 have no existing seam in the installed helper.**
Location: plan lines 53, 55; `transactional-matrix.test.ts:93–104, 160–173, 227–232`.
Issue: `observe()`'s control surface is exactly `budgetMs | invalidReceiptCredentials | signal | children | afterExchange | ready | manifest`. Routes are derived at `:160–173` from the module-level canonical `bundle`, never the mutated `runBundle` — so `control.manifest` cannot add or remove an exact route (which the plan correctly notes at line 22). `afterExchange` returns `Promise<void>` (`:99`) and the response is returned unmodified at `:227–232`, so it cannot corrupt a receipt id or retained body. The "existing test wrapper pattern" the plan invokes exists only at `transactional-cumulative.test.ts:596–604`, a unit-level raw wrapper.
Impact: as written, control 5 ("Remove one new exact static route and prove that request never reaches the target") and control 3's corruption clause read as free but are unimplementable; the predeclared-route refusal they depend on does exist (`http-executor.ts:548–567`), so only the test seam is missing. Risk is that an implementer reaches for the route derivation or weakens route policy to make the control pass — which the plan itself forbids.
Correction: state that `observe()` gains two explicitly negative-only controls in the owned file — a route-suppression option applied to `exactMode.routes`, and a response-transform option distinct from the void `afterExchange` gate — or assign the receipt-corruption control to `transactional-cumulative.test.ts`, where the wrapper already exists. Both files are already owned, so this is a scope statement, not a new seam decision.

Correction: in the dependency paragraph, list both consumed S2a capabilities — the two singleton set targets and set members admitted on `operations/batch` — and in line 45 distinguish the existing batch *receipt-authority suffix* from the new batch set-member serving.
