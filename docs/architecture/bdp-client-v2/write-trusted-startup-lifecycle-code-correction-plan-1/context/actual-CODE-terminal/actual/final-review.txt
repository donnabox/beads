### 1. Medium — unrecognized post-ready IPC control silently terminates the lifecycle with exit 2; branch is neither documented nor witnessed

**File:** `packages/server/src/reference-deployment-process.ts:50-60`, with the consequence at `:83`

**Defect (static).** The control receiver records a failure but then stops unconditionally:

```ts
control = (message) => {
  try { ...; if (data.command !== "close") throw new Error("invalid control"); }
  catch (error) { controlFailure ??= error; }
  stop();                      // runs on every message, valid or not
};
```
`stop()` aborts and resolves `stopped`, so `Promise.race([stopped.promise, runtime.completion])` returns; then `:83` `if (controlFailure !== undefined) throw controlFailure;` turns a clean shutdown into `primary`, yielding the fixed stderr line and exit 2.

So any post-ready parent message that is not exactly `{command:"close"}` — an oversized message, an extra field, or a future `{command:"ping"}` — both terminates the deployment and reports it as a startup failure.

**Practical impact.** Two gaps, not one. (a) The pinned contract at `docs/design/startup-configuration.md:731-734` enumerates only "SIGTERM, SIGINT, IPC close and disconnect" as stop triggers and ties exit 2 to "refusal"; this branch is a fifth trigger with refusal semantics and is unstated. (b) Neither new test file reaches it. The only invalid-IPC witness, `guard("invalid-ipc")` (`apps/bdptest/src/reference-deployment-lifecycle-installed.test.ts:937-955`), sends `{configuration:{}}` as the *first* message, which is consumed by the `received` handler at `:46`, not by `control`. `stop()` in the installed test (`:599-622`) always sends the valid `{command:"close"}` and asserts exit 0. The doc's own witness accounting (`:736-748`) claims four guard children cover entry-point guards, but none covers the control receiver.

**Smallest contract-preserving correction.** Keep the fail-closed behaviour and make it observed and stated: add one installed callback (or extend I21, which already owns one guard child and 0 HTTP) that launches normally, sends `{command:"stop"}`, and asserts `{code:2,signal:null}` plus the exact fixed stderr; and add one clause to `startup-configuration.md:731-734` naming an unrecognized control as a stop-and-refuse trigger. No new API, mechanism, or budget change. If instead the intent is that only `close` stops, move `stop()` inside the success path and leave an unrecognized control inert — but that changes behaviour and needs its own acceptance, so I recommend documenting plus witnessing the existing semantics.

### 2. Low — RU request task's derived rejection is discarded, unlike the TX dispatcher

**File:** `packages/server/src/development-runtime.ts:551-555`

```ts
const server = createServer({ maxHeaderSize: 16 * 1024 }, (request, response) => {
  const task = handle(request, response);
  pending.add(task);
  void task.finally(() => pending.delete(task));   // derived promise adopts task's rejection
});
```

**Defect (static asymmetry).** `.finally()` returns a *new* promise that adopts `task`'s rejection; `void` discards it. `close()`'s `Promise.allSettled([...pending])` handles `task` itself but not this derived promise. `transaction-runtime.ts:300-307` does it correctly:

```ts
void task.then(() => pending.delete(task), () => pending.delete(task));
```

`handle()`'s own catch block (`:544-549`) is itself capable of throwing: `refused()` calls `response.setHeader("connection","close")` at `:103` *before* any destroyed/headers-sent check, and `setHeader` throws `ERR_HTTP_HEADERS_SENT` once headers are sent; `empty()` calls `writeHead` with the same exposure. A secondary failure inside the catch therefore escapes `handle()`.

**Practical impact.** In the trusted child process, an escaped rejection becomes a process-level unhandled rejection (Node's default is throw), which would bypass the fixed `reference deployment startup failed` / exit-2 diagnostic that `reference-deployment-process.ts:112-117` and the installed `refused()`/`stop()` assertions depend on. **I could not establish a concrete reachable throw path** — every post-`writeHead` code path returns immediately, and the destroyed-socket cases in S12 go through the guarded early returns — so this is a latent robustness asymmetry, not an observed defect.

**Smallest correction.** One line, matching the TX dispatcher exactly and preserving the `pending` drain contract:
`void task.then(() => pending.delete(task), () => pending.delete(task));`

### 3. Low — post-publish guards throw outside the cleanup scope, and one explanatory comment is inaccurate

**Files:** `packages/server/src/development-runtime.ts:757-762`; `packages/server/src/transaction-runtime.ts:527`

**Defect (static).** In both runtimes the startup `try…catch` that owns listener and owner cleanup ends before the prepared result is assembled (`development-runtime.ts` try spans `:664-717`; `transaction-runtime.ts` `:421-476`). The final guards run after `published = true`:

```ts
// development-runtime.ts
if (!address || typeof address === "string" || !checkedOwner) throw new Error("missing prepared owner");
const state = referenceDeploymentState(prepared.handle);
if (state.profile !== "read-update") throw new TypeError("prepared Read/Update required");

// transaction-runtime.ts
if (!checkedOwner || !configurationMetadata) throw new Error("missing prepared owner");
```

If any fires, the function rejects while the listener is bound and the owner (RU) or service+owner (TX) is open, and no `close` handle reaches the caller — exactly the unknown-ownership state the lifecycle is built to avoid. The same shape appears at `reference-deployment-runtime.ts:17-33`: if the defensive `await runtime.close()` rejects, the close error replaces `new Error("prepared lifecycle unavailable")`, losing the primary reason (and `runtime.scope` is returned without the `typeof` check applied to `listenUrl`/`history`).

I traced all three guards as **unreachable** on the current code: `checkedOwner` is always set by `acquireOwner()`/`prepareOwner()` under `prepared`; `profile` is already checked at `development-runtime.ts:201` and `:625`; and no await separates `published = true` from the guards, so `server.address()` cannot go null there.

**Separately, the comment is wrong.** `development-runtime.ts:758` says "Already checked immediately after listen. No asynchronous work intervenes here." Asynchronous work *does* intervene: `await Promise.resolve()` at `:690` sits between the two `server.address()` reads. The conclusion still holds (a fault in that microtask is caught by `checkPrepared()` at `:691`), but the stated reason is not the operative one.

**Smallest correction.** Move the three post-return guards inside the existing `try` in each file (or have the final assembly re-enter the same cleanup path), so a defensive failure closes what startup acquired; and restate the `:758` comment to the actual invariant ("no await separates `published` from this read; an intervening listener fault is caught by `checkPrepared()` at :691").

### 4. Low — the installed report's secret tripwire cannot screen its own base64 wire fields

**File:** `apps/bdptest/src/reference-deployment-lifecycle-installed.test.ts:272-275`, with the unscreenable fields at `:703-706` and `:894-895`

```ts
const text = JSON.stringify(report);
if (f.secrets.some((secret) => text.includes(secret))) failure ??= Error("unsafe lifecycle report");
else console.log(text);
```

**Defect (static).** The scan is a substring test over the serialized report, but the report embeds raw server bytes only in base64 form: `wireBase64: Buffer.from(response.wireResponseBytes).toString("base64")` (`:703-704`) and `state.refusalWireBase64 = bytes.toString("base64")` (`:895`, reached through `controls` → `beforeShutdown`). A credential present in those bytes is base64-encoded and will not match `text.includes(secret)`, so the report is printed to stdout.

**Practical impact.** Not currently exploitable — I checked every response path that the 126 finite requests and 2 CONNECT peers can reach, and none echoes the `Authorization` header: `refused()` emits a fixed problem plus `www-authenticate: Bearer realm="bdptest-development"`, the RU CONNECT reply is a literal 405, and the TX CONNECT reply is `transactionHttpProblem("malformed-request")` over the authority-form target, which carries no credential. The gap is in the safety net itself: it is weakest for exactly the two fields whose purpose is to carry unredacted server bytes, and the test rotates real `randomBytes(32)` secrets (`:305-308`, `:1012-1017`).

**Smallest correction.** Screen the decoded form too, inside the existing check — e.g. collect the base64 fields and test `f.secrets.some(s => decoded.includes(s))` where `decoded = Buffer.from(b64, "base64").toString("latin1")`; or test each secret against `response.wireResponseBytes`/`bytes` before encoding. No new mechanism, no change to what is recorded.

### 6. Low — the RU prepared bind host is neither taken from nor asserted against `handle.listener.host`

**Files:** `packages/server/src/development-runtime.ts:675`; `packages/server/src/reference-deployment-runtime.test.ts:541`

```ts
server.listen(options.port, (transport?.host as string | undefined) ?? "127.0.0.1", () => { ... });
```

**Defect (static).** The intended **port** is pinned twice (`:666` checks `prepared.handle.listener.port` against `options.port`, and `options.port` originates from `installed.port`), but the **host** is read from `transport.host` — i.e. from the registry's `installed.host` — never from `prepared.handle.listener.host`. The two are equal today only transitively, because `reference-deployment.ts:302` builds `projectedInput.listener` from the same `startup.listener` that becomes `handle.listener`. The RU loader admits `::1` as well as `127.0.0.1` (`reference-deployment.ts:161-165`, `installed-reference-configuration.ts:100`), so this is a live second value, not a constant.

No witness pins them equal. The only bind-argument assertion, `expect(listenArgs[0]!.slice(0, 2)).toEqual([h.listener.port, h.listener.host])`, lives in S03, which is transactional-only; TX does bind from the handle directly (`transaction-runtime.ts:434-436`). Neither the source nor the installed suite exercises `::1` — the installed fixture always configures `127.0.0.1` (`:357`) and labels the `listenUrl`-origin check "fixture law, not loader rewrite" (`:582`).

**Practical impact.** The "genuine intended nonzero listener host/port" claim is enforced and witnessed for one profile and only derived for the other. Any future divergence between the registry capture and the handle summary would bind the wrong loopback interface with no failing assertion.

**Smallest correction.** Bind from the handle in the prepared branch — `server.listen(options.port, prepared ? prepared.handle.listener.host : ((transport?.host as string | undefined) ?? "127.0.0.1"), …)` — and/or add the one-line equivalent of the S03 assertion to S02's success branch, which already captures `listenArgs` and the handle.
