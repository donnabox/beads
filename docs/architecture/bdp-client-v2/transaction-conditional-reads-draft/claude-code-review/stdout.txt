### 4. MEDIUM — only `*` and a fabricated non-matching tag are exercised; no specific matching validator, and the coverage reason does not disclose it

**Where:** `manifest-v1.json` `if-none-match: "*"` on actions 3, 4, 7, 8, 9, 10; `if-match: "\"conditional-no-match\""` on 5, 6.

The catalog row's title is *"Read conditions use **observed validators** and preserve native bodyless outcomes"*, and the Transactional row pins *"Omitting optional validators does not permit ignoring HTTP preconditions."* The row never sends a concrete entity tag that **matches** — not `If-None-Match: <observed etag>` → 304, not `If-Match: <observed etag>` → 200, not `If-Match: *` → pass (`bdp.md:1995-1996` names all three). A server implementing only the `*` wildcard branch and a blanket "any specific tag fails" rule passes this row.

This is forced by a real constraint, not an oversight: dynamic validator substitution lives on the non-exact `headers` path (`runner.ts:1161` `headers = exact ? {} : resolveScenarioHeaders(request.headers ?? {}, priorResponses)`), and raw `headerLines` are byte-literal. So `*` is the only option for a raw-exact row — that's fine. The defect is **disclosure**: the coverage `reason` omits it. "date/validator combinations … remain omitted" reads as *combined* date+validator conditions, not *"no matching specific entity tag is exercised at all."*

The row does avoid the corresponding false-positive correctly: the app oracle asserts `initialTag !== conditionalFalseTag` (`transactional-matrix.test.ts:4420`, `:4429`), so the 412 cannot come from an accidental tag collision. Good.

**Fix:** add an explicit clause to the coverage `reason`, e.g. "Conditions use `*` and a validated non-matching tag only; raw exact header lines cannot carry an observed validator, so matching specific `If-None-Match`/`If-Match` tags and `If-Match: *` remain omitted."

### 5. MEDIUM — `etag absent: false` on the 412 pair over-asserts beyond the spec and RFC 9110

**Where:** `manifest-v1.json:679-684` (`mismatch-get:etag`) and the matching `mismatch-head:etag`.

`bdp.md:1990-1991` requires 412 to be bodyless with no Problem body and keeps "applicable cache fields"; `bdp.md:5877-5878` adds the three Scope-context fields. Neither requires `ETag` on a 412. RFC 9110 §15.4.5 makes ETag mandatory on **304** only ("MUST generate … ETag … that would have been sent in a 200"); there is no equivalent for 412.

This happens to pass against the reference service — `read-http.ts:30-38` deletes `content-type`/`content-length` and only drops `etag` for 406, so 412 keeps it — so this is a portability/false-negative risk in the canonical artifact, not a failing assertion: a spec-conformant implementation that omits ETag on 412 is rejected by this row.

**Fix:** drop `etag` from the `mismatch-get`/`mismatch-head` assertion sets, or keep the 412 ETag check in the app-side oracle only (where it is a legitimate reference-service observation). Keep the 304 `etag` assertions — those are well-founded.
