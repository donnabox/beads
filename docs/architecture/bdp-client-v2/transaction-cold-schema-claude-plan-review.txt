### 1. High — the served key is the retrieval URI, but the URL a cold client dereferences is derived from `$id`; nothing aligns them, so an installed, validating Type can 404 at the first schema request

**Location.** Audit line 31 ("exact captured schema retrieval URIs"), audit line 50 (ledger requests 3–4), native review §2. Source: `packages/server/src/installed-schema-graph.ts:326-336`, `:500`, `:517`; `packages/server/src/installed-contract-artifact.ts:369-383` (cf. `:378`); `docs/specs/bdp.md:1241-1243`.

**Impact.** Offline compilation does not resolve schemas by retrieval URI. For each root document the graph registers **two** identities — the `$id`-resolved canonical URI and the retrieval URI (`:330-336`) — and both `$ref` resolution (`:500`, base = `resources[...].canonicalUri`, i.e. the `$id`) and the descriptor's own `propertiesSchema` resolution (`:517`) look up that merged `identities` map. `installed-contract-artifact.ts:378` pins `descriptor.id === retrievalUri` for descriptors; **there is no `$id === retrievalUri` requirement for schemas**. Consequently a closure in which a schema document's `$id` differs from its captured retrieval URI compiles, installs and validates mutations offline, while:

- ledger request 3 (`GET` the returned `propertiesSchema` URL) 404s whenever `propertiesSchema` names the document's `$id` rather than its retrieval URI, and
- ledger request 4 (the resolved local `$ref`) 404s whenever the root's `$id` establishes a different base than the URL it was fetched from — which is exactly the Draft 2020-12 behaviour `bdp.md:1241-1243` makes normative.

This is the plan's stated objective failing silently: the adapter reports "exact captured bytes served" for the set it keys on, while the set a cold client actually dereferences is unverified. The audit's "no new installation rejection is needed to make the known local fixture usable" is true of today's fixtures (`transactional-direct-refusal-installed.test.ts:63-72` and `transaction-owned.test.ts:830-836` both use `$id === retrievalUri`) but leaves the invariant unpinned precisely where the plan introduces a new two-document closure.

**Smallest correction.** In the new adapter's construction, decode each to-be-served schema artifact's captured bytes once and require that a present top-level string `$id` equal that artifact's `retrievalUri`; fail runtime start with a named error otherwise. Add one source control with `$id` ≠ `retrievalUri` asserting the named refusal rather than a silent `$ref` 404, and one asserting the positive fixture's root `$id`, its retrieval URI and the resolved `$ref` target are the same three strings the adapter serves. Stays inside the seven-file ceiling (new private file only); adds no installation rejection and no new URI law.

### 2. High — Scope-local schemas outside `${scope}schemas/` are silently unserved, and TX has no substitute for the completeness guard that makes RU's manifest closed

**Location.** Audit line 31 (namespace restriction) and line 19 ("Do not copy RU's broader administrative restrictions into TX"). Source: `packages/server/src/installed-reference-configuration.ts:151-159` vs. `packages/server/src/transaction-runtime-configuration.ts:257-284`.

**Impact.** RU's prefix-closed manifest is complete only because installation **rejects** any schema not under `${scope}schemas/` and any schema URI bearing a query or fragment (`installed-reference-configuration.ts:152-157`, "installed schema hosting must be Scope-local"). TX deliberately accepts external and arbitrary schema URIs and imposes no locality constraint at capture, so a prefix-only filter is not equivalent: a captured schema at, say, `${scope}contracts/base` or `${scope}schemas/base?v=1` is Scope-local, reachable in the installed closure, and silently 404s with no diagnostic. The audit correctly refuses to import RU's administrative policy, but then supplies nothing in its place, so the plan's "include every captured local schema resource in that namespace, including transitively referenced resources" cannot be audited against what the closure actually needs. (Conversely, widening the adapter to all Scope-local paths is worse: placed before `handler.handle`, it would shadow real `beads/`, `links/`, `types/` and `receipts/` Read routes.)

**Smallest correction.** Keep the `${scope}schemas/` namespace, and in the same adapter-construction step assert that **no** captured schema artifact has a retrieval URI that lies under the configured Scope yet outside `${scope}schemas/`, or that carries a query or fragment; fail runtime start with a named error. This is a serving-completeness assertion in the new private file — not an installation rejection, not a universal hosting rule, and it leaves external schemas untouched. Pair it with the matching source control in the required-checks list at audit line 43.

### 3. Medium — the three minimum-header names become a third, unsynchronised copy, and it is the copy that decides whether the gate runs at all

**Location.** Native review line 7, final sentence: "A new helper/export from the HTTP module is unnecessary for a fixed three-header routing exclusion." Source: `packages/server/src/transaction-http.ts:144-148` (`hasMinimumControls`, **not exported**); `packages/server/src/transaction-consistency.ts:45-55`.

**Impact.** The field set is already duplicated twice in source. The adapter's copy is different in kind: the other two choose *which refusal* to emit, whereas the adapter's decides *whether the handler's gate runs at all*. Divergence in the permissive direction therefore produces a 200/304/412 on a minimum-bearing schema request — the exact bypass the correction exists to prevent — and it fails open silently rather than loudly. "Fixed" is also the wrong assumption for this slice's lifetime: the audit itself (lines 3, 37, 66) records the minimum/precedence ruling as unresolved and the adjacent minimum work as actively authored, so the set is the most likely thing in this area to move while the adapter is in flight.

**Smallest correction.** Export the field-name list once from the module that already owns it — a single added line beside `hasMinimumControls` in `transaction-http.ts` (or in `transaction-consistency.ts`, which already enumerates the same three at `:48-50`) — have both the gate and the adapter read it, and declare that file in the footprint (seven → eight, or drop `transaction-service.ts`'s test if the ceiling is hard). If the ceiling genuinely cannot move, keep the literal in the adapter but add a source assertion that the adapter's exclusion set and the handler's recognised minimum fields are equal, so divergence fails a named oracle instead of serving a 200.

### 4. Medium — the Scope tuple on static contract bytes is asserted as protocol law; the cited text binds Scope-bounded reads, and that assertion is the sole reason the contended `transaction-service.ts` is in the footprint

**Location.** Audit line 23 ("5768–5774 gives the general Transactional Scope-response tuple") and line 35; native review §4 ("General Transactional Scope response law 5768–5774 applies to the selected local deployment's responses"). Source: `docs/specs/bdp.md:5767-5774` and `:5791-5796`; `:2543-2548`.

**Impact.** `bdp.md:5768-5774` is a field-syntax block; the reporting obligation is stated at `:5791-5796` as "Every Transactional **Scope-bounded** read reports the Scope epoch, Authorization View token, and position **of the transaction-consistent projected prefix it observed**." A pinned contract artifact is, by `:2543-2548`, immutable, never refreshed and never substituted at the same ID — it is not a read of the projected prefix, and the spec enumerates no schema route among Transactional targets at all. The classification may still be the right conservative choice, but it is asserted rather than argued, and it is what forces (a) an owner entry per static-byte read, (b) a new `transaction-service.ts` observation method, and (c) the footprint overlap with the active sequence author that the audit itself names as the blocking dependency and its main open design question (lines 35, 39, 66). It also sets a precedent that any Scope-local byte route is a Scope-bounded read. Note that `discoveryObserved` (`transaction-service.ts:243-269`) already contains the exact primitive needed, but only behind `assembleTransactionDiscovery`, which audit line 35 rightly forbids — so the premise really does cost a new service method.

**Smallest correction.** Replace the normative claim with an explicit statement that the tuple on schema responses is a deliberate conservative local deployment convention, not an obligation under `:5791-5796`, and record that the convention — not the byte serving — is what requires `transaction-service.ts` and therefore gates the slice on the sequence author's release. If root wants the contention removed, the honest split is: land byte serving first in five files (adapter + its tests, `transaction-runtime.ts`, the installed test, the progress document), then add the tuple as a follow-on; this changes ledger items 5, 6–8 and 14, which currently assert context on HEAD, on the three selection refusals, and the post-write position, so those assertions must move with it rather than be quietly dropped.

### 5. Low — the new delivery path is the one place where neither existing non-attesting-marker setter nor the HEAD body strip runs

**Location.** Audit lines 33 and 35 ("do not pass schema objects through the current runtime `deliver()` JSON serializer"; "the non-attesting marker"). Source: `packages/server/src/transaction-runtime.ts:86-93`; `packages/server/src/transaction-http.ts:602`; `apps/bdptest/src/transactional-direct-refusal-installed.test.ts:212`.

**Impact.** `x-bdp-development: non-attesting` is set in exactly two places — `deliver()` at `:89` and `handle()` at `:602` — and the adapter bypasses both. `deliver()` also owns the `response.destroyed` guard (`:87`) and the final defensive HEAD body strip (`:92`). A parallel writer must re-implement all three, and the installed cohort asserts the marker on every exchange unconditionally. The plan never says which path is responsible, so the most likely reading ("don't use `deliver`") invites a second writer that drops one of the three.

**Smallest correction.** State that the adapter returns `{ selected, bytes }` and that `deliver()` gains an optional exact-bytes argument used in place of `stringifyJsonValue(selected.body)` — keeping the marker, the destroyed guard and the HEAD strip in one place, and keeping raw bytes out of `HttpResponse.body` (typed `unknown` at `index.ts:343`, which would otherwise be silently serialized). Add the marker on 200/304/406/412 to the required-checks list at audit line 43. This mirrors `development-runtime.ts:359-364`, which overrides `content-length` only when `status === 200` and writes bytes only for non-HEAD 200.

### Verified with no finding

- **Exact capture is sufficient and immutable.** `installed-contract-artifact.ts:306-405` copies bytes through the typed-array intrinsic, records `kind`/`retrievalUri`/`byteLength`/`sha256`/`bytesBase64`, freezes each entry, dedupes by exact URI with an `identity-conflict` refusal, and `development-contracts.ts:79-90` recompiles **only** from `bytesBase64`. Building the lookup from `contracts.capture.artifacts` rather than caller options is correct and achievable; post-capture caller mutation cannot reach it.
- **Raw delivery is necessary.** `transaction-runtime.ts:88` serializes via `stringifyJsonValue`, which cannot preserve original whitespace or number spelling; `read-http.ts:42-46` computes HEAD `content-length` from the serialized body. The native review's "override successful 200 GET/HEAD `content-length` with the captured byte length after selection" is the right fix and matches `development-runtime.ts:348-364`.
- **Negotiation and preconditions need no new machinery.** `read-http.ts:50-55` + `:62-83` already give `If-Match: *` → 200, specific `If-Match` with absent ETag → 412, `If-None-Match: *` → 304, and `applyReadHttpSemantics` already deletes `content-length` on 304 (`:33-36`) and sets `0` on 406/412, while preserving the `bdp-*` context headers set before selection. Ledger items 6–8 are satisfiable with no invented ETag.
- **Closing/fault behaviour.** For GET/HEAD there is no suspension point between the `closing` check at `transaction-runtime.ts:154` and a synchronous `run()`/`check()` in the service, so the claimed 503-on-close and sanitized-500-on-observation-fault behaviours hold.
- **Installed harness capability.** `packages/conformance/src/http-executor.ts` supports `HEAD` (`:355`) and correctly frames HEAD/204/304 as bodyless (`:1087`, `:1187`); `exactMode.routes` is caller-supplied and only checked against the declared Scope prefix (`:540`, `:557-563`), so the new GET/HEAD schema routes need **no** conformance-catalog or fixture-authority change. `accept`, `if-match` and `if-none-match` are permitted raw header lines. Separately, `SECRET_FIELD` (`:340-341`) matches `bdp-authorization-view`, so the minimum-header gate cases genuinely cannot be installed exchanges — the native review's decision to keep them as source observations is required, not merely economical.
- **Ledger arithmetic and route reachability.** The 14 requests reach real routes: `${scope}types/` and `${scope}types/<id>` via `readRoute`; `${scope}` → `developmentGap("transactional-discovery")` (`transaction-http.ts:552-557`); `${scope}operations/<singleton>` for the write. `readDefaultItems: 2` (`transaction-runtime-configuration.ts:96`) makes the native review's single-page Type fixture a hard constraint, not a preference — a third descriptor adds a silent pagination request.
- **No existing source test regresses.** `transaction-runtime.test.ts` uses an external schema URI (`https://offline.invalid/process-properties`); `transaction-owned.test.ts:803-895` installs `${scope}schemas/link-properties` over a real runtime but never requests it; `transaction-runtime-configuration.test.ts:32` is capture-only. No current test asserts a 404 on a Scope-local schema path, so the footprint is not short on that account.
- **Spec citations check out** at `bdp.md:1091-1098`, `:1198`, `:1234-1243`, `:2533-2584`, `:2592-2596`, `:1935-1944`, `:2002-2007`, `:46-56`, and the audit's precision point is right: `:2592` explicitly permits a client to skip all schema reads, so there is no blanket hosting MUST and none is invented here. `transaction-implementation-progress.md:980-986` accurately states the gap.
- **Scope discipline.** No universal external hosting rule, no proxying, no profile advertisement, and no silent satisfaction of minimum semantics is proposed; the withheld-discovery boundary (`transaction-http.ts:552-557`) and the explicit minimum refusals are preserved by the correction as written.
