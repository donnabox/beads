## Review verdict

**Normative authority is sufficient for this narrow reference choice.** The chain holds exactly as the plan states: `docs/specs/bdp.md:5841-5843` enumerates the permitted outcomes for "the remaining reads" (representation at/after position, wait/route, or normative foreign-view / cursor-expired / catch-up-timeout); `:5329-5332` defines `catch-up-timeout` as inability to serve at/after the requested position within the authority's wait bound, which is literally true of an uninterpretable position identity; `:5794-5800` forbids returning older state as current. A bodyless private 500 is not an enumerated outcome, so this is a conformance repair, not a policy invention. The plan correctly does **not** claim the `:5844-5849` Resource mandate extends to collections. `sole-design.md:94` already records this exact gap and basis, and `:111` confirms S1/G2/discovery stay closed — the plan's scope matches its own authority.

**The mechanism works with the delta the plan claims.** I traced it end to end: classifier kind → `transaction-http.ts:583-587` stops blocking (the `=== "strict"` test falls through) → `transaction-read.ts:226` waitable → `checkCurrentReadMinimum` throws `TransactionMinimumUnproved` (`transaction-consistency.ts:122-129`) → `waitForTransactionMinimum` retries to the original deadline → `TransactionMinimumFailure("catch-up-timeout")` → `transaction-http.ts:624-637` 503 + `retry-after: 1` + actual context. No change is needed in `transaction-service.ts` (`readAtMinimum` at :382-420 already wraps the wait), `transaction-consistency.ts`, or `authority-read.ts`.

**Confirmed correct, do not re-litigate:**
- **No failed-attempt continuation allocation.** `authority-read.ts:983-993` runs `checkSourceCondition` inside `prepared.enter`; `finish` (:1017) — the only caller of `pagination.firstPageWithContext` (:875-895) — is never reached when the condition throws. Existing direct evidence: `transaction-read.test.ts:708-733` (`allocations === 0` across 4 failed collection attempts).
- **No held owner/SQLite across a wait, owner available between retries.** `deliver` (:1025-1118) is fully synchronous and clears `busy` in its `finally` (:1116); each attempt is a separate `withRead` entry.
- **Conditional 304/412 cannot escape the barrier.** `read-http.ts:12-14` only transforms 200-JSON/204, so a 503 is untouched; `transaction-http.ts:403` (401) and `:404-405` (400 malformed) precede; `authority-read.ts:983` skips the condition entirely on an authorization-context refusal.
- **Known-position and no-minimum paths are untouched.** `waitable` is consulted only when `position(minimum.minimumPosition) === undefined` (`transaction-consistency.ts:122`), so recognized minima are bit-identical.
- `transaction-read.ts` is not re-exported from `packages/server/src/index.ts`, so widening the classifier union is source-private.

## Findings

**1. High — parser-rejected query plus an unrecognized minimum keeps the bodyless 500, and the plan's verification bullet says otherwise.**
*Path:* `plan.md:32` (and `:21`) vs `packages/server/src/transaction-http.ts:583-587`.
*Issue:* `requestFromUrl` rejects several query forms before classification (`read-request.ts:151-152` unknown/repeated parameters, `:154-155`/`:258-263` `limit=0`, non-numeric, unsafe; `:165-168` malformed `type`/`conformsTo`; `:182-187` endpoints). For those, `isReadProblem(parsed)` is true, so the unknown-token branch at :583-587 returns `developmentGap("minimum-position")` **before** :588 can return the 400. Materialize-tier refusals (`?limit=33` → `limit-exceeded`, bad/oversized `selector` → `invalid-parameter`/`limit-exceeded`, via `authority-read.ts:752-761` → `read-request.ts:954-969`) do reach the authority and return 413/400 with context. After this slice: `beads/?limit=33` + `opaque` → **413**, `beads/?limit=0` + `opaque` → **bodyless 500** — an arbitrary split driven by *where* the limit is validated, invisible to the client. Today both are 500, so the asymmetry is newly created. The plan's bullet ("malformed or over-budget controls materialized as invalid-parameter/limit-exceeded retain their existing status") only covers the second tier; `plan.md:21` gestures at the first ("Parser-invalid paths retain their existing receiving precedence") without stating the observable outcome.
*Impact:* The author writes the plan-line-32 expectation, sees a 500, and either marks the test wrong or "fixes" it by reordering :588 ahead of :583 — which also changes excluded routes (`types/?limit=0`, `beads/a?view=links&bogus=1`), i.e. silent scope broadening. Existing coverage hides this: `transaction-http.test.ts:2727-2736` exercises `limit=0` and `limit=1&limit=2` only with a *recognized* `pos-2`.
*Correction:* Add an explicit precedence row to the plan: *unrecognized token + parser-rejected query keeps status 500 with `x-bdp-development-limit: minimum-position` at `transaction-http.ts:583-587`; only parser-valid queries with materialized control refusals return 400/413 with context.* Pin it as a named negative check (at minimum `beads/?limit=0` and `beads/?limit=1&limit=2` with an unrecognized token) so the split is asserted rather than discovered. State that reordering :588 before :583 is **out of scope** for this slice, and record the parser-tier 500 as residual nonconformance against `bdp.md:5819-5826`/`5841-5843` for separate disposition.

**2. Medium — the preservation trap is stated in prose but not as the exact predicate, and the kind union is duplicated.**
*Path:* `transaction-read.ts:86`, `:101-104`, `:207-208`, `:226`; `plan.md:19`.
*Issue:* Two sites must change together and the plan names neither precisely. `:207-208` must become an explicit allowlist (`kind === "resource" || kind === "missing"`), not the current negation; `:226` must become `kind === "resource" || kind === "initial-collection"`. Separately, `MinimumCondition["kind"]` at `:101-104` repeats the literal union `"resource" | "missing" | "strict"` independently of the classifier's return type — the plan's "one shared precise classifier" requirement is violated at the type level the moment a fourth member is added to only one of them.
*Impact:* A widened `:207-208` silently converts a collection refusal path; a forgotten `:226` leaves the 500 in place with a green-looking classifier; a forgotten `:101-104` is a type error at best and a divergent union at worst.
*Correction:* Name both predicate rewrites literally in the plan, and require `MinimumCondition["kind"]` to be derived (`ReturnType<typeof currentReadMinimumKind>`) rather than restated. Also note for the author that the collection `resource-not-found` branch is **unreachable today** — `materialize` never produces `notFound` for `beads`/`links` collections (`authority-read.ts:814-838`) — so the preservation is defensive and must not be given a fabricated positive test.

**3. Medium — the HTTP gate needs no code edit; the plan's wording invites a duplicated route predicate.**
*Path:* `plan.md:17,21` vs `transaction-http.ts:582-587`.
*Issue:* "The HTTP gate should admit this new classified current route" reads as an instruction to edit :583-587, but admission falls out of the existing `currentReadMinimumKind(parsed) === "strict"` test automatically. An author following the prose may add an explicit `collection === "beads" || "links"` check there — exactly the "duplicated inconsistent route predicates" the plan forbids one paragraph earlier.
*Correction:* State explicitly that no behavioral edit is expected at :583-587, that any edit there must not re-enumerate routes, and that the stale comment at :582 ("Preserve the old early unknown-token label on every excluded route") should be updated to name the admitted kind. `currentReadMinimumKind` has exactly two call sites (`transaction-http.ts:585`, `transaction-read.ts:301`) — I verified this; the single-classifier requirement is satisfiable as written.

**4. Medium — the plan omits the strongest internal-consistency evidence and understates existing collection coverage.**
*Path:* `plan.md:11` ("checkSourceCondition:201-226 only marks current Resource checks waitable").
*Issue:* True but misleading. Initial `beads/`/`links/` collections **already** wait and return 503 `catch-up-timeout` for a recognized-but-unreached position, because `waitable` is never consulted when the position parses. Live evidence: `transaction-http.test.ts:2662-2720` (behind collection waits, re-enters, exposes the intervening commit), `:2749-2803` (`beads/` wait + real Node disconnect), and the installed `transactional-collection-minimum-installed.test.ts:472-505` (`pos-999` → 503 for both collections × GET/HEAD with conditional headers set).
*Impact:* Two costs. (a) The normative argument looks weaker than it is: the same route, same code path, same client input class already returns 503 for `pos-99` and 500 for `opaque` — a pure internal inconsistency, which is the cleanest justification available. (b) The author may re-author "retain recognized satisfied/behind/future collection behavior" coverage that already exists.
*Correction:* Cite the existing recognized-behind collection 503 as the governing precedent in the plan's "existing law" paragraph, and point the retention bullet (`plan.md:34`) at those three existing callbacks instead of new ones.

**5. Medium — the installed check as planned cannot distinguish a real bounded wait from an immediate 503.**
*Path:* `plan.md:35`; `apps/bdptest/src/transactional-collection-minimum-installed.test.ts:482,497-504`; `apps/bdptest/src/transactional-minimum-current-resource-installed.test.ts:340-342,649-651,691-700`.
*Issue:* The installed collection test already measures `performance.now()` around the timeout exchange and **logs** `elapsedMs` without asserting it. The 503 envelope alone (status + Problem + `retry-after` + context) is producible with no wait whatsoever, so the planned installed evidence proves conformance of the envelope but not that the bounded wait happened. Separately, this repo already has the right discrimination mechanism for "old 500 vs required 503": the env-selected counterfactual mode in the Resource installed test (`restore-unknown-gap`, selecting one row and asserting 500 + `minimum-position` against restored-gap source, with `expect(mode).toBe("positive")` guarding the positive claim). The plan requires discrimination (`plan.md:37`) but names no mechanism, while also forbidding new test-only installed configuration or IPC seams.
*Correction:* Require (a) one installed unprovable collection request to assert `elapsed >= ` the existing default 1 s bound plus a sane ceiling, and (b) an explicit decision: either mirror the existing `restore-unknown-gap` counterfactual as a test-local mode for the collection callback (it reads only a test-file env var and needs no product seam, so it does not violate `plan.md:29`), or state in the plan that the source-level split negative table plus the elapsed assertion is accepted as sufficient discrimination and no counterfactual mode is added.

**6. Medium — per-attempt cost of waiting on a collection is unrecorded and unmeasured.**
*Path:* `transaction-consistency.ts:144,176`; `authority-read.ts:822`; `plan.md:29,33`.
*Issue:* Each retry re-enters the owner and re-materializes the whole collection (`reader.resources()` plus per-row `accept`/`visible`), versus a point lookup on the Resource path. With the default 1000 ms budget and a `min(5, remaining)` step, an unprovable request costs up to ~200 owner entries and full scans — and because an unrecognized identity can never be satisfied, **every** such request deterministically burns the entire budget. This amplification class is pre-existing (reachable today via a recognized future position, per Finding 4), so it is not a blocker, but the increment makes it guaranteed rather than incidental, and the plan forbids touching the deadline.
*Correction:* Record the cost asymmetry explicitly and accept the fixed 1 s / 5 ms policy unchanged as a stated consequence rather than an unexamined one. Measure it with the existing seam, not a new one: wrap the owner's `withRead` to count entries, as `transaction-read.test.ts:2201-2210` does, and assert an exact entry count per unprovable collection request under a controlled budget, exactly as `:2275-2283` asserts `entries - start === 3` for the Resource case. That single assertion simultaneously discharges "finite attempts", "original deadline", and "no SQLite entry survives a wait".
