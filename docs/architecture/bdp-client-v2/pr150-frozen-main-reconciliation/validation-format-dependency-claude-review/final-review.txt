## Blockers

**1 — BLOCKER: origin reuse has no hash pin for 10 of the 11 exit records.**
`gate.py:54-55` trusts the content of `<name>.exit.json` and derives the log hash from that same file. Only the `build` stage is externally pinned (`build-artifacts.json:484-497`, verified at `gate.py:60`), and `build-artifacts.json` itself is unpinned. The sibling's pinned set covers sibling-local files only (`gate.py:74-75` over `preparation-index.json`), and the origin directory is writable.
*Consequence:* "immutable origin reuse" is narrative, not a gate property. An edited origin `exit.json` (flipping `accepted`, or restating `logSha256` to match an altered log) would be accepted by `complete()` — exactly the retroactive-pass outcome the plan forbids.
*Minimal correction:* add a `preparation-index.json`-listed `prefix-origin.json` mapping each of the 11 names to `{exit:{path,sha256}, log:{path,sha256}}` plus `build-artifacts.json`, and have the adapted `complete()`/`verify_build()` validate through the existing `document()` primitive (`gate.py:15-17`) before reading.

**2 — BLOCKER: `rootResultsAccepted` seeding is unspecified.**
The plan enumerates only `rootExecutionReleased=false`, empty `approvedStages`, and null consumer pins. But `gate.py:87` requires `'full-test' in g['rootResultsAccepted']` before `packed-affected-1`, and `gate.py:89` for each prior packed stage. The predecessor carries `["full-test"]` (`execution-gate.json:35-37`).
*Consequence:* seeded empty by analogy, the chain cannot reach `packed-affected-1` without root accepting a `full-test` that will never re-run in the sibling; seeded silently, the 9375-test result is attributed to the new run — the precise misattribution the plan sets out to prevent.
*Minimal correction:* state that `rootResultsAccepted` starts as exactly `["full-test"]`, bound by a `document()` pin on `root-full-suite-acceptance.json` (which already carries `exitSha256`/`jsonSha256`/`logSha256`) and labelled as prior-run attribution; packed entries accumulate fresh.

**3 — BLOCKER: the pinning mechanism permits the incidental upgrades the plan rejects.**
Intent is right; mechanism is missing. The existing provisioning idiom pins only two top-level names (`tools/python-requirements.json:4-7`), with `attrs`/`jsonschema-specifications`/`rpds-py` arriving as pip resolutions (`python-install-report.json`, `requested: false`). The plan pins archive identities only for "added" packages. A fresh venv provisioned the same way re-resolves the entire closure to whatever is current at provisioning time.
*Consequence:* a stated dependency-only correction can silently become a five-package upgrade, invalidating reuse of the 11 stages that ran against the recorded versions.
*Minimal correction:* provision from a fully pinned set — `jsonschema==4.26.0`, `referencing==0.37.0`, `attrs==26.1.0`, `jsonschema-specifications==2025.9.1`, `rpds-py==2026.9.1`, plus `rfc3339-validator==<resolved>` and `six==<resolved>` — using `--require-hashes` with the wheel `sha256`s already recorded in `python-install-report.json`; then assert the resulting installed set equals exactly those seven plus `pip`, with no extras.

*Consequence:* as written the sentence either overstates the delta root is asked to review, or implies two new reads — contradicting "the only gate adaptation needed" and "minimal helper delta." Those files also have no existing hash to validate against (`run.py:91` records none).

**6 — provisioning and probe cannot run through `run.py`, and the plan doesn't say so.**

The plan governs final *reporting* but not these two fields. *Correction:* specify replacement text naming 11 reused origin stages and 14 fresh attempts, and list `note`/`state` alongside the three initial-state fields already enumerated.

**9 — the probe should name the exact `FormatChecker` instance.** `check_type_examples.py:38` uses `format_checker=FormatChecker()` — the bare instance, which snapshots the class-level dict populated at `_format.py:225-228` — not `draft202012_format_checker` (`_format.py:176`). *Correction:* specify `FormatChecker()` constructed with no arguments, assert `"date-time" in FormatChecker().checkers`, and record `rfc3339_validator.__file__` and version as provider identity. The positive/negative pairing is otherwise well chosen: the negative case is the only thing that detects silent non-enforcement, which is exactly how the original failure arose.

**10 — pip version continuity is assumed, not pinned.** The plan lists `pip 26.1.1` under "keep existing versions," but in a new venv pip comes from `ensurepip` on the base interpreter, outside the requirement set. *Correction:* record the bootstrapped pip version in the provisioning record and treat any difference from 26.1.1 as a stop-for-root, not an accepted incidental change.

**11 — the 120s provisioning cap is tighter than the comparable precedent.** Provisioning installs seven wheels under 120s/TERM115 with no retries, while the predecessor's `dependencies` install stage was given 300/295 (`commands.json:38-39`). A slow index makes a transient timeout indistinguishable from a real failure, which then escalates to root. *Correction:* either pre-stage the pinned wheels locally and provision offline (`--no-index --find-links`), which also reinforces finding 3, or state explicitly that a provisioning timeout is a stop-for-root with the partial venv discarded rather than reused.
