## Findings

### 1. HIGH — supplemental header comparison omits the serializer's generated default headers; throws inside the executor before any named assertion

**Location:** `apps/bdptest/src/transactional-matrix.test.ts`, `commandMinimumWire().afterExchange`, the block commented *"Credentials and generated framing are checked by the runner's exact request assertions"*:

```ts
expect(
  request!.headerLines.filter(
    (h) => !["authorization","host","content-length","connection"].includes(h.name.toLowerCase()),
  ),
).toEqual(expected.headers);
```

**Demonstrated:** `runner.ts:1845–1867` (`exactHeadersMatch`) is the authority on what the raw serializer emits, and the positive test requires the authored `request-headers` assertion to pass, so the observation must be exactly:

`authored lines` → `credential lines` → `[Accept */*, Accept-Language *, Accept-Encoding identity, User-Agent bdp-conformance/0]` *(each dropped only if authored or supplied as a credential)* → `Host` → `Connection` → `Content-Length` (bodies only), with `index === actual.length`.

The exclusion list drops only `authorization/host/content-length/connection`. For the eight POSTs, `accept` is authored so `Accept` is suppressed, but **`Accept-Language`, `Accept-Encoding`, `User-Agent` survive the filter**; for `m-current`/`m-events` (`headerLines: []`) **all four** survive while `expected.headers` is `[]`. So on `m-create-a` the comparison is 9 lines vs the 6 authored → fail.

**Impact:** fires on the first minimum exchange of (a) the positive fourteen-row test, (b) `minimum-batch-body-conflict`, (c) `minimum-readonly-credential`. Because `afterExchange` runs inside `exactExecution.execute`, the assertion error propagates as an executor throw, so the row is recorded with a transport/harness error and the control paths you asked about — `expect(exchange.transportError).toBeUndefined()` and `expect(last.assertions.filter((a) => !a.passed).map((a) => a.id)).toEqual(description!.failingIds)` — are never reached with real named outcomes. The authored-assertion discrimination this row exists to prove is unobservable.

**Minimal fix:** compare the authored prefix, which `exactHeadersMatch` guarantees occupies indexes `0..n-1` in order, and keep the absence claim explicit for the remainder:

```ts
expect(request!.headerLines.slice(0, expected.headers.length)).toEqual(expected.headers);
expect(
  request!.headerLines.slice(expected.headers.length)
    .filter((h) => h.name.toLowerCase().startsWith("bdp-")),
).toEqual([]);
```
(Do *not* just add `accept`/`accept-language`/`accept-encoding`/`user-agent` to the exclusion list — that silently stops checking the authored `accept` line.)

### 2. MEDIUM — event↔receipt transaction correlation can pass vacuously

**Location:** same hook, events branch:

```ts
if (i < 2) expect(event.transaction).toBe(baselines.get(`m-create-${name}`)!.transaction);
```

**Demonstrated:** `body` is `JSON.parse(...)` (`any`) and `baselines` holds `Record<string, unknown>`. Nothing in the manifest, the coverage row, or the hook establishes that `transaction` exists on either side — `m-create-a`/`m-create-b`'s pinned receipt fields are `status/detail/idempotencyKey/scopeEpoch/authorizationView/requiredPosition/effectPosition/next/id`, and `ordered-facts` projects only `id/source/type/subject/subjectType/ordinal`. If the field is absent or renamed on either side, `expect(undefined).toBe(undefined)` passes. This is the only evidence tying the Scope Events to the mutation receipts, and it is the piece most likely to silently stop proving anything.

**Minimal fix:** before comparing, require presence on both sides:

```ts
const expectedTransaction = baselines.get(`m-create-${name}`)!.transaction;
expect(typeof expectedTransaction).toBe("string");
expect((expectedTransaction as string).length).toBeGreaterThan(0);
expect(event.transaction).toBe(expectedTransaction);
```

### 3. LOW — two supplemental equalities are stricter than the row's contract and fail at the wrong site

**Location:** same hook — `expect(body.items).toEqual(resources)` (`m-current`) and `expect(event.data).toEqual({ revision, properties, metadata })` (`m-events`).

**Issue:** these demand that a collection item be *structurally identical* to the receipt-embedded resource, and that `data` have exactly three keys. The manifest deliberately uses pointer projections (`ordered-state`, `a-properties`, `a-metadata`, `a-no-provenance`) precisely because the clause under review is about ignored minimum fields, not about the full shape of collection items. Any additional server field (a link summary on items, `id`/`type` inside `data`) fails as an in-executor throw — reported as a transport error on a passing-by-contract row — rather than as a named assertion failure. Note the asymmetry: the hook's own created-resource checks correctly use `toMatchObject` plus explicit `not.toHaveProperty`, but these two do not.

**Minimal fix:** `expect(body.items[i]).toMatchObject({ id, type, properties, metadata, revision })` plus the existing explicit absence claims; likewise `expect(event.data).toMatchObject({ revision, properties, metadata })` with `expect(event.data).not.toHaveProperty("revisionProvenance")`.

### 4. LOW — ledger's comparison-mode element is inert; the ledger check is two hand-copied literals

**Location:** `minimumReplayLedger` / `assertMinimumReplayLedger` / the `pair` lookup in the hook.

**Issue:** `assertMinimumReplayLedger` compares its argument against an inline duplicate of the same three tuples, so it detects mutation of the value passed in (which the two new probes in the route-digest test exercise correctly) but cannot detect a wrong canonical ledger. `pair[2] === "whole-json"` is never read — the hook unconditionally performs a whole-body `toEqual`, so the mode field carries no weight and a future `"headers-only"` entry would be honoured as whole-body. `performed.push([...pair])` and `finish()`'s slice comparison do correctly prove *which* comparisons ran, and the baseline ordering is right (all independent schema/literal/absence checks execute before `baselines.set`), so this is hardening, not breakage.

**Minimal fix:** make the mode load-bearing at the use site: `if (pair[2] !== "whole-json") throw new Error("minimum-replay-comparison-ledger");` before the `toEqual`.

### 5. LOW — the 63 s wall-clock bound is the one count the diff did not adjust, and fanout grows by two installed cohorts

**Location:** positive test `expect(performance.now() - started).toBeLessThanOrEqual(63000)`; new `it.each(minimumControls)` (120 s each, bootstrap + 1 session apiece).

**Issue:** every other quantity was bumped (`sessions` 20→21, `children` 21→22, exchanges 192→203, the four control ceilings, the fences) but the wall-clock assertion is unchanged while the cohort gained a process launch, 11 exchanges, and a per-exchange hook that runs for all ~203 exchanges. Combined with two new 120 s installed-cohort tests in the same file, this is the most likely new source of CI flake.

**Minimal fix:** raise the bound proportionally (e.g. 68000) or state why 63000 still holds with the measured elapsed from a real run.

## The N1 repair, judged as code

`onObserved` is invoked inside the `try`, immediately after `observed = { result, sessions, baseline }` and before the `finally` that calls `target.close()`. That does fix the targeted loss: a throwing `close()` (→ `AggregateError`) or a later failing assertion in the test body no longer discards the report, and `observed` is fully populated at that point (all sessions pushed, matrix resolved). Two residual properties, both acceptable but worth stating: it still writes nothing when the matrix itself throws or the cohort deadline aborts (`observed` is never assigned — unchanged from before), and a throw from `onObserved` itself (e.g. a bad output path) is folded into `failure` and aborts the cohort. The success-only `console.log` summary remains at the end of the test, so a failing run now yields the file but not the `installed-tx-fourteen-partial-summary` line.
