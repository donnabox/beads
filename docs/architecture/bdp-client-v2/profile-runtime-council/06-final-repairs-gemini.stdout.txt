##### [Low] Multi-Alias Heading Prefix Truncates Preceding Anchor Excerpts
- **File & Section**: [`packages/conformance/src/markdown.ts#L48-L56`](file:///Users/dbox/repos/wt/vickie/bdp-integration-logs/profile-runtime-council/packages/conformance/src/markdown.ts#L48-L56)
- **Concrete Issue**: In [`markdownAnchors`](file:///Users/dbox/repos/wt/vickie/bdp-integration-logs/profile-runtime-council/packages/conformance/src/markdown.ts#L11), heading aliasing is evaluated as:
  ```ts
  const aliasesHeading =
    next !== undefined && markdown.slice(match.index + match[0].length, next.index).trim() === "";
  ```
  If multiple explicit anchors precede a single heading sequentially (e.g. `<a id="alias-1"></a>\n<a id="alias-2"></a>\n### Heading`), the slice between `alias-1` and `Heading` contains `<a id="alias-2"></a>`. `trim() === ""` is `false` for `alias-1`. Consequently, `alias-1` is classified as an interior anchor rather than an alias, setting `end: next.index` (the offset of `### Heading`). Citations pointing to `alias-1` receive only the whitespace and HTML tag between the anchors, entirely excluding the heading and section body.
- **Reachable Trigger**: Authoring more than one explicit anchor before a heading in specification documents and citing the earlier anchor.
- **Impact**: Any catalog requirement referencing the non-immediate alias fails catalog citation validation (`CatalogValidationError`) because the section body is truncated before the heading text starts.
- **Fix / Next Step**: Allow `aliasesHeading` to recognize preceding siblings by stripping whitespace and preceding standalone `<a\s+[^>]*><\/a>` tags from the slice between `match.index + match[0].length` and `next.index`.

#### Questions Needing Omitted Context

1. **Multiline Regex Behavior with CRLF Line Endings**:
   - In [`packages/conformance/src/markdown.ts#L15`](file:///Users/dbox/repos/wt/vickie/bdp-integration-logs/profile-runtime-council/packages/conformance/src/markdown.ts#L15) and [`packages/conformance/src/markdown.ts#L43`](file:///Users/dbox/repos/wt/vickie/bdp-integration-logs/profile-runtime-council/packages/conformance/src/markdown.ts#L43):
     ```ts
     /^(#{1,6})[ \t]+(.+?)[ \t]*#*[ \t]*$/gm
     /^ *<a\s+(?:id|name)=["']([^"']+)["']\s*><\/a> *$/gm
     ```
     In JavaScript RegExp multiline mode (`m`), `$` asserts position before `\n`. If input markdown contains Windows CRLF (`\r\n`), `[ \t]*` and ` *` do not match `\r`, causing matches to fail. The supplied packet shows standard Unix LF usage, but git checkout settings with `core.autocrlf=true` could break anchor indexing.
