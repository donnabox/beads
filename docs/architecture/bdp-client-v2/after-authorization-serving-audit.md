## Recommended next slice: retained sequence-member comparison before private depth refusal

**One concrete remaining serving obstruction is established by source.** After a shallow singleton creation has retained key K, submit a syntactically valid one-member sequence with the same operation, ID, principal and K, changing only metadata to exceed the private depth ceiling while staying within the byte/member limits. Current `transaction-batch.ts:257–267` throws on the whole carrier before constructing members. `transaction-http.ts:328–340` turns that exception into bodyless 500 with `unsupported-transaction-composition`, before calling the owner. The retained member can never reach identity classification.

The required eventual behavior is HTTP 200 with the sequence's positioned `idempotency-conflict` member; no effect, receipt replacement or position advance. `docs/specs/bdp.md:3284–3310` specifies retained-key outcomes in the member's turn and unchanged retained disposition; `4057–4108` preserves those laws for one-operation Transactional sequence members. The exhaustive command status table at `4617–4652` places a member conflict inside the sequence envelope, and permits a bodyless 500 only for an unexpected internal fault. Metadata depth is not a malformed-carrier grammar rule. A private predictable refusal remains an honestly exposed implementation limitation, not final conformance.

This is **known unfinished scope, not a regression introduced by PR139**. `transaction-depth-key-order-plan/plan.md` explicitly restricted PR131 to direct batch/singleton receiving, kept sequence construction strict, and documented the remaining sequence/fresh-depth limitation. Current `transaction-http.test.ts:1625–1652` tests a *fresh* deep sequence's 500 and later shallow key reuse; it does not test an already retained key followed by a deep differing member. Direct repair and existing sequence tests therefore do not close this case.

The smallest useful next plan should carry a private depth-capacity fact into member admission/comparison, retaining complete carrier syntax validation and refusing fresh deep execution. Reuse the owner-side ordering already in `transaction-store.ts:1130–1180`; do not perform an HTTP existence probe or assume a retained row cannot expire. `admitSequence` (`1958–2030`) atomically reserves every unknown member key and skips retained rows until the eligible turn; `nextSequence` (`2033–2147`) performs authoritative turn-time comparison. Preserve all-or-none reservations, creator facts, deferred aliases/labels, cleanup and the no-controls defensive refusal when a previously retained key becomes unknown.

**Important implementation uncertainty:** deleting the global depth assertion alone is unsafe. Sequence member construction currently uses unannotated `prepareCarrier`; fresh deep work could then reach execution. Conversely, throwing during owner admission may escape the existing preparation-only HTTP catch and change the private failure marker. A bounded plan must establish the receiving/strict-construction split and exact failure propagation before authoring. The source proves the obstruction and required retained outcome; it does not justify a one-line fix or arbitrary-depth execution support.

A compact proposed wire witness is six requests on one owner/listener: shallow singleton seed; deep same-key sequence conflict; original singleton replay; original Resource GET; fresh deep sequence refusal; shallow reuse of that refused key. Compare the full sequence Problem/index, complete original receipt and Resource, and unchanged position through the retained conflict/replay. The final two requests preserve today's private fresh-depth boundary without representing it as qualified behavior. A copied emitted early-depth refusal should discriminate at request 2, with the named sequence-member conflict oracle; generic failures do not qualify. Owner tests must separately cover atomic reservation cleanup and a retained-to-unknown recheck. These are proposed bounds, not frozen executable counts or evidence.

Likely implementation ownership is batch preparation plus sequence/owner admission, with narrowly affected sequence tests. HTTP/service error propagation may need a small integration hunk; their files are currently owned by the minimum worker, so root must schedule that shared-file edit. This is independent semantic work and does not change minimum parsing, unknown-position behavior, S1 or G2. Do not start a competing HTTP/service draft.

## Two remaining delivery limitations, not alternative immediate patches

1. **Cold navigation remains intentionally unavailable.** `transaction-http.ts:586–593` returns `transactional-discovery` for canonical Scope, `bdp.json` and `operations/`. `transaction-discovery.ts:24–66` already assembles a same-context descriptor and directory, but explicitly emits `profile: transactional`. The sole design's T2/P predicates and the previously accepted `transaction-cold-navigation-next-plan.md` prohibit activating that advertisement while required functionality/qualification is incomplete. A non-attesting header does not change the advertised profile. No inactive duplicate adapter or admission bypass is recommended.
2. **Authorization is genuine but deliberately Scope-wide and monotonic.** `transaction-authorization.ts:10–36,49–64` supports all-visible to empty, not a per-resource subset, per-principal policy map or regrant. PR139 proves actual narrowing and view/lease fencing; it does not prove those broader policies. This is a named capability follow-up under the sole plan's U2/T3 work, not evidence that the supported configuration violates an unconditional ACL law. Broadening it is materially larger than the retained-sequence repair and should not be invented as a prerequisite for this next slice.
