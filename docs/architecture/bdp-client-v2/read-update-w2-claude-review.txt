### 1 — MEDIUM — the sole promoted whole row observes two of the three normative result-entry branches, and only one of the two name-declaring member kinds

**Location** `packages/conformance/test-support/read-update-coverage-v1.json:4217` (`wholeContract: true`); scenario at `packages/conformance/matrices/read-update-v1.json:40299`, action `member-shapes` at `:40715`.

`schemas/bdp-v0.schema.json` `$defs.sequenceResponse` resolves each entry through a three-branch `oneOf`: `sequenceMemberResult`, `sequenceMemberAliasResult` (`operationIndex` alone, `unevaluatedProperties: false`), `sequenceMemberProblem`. Second gap: `name` is declarable on exactly two member kinds — `sequenceCreateBead` and `sequenceCreateLink` (`sequenceUpdateBead`/`sequenceDeleteBead`/`sequencePutAlias`/`sequenceDeleteAlias` all have `unevaluatedProperties: false` with no `name`). The row witnesses the "declared ⇒ present" and "undeclared ⇒ absent" directions only on `createBead`; `createLink` is never a sequence member.

This is the project's own standard elsewhere: `read.types.descriptor` enumerates all thirteen descriptors, `result-headers` enumerates all eight singleton targets, and `create-link` was just held incomplete in this very commit for one unobserved conjunct (`docs/design/read-update-executable-progress.md:50`). **Impact** The one row this slice promotes to `wholeContract: true` has an unobserved branch of its own cited clause. If the authority omitted `operationIndex` on alias-result entries, or dropped `operationName` on a named `createLink`, nothing in-tree would notice, yet the row reads as complete.

**Fix** Cheapest genuine close — extend the existing `member-shapes` body from 4 to 6 members (well inside the advertised 32 and the 65536-byte cap) and add their index/name assertions:

```json
{ "operation": "createLink", "idempotencyKey": "w2-link", "type": "https://reference.invalid/acme/types/relates",
  "source": "@prefix", "target": "beads/w2-collision", "name": "edge" },

The alias entry also pins the "`operationIndex` alone, and it is closed" half via the existing schema branch. Otherwise, append to the row's reason "only Bead create/update result entries and member problems were observed; alias result entries and a declared `createLink` name remain unobserved" and leave `wholeContract: false` until a later slice.

### 2 — MEDIUM — the harness body cap was raised past the installed policy, but no row observes the advertised `/limits/request/bodyBytes`

**Location** `apps/bdptest/src/read-update-matrix.test.ts:173` (`maximumRequestBodyBytes: 65536 → 131072`); carrier discovery assertions at `packages/conformance/matrices/read-update-v1.json:41339-41344`; claim at `docs/design/read-update-executable-progress.md` ("The harness request capacity is131072 bytes, solely to observe the installed unchanged65536-byte body policy").

`development-composition.ts:36` advertises `/limits/request/bodyBytes` from `authority.limits.requestBodyBytes` (`development-authority.ts:42`, `64 * 1024`), and `$defs.readUpdateAdvertisedLimits` declares it. The carrier row correctly pins the count limit in-row — `target-member-limit`, `/limits/sequence/operations` `equals: 32` — but `grep '/limits/'` over the whole 1.68 MB manifest returns **exactly one hit**. The body bound is never observed anywhere.

So the `body-size` variant (65937 authored octets → `413 request-too-large`) is bound only to two hard-coded integers in the test file (`:650` `< 65536`, `:655` `> 65536`). Both `limit-exceeded` and `request-too-large` map to `type: size` / `status: 413` / `retry: never` in `readProblem`, so `code` is the only discriminator — and the row does assert the two codes distinctly, which is good. This is the exact asymmetry external L6 closed for the count case.

Secondary: raising the cap to 131072 applies to the shared `exactMode` consumed by `createRawHttpScenarioTarget`, `createInstalledExactClient` and `seedInstalledReadFixture`, so **every** row may now exceed the installed policy. Nothing asserts that only `body-size` does.

**Impact** The one place the harness was deliberately relaxed beyond installed policy has no in-row evidence of where that policy actually sits, and no guard that other authored bodies stay under it.

**Fix** One assertion on the carrier row's `discovery` action, mirroring `target-member-limit`:
```json
{ "id": "target-body-limit", "kind": "json-pointer", "pointer": "/limits/request/bodyBytes", "exists": true, "equals": 65536 }
```
and, alongside the existing checks at `read-update-matrix.test.ts:650-656`, assert the complement — every authored raw body other than `body-size`, and every client `input.body`, serializes to ≤ 65536 bytes — so the elevated harness capacity can only ever be consumed by the one variant that is meant to consume it.

## What holds

- **No runtime, protocol, Type, public schema, runner, catalog or admission change.** `installed-body-schema.ts` adds one list entry; `harnessInstalled_sequenceResponse` `$ref`s the unmodified `$defs.sequenceResponse`, which is `additionalProperties: false` over `results` — so the top-level envelope is genuinely closed, and the three-branch `oneOf` is mutually exclusive (a problem fails `sequenceMemberResult`'s `unevaluatedProperties: false`; a success fails `sequenceMemberProblem`'s `outcome: false`).
- **The code/type/status/retry pins are not schema-redundant, and the schema is not bypassed.** `readUpdateProblem`/`readProblem` carry 20 `if/then` branches binding each code to its `type`/`status`/`retry`, so `schema` + `code` transitively pins the tuple; the `problem` control substitutes a *coherent* wrong tuple (404/not-found/resource-not-found/after-state-change) and fails exactly `["1-code","1-status","1-type","1-retry"]`, proving the pins discriminate beyond schema validity. `sequenceMemberProblem` deliberately has no `unevaluatedProperties: false`, so Problem bodies stay extensible — never a closed-object oracle.
- **The alias/identity discriminator is real.** `resource-evaluator.ts:661-669` fires `identity-taken` only on `tx.identityWasCommitted(id)` and `alias-path-taken` only on `tx.alias(id.slice(6)) !== undefined`, with distinct `retry` (`never` vs `after-state-change`). `member-problem-shape` observes the first, `local-bindings` the second against a never-committed `beads/w2-held` (proved absent by `no-blocked` 404, then created by `fresh-creator-key`).
- **The retained-failure chain is tight.** `occupy-path` → `failed-bindings` (409 `alias-path-taken` + 400 `binding-unavailable` + successful tail) → `release-path` (`outcome: deleted`) → `retained-bindings` whose `retained-results` deep-compares the **entire** replayed array, including the tail's original creation postimage, against the captured `failed-results`. Then `dependent-key-conflict` (changed input, old key → 409 `idempotency-conflict`) with `conflict-unchanged` proving the target preserved byte-for-byte, `fresh-dependent-key` + `fresh-dependent-read` performing the update, and `fresh-creator-key` + `freed-path-readable` proving the cleared path usable. `allocated-read.postimage` correctly compares against `results[1].resource` (the dependent's postimage), never the creator's stale creation record — exactly the trap the plan warned about.
