## Cross-cutting CLI compatibility

Argument parsing, aliases, shell completion, stdin/file/editor inputs, templates, `--json`, JSON Lines, silent output, exit codes, error precedence, `--dry-run`, confirmation and output stability are CLI responsibilities. A BDP mapping must preserve or explicitly change these independently of the store. The repository has a protocol output corpus: [cmd/bd/protocol/CATALOG.md:1](https://github.com/gastownhall/beads/blob/5126de8c1a02d01db2481e4fd5e78dd41010e25f/cmd/bd/protocol/CATALOG.md#L1). An equivalent Rust command host should replay those applicable transcripts after its pack commands exist. This audit did not execute that corpus and does not claim byte-for-byte output parity.

The capability registry is a useful complete list of intentionally classified command paths, but a permitted gate is not proof that a provider route implements a command. Likewise static test declarations are an inventory of obligations, not test execution or coverage percentages. `command-crosswalk.csv` gives every registry path an architectural disposition and report pointer; `cli-ast-main.json` and `cli-ast-preview.json` preserve extracted test/command/flag/registration evidence.

Flags have different kinds of effects: scalar filters often push down; text/glob/ranking flags may force scans; cascade/recursive/claim/force flags alter transaction policy; output/input flags stay local; backend/branch/SQL/repair flags may be provider administration. Do not classify a whole command as portable simply because its default path maps. The detailed Issue and other-family reports examine the high-risk flags; exhaustive combinations and runtime error/output parity remain qualification work, explicitly unproved here.
