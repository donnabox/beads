## Findings

### 1. `s-events:ordered-facts` asserts `ordinal: 0` for *both* created events — Medium (unverified value, gates the positive scenario)

Location: manifest row `transactional.sequence.member-transactions`, action `s-events`, assertion `ordered-facts`.

```json
"equals":[[".../events/","created",".../beads/a",".../types/task",0],
          [".../events/","created",".../beads/b",".../types/task",0]]
```

Two distinct events on one `eventPage` carry the same `ordinal`. This is coherent **only** under a per-transaction reading of `event.ordinal` (each member commits separately, so each transaction's single event is ordinal 0). The provided `event`/`eventPage` schema requires both `ordinal` and `transaction` but pins neither's semantics, so I cannot prove which reading is normative.

Why it matters either way:
- If `ordinal` is **source-global**, the second tuple must be `1` and this is a defect: the positive scenario fails at the last assertion of the last of ten actions. Smallest correction: `0` → `1` in the second tuple.
- If **per-transaction**, the value is correct *and load-bearing*: an implementation that committed the three members atomically would emit ordinals `0` and `1` and fail this assertion, whereas a global ordinal would yield `[0],[1]` for both the atomic and the separated case and discriminate nothing. Smallest correction: none, but record in the coverage `reason` that `[0,0]` is the discriminator against a single atomic commit, since nothing else in the row says so.

This value is exercised by no negative control (the control stops at action 0) and by no other assertion, and the two 900 s timeouts mean it has never been observed. It is the highest-value thing to confirm in this row.
