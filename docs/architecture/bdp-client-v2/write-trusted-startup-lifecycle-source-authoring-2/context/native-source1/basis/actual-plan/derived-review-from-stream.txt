## A. Implementation / integration issues

### F1 — HIGH. TX prepared path: the reused frozen preflight carries `port: 0`, and the existing core line binds `captured.port`
- **Source:** `packages/server/src/transaction-installed-configuration.ts:62` returns `port: 0`. `packages/server/src/reference-deployment.ts:322-323` builds `state.installed` / `state.preflight` from exactly that capture, so **`state.preflight.port === 0`**. The existing bind is `server.listen(captured.port, settings.transport.host, …)` at `packages/server/src/transaction-runtime.ts:316`.
- **Frozen plan refs:** `plan.md` §"Smallest module and export decision" ("the new TX entry consumes `state.preflight` without calling `captureTransactionRuntimeConfiguration` again"); §"Bind, stop and error mechanics" ("Only the trusted branch uses intended host/port from the genuine handle… Intended port is 1..65535"); `future-footprint.json` → `transaction-runtime.ts` purpose ("reuse registered preflight").
- **Why high:** the requirement is stated but nowhere *guarded*, and the factored core's natural reuse point is the line that already reads `captured.port`. If an author factors around it, the prepared TX path silently binds an ephemeral port. Every TX intended-listener witness then becomes vacuous: S07/S08/S13(TX) occupied/throw/cancel semantics, I11 occupied-listener, and the canonical-Scope Host gate at `transaction-runtime.ts:132-133` (`new URL(scope).host`) — with `plan.md:43`'s installed Scope being "canonical HTTP loopback with the reserved intended port and /acme/ path", request-table rows 1-3 are only reachable when the listener holds that exact reserved port.
- **Already known elsewhere, not carried into the plan:** `docs/design/startup-configuration.md:697` already records "TX intended listener is retained separately from its existing private port0 capture." `plan.md` never forwards it.
- **Affected witnesses:** S03, S07(TX), S08(TX), S13(TX); I02, I04, I09, I11, I13, I15, I17, I19; request-table rows 1-3.
- **Smallest correction:** one sentence in `plan.md` §Bind and in `future-footprint.json`'s `transaction-runtime.ts` purpose — the trusted TX startup mode takes host/port **only** from `handle.listener`; `state.preflight.port` (0) is never passed to `server.listen`. Extend S03 (or S07) with one assertion that the recorded listen argument equals `handle.listener.port` and is nonzero. For symmetry, note that RU needs no override because `state.installed.port === handle.listener.port` by construction (`installed-reference-configuration.ts:97-105`, `reference-deployment.ts:298-301`).

### F2 — MEDIUM. One factored core is asked to satisfy two mutually exclusive listener-error contracts
- **Source:** both legacy entries attach `server.once("error", reject)` and **remove it in the listening callback**: `development-runtime.ts:507-513`, `transaction-runtime.ts:314-320`. After successful startup neither server has an `'error'` listener.
- **Frozen plan refs:** §"Concrete problem and boundaries" ("Keep `startDevelopmentReferenceRuntime` and `startTransactionRuntime` behavior … unchanged") vs §Bind ("Attach a listener error observer before calling listen and **keep it through startup publication and serving**"), under §"Smallest module and export decision" ("Factor each runtime's existing body into one internal core").
- As written these cannot both hold in one core. A persistent observer in the shared path changes legacy behavior (a post-startup listener error stops being an uncaught exception); omitting it defeats S09/S11 and the completion promise.
- **Affected witnesses:** S08, S09, S11; I10/I11, I12-I19.
- **Smallest correction:** state that the persistent listener-error observer **and** the serving-time completion promise exist only in the *trusted* startup mode of the core, and that the legacy mode retains attach-then-remove verbatim. Add one source assertion that after a legacy start `server.listenerCount("error") === 0` and the legacy result shape is unchanged.
