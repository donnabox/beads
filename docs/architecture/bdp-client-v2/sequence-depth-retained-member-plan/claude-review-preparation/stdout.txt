**1. MEDIUM — the control's expected private marker is unreachable under the planned HTTP hunk.**
*Location:* `ledger.json` `control.expectedMarker: "unsupported-transaction-composition"`; `plan.md` §Control ("record actual second response500/private marker/empty body").
*Issue:* The plan removes the catch at the preparation call site (`transaction-http.ts:329‑335`) and forbids a broad catch around receiving errors. The control restores strict behaviour inside `prepareTransactionSequenceForReceiving`, so the mutated build throws `TransactionDevelopmentLimitError` out of `route()`; the listener's generic fault path (`transaction-runtime.ts:260‑267`) answers bodyless 500 with only `content-length: 0`, `cache-control`, `x-bdp-development` — no `x-bdp-development-limit`, no context.
*Impact:* The control's recorded observation contradicts its stated prerequisite, making "fail solely `sequence-depth:retained-member-conflict`" ambiguous, and tempts an author to re-add a preparation-site catch purely to satisfy the control.
*Fix:* Set `expectedMarker: null` and restate the control's second response as "bodyless 500, no development-limit marker, no context"; require the named oracle to assert status before headers/schema.

**2. MEDIUM — the selection omits the three existing regressions most exposed by this refactor.**
*Location:* `ledger.json` `sourceSelections` (11 sequence titles, 2 HTTP titles).
*Issue:* The change moves the depth assert from one pre-loop whole-carrier call (`transaction-batch.ts:268`) into per-member construction inside the label/dependency loop (`:270‑322`), and moves the HTTP depth refusal after negotiation. The direct guards for those exact properties are unselected: `transaction-sequence.test.ts:439` "rejects duplicate keys and invalid dependency edges before any key effects", `:269` "projects mixed retained, conflicting, failed and unknown keys in declaration order" (the shallow retained-conflict-at-turn projection the new case extends), and `transaction-http.test.ts:443` "rejects sequence carrier syntax/keys/negotiation before claiming any member" (shallow 406 before any claim — the ordering the new design now depends on).
*Impact:* The plan's load-bearing claims ("all syntax/labels/duplicates finish before capacity can be deferred", "ordinary negotiation then one authoritative admission") have no selected shallow regression.
*Fix:* Add those three titles and recount (≈18 callbacks, ≈21 source HTTP, 15 owners/directories, 3 listeners), or state explicitly why they need not run.

**3. LOW‑MEDIUM — strict preparation's error precedence changes for deep + label-broken carriers.**

*Issue:* Today the depth class is thrown before the member loop; afterwards a carrier that is both deep and label-broken would surface `TypeError("unknown sequence creator")` (`:284`) instead. ## Load-bearing claims I verified as sound (no action)

- **Strict vs receiving wrapper / unforgeable facts:** `depthRefusals` is a module-private `WeakMap` keyed by branded `PreparedTransaction`; `transactionDepthRefusal` brand-checks and there is no setter (`:339‑362`). Annotating `member.request` is exactly what `admitKey` reads (`transaction-store.ts:1163`). The no-controls overload cannot return `development-limit` (`:1116‑1141`) — it throws, so the receiving variant cannot leak into `TransactionAdmission`.
- **Retained before refusal:** `admitKey` gates the fact on `!prior` *after* `expireRow`, `pendingWins` and the dependency-template branch (`:1142‑1167`); `admitSequence` skips unexpired retained rows entirely (`:1977‑1979`), and `nextSequence` classifies them at their turn (`:2103‑2124`). A completed row has `owner === null`, so `pendingWins` does not short-circuit it. Deep comparison is feasible: `encodeSemanticValue` is iterative with no nesting limit (`semantic-identity.ts:53‑144`), `normalizeTransaction` is shallow over operations (`transaction-batch.ts:460‑535`), and dependency comparison compares identity strings only (`transaction-dependencies.ts:173‑217`).
- **Atomic rollback and turn recheck:** the fresh-deep throw happens inside the single `atomic()` claim step, so SQLite rolls back receipts and `creator_facts` with no fence (`:408‑441`), the `catch`/`finally` clears this attempt's in-memory claims (`:1999‑2019`), and the stepper is constructed outside `executeSequence`'s try (`transaction-service.ts:237`), so admission-stage refusals never become `AggregateError`. On the later-turn path `cancelSequence` is reached up to three times (store `:2160`, stepper `:106`, `abort()` `:114`) but is idempotent (`:1429`) and `state.busy` is cleared first (`:2159`), so the typed error survives to HTTP.
- **Intentional 406-before-500 change:** spec 1949‑1957 plus the exhaustive table's shared‑406/"500 anywhere" exceptions (4618‑4628) permit either order; the sequence row carries no direct `409`, so a retained-member conflict must ride inside the 200 envelope, and the direct step‑4 rule (4533‑4539) is specific to the direct carrier. Existing `transaction-http.test.ts:1625‑1652` sends no `Accept` (`acceptsJson(null) === true`, `read-http.ts:90‑92`) and still reaches the 500 under the new order.
- **Oracles/counts:** the sequence root schema is closed to `operations` (`schemas/bdp-v0.schema.json:1778‑1792`), so per-member checking leaves no uncovered depth surface; `sequenceMemberProblem` permits `operationName` (`:2579‑2592`); the 41-object metadata claim matches the existing fixture construction (`transaction-set.test.ts:1123‑1125`) and the existing installed 41-iteration oracle (`…installed.test.ts:354‑359`); ledger request bytes are internally consistent (677/674/680/219/126, total 3179, max 680); installed bounds (5 s, 64 KiB request, 16 KiB request headers, 128 KiB response, 64 KiB response headers) match the existing direct executor wiring (`…installed.test.ts:382‑399`); all eight "unchanged" sequence titles and both HTTP titles exist verbatim and are top-level/`describe`-prefixed consistently with the anchored regexes; the crash-spawning case (`:454`) is correctly unselected.
