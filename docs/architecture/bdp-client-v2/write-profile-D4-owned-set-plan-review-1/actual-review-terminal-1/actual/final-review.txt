## Findings

### F1 — High — Report `counts` are frozen literals, not observations; the new mandatory failure report makes them actively false

* Current source: `apps/bdptest/src/transactional-set-installed.test.ts:429–436` — `receiptEntries: 33`, `receiptPages: [32, 1]`, `events: 96`, `groups: 1`, `negativeOracles: 5` are **literals**; only `eventPages: suffix.lengths` is derived from an observation.
* Frozen plan: `plan.md:9` gap list omits this; `report-contract.json:11` demands "**actual** receipt33/pages32+1, **actual** suffix96/pages32+32+32,group1"; `report-contract.json:17` forbids coercing unknown/null to clean; `request-inventory.json:484` warns counters must derive from observed rows; `plan.md:15` newly requires emitting a cached report on failure.
* Affected cases: C8 store/report barrier, M1/M2/M6, and P3 ("33 receipt entries/96 deletion Events/one group").
* Why it matters now: today these literals sit after passing assertions, so they are merely redundant. Once a **partial report must be emitted on failure** (`plan.md:15`, `report-contract.json:16`), an incrementally built report carrying the same literals reports `receiptEntries: 33`/`events: 96`/`groups: 1` for a run that observed none of them. That is precisely the "expected counts inferred as actual" failure the instruction set forbids.
* Smallest correction: inside the one owned file, split `counts` into `expected` (frozen inventory values) and `observed`, deriving the latter from captured bodies — `[...array(receipt.results), ...array(page.results)].length`, `[array(receipt.results).length, array(page.results).length]`, `suffix.events.length`, `array(feed.groups).length` — and keep `negativeOracles` as an explicitly labeled static local-oracle count (it is not a wire observation). Add the gap to `plan.md:9` and the derivation requirement to `report-contract.json` success/failure lists.

### F3 — Medium — The metadata capture to be "cached before launch" currently lives at module scope, so M7's `nullReason`/partial-report path is unreachable as written

* Current source: `test:23–26` (`realpathSync(entry)`), `:27–28` (env guard), `:29–31` (`execFileSync git rev-parse`, no timeout/maxBuffer), `:32–36` (fixture `readFileSync`) all run during **module evaluation**, before `it(...)` at `:103`; `entry`/`entrySha256`/`workspaceDirty` are produced late, at `:422–424`.

### F4a — Low — The proposed `8MiB maxBuffer` is a widening, not a bound

* Current source: `test:31` and `test:422` call `execFileSync` with no `timeout`/`maxBuffer`, i.e. Node's **implicit 1 MiB** `maxBuffer` applies today.
* Frozen plan: `plan.md:11` "bounding any retained Git capture (1000–2000ms timeout, 8MiB maxBuffer)".
* Smallest correction: label the two halves accurately — the timeout is new (tightening); `8MiB` **raises** the effective output ceiling 8× over the current default and needs a one-line rationale (large porcelain output should be captured rather than throw `ENOBUFS`) — or pin `maxBuffer ≤ 1MiB` to preserve the current effective bound. Either is contract-preserving; the plan should not call a widening a bound.

### F4b — Medium — "capture failure aborts before launch" collides with the external-consumer retarget run

* Frozen plan: `plan.md:11` + M7 require abort-before-launch on capture failure; `plan.md:21` and P3 require running **this same callback** from a fresh external consumer install; `report-contract.json:6` requires "actual bounded diff SHA/cache disposition" on success.
* Current source: `workspaceDirty` (`test:422`) unconditionally shells out to git with `cwd: root` (`test:13`), even when the source commit is already explicitly bound by env (`test:27–31`). In a consumer tree that is not a git work tree (or without git), the mandatory capture fails and, under the stated rule, the run can never reach launch.
* Smallest correction: make C0 path-explicit — ordinary workspace path = bounded capture whose failure aborts before launch; explicit-env retarget path = **no** Git capture, with a fixed `workspaceDirty: "not-applicable-externally-bound"` disposition that `report-contract.json:6` admits as a valid success value (distinct from a null-failure).

### F5 — Medium — Attribute store-lock release to process **exit**; the stdio `close` event is evidence completeness, not the reopen precondition

* Current source: `packages/server/src/transaction-store.ts:582` — `PRAGMA locking_mode=EXCLUSIVE; PRAGMA busy_timeout=0`; reopen also requires byte-exact stored configuration/contract capture (`:593–613`, `:599`, `:611`). Launcher `close()` resolves on the **exit** event only (`scripts/transaction-installed-observation.mjs:19–21`, `:48–60`).
* Frozen plan: `plan.md:13`; C4; M3 ("no reopen/removal until separate actual close; exit is not close").
* Why actionable: M3's phrasing can be read as making the stdio `close` event the predicate that *permits* reopen. What releases the exclusive SQLite lock is **process exit**; with `busy_timeout=0` a premature reopen fails immediately with SQLITE_BUSY. The `close` event is the stdio/IPC drain evidence. Both are required, but conflating them lets a future author mis-attribute an immediate-busy reopen refusal to "missing close evidence" (or vice versa).
* Smallest correction: in C4/M3, label `exit` code0/signal null as the **shutdown + lock-release** predicate and the actual `close` event as the **stdio/IPC drain evidence** predicate, require both, and give reopen rejection its own fixed stage label. Related: a reopen with mismatched artifacts/config fails *inside* the child before ready (`transaction-store.ts:599/611`), so it surfaces as a pre-ready rejection → UNKNOWN acquisition under C1/M5. Correct and fail-closed, but the fixed label should read "reopen refused pre-ready" so root can tell a configuration refusal from a genuine ownership unknown. Both stay UNKNOWN; no weakening.

### F6 — Medium — The CLOSED outer 150/TERM145/KILL149 proposal states no runner-startup budget, and the post-test detached drain is unaccounted for (assessment only)

Arithmetic from pinned sources: work deadline 90s (`test:108`); plan-local cleanup cap 10s (`lifecycle-inventory.json` `proposedCallbackCleanupMs`); callback 120s (`test:454`). Separately, the launcher's failure path can keep a **detached** 10s timer alive after the callback returns (`launcher:28–31` inside `bounded`, re-armed by `drainFailure` at `:38–45`), delaying worker exit by up to ~10s — the plan already notes the drain can outlive the local wait (`plan.md:17`) but never carries it into the outer budget. So worst case to observed runner exit ≈ `S` (runner startup) + ~100s callback + report flush + ~10s drain. With TERM at 145s, the proposal silently assumes `S + flush ≲ 33s` and never says so.

`history.json:3–18` records exactly this failure class twice (startup CODE, D3a PLAN): complete substantive results, **FAILED supervised finalization, CLI exit UNKNOWN**. The margin above is where D4 would reproduce it.

* Smallest correction (no change to REVIEWER 1800/TERM 1790/KILL 1798; no execution, signal or deadline release): the separate CLOSED mechanics packet must bind a **measured** maximum runner startup `S`, include the ~10s post-test launcher drain, require `S + 120s + report flush ≤ TERM`, and state that TERM must not precede the emitted-report flush. One attempt, no automatic extension, no retry — unchanged.
