## Findings

### 1. HIGH — The "entire record equals the prior record" oracle is not expressible
**Source:** §A.3, §A.5, §A.6, §B bullet 2; presupposed by §A.7 ("a whole-record comparison alone is not a property-view oracle"). Code: `executable-manifest.ts:166-183` (`json-equals`) vs `:187-198` (`json-pointer`).

**Issue:** `json-equals` has only two variants — authored `value` or fixture `fixturePointer` — with `normalize:"iso-timestamps"` and `timestampPointers`. It has **no `equalsBinding`** and **no scope-relative-URL normalization**. Only `json-pointer` carries `equalsBinding` (`:193`). A live Bead/Link record contains a server-allocated opaque `revision`, scope-absolute `endpoints`, and a dynamic `revisionProvenance.committedAt`, so no authored literal can equal it. Corroboration: across all 49 scenarios `json-equals` is used **twice**, both `fixturePointer`, both for `read.resource.properties-view`; `equalsBinding` is used **1,848** times; the installed `read-update.singleton.owned-link-no-op` row realizes its retention oracle with 275 `json-pointer` assertions and zero `json-equals`.

**Impact:** The plan's central retention oracle needs either a new assertion kind — which §B line 51 forbids ("no new assertion kind") — or a pointer-by-pointer enumeration whose exhaustiveness is exactly the failure the plan warns against ("do not merely compare actor or revision and miss other envelope changes"). As written the strongest clause in both rows is unimplementable, and the author discovers it mid-authoring.

**Minimal fix:** Name the realization: a closed `json-schema` assertion against `#/$defs/beadRecord` / `#/$defs/linkRecord` (both verified `additionalProperties:false`) to bound the member set, **plus** an enumerated `json-pointer`+`equalsBinding` assertion per member (`id`, `type`, `revision`, `properties`, `metadata`, `source`, `target`, `ownedLinks`, `revisionProvenance.actor.{id,basis}`, `.committedAt`, `.agent`, `.message`). Enumerate that list in the plan so "entire record" is auditable rather than aspirational.

### 2. HIGH — `bodyDigest`/`source` unobservable; the named digest control has nothing to mutate
**Source:** §B line 49 ("Raw-request observation source/writeState/bodyOctets/bodyDigest must agree with independently hashed authored bytes"); §B controls line 51 ("mutation of expected raw-body digest fails exact binding"); cites `runner.ts:1671-1673,1807-1808`.

**Issue:** Three separate defects.
- `request-authored-body` (`runner.ts:1921-1925`) does compare `bodyOctets` and `bodyDigest` to sha256 of the materialized authored body — but the expected digest is **recomputed**, never authored. There is no "expected raw-body digest" in the manifest to mutate, so the control cannot exist as described; the only way to break the assertion is to corrupt the observation.
- The cited `runner.ts:1802-1809` is the **report projection**, not the check, and it withholds `bodyDigest` unless `exactExecution.approvedSyntheticManifestDigest === artifactBundle.digests.manifestDigest`. `read-update-matrix.test.ts:385` sets `exactExecution` without that field, so `bodyDigest` is always absent from the installed report. The existing manifest contains **zero** `bodyDigest` references.
- `exactRequest.source` (`http-executor.ts:753`) has no assertion kind at all and is only in the report projection.

**Impact:** One promised oracle and one named sensitivity control are unbuildable; setting `approvedSyntheticManifestDigest` would hardcode a manifest digest in a test (and `runner.ts:1617`, `:2818` throw on mismatch) — brittle, and a semantic misuse of a *synthetic*-body approval on a production manifest.

**Minimal fix:** Reword line 49 to "`request-authored-body` + `request-write-state` prove the submitted octets, length and digest agree with the authored body"; realize the digest control as a wrapper in the owned `read-update-matrix.test.ts` that corrupts the returned `exactRequest.bodyDigest` after the real exchange; drop the `source` claim or move it to a static report check, and state that `bodyDigest` is absent from the installed report.

### 3. HIGH — `cumulative-artifact.test.ts` breaks beyond the whole-list the plan reserves to root
**Source:** Plan line 61 ("Root alone authorizes any eventual exact-whole-list update in `cumulative-artifact.test.ts`"). Code: `packages/conformance/src/cumulative-artifact.test.ts:100-193`.

**Issue:** That test builds its bundle from the single baseline `matrices/read-update-v1.json` and then asserts, for **every** coverage row: `expect(row.status).toBe(planned ? "bounded-observation" : "omitted")` (`:182`) and `expect(row.bindings[0]?.assertions).toEqual(...)` derived from the baseline manifest (`:189`). Flipping the two rows to `bounded-observation` with bindings owned by the **continuation** shard fails `:182` and `:188-193` independently of the whole-list at `:147`.

**Impact:** The slice cannot land green, and the plan assigns no owner for that edit — it permits only the whole-list change, by root.

**Minimal fix:** Name the planned/omitted + bindings cross-check as an edit that must be generalized to the artifact set (or confirm the segmentation lane already did it) and assign it an owner. *Caveat:* this breakage is implied by segmentation itself for any relocated row, so the other lane may have pre-resolved it — I cannot see that lane at `b919`.

### 4. MEDIUM — The Event clause is the likeliest whole-flag blocker and is absent from the council ask
**Source:** Plan line 22 (interpretation) vs line 69 (council-approval list). Law: `numeric-model-v1.json` 3rd requirement, `bdp.md:6649`.

**Issue:** The catalog selects "Read+Update has no durable Mutation Receipts and no BDP Events", and the spec's obligation row phrases the behavior as "...retains the revision **and emits no `updated` Event**". Line 22's interpretation is correct and honest. But line 69 asks council to approve only "the finite numeric equivalence partitions and the configuration-specific provenance absence interpretation". The Event clause — where the gap between the selected text and what HTTP can show is widest — is not put to council.

**Impact:** Council can close the slice having approved the two stated interpretations and still decline the numeric row's whole flag on the unapproved third, after all authoring and execution cost is spent.

**Minimal fix:** Add the Event clause to line 69's approval list, and name the concrete observation: closed `json-schema: #/$defs/readUpdateDiscovery` (verified `additionalProperties:false`, declaring no `events`/`receipts`/`changes`/`snapshot` — unlike `#/$defs/transactionalDiscovery`, which requires all four), plus `json-pointer exists:false` on those pointers.

### 5. MEDIUM — Guard pairs need distinct Idempotency-Keys; stated only for §B
**Source:** §A.2, §A.3, §B bullet 3 (vs §B bullet 4, which does say "under fresh keys"). Code: `member-executor.test.ts:523-531`.

**Issue:** Re-using a key with a changed body returns `idempotency-conflict` (409), not the intended outcome. §A.2 ("Old revision must fail … with `revision-mismatch`; the current revision must admit that no-op"), §A.3 ("Check a retained current guard succeeds") and §B bullet 3 each submit two bodies differing only in `expectedRevision`.

**Impact:** With a reused key the authority answers `idempotency-conflict` where the row expects `revision-mismatch` (409, `resource-evaluator.ts:145`) or success — the row silently measures the wrong law, and the failure looks like a target bug.

**Minimal fix:** State once that every guard, no-op and restore request in both rows carries a distinct literal Idempotency-Key, and count those keys in the per-row action ledger (line 57).

### 7. LOW — The index-schema question the plan defers is already settled at `b919`
**Source:** Plan line 61 ("may change only if its current schema actually carries digest fields needing refresh").

**Issue:** `parseIndex` (`read-update-artifact-set.ts:108`) routes the index through `ownData(…, ["version","shards"])`, each entry through `ownData(value, ["id","source"])`, and `ownData` throws on any other key (`profile-contract-plan.ts:84-86`). **Impact:** A live decision point is left open that the frozen source answers definitively; an implementer may re-derive it or, worse, add a field.

**Minimal fix:** Replace the conditional with the determined answer: the index is `{version, shards:[{id,source}]}` only and is not edited by this slice.

### 9. LOW — Per-resource GETs must bind their own fixture IDs, not the collection bases

**Minimal fix:** State that each row-owned Resource gets its own fixture binding, and that `view=properties` rides `target.query` on that binding.
