## Findings

### 1 — LOW-MEDIUM — The command minimum-control refusal runs ahead of authentication, suppressing the `401` challenge

- **Location:** `packages/server/src/transaction-http.ts:224`, inside the `operation !== undefined` branch. The auth decision for singleton/batch is only built at :257-262 and resolved inside `service.submit`; the sequence branch's own `401`/`403` checks are at :235-237 — all after :224.
- **Repro (probed):** `POST /acme/operations/batch`, `Content-Type: application/json`, `Idempotency-Key: u2`, `BDP-Minimum-Scope-Position: pos-9`, **no `Authorization`** → `500`, `x-bdp-development-limit: minimum-position`, **no `WWW-Authenticate`**. The identical request without that header → `401` + `WWW-Authenticate: Bearer realm="bdp-transaction-development"`. Same on `operations/sequence`. A read-only (non-mutating) principal → `500` + marker instead of `403`. Contrast the read branch, which is correctly auth-first: `GET /acme/beads/a` unauthenticated + the same header → `401`.
- **Impact:** no effect, no key capture and no protected state disclosed — verified `beads/a` still `404` after the unauthenticated probes. But a client or intermediary that relies on the `401`/`WWW-Authenticate` challenge to acquire credentials now gets an opaque bodyless `500` whenever it also sends a minimum control, and the fixture answers an unauthenticated request with a private development marker. It also breaks the ordering symmetry the slice deliberately maintains on the read side (`:291` before `:306`) and on the receipt branch (auth *and* existence before `:303`). This behavior is new in `7bfba52`, is not mentioned in `report.md` or the progress doc, and is untested — the new test always sends `Authorization: Bearer ${token}`.
- **Fix:** resolve authorization before emitting the marker, without disturbing the ordinary path:
  ```ts
  if (hasMinimumControls(request)) {
    if (authorization.kind === "unauthenticated") return transactionHttpProblem("unauthenticated");
    if (!authorization.canMutate) return transactionHttpProblem("forbidden");
    return developmentGap("minimum-position");
  }
  ```
  This keeps the refusal strictly before any key binding or effect, so F-A stays closed, and leaves the existing test green (it authenticates with a mutating token). Add unauthenticated and read-only rows to that test.

### 2 — LOW — Real authority-form `CONNECT` is refused `400 malformed-request`, never the method table; the test asserts a CONNECT shape no client sends

- **Location:** `transaction-runtime.ts:186-197` (the new `connect` listener) versus the origin-form gate at `:114-122`, which precedes `methodResponse` at `:124`. Test row: `transaction-http.test.ts:723` includes `"CONNECT"` in the method list asserting `405`.
- **Repro (probed):** raw `CONNECT 127.0.0.1:PORT HTTP/1.1` + `Host:` → **`400`** with a `malformed-request` problem body. Raw `CONNECT /acme/beads/a HTTP/1.1` → `405 Allow: GET, HEAD`. RFC 9110 §9.3.6 makes authority-form the only CONNECT request-target, so the `405` branch is unreachable in practice; the test passes only because its `rawMethod` helper always writes `url.pathname`.
- **Impact:** the `connect` listener does fire and does produce a well-formed response instead of a destroyed socket, so F-D's "no bodyless `500`" goal holds. But the one method the listener was added for never reaches `methodResponse`, so a tunnel attempt is labelled a malformed request rather than an unsupported method, and the test's CONNECT row gives false confidence that the method table covers it. No tunnel is opened either way, hence LOW.
- **Fix:** in the `connect` listener, refuse directly from the method (`empty(405, "GET, HEAD")` or a dedicated refusal) rather than routing an authority-form target through the origin-form path gate; or drop `CONNECT` from that test's method list and state in the progress doc that authority-form CONNECT is a `400`.

### 3 — LOW — F-B's `404`-vs-`405` contradiction survives outside `operations/` and is recorded nowhere

- **Location:** `transaction-http.ts:178-183` — the `404` arm is scoped to `pathname.startsWith(`${scopeUrl.pathname}operations/`)`; everything else falls to the shape-derived `405 Allow: GET, HEAD`.
- **Repro (probed):** `GET /acme/operations` → `404`, but `POST /acme/operations` and `DELETE /acme/operations` → `405 Allow: GET, HEAD`. Same for `/acme/zzz`, and for any absent bead: `GET /acme/beads/a` → `404` while `POST`/`DELETE` → `405 Allow: GET, HEAD`.
- **Impact:** this is literally F-B's original complaint — "handed a Read method table for a resource that does not exist" — now fixed inside `operations/*` and unchanged everywhere else. The design note at `:169-171` ("Target shape, never receipt existence or authorization, determines Allow") is the reason, and it is the right call: resolving existence before `Allow` would reintroduce exactly the receipt-existence oracle the slice works to avoid, which F-B's full fix text did not account for. So the gap is documentary, not architectural: `report.md` and the progress doc both describe the fix truthfully but narrowly, and nothing records that the contradiction persists for non-operation paths, so T3 may inherit F-B as fully closed.
- **Fix:** no code change recommended. Add one sentence to the progress doc: `Allow` is derived from target shape only, so non-operation paths answer `405` for wrong methods whether or not a Read resource exists there — the nondisclosure requirement for receipts is what rules out existence-resolved `Allow`.

### 4 — LOW — The batch-depth marker, which F-C used as its correctness reference, is still unasserted

- **Location:** `transaction-http.test.ts:408-412` — the pre-existing batch depth case asserts `status === 500`, empty body, no effect and key reuse, but not the marker. The new test at `:832-842` pins the marker for the sequence carrier only.
- **Repro (probed):** batch depth-40 does emit `unsupported-transaction-composition` today, so the behavior is correct. F-C's fix text asked for "a marker assertion to the depth cases on **both** carriers".
- **Impact:** the side F-C treated as the reference is unpinned, so a future change that flips the batch depth marker would be caught on the sequence side only — and the whole point of F-C was that a wrong marker is the failure mode that tests do not otherwise see.
- **Fix:** one line — `expect(depth.headers.get("x-bdp-development-limit")).toBe("unsupported-transaction-composition")`.
