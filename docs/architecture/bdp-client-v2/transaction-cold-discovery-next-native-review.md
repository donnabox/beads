# Native plan review: internal Transactional discovery assembly

## Finding

**P3 / Low — distinguish schema rejection from owner-identity rejection in the foreign-Scope predicate.** `transaction-cold-discovery-next-plan.md:46` groups foreign Scope into “Schema tests” with wrong profile, missing members and forbidden retention. The existing `$defs.transactionalDiscovery.properties.scope` is only an `absoluteHttpUrl` reference (`schemas/bdp-v0.schema.json:5014–5016`); it does not bind that value to the owner, nor does it enforce relationships between Scope and target URLs. A different well-formed absolute Scope remains schema-valid. Similarly, the schema deliberately accepts optional `historicalResolution` even though this candidate must omit it. Expecting the existing schema to reject either candidate-specific mismatch would produce an impossible negative oracle or pressure to change the schema outside the plan.

**Correction:** explicitly separate structural AJV controls (wrong profile, missing required member, invented/wrong directory member, forbidden retention.idempotency) from independent candidate-authority assertions (exact owner Scope and derived URLs, context equality, History absence, consumed limits). Require the foreign-Scope/source-context substitution to fail the owner-bound literal/identity assertion while documenting that the structurally valid mutated object can pass the unchanged normative schema. No schema or protocol change is needed. This is a test-plan precision issue, not a defect in the proposed owner seam or a request for broader implementation.

## Source-grounded feasibility and boundaries

The proposed private module/map extraction is feasible. `transaction-http.ts:56–69` supplies one frozen twelve-name map; its targets are constructed under `new URL("operations/", scope)`. `$defs.transactionalOperationDirectory` independently fixes all twelve relative values and closes membership. Reusing the map for HTTP while tests retain an independent normative literal avoids a shared wrong map validating itself. The new module can remain package-private under the current exports map; only its four emitted entries need the smoke inventory adjustment already permitted by the plan.

The service can produce an internal observation without a store accessor change: `owner.scope`, immutable `readConfiguration()`, and `withRead` expose the required data. Existing `sequenceObserved` demonstrates lifecycle `run`, a synchronous withRead callback, immutable return data and explicit propagation of `entry-refused.cause` (`transaction-service.ts:420–435`). `withRead` refuses fenced/closed/reentrant owners and rejects thenable callbacks; it expires its reader at exit. The proposed service method must use that same discipline, not return an entry-refused object as a successful description. Existing plan wording already requires this. No competing observation framework is warranted.

The no-pruning floor inference is grounded: spec3743–3747 defines minimumReplayPosition as the oldest legal exclusive Scope-changefeed cursor. `transactionCheckpoint(scope, context, 0)` returns genesis, and the current reader accepts it, treating missing committed positive rows as integrity failures (`transaction-changefeed.ts:53–85`; `transaction-store.ts:1660–1690`). Head pos-N and floor genesis are intentionally different token forms. Required bounded replay/reopen/receipt-expiry tests are a useful proof; the builder need not scan groups. The plan properly excludes future pruning and does not infer a duration promise.

For limits, `authority-read.ts:369–390` captures and checks page/Selector values against actual enforcement. The runtime derives those inputs, and service startup equates page maximum to persisted receipt maximum. Preserve exactly those captured page/Selector fields. The internal input also contains cursorTtlMilliseconds, which is not a Transactional wire limit field; the plan's closed wire projection must not spread that internal object. This is consistent with the plan's explicit prohibition on copying settings wholesale, not a new finding. Mutating caller-supplied options after service creation must not change either the established Read configuration or the discovery description.

Discovery success remains withheld at the explicit HTTP guards. The plan correctly distinguishes internal schema-shaped construction from a served profile assertion. C1 and alias HTTP integration remain prior serving work; no directory/Scope/descriptor route should begin succeeding in C3. No observed source dependency requires changing the store, public parser, configuration or admission APIs.

## Installed acceptance and scope

`packages/server/src/transaction-installed.test.ts` currently tests configuration capture only; it has no packed launcher fixture. The plan's conditional therefore resolves to the allowed app-level installed test using the existing launcher, not an expansion of the configuration test into a second launcher. `transaction-installed-observation.mjs` explicitly supports retaining a disposable directory and reopening with create:false. Reuse the same credentials/artifacts/configuration for reopen; live metadata and payload identity remain independently checked rather than inferred from the plan's description object.

Two sequential child sessions and32 requests are feasible for bounded negative discovery, credential checks, seed mutation, minimum collection reads and retained receipt replay/reopen. The exact test inventory still must be fixed before execution as required. No all-twelve-operation or complete cold walk belongs in that cohort; those are C4. A negative discovery cohort does not exercise the new internal description through wire/IPC, so its evidence must stay distinct from assembly/service tests. The plan explicitly preserves that distinction and does not advertise a successful cold client.

No other actionable finding in the bounded C3 proposal. This report does not authorize implementation, C4 serving, public admission or whole-contract credit.
