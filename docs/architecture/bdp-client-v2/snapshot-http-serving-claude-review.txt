### 1. MEDIUM — the nonallocating decision path does a full capture's work with no backpressure and no rate limit
`packages/server/src/transaction-http.ts:362` (`service.snapshot({ kind: "preflight" })`) → `packages/server/src/transaction-snapshot.ts:787-789` → `607-611`.

**Issue.** Every creation HEAD/304/412/406 runs the complete bounded pass — ledger + live-ledger validation, per-record decode/validate (`record`), the outgoing index, `checkGraph` over the whole graph, full page packing with SHA-256 digests, and prospective manifest/page serialization — inside the exclusive owner entry. By design it allocates nothing, which also means it consumes no live handle and therefore never trips the only pressure valve this slice has (`liveHandles: 8` → 503).

**Impact (measured, 4000 beads / ~4 MiB of bodies, this machine):** `HEAD` 90 ms, `If-None-Match: *` 304 85 ms, `If-Match:"x"` 412 86 ms, `Accept: text/plain` 406 85 ms — versus 5 ms for a retained manifest GET. All owner work is serialized on a single `busy` entry, so roughly 11 such requests per second saturate the owner for 100% of wall clock, blocking every mutation, point read, changefeed and retained snapshot read. There is no rate limit or connection cap anywhere in `transaction-runtime.ts`/`transaction-runtime-configuration.ts`, and unlike GET creation this path cannot be refused with 503. Cost at the real 32 MiB/4096-record ceiling with owned topology is higher still. The progress note discloses only "not a constant-time operation" (line 22) and "ledger/detail scans have nonconstant cost under the owner lock" (line 51) — neither names the asymmetry that the *nonallocating* path is both unmetered and unrefusable, and no evidence predicate covers repeated-decision cost.

**Fix.** Keep the strict nonallocation semantics (they are plan-mandated, and test 12's HEAD-observes-corruption predicate requires the full graph pass). Either (a) add this explicitly to the known-gaps paragraph in `docs/design/transaction-snapshot-serving-progress.md:49-51` — "repeated nonallocating creation decisions are unmetered, cost one full bounded pass each under the exclusive owner entry, and are not subject to the eight-handle refusal" — and add a measured repeated-decision predicate alongside the existing `offline4097-realHTTP413` witness; or (b) if a mitigation is in scope for a follow-up, gate it on the cheap prefix that already exists (`ledgerBounds()`/`totals` count-and-byte checks at `transaction-snapshot.ts:613-620` are O(1)-ish and answer 413/503 without any decode), deferring the full pass only where corruption detection genuinely requires it.

### 2. LOW-MEDIUM — a successful GET creation does the bounded pass twice, avoidably
`packages/server/src/transaction-http.ts:361-366`.

**Issue.** For `target.kind === "create"` the preflight always runs, then a GET that survives it runs the whole pass again in `service.snapshot(target)`. But the preflight contributes nothing to a GET whose `Accept` is acceptable and whose preconditions pass: `conditionalReadStatus` is evaluated against `headers.get("etag")`, which is `null` for both the preflight response and the final manifest response, and both responses are status 200 `application/json`. So the decision is a pure function of request headers in that case, and if the preflight had instead failed, the capture entry returns the identical problem code/status.

**Impact.** Measured 185 ms for a successful creation GET versus ~90 ms for the decision alone on the same 4000-record scope — the common success path costs 2× the necessary exclusive owner-lock time. Compounds finding 1.

**Fix.** Run the preflight only when it can change the outcome:
```ts
const probe = applyReadHttpSemantics(request, {
  status: 200,
  headers: new Headers({ "content-type": "application/json" }),
});               // header-only, owner-free: same status/content-type/absent-etag inputs
if (request.method === "HEAD" || probe.status !== 200) {
  const decision = applyReadHttpSemantics(
    request, snapshotResponse(await service.snapshot({ kind: "preflight" })));
  if (decision.status !== 200 || request.method === "HEAD") return decision;
}
```
This preserves every pinned behavior — no allocation on HEAD/304/412/406, observed context and `Vary: Accept` on 406/304/412, real capacity/integrity failures not converted into conditional success — because the only paths that skip the preflight are GETs that go straight to the allocating capture and return its own status and same-entry context.

### 3. LOW — uncovered scope: creation by a `canMutate: false` principal is an explicit plan requirement with no test
`packages/server/src/transaction-snapshot-http.test.ts:237` is the only use of the `reader` credential, and it covers retained manifest/page refetch only.

**Issue/impact.** Plan item 4 states "canMutate=false does not deny a safe Snapshot read"; the report's predicate 1 claims only "a second authenticated read-only principal reads it". The *creation* target is also a safe GET, and nothing in the route checks `canMutate`. I confirmed by live probe that `GET <scope>snapshot` with the read-only credential returns 200 with a schema-shaped manifest, `Vary: Accept`, `cache-control: private, no-store` and context. So this is uncovered scope, not a defect — but a future `canMutate` guard added to this route (as the operation branch at `transaction-http.ts:253` does) would regress silently.

**Fix.** In test 2 or test 1, issue one creation with `{ headers: { authorization: `Bearer ${reader}` } }` and assert 200 plus a usable `id`.

### 4. LOW — uncovered scope: continuation page bodies are never schema-validated
`packages/server/src/transaction-snapshot-http.test.ts:57-58` compiles only `snapshotManifest` and `transactionalProblem`; `collect()` at `183-195` asserts status 200 and then reads `items`/`next` untyped.

**Issue/impact.** Predicate 1 claims "creates a schema-valid manifest, follows both streams to null independently" — validity is asserted for the manifest only. I checked `schemas/bdp-v0.schema.json`: `beadCollection`/`linkCollection` require exactly `items` + `next` with `additionalProperties: false`, and the manifest additionally forbids a `links` affordance on bead items; the served `{items, next}` pages satisfy both (the same stored bodies back the inline first page, and test 1 line 263-266 shows the captured records carry no `links`). So no defect — a coverage gap on the one body shape that is only reachable over the new route.

**Fix.** Compile `{ $ref: `${schema.$id}#/$defs/beadCollection` }` and `linkCollection`, and assert the matching one on each page inside `collect()`.

### 5. LOW — uncovered scope: the preflight-specific byte-bound witnesses never run near their ceilings
`packages/server/src/transaction-snapshot.ts:765-775` (`firstPage`, `"serialized page bound"`) and the preflight call into `manifestValue`'s `"serialized manifest bound"` at `604`.

**Issue/impact.** The report claims preflight "validates prospective first-page/manifest byte bounds with the same serializer" — true in code, but the only boundary coverage is `transaction-snapshot.test.ts:742-747`, which exercises the retained path (`retain = true`). The new core test touches preflight only through a 503. A related by-design consequence is also unproven: because preflight and capture are separate owner entries, a scope sitting exactly on the 4 MiB/10 MiB boundary can yield HEAD 200 followed by GET bodyless 500 (the plan sanctions this — "capture-time capacity/integrity failure remains the real failure"), and nothing demonstrates it. Consistent with the disclosed unrun byte-cap stress; listing it so it is not mistaken for proven.

**Fix.** Add a `preflight` assertion to the existing page-boundary core test (same fixture, assert it succeeds and writes no rows), so the shared packing boundary is witnessed on both branches.

### 6. LOW — latent invalid `Retry-After: Infinity`
`packages/server/src/transaction-snapshot.ts:627` and `:689`.

**Issue.** `Math.min(...live.map((row) => row.d.expires))` returns `Infinity` for an empty `live`, which reaches HTTP as `String(result.retryAfter)` at `transaction-http.ts:345` — an invalid header value.

**Impact.** Unreachable today, and only by an unstated coincidence of two unrelated constants: the 503 branch with `live.length === 0` requires `totals.bytes > liveRecordBytes` (64 MiB), which the earlier 413 check at `:619` forecloses because `recordBytes` is 32 MiB. Nothing in the code asserts or documents `recordBytes < liveRecordBytes`, so retuning either limit silently turns this into a malformed response.

**Fix.** `live.length === 0 ? 0 : Math.max(0, Math.ceil((Math.min(...) - now) / 1000))`, or an `integrity(limits.recordBytes < limits.liveRecordBytes, ...)` at construction.
