## Findings

**1. Medium — `docs/specs/bdp.md:212` — `bead-data-model` alias silently widens the citation gate 93×**
`<a id="bead-data-model"></a>` sits immediately before `## Part I — Data Model`, so `markdownAnchors` classifies it as a heading alias (`level: 2`, `end: next.end`). `markdownSection("#bead-data-model")` therefore grew from 324 B (the base `### Bead Data Model` subsection) to 30,058 B — all of Part I. `validateCatalogCitations` (`packages/conformance/src/catalog.ts:164`) only requires `selectedText` to appear somewhere inside the anchored section, and `#bead-data-model` is not in `sharedAnchors`, so it has no excerpt bound.
*Impact:* a future catalog citation anchored at `#bead-data-model` can excerpt anything in the model — Types, aggregate constraints, revisions, attribution — and still pass. No live failure: no catalog cites it today.
*Fix:* move the anchor line to immediately **after** the `## Part I — Data Model` heading, ahead of the intro paragraph. The intervening prose makes `aliasesHeading` false → `level: 0`, `end` at `### Scopes and identity`, restoring a base-sized span. `headingOwners` still records profile 1 (the Part I owner is set before the sorted anchor is visited), so `profile-catalog-boundaries.test.ts:118` keeps passing.

**2. Medium — `packages/conformance/src/profile-catalog-boundaries.test.ts:76` (with `:18-19`) — the new link test cannot see the boundary this commit creates**
`assertProfileLinks` gates on profile rank, and `sections` assigns both `Part I — Data Model` and `Part II — Read` rank 1. The Data Model → Read boundary is therefore entirely unchecked. Evidence: the patch introduces exactly one new cross-part forward reference — `docs/specs/bdp.md:740`, in Part I / `Actor attribution`, links to `#immutable-change-context`, an L4 under Part II / `Historical resolution` (the *optional* History capability) — and `assertProfileLinks(spec)` passes.
*Impact:* the invariant the reorganization exists to express is unguarded; later edits can add model→Read dependencies freely. The editorial map's wording ("lower-profile forward dependencies") is technically accurate, which makes the gap easy to miss.
*Fix:* index each L2 part to an ordinal alongside the profile rank and assert no Part I-sourced link targets a Part II+ section; either relocate the `#immutable-change-context` sentence or record it as one explicit allow-list entry.

**3. Medium — `docs/specs/bdp.md:214` (Part I intro), with `:94-95` — Part I is not the minimal shared model it is introduced as**
Because no bodies were edited, Part I retains Read-profile wire statements and dependencies: `:266` "Serving alias resolution is Read surface, advertised through the `aliases` discovery member"; `:469` "The `ownedLinks` member defined below" (defined at `:1274`, Part II / `Resource records`); `:673` "Discovery MAY contain `maximumEndpointMultiplicity`" plus a discovery JSON example; `:727` "An advertised History resolver **MUST** serve the requested token unchanged"; and the `:740` forward link. Relatedly, the reading-guide invariant at `:94-95` was reworded from "A lower **part** does not depend on a later **part's** definitions" to "A lower **profile** does not depend on a higher **profile's** definitions" — that rewording is what makes the above legal, since the Data Model is declared not to be a profile.
*Impact:* a reader may treat Part I as self-contained and a reviewer can't tell whether the rewording is deliberate scope relief or incidental.
*Fix:* one sentence in the Part I intro — the shared model names Read-profile wire members where it constrains them, their definitions appear in Part II — and a line in the editorial map disclosing the rewording. No body edits needed, so the 137-body audit survives.
