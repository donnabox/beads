## Chosen input contract

Add `bdptest.deploymentFile?: string`, environment `BDP_BDPTEST_DEPLOYMENT_FILE`, absent by default. Validate only for bdptest/no-role content consumption: absolute filesystem path, nonempty well-formed string, no NUL/control characters, bounded to16384 UTF-8 bytes. Parse/store only; no file I/O inside `@bdp/config`. Known vocabulary remains global. Other roles ignore its content and omit it, preserving existing role isolation. Use the same name in code/docs; no aliases or implicit profile selection.

The file is a closed internal reference-deployment artifact, not a BDP artifact or protocol `$id`. `contract.md` below specifies the precise union and transformations. The implementation's validator/tests become its executable authority; do not add it to BDP schemas or normative conformance catalogs.

Top-level exact keys: `format`, `profile`, `configuration`. Format is `bdptest-reference-deployment-1`; profile is `read-update` or `transactional` and must exactly match explicitly configured server.advertisedProfile. No profile default/downgrade. Scope, listener, limit overrides, test seams, evidence constants, claimEligible, history, actor/provenance fields and arbitrary URLs do not belong at this level. Unknown fields are errors.

RU configuration exact keys: `directory`, `create`, `credentials`, `policies`, `contracts`, `maximumEndpointMultiplicity`. Delegate those values unchanged to `captureInstalledReferenceConfiguration` after injecting shared startup `scope` and `listener`. TX configuration exact keys: `directory`, `create`, `credentials`, `artifacts`; inject shared `scope`, invoke `captureInstalledTransactionConfiguration`, then seam-free `captureTransactionRuntimeConfiguration`. All strings for inner artifacts remain exact UTF8 strings for the existing compiler. No network retrieval, Type remapping beyond existing RU default, extra local artifact includes, external credential lookup, JavaScript plugins, implicit directory creation or stores opened by the loader.

**Bounded support choices for this slice:**

- RU permits existing installed loopback hosts127.0.0.1/::1 and port1..65535. TX permits its current fixed host127.0.0.1 and intended port1..65535. TX's private port0 remains internal capture machinery; the loader retains the separately validated intended listener for D3c, and does not claim current `startInstalledTransactionCandidate` consumes it. No public port0 support is introduced.
- Require the resolved shared Read limit tuple to equal the current seam-free enforced tuple for the chosen profile. Compare imported internal constants/readOptions, not hand-copied numbers used as a second enforcement source. Operators must explicitly configure differing-from-Read-default values. Unsupported limits fail closed with a fixed local configuration error. A later reviewed tuning slice can extend runtime enforcement, but is not necessary for this bounded supported configuration. Preserve all existing Read tuning behavior.
- `bdptest.fixture` must be absent when a write deployment file is actually consumed. A stored fixture identifier alone remains untouched; future fixture resolution is separate. No-serve mode only parses/stores configuration and must not read deploymentFile.
- Refuse `server.internalFaultResource` in this write loader because current mutable candidates do not implement that public fault wrapper. Do not silently drop it or inject test faults as ordinary credentials/policy. Existing Read handling remains unchanged.
- Read profile must not consume this Write loader. Later main selection should route explicit Read through the existing composition, without opening a write deployment file. An attempted direct loader call with read/undefined profile returns a fixed configuration error.

These are finite implementation support boundaries, not new BDP wire semantics or human-decision gates. The eventual complete profile requires honest applicability and sufficient supported fixtures; this plan does not waive D4.

## Loader algorithm and return boundary

Proposed new `packages/server/src/reference-deployment.ts` exposes one `loadReferenceDeployment` through new package subpath `@bdp/server/reference-configuration`, plus its structural input/result/error types. It is data/compilation only, never a start/admit factory. No root-index export and no new server→config dependency: receive a narrow structural snapshot of the already resolved startup fields.

Input fields: deploymentFile, scope.url, server.host/port/advertisedProfile/limits/internalFaultResource, and optional bdptest.fixture. Snapshot own data and validate shape; do not trust a public TypeScript cast. Use the existing administrative data discipline. Copy/freeze limit and listener data before any asynchronous/file operation; later changes to caller objects do not change the prepared result.

1. Reject unsupported/missing intent, fixture/fault conflict, unsupported host/port and mismatched limits before loading the artifact. Do not access a store, bind, call candidate factories or load any Type/schema resource over the network.
2. Open the specified file once; require an ordinary file and read at most32MiB+1 bytes, rejecting overflow, then close in finally. A stat check alone is not a read bound. Decode fatal UTF8; refuse BOM if the existing strict JSON decoder refuses it. The bound is an explicit deployment transport ceiling independent of the existing16MiB admitted inner-artifact budget: JSON escaping may cause a semantically small inner bundle to exceed it, which is an honest local input refusal.
3. Use existing `decodeJsonDocument` + `admitJsonNumbers` for duplicate-decoded-name, scalar/string and numeric admission; require the successful value, then enforce envelope maxdepth16 and100000 nodes using a finite iterative traversal. These bounds concern the outer document: embedded schema/descriptor JSON is still a string and retains its existing compiler depth/node budgets. No plain `JSON.parse` last-key-wins alternative.
4. Validate exact union keys and profile equality, then invoke the existing capture functions above. For TX, retain the installed capture and runtime preflight result; require contracts present, canonical authority, no seams, matching configured Scope, actual fixed readOptions tuple and compatible stream defaults. Runtime preflight compiles/authenticates data but does not produce live-owner metadata. For RU, use existing compile/policy/aggregate checks unchanged.
5. Return a frozen discriminated prepared object containing profile, canonicalScope, intended listener, enforced Read limits, captured installed input and compiled/preflight data needed by later internal startup. It is secret-bearing prepared state, not an admission capability. Do not serialize/log the whole object. A separately constructed safe summary may expose format/profile/Scope, artifact identity, matched limit tuple and a file-byte digest. RU existing policy/authentication/configuration identities may be included; for TX leave live policy/view/runtime identities explicitly unavailable until owner readback supplies them through the existing metadata function. Do not manufacture placeholder digests or parallel credential hashing.
6. Map expected read/syntax/shape/unsupported/contract errors to a typed fixed-code local error with sanitized message. Do not attach original parser text, file contents, tokens, arbitrary URI fields or credential-bearing cause. Unexpected invariant errors remain local failures with sanitized diagnostics, not BDP Problems. Config startup diagnostics only see the file path and shared settings, never inline registry data.

The immutable captured data, not a reread of deploymentFile, must be passed to later startup. Replacing the file after preparation cannot change the running selection. Existing runtime capture may compile the same frozen TX input again until D3c provides an internal captured-runtime seam; that is deterministic validation duplication, not a second policy. Do not add that runtime refactor here just to avoid it.
