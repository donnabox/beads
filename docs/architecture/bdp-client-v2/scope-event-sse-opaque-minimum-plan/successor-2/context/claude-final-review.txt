## Numbered findings

### 1. BLOCKER — D's baseline event count is wrong: the seeded group yields five Scope Events, not three

**Plan location:** `plan.md` §"D — serves initial Scope Event SSE opaque minima before conditional admission" ("One actual batch creates a,b,l", "the first returns two Events … The second returns one Event and next:null", "concatenate exactly three Events"), D table rows 2–3 and 30, "Status totals:200x5", the §"Exact legacy selection and aggregate bounds" totals (`75`/`86`), report contract `baselinePages array2`, and `workload.json` `newHttp:30`, `source.http:75`, `combined.http:86`, `newHttpStatuses."200":5`, `corrections.N1`.

**Source evidence:** `packages/server/src/transaction-batch.ts:771-804` — a `created` outcome emits one `created` scopeEvent, and then, for a Link whose `source`/`target` resolve in-scope, one `linked` scopeEvent **per endpoint** (`791-803`). `packages/server/src/transaction-store.ts` → `transaction-events.ts:250` sets `include = true` for every group event when `source.kind === "scope"`. Confirmed empirically in-repo: `packages/server/src/transaction-store.test.ts:125-130` shows `[create bead, create self-link]` → `created, created, linked, linked`; `transaction-store.test.ts:187` shows an external target drops one `linked`.

So D's seed `[create("a"), create("b"), link() /* a→b, transaction-event-sse.test.ts:471-478 */]` produces **five** Scope Events (ordinals 0–4: `created a`, `created b`, `created l`, `linked source`, `linked target`). The `linkType` at `transaction-event-sse.test.ts:24-31` is not an owning link, so no sixth `updated` source event (consistent with `transaction-store.test.ts`).

**Impact:** With `runtimeFixture`'s `receiptMaximumItems: 2` (`transaction-event-sse.test.ts:205`, cap applied at `transaction-store.ts:1745`), the canonical Scope `events/` baseline paginates **2 + 2 + 1 = three pages**, not two. D's row 3 would return 2 Events with a non-null `next`, so `expect(next).toBeNull()` and "exactly three Events" both fail; row 30 would receive five complete frames, not three; and the 30/75/86 and `200x5` totals are off by one request. The native N1 correction fixed the page count but inherited the same three-event premise, so successor-1 does not close this.

**Smallest concrete correction (recommended, preserves every count):** change D's seed to `[create("a"), link-to-self]` i.e. one bead `a` plus `links/l` with `source: "beads/a", target: "beads/a"` → **four** Scope Events → exactly **two** baseline pages (2 Events + actual next, then 2 Events + `next:null`). D stays at 30 requests, `200x5`, source 75, combined 86, `baselinePages array2`, and rows 24 (`beads/a`) / 25 (`links/l`) / 26 (`beads/missing`) still resolve — `b` is referenced nowhere else in D. Update the three affected sentences to "two Events … two Events and next:null", "concatenate exactly four Events", and "await exactly the four complete id frames".

**Alternative (if the a/b/l seed must be retained):** make the baseline three finite pages (2+2+1) and reindex D to **31** requests, `200x6`, source **76**, combined **87**, `baselinePages array3`, row 31 awaiting five frames, and update `workload.json` accordingly.

**Also (same root cause, prose only):** §A says "their equality does not claim the entire three-Event group" — the group is five Events under A's stated seed (A seeds the same `a,b,l` batch). A's assertions are unaffected (at `ownerFixture` maximum 1 both packets hold one Event), so this is a factual-statement fix, not an assertion fix.

### 2. BLOCKER — an existing assertion outside the six-file scope contradicts the new behavior, and the plan's own validation run cannot detect it

**Plan location:** §"Exactly six owned files, three production seams" ("no seventh file"), `preservation.json.productionChangedOnly`, `plan-binding.json:691-698` `ownedFiles`, and §"Review, validation and provenance sequence" (runs only `transaction-event-sse.test.ts` + `transactional-event-sse-installed.test.ts`).

```
await pair("events/", { ...opaque, accept: "text/event-stream" }, 500);
```

where `opaque` (`transaction-events.test.ts:1454-1458`) is the actual epoch + actual view + `bdp-minimum-scope-position: "opaque"`, the target is canonical Scope `events/` with no `after` and no `Last-Event-ID`, and `pair` (`1459-1512`) runs both GET and HEAD and, for status 500, asserts empty body, `x-bdp-development-limit: "minimum-position"`, and **absent** context headers (`observed = false`, line 1506).

Under the plan it becomes 503 `catch-up-timeout` with full context, `Retry-After: 1`, `application/problem+json` — so the status, body, limit-header, and context assertions all fail. (Verified path: `transaction-http.ts:514-529` new SSE predicate → `currentReadMinimumHeaders` parses `"opaque"` as a valid token (`transaction-consistency.ts:13,63`) → `checkCurrentReadMinimum(..., true)` (`transaction-consistency.ts:122-129`) → `TransactionMinimumUnproved` → `waitForTransactionMinimum` budget 80ms (`transaction-events.test.ts:1416`) → `catch-up-timeout` → `transaction-http.ts:650-663`.)

**Impact:** The "exactly six owned files / no seventh file" boundary is not achievable; the change breaks a seventh file. Worse, the plan's prospective command set runs only the two owned test files with an anchored title regex, so the break would first surface in full CI, after the plan's own "independent native and actual Claude CODE review" gate.

**Smallest concrete correction:** add `packages/server/src/transaction-events.test.ts` as a **seventh owned, test-only** file with a single-line change at `:1530` to
`await pair("events/", { ...opaque, accept: "text/event-stream" }, 503, "catch-up-timeout", true);`
plus the adjacent comment, and select the callback `serves initial finite Scope Event opaque minima through bounded waiting` (`transaction-events.test.ts:1398`) as a fourth legacy regression witness. `pair` issues 2 requests either way, so `expect(calls).toBe(32)` (`:1538`) and the `finite-event-minimum-http` report are unchanged; that callback's existing observation emits only `calls`, so no new report is invented. Then update `preservation.json` (add a prefix/whole-file hash entry or move it to a "changed" list), `plan-binding.json.ownedFiles`, `selection.json.legacySource` (+1 callback, +32 HTTP, +1 store/listener, +2 commits), and the aggregate totals. Alternatively, if the six-file boundary is hard, the plan must say explicitly that it leaves a known-failing test outside its scope — which would contradict "Known minimum, source identity/missing handling … retain their existing order" and should not be the chosen path.

### 3. MAJOR — A/B/C must pin the **src** module graph; a `../dist/*` import silently defeats the wait

**Plan location:** §"Exactly six owned files" item 4 ("Local imports needed by new cases may be dynamic inside appended callbacks/helper code. A may load test modules asynchronously…"), §B ("handing the real owner to `createTransactionService`").

**Source evidence:** `transaction-event-sse.test.ts:11` imports `openTransactionStore` from `./transaction-store.js` (src), while `:190`, `:611`, `:613`, `:754-757`, `:881-883` dynamically import from `../dist/*`. `waitForTransactionMinimum` (`transaction-consistency.ts:160-178`) retries **only** on `error instanceof TransactionMinimumUnproved` / `TransactionMinimumFailure`. Those classes are module-identity-scoped.

**Impact:** If B/C obtain `createTransactionService` from `../dist/transaction-service.js` while `ownerFixture` builds a **src** store, the dist copy's `instanceof` checks fail against src-thrown `TransactionMinimumUnproved`, so the first attempt rethrows immediately: no held wait, no second attempt, no `catch-up-timeout` at pos-2. B's entire schedule (3 attempts / 1 wait / 4 clock calls) and C's abort-during-wait collapse. The same hazard applies to A's `instanceof TransactionMinimumUnproved | TransactionMinimumFailure | TransactionMinimumUnsupported` checks. The plan's existing-precedent language ("may be dynamic", and every current dynamic import in the file targets `dist`) actively invites the wrong choice.

**Correction:** state explicitly in items 2/4 that A, B and C import `createTransactionService` from `./transaction-service.js` and the minimum error classes from `./transaction-consistency.js` — the same src graph as `ownerFixture`'s `openTransactionStore` — and that `../dist/*` must not be used for these three callbacks. (D and the legacy callbacks keep the dist runtime, which is correct and unaffected.)

### 4. MAJOR — C's `closed === false` check is not implementable as written

**Plan location:** §C ("Start service.close() while wait is held and observe that promise immediately. A synchronous `closed === false` assertion merely records that instant"); report contract C `closed:true`.

**Source evidence:** `transaction-service.ts:372` — `closed: completion.promise`. `service.closed` is a `Promise<void>`, not a boolean, so `service.closed === false` is vacuously `false` and asserts nothing. (`close()` itself is at `:737-758`; it sets `accepting = false` synchronously, then awaits `[...streams.values(), ...active]`, so the deferred-close instant the plan wants to record is real — only the expression is wrong.)

**Correction:** specify a callback-local flag, e.g. `let settled = false; void service.closed.then(() => { settled = true; }, () => { settled = true; });` and assert `settled === false` at that instant, retaining the existing caveat that this records an instant rather than proving deferral.
