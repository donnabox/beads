### High

**1. The Read/set-Selector coherence check duplicates an existing enforcing check and misses the one mismatch class it can actually catch.**
*Location:* plan line 67 · `authority-read.ts:367–389` · `transaction-read.ts:48–55` · `transaction-service.ts:65–97` · `transaction-set.ts:16`

`authority-read.ts:388` already throws `AuthorityReadError("configuration", "advertised Read limits must match enforcement")` when `advertisedLimits.selector` ≠ `selectorLimits` (and page/cursorTtl vs pagination). `createTransactionReadPlane` feeds both into that check at service construction (`transaction-service.ts:97`), i.e. before any `discoveryObserved()` can run. So "captured Read values agree with enforcement" is *already* a single enforcing source for the Read side; re-implementing it in the projection violates the plan's own single-enforcing-source rule. The genuinely reachable incoherence is the other one: advertised == Read-enforced but both ≠ `TRANSACTION_SELECTOR_LIMITS` (`transaction-set.ts:16`, fixed `4096/32/256`, not configuration-derived).

*Impact:* as written, the slice's "mismatched Selector bytes/depth/nodes each rejected" tests either re-prove an existing guarantee or exercise a state the service cannot reach, while the real mismatch class (Read config diverging from the fixed set core) can be read out of scope.

*Correction:* state that the advertised-vs-Read-enforced side is closed at `authority-read.ts:388` and must not be duplicated; the new check in `assembleTransactionDiscovery` compares the captured advertised triple against imported `TRANSACTION_SELECTOR_LIMITS` only.

**2. The premise that "arbitrary private seams can differ" is false for the installed configuration surface.**
*Location:* plan line 67 · `transaction-runtime-configuration.ts:89–97`, `:134–197`, `:291–297`, `:336–340`

There is no configuration seam for the Read Selector triple. `TRANSACTION_RUNTIME_DEFAULTS.selector` is fixed at `:97`; `captureSeams` (`:134–197`) accepts no `selector` key; `settings` (`:291–297`) overrides only `transport`, `receiptMaximumItems` and `maintenanceIntervalMs`. So `settings.selector` is always `{4096,32,256}` — identical to the set core. Only a direct in-source `createTransactionService` caller can produce a mismatch.

*Impact:* the row and the done-when read as guarding a configurable surface that does not exist. Worse for dispatch: the required test cannot be written through the runtime configuration path at all.

*Correction:* restate as defense-in-depth against a future seam or a direct in-source caller, and say explicitly that the mismatch test constructs the service/assembler directly.

**3. The installed-evidence condition is wrong: the C3 packed proof is invalidated by the source change itself, not only by an emitted-payload change.**
*Location:* plan line 80 · `apps/bdptest/src/transactional-discovery-installed.test.ts:255–278`

*Impact:* the condition "only if emitted payload changes" permits skipping fresh installed evidence while the progress doc would still read as if the refusal boundary is proven at the projection commit — the exact evidence-honesty failure this plan family forbids.

*Correction:* replace the condition with a stated disposition: either (a) re-run the unchanged 12/1 ledger against the new frozen commit (headroom exists under 16/1), or (b) record in the progress doc that the C3 packed proof binds `b20c929` only and the projection commit carries no fresh installed proof.
