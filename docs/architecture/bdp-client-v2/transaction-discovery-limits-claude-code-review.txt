## Findings

### 1. `limits.selector.*` is read twice — check and projection can disagree
**Severity:** Low · **Location:** `packages/server/src/transaction-discovery.ts:32-34` vs `:58-60`

The coherence check reads `limits.selector.bytes/depth/nodes`, then the object literal reads the same three properties a second time. Before this commit each advertised value was read exactly once.

**Failure scenario:** a direct internal caller passes an accessor-backed `advertisedLimits` (`Object.defineProperty(selector, "bytes", { get })`) returning `4096` on the first read and `1` on the second. The check passes; the candidate is assembled, schema-validated and frozen advertising `bytes: 1` — a Selector bound that neither the Read plane nor set mutation enforces. The frozen document carries no trace of the value that was actually validated.

**Impact:** bounded to direct `assembleTransactionDiscovery`/`createTransactionService` callers — the production path (`transaction-service.ts:87-95`) passes a frozen plain copy, and nothing serves the candidate. It is, however, a deviation from this repo's own read-once discipline: `authority-read.ts:369-389` builds the frozen copy *first* and compares the copy, and `transaction-service.test.ts:1293-1300` asserts single-read semantics against getters for the adjacent pagination fields.

**Bounded fix (owned file, no behavior change on the frozen path):** destructure once and use the locals in both places —
```ts
const { bytes, depth, nodes } = limits.selector;
if (bytes !== TRANSACTION_SELECTOR_LIMITS.bytes || depth !== … || nodes !== …) throw …
// …
selector: { bytes, depth, nodes },
```
Optional companion case in `transaction-discovery.test.ts`: a getter-backed `selector` that flips after the first read must not produce a candidate.

### 2. Test gap — the installed default Selector triple is never bound to `TRANSACTION_SELECTOR_LIMITS`
**Severity:** Medium (test coverage) · **Location:** `packages/server/src/transaction-runtime-configuration.ts:96` (duplicated literal `{ bytes: 4096, depth: 32, nodes: 256 }`); gap at `transaction-runtime-configuration.test.ts:400-401`

`TRANSACTION_SELECTOR_LIMITS` is referenced by **no test file in the repo** (`grep` over `src/*.test.ts` and `test-support/` returns nothing). The runtime-configuration test only asserts *identity* between `settings.selector`, `readOptions().selectorLimits` and `readOptions().advertisedLimits.selector` — never equality with the constant the new check enforces.

**Failure scenario:** the duplicated default at `:96` is edited to `{ bytes: 2048, depth: 32, nodes: 256 }`. `authority-read` is satisfied (advertised == Read-enforced == 2048), Read then enforces 2048 while `updateWhere`/`deleteWhere` keep enforcing 4096 (`transaction-set.ts:135`, `transaction-batch.ts:854`). The entire suite still passes — the new assembler check is the only live consumer of the agreement, and no installed/HTTP path and no runtime-configuration test calls `discoveryObserved()`, so the frozen 12/1 installed cohort cannot exercise it either. The commit makes this agreement load-bearing without pinning it.

**Impact:** the coherence check cannot detect the drift it exists to catch in the only configuration that ships; the divergence stays silent until discovery is actually served.

**Bounded fix:** one assertion, e.g. `expect(TRANSACTION_RUNTIME_DEFAULTS.selector).toEqual(TRANSACTION_SELECTOR_LIMITS)` in the existing `transaction-runtime-configuration.test.ts` case at `:399-401`. This is a fifth file, outside the four approved — report to root for bounded disposition per plan ¶26 rather than broadening scope here.
