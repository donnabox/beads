## Findings

1. **Optional (low) — `packages/server/src/transaction-events.test.ts:1940-1945`.** The proven‑minimum positive read asserts only `current.kind === "page"` and `groupReads > 0`; nothing pins the served representation. A regression that satisfied the gate but served an empty or non‑member page would pass. Smallest correction: add `expect(current).toEqual(setup);` (both results are deterministic at `pos-1`, same context, same deterministic Event ids). Same gap exists in the Scope/Bead predecessors, so this is a consistency improvement, not a new defect.

2. **Optional (low) — `packages/server/src/transaction-events.test.ts:2063-2068`.** D validates the live Link page only by schema plus `page.source`; own‑membership at the HTTP layer is asserted solely for the *retained* page (2190‑2191). Consequence: an HTTP‑layer projection change that added a non‑member fact (e.g. a `linked` row) to a live Link page would be caught only at the owner layer (A) and in installed E. Smallest correction: after line 2067 add `expect(page.events.map((event) => event.type)).toEqual(["created"]);` and `expect(page.events[0].subject).toBe(`${scope}links/l`);`.

3. **Optional (low) — `packages/server/src/transaction-events.test.ts:2211-2213`.** Plan D specifies the exact distribution `200×8, 400×4, 404×3, 500×12, 503×8` and "ordered method/suffix/status observations", but only `503`, `500` and `calls` are asserted; the ordered array and the 200/400/404 families are logged only (2223‑2233). Per‑row `expect(response.status…)` already pins each individual status, so this is defense in depth for the audit rather than a behavioral hole. Smallest correction: add `expect(responses.filter((r) => r.status === 200)).toHaveLength(8);` plus the 400/404 equivalents, or assert the full ordered list the way the installed callback does at `apps/bdptest/src/transactional-event-missing-context-installed.test.ts:1195-1200`.

4. **Optional (low) — `packages/server/src/transaction-events.test.ts:2038-2054` and `apps/bdptest/src/transactional-event-missing-context-installed.test.ts:1056-1127`.** The mandatory "`x-bdp-development-limit` absent on non‑500" rule is asserted only inside `pair` (2102) and inside E's 503 loop (1165). The five non‑`pair` exchanges in D (seed 2055, setup 2063, deletion 2167, `links/gone` 2178, retained 2185) and E's two 200 exchanges have no such assertion; a stray gap marker on a 200/404 would be recorded in the observation JSON but not fail. Smallest correction: inside each `exchange`, add `if (response.status !== 500) expect(response.headers["x-bdp-development-limit"] ?? null).toBe(null);` (Headers form in D: `expect(response.headers.has("x-bdp-development-limit")).toBe(false)`).

5. **Optional (low) — `packages/server/src/transaction-events.test.ts:2217-2222`.** If `runtime.close()` rejects, `rmSync(directory, …)` is skipped, so the temp directory survives; the log is still truthful (`directoryAbsent: false`, `failureCount ≥ 1`), so this is a leak‑hygiene point, not a false claim. Smallest correction: give `rmSync` its own `finally` (or a second `try`) so close failure cannot skip removal. Note the trade‑off: adopting it here diverges from the Bead predecessor at 2217, which plan‑v3 requires to stay unchanged (only two sentinels may move), so leaving it as‑is is also defensible.

6. **Optional (cosmetic) — `packages/server/src/transaction-service.test.ts:2992-3003` and `3053-3064`.** The three‑operation seed literal is duplicated verbatim across B and C. Smallest correction: one module‑local `const linkSeed = [create("a"), create("b"), { operation: "createLink", … }]` next to `linkEventTypes:2975` and pass `batch(linkSeed)` in both. Purely editorial; the plan's "no broad helper extraction" also makes keeping the duplication acceptable.
