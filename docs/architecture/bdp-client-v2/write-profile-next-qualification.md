## Transactional: first atomic owner/store slice

1. **Atomic success:** preseed target B; batch creates A and an ordinary unowned Link `@A → B`. Observe complete Resource effects, durable terminal receipt and one ordered group with a common transaction identity/position. For this chosen topology, expect A `created`, Link `created`, and its source/target `linked` facts. Validate receipt and group against current wire schemas.
2. **Late permanent failure:** append a failing guard or invalid mutation. Verify A, Link, allocations and induced facts all roll back; a failed terminal receipt remains under the admitted key, with no group/new position. Correcting the body under that retained key conflicts; a new key may execute.
3. **Intermediate state versus final state:** update one Resource twice, including reversal. Keep both real transitions/revisions/ordered Events, but only its final complete postimage in the group. An entirely semantic-no-op batch completes without a group or `effectPosition`; its receipt still reports current `requiredPosition`.
4. **Concurrency:** two batches sharing an `expectedRevision` cannot both succeed. Identical concurrent principal/key submissions join the same pending/terminal receipt; changed semantics conflict. Race a multiplicity bound if the first contract set supports it; otherwise mark that case unexercised.
5. **Durable admission and recovery:** key, normalized identity, pending receipt, transaction ID and exclusive attempt ownership persist together. Crash after admission but before commit; reopen and retract every pending receipt without a committed group within advertised `transaction.duration` or an authority-selected finite bound. Recovery MUST NOT resume execution on its own; the client retry is a fresh admission after retraction. Crash after effects/receipt/group commit but before response; retry returns the same disposition and cannot duplicate facts.
6. **Transient abort/fencing:** retract pending receipt and release key together for a transient abort. A replacement attempt gets distinct ownership; the stale owner cannot subsequently commit or resolve its replacement. Do not convert an internal error automatically into a retained permanent failure.
7. **Atomic publication failure:** inject a failure writing the receipt/group after staged Resource mutations. Recovery sees either the entire completed boundary or no Resource/group commit; no successful Resource commit followed by a best-effort publication step.

Naming these rows is traceability, not an assertion that one test completely covers each row.

Reuse the `ResourceTransaction` interface in `resource-evaluator.ts` and its evaluator tests for guarded mutations, owned-Link effects, final Type validation and metadata changes. Supply one transaction facade for the entire batch. **Do not loop through `executeMember` or reuse the Read+Update store's per-member terminal commit:** those would commit prefixes and apply the wrong key-state law. `recovery-store.test.ts` offers useful failure-injection and ownership patterns, not evidence for the new Transactional store.

The Transactional catalog retires twelve Read+Update rows, explicitly listed in `transactional-catalog.test.ts`: discovery/limits/directory, singleton result headers/retry, concurrent-in-progress behavior, replay authorization, retention/expiry, restore namespace and internal-fault handling. Preserve those overrides. Later Transactional sequence support also needs the T62/T65 unresolved-dependency reservation/comparison rules; a batch-only first slice should refuse unsupported sequence forms and leave those cases unclaimed.

Snapshots/checkpoint rendezvous, full Event-source delivery, pending receipt HTTP admission, receipt pagination, authorization projections, erasure, set mutations and restored-epoch semantics remain separate qualification work. A stored group or receipt reader alone is not the Transactional profile.
