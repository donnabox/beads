**1. HIGH — Done-when #3/#4's "controlled actual owner progression" is unreachable in the installed harness the same plan mandates.**
*Location:* plan lines 75, 76, 81 vs. 73, 82; `packages/server/src/transaction-installed.ts:8,11-12`; `transaction-installed-configuration.ts:20-26`; `transaction-installed-process.ts:1-3`; `transaction-runtime-configuration.ts:112,196,371`.
*Issue:* `startInstalledTransactionCandidate` calls `startTransactionRuntime(captured)` with **no seams argument**, and `captureInstalledTransactionConfiguration` admits only `scope/directory/create/credentials/artifacts`. Even if a seam could be threaded, `captureSeams` sets `supplied: true` for *any* seam key, which makes `metadata()` return `undefined` (`:371`), which `transaction-installed.ts:11-12` then converts into a hard `"installed transaction metadata unavailable"` throw. So the installed candidate is locked to `minimumReadBudgetMs: 1000`, real `performance.now()`, and real `≤5 ms` sleeps (`transaction-consistency.ts:90-92,118`). The deterministic mechanism the plan is implicitly pointing at — `minimumReads.wait` performing a real commit, as in `transaction-http.test.ts:1093-1122` — exists only in the source-private fixture.
*Impact:* Done-when #3 (behind → later commit satisfies) and #4 (no progress → 503) can only be witnessed installed as wall-clock races, which plan line 81 forbids; and #10's "runtime configuration identities" is mutually exclusive with any seam that would remove the race. An implementer will discover this only after writing the installed test.
*Fix:* Split the oracle in the plan: keep controlled progression in the private HTTP test (reuse the `minimumReads.wait` pattern), and state that the installed witnesses for #3/#4 run against the fixed 1 s budget with real sleeps — with a measured wall-clock line in the ledger (≥1 s per no-progress assertion × GET/HEAD × bead/link ≈ 4 s+ before the 32-row/cohort caps). If genuinely controlled installed progression is required, declare it as scope expansion into `transaction-installed-configuration.ts` + `transaction-runtime-configuration.ts` as a *recorded wait-policy setting* (so `configurationMetadata` survives), and get root approval before implementation — not as a seam.

**2. HIGH — Minimum-vs-control-refusal precedence is unresolved, and the slice silently converts existing 400s into 503s.**
*Location:* `authority-read.ts:982-993` and `:751-760`; `transaction-read.ts:46-56`; `read-request.ts:954-968`; `read-pagination.ts:581-592`; `transaction-http.ts:531-532`; plan line 61 and done-when #7.
*Issue:* `observe` materializes first, then calls `checkSourceCondition` with the materialized refusal. `transaction-read.ts`'s hook special-cases only `resource-not-found`; every other refusal falls through to `checkTransactionMinimum`. Point reads cannot produce `control()` refusals, so this path is new with collections: `validateLimit` and `selectReadResources` run inside `control()`. Concretely, `GET beads/?limit=33` (over `maxPageItems` 32, `transaction-batch.ts:63`) or `?selector=<malformed>` with a behind minimum waits the full budget and returns **503 `catch-up-timeout`** instead of the existing **400 `limit-exceeded`/`invalid-parameter`**. The route gate at `:531-532` only intercepts URL-grammar 400s, so `?limit=0` stays 400 while `?limit=33` becomes 503.
*Impact:* An inconsistency introduced by this slice, directly contrary to plan line 61 and done-when #7, with no normative basis — spec:5805 orders the minimum check before *conditional* shortcuts only, not before request-validity refusals.
*Fix:* Write the rule into the plan and pin it: either (a) validate `limit` and `selector` in the route predicate / `minimumFor` before the owner entry so these remain 400, or (b) have `transaction-read.ts`'s hook re-raise any materialized 400-class refusal before `checkTransactionMinimum`. Add the `?limit=33` + behind and `?selector=<malformed>` + behind cases to the private HTTP test either way.

**3. MEDIUM-HIGH — "initial Bead/Link collection" does not close the route set, and `bead-links` behaves differently.**
*Location:* plan lines 61, 65, 73-74; `read-request.ts:236-251`; `authority-read.ts:815-820`; `transaction-read.ts:47-51`; pinned at `transaction-http.test.ts:1065-1091`.
*Issue:* `beads/{id}?view=links` parses to a distinct `kind: "bead-links"` page operation, not `kind: "collection"`. When its anchor Bead is absent or invisible, `materialize` returns `resource-not-found`, which the existing hook turns into `TransactionMinimumVisibilityGap` → 500 `minimum-position-visibility`. The plan explicitly defers absent-point-vs-minimum ordering (lines 46, 53) yet its predicate wording ("initial current Bead/Link collection", "initial Bead and Link collection GET") does not exclude incident-Link collections or `collection:types`.
*Impact:* If an implementer includes `bead-links`, the slice imports an unresolved normative question and contradicts done-when #2 for an absent anchor; if they exclude it, nothing in the plan says so, and the two allowlists (`transaction-http.ts` route gate and `transaction-read.ts.minimumFor`) can drift — a drift that surfaces as a bare 500 with no `x-bdp-development-limit`, since `minimumFor` rejects with a plain `TypeError` caught by `transaction-http.ts:591`.
*Fix:* State the predicate as one closed, shared expression — `kind === "collection" && (collection === "beads" || collection === "links") && continuation === undefined` — name `bead-links` and `collection:types` as out of scope and retained on `minimum-position-route`, and require the identical predicate in both files (ideally one exported helper) so a mismatch is impossible.

**4. MEDIUM — The "real read-after-write failure" framing is not supported by the source, and done-when #1 is not a discriminating oracle.**
*Location:* plan lines 13, 15; done-when #1 and #9; `transaction-store.ts:897-956`; `transaction-http.ts:530-539`.
*Issue:* On this single-owner installed service, `withRead` captures `readContext()` inside the same `enter` as the read, so an ordinary collection GET issued after a completed mutation already observes at-or-after that mutation's effect position. Nothing stale is served today; what `:530-539` refuses is the *explicit* minimum assertion. So done-when #1 would pass identically with the source condition deleted, and with a header-echoing fake.
*Impact:* Overstates the defect being fixed, which is what justifies this slice's priority over C2/C3; and done-when #9's negative control cannot bite on #1, only on the behind/timeout/foreign-view/epoch cases — which is exactly where finding 1 says the installed harness is weakest.
*Fix:* Reword line 15 to "closes an unsupported-control refusal on the read-after-write path" rather than a read-after-write failure, and bind done-when #9 explicitly to #3/#4 (behind, catch-up-timeout, 409 `foreign-view`, 410 `cursor-expired`) rather than to #1.

**5. MEDIUM — No abort signal reaches the minimum read, so an abandoned collection read burns the full budget at collection cost.**
*Location:* `transaction-http.ts:227` vs. `:444`, `:474`, `:487`; `transaction-service.ts:240-247`; `transaction-consistency.ts:107,118`; `authority-read.ts:822-838`; plan line 84.
*Issue:* The Read `perform` route calls `facet.perform(parsed)` with no options, so no signal — while the changefeed and Event routes do pass `request.signal`, and both `readAtMinimum` and `waitForTransactionMinimum` already honour one. With 5 ms backoff against a 1000 ms budget, a behind collection read re-runs full materialization (`reader.resources()` plus per-row parse/validate/owned-pair checks) roughly 200 times, and a client disconnect does not stop it. The plan discloses the repeated-materialization cost but not the missing cancellation.
*Impact:* The slice turns an existing cheap uncancellable wait (≈200 single-row lookups for points) into an uncancellable O(200 × N) row-parse amplification on the serving path. The asymmetry with the feed routes indicates omission, not a decision.
*Fix:* Pass `{ signal: request.signal }` from the `perform` route in `transaction-http.ts` (an owned file), state in the plan that this also newly cancels the existing point-minimum wait, and add a disconnect test. If that behaviour change to the point path is unacceptable, say so and record the uncancellable amplification explicitly in the feasibility paragraph instead of only the per-attempt cost.

**6. LOW-MEDIUM — Widening the allowlist flips a pinned negative expectation the plan never names.**
*Location:* `transaction-http.test.ts:1016-1028`; plan line 69, done-when #7.
*Issue:* An existing test asserts 500 / `x-bdp-development-limit: minimum-position-route` for the exact list `["beads/", "alias/missing", "", "bdp.json", "operations/", "beads/?cursor=missing"]`. Plan line 69 permits "corresponding private Read/HTTP tests" changes but never identifies this assertion, nor that `beads/` must flip to 200 while `beads/?cursor=missing` must stay 500.
*Impact:* The one existing guard against exactly the regression done-when #7 is worried about gets edited without the plan saying how, inviting a wholesale deletion of the pinned list instead of a split.
*Fix:* Name this test in the owned-files section and require it split: `beads/` and `links/` move to positive cases; the refused list keeps `?cursor=` continuations, `alias/`, scope, `bdp.json`, `operations/`, and gains `types/` and `beads/{id}?view=links` (per finding 3) so the out-of-scope routes are positively pinned rather than merely untested.

**7. LOW — "current revision" in done-when #1 is ambiguous, and the wrong reading adds an out-of-scope validator.**
*Location:* plan line 74; `read-http-routing.ts:55-76`; `read-http.ts:50-55`.
*Issue:* `scopeDataResponse` sets `ETag` only for `kind === "properties"` (from the observed revision) and `kind === "resource"` (from `body.revision`). Collections carry no `ETag`; a record's `revision` appears only inside the body.
*Impact:* An implementer reading "current revision" as an ETag would add a collection validator, changing `conditionalReadStatus` outcomes and silently expanding done-when #5 beyond the slice.
*Fix:* Say "each returned record's `revision` member; collections intentionally carry no `ETag` and this slice adds none", so done-when #5 is tested against the existing behaviour (`If-None-Match: *` → 304, a concrete `If-Match: <tag>` → 412, both carrying the three context headers, which `applyReadHttpSemantics` already preserves by copying the response Headers).
