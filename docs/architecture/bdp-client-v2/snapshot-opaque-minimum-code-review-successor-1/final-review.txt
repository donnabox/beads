## Findings

### Optional improvements (non-blocking)

**O1 — Low — `packages/server/src/transaction-service.test.ts:3347-3349`: the "abort does not interrupt the deferred wait" claim is not discriminated.**
`controller.abort(); release[0]!.resolve(); expect(await cancelled).toBeInstanceOf(ScopeServerOperationAbortedError);` releases the gate in the same synchronous block as the abort, so a hypothetical implementation that aborted the in-flight `wait()` would produce an identical observation (same error class, same `waits === 1`). The intended ordering property (`waitForTransactionMinimum` only checks `signal?.aborted` at `transaction-consistency.ts:161`, i.e. after the wait resolves) is therefore asserted by construction, not observed.
*Smallest correction:* attach a `settled` flag in the `cancelled` chain, and between `controller.abort()` and `release[0]!.resolve()` insert `await Promise.resolve(); expect(settled).toBe(false);`.

**O2 — Low — `packages/server/src/transaction-service.ts:444` and `packages/server/src/transaction-store.ts:1573`: bare `catch { throw captured.error; }` in the lexical arm.**
A non-`TypeError` escaping `snapshotCurrentReadMinimum` would be replaced by the strict `TypeError`. This is currently **unreachable**: `snapshotTransactionMinimum` (`transaction-consistency.ts:57-62`) already ran the identical data-only capture on the same input with no intervening user code, so any non-`TypeError` would have escaped the first catch's `if (!(error instanceof TypeError)) throw error;`. The shape also matches the plan's "lexical failure rethrows the original strict error" wording, so this is a deliberate choice.
*Smallest correction (only if defensive symmetry is wanted):* `catch (error) { if (!(error instanceof TypeError)) throw error; throw captured.error; }` in both files.

**O3 — Low — `packages/server/src/transaction-http.test.ts:5734`: `expect(waits).toBe(8)` proves the aggregate, not per-request attribution.**
The eight 503 rows and the two known-minimum rows (2–3) share one counter; the test would still pass if, say, one 503 row waited twice and one known row waited zero/once incorrectly. The one-call-per-branch property is covered separately at `transaction-service.test.ts:1208-1226`.
*Smallest correction:* record `waits` before/after each `get(...)` in the 503 loop and assert a delta of 1 (and 0 for rows 2–3).

**O4 — Informational — `packages/server/src/transaction-snapshot.test.ts:1504`: `expect(after).toEqual(baseline)` is vacuous if neither callback ran** (both `undefined`). Mitigated by `expect(offlineInspections).toBe(2)` at line 1510, so no change is required.

**O5 — Known, plan-deferred coverage gap — `packages/server/src/transaction-http.test.ts:2749-2803`.** The two emitted Snapshot GET/HEAD disconnect rows remain strict `pos-2` only; no selected callback exercises client disconnect on the new opaque wait (same waiter, `transaction-http.ts:636` rethrows `ScopeServerOperationAbortedError`, so the risk is low). Plan v3 §"Exact selection totals" defers this explicitly; it is a real residual gap, not a divergence.

### Behavior-surface notes (intentional, but observable beyond the "unknown token" framing)

**N1 — `packages/server/src/transaction-http.ts:423-425`.** Switching to `currentReadMinimumHeaders` changes the fresh-create response for *every* position token the strict helper rejects — not just opaque words. Non-canonical canonical-looking spellings (`pos-01`) and unsafe-integer positions (`pos-9007199254740992`) now take the bounded-wait path and answer 503 instead of the private 500 gap (`transaction-consistency.ts:26-31,122-130`). This is intended and pinned (`transaction-snapshot.test.ts:1487` uses `pos-01`), and it matches the already-shipped Resource behavior at `transaction-http.test.ts:4886`. Worth stating explicitly in any release note so it is not mistaken for accidental widening.

**N2 — unknown + foreign epoch/view stays non-normative.** `checkCurrentReadMinimum(..., true)` raises `TransactionMinimumUnsupported` (`transaction-consistency.ts:122-128`) → `developmentGap("minimum-position")` → private 500, rather than the 410/409 a known tuple gets. Byte-for-byte the same observable outcome as before the change (previously via `minimum === undefined`), so there is no regression, and plan v3 excludes the policy decision. Spec §5841-5843 would want one of representation/wait/foreign-view/cursor-expired/catch-up-timeout here, so this remains a tracked non-conformance, unchanged by this draft.

**N3 — `closed-malformed` ordering (`transaction-service.test.ts:3449,3468-3473`).** A closed service still performs synchronous tuple validation before `run()`'s `check()` (`transaction-service.ts:430-454` vs `140-141`), so the malformed `TypeError` wins over "closing or closed". That is the pre-existing Snapshot order and is now pinned; it is the opposite of what a lifecycle-first reading would predict.

I read `design.md`-adjacent normative spec lines only as cited; no mutable workstream plans or historical validation paperwork were consulted.
