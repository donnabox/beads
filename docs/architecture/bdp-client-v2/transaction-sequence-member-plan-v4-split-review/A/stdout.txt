## Verdict

Not clean. One **proven Critical defect** makes six of the ten actions (2–7) unachievable as literally specified; the remaining findings are mostly missing-supplied-proof gaps plus two robustness defects in how position tokens and the negative's scope are pinned. After Finding 1 is repaired, the narrowed claim set (terminal success/failure/success, independently retained receipts, no-effect replay, member-index-vs-internal-index, current-vs-historical context, deleted identity) is semantically feasible within the literal requests, with no runner/API/fixture widening.

## Critical

**1. Companion singleton bodies for s-first-receipt / s-failed-receipt / s-last-receipt carry no idempotency key, so they cannot return the retained member receipts.**
- Location: `COMPANION positivePostBodies[1]` (bytes 147), `[2]` (bytes 66), `[3]` (bytes 146) vs `PLAN ten actions` rows 2, 4, 6 ("POST batch equivalent create a/**member-a**", "missing delete/**member-fail**", "create b/**member-b**").
- Status: **proven defect** from supplied source.
- Why the required results are only reachable by keyed replay: `transaction-store.ts:1258-1310` assigns a successful group `position = previous+1` and sets `requiredPosition/effectPosition` to that position; a failed member gets `requiredPosition: pos-${previous}`. After action 1 the Scope is at pos2. Therefore:
  - Row 2 asks for `completed`, `required/effect pos1`. A fresh (keyless) transaction cannot be assigned an already-committed earlier position, so `effectPosition pos1` is impossible regardless of how a duplicate create of the existing `beads/a` is dispositioned.
  - Row 4 asks for `required pos1`. A fresh keyless failing delete yields `requiredPosition: pos-2` (previous = 2), not pos1.
  - Row 6 asks for `required/effect pos2`; impossible for the same reason as row 2.
  - Rows 2/4/6 also require retained *internal* framing (`internal index 0`, `next null`, retained problem) that only exists on the member's own singleton receipt.
  - Rows 3/5/7 depend on the `/id` captures from rows 2/4/6, so they fall with them.
- Supplied evidence that keyed replay *does* reach the member receipts: receipts are keyed by `(principal, key)` with no carrier discriminator (`transaction-store.ts:1104-1125` INSERT), and member keys are the sequence body's `idempotencyKey` values (`transaction-batch.ts:277-309` uses `carrier.keys[index]` for the derived singleton).
- Smallest correction: add the member key to each of the three singleton bodies, matching the sequence members' own construction — `,"idempotencyKey":"member-a"` → bytes 175; `,"idempotencyKey":"member-fail"` → bytes 97; `,"idempotencyKey":"member-b"` → bytes 174 (byte deltas 28/31/28 computed from the supplied literals); digests must be recomputed. Prefer the body field over a header (see Finding 10).

## High

- Location: `PLAN ten actions` rows 1,2,3,4,6,7,8,9,10 ("current pos2", "required/effect pos1", "required pos1", "required/effect pos2"); spelling source `transaction-store.ts:1258` / `:1272-1296`; `transaction-events.ts:74-75` grammar.

- Impact: if the Scope is not fresh at pos0 (shared-scope execution, any preceding baseline write), all ten rows' position literals are wrong and the run fails for a non-semantic reason; the literals also re-pin a private token spelling.
