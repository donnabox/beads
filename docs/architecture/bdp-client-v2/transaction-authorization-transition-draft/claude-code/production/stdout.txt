## Findings

**1. HIGH — receipt prefix and first continuation page can overlap or skip entries.**
`transaction-store.ts` → `observeReceipt` (lines ~903-915). `prefix = receiptPrefix(receipt)` slices to `plan.maximum` from `pagePlan(receipt)` and takes `next` from `plan.pages[0]`, whose `start` is that same `plan.maximum` (the page path reads `plan.pages[index].{start,end}`). The projected body instead slices to the configured constant `receiptMaximumItems` while reusing `prefix.next`. The two boundaries coincide only if `pagePlan` is purely count-bounded. If `pagePlan` also bounds by bytes (the usual reason a plan exists), then for any receipt where `plan.maximum < receiptMaximumItems` the embedded prefix serves entries `[plan.maximum, receiptMaximumItems)` that the first `next` page serves again — duplicated result entries across one receipt's representation, and a prefix that can exceed the page byte budget. Minimal fix: derive the slice from the plan actually used, e.g. `results: projection.results.slice(0, (prefix.results as readonly unknown[]).length)`.

**2. HIGH — `projectTransactionEntry` fails open on unrecognized entry shapes.**
`transaction-authorization.ts` → `projectTransactionEntry`. Under `visible === false`, anything that is not an object with `outcome` in `{created, updated}` *and* a defined `resource` is returned verbatim. The function is applied to three distinct streams (`observeReceipt`/`receipt()` results, the page path in `transaction-store.ts`, and `sequenceObserved` in `transaction-service.ts`). Any record-bearing shape it does not pattern-match — a record under a different outcome, a nested record, a future entry kind — is disclosed in full under the empty policy, silently. The permissive fallback is the privacy-relevant default in a module whose whole job is withholding. Minimal fix: invert to a whitelist — under `visible === false`, accept only `matched`/`deleted`/`erased`/`withheld`/alias shapes, assert that no `resource`, `source`, or `sourceRevision` member survives, and throw otherwise.

**3. HIGH — `sequenceObserved` narrows the response body to `{results}` in both generations.**
`transaction-service.ts:628-654`. Previously `body` was the whole `response`; now it is a fresh object literal containing only `results`. Every other retained member of `TransactionSequenceResponse` is dropped unconditionally, including on the generation‑0 all‑visible path, so this is not gated by the policy change. Minimal fix: `const body = { ...response, results: response.results.map(...) }`. Related: if `response.results` members are member *receipts* (bdp.md:5230 explicitly names "the projection of a member's receipt into a sequence response"), then `projectTransactionEntry` is the wrong projector — a member receipt has no `outcome`, so finding 2's fallback returns it unchanged and discloses its `created`/`updated` records. The per-receipt `detail: "withheld"` collapse is also never applied on this path.

**4. MEDIUM — any rejected in-flight mutation aborts the policy transition.**
`transaction-service.ts` → `replaceAuthorizationPolicy`. After `Promise.allSettled([...mutations])`, `failed.length` throws `AggregateError`, and `finally` calls `resume()`, re-admitting mutation under the old snapshot. Mutation rejections are routine (client disconnect → `ScopeServerOperationAbortedError`, development-limit errors, prepared-batch assertion failures), so a single unrelated failed request anywhere in the drain window defeats the transition; under sustained traffic it can fail indefinitely. The accepted semantics ("abandons waiting/publication, not admitted work") do not require treating a *settled* failed mutation as a blocker — a rejected mutation holds no admitted work, and a drain that fenced the owner is already caught by the following `check()`/`enter()`. Minimal fix: drop the `failed` check, or restrict it to owner-fencing causes.

**5. MEDIUM — the format‑10 → format‑11 migration is non-idempotent on partial application.**
`transaction-store.ts` open block (`if (storedConfiguration === legacyBytes)`). Two statements run in order: `INSERT INTO metadata VALUES('authorizationPolicy',?)` then `UPDATE metadata SET value=? WHERE name='configuration'`. If they are not inside the enclosing `atomic()` (not visible in the supplied region — see omitted context), a crash or error between them leaves `configuration === legacyBytes` *with* an `authorizationPolicy` row, and the next open hits `throw new Error("unexpected legacy authorization policy")` — a permanently unopenable store. Minimal fix: wrap the migration in `atomic()`, and make the guard tolerant: accept an existing policy row that parses to the generation‑0 snapshot instead of rejecting it.

**6. MEDIUM — non-authenticated read routes now yield 500 rather than an authorization problem.**
`transaction-http.ts` → `readPrincipal` / the wrapper's `readPrincipals.set`. The map is populated only when `authorization.kind === "authenticated"`; otherwise `readPrincipal` throws a plain `Error`, which the catch chain maps to `empty(500)`. The prior code passed `{kind:"anonymous"}` and served. This is correct only if the outer admission gate guarantees `authenticated` for `resolveAlias` and `perform`; otherwise an ordinary unauthenticated read becomes a 500. Minimal fix: fall back to `{kind:"anonymous"}` (or raise `TransactionAuthorizationFailure("forbidden")`) instead of a bare `Error`.

**7. MEDIUM (unverified, concrete) — generation‑0 Snapshot handles may permanently consume issued-handle capacity.**
`transaction-snapshot.ts`. The relaxation `d.view === context.authorizationView || d.view === INITIAL_TRANSACTION_VIEW` was added to the shared `integrity` helper, and `lookup` then rejects old-view handles as `foreign-view` before the expiry check. But `expire(now, context)` and `liveLedger(now, context)` selection predicates are not in the diff. If either selects on the current view, old-view handles are never reclaimed, `ledgerBounds() >= limits.issuedHandles` stays true, and every subsequent `allocate` fails `limit-exceeded` — including the empty-snapshot allocations the new policy is supposed to serve. Needs confirmation against the unchanged bodies; if it holds, the fix is to make expiry/ledger accounting view-agnostic within the epoch.

**8. LOW — the installation assertion is now vacuous.**
`transaction-runtime-configuration.ts` → `captureTransactionRuntimeConfiguration`. `actual.authorizationView !== actual.authorization.authorizationView` compares two copies of one field: `readConfiguration()` sets `authorizationView` *from* `authorization.authorizationView`, so the condition can never be true. Replacing a literal check with a self-comparison removes the only live validation that the serving view is one of the two legal values. Minimal fix: assert the generation invariants (generation 0 ⇒ `INITIAL_TRANSACTION_VIEW` + `all-visible` + `canMutate`; generation 1 ⇒ UUIDv4 + `empty` + `!canMutate`).

**9. LOW — `activeSequences` membership has no `finally`.**
`transaction-store.ts` → `admitSequence` (`activeSequences.add`), `advance` (`if (done) ... delete`), release path (`activeSequences.delete(attempt)`). Any abandonment that routes through neither leaves a stranded entry, after which `replaceAuthorizationPolicy` returns `temporarily-unavailable` for the life of the process — an in-memory latch on a privacy-critical operation. Minimal fix: derive liveness from `sequenceAdmissions` + the existing `cancelled` flag rather than a parallel set.

**10. LOW — idempotent replacement can fail after it has already succeeded.**
`transaction-store.ts` → `replaceAuthorizationPolicy`. The `activeSequences`/`owner IS NOT NULL` liveness refusal precedes `if (authorization.generation === 1) return authorization;`, so a retry against an already-final policy reports `temporarily-unavailable`. Move the generation check first.

**11. LOW — pause acquired outside the protected region.**
`transaction-service.ts` → `replaceAuthorizationPolicy`: `owner.pauseMutationAdmission()` runs before `run(...)`, so its `resume` lives only in the async body's `finally`. Currently unreachable (nothing between the two can throw once the first `check()` passed), but a throw there would strand `mutationPause` and refuse all mutation permanently. Acquire inside the `try`, or guard with a local `catch { resume(); throw; }`.

**12. NIT.** Four files (`transaction-events.ts`, `transaction-runtime.ts`, `transaction-snapshot.ts`, `transaction-service.ts`) now place the new `import` *above* the module docblock, which detaches each file's `/** ... */` from the module. `transaction-service.ts` → `stream` drops `observed.cause` when `withRead` refuses, and its `"kind" in selected` coercion silently breaks if `TransactionReadContext` ever gains a `kind`.

## Essential omitted context

- `transaction-changefeed.ts` → `projectTransactionChangeGroup` lines ~133-147 are elided. If that validation compares the retained group's `authorizationView`/`scopeEpoch` to `context` (as the sibling `projectTransactionEventGroup` does, which is why *it* needed the `visible ? context.authorizationView : INITIAL_TRANSACTION_VIEW` relaxation), then every post-transition changefeed read throws "invalid retained change group" → 500 instead of the invisible group. No equivalent relaxation appears in this diff. This is the single highest-value gap to close.
- `pagePlan` / `receiptMaximumItems` relationship (finding 1), `TransactionSequenceResponse` shape (findings 2, 3), and whether the open-time provisioning block is inside `atomic()` (finding 5).
- Whether `authorization.kind` can be other than `"authenticated"` on read routes, and whether `createReadHttpRoute` ever invokes `perform`/a lazy body after the wrapper's `finally`, or re-dispatches HEAD/duplicate POST with the *same* `Request` object — the `readPrincipals` WeakMap delete is not nest-safe.
- `transactionCheckpoint` and the changefeed `after`-cursor binding: the invisible group recomputes `checkpoint` from the current context while the visible branch returns the retained `group.checkpoint`. Whether pre-transition cursors and minimum-position tuples are rejected or silently accepted across the view change is not shown.
- Snapshot issued-page serving: whether page bodies can be fetched by token without passing through `lookup`'s new `foreign-view` fence.
- `transactionHttpProblem` status mapping for `forbidden` / `foreign-view` / `temporarily-unavailable`, and the `allocated`-entry schema (`receiptAllocation` was not expanded), needed to confirm `{operationIndex, operationName?, withheld:true}` is schema-valid.
- The five test diffs are outside this review's scope; findings 1, 2, 3, and 7 are the ones most likely to be unobserved by the authored workload, since each is either byte-boundary dependent or shape dependent rather than path dependent.
