1. MEDIUM — Private-session and ledger refusals are reported as a target

--------------------------------------------------------------------------------
Location: packages/conformance/src/runner.ts:868-984 (privateExecute body),
          packages/conformance/src/runner.ts:1064-1079 (runProgrammaticAction

Impact: every refusal raised inside `privateExecute` is a plain `Error` (or a
`ConformanceRunnerError`) thrown through `execute(execution)`, and
runProgrammaticAction's catch rewrites *everything except* ScenarioDeadlineError
into `new ScenarioActionExecutionFailure("action execution failed", {cause})`.
runScenario:695 maps that to `state: "fail"`. So these all surface as the
installed target failing a Transactional contract:

  - "receipt not authorized by original wire observation"  (unobserved URL,
    cross-binding, substituted receipt)
  - "transaction session unavailable"  (action before prepare / after close)
  - "unvalidated physical session transition"  (endpoint change without reopen)
  - "invalid reopened session", "source receipt observation changed"
  - "receipt session logical identity changed"
  - "exact transport required", "missing actual receipt observation"
  - "invalid private receipt input" / "unsupported private transaction action"

This directly contradicts the reviewed plan's receipt-authority item 7
("Unknown/mismatched ledger data is harness error, not server outcome") — a
harness/manifest defect is published as negative target evidence. Worse, both

Note the asymmetry: register-time refusals thrown from runRequest's capture loop
(runner.ts:1476) *do* reach runScenario as unclassified errors and become
`harness-error`. Only the client receipt lane is mislabeled.

Fix: classify these as harness errors. Either (a) perform
`transactional.resolve(...)` / session validation in runScenarioAction before
calling runProgrammaticAction so the `ConformanceRunnerError` propagates
unchanged, or (b) let runProgrammaticAction rethrow `ConformanceRunnerError`
(and a new `TransactionalHarnessError`) verbatim the way it already passes
ScenarioDeadlineError through, and record `failure.cause` message in
`executionError.message`. Then pin each countercontrol test to its expected
refusal reason rather than `not.toBe("pass")`.

4. LOW — The "internal source-response digest mismatch" countercontrol has no
   reachable failure mode
--------------------------------------------------------------------------------
Location: packages/conformance/src/transactional-observation.ts:140, 145, 153

Impact: `responseDigest` is sha256 of `response.wireResponseBytes` at
registration; `entry.wire` is a `Buffer.from(...)` copy of the same bytes held in
a closed Map that nothing else can reach. `resolve()` then re-hashes that private
copy and compares it to the digest derived from it — the branch is a tautology
and can never fire. The reviewed plan lists "internal body or source-response
digest mismatch" as a mandatory countercontrol; the observation test's
`["body","octets","status","headers","wire","absent"]` cases all exercise
*registration-time* inconsistency (transactional-observation.test.ts:141-161),
none exercise post-registration tampering.

Fix: either drop the branch as dead defensive code, or make it meaningful — e.g.
digest the bytes that the subsequent read actually re-derives, and add a test
that injects a differing stored copy.
