## Optional observations (no behavior defect)

**2. Low — `apps/bdptest/src/transactional-minimum-receiving-installed.test.ts:987-994`: the deliberately preserved directory is itself recorded as a failure on every failing run.**
Issue: deletion is gated on `!launchAttempted || (closed && failures.length === 0)`, but the following `if (!directoryAbsent) fail(new Error("installed receipt root directory preserved"), "directory-retained")` is unconditional. Whenever the callback has any real failure, the directory is intentionally retained and then reported as an additional failure.
Impact: cosmetic but misleading evidence — `failureCount`/`failureCategories` in the `private-installed-receipt-root-minimum` record and the thrown `AggregateError` gain a non-failure entry that contradicts the record's own `startupLimitation` note. It cannot mask a real failure (the run is already failing) and cannot cause a false clean deletion.
Smallest fix: hoist the predicate — `const removable = !launchAttempted || (closed && failures.length === 0);` — use it for the `rmSync` guard and change the check to `if (removable && !directoryAbsent) fail(…)`.

**3. Low — same file, `:972-975`: one cleanup-deadline root cause yields two distinct failures.**
Issue: when `cleanupExceeded` is set, the race rejection already produces `fail(cleanupReason, "cleanup")`, and the `else if (launchAttempted)` branch adds a second, different error object (`"installed receipt root clean close unproved"`, category `unclean-close`). `fail`'s dedupe is identity-based, so both are retained.
Impact: truthful but doubled accounting; the aggregate's member count no longer corresponds to distinct causes. Deletion/`closed` remain correctly fail-closed.
Smallest fix: skip the `unclean-close` entry when `cleanupExceeded` is already recorded (`else if (launchAttempted && !cleanupExceeded)`), or leave as-is deliberately.

**4. Low — `packages/server/src/transaction-http.ts:574-578` and `:587`: the root-path `?? "unsupported"` fallback and the root `result.kind === "unsupported"` branch are now wire-unreachable.**
Issue: `malformedTransactionMinimumHeaders` at `transaction-http.ts:404` already returns `400 malformed-request` for any present-but-missing/lexically-invalid field, and `Headers.get` joins repeats, so once `hasMinimumControls(request)` is true on the root path `currentReadMinimumHeaders` always parses (every token-valid position, recognized or not, is accepted by `snapshotCurrentReadMinimum`). The owner's `{kind: "unsupported"}` root sentinel therefore can no longer be produced over HTTP; the private `500 minimum-position` gap now arrives only via the thrown `TransactionMinimumUnsupported` caught at `:663-664`.
Impact: none observable — the retained fallback is defense in depth and keeps `receiptAtMinimum`'s `TransactionMinimum | "unsupported"` contract and the direct-API sentinel intact. It does mean the historical title `refuses unsupported root controls …` (`transaction-http.test.ts:2174`) no longer has any sentinel oracle at all; the remaining root-sentinel coverage is the direct service call in `transaction-service.test.ts:3594` and the untouched page fences (`transaction-http.test.ts:2230-2256`, installed page row `:507-512`). The inline comment at `transaction-http.test.ts:2211` is the only in-test statement of that; this matches the corrected plan's "evidence identifier" instruction.
Smallest fix: none required. If you want the comment to carry the whole claim, extend it to say the sentinel is now exercised only by the direct service/page paths.

**5. Low — `packages/server/src/transaction-http.test.ts:2176-2179`: the added waiter seam is load-bearing, not cosmetic.**
Issue/impact: after the owner change, the four own-credential root reads each exhaust a minimum-read budget. With the default 1000 ms budget plus the retained real 1100 ms sweep-isolation delay at `:2187`, the callback would need ≈5.1 s against Vitest's unoverridden 5000 ms default (`vitest.config.ts` sets no `testTimeout`), i.e. the historical callback would time out without `budgetMs: 2`. Removing or widening the seam later re-introduces flakiness; `maintenanceIntervalMs: 60000` and the 1100 ms delay must both stay for the no-disposal oracle.
Smallest fix: none; consider a one-line comment recording why the seam is required.

**6. Low — spec framing of the unchanged foreign-opaque gap (`transaction-http.test.ts:5852-5862`, installed `:507-512`).**
Issue: spec 5841-5843 lists foreign-view / cursor-expired / catch-up-timeout as the normative outcomes for remaining reads; D rows 5/6 pin a bodyless `500` with `x-bdp-development-limit: minimum-position` and no context. That is a deviation, but it is byte-identical before and after this draft: previously the strict parser produced the `"unsupported"` sentinel and `developmentGap("minimum-position")`; now `checkCurrentReadMinimum(…, true)` throws `TransactionMinimumUnsupported` and reaches the same `developmentGap("minimum-position")` (`transaction-http.ts:663-664`), with the same `empty(500)` headers and the same HEAD behavior (`applyReadHttpSemantics` is a no-op for a bodyless 500).
Impact: no regression; flagged only so the newly added rows are not read as new conformance coverage. The draft's comment already says they "preserve the excluded foreign-opaque gap, not 409/410 conformance."
Smallest fix: none in scope (foreign-opaque normative policy is excluded).
