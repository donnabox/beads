## Findings

Line numbers are post‑patch, per the supplied working‑repair excerpt.

**1. Low (diagnostic precision; introduced by this patch) — `retained-failure-full-equality` now asserts two unrelated properties under one label.**
`apps/bdptest/src/transactional-guarded-batch-installed.test.ts:830-837`. The closure first asserts request‑4 fingerprint binding (`:832-835`) and only then the receipt comparison the label names (`:836`). Because `check()` propagates the first failing expectation, a fingerprint divergence is reported as `failedAssertion: "guarded-batch:retained-failure-full-equality"`, and `performed` omits the label in both cases. Impact: a supervisor reading the report cannot distinguish "the retained failure receipt changed across replay" (the contract) from "request 4's send‑local key/body selection diverged" (a harness fault); the two have different dispositions. Fix, within the stated no‑new‑label constraint: move `expect(replay.body).toStrictEqual(loser.body)` to the top of the closure so the named property is the one that fails first, and keep the fingerprint binding as trailing corroboration. (A distinct label would be cleaner but adds a `performed` entry, which is out of scope here.)

**2. Low (latent, currently unreachable) — `losingResponse?.…` is used as the *expected* value, so undefined‑vs‑undefined would pass.**
`:833-835`. `expect(replayResponse?.sentKey).toBe(losingResponse?.sentKey)` and the two following assertions compare optional‑chained reads on both sides. Today `losingResponse` is proven non‑undefined by `:820` (`expect(losingResponse?.index).toBe(aWire.index)` fails on `undefined` because `aWire.index` is `2`), and `check()` throws before `send(4)`, so the path is unreachable. But the guarantee is positional: if `:820` is ever reordered, weakened, or the index predicate at `:818` drifts, all three bindings degrade to vacuous `undefined === undefined` passes while the label still lands in `performed`. Fix: bind once non‑optionally after an explicit existence assertion — `expect(losingResponse).toBeDefined(); const losing = losingResponse!;` — and use `losing.sentKey` / `losing.requestBodySha256` / `losing.requestBodyBytes` as the expected values.

**3. Low (evidence attribution; regression from the removed wrapper) — a one‑sided pair rejection is no longer distinguishable from a solo transport‑3 fault.**
`:755-758`. `currentAssertion` is last set by `send(3)` to `guarded-batch:transport-3`, so the outer catch records `failedAssertion: "guarded-batch:transport-3"` and `failedPhase: "transport"` whichever contender rejected. Previously the thrown `AggregateError` carried `"guarded-batch pair transport failed"` plus both reasons, which compensated; now the thrown value is `pairErrors[0]` and, when only one contender rejects, the final rethrow is that bare error (`failures.length === 1`). Impact: the report and the thrown value both read as "request 3's transport failed", losing the fact that the fault occurred in the concurrent pair dispatch and, when request 2 was the failing one, misnaming the request. Accounting itself is correct — this is evidence fidelity only. Fix, with no report‑shape change: set `currentAssertion = "guarded-batch:pair-transport"` immediately before the `throw` at `:757` (the field already ranges over `setup`/`launch`/`transport-N`/`receipt-N`, so this is a new value, not a new field), or add the pair context via `cause` on a rethrow of `pairErrors[0]` only if a non‑identity wrapper is acceptable — which it is not under F1, so prefer the label.

**4. Informational (no defect) — residual self‑comparison in `frozen-loser-replay-input`.**
`:820`, `:824-825`. Given `replayBody = losingInput.body` at `:816`, the assertions `requestBodySha256 === sha(replayBody!)` (`:824`) and `requestBodyBytes === Buffer.byteLength(replayBody!)` (`:825`) cannot fail independently of `:823` (`requestBodySha256 === losingInput.hash`), since `losingInput.hash` is itself `sha(losingInput.body)`. Likewise `:820` compares `responses[loserIndex+2].index` with `(aWire|bWire).index`, both of which are the same `index` closure constant from one `send()` invocation. The load‑bearing new facts are exactly: `:823` (the body handed to `req.end` for the losing contender hashes to the `originals` entry) and `:821-822` (receipt key ↔ dispatched `Idempotency-Key` ↔ frozen `replayKey`). No change required; flagged so the strengthening is not over‑read.
