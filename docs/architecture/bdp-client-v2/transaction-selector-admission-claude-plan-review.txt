## F1 — HIGH: deep-safety specimen's expected `413` contradicts the plan's own cap precedence

**Location:** plan §"Exact Selector constructions for tests" → "Deep safety specimens"

The specimen is `$[?` + 10000 `(` + `@.missing` + 10000 `)` + `]` = **20,013 UTF-8 bytes**, depth 10002, nodes 10002. All three caps are violated. The plan's authoritative selection rule is "within it bytes, then depth, then nodes", so the emitted limit is `selector.bytes` — but the plan asserts "fresh submission gets `selector.depth` 413".

**Impact:** the authored test fails; the likelier bad outcome is an author "fixing" it by reordering precedence, silently diverging from the rule H1, H2 and installed rows 7–11 all depend on. It also violates the plan's own isolation rule ("independent measured bytes/depth/nodes must prove isolation").

**Smallest fix:** expect `selector.bytes` for this specimen. If a depth-isolated deep specimen is wanted, use one that stays ≤4096 bytes (e.g. 2040 pairs → 4093 bytes, depth/nodes 2042). Alternatively declare the deep specimen parser-only and drop its submission claim, keeping `D31` (75 bytes, depth 33, nodes 33) as the sole depth case.

## F2 — HIGH: pinned N-specimen byte lengths are wrong (836/838 → 773/775)

**Location:** plan §"Exact Selector constructions for tests", `T(k)` bullet

For `T0=@.missing` (9) and `T(k+1)=(`+Tk+`||`+Tk+`)`, the recurrence is `L(k+1)=2L(k)+3`, so `L(6)=64·9+63·3=765`. With `$[?`+g groups+T6+g groups+`]` the totals are **773** (g=2) and **775** (g=3). The plan's figures assume per-combine overhead 4 instead of 3 — a consistent **+63** (= the 63 binary operators). The superseded `@.id` figures are wrong the same way: 453/455, not 516/518.

The depth/nodes arithmetic in the same bullet is **correct** (T6 = depth 14 / nodes 254; +2 groups = 16/256; +3 = 17/257; 64 leaves × 2 nodes + 63 or + 63 group = 254).

**Impact:** the plan explicitly instructs "measure … against independent arithmetic" and "pin them rather than reusing 516/518" — so it pins the one number it got wrong. An author trusting the plan may pad the construction to reach 836, perturbing the node/depth arithmetic that the `N256`/`N257` boundary depends on.

**Smallest fix:** replace 836/838 with 773/775.

## F4 — MEDIUM: the normative amendment doesn't address the `limit`/code asymmetry with the Read query path

**Location:** `packages/server/src/read-request.ts:954-968`; plan §"Normative amendment and exact file ownership"

Existing Read behavior: `syntax`/`unsupported-feature` → **`invalid-parameter`** 400; the three limit codes → **`limit-exceeded` 413 with no `limit` field and no `pointer`** (asserted at `read-request.test.ts:268-277`; installed 413 at `apps/bdptest/src/development-discovery.test.ts:430-432`; installed 400 `invalid-parameter` at `transactional-collection-minimum-installed.test.ts:552`).

The plan's body-path mapping — `malformed-request` 400 + pointer, `limit-exceeded` 413 + `limit: selector.bytes|depth|nodes` + pointer — is well grounded (admission step 2 at `docs/specs/bdp.md:4491-4504` already specifies `malformed-request` SHOULD carry `pointer`). But the amendment as drafted ("Assign complete embedded bounded grammar to syntax step 2 and fixed structural capacity for unknown keys to step 5") reads as if both surfaces behave identically.

**Impact:** a conformance reader could require `invalid-parameter` on the body path or a dotted `selector.*` on the query path; neither matches the implementation.

**Smallest fix:** one sentence recording that the query-parameter surface keeps `invalid-parameter`/bare `limit-exceeded`, while the JSON-body member surface uses `malformed-request`/`limit-exceeded` with `pointer` and the dotted `selector.*` name.

## F6 — MEDIUM: the deep-specimen envelope is ~30% of the budget the plan claims to bound

**Location:** plan §"Risks", §"Deep safety specimens"

The safety claim itself **holds** — I verified every traversal is iterative with explicit arrays: `tokenize` (`read-selector.ts:467-535`), `parseSelector` (`:199-286`), `closeGroup` (`:327-352`), `reduceForIncoming`/`reduceAll`, `evaluate` (`:764-803`). Nothing recurses over, deep-freezes, or stringifies the AST (`makePath:295` freezes only a segment array). And the work already ahead of `assertTransactionInputDepth` today — `prepareResourceBatch`, `prepareSetShape` → `transactionInputText` (iterative, `transaction-set.ts:19-49`) → `prepareReadUpdateSingleton` — already survives a 20,000-deep `change` (proved by `transaction-submission.test.ts:821-857`). But the plan pins exactly 10,000 pairs (20,013 bytes) while asserting memory is "bounded by the existing body envelope" (65,536). The near-envelope case is ~32,760 pairs.

**Smallest fix:** either justify 10,000 as the operating point, or make one of the two specimens near-envelope and fold it into the per-case duration measurement the plan already promises.
