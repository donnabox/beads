## Findings

1. **Medium / P2 — Freeze synthesized legacy metadata before returning parsed records.** `packages/protocol/src/read-values.ts:124` and `:159` synthesize ordinary mutable `{}` objects after `snapshotProtocolRecord` has already made the input immutable. The outer freezes at `:205` and `:220` do not freeze these new child objects, and the `?? Object.freeze({})` fallback is never selected because projection already inserted metadata. As a result, direct `parseBeadRecord`, `parseLinkRecord`, History parsing and retained mutation-result parsing can return a supposedly deeply immutable snapshot whose `metadata` can be changed without its revision changing. This is newly introduced and affects the explicitly supported pre-metadata form. Collection and owned-Link paths happen to snapshot the projected child again and do not have the same escape. **Fix:** freeze the synthesized empty objects in both projection helpers, or deep-snapshot the projection before returning it; add direct Bead/Link and wrapper regression assertions for omitted metadata. **Landing:** resolve before marking the current delta ready; no semantic ruling is needed.

   Reproduction used an external copy of exactly the reviewed protocol sources, transformed with Node 24.16.0's TypeScript transform and the repository-pinned AJV dependencies. For direct Bead, Link and mutation-result parsing, `Object.isFrozen(parsed.metadata)` was false and `parsed.metadata.injected = "changed-without-revision"` succeeded while revision stayed `r1`. The collection control was frozen and rejected the assignment. Result: `native-probe/probe-result.json` beside this report. Source checkout was not modified. Two initial probe setup attempts using ambient Node 26 failed before execution because its TypeScript stripping lacks transform mode; the successful reproduction used the pinned Node version.

2. **Low / P3 — Make the advertised patch-count definition agree with the combined-update rule.** `docs/specs/bdp.md:976` now says limits bound the **combined** patch-operation count, and `packages/server/src/resource-evaluator.ts:1009` correctly sums the two arrays. However, `docs/specs/bdp.md:2352` still says `patch.operations`, `patch.pathBytes`, and `patch.pathDepth` bound “one property patch.” A request with one operation in each array and an advertised count of one is rejected by the implementation, while the discovery-limit definition still suggests each patch separately fits. **Fix:** state that `patch.operations` counts both arrays together for a Resource update, while path-byte/depth limits apply to each path; preserve the existing set-operation interpretation. **Landing:** documentation correction, not a runtime blocker.

No Critical/High finding was established. No other concrete blocker was found in this bounded delta. The supported legacy projection is accepted scope; this review does not ask to remove pre-metadata clauses or to complete the write profiles before landing development code.
