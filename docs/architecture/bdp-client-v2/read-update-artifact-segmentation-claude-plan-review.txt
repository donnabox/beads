### 1. [HIGH — A] The necessity premise is a 262-node margin against an input that is not in this checkout, and no done-when predicate re-measures it

**Location:** plan lines 5, 16, 33, 106–108.

**Evidence:** C's scenario measures **3,154 nodes / 57,185 bytes**. Frozen manifest is 96,446 nodes. `96,446 + 3,154 = 99,600` — which is *exactly* the retained draft ledger's `"manifestNodes": 99600, "manifestNodeHeadroom": 400`. Projected bytes 3,658,237 against `CUMULATIVE_MANIFEST_MAX_BYTES` 4,194,304 leaves 536,067 bytes (12.8%). **So at `579019b`, C fits in one ordinary manifest with 400 nodes and 536 KB to spare.** The "cannot fit" conclusion holds only after root's comparator: the plan's own arithmetic is 97,108 + 3,154 = 100,262, i.e. **262 nodes (0.26%) over cap**. And `git cat-file -t 6f3e3bd` → `fatal: Not a valid object name` — the 662-node figure cannot be verified here.

**Impact:** The whole layout change is justified by 262 nodes sourced from an unverifiable tree. If root's merged base lands even ~300 nodes lighter, two shards, a new index, a new validator and a new progress record are all unnecessary. The plan dismisses "More constant deduplication/cap increase" (line 16) as "Not the needed mechanism" without quantifying it against 262 nodes — yet the draft's own approved fixturePointer compression already removed 801 nodes from three rows (12,039 → 11,238), 202 of them from C alone (3,356 → 3,154).

**Fix (smallest):** Add a **gating** step as done-when predicate 0, before any new file exists: compute the exact merged 579+6f3 base node count and base+C total with the same traversal the parser uses, and proceed with segmentation only if base+C > 100,000. Record both integers and the measured margin in the implementation note. One command, no new semantics. If the margin is under ~500 nodes, say so explicitly in the recommendation so root can choose compression instead.

### 2. [HIGH — P + A] `scenarioSelection` has no prerequisite-closure preflight; plan line 67's "validates prerequisites normally" is false

**Location:** `runner.ts:2565–2574`, `2663–2682`, `2792–2817`, `436–440/451`; plan lines 67, 102.

**Evidence:** `validateRunOptions` checks `scenarioSelection` only for mutual exclusion with `scenarioFilter`, non-emptiness, and no repeats (2570–2573). The closure check — "selects dependent scenario X but excludes prerequisite Y" — is inside `if (options.scenarioFilter !== undefined)` at 2663 and has **no `scenarioSelection` counterpart**. A selection that omits a prerequisite therefore reaches `prerequisiteResultBeforeRun`, which returns `state:"harness-error", category:"not-run", prerequisiteFailure.reason:"prerequisite was not selected or did not run", phase:"initial"` (2800–2817). `mustStopMatrixAfter` requires `phase === "recheck"` to stop (437–439) and returns `false` for `category:"not-run"` (451) — **the matrix continues and later rows still execute.**

**Impact:** The plan's design runs every shard through `scenarioSelection` (line 67) and asserts the runner validates prerequisites. It does not. If the new set validator's cross-shard check is absent, mis-scoped, or bypassed (e.g. a new app control that passes IDs directly), a dependent row is silently recorded as `not-run` rather than rejected, and the run still reports `claimEligible:false` with a plausible-looking scenario list. Negative control #3's "Cross-shard prerequisite fails preflight" has no runner to lean on.

**Fix (smallest):** The asymmetry is an existing product gap and `runner.ts` is correctly off-limits, so (a) state in the plan that cross-shard and intra-shard prerequisite closure is enforced **solely** by the new set validator before any run is launched; and (b) add one executable control that pins the runner's real lenient behaviour — build a two-row test manifest where row B depends on row A, run with `scenarioSelection:["B"]`, and assert the result is a single `harness-error`/`not-run` row with `prerequisiteFailure.reason === "prerequisite was not selected or did not run"`, **not** a thrown `ConformanceRunnerError`. That pins the thing the validator must compensate for and will fail loudly if the runner is ever tightened.

### 3. [HIGH — L] Per-shard `scenarioSelection` deletes the only executable witness that ~80 obligations are unplanned

**Location:** `apps/bdptest/src/read-update-matrix.test.ts:828–831`; `runner.ts:347–363`, `375–378`, `2757–2767`; plan lines 67, 79, 102.

**Evidence:** Today no `scenarioSelection` is passed in the positive aggregate, so `selected` = all applicable catalog rows (`runner.ts:341,347`) and every canonical row without a manifest plan becomes `missingPlanResult` → `category:"not-implemented"` (2757–2767). The positive test then asserts, for **every** row: `state: !report.plannedIds.includes(row.id) ? "harness-error" : "pass"`. With 49 planned of 129 required, that loop is the executable proof that ~80 obligations are genuinely unplanned. Pass exact owned IDs per shard (plan line 67) and `result.scenarios` contains only owned rows — every row is in `plannedIds`, so the `harness-error` branch becomes **unreachable** and the assertion degenerates to "everything passed".

**Impact:** Completeness accounting moves wholesale out of the unchanged runner into the brand-new, never-executed private progress record. Plan line 102 ("Missing inherited obligation remains visible even if every authored shard passes") loses its anchor exactly where the plan's stated main risk — "incomplete union accounting" — lives.

**Fix (smallest, and smaller than the plan's own proposal):** Run the **baseline shard unselected** — byte-for-byte today's call — and pass `scenarioSelection` **only** to the continuation shard. This gets the plan's stated goal (no duplicate missing-plan rows: only shard 1 enumerates absences) while leaving `828–831` untouched. The aggregate record then asserts one extra, strictly stronger invariant: for each required ID, exactly one shard reports a non-`not-implemented` row, and every **non-owning** shard that enumerated it reports `category:"not-implemented"`. That proves shard 1 genuinely lacks C rather than inferring it from an index file.

### 4. [MEDIUM — L] Shared-fixture oracle names are strictly sequential, so a same-name/different-value comparator append silently rebinds C's oracles

**Location:** `packages/conformance/fixtures/read-update-reference-v1.json` (`oracles.referenceEvidence`); `artifact-bundle.ts:255–353`; plan lines 37, 57.

**Evidence:** Current `oracles.referenceEvidence` has exactly 40 keys: `value-0…value-23` and `identities-0…identities-15`. The draft appends exactly `value-24…value-28` and `identities-16…identities-19` (9 keys), and C's 14 pointers are `value-0,1,2,3,8` (pre-existing, shared with A/B) plus those 9 new names. Measured against the draft: zero binding-value conflicts, zero oracle-value conflicts — the draft fixture *is* the exact union today (222→232 bindings, 40→49 oracles). But the naming scheme is positional, so **any** independently authored pass — including root's comparator — takes the same next names. `validateFixtureOraclePointers` only checks that a pointer *resolves* and matches the assertion's type shape (255–353); it has no provenance or uniqueness notion. A comparator `value-24` with different content yields a resolvable pointer bound to the wrong constant, and the legitimately-new fixture digest provides no signal.

**Impact:** C could assert against a comparator-authored constant. Depending on type this either fails as a confusing C regression or, for same-shaped values, passes against the wrong oracle — precisely the "no target-produced value becomes an authored oracle" boundary the plan claims to hold. Plan line 37's "identity-preserving new names resolve any collision" presumes the collision is *visible*; a same-name append is not.

**Fix (smallest):** One equality control over the two fixture sources, no framework: assert (a) every pre-merge `oracles.referenceEvidence` key retains its pre-merge value byte-for-byte, (b) the merged fixture's added key set equals exactly the draft's 9 names with the draft's values, and (c) C's 14 pointers resolve, in the merged fixture, to the same values they resolve to in the draft fixture. Three `expect`s against two already-read JSON files.

### 5. [MEDIUM — L] The exact route table is not actually derived per shard; nine `operations/*` POSTs are unconditional

**Location:** `read-update-matrix.test.ts:220–234` (hard-coded list), `188–213` (derived routes); plan line 73.

**Evidence:** `readRoutes`/`clientReadRoutes` are derived from the bundle's actions, but the nine `operations/{sequence,create-bead,update-bead,delete-bead,create-link,update-link,delete-link,put-alias,delete-alias}` POST routes are appended unconditionally. C's actual operation surface is seven of those nine — it never calls `delete-bead` or `delete-link` (C's 46 http actions resolve to 12 GET routes; its 13 client `targetBinding`s cover the other seven operations).

**Impact:** The continuation shard's exact client allowlist is wider than its actions, contradicting plan line 73 ("derived per shard from that shard's actual actions and necessary directory operations") and weakening for operation routes exactly the tightness property that `read-update-matrix.test.ts:1225` ("does not admit an unused fixture binding as a fixed client GET route") protects for fixture bindings. It also makes the two shards' `exactConfigurationDigest` values less distinguishable than the plan assumes.

**Fix (smallest):** Derive the operations POST list from the shard's own client-action `targetBinding`/`operation` values (union with any http POST targets) instead of the fixed array, and add one control asserting each shard's route table contains no entry unreferenced by that shard's actions. If root prefers to keep the fixed list for the baseline, scope the derivation to the continuation shard only and say so in the plan.

### 6. [MEDIUM — A] Plan line 65's "preserve existing … assertions" is unachievable: the pinned `exactConfigurationDigest` literal must change, twice

**Location:** `read-update-matrix.test.ts:917–919` and `1234–1236` (two occurrences of `3224c31c83988dc0606cb76ee1f4ba8e6394159bdf7daaccc301461316cc2477`); `runner.ts:1383–1401`; plan lines 65, 73, 106.

**Evidence:** `exactConfigurationDigest` hashes `{scope, profile, routes, maximumRequestHeaderBytes, maximumRequestBodyBytes}` — it is **invariant to `scenarioSelection`** (proved by line 1235's single-scenario run pinning the identical literal as the full run at 918) but **varies with the manifest**, because `routes` is built from `bundle.manifest.scenarios`. The baseline shard adopts the merged 579+6f3 manifest, whose added actions change `routes`.

**Impact:** The literal is stale for the baseline shard and absent for the continuation shard. It fails loudly rather than silently, so this is a scoping defect, not a correctness hole — but plan line 65 instructs the implementer to preserve it, which will read as a conflict mid-implementation.

**Fix (smallest):** State explicitly that both occurrences are re-pinned to the merged baseline's value and a second literal is introduced for the continuation shard, keyed by owning shard. Add one assertion that the two shard digests **differ** and that each report's `declarations.exactConfigurationDigest` equals its own shard's pin — otherwise a shard run against the wrong manifest's route table is undetectable.

### 7. [MEDIUM — L] The coverage↔manifest check is single-bundle, and `(planned.actions ?? [])` lets an empty assertion list satisfy "full ordered binding"

**Location:** `cumulative-artifact.test.ts:176–190` (plan cites `109–204`; the `it` block is actually `100–191`, with the bidirectional check at `178`); plan lines 26, 55, 89.

**Evidence:** Line 178 asserts `row.status === (planned ? "bounded-observation" : "omitted")` where `planned` is looked up in **one** bundle's manifest. C's coverage row is `bounded-observation` and absent from the baseline bundle ⇒ this test fails under segmentation; the plan identifies the file but not this specific invariant. Separately, lines 185–189 bind `row.bindings[0].assertions` to `(planned.actions ?? []).flatMap(...)` — a scenario authored with legacy `requests` instead of `actions` yields `[]`, and `expect([]).toEqual([])` passes. C uses `actions` (73 of them), so this is latent today, but the plan's line 55 requirement ("its full ordered action/assertion binding") would be satisfiable by an empty list.

**Impact:** The principal static coverage authority either breaks or, once rewritten over the union, can accept a vacuous binding for a row the plan counts as observed.

**Fix (smallest):** Rewrite `planned` as a lookup over the union of shard manifests (ownership derived from manifests, as plan line 38 requires), and add `expect(row.bindings[0].assertions.length).toBeGreaterThan(0)` for every `bounded-observation` row. Keep the reviewed whole-ID gate at `147–174` and the `rows ≡ selected.required` identity at `175` verbatim.

### 9. [LOW — A] Aggregate parsed-source accounting counts only manifests

**Location:** plan lines 33, 42; `artifact-bundle.ts:116`, `159–177`.

**Evidence:** Each shard's bundle re-parses the canonical selection catalog (`Buffer.from(JSON.stringify(selection.catalog))`, line 116) and the shared fixture, each under its own 1 MiB / 100,000-node budget. Catalog sources measure ~123,854 bytes / ~1,964 nodes; the merged fixture is 28,753 bytes / 742 nodes. Plan line 33's "at most 8 MiB / 200,000 parsed manifest nodes across sources" is a cap, not an estimate: the real two-shard total is ~3.66 MB / ~99,604 manifest nodes plus ~2×2,706 nodes of re-parsed catalog + fixture.

**Impact:** Minor, but line 42's "actual summed source bytes/nodes" will understate resident parse cost if it covers manifests only — and that figure is the one feeding the memory claim the plan is careful not to overstate.

**Fix:** Have line 42's recorded sum enumerate catalog × shards, fixture × shards, coverage, index and both manifests separately, and state the realistic ~3.7 MB / ~105 K-node total alongside the 8 MiB / 200 K bound.

## Overall

The layout recommendation is structurally sound and the seam reading is unusually accurate — every citation I checked holds, including the subtle ones (port/directory excluded from installed identity; served-configuration shard-invariance vs. route-digest shard-variance; the seven-edge prerequisite cluster wholly inside shard 1; C carrying zero prerequisites; the fixture union being collision-free today). Nothing in the plan touches historical Read, `cohort-artifact.ts`, public exports or normative schemas.

Two things should change before approval. **Finding 1** is the decision-level one: at the frozen SHA the problem the plan solves does not yet exist, and it exists afterwards only by 262 nodes measured against a tree absent from this checkout — that belongs in the recommendation, with a measurement gate, not in a provenance paragraph. **Finding 3** is the implementation-level one: the plan's uniform `scenarioSelection` is a larger change than necessary and it silently retires the only executable proof of unplanned obligations; running the baseline shard unselected is strictly smaller and strictly stronger. Findings 2, 4, 5 and 7 are each one bounded control or one lookup change, and findings 6, 8, 9 are scoping/accounting corrections to the plan text.
