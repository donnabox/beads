## Required

**1. The 413 `limit-exceeded` shares one `problem()` sink with five excluded dispositions.**
*Location:* `transaction-http.ts:359–362`; `transaction-submission.ts:69, 84, 88, 91, 93, 122–137`. Plan line 27.
*Impact:* The seam has only two exits for every `refused` result: the 409 special case at 350–358 and the single fallback `problem({...readProblem(result.code), ...})` at 359–362. `request-too-large` (413, returned at `transaction-submission.ts:69` before the store is ever entered), `malformed-request` (400), `unauthenticated` (401), `forbidden` (403) and `temporarily-unavailable` (503) all leave through that same call. Applying `context(...)` there, or making context a required member of the shared `refused` variant, either attaches context to the dispositions the plan explicitly defers (auth nondisclosure, comparison 503) or makes `request-too-large` unsatisfiable. Note both 413s carry status 413, so status is not a usable discriminator.
*Concrete fix:* Require the fallback to branch on `result.code === "limit-exceeded"` (equivalently `result.limit === "transaction.operations"`), never on status. Keep the context member optional on the shared `refused` variant and enforce presence with a code-specific throw mirroring the existing `existing receipt lost same-entry context` guard at `transaction-submission.ts:139–142`, rather than by a required type member.

**2. The focused-test gate under-covers the unobserved-shape regression surface.**
*Location:* Plan line 81 vs. `store.admit` assertions.
*Impact:* Exact `toEqual({kind:"conflict"|"operation-limit"|"not-acceptable"})` assertions on the unobserved `store.admit` path: `transaction-store.test.ts` 18, `transaction-submission.test.ts` 8, `transaction-dependencies.test.ts` 3, `transaction-sequence-alias.test.ts` 3, `transaction-set.test.ts` 2, `transaction-owned.test.ts` 1. The plan correctly requires preserving unobserved shapes (lines 25, 26, 47), but the gate names only "focused owner/submission/HTTP tests" — missing 9 assertions across 4 files that are the actual tripwire for a context leak into `store.admit`.
*Concrete fix:* Name `transaction-dependencies.test.ts`, `transaction-sequence-alias.test.ts`, `transaction-set.test.ts` and `transaction-owned.test.ts` in the gate, or require the whole `packages/server` suite. Add a §Sensitivity control: removing the `observed` gate on the capture must fail those named exact-equality assertions.

**3. The existing-receipt 406 branch has no `observed` discriminator today.**
*Location:* `transaction-store.ts:1391–1393`. Plan line 25.
*Impact:* `if (result.kind === "existing") { if (!receiving.acceptsJson) return { kind: "not-acceptable" }; if (observed) return {...observeReceipt(...)} }` — the 406 early return precedes the `observed` check and is reached identically by unobserved `admit` callers. An implementer following line 25's "Handle the existing-receipt406 branch too" literally adds context unconditionally and breaks `transaction-submission.test.ts:162` and the files in finding 2.
*Concrete fix:* State that both 406 exits — `store.ts:1392` and the fresh `admitKey` result at `:1084` flowing through `:1395` — must be gated on `admit`'s `observed` parameter, and that this gate is precisely why the unobserved shapes survive.

**4. The three-file ownership boundary holds only if the new context members are optional.**
*Location:* `transaction-store.ts:121–138`; `transaction-comparison.ts:10–12, 16–23`; `transaction-service.ts:47–49`. Plan line 29.
*Impact:* `TransactionAdmission` already carries `context?: TransactionReadContext` on the `existing` variant only (`store.ts:126`). Both `DirectComparison` (`comparison.ts:10–12`) and the structural `admit` parameter type (`comparison.ts:17–22`) reference `TransactionReceivingAdmission`, and `TransactionServiceSubmissionResult` is derived from `TransactionSubmissionResult`. Adding *optional* members to the conflict/operation-limit/not-acceptable variants leaves comparison and service untouched, as the plan claims. Introducing a separate observed-admission type instead forces edits to `comparison.ts:10–23`, which the plan's own rule (line 29) would then treat as a stop-and-report ownership expansion.
*Concrete fix:* Make the optional-member constraint normative in points 4–5 and name those two type sites, so the implementer does not reach for a new observed admission type and then re-open the ownership question.

**5. The `isTransaction` control is sound only at the owner level, and will misfire if lifted.**
*Location:* `transaction-store.ts:407–411, 1713`; `transaction-comparison.ts:45`; `transaction-store.test.ts:3036–3044`. Plan lines 47, 50.
*Impact:* `metadata()` issues the same SQL for position and epoch, and the existing spy keys on that string. Inside `admitObserved` only position is read (epoch and view are open-time constants used at `store.ts:588–589`), so the control is valid there. But `comparisonEpoch` (`store.ts:1713`) reads `metadata("epoch")` inside `enter` and *outside* `atomic`, and the comparison loop calls it before every attempt. Reusing the same spy in the submission- or HTTP-level tests the plan proposes would fail on `isTransaction === false` for the epoch read — a false negative, not a defect.
*Concrete fix:* Scope the `isTransaction` assertion to the owner-level `admitObserved` tests explicitly. If a submission-level variant is wanted, filter the spy by bound parameter (`name === "position"`) rather than by SQL text.
