# Supplement review — two-file evidence repair on frozen `dirty67a2842`

Scope: only the `correction.patch` delta to `transaction-authorization.test.ts` and `transaction-runtime.test.ts`, read against the supplied pinned sources. I executed nothing; all pass/fail attributions below are structural reasoning over the delivered bytes, not observed runs. I do not re-open the deferred items (generic timeout/T4 sync surface, sixth tamper copy, arbitrary-shape corrupt storage) and do not propose a product-policy change.

## Findings

**1. Medium — `transaction-runtime.test.ts` T1, new HEAD block: the `cache-control` / validator assertions (and 200-on-HEAD for the receipt target) have no production evidence anywhere in this packet.**
`expect(response.headers["cache-control"]).toBe("private, no-store")` is applied to *both* `receiptResponse` (the pre-existing GET at request 16) and `receiptHead`. Neither supplied response-shaping function sets that header: `read-http.ts:10–47` touches only `vary`, `content-type`, `etag` (406 only) and `content-length`; `transaction-runtime.ts:88–95` sets only `x-bdp-development` and `content-length`. So the header must come from an unshown route builder, and the historical passes give zero evidence about it — request 16 previously asserted nothing on `cache-control`. The same class of exposure applies to `expect(receiptHead.status).toBe(200)`: nothing supplied shows the receipt target routes HEAD to 200 rather than 405. This is the only part of the delta that can fail against byte-identical production, which would convert a test-only repair into a forced production change root explicitly declined. This is a bounded-context gap, not a claim that the production code is wrong. Fix (cheapest, keeps the leak oracle): assert HEAD/GET *agreement* rather than literals — `expect(receiptHead.headers["cache-control"]).toBe(receiptResponse.headers["cache-control"])` — and retain the absolute `"private, no-store"` form only if the setting line is pinned into the packet. Keep `etag`/`last-modified` `toBeUndefined()`: those fail only in the leak direction and are the point of F8.

**2. Low-medium — `transaction-authorization.test.ts:414–440`: the new AJV checks validate *in-process* objects against a wire schema whose `receiptCore` is `additionalProperties: false`.**
`observed.receipt` and `afterPage.page` are the frozen objects returned by `observeReceipt` / `readReceiptPage`, not a parsed HTTP body. Any field the owner retains in-process but the route drops before `stringifyJsonValue` would now fail `additionalProperties: false`, even though the delta changes no production byte. Relatedly, a key present with value `undefined` passes `toEqual` but is *visible* to AJV (and fatal where a branch sets `results: false` / `allocated: false`). I traced this as safe for the two shapes actually validated — `projectTransactionReceipt` uses real `delete`, `{...receipt}` copies only existing keys, and the mixed root keeps exactly `id/status/detail/idempotencyKey/scopeEpoch/authorizationView/transaction/requiredPosition/effectPosition/results/next/expiresAt`, all in `receiptCore` — but that conclusion rests on files not supplied in full. Fix if you want it independent of unshown route behavior: validate `JSON.parse(JSON.stringify(observed.receipt))`. Cost 0.

**3. Low-medium — T10/T11 (`:502–522`, `:616`): `toThrow(expect.objectContaining({ code }))` *replaces* the message oracle instead of adding to it.**
Vitest's `toThrow` does accept an asymmetric matcher (it asserts `thrown && matcher.asymmetricMatch(thrown)`), and `objectContaining`'s property lookup walks the prototype chain, so `code` on a `TransactionAuthorizationFailure` matches — the mechanism is correct. But the three rewritten assertions no longer pin the message *or* the class: any thrown value carrying `code: "temporarily-unavailable"` / `"forbidden"` now satisfies them, including a non-`Error` object or an unrelated carrier (Node SQLite errors carry `code`). Finding 5 asked to narrow the oracle, not to trade one axis for another. Fix (0 cost, no new import): `expect.objectContaining({ name: "TransactionAuthorizationFailure", code: "forbidden", message: expect.stringContaining("authorization admission refused") })`; `name` resolves off the prototype and nested matchers are supported.

**4. Low — residual ambiguity in `temporarily-unavailable`.** Per `transaction-store.ts:1892–1926` that code is emitted by at least three distinct guards: `activeSequences.size`, an owned-receipt row, and `pauseMutationAdmission` double-pause (plus `admit` under pause/pending replacement). The F5 concern that mattered — a leaked administrative pause being indistinguishable from a published-policy refusal — is genuinely resolved, because the post-publication refusal is now pinned to `forbidden`. What remains unresolved is *which* drain guard fired. For the first assertion this is harmless (no pause exists yet at that point in T10, so only the sequence/owned-receipt guard can fire), so I would not expand it; noted so root does not read this as fully disambiguated.

**5. Low — T1 stream check (`:661`) excludes only `id:`-prefixed frames.** `frames` is `body.split("\n\n").slice(0,-1)`, and the `id:`-first convention is confirmed by T2's working parse, so the assertion is well-formed and the preamble/keepalive case is correctly tolerated. But a terminating or fenced frame with no `id:` line would pass while still carrying the hidden transaction. The T11 half of this same patch establishes the right idiom; mirroring it here costs 0 HTTP and no new helper: after `await authorizationBound(stream.closed, …)`, add `expect(stream.body).not.toContain(authorizationText(first.receipt.transaction))`. Placement of the existing assertion (post-close) is correct — `body` is complete there.

**6. Low — T11 exclusion assertions (`:635–642`) are encoding-fragile, and the checkpoint half is near-vacuous.** `transactionCheckpoint(scope, context, position)` (`transaction-changefeed.ts:169`) derives the checkpoint from scope/epoch/view/position only, so `not.toContain(receipt.transaction)` on it cannot fail by construction; the `JSON.stringify(page.page.groups)` check is the real net. That net is substring-only: it passes if an identifier leaks digested, base64'd, or through a JSON-escaped character. `transaction` is a `wireToken`, so escaping is not a practical hazard, and the surrounding `toEqual` over the whole `groups` array already forbids extra fields — the one field it could not police was the self-referenced `checkpoint`, which this now covers. Keep as written; recorded as a bounded oracle, not a defect.

**7. Low — `AuthorizationResponse.bodyBytes` loses its "actual delivered bytes" meaning at the reconnect call site (`:696–704`).** In `request` the field is transport-observed (the `res.on("data")` accumulator). The reconnect literal synthesizes it with `Buffer.byteLength(reconnect.body)` — a decoded-body recomputation that `authorizationChecked` never reads. Nothing is wrong today, but the field is now sometimes evidence and sometimes derived, and a later reader could compare the derived value against a `content-length` header believing it is byte evidence. Fix: declare `bodyBytes?: number` and omit it at that site, or compare it to `reconnect.headers["content-length"]` only when present.

**8. Nits.** (a) T6's `f.reopen()` is correctly placed *after* the `finally { lease.release() }` and outside the try, so a failed in-try assertion skips it — intended. The fixture's `fault` survives the reopen via `{...options, create: false}`, which is benign because only `replaceAuthorizationPolicy` emits `before-policy-commit`. (b) The `cleanup` closure reads the mutable `owner` binding, so it closes the *post*-reopen handle and the pre-reopen handle is closed by `reopen()` — no leaked handle, bounded cleanup preserved. (c) The new `Ajv2020` import sits after `@bdp/protocol` here but before it in the sibling runtime file; if an import-order lint rule is active this trips packaging, not the test run.

A length derived from the retained unprojected receipt fails at the second link. This is delivered-byte evidence, not reserialization.

The schema path `../../../schemas/bdp-v0.schema.json` resolves identically to the proven runtime-test copy (same directory).
- **No further validator is needed.** The collapsed all-withheld shape (`detail: "withheld"`, results/next/allocated/expiresAt deleted — oneOf branch 5) is already AJV-validated on the wire at T1 request 16, and the delta adds the two previously unvalidated shapes (mixed root, all-withheld page). Coverage across the suite is now complete; the drain test's `projected.receipt` and the retention-expired receipt need no duplicate check.
