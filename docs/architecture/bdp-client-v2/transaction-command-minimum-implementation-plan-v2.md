## Exact contract amendment

Place the complete exact-field rule where its vocabulary is defined, in `docs/specs/bdp.md`, “Transactional HTTP consistency” (current lines 5766–5789). Its explicit applicability is mutation POSTs, including Read+Update and Transactional; placement must not narrow the operator ruling to Transactional:

> On mutation POSTs to operation command targets, authorities MUST ignore the BDP-Minimum-Scope-Position, BDP-Scope-Epoch and BDP-Authorization-View request fields. Their presence, absence, completeness and field values do not impose a minimum-position barrier or affect command identity. Ordinary HTTP field syntax and transport/header/body bounds still apply, as do authorization, idempotency, carrier validation and expectedRevision. This rule does not change minimum controls on reads, including subsequent Mutation Receipt GET or HEAD requests.

In “Mutation command preconditions” (3565–3578), add a short explicit cross-reference: “The [mutation-POST exception for read consistency request fields](#transactional-http-consistency) applies to mutation POSTs under this profile as well; those copied fields add no command precondition.” This does not expose Transactional response fields, receipts or Scope history in Read+Update, nor change its existing runtime behavior. The full rule stays at the field definitions; the cross-reference makes the generic command applicability explicit.

Within “Transactional HTTP consistency,” scope the request-side minimum-position paragraph to reads using adjacent wording. Preserve the exact sentence `It never reports success with an older position.` byte-for-byte in that anchored section: `packages/conformance/catalog/transactional-v1.json:1179–1181` selects precisely that sentence. The existing exact catalog citation test below is a required gate. Preserve response-context requirements, receipt current-context rules (5233–5244), conditional-read ordering (5800 onward), and lower-profile distinctions (3557–3563). No schema or catalog source change is needed: there is no new wire field, Problem, receipt shape or capacity vocabulary.

“Ignore” includes a lone field, partial tuples, empty field values, read-token-invalid strings such as `not a position!`, accepted comma-joined strings, unknown opaque positions, and complete foreign or far-future tuples. These are values of otherwise receivable HTTP fields. It does not authorize CR/LF injection, illegal HTTP framing, unlimited fields, oversized headers/body/target, an unsupported Content-Type, or a method on an unrelated route. Do not parse a copied tuple merely to decide whether to ignore it. The command law does not resolve malformed/partial read tuples or retained-page semantics.
