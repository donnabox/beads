## Verdict on independence

# Authoring blockers

### A1 · HIGH · Conditional headers on the creation target burn permanent issuance capacity
**Location:** plan:50, 52, 72; done-when #5 (plan:99), #8 (plan:102). Source: `transaction-http.ts:448–450`, `read-http.ts:26–38, 50–56, 63`.

`applyReadHttpSemantics` runs on every transactional GET/HEAD and evaluates conditionals *after* the route produced its 200. So a creation GET carrying `If-None-Match: *` returns **304**, and one carrying a specific `If-Match` returns **412** — in both cases after the capture has committed and the identity has been issued. Combine with plan:50 (permanent 65,536-identity cap, no reprovision, no tombstone deletion) and plan:52 (a committed-but-undisclosed capture counts as issued): an authorized client can permanently brick snapshot creation for the installation with 65,536 conditional creation GETs, each of which looks to the client like an ordinary successful cache revalidation. The plan treats undisclosed captures as a fault-path curiosity; this is a routine, client-reachable path.

**Fix:** decide the creation-target conditional policy before step 2. Either suppress conditional evaluation on the creation target — it has no prior representation to revalidate, so a 304/412 there asserts something false — or commit the capture only after the conditional decision. Add a done-when row: conditional headers on the creation target neither issue an identity nor consume capacity. Do not leave this to the shared wrapper.

### A2 · HIGH · Supplied epoch/view is swallowed by the minimum gate, so done-when #6's foreign-view row is unreachable
**Location:** plan:72, 74, 80; done-when #6 (plan:100) vs #9 (plan:103). Source: `transaction-http.ts:102–106, 387`; `transaction-consistency.ts:20–44, 45–55, 69–72`.

`hasMinimumControls` fires on **any** of `bdp-minimum-scope-position`, `bdp-scope-epoch`, `bdp-authorization-view`. `snapshotTransactionMinimum` requires all three present and valid, so a partial tuple throws → `undefined` → `developmentGap("minimum-position")`. Meanwhile `foreign-view` and `cursor-expired` are produced *only* by `checkTransactionMinimum` (`:71`, `:70`), which needs a complete tuple. On a retained snapshot read that leaves no reachable input: epoch/view alone → bodyless 500; epoch/view plus a minimum → the input plan:80 declares unsupported → also bodyless 500. Both collapse to the same undifferentiated 500. Done-when #6's requirement that "foreign supplied epoch/view token" take a *distinct path* cannot be met, and plan:74's claim that current fixtures can establish foreign supplied-token refusal is not true for snapshot targets.

**Fix:** state whether a supplied epoch/view *without* a minimum position is inside the private snapshot contract. If yes, the snapshot route needs its own epoch/view gate that does not route through `hasMinimumControls`/`snapshotTransactionMinimum` — that gate is Q1-independent and authorable now. If no, delete that row from done-when #6 and say the case is a development gap until Q1 rules. Do not leave #6 and #9 both asserted.

### A3 · MEDIUM · Expiry reclamation vs. capacity measurement is unspecified; no clock named
**Location:** plan:48, 50, 58, 60; done-when #8. Source: `transaction-store.ts:241` (`clock = options.clock ?? Date.now`), `:249` (`instant()`), `:448` (`sweep`), `:457` (`expireRow`), `:463` (`maintain`), `:242` (interval default 1000 ms).

The 503 decision depends on live-handle count and aggregate captured bytes. The plan never says whether expired-but-unswept captures still occupy that capacity, nor which clock evaluates snapshot expiry — it says only "fixed creation/expiry instants" and "five minutes." The store already solves exactly this for receipts by expiring in place inside the entry with `instant()`; otherwise maintenance runs on a 1,000 ms timer. As written, done-when #8's "eight small handles" and "two near 32-MiB captures" boundaries depend on timer interleaving, and a 503 could be returned when every handle is already expired.

**Fix:** state that snapshot expiry uses the store's injected `clock`/`instant()`; that capacity prechecks expire-in-place inside the same owner entry *before* measuring; that the maintenance sweep is a space reclaimer, not the capacity oracle; and that tests drive expiry through the injected clock, never wall time.

### A4 · MEDIUM · "The installed Resource page count ceiling" resolves to nothing
**Location:** plan:64, 68.

At `d907a1e` the only candidates are `development-authority.ts:50` — `page: {defaultItems: 20, maximumItems: 100}`, the *Read-profile* development authority's advertised limits, a different authority from the transactional owner — and `receiptMaximumItems`/`TRANSACTION_MAXIMUM_OPERATIONS` = 32 (`transaction-batch.ts:61`, `transaction-store.ts:231`), a receipt bound derived from the operation budget. `TRANSACTION_RUNTIME_LIMITS` has no page-item field; `CONTRACT_ARTIFACT_CEILINGS` (`installed-contract-artifact.ts:19–34`) is unrelated. Since page ranges are immutable, persisted in `configuration`, and any configuration change is a hard reopen refusal, this value cannot be corrected later without abandoning every prior store — which plan:46 already forbids migrating.

**Fix:** name the constant and its file, or declare an explicit new private `snapshotPageItems` capacity alongside the 4 MiB page byte bound. Do not inherit the Read authority's advertised 100 — it belongs to a profile whose discovery the snapshot route cannot advertise.

## Verified correct — do not re-litigate

Capacity arithmetic is internally consistent with R correct: 128 × 262,144 = exactly 32 MiB; 4,096 rows needs ≤ 8,192 bytes/record, trivially reachable with small records, so all four done-when #8 conditions are distinguishable; "byte ceiling binds before row count for large records" follows. The page-fit proof holds — `scopeSourceBytes` is 65,536 (`transaction-batch.ts:65`), 6·(65,536+1,024)+1,024 = 400,384, plus R = 662,528 < 4 MiB, and 6× per input byte is a genuinely safe JSON-escape bound. The UTF-8-bytes ≥ UTF-16-code-units direction is correct, so the 10 MiB manifest bound against `MAX_STRING_LENGTH` is sound. The SQLite collation caveat is right: UTF-8 binary order and UTF-16 code-unit order genuinely diverge at supplementary characters (4-byte UTF-8 sorts above 3-byte; surrogates sort below U+E000), and `compareCanonicalIds` (`packages/protocol/src/index.ts:252`) is UTF-16 code-unit order. Omitting `limit` is schema-valid — it is forbidden unless code is `limit-exceeded` and never required (`:4213`, `:4300–4315`). `limit-exceeded` = 413/`size`/`never` and `temporarily-unavailable` = 503/`unavailable`/`after-delay` (`bdp.md:1905–1907`), both in `transactionalProblemCode` with 413/503 admitted. `configuration` is exact-string compared, so capacity changes do yield `transaction installation mismatch`, with `identityPolicy` checked first (`:483`) — the plan's separation is exactly right. Hot-journal recovery (`:468–471`) precedes comparison (`:480`) precedes maintenance (`:501–505`). `resources` has no `(kind,id)` index; `receipt_page_ranges` is the existing precedent for recorded ranges. The clock seam exists at `:241`. All six catalog rows exist. No snapshot route or table exists — "genuinely missing" holds.

One minor correction to a plan phrase, no action needed: plan:60 calls `transactionalProblem` → `readUpdateProblem` → Read problem a "schema chain." They are three parallel `$defs` with superset enums, not `$ref`-linked. The substance — that these bodies validate — is right.
