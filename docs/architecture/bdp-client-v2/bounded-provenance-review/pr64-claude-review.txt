# Blockers

**1. HIGH — Metadata-plane validation diagnostics are indistinguishable from properties diagnostics; the spec's `validation-failed` clause was not amended.**

`packages/server/src/resource-evaluator.ts:506` · `:456,469,474,488,494` · `packages/server/src/member-identity.ts:451` · `docs/specs/bdp.md:2553,2568,2570`

Defect: three separate paths emit metadata faults in properties clothing.
- `:506` emits the literal message `"resulting properties must be an object"` when it is the **metadata** patch that yielded a non-object, with `instanceLocation: ""`.
- `:456`–`:494` emit `instanceLocation = change.path` — the raw metadata-relative pointer — with no plane marker, identical to a properties failure at the same path.
- `member-identity.ts:451` slices the plane prefix off create-time numeric diagnostics (`occurrence.pointer.slice(object.length + 1)`), so `/metadata/nested/bad` is reported as `/nested/bad`. `member-identity.test.ts` codifies this: the wire `diagnostics` entry is `{instanceLocation: "/nested/bad"}` and the only discriminator (`/metadata/nested/bad`) lives in the internal `offending.pointer`.
- Meanwhile `docs/specs/bdp.md:2568,2570` still normatively define `instanceLocation` as "a JSON Pointer within `properties`", and `:2553` still enumerates the causes as "the resulting **`properties`** … is not a JSON object" — no mention of a non-object metadata result at all.

Impact: a client implementing the spec correctly will read a metadata fault's pointer as a properties pointer. For an atomic two-document update with the same path invalid in both planes, the authority emits two diagnostics with identical `instanceLocation` and no way to tell them apart. The PR's own new conformance row `read-update.singleton.document-patch-validation` asserts behavior the problem-details clause does not define.

Fix: pick one discriminator and apply it in all three paths — either root `instanceLocation` at the record (`/properties/…`, `/metadata/…`) or add a `document` member to the diagnostic entry — then amend `docs/specs/bdp.md` §`validation-failed` to add the non-object-metadata cause and define the pointer base. Change `:506`'s message to name the failing document.

**2. HIGH — The new metadata-requiring Read schema cohort is unenforceable: no code path in the repo can reject a read that omits `metadata`.**

`packages/conformance/matrices/read-v1.json` · `packages/protocol/src/read-values.ts:42-45,122,138,170,216,239,262`

Defect: two independent reasons.
- The executable Read manifest's JSON-Schema assertions still name the **legacy** definitions: `#/$defs/beadRecord` (1), `#/$defs/linkRecord` (1), `#/$defs/beadCollection` (6), `#/$defs/linkCollection` (17) — all metadata-**optional**. The packaged conformance run therefore cannot fail on a missing member.
- The only consumers of the new `current*` definitions are the five parse functions in `read-values.ts`, and every one of them calls `projectLegacyBeadMetadata`/`projectLegacyLinkMetadata` **before** `validateFromSchema`. The injected `metadata: {}` guarantees presence, so `currentBeadRecord`'s `required: ["metadata"]` is unreachable by construction. `read-values.test.ts` asserts exactly this leniency (`parseBeadRecord(beadWithoutMetadata)` succeeds); there is no negative case.

Impact: the PR pays a full re-seal — 42→47 sealed definitions, a new projection digest, a new evidence constant, a new `runHead` — for a constraint that no input can violate. `docs/specs/bdp.md:2965` ("Successful reads always expose `metadata`") is normatively asserted but neither proved nor provable by the kit, which is precisely the overclaim risk the seal exists to prevent.

Fix: bind the manifest's record and collection assertions to the `current*` refs (the projection roots already include them), or add a strict non-projecting validate entry point that the conformance kit uses while client parsing stays lenient. Add at least one negative case asserting a missing `metadata` is rejected by whatever surface is meant to enforce it.

**3. MEDIUM — Advertised-limits prose contradicts the new combined-count rule and the implementation.**

`docs/specs/bdp.md:2351` vs `docs/specs/bdp.md:975` vs `packages/server/src/resource-evaluator.ts:1009-1015`

Defect: `:2351` still reads "`patch.operations`, `patch.pathBytes`, and `patch.pathDepth` bound **one property patch**". The amended Property Changes section at `:975` says limits "bound the **combined** patch operation count", and the implementation concatenates both arrays and tests `changes.length > limits.patchOperations`.

Impact: a client that reads `:2351` and budgets `patch.operations` per array gets `limit-exceeded` on a request it had every reason to believe was in bounds. Two readings of one normative document, with the implementation following only one.

Fix: amend `:2351` to say the operation count bounds the combined operations of one Resource update, and state that `pathBytes`/`pathDepth` remain per-operation.

**4. MEDIUM — Selector addressability for `metadata` is asserted as decided but landed nowhere, and fails silently.**

`docs/specs/bdp.md:797,803` · `packages/server/src/read-selector.ts:150-156,817-818` · `docs/design/preview2-common-metadata-amendment.md`

**5. MEDIUM — Two Transactional catalog citations were weakened to fragments that no longer support their row titles.**

Defect: `transactional.event.owned-link-delta` is titled "Owned-Link mutations emit source updated Events carrying **exactly one** ownedLink delta". **6. MEDIUM — Two write surfaces were missed by the amendment: `updateWhere` has no metadata plane, and `stateChange` upserts still admit a record without metadata.**

Defect: `UpdateWhere(collection, selector, change, …)` keeps a single required `change` with no `metadataChange`; I confirmed `updateWhereOperation` **rejects** `metadataChange`. Impact: set-based updates cannot touch metadata at all, and the one plane that can only ever carry current state is the one left schema-unconstrained. Both are Transactional-profile prose/schema (unrealized), so this is a spec-coherence defect rather than a runtime one.

**7. MEDIUM — The new pre-metadata erasure-digest clause is self-defeating: no served or SDK-returned representation can reproduce the digest, and nothing marks which form to use.**

`docs/specs/bdp.md:5829-5838` · `packages/protocol/src/history-values.ts:180,188` · `scripts/demo-history.mjs:256,267,297-303`

Defect: the new text requires that "verification of that historical digest uses the retained original record, never the later compatibility projection." But History exact reads go through `parseBeadRecord`/`parseLinkRecord`, which unconditionally inject `metadata: {}`; the SDK exposes no un-projected form. Impact: a holder of an erased version's content who obtained it after this amendment cannot recompute its committed digest, and cannot determine that it should strip the projection. # Inherited / out-of-scope observations

1. **Unknown selector root members resolve to `MISSING` rather than refusing** (`read-selector.ts:817-818`). Pre-existing for `attribution`, `changeContext`, etc.; `read-selector.ts` is unchanged in this PR. It is the mechanism behind Blocker #4's silent failure mode, not a defect introduced here.
2. **Patch application precedes limit enforcement.** `patch()` runs at `:775-789`; the operation-count check is at `:1009-1015`. An over-limit patch is fully applied in memory before rejection. Pre-existing ordering (the old single-`change` code did the same); no state escapes because writes happen only after `fault.check()`. The combined count now roughly doubles the worst-case pre-check work, still bounded by `request.bodyBytes`.
3. **README↔fixture declaration agreement is unenforced.** `packages/adapter-bd/README.md` and `oracles.numeric-model.declaration` must agree ("the successor observation tests require agreement with this document"), and `declaration.source` names the README — but nothing checks it. I verified PR64 kept them byte-identical; nothing would have caught it otherwise. Relevant to PR65 (see P8).
4. **Event and change-feed records remain metadata-lenient by design.** `createdData`, `ownedLinkChange.created`, `historicalBeadRecord`/`historicalLinkRecord` all permit a missing member. For Events this is explicitly reasoned in the spec; for `stateChange` it is not (Blocker #6).
5. **`cohort-artifact.ts` contains a literal NUL byte** as a composite-key separator (`${scenarioId}\x00${variant}`). Intentional, inherited, and makes `grep` treat the file as binary — worth knowing when searching, not a defect.
