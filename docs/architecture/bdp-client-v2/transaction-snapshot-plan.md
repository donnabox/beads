## Intended result and limits

Create and durably serve a complete finite Snapshot of the current fixed all-visible Scope, with independent Bead and Link streams anchored to exactly one owner prefix. A client can reconstruct a replica from both streams and resume the existing finite changefeed at the manifest checkpoint without a gap. Captured bodies, identities, revisions, page boundaries, checkpoint and expiry survive mutation and ordinary/crash restart. No second graph owner, all-graph JavaScript array, ordinary collection cursor substitution or Snapshot-dependent write admission.

The first implementation remains source-private and explicitly partial. It does not activate Transactional discovery, optional History, SSE, erasure administration, mutable authorization views or a complete profile claim. Actual empty erasure ledger is valid only for this existing no-erasure installation. Public discovery and complete minimum handling remain separately gated. Minimums on retained Snapshot targets have an unresolved meaning identified below; do not quietly choose it.

## Existing seams and missing work

`transaction-store.ts` owns one locked SQLite connection, resources, identities, durable groups, receipt pages, epoch and current position; synchronous guarded entries reject reentrancy, leaked callbacks and sticky failures. Groups are retained without pruning. Thus a valid capture checkpoint can continue through the entire current retention horizon without per-Snapshot pins or any new replay log. The distinguished checkpoint `genesis` names exclusive replay from the initial prefix; the separate position token for that prefix is `pos-0`. A future no-pruning discovery could truthfully report `minimumReplayPosition: pos-0`; no current serving discovery site does so. Neither token is the most recent Snapshot anchor, and positions are not interchangeable with checkpoints. Aliases never enter Snapshot streams or advance its anchor.

`withRead().resources()` builds an entire array and is unsuitable for bounded capture. `transaction-read.ts` ordinary pagination is also unsuitable: query-selected in-memory cursors do not supply this complete durable graph promise. `transaction-changefeed.ts` already provides the actual Scope/epoch/view-qualified checkpoint codec and complete group renderer. Reuse `transactionCheckpoint`, including genesis at zero; do not derive a new token spelling from examples.

`transaction-service.ts` has tracked finite waits/drain and paired owner observations. `transaction-http.ts` supplies trusted credentials, raw method classification, JSON negotiation and conditional response handling. Reuse these rather than adding a new listener. `openTransactionStore` in `transaction-store.ts` is the owner factory, also used directly by fault/recovery tests. `transaction-runtime.ts` is the private listener/process composition factory; direct owner tests do not need to start that transport. Snapshot persistence/schema/versioning is genuinely missing; no durable installer or capture API already supplies it.

## Minimal private representation and lifetime

Propose a separate private `transaction-snapshot.ts` for target parsing, immutable body types, page URL construction and bounded projection/integrity checks; persistence stays in the existing store. No generic pagination framework and no public exports.

Add locked metadata and captured-row tables, conceptually:

- Snapshot row: random opaque identity, Scope epoch/view, position/checkpoint, fixed creation/expiry instants, recorded per-stream counts/bytes/page boundaries, and the actually projected ledger (empty here).
- Captured Resource rows: Snapshot identity + kind + ordinal + canonical identity + exact bounded wire body; unique identity per Snapshot. Store only the immutable projected records, not a reference to mutable resources.
- Recorded page ranges or equivalent deterministic ranges fixed by the captured configuration. Tokens bind Snapshot/kind/range; do not recalculate ranges from current resources or changed limits on reopen. Capture each typed stream in ascending Unicode code-unit order of absolute canonical identity using the existing `compareCanonicalIds` definition (`packages/protocol/src/index.ts:252`). Persist that order as ordinal. Do not equate SQLite UTF-8 BINARY collation with UTF-16 code-unit order for arbitrary Unicode; use an explicit order-preserving encoded sort key or a bounded identity-only sort using the existing comparator, then fetch/copy bodies rowwise. Canonical-owned arrays retain their existing comparator order. The latter identity-only sort is the smallest initial seam under the 4,096-row cap; include supplementary-character ordering tests and never materialize all bodies to sort them. Initial ranges and absolute next URLs are part of the immutable manifest.

Capture occurs inside one existing owner entry and SQLite transaction, with no await or external callbacks. Obtain context, exact graph rows and checkpoint together. Before materializing the identity list, precheck count and summed encoded record lengths under the same owner entry, failing the conjunctive count/byte ceiling. Then use bounded identity enumeration (at most cap+1 IDs) and rowwise body retrieval confined to that entry; precheck per-row encoded size before loading a potentially corrupt body. An existing primary-key scan plus bounded canonical-ID sort is acceptable at this cap; do not add a new resources index merely for Snapshot pagination, which reads captured `(snapshot,kind,ordinal)` keys. Record this bounded scan cost rather than claiming an indexed per-kind stream already exists. Apply the existing lossless JSON/value codec and Resource projection rules; no JSON.parse/stringify replacement that rounds literals. Validate canonical/local identity conversions and inline-owned consistency without confusing the two ID forms. No open SQL iterator or mutable row escapes. Persist the complete capture before returning any usable handle; failed capture rolls back all its rows and leaves graph, receipts, keys, positions and groups unchanged.

No historical preimages, new Resource revisions, group or Events are produced by capture. The Snapshot table is retained read state. Reuse the owner's atomic-failure fencing and original/cleanup-cause preservation. Required SQLite journal recovery precedes configuration comparison; do not reintroduce the defective read-only preflight. Bump the private store `format` from `bdp-private-transaction-contracts-8` to a distinct Snapshot-table version selected at implementation; retain the unchanged identity policy. Persist Snapshot capacities, lifetime and page plan policy in the existing bounded configuration. The present format/configuration comparison throws `transaction installation mismatch`; identity-policy mismatch has its distinct existing `explicit new-store provisioning required` diagnostic and is not the Snapshot compatibility mechanism. Test prior-format refusal and same-format changed-capacity refusal separately, before BDP maintenance. No migration/reseed: prior installed evidence stores cannot be opened by the new format and remain preserved as historical artifacts. Actual valid incompatible files remain byte-identical; necessary hot-journal SQLite recovery is a separately tested exception, not BDP maintenance. Proposed private fault stages `after-snapshot-copy` (inside transaction) and `after-snapshot-commit` (after durable commit, before delivery) support direct owner tests; use the existing DatabaseSync failure seam for uncertain COMMIT/ROLLBACK instead of inventing a new failure subsystem.

Expiry is fixed at capture, not renewed by HEAD, page reads, manifest refetch or restart. Proposed private lifetime is five minutes, persisted as installation configuration; this is a reference capacity choice, not a normative duration. At expiry, release captured bodies/page data but preserve a compact issued-handle disposition row for the life of this store epoch. This keeps authorized issued-expired selectors at 410 without assuming that forgetting after an arbitrary horizon is lawful. No receipt forgetting rule is imported.

Minimal bounded implementation proposal: at most 65,536 total successfully issued Snapshot identities per installation epoch, with bounded compact identity/expiry/disposition fields (at most 1 KiB encoded metadata each). Do not repeat the potentially long Scope URL in each disposition; it is fixed installation metadata. At that total capacity, refuse further creation with permanent `limit-exceeded` 413, omit a fictitious `limit` name, and preserve all existing classifications. This is a deliberately finite development installation, not a service that promises unlimited creation or a transient condition that expiry can clear. No automatic reprovision, epoch rotation or tombstone deletion. The cap is an engineering proposal for council; it avoids an unproven semantic forgetting horizon and a new authenticated-token framework. A later scalable issuance scheme is separate work.

A committed but undisclosed capture still counts as issued and consumes live capacity until fixed expiry; an after-commit delivery failure cannot pretend it allocated nothing. Pre-commit capture failures roll back all rows/count effects. Missing/corrupt captured rows before expiry remain service failure, never 410, replacement or truncation. A bounded disposition retained after expiry is not a promise to retain bodies indefinitely.

## Bounded materialization proposal

A complete graph is not bounded by the per-transaction matched-Resource budget. Do not use M32/M64 or Event E256 as a Snapshot resource ceiling. Capacity limits must be explicit private installation limits, not new protocol limits or excuses to publish incomplete streams.

Propose initial development capacity of 4,096 Resource rows **and** 32 MiB total encoded records per Snapshot; at most eight live handles **and** 64 MiB aggregate captured records, plus the separate lifetime issuance/disposition cap above. These are conjunctive ceilings, not entitlements: no promise that 4,096 maximum-size records fit, or eight 32-MiB captures fit simultaneously. The byte ceiling binds before row count for large records, and aggregate bytes bind before live handle count for large captures. At exactly R=262,144 encoded bytes each, 128 records consume the full 32-MiB record budget; metadata/page framing is charged separately to explicit bounded envelopes. Two captures at that record-byte ceiling consume 64 MiB; a third is temporarily unavailable even though fewer than eight handles exist. Small graphs can instead reach the row or handle ceiling. Tests distinguish all four conditions.

A Scope exceeding per-Snapshot rows/bytes, or an installation reaching the permanent issuance cap, returns normative `limit-exceeded` 413, retry `never`, family `size`, with no invented `limit` member. Temporary live-handle/aggregate-body exhaustion returns `temporarily-unavailable` 503, retry `after-delay`, with Retry-After and no claim that retry is guaranteed to succeed. These dispositions are supported by `bdp.md:1049–1053,1905–1907` and the normative schema chain `transactionalProblem` → `readUpdateProblem` → Read problem. Validate exact bodies against that schema. Missing capacity advertisement never permits silent truncation or a new refusal law. Bodyless 500 is reserved for genuine internal faults such as corrupt promised data. None of these capture capacities changes mutation admission or transaction Resource/Event counts.

Use the installed Resource page count ceiling and additionally bound encoded bytes per typed page, proposed 4 MiB. The current evaluator materializes `subjectRecipe` and `sourceRecipe` into `after`/`sourceAfter` (`resource-evaluator.ts:1008–1014`); `materializeVersion` includes inline `ownedLinks` (`:1150–1161`); then `:1050–1058` serializes each complete record and enforces `representationBytes`. Thus the stored/served canonical record's inline-owned content is already inside R=262,144, not outside R and not an additional 8R. Descriptor maxima remain required graph constraints, but the suggested 9R proof premise is false for this owner. Existing `transaction-materialization.test.ts:247–265` distinguishes the exact-R Bead from an owned-source overflow. Add a near-R accepted owned-source body fixture and one-byte overflow refusal; do not attempt eight individually maximum-size Links inside one R-bounded source and call that legal.

Snapshot projection must preserve the complete bounded canonical record using the existing lossless codec, without adding incidental `links`. If a proposed projection adds bytes beyond the stored full record, measure and bound that delta explicitly before reusing R. The page bound includes actual `{items,next}` serialization. With at most one newly added continuation URL, source URL ≤65,536 UTF-8 bytes and conservative worst-case JSON escaping reserve 6*(S+1,024)+1,024, even one R-sized Resource plus this framing is <4 MiB. Check actual encoded lengths before publishing pages; never use an approximate bound to truncate. Count ceiling and byte ceiling apply together and each page makes progress.

The manifest embeds two already-bounded initial pages: ≤8 MiB plus empty-ledger/identity/Scope/context/checkpoint/expiry framing. Reserve 2 MiB for that bounded envelope at the current Scope/token limits, then derive/check the exact source-driven inequality when implementing. This 10-MiB outer bound is well below pinned Node24 MAX_STRING_LENGTH=536,870,888 even using the conservative UTF-8-bytes ≥ UTF-16-code-units bound. No huge proof allocation. Retained graph bytes, live handle bytes, per-page response bytes and parsed heap are different measurements; representative memory evidence remains necessary, not a universal heap claim.

Capture is rowwise and bounded in total work; no SELECT-all plus later truncation. Ordinal continuity, row counts, kinds, unique identities, page boundaries and all recorded next links are checked. Refetch does not recompute or repair corrupt data. The total captured graph can exceed one page and one transaction, so tests must establish both independently. Page maximum/configuration must be persisted and compared before BDP maintenance on reopen, including retained expired captures.

## Serving context, minimums and unresolved decisions

Creation GET with a complete valid minimum tuple can reuse the existing finite wait loop: each attempt checks that tuple and captures only an eligible owner prefix. HEAD creation makes the same auth/epoch/view/minimum/service decision but returns no usable handle; it may use bounded counts/size checks rather than persist a copy. A HEAD preflight is not a reservation guaranteeing a later independent GET. Waits never hold SQLite entries; existing finite deadline/cleanup semantics apply. Partial/unknown opaque tuples retain current explicit gaps.

For ordinary retained GET/HEAD, independently authorize the caller under the current fixed all-visible view. A second authorized principal with that same view may use the handle; no creator-principal isolation is inferred from receipts. Missing credentials and an actually undisclosable/foreign-view selector are separate controls. The immutable capture carries epoch/view, not an authority-attested actor. Current fixture tests can establish foreign supplied-token refusal, not actual policy rotation. Snapshot bodies, checkpoint and manifest anchor remain original. Recorded expiry/integrity and applicable epoch/view gates precede conditional handling.

Choose **no ETag or Last-Modified initially** for these private Snapshot responses. Snapshot-specific validators are not assigned by `bdp.md:6546`; general preconditions at `:1991–2000` still apply. Actual `read-http.ts:50–66` gives `If-None-Match: *` →304 without an ETag, specific `If-Match` →412, `If-Match: *` passes, and a specific `If-None-Match` cannot match. No hash or invented revision is needed. Test both methods and precedence, after auth/fences. Current serving context is already mandatory on304/412 (`:5801–5814`); a stale captured-header proposal is not an acceptable alternative for those responses.

**Question S1-Q1 remains with the operator:** `:5779–5785` requires a minimum response at/after its minimum, while `:5899–5931` preserves the captured Snapshot anchor. Does a retained Snapshot minimum gate the current serving replica's prefix while retaining the older body, or the immutable anchor itself? Receipt `:5233–5244` explicitly uses current observation but is receipt/page-specific; receipt lookup ordering `:4618–4623` is also not a Snapshot-specific ruling. Neither is silently extended here. If the minimum gates the anchor and lies above it but below current head, waiting cannot advance that handle; the exact permitted refusal is not stated. Root has already asked the operator. Do not manufacture `catch-up-timeout` for an authority known to be caught up, and do not call a development-gap500 a normative minimum response.

Pending Q1, author only durable capture, creation with settled complete minima, and retained reads **without minimum controls** as private partial functionality. Capture both immutable anchor and same-entry current observation internally so either eventual ruling remains representable. Use current serving context for 304/412 as already required; propose current serving headers for ordinary retained200/HEAD consistently with the general observation clause, while clearly withholding a full retained-minimum claim. Any supplied retained-minimum input stays outside the implemented private contract with an explicit development-gap report; tests must label it unsupported, not a conforming refusal or evidence of catch-up. No full Transactional service may ship on that exception.

**Q2 disposition policy:** the minimal retained-disposition proposal above preserves 410 for issued expired handles and 404 for never-issued/undisclosable handles without any time-based forgetting. Current text does not positively authorize importing receipt forgotten-failure rules or optional History cursor-lifetime language. This engineering choice has finite total issuance and permanent creation backpressure; council approval is needed for that stated private limit, not a new wire rule. If root instead wants indefinite issuance with finite disposition storage, that requires another proven representation or an explicit forgetting ruling. It is not necessary to begin bounded capture work.

Malformed canonical query mappings also need explicit reference convention (as finite Events/G1), not a universal rule inferred from a fixture. Canonical query namespace should distinguish creation, manifest and stream targets; reject repeated/extra/conflicting parameters without allocation. Tokens are selectors, not credentials. GET/HEAD auth, method-first bodyless 405, unknown/foreign nondisclosure and Accept negotiation reuse existing established routing. Current Origin refusal means CORS remains unimplemented, not implicitly satisfied.
