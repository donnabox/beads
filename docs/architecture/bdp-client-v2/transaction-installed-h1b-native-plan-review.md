## Two implementation constraints

1. **Receipt provenance must survive a valid reopen without being rebound retroactively.** The plan correctly requires both immutable source-response provenance and a newly validated physical endpoint on reopen. Implement a chain with the original receipt observation retaining its original process/dial binding, and the later dynamic exchange referencing the newly validated process binding with equal logical Scope/artifact/runtime/policy/authentication identities. Do not rewrite the old observation to the new endpoint, and do not require the old physical port to equal the newly allocated port. A positive test must capture a receipt, close/reopen, then follow that original capture through the new validated endpoint; a changed endpoint without that validated reopen transition must fail before dialing. This makes the plan's durable receipt witness compatible with its physical-binding tamper control.

2. **Prefer the already authored private client operation over a new action family.** H1a already contains `family:client`, `operation:transactional.receipt-read`; its factory uses the shared closed executable-manifest parser. Retain that carrier with a closed private operation handler and mandatory private recording, unless implementation demonstrates a need for a distinct private parser. A new `family:transactional.receipt-read` cannot simply be inserted into the shared grammar while claiming ordinary parser semantics are unchanged. In either form, ordinary runner invocation must refuse the private operation/recorder path, not merely fail later because an adapter is absent. This is the minimal implementation of the plan's private-only requirement, not new wire semantics.
