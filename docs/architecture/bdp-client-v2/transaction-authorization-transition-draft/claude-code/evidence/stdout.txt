# Evidence (test-path) review — Scope authorization transition

Scope: the five complete test diffs. Production excerpts used only as shared interfaces. "Passed/failed" statements are taken from the supplied root-run attributions, not from execution by me.

## Findings

**1. Medium — `transaction-authorization.test.ts`, "preserves policy and delivery leases after confirmed policy rollback": the rollback is never confirmed durably.**
The `before-policy-commit` fault throws *inside* `atomic(...)`, after `UPDATE metadata ... authorizationPolicy`. The only rollback oracle is `expect(f.owner.authorizationSnapshot()).toBe(before)` — but on that path `authorization = next` is never reached regardless of whether the SQLite transaction actually rolled back. If `atomic` failed to roll back (or the fault were ever moved outside it), the on-disk row would carry generation 1 while memory reports 0, and the store would surface a phantom revocation at the next open; this case would still pass. Minimal fix: after the final assertion, `f.reopen(); expect(f.owner.authorizationSnapshot()).toEqual(before);` (or a `f.raw` read of the metadata row). Cost: +1 owner open, 0 HTTP. Note the sibling fence case already reopens — the asymmetry is the tell.

**2. Medium (fail-open) — same file, test 1: migration precedence over an existing policy row is unpinned.**
Test 1 establishes exactly one migration fact: legacy `configuration` + *absent* `authorizationPolicy` ⇒ open succeeds with generation 0 / all-visible / mutable. All five rejected-open copies start from the *current* configuration. Nothing pins legacy configuration + a **present generation-1** row — a state constructible by the fixture's own `raw()` and reachable by operator metadata restore or a partially applied migration. If the migration branch installs the initial policy unconditionally, an administrative revocation is silently re-granted; every other metadata guard in this suite is fail-closed, so the omission is asymmetric. (Plain binary downgrade is blocked by the installation-mismatch guard, so this is tamper/restore, not routine lifecycle.) Minimal fix: a sixth rejected-open copy asserting refusal (or an explicit preserve assertion). Cost: +1 copy dir, +1 open, exceeding the frozen five copies by one.

**3. Medium — projected shapes that are *not* wholly collapsed are never schema-validated anywhere.**
Ajv exists only in `transaction-runtime.test.ts`. T1's seed receipt has 32 `created` entries, so post-publication it collapses whole and only the `withheld` branch is validated; its `next` is asserted `null`, so **`mutationReceiptPage` is never validated in this suite at all**. The two remaining wire shapes — the partially withheld receipt `{results:[{outcome:"withheld"},<deleted>], next:<url>, expiresAt:…}` and the all-withheld page — exist only as structural `toEqual` comparisons in `transaction-authorization.test.ts` ("projects receipt records and allocations…"). The documented source-v3 failure (forbidden `expiresAt` at request 16) was precisely a schema violation that structural equality cannot see. Minimal fix: compile `mutationReceipt` / `mutationReceiptPage` in the unit file and validate `observed.receipt` and `afterPage.page`. Cost: 0 HTTP, 0 owners.

**4. Medium-low — the mandatory-timeout contract and the sync-throw surface are unexercised.**
The lifetime correction makes `timeoutMs` mandatory and bounded (`!Number.isSafeInteger || <1 || >2147483647` ⇒ `TypeError`), yet every call in the suite passes 1000 or 10; neither the `TypeError` branch nor `signal?.throwIfAborted()` on an already-aborted signal is asserted. Both throw **synchronously**, while cancellation and deadline *reject* — a caller writing `await expect(...).rejects` would be misled. The same mixed contract appears in `service.stream`: aborted-supplied-signal rejects, but capacity and `foreign-view` throw synchronously, and `transaction-service.test.ts` masks this with `Promise.resolve().then(() => service.stream(...))`, so no evidence shows a handler path surviving a synchronous `TransactionAuthorizationFailure`. Minimal fix: two synchronous assertions in the existing drain case plus one direct (unwrapped) `expect(() => service.stream(...)).toThrow` in the service case. Cost: 0.

**5. Low-medium — error oracles are substring-only and cannot identify which guard fired.**
`toThrow("authorization admission refused")` matches every `TransactionAuthorizationFailure` irrespective of `code`, so in the drain case and in "captures one Scope policy…" a refusal caused by the published policy (`forbidden`) is indistinguishable from a leaked administrative pause (`temporarily-unavailable`) — and `resume()` is only reached in a `finally`, so a leak is exactly the failure this suite should catch. Likewise, all five rejected opens match `"authorization policy"` / `"installation mismatch"`, which `parseTransactionAuthorization` emits for three different guards (`exceeds storage bound`, `invalid … fields`, `invalid …`). Minimal fix: assert `code` (`expect.objectContaining({ code: "forbidden" })` via try/catch or `toThrowError`), and distinguish the open guards by message.

**6. Low-medium — `transaction-runtime.test.ts` T1: the revoked change stream's delivered bytes are never inspected.**
The test asserts only `stream.closed` / `streamClosed`. The recorder already exposes `frames` and `wireBytes`, but nothing asserts that no frame crossed the publication boundary (a flushed group or a terminating event carrying the hidden transaction would pass unnoticed). Minimal fix: after `await stream.closed`, `expect(stream.frames.filter((x) => x.startsWith("id:"))).toEqual([])`. Cost: 0 HTTP. (The analogous assertion on the 409 reconnect is near-vacuous for a different reason: a JSON problem body has no `\n\n`, so `frames` is always `[]` there.)

**7. Low-medium — `transaction-authorization.test.ts`, last case: the hidden group's `checkpoint` is self-referenced.**
`checkpoint: page.page.groups[0]?.checkpoint` makes the oracle vacuous for the single field of a `projectionAdvance` group that could carry identity across the boundary; `not.toBe("genesis")` does not address it. bdp.md:5751-5754 requires that no transaction identifier from the hidden group cross. The seed transaction id is in scope as `receipt.transaction`. Minimal fix: additionally assert the checkpoint neither equals nor contains it. Cost: 0.

**8. Low-medium — no `HEAD` delivery of a withheld receipt is tested.**
bdp.md:5230 names `HEAD` as one of the deliveries that must be projected under the current view; no test in any of the five paths issues a `HEAD`. A `Content-Length` or `ETag` derived from the retained (unprojected) receipt would leak entry count/size while the `GET` body stays correct. Minimal fix: one `HEAD` on `first.receipt.id` after request 16, comparing `content-length` (and `etag`, if served) with the projected `GET`. Cost: +1 HTTP, raising T1's exact bound 17→18.

**9. Low — assertions over unreachable states; fixture nit.**
The pure-projection cases use `results: []` on a `completed/available` receipt and `allocated: []` on an `expired` one; both are states the schema and the executor do not produce, so the `length > 0` guards are only exercised synthetically. Relatedly, the `allocated → {operationIndex, operationName?, withheld: true}` mapping is **unobservable**: under the Scope-wide binding every nonempty allocation set is wholly withheld, so the collapse always deletes the mapped array — no assertion can ever see that shape, and its conformance to the (unsupplied) allocated `$def` is unproven. Also, `fixture().raw()` closes the owner and never reopens it, so `f.owner` silently returns a closed handle until the next `reopen()`; every current call site happens to reopen.

## Essential omitted context

- Store `open`/migration code, `atomic`, `fence`, `enter`, `revokeLeases`, `expireRow`, `pagePlan`, `inspect`, `observeSnapshot`, `readChanges`, and the `receipt` vs `readReceipt` APIs (both are used; only `readReceipt` is in the excerpts). Findings 1–2 are stated as evidence gaps, not verified production defects, for this reason.
- Test 3 asserts `lease.signal.aborted` after a fault that throws *before* `revokeLeases()`; this can only hold if `fence()` revokes leases, and that coupling is unverifiable here and undocumented in the diff.
- The allocated-entry and `receiptCore`/`stateChange`/`event` `$defs` were not supplied, so finding 9's conformance claim is bounded.
- T1/T2 import `../dist/transaction-runtime.js`; the HTTP evidence validates built bytes, and no assertion detects a source/dist divergence. Any fix landed for findings above must be rebuilt before re-running.
- `inspect().position` is asserted as `"0"/"1"/"2"` while the wire uses `"pos-N"`; I assumed these are different representations rather than a defect.
- Root-run attributions (source-v3/v4 outcomes, the 10-of-11 callback result) are taken as given; I executed nothing, and no timing/HTTP bound here is a performance claim.
