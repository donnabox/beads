### 1. Two new tests use a non-advancing clock, so a regression hangs the worker instead of failing — Medium
**File/line:** `packages/server/src/transaction-service.test.ts:1415` and `:1501` (`tracked({ budgetMs: 2, now: () => 0, wait })`)

**Impact:** With `now: () => 0`, `waitForTransactionMinimum` computes `deadline = 2` and `current = 0` on every pass, so `current >= deadline` is never true — the deadline branch is unreachable and these two tests rely entirely on their *subject behavior* to terminate (catch-up: the independent submit to `pos-2`; pending abort: observation of `signal.aborted`). Once `release.resolve()` has run, the held `wait` returns after a single microtask. If either escape regresses, the loop becomes an unbounded resolved-promise retry that never yields to the macrotask queue, so vitest's per-test timeout timer cannot fire. I confirmed the starvation property in isolation: 7,448,006 iterations of `await Promise.resolve()` in 300 ms with a 50 ms `setTimeout` never firing. The result is a pegged, hung CI worker rather than a named assertion failure — exactly the weaker outcome the plan warned about ("a timeout alone is weaker than the intended named assertion"). Note this is a regression from the pattern this same file already uses for the analogous C3 held-wait case, which supplies `budgetMs: 100, now: () => tick++` (`:824-826`). The recorded mutants did not expose it: `mutable-control` happens to terminate on `cursor-expired`, and no mutant targets abort observation.

**Repair:** give both tests the advancing clock the existing case uses, keeping the deadline well beyond the intended retry count so the loop stays bounded without perturbing the asserted counts — at `:1415` and `:1501` declare `let tick = 0` and pass `tracked({ budgetMs: 100, now: () => tick++, wait })`. Both tests need only one held wait and two attempts, so `wait` call counts and entry counts are unchanged; a regressed escape then terminates in `catch-up-timeout` and fails the existing `rejects.toBeInstanceOf(ScopeServerOperationAbortedError)` / `observed.context` assertions by name. (Additive alternative, if the fixed tick is to be preserved verbatim per the plan's "keep tick fixed while paused": make the held `wait` throw on an unexpected extra invocation, e.g. `if (wait.mock.calls.length > 1) throw new Error("unexpected extra minimum retry");` as the first statement at `:1411` and `:1497`.)

### 2. Drain test's "close remains pending" assertions run with no await, so they cannot distinguish a draining close — Low
**File/line:** `packages/server/src/transaction-service.test.ts:1546-1547`

**Impact:** `expect(closed).toBe(false)` and `expect(f.owner.inspect().position).toBe("0")` execute with zero awaits since `f.service.close()` at `:1540`. `closed` is set in a `.then`, and `close()`'s body always suspends at `await read.close()`, so both assertions hold even if `close` dropped `...active` from its `Promise.allSettled` — i.e. the plan's "close remains pending while the admitted wait is held" is asserted vacuously. The underlying ordering property *is* still proven indirectly: with the drain removed, the drain-time retry at `:1552` would hit a closed owner and reject with `"transaction discovery observation refused"` instead of `catch-up-timeout`, failing `rejected`. So this is assertion rigor, not a coverage hole. Again, the existing C3 analogue is stricter — it inserts `await Promise.resolve()` at `:853` before the same `expect(closed).toBe(false)`.

**Repair:** insert a macrotask flush before the two assertions, e.g. `await new Promise((resolve) => setImmediate(resolve));` as the first statement inside the `try` at `:1545`, so the assertions are reached only after `close()` has had the chance to complete if it were not draining. (A bare `await Promise.resolve()` as at `:853` is the minimum; `setImmediate` is strictly stronger and safe here because the held `wait` only resolves in the `finally`.)

### 4. Three plan-mandated assertions absent from the refusal and final-prefix cases — Low
**File/line:** `packages/server/src/transaction-service.test.ts:1558-1600` (distinct-failures test) and `:1408-1445` (catch-up test)

**Impact:** The plan's *Reentry/closed/fenced entry* row requires, for repeated minimum-bearing refusal, "exact existing wrapper error/cause, **zero waits/parses**". The test asserts the wrapper message and `cause` identity for the reentrant (`:1565-1568`), delegated-throw (`:1589`), delegated-refuse (`:1591-1594`) and closed-owner (`:1597-1599`) paths, but installs no `wait` spy (`tracked({ now: () => 0 })` at `:1559` leaves the real `delay`), no assembly spy at those points, and no entry count on the delegating service — so "zero waits/parses" and "is not retried" are unasserted for all three non-malformed refusal paths. **Repair:** in the distinct-failures test, pass a `wait` spy through `tracked` at `:1559` and assert `expect(wait).not.toHaveBeenCalled()` plus `expect(assemble).not.toHaveBeenCalled()` after each refusal, and wrap the delegating owner's `withRead` at `:1578-1583` with the same `entries++` counter to assert one attempt per delegated failure.
