## 1. MEDIUM — test flaw: the late cancellation/deadline subtest cancels nothing

**Location** `internal/storage/graphstore/legacy_import_test.go:284-298`

**Issue** `s.afterWrite` returns `context.Canceled` / `context.DeadlineExceeded` as a plain sentinel *value*. `ctx` is never cancelled and no deadline elapses. The subtest is mechanically identical to the `"import-retained"` entry in the stage-fault loop immediately above it (line 265), only with a different error value — so it adds zero coverage over an already-covered case.

**Impact** The behavior it names is unverified, and the real path differs materially. With a genuinely cancelled context, `database/sql`'s watcher rolls the Tx back asynchronously, so the explicit `tx.Rollback()` in `backend.go:214-222` returns `ErrTxDone`; because `write` is true, `withTx` then joins `ErrOutcomeUnknown` into the error. `graphStorageError` checks `ErrOutcomeUnknown` (`cmd/bd/graph_preview.go:767`) *before* `context.Canceled`/`DeadlineExceeded` (line 769), so a real late cancellation reaches the operator as `outcome_unknown`, exit 6, "do not automatically replay" — not the clean refusal `docs/reference/graph-legacy-import.md:70` promises ("Engine errors and timeout roll back before commit"). The snapshot assertions (`errors.Is(err, fault)` plus unchanged state) would still pass against the real path, so even once executed this test cannot discover that exit-code difference. This is listed as not-yet-executed evidence; executing it as written buys nothing.

**Fix** Drive a real `context.WithCancel`/`WithTimeout` that fires at the `import-retained` stage, pass that context to `ImportLegacy`, and read state back through an independent live context. Assert the error classification (including whether `ErrOutcomeUnknown` is expected) as well as the absence of rows and the preserved prefix.

## 2. LOW-MEDIUM — the prefix-config read flattens its error chain

**Location** `internal/storage/graphstore/legacy_import.go:76-78`

**Issue** `fmt.Errorf("%w: fresh workspace Issue prefix configuration is missing or unreadable: %v", ErrInvalidStore, err)` — the driver error is formatted with `%v`, so it leaves the chain.

**Issue impact** This `SELECT` is the first statement that can fail for a transient reason (cancellation, deadline, pool/engine error), and every such failure is reported as `ErrInvalidStore` alone → CLI `invalid_store`, exit 5, i.e. "your store is corrupt" for what was a cancelled import. `errors.Is(err, context.Canceled)` fails for SDK callers. No test covers it: the injected faults are at `afterStage("import-prefix")`, which runs *after* both the read and the `UPDATE`.

**Fix** Second `%w`: `fmt.Errorf("%w: ...: %w", ErrInvalidStore, err)`. (The live worktree already carries exactly this change, which corroborates it.)

## 3. LOW — the infra-type gate is the one fail-open config read in a fail-closed transaction

**Location** `internal/storage/graphstore/legacy_import.go:86-91`

**Issue** `issueops.ResolveInfraTypesInTx` discards DB errors and falls back to YAML then `domain.DefaultInfraTypes()` (`internal/storage/issueops/config_helpers.go:543-546`); `ResolveInfraTypesStrictInTx` exists for exactly this case. Eleven lines earlier the same function deliberately refuses a missing/unreadable `issue_prefix` row — the stated repair.

**Impact** If the `config` read fails mid-transaction, the gate silently falls back to `{agent, role, message}` instead of the workspace's configured `types.infra`, so a locally-configured infra type could be admitted as an ordinary imported Issue. Narrow (target must be a fresh workspace, which rarely configures `types.infra`), but it contradicts the import's own fail-closed posture and is invisible when it happens.

**Fix** Use `ResolveInfraTypesStrictInTx` and return its error.

## 4. LOW — docs example omits `--source-prefix` from the apply step

**Location** `docs/reference/graph-legacy-import.md:15-18`

**Issue** The example sequence is `bd import … --dry-run`, then `bd import … --source-prefix web-app --dry-run`, then a bare `bd import old-issues.jsonl --json`.

**Impact** The prefix is not persisted between invocations, so an operator who follows the example verbatim for ambiguous IDs gets a clean dry run and then `invalid_properties` ("source Issue prefix is ambiguous; supply --source-prefix…") on apply. The CLI test itself passes the flag to both forms (`cmd/bd/graph_preview_import_workflow_test.go:220-225`), and the prose table at line 49 implies it is needed on both.

**Fix** Show `--source-prefix` on the dry run *and* the apply.

## 5. LOW — the human-readable summary never discloses that the workspace Issue prefix was replaced

**Location** `cmd/bd/graph_preview_import.go:54` (write at `internal/storage/graphstore/legacy_import.go:79`)

**Issue** Import unconditionally overwrites `config.issue_prefix` with the inferred or supplied source prefix — changing how every future `bd create` mints IDs. `IssuePrefix` is reported only in the JSON result; the non-`--json` message carries counts and the history disposition.

**Impact** An operator who ran `bd init --prefix myproj` and then imported an `old-*` export sees no indication that new beads will now be `old-…`. This repo otherwise discloses overwrites explicitly (`internal/storage/graphstore/overwrite_disclosure.go`; `cmd/bd/import.go:93-99` on why `updated_issues` exists).

**Fix** Append the adopted prefix to the human summary when `result.IssuePrefix != ""`.

## 6. LOW — a repeated label refuses the whole import, contradicting "preserved as a set"

**Location** `internal/storage/graphstore/legacy_import.go:522-553`; docs line 52

**Issue** Neither label writer mutates `issue.Labels` — both dedup into a local `seen` map (`internal/storage/issueops/create.go` `persistLabelsCached` and `persistLabelsPerRow`). So for source `labels:["a","a"]`, `want.Labels` stays `["a","a"]` while the hydrated row returns `["a"]`, and `verifyLegacyIssue`'s canonical-JSON comparison fails.

**Impact** A JSONL whose `labels` array repeats a value (hand-written, third-party, or pre-dedup-era) refuses the *entire* import with `Issue X field labels cannot be represented exactly in graph storage` — blaming storage for a source-side set artifact. Classic `bd import` dedups silently, and the docs describe labels as "preserved as a set".

**Fix** Dedup `issue.Labels` in `prepareLegacyImportWithPrefix` (first-seen order), so the set semantics the docs promise are what gets compared. Keep the refusal for values storage actually loses (over-length, truncation).

## 7. LOW — the JSON clone silently drops non-serialized Issue fields on the SDK path

**Location** `internal/storage/graphstore/legacy_import.go:243-264`

**Issue** UTF-8 validation walks the caller's original struct (`legacyImportStringsValid(reflect.ValueOf(input))`), but every later check and the import itself run on the `json.Marshal`/`Unmarshal` clone. `types.Issue` fields tagged `json:"-"` — `WispPlaneOverride`, `IDPrefix`, `PrefixOverride`, `SourceRepo`, `IsLitePartial` — do not survive the clone, so no check ever sees them.

**Impact** Only reachable through the exported `ImportLegacy`/`ImportLegacyWithPrefix` Go API (the CLI parses JSONL, where these cannot be set). A caller passing `WispPlaneOverride: &true` has it *ignored* rather than refused, even though the adjacent gate at lines 290-292 explicitly refuses ephemeral/no-history/storage-class records. The outcome is safe (the row lands durable, and `requireEmptyLegacyTarget` plus `showIssueInTx`'s `IsWisp` check backstop it), so this is a silent-ignore, not a wrong write.

**Fix** Refuse a non-nil `WispPlaneOverride` (and, if you want symmetry, non-empty `IDPrefix`/`PrefixOverride`) in prepare, before the clone.

## 8. LOW — each issue's owned-Link set is read twice per import

**Location** `internal/storage/graphstore/legacy_import.go:146-162`

**Issue** `recordIssueMappingInTx` calls `ownedLinksInTx` → `showLinkInTx` per link (≈4 queries each) and stores the canonical owned JSON; `showIssueInTx` two lines later recomputes the identical set and compares it to the bytes just written.

**Impact** Bounded — `PreviewSnapshotLimit` caps issues + memories + dependencies at 1000 — but it doubles the link-read cost of the import's most query-heavy pass inside one transaction that also carries two full `HydrateIssueOperationResult` hydrations per issue, against a fixed 5-minute `withGraphStoreBudget` with no partial progress and no flag to raise it. At the admission ceiling on a slow shared server this is the pass most likely to hit the deadline, and the second read can only disagree with the first if the engine is non-deterministic within a transaction.

**Fix** Either reuse the owned bytes `recordIssueMappingInTx` already computed, or keep `showIssueInTx` as the post-read verifier and let it be the only owned-link reader.

## Checked and sound (the prior council's repairs)

Stated for completeness, since the ask was to not assume pending evidence:

- **Batch prefix consensus, no recomputation.** `resolveLegacyImportPrefix` runs once, after preparation; `prepared.prefix` feeds both `result.IssuePrefix` and the config `UPDATE`. Longest-candidate-then-lexicographic selection is order-independent, and it is *correct* for ordinary spellings given `utils.ExtractIssuePrefix`: `web-app-123`→`web-app` (7) beats `web-app-abcdef`→`web` (3, first-hyphen fallback), so mixed numeric/all-letter batches resolve to `web-app` either way. The single-all-letter case yields `web`, fails the `LastIndex == len(prefix)` confidence test, and correctly demands `--source-prefix`. Supplied prefixes are matched literally (`HasPrefix(id, prefix+"-")`), with no trimming and trailing hyphens refused.
- **Memory path allocation is deterministic and collision-free.** Direct allocation is inherently order-independent (keys are unique, so `beads/`+key is unique); only remaps are sorted. `CanonicalSegment` escapes `%` as `%25`, so `"has space"` and `"has%20space"` cannot converge; the direct key always keeps the canonical address and the loser falls to its digest. The `-N` suffix loop terminates (bounded by occupied paths ≤ 1000) and the digest base is always a valid ≤94-byte path. Keys too long to encode skip straight to the digest.
- **Memory key/value exactness, duplicate rejection, original-UTF-8-before-clone.** Confirmed, including that `commonMetadata`→`graph.CanonicalizeJSON` (`graphops/laws.go:747`) covers the one blind spot in `legacyImportStringsValid` (`json.RawMessage` is skipped as `[]uint8`; `appendCompact` does not replace invalid UTF-8, so the bytes reach the validator intact).
- **Comment handling.** The 1000-comment cap is cumulative and independent of the Bead/Link budget. Indexing post-native IDs is sound: `PersistComments` assigns `comment.ID = id` through the shared `*types.Comment` pointer (`internal/storage/issueops/create.go:1067`), and `NextLiveCommentTime` separates same-second derived IDs so distinct comments cannot collapse. Native dedup is unchanged and a collapse is caught by the count check → rollback. Zero `CreatedAt` is a wildcard; a supplied one is compared with `Equal`, so offsets round-trip and only precision loss refuses.
- **Identity preservation.** `assignCreateIssueIDInTx` never rewrites a non-empty ID, and `SkipPrefixValidation: true` skips the target-prefix gate — so `want`/`got` and the allocated `beads/ID` path all carry the source ID. `depid.New` is a deterministic UUIDv5 over `(issue, target)` and matches what `PersistDependencies` inserts, so `IDs`/`MemoryIDs`/`DependencyIDs` are identical between dry run and apply.
- **Atomicity/ordering.** Links are fully written before the mapping pass, so `ownedLinksInTx`/`showLinkInTx` never depend on an issue processed later — a batch listing a dependent before its target is safe. The all-zeros catalog revision is a within-transaction placeholder replaced by `recordIssueMappingInTx`'s fresh token, and it matches `authorityID` in the interim. Multiple `backing='generic', backing_key=NULL` catalog rows are fine under `UNIQUE KEY one_backing` and are pre-existing behavior. The store-wide `writer_token` fence makes concurrent imports fail one at COMMIT. `workflowState`+`legacyImportState` cover every table the import writes, including `config.issue_prefix` — the dry-run prefix-rollback assertion is real.
- **Overlap with Janet's core.** No schema change, no new type, no issueops primitive. `ImportLegacy` remains a thin wrapper over `ImportLegacyWithPrefix`. The import only *calls* `issueops`; the one deliberate reliance on core in-place mutation (comment IDs) is sound, and I checked that the other in-place mutations in `PrepareIssueForInsert` (UTC normalization, `ClosedAt` synthesis for closed rows, `ContentHash`) are all either documented behavior or excluded from the comparison — so the shared-pointer verification is not meaningfully blinded.
- **Pending completeness fixture.** Statically cross-checked `scripts/legacy-import-fixture.py --profile completeness --prefix web-app` against `TestGraphPreviewLegacyImportCompletenessInstalledWorkflow`: 4 issues (`web-app-a1b`, `web-app-b2c`, `web-app-abcdef`, `web-app-d4e`) and 16 memory keys, matching the test's assertions, including the intended `web-app-a1b` key↔Issue-ID collision and the `config set kv.memory.empty-value` record. `decision` and `event` types and `pinned`/`deferred` statuses all pass `ValidateWithCustom(nil, nil)` (`event` via `IsBuiltIn`), and `event` is not in `DefaultInfraTypes()` (`{agent, role, message}`), so the infra gate does not refuse it. `types.Comment` has exactly the five fields `legacyimport` admits, with no `omitempty`, so the producer's comment round-trips for the `reflect.DeepEqual` at line 284. I found no producer/importer contradiction that generating the fixture would expose — but that is static reasoning, not the runtime receipt, and the qualification gate stands.
