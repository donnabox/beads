## Findings

**1. Low–Moderate — depth development-limit now preempts the batch closed-shape check**
*Location:* `packages/server/src/transaction-batch.ts:143-145` (`prepareMixedTransaction`), reached for every batch via `prepareTransaction` at `:125-127`.
*Issue:* The unified path runs `losslessText(root)` — which throws `TransactionDevelopmentLimitError("development batch depth limit")` for depth > 32 — **before** the root closed-shape check at `:144` and before all member discriminator/body-key/reference/label checks. The retired `prepareTransaction` (old `:106-122`) completed root shape, `assertResourceOperation`, the `idempotencyKey` rejection and the full RU member parse *before* its depth walk (old `:121`). The ordering was inherited from `prepareTransactionSetCore`, where it was previously confined to a core test seam.
*Impact:* A batch body that is both over-depth and closed-shape invalid — e.g. `{"operations":[{"operation":"createBead","type":"T","properties":{…31 levels…}}],"extra":1}`, or a deep member carrying `idempotencyKey` — now returns the bodyless `500` + `x-bdp-development-limit: unsupported-transaction-composition` instead of `400 malformed-request`. A defect with a determinate normative answer is reported as an indeterminate private gap, contradicting root acceptance ("Unsupported preflight must still finish later unambiguous shape/key checks before principal and gap return") and the new progress note ("Complete known carrier shapes, labels and key grammar are checked before principal authorization"). No key, receipt or effects are created either way, and the Selector gap itself is correctly deferred (`:167-169`) — only the depth gap is eager.
*Repair:* move the root/member closed-shape checks (`:144-151`, plus `prepareSetShape`/`prepareResourceBatch`) ahead of `losslessText(root)`, or record the depth refusal and continue as `validateSetSelector` does; add a discriminating over-depth × malformed-member case to `transaction-http.test.ts`/`transaction-submission.test.ts`.

**2. Low — `problem.pointer` still absent for identically locatable non-set receipt failures, and the remaining gap is undisclosed**
*Location:* `packages/server/src/transaction-batch.ts:928-941` (RU numeric admission) and `:673-681` (`applyResource` failures), versus the new set mappings at `:822`, `:854`, `:906`; doc at `docs/design/transaction-implementation-progress.md:1480-1486`.
*Issue:* bdp.md 5258–5262 makes the pointer obligation conditional on locatability, not on operation kind. An ordinary batch `updateBead` member with `propertiesChange:[{"op":"remove","path":"/missing"}]`, or a non-round-tripping number under `propertiesChange`, still yields `validation-failed` with no `pointer`, while the identical cause expressed as `updateWhere` now carries `/operations/N/change/0/path`. The plan/F6 deliberately scoped the repair to sets, so this is a disclosure gap, not a scope violation — but the S2a note records the repair and adds "Shared evaluator behavior is unchanged" without naming what remains unmet.
*Impact:* A reader of the progress doc can conclude the conditional-pointer contract row is satisfied; it is satisfied only for set failures. F6 explicitly directs reporting scope rather than leaving the requirement silently waived.
*Repair:* add one sentence to the S2a section stating that ordinary Resource-operation receipt failures still omit `pointer` for locatable causes and that the shared RU/evaluator mapping needs separate scope.

**3. Low — set singleton bodies are shape-validated and re-serialized twice per request**
*Location:* `packages/server/src/transaction-batch.ts:199-203` together with `:158-166`.
*Issue:* For `update-where`/`delete-where` singletons, `prepareSetShape` runs at `:201` and again from `prepareMixedTransaction` at `:165`. Each call re-serializes the synthetic Resource body via `transactionInputText` and re-runs a full `prepareReadUpdateSingleton` syntax parse (`transaction-set.ts:79-94`), so one singleton costs four lossless walks (`:198`, two synthetic, `:143`) and two full RU parses where two walks and one parse suffice.
*Impact:* roughly 2× pre-admission parse/validate/allocation CPU for set singleton bodies up to the 64 KiB cap, on the one route whose unbounded-work profile this increment is explicitly instrumenting. No observable behavior difference.
*Repair:* before wrapping, check only what the wrapper cannot — reject `operation`, `name`, `idempotencyKey` and any other non-set member of the raw body (preserving the "never let `body.operation` override the route" guarantee the `:201` call exists for) — and let `prepareMixedTransaction`'s `prepareSetShape` be the single authoritative shape validation.

**4. Low — no regression test pins "sets are forbidden as sequence members"**
*Location:* `packages/server/src/transaction-http.test.ts` (sequence cases at `:399-420`), `transaction-set.test.ts` (no `sequence` reference).
*Issue:* The plan keeps "Sets remain forbidden in sequence" as an invariant of this change. The behavior is currently correct — the sequence route parses with `prepareReadUpdateSequence` (`transaction-http.ts:312`), whose `sequenceRequest` carrier union excludes the set roots, yielding `400` — but nothing asserts it, while `updateWhere`/`deleteWhere` are now accepted discriminators in the adjacent mixed parser.
*Impact:* a later consolidation of the sequence route onto the mixed parser would silently admit set members (and `prepareTransactionSequence` has no set handling at `:236-280`) with no test to catch it.
*Repair:* add one case posting `{"operations":[{"operation":"deleteWhere",…,"idempotencyKey":"m"}]}` to `targets.sequence` and assert `400` with no key/receipt rows.

**5. Low — superseded present-tense claims in the progress doc are not retracted**
*Location:* `docs/design/transaction-implementation-progress.md:722` ("The normal batch, singleton and HTTP preparation paths still refuse sets"), `:390` ("Unsupported set operations and excessive private depth return an explicit development-limit result"), `:359` and `:583` (set operations listed as remaining/open).
*Issue:* The S2a section states the new reality but only marks historical *budgets* as superseded ("Historical larger-budget evidence above remains historical"), following the file's existing supersession convention (e.g. `:736-738`). The set-refusal and development-limit-ordering statements now read as current.
*Impact:* the file assigned to record the exact supported subset carries contradictory current-tense statements about whether sets are served and when the development limit is returned relative to principal.
*Repair:* add explicit supersession pointers for `:390` and `:722` in the S2a section, in the same form already used for the budget text.
