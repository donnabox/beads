## Regression-test meaningfulness

The new test (lands after base `:457`) is a genuine two-sided guard, and each fix is independently pinned:

- **Red at base for N1:** v1 iteration — `carrierBlocker` set ⇒ base `dependencyReady(first)` is `false` ⇒ `second.blockedPrerequisites === [first.id]` ⇒ `rows.every(length === 0)` fails.
- **Red at base for N2:** v2 iteration — base rule ignores version at non-Read ⇒ readiness `carrier-unsupported`, not `ready-unexecuted`.
- Reverting either fix alone still fails exactly one iteration; they are not co-dependent.
- The fixture is real, not invented: filtered RU rows resolve to `read.discovery.scope-service-desc` (`requests`-form) and `read.discovery.canonical-navigation` (`requests`-form, no `actions` key, so the injected `requests` override is the one `(row.actions ?? row.requests)` reads). Both declare `setup.requires: ["public-http"]` ⊆ the 18 fixture capabilities, `applicability.requires: []`, `setup.fixture: "reference-read-v1"` = derived `fixtureId`; catalog positions 0 and 2 satisfy `earlier`. `own`'s key set `{id, method, target, headers, captures, assertions}` ⊆ `REQUEST_KEYS`, so the v2 `reportExactUnknownKeys` pass (`executable-manifest.ts:910-911`) has nothing to reject; `[dependency, own]` satisfies both "prerequisite requests must precede own requests" and "at least one owned request". `rows` is exactly 2 by construction (ids come from `selected.required`, so a non-selected id would throw rather than silently vacuum the `every`).
- `claimEligible:false` is asserted in both iterations; no admission path, served target or observation is claimed anywhere.

Weaknesses in the new test, all minor:
- `expect(plan.unobservedIds).toHaveLength(selected.required.length)` is tautological — `unobservedIds` is `requirements.map(id)` and `requirements` maps `selection.required`. It can never fail. (Same shape as the pre-existing `:451`.)
- The N2 guard is a ternary inside a test named only for N1 ("does not turn supported prerequisites into blockers…"), so an N2-only regression reports under a misleading name.
- The `read` + `manifestVersion: 2` cell — newly adjacent to a version-sensitive condition — is pinned by no test; `:289-311` covers `read` only with `catalogId: "unadmitted-v1"`.

## New findings

**NEW‑1 (LOW, fail-open mirror gap) — the v2 Read+Update admission drops the runner's `exactExecution` condition.**
`test-support/profile-contract-plan.ts` patched `:346-352`. The runner admits v2 at `read-update` only when `options.exactExecution` exists and its `configuration.scope`/`profile` equal the run's (`runner.ts:2576-2586`); a stricter runtime gate repeats this for *every* HTTP action whenever `profile !== "read"` (`runner.ts:1384-1398`: `manifestVersion !== 2` or a missing/mismatched binding throws). The planner models no `exactExecution` at all — `grep` finds the identifier nowhere in the module or the design doc. So a future RU v2 manifest planned here reports `ready-unexecuted`, i.e. "supported carrier" per `docs/design/profile-contract-planning.md:49`, for a combination the runner refuses unless the eventual caller also passes a matching binding. Narrow in practice — the plan's own `ServedProfileConfiguration` carries exactly the `scope`/`profile` R3 compares, so a runner invoked with it satisfies the condition — but the direction is now fail-*open*, the opposite of every other gate in this module, and N2's correction traded a false refusal for an unconditional admission. Fix: either carry the condition into the reason/readiness ("carrier admissible only with matching exact execution configuration"), or key the rule on a modeled exact-execution binding rather than profile+version alone.

**NEW‑2 (LOW, doc/code divergence) — the design doc now contradicts the rule it documents, and no lockstep test covers it.**
`docs/design/profile-contract-planning.md:51`: "Current ordinary normative bundles admit only `read-v1`; normative Update/TX carriers therefore remain unsupported in this groundwork." After this patch an RU-profile plan over a v2 `read-v1` manifest is a **supported** carrier and its rows can reach `ready-unexecuted`, so the second clause is false as a statement about the planner. `:47`'s `carrier-unsupported` row also still describes the gate as a "manifest catalog/profile combination", omitting the manifest version the rule now reads. This is a two-file patch; the doc is untouched. The only test that opens this file (`profile-contract-plan.test.ts:226`) parses the 81-row audit table, not the readiness prose, so nothing fails on the drift. Same class of defect as prior finding 2 (behavior moved without its normative description), at much lower stakes.

**NEW‑3 (nit) — the replacement comment no longer explains the refusal the expression still encodes.**
The deleted comment stated the live reason `read-v1` + v1 is blocked at non-Read profiles; the new one explains only the v2 RU admission. A reader of patched `:343-352` cannot derive why `read-v1`/v1/`read-update` is refused, which is the branch the pre-existing tests at `:268-288` and `:289-311` actually exercise. One clause restoring the `runner.ts:2559-2566` refusal would make the comment match the rule.
