## Findings

**1. LOW — `capture` is now retained in memory by every `DevelopmentContracts` consumer, including the Read+Update path**
`packages/server/src/development-contracts.ts:138-143`
Before this commit the ingest candidate's `bytesBase64` entries became unreachable once `compileDevelopmentContracts` returned; the frozen object kept only `descriptors`/`types`/`registry`/`identity`. They are now strongly retained for the object's lifetime — and `installed-reference-configuration.ts:147` compiles through the same factory while separately keeping its own utf8 copies at `:151-159`, so an RU reference authority now holds two in-memory copies of the schema closure (≈1.34× base64 plus 1× utf8, up to ~38 MiB at the 16 MiB ceiling). Impact: unstated retention growth on a path the plan listed as untouched; report:24 attributes "full capture persists for installation lifetime, no artifact GC" to the TX *persisted row*, and the progress note repeats only that framing. No correctness effect — nothing serializes the contracts object and `artifactIdentity` is unchanged.
Fix: say so in the progress-note paragraph that introduces the accessor, and/or have `installed-reference-configuration.ts` read its hosted schema bytes from `contracts.capture.artifacts` instead of keeping a second copy.

**2. LOW — the "offline-only schema URI" resolution is documentation, not a constraint**
`packages/server/src/transaction-store.ts:185-195`
The plan's schema-hosting LOW was dispositioned as "external synthetic schema URI is offline-only" (plan:215) and the fixture honours it (`https://offline.invalid/...`). But the bridge places no constraint on `propertiesSchema`: a compiled TX installation may pin `{scope}schemas/object`, and `transaction-http.ts` has no schema route, so the served Type descriptor would advertise an in-Scope URL that 404s. Contrast `installed-reference-configuration.ts:151-159`, which both requires `{scope}schemas/` and actually hosts the bytes. Failure scenario: a later TX fixture or caller supplies a scope-local `propertiesSchema`; Type GET succeeds, the advertised schema reference is dead, and nothing refuses.
Fix: one line mirroring the locality check — refuse any `propertiesSchema` starting with `${scope}` in the compiled branch — or record the unenforced convention explicitly in the progress note.

**3. LOW — the shared module's own tests were not extended, and the identity witness is a same-commit re-derivation**
`apps/bdptest/src/development-contracts.test.ts` (unchanged); `packages/server/src/transaction-installed-contracts.test.ts:156-187`
Plan:118 and plan:217 require the shared compiler's existing tests to verify immutable capture and unchanged identity. That file has no `capture`, `isFrozen` or key-count assertion and is not in the diff; all capture evidence is TX-owned. Separately, report:14-15's "witnessed against the independent previous identity calculation" overstates what exists: test `:160-170` re-derives the identity with the same expression added in the same commit, and no committed artifact or test pins a prior value (`scripts/installed-reference-observation.mjs:65` and `apps/bdptest/test-support/installed-contract-identity.ts:3` only match the `development-schema5-<64 hex>` shape; `read-update-matrix.test.ts:227` compares two values from the same run). Failure scenario: a later RU-side edit folds `capture` into `identity` or loosens its freezing — caught only by a transaction test, and no pinned digest fails.
Fix: add a capture-immutability + identity assertion to `apps/bdptest/src/development-contracts.test.ts`, and either pin one literal reference identity or soften the report wording to "re-derived against the unchanged expression".

**4. LOW — `configurationIdentity` still has no byte bound, while the capture now does**
`packages/server/src/transaction-store.ts:213-221,505`
`configuration` embeds the whole installed inventory and is handed to Read verbatim as `configurationIdentity`, which `authority-read.ts:269` `.trim()`s on every read-entry capture. The capture got an explicit finite cap in response to the plan's HIGH; the inventory text did not, and is now bounded only by the artifact ceilings this slice brings into play (≤4096 descriptors × ≤1 MiB ⇒ a multi-GiB string copied per read request). Test `:257-259` asserts `< 4096` bytes, which is a fixture fact, not a bound. Pre-existing in kind — schema-free `options.types` was never bounded either — but this slice is what makes large descriptor artifacts reachable.
Fix: bound the serialized `configuration` the way the capture is bounded, or record the asymmetry next to the capture bound in the progress note.

**5. LOW — predicate 3's identity rollback is unasserted; no rolled-back id is re-created**
`packages/server/src/transaction-installed-contracts.test.ts:217,235-240`
The test checks the `resources` table and the absence of page plans, but never the `identities` table, and the follow-up valid write uses a fresh id (`beads/later`) rather than re-creating `beads/tentative`. The mechanism looks right — `INSERT OR IGNORE INTO identities` is inside the `effects` savepoint (`transaction-store.ts:996`) and `:1048` does `ROLLBACK TO effects` — but a leak would make a never-committed id permanently unusable via `identity-taken`, and this slice is the first to reach that rollback through `validation-failed`. Plan predicate 3 names "identities" and "a new valid key succeeds".
Fix: after the failed batch, re-create `beads/tentative` under a new key and assert it completes.
