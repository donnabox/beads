## Contract to preserve or decide

The recommended organizing rule is `bd` for Beads, `bd link` for Links, `bd dep` for Dependency Link conveniences, and `bd graph` for views. It is a namespace rule, not a claim that every flag is symmetric. A local bare ID resolves as `beads/ID` in Bead commands and as `links/ID` in `bd link` commands; canonical path and URL handling should be specified and tested per route. Keep ordinary Issue task-management commands Issue-specific. No Preview 1/2 compatibility promise or in-place migration is required for Preview 3; compare shipping-product Issue behavior separately and record deliberate exceptions. Do not admit a graph command merely because it has a Cobra registration: the closed front door and per-route `graphPreviewFlags` are deliberate safety boundaries (`graph_preview.go:356-399`).

## Relationships, graph and Type boundaries

* **Dependency versus general Link.** Keep `bd dep` only for Dependency Links and `bd link` for every admitted Link Type. P2 `bd dep add ISSUE BLOCKER [--type KIND]` and `bd link SOURCE TARGET [--type KIND]` create native Issue-to-Issue Dependencies. P2 narrows `KIND` to well-known values, while the ordinary source `cmd/bd/link.go:48-85` checks only `types.DependencyType.IsValid()`; this is a **source-level potential compatibility exception**, not yet a shipping-binary result. A single ordered pair carries at most one native Dependency for now, per Donna's prior decision. The meaning of `blocks` and `parent-child` remains distinct in native Issue projections; do not collapse semantics merely because they share a nominal P2 Dependency Type (`graph_preview_workflow.go:75-153`).
* **Removal.** P2 `bd dep remove ISSUE BLOCKER` is a blocks-pair operation with absent-pair no-op; non-blocking Dependency deletion is by canonical Link ID (`graph_preview_workflow.go:175-215`; `internal/storage/graphstore/dependency_unlink.go:17-92`). P2 `bd link delete LINK --force` is the all-Link ID route. Decide any generalized pair removal only after Type/arity and pair-uniqueness rules are explicit.
* **Views.** P2 `bd dep list` is human, blocks-only; `--json` refuses (`graph_preview_structure.go:12-59`). `dep tree/cycles`, default `bd graph ISSUE`, and `bd graph check` project blocking Dependencies and refuse unsupported layouts/row caps (`graph_preview_dependency_views.go:50-125,145-240`). `bd graph BEAD --view generic` traverses current Link edges from an Issue or Memory root, with explicit `--direction`, `--depth`, `--max-nodes`, `--max-links` bounds and structured `--json` (`graph_preview_generic.go:28-91`). **Decision:** keep default graph Issue-centric for shipping familiarity or make generic view the default in P3; do not silently change it as part of Link parity. `bd link query/search` remain absent, with no proposed implicit substitute.
* **Types.** P2 `bd types` is a useful effective-selector display, while persisted installed descriptors remain fewer and different (`graph_preview_types.go:25-115`). Trish owns the Type/metatype, constraints and install semantics. CLI Wave A may validate existing selectors and error precedence, but should not hard-code a new registry or schema that preempts her work. When her contract lands, test `bd types` human/JSON agreement about **which values are selectors versus installed Type identities**.
* **Link References and lifecycle.** Trish's accepted Link Reference/arity rules must govern both `bd link` and `bd dep` through one domain writer. Validate per-kind arity independence, duplicate-pair conflicts, allowed endpoint categories, deletion/incident rules and cycle/readiness effects before widening CLI admission. The present P2 implementation does not establish the final P3 constraints.

## Questions for Donna's morning design pass

1. Should `bd count` remain Issue-only for shipping compatibility, or should Preview 3 give it an all-Bead mode? If changed, what is the default and how is Issue-only counting selected?
2. Is `bd update links/PATH` an intentional alias to retain, or may Preview 3 make `bd link update` the only Link edit path?
3. Do we keep `bd graph ISSUE` as the default blocking view and require `--view generic` for mixed graphs, or should a Bead root default to generic traversal?
4. Should `bd dep list` remain the familiar blocks-only human view, or enumerate all Dependency kinds with typed filters and JSON? Relatedly, should pair removal stay blocks-only?
5. May Dependency Link properties/metadata be updated in P3, and if so which fields belong to the native Issue/Dependency writer versus common Link metadata? Defer implementation until Trish's schema and Polly's provenance contract answer this.
6. Is Link query/search in the P3 cutline, or is filtered `bd link list/count` enough? The former needs a separate predicate/index/output contract.
7. Which exact shipping-product output/flags are compatibility requirements for Issue paths, and which are deliberately replaced by complete-record formats? Wave 0 should bring concrete diffs rather than ask this in the abstract.

The first four questions can be decided from CLI behavior. Questions 5–7 benefit from Trish/Polly's accepted model and the binary comparison. Unanswered decisions block only their dependent wave.
