## Low — the new equality guard is unreachable in every real composition

`packages/server/src/transaction-runtime-configuration.ts:327-328`

`actual.scopeSnapshot` (built at `transaction-store.ts:539-542`) and `settings.scopeSnapshot` (built at `transaction-runtime-configuration.ts:89-92`) read the same two module-singleton bindings from `transaction-snapshot.js`; `limits` is literally the same frozen object on both sides. `metadata()` has exactly one production call site (`transaction-runtime.ts:230`), which passes `owner.readConfiguration()`. So `isDeepStrictEqual` is structurally true by construction and cannot fail outside a hand-forged `actual` — which is precisely what the test at line 448 supplies.

Concrete impact: the guard contributes no protection against the divergence it reads as guarding. A store whose persisted snapshot tuple disagrees with the running build never reaches `metadata()` — it throws `"transaction installation mismatch"` at `transaction-store.ts:503`. The guard is therefore a forward-looking assertion (it would start earning its keep only if a seam or override were ever allowed to set `settings.scopeSnapshot`), not a live cross-check.

Fix (optional, pick one): keep it as a documented forward guard with a one-line comment saying the live divergence is already fatal at open, so a future reader doesn't mistake it for the load-bearing check; **or** make it load-bearing by sourcing `readConfiguration().scopeSnapshot` from `JSON.parse(storedConfiguration).snapshotLimits/.snapshotTokenPolicy` instead of restating the compiled constants — then `actual` really is "actual" and the comparison spans persisted vs. runtime. I'd take the comment; the second option duplicates a guarantee the byte check already gives.

## Low — the new test's identity assertion is a re-derivation, not a binding assertion

`packages/server/src/transaction-runtime-configuration.test.ts:416` and `:425-437`

Line 416 (`expect(actual.scopeSnapshot).toEqual(captured.settings.scopeSnapshot)`) compares two structurally identical objects sharing the same `limits` reference. Lines 425-437 recompute the digest by feeding `captured.settings` straight back into `transactionRuntimeDigest` with the same revision string, so the assertion mirrors the implementation.

Concrete impact: if `scopeSnapshot` were dropped from the digest input (e.g. a future change filters `settings` before hashing), this assertion still passes — it only re-derives whatever the implementation did. The failure is caught instead by the pre-existing leaf test at line 452. Similarly, line 422-424 (`lifetimeMs !== cursorTtlMs`) asserts that two unrelated compiled constants, 300000 and 1000, differ; it documents intent rather than constraining behavior.

Fix: to make the new test carry its own weight, assert the digest *changes* under a perturbed `scopeSnapshot` — e.g. compare `transactionRuntimeDigest({...sameInput, settings: {...captured.settings, scopeSnapshot: {...captured.settings.scopeSnapshot, tokenPolicy: "other"}}})` against `metadata.runtimeConfigurationIdentity` with `.not.toBe(...)`. The genuinely novel coverage in this test — the frozen assertions at 417-418, the persisted-tuple reads at 419-421, and the two mismatch cases at 438-450 — is worth keeping as is.
