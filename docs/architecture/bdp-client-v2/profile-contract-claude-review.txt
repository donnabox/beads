# Findings

## 1. HIGH — The closed served-configuration mismatch binding is bypassable: two different targets compare equal
**Location** `packages/conformance/test-support/profile-contract-plan.ts:158-175` (validation) and `:178-187` (`assertSameServedProfileConfiguration`)

**Evidence** The digest/commit fields are validated by regex (`/^[0-9a-f]{64}$/.test(input[key])`), which coerces via `toString()`, while equality is decided by `canonicalJson`, which serializes a prototype-only object as `{}`. I ran the `abdd1d4` function verbatim:

```
A: BYPASS - two different policyDigests accepted as the same target
   canonicalJson(policyDigest) for both = {} / {}
B: reads=2  validated=a*40, stored="deadbeef"
C: boxed fixtureDigest accepted
```

A: `policyDigest: Object.create({toString(){return "1".repeat(64)}})` vs `"2".repeat(64)` — both pass validation, both canonicalize to `{}`, `assertSameServedProfileConfiguration` returns without throwing. Same hole for `sourceCommit`, `installedPayloadDigest`, `installedContractsDigest`, `authenticationDigest`, `fixtureDigest`. (`scope` is protected by `url.href !== input.scope`; `fixtureId` by its `typeof` check.)
B: validate-then-copy. `freeze({ ...input, … })` at `:175` re-reads every field *after* validation, so an enumerable getter passes the regex on read 1 and stores a different value on read 2.

**Impact** This is exactly the property the design doc sells (`profile-contract-planning.md:21`, "refuses to combine records differing in any field") and the report's "Mismatches in any field refuse combination". At `abdd1d4` a launcher can combine a plan built against one installed payload/policy/auth/fixture identity with an execution against another, and the plan's own `configuration` can hold values that never passed validation. Everything the binding exists to prevent.

**Fix** Already fixed, post-freeze, by `9ea4089` (`configurationData` + `primitiveString` + `capabilitySnapshot`: own-data-descriptor capture, proxy/accessor/boxed rejection, detached copy before validation). That commit is outside the reviewed range and outside the report's declared frozen artifact — it needs its own review, and the report's "Validation"/"Delivered" sections should stop describing `abdd1d4` as the frozen deliverable.

## 2. HIGH — The new retirement edge has no normative spec basis and falsifies the spec's inheritance sentence
**Location** `packages/conformance/catalog/read-update-v1.json:16`; `docs/specs/bdp.md:6798-6823`; `packages/conformance/src/read-update-catalog.test.ts:75-88`

**Evidence** The spec enumerates retirements normatively, and only TX→RU: *"A Transactional claim inherits the Read rows and the Read+Update rows whose obligations the profile preserves … and retires the twelve Read+Update rows the profile contradicts … The retiring row names them in its `retires` member"* + twelve bullets (6798-6819). `#### Read+Update conformance rows` (6698-6704) declares no retirement at all. After this change I measured `retiredScenarioIds(combined, "transactional")` = **13** ids, one of them a Read row. The TX catalog test enforces the spec text bullet-by-bullet (`transactional-catalog.test.ts:204-228`, including `expect(boundedSection).toContain("retires the twelve\nRead+Update rows")`); `read-update-catalog.test.ts` asserts *nothing* about `retires` — it mirrors ids only.

**Impact** The catalog is now sole authority for a cumulative-selection rule the normative spec does not state and, as written, contradicts. The report's "No spec change required" (line 19) is wrong. The asymmetry also means the RU edge has no erosion guard, in a repo whose test comments exist specifically so this "cannot erode silently".

**Fix** Either (a) add the declared bullet under `#### Read+Update conformance rows`, amend 6798-6801 to "twelve Read+Update rows and one Read row", and add the mirroring assertion to `read-update-catalog.test.ts`; or (b) hold the catalog edge until that spec change lands. Note the retirement *reasoning* is sound — `read.discovery.document` asserts "These are the only members admitted by the closed `readDiscovery` definition" and that `aliases` is conditional, both false at RU — the defect is that only a design doc says so.

## 3. HIGH — The retirement drops the only row binding "An omitted `order` means `canonical-uri`" from the RU and TX sets
**Location** retired row `packages/conformance/catalog/read-v1.json:18` (second citation); replacement `read-update-v1.json` `read-update.discovery.document`

**Evidence** I scanned every citation in all six catalogs: that sentence appears in exactly one row, `read.discovery.document`. `read.collections.beads`/`.links` bind only that `canonical-uri` ordering MUST be supported and how it compares — not the discovery default. The replacement row's single citation says only that `order` is "optional under their inherited contracts", a pointer rather than a binding. `maximumEndpointMultiplicity`'s optionality survives only as the same passing mention.

**Impact** A normative default silently leaves the RU and TX required sets — the precise "missing mandatory row" the audit was supposed to rule out. The derived counts (129/250, which I independently recomputed and confirm) hide it, because one row left and one arrived.

**Fix** Carry the orphaned citation into `read-update.discovery.document` (or a new `read-update.discovery.order-default` row) before retiring, and add a guard: for every retirement edge, assert each citation of the retired row is still bound by some row selected at the retiring profile. That test would have caught this.

## 4. MEDIUM — `ready-unexecuted` is reported for manifest/profile combinations the runner categorically refuses
**Location** `profile-contract-plan.ts:231-252`, `:262-269`; test `src/profile-contract-plan.test.ts:198-227`; guard `src/runner.ts:2557-2585`

**Evidence** The planner never reads `manifest.manifestVersion` or `manifest.catalogId`, though `parseExecutableScenarioManifest` requires both (`executable-manifest.ts:466-470`) and `createBoundArtifactBundle` enforces the catalogId↔catalog binding (`artifact-bundle.ts:143-147`). `validateRunOptions` throws `"read-v1 executable scaffold currently supports targets advertising the Read profile only"` for (v1, `read-v1`, profile ≠ read), and for manifestVersion 2 throws unless the profile is `read` or `read-update` — so Transactional is refused outright. The new test feeds `matrices/read-v1.json` (v1, `catalogId: "read-v1"`) with a `read-update` selection and asserts `read.discovery.scope-service-desc` → `ready-unexecuted`.

**Impact** The readiness vocabulary the doc defines as honest ("A future runner may attempt it", `profile-contract-planning.md:48`) is asserted for combinations no runner can attempt, and the one case is pinned by a passing test. A TX plan will report ~250 `ready-unexecuted` rows for a profile the runner refuses to start.

**Fix** Validate `catalogId`/`manifestVersion` against the selection and mirror `runner.ts`'s admission guards, or add a distinct readiness (`carrier-unsupported`) rather than folding it into ready.

## 5. MEDIUM — Readiness ignores `prerequisiteScenario`, and this retirement makes nine inherited Read rows unsatisfiable at RU/TX
**Location** `profile-contract-plan.ts:255-273`; `runner.ts:320-324`, `:2744-2781`

**Evidence** Measured against `matrices/read-v1.json`: nine rows name `read.discovery.document` as an action prerequisite — `read.collections.beads`, `.links`, `.structural-predicates`, `read.types.inventory`, `read.http.get-head`, `.method-405`, `.cache-cors`, `read.alias.resolution`, `.absent`. `selectApplicableScenariosForProfile` drops a retired row from `selected` with no error (only ids absent from the *catalog* throw, `runner.ts:321-324`), and `prerequisiteResultBeforeRun` then returns `harness-error`/`not-run` with `"prerequisite was not selected or did not run"`. The planner inspects only `setup.requires`/`applicability.requires`, so all nine would be reported `ready-unexecuted`.

**Impact** Directly on the stated next step (U1's cumulative RU manifest). A cumulative run reusing the existing Read realizations converts nine inherited Read obligations into harness errors, after a plan that called them ready. Latent today only because `runner.ts:2557` blocks that manifest at non-Read profiles (finding 4).

**Fix** Classify a row whose prerequisite is retired, unplanned or not-ready as not ready; add a test planning the real Read manifest at profile `read-update`.

## 8. MEDIUM-LOW — Fixture identity and capabilities are three unverified caller claims, where the package already derives them from fixture bytes
**Location** `profile-contract-plan.ts:116-120`, `:250-253`; compare `cohort-artifact.ts:448-466` and `artifact-bundle.ts:110-113,148-155`

**Evidence** The manifest is consumed as bytes and parsed; the fixture is three independent strings (`fixtureDigest`, `fixtureId`, `capabilities`) with no cross-check. `deriveReadCohortNotApplicableRows` computes the identical applicability classification and documents the opposite discipline: *"Derived, never supplied; the verifier recomputes it from the committed catalog, manifest, and fixture bytes."* `createBoundArtifactBundle` parses the fixture, computes `fixtureDigest` from its bytes, and checks `setup.fixture === fixture.id`.

**Impact** `capabilities` alone decides `setup-unavailable`/`applicability-unresolved` vs `ready-unexecuted`, so the one output property the doc insists on — "never turns missing fixture capability into an automatic N/A or pass" — rests entirely on launcher honesty, while the hardened derivation sits in the same package.

**Fix** Accept the factory-created `ConformanceArtifactBundle` (or the fixture source bytes) and derive `fixtureId`/`fixtureDigest`/`capabilities` from it.

## 9. LOW — Scope validation diverges from the runner's canonical-scope predicate
**Location** `profile-contract-plan.ts:146-155` vs `runner.ts:3100-3110` + `isCanonicalUrlPath` `:3230-3244`

**Evidence** Measured: `http://127.0.0.1:43210/a%2fb/`, `http://127.0.0.1:43210//x/` and `http://127.0.0.1:43210/%7Ea/` all pass `bindServedProfileConfiguration` and all fail `isCanonicalScope` (which rejects `%2f`/`%5c`, empty segments, and needless encoding of unreserved characters). Separately, `fixtureId` and `capabilities` skip the repo's `ARTIFACT_ID_PATTERN`/`BINDING_ID_PATTERN` and accept untrimmed strings — `" reference-read-v1 "` binds fine and can then only ever produce `manifest fixture mismatch`.

**Impact** A "closed" binding that admits Scopes the executing runner rejects, and identities no manifest can name.

**Fix** Export and reuse `isCanonicalScope` and the existing id patterns.

## 10. LOW — Manifest bytes bypass the package's hardened source boundary
**Location** `profile-contract-plan.ts:231-238`, `:278` vs `artifact-bundle.ts:306-329` (`copySourceBytes`) and `parseBoundedJson` (1 MiB, depth 128, 100k nodes, 10k container entries)

**Evidence** `Uint8Array.from(execution.manifest.bytes)` accepts any array-like/iterable and coerces elements mod 256 (`300 → 44`), so `manifestDigest` can hash coerced bytes while the doc promises "exact executable manifest bytes". No size or JSON-shape bound is applied. `copySourceBytes` deliberately uses intrinsic `byteLength`/`Symbol.toStringTag` getters precisely to reject a non-`Uint8Array` lookalike — the threat model this module reimplements more weakly. Separately, `freeze` (`:288-294`) recurses with no cycle guard; unreachable with current inputs.

**Fix** Export `copySourceBytes`-equivalent validation and use it before decoding and hashing.
