## Findings

**F1 — Medium. The TX sidecar destination is unnamed and lands in the RU sidecar namespace, with no freshness refusal on the TX path.**
`context/plan2/lifecycle-and-adapters.json:5` makes `BDP_PRIVATE_PROFILE_EVIDENCE_PATH` the sidecar *base* producing `.profile.attempt.json`/`.profile.json`. `:13` says only "Optional private carrierPath scalar remains positive-only" — plan1 said "from same opt-in env" and plan2 deleted that clause without naming any replacement (`deltas/lifecycle-and-adapters.json.patch:14–15`). `vitest.config.ts:66` collects both `apps/**/*.test.ts` files, so the RU positive callback (`read-update-matrix.test.ts:2563`) and the TX positive callback (`transactional-matrix.test.ts:385`) run in one `vitest run`, in parallel workers, under one process env. The only destination-existence refusal is the writer constructor list at `read-update-artifact-execution.ts:348–356`, which covers only `filename`, `${filename}.attempt.json` and `${filename}.<shardId>.json`; `replaceFile` takes `wx` on the randomUUID temp only (`:410`) and then `renameSync` overwrites the destination unconditionally (`:411`). TX has no constructor and `:13`/`TX.*` state no collision refusal at all.
*Consequence:* under the opt-in, the RU and TX carriers silently overwrite each other's `.profile.json`/`.profile.attempt.json`, and a stale sidecar from a prior run is overwritten even in the RU-only case. L10 ("no existing file overwritten", `source-data-cases.json:437`) is unachievable on the TX path.
*Smallest correction:* in `lifecycle-and-adapters.json:13`, name a distinct TX-only source for `carrierPath` (a separate variable, or a mandatory per-profile suffix on the shared base), and add to both `:5` and `:13` an explicit `existsSync` refusal over the exact new destinations before any new output, mirroring `read-update-artifact-execution.ts:348–356`.

**F2 — Medium. The authored-assertion join rule across `exchanges[]` and `actions[]` is unspecified, so `authoredAssertionsAllPassed` can be computed from the wrong assertion set.**
`context/plan3/output-schema.json:28` requires `authoredAssertionInventoryDigest` and `authoredAssertionsAllPassed`, and `verification-order.json:21,37` require "full authored action/assertion bindings" and honest credit. Authored IDs are `${action.id}.${assertion.id}` for RU (`read-update-artifact-set.ts:249`) and `${a.id}:${x.id}` for TX (`profile-contract-plan.test.ts:326`), i.e. keyed by manifest action. In the report, an http action's authored outcomes land on the matching `exchanges[].assertions`, but a programmatic action's authored outcomes land **only** on `actions[].assertions` (`runner.ts:1103–1118`) — and an exchange with the *same* `request.id` also exists for that action, carrying a different assertion set (`transactional-matrix.test.ts:544–555`, and the explicit split at `:1287–1291`). Both profiles contain client-family actions (`read-update-artifact-execution.ts:49–57`).
*Consequence:* an exchange-first lookup silently reads the wrong assertions for every client action and can report `authoredAssertionsAllPassed: true` from assertions that are not the authored ones — precisely the "no count or assertion list proves its own semantic adequacy" failure the plan forbids.
*Smallest correction:* add to `verification-order.json` n=5/n=9 that each authored joined ID resolves its outcome by the manifest action's `family` — `actions[]` for non-http families, `exchanges[]` for http — and that `authoredAssertionsAllPassed` is `true` only when every authored ID resolves to `passed:true`, `false` when any resolved outcome is `passed:false`, and `null` when any authored ID has no resolved outcome.

**F3 — Medium. Where a rejected or absent TX handoff surfaces is contradictory; as written it can fail the existing TX positive test.**
`lifecycle-and-adapters.json:22` says "Reject mutated hook data or missing/invalid handoff when carrierPath set"; `:23` and `plan.md:19` say the same situation "preserve[s] fixed failed/pending attempt with rawWrapper unavailable". The handoff and its acceptance sit immediately after `control?.onObserved?.(observed)` inside `observe`'s try block (`transactional-matrix.test.ts:358–361`); anything thrown there is captured as `failure` and rethrown at `:380`, so `observe` never returns and the 17-partial assertions at `:421–643` never run.
*Consequence:* the two clauses specify different behaviours. One implementation aborts the existing positive TX product test over a carrier-only problem — a change to existing behaviour under the opt-in, against "Legacy-only bytes/field order/output/default behavior remain unchanged"; the other records unavailability. Nothing in the plan decides it.
*Smallest correction:* state in `TX.singleSerialization.acceptance`/`failure` that a rejected or absent handoff never propagates out of `observe` — it records `rawWrapperSha256: null` plus the fixed `evidence-mismatch`/`invalid-report` attempt state while `observe` still returns the genuine `{result,sessions,baseline}` — or, if aborting is intended, say so explicitly.

**F4 — Low. Comparison semantics for the pre-hook capture versus the parsed handoff bytes are unspecified.**
`lifecycle-and-adapters.json:22` compares an in-memory capture against values recovered from `JSON.stringify(...,null,2)` (V06 at `source-data-cases.json:59`, R20 at `:238`). JSON omits `undefined`-valued members and does not preserve key order, and `isDeepStrictEqual` — the house idiom (`read-update-artifact-execution.ts:4,90`) — treats `{a:undefined}` and `{}` as unequal. Current shapes happen to round-trip cleanly (`runner.ts:3174–3183` and `:1171–1180` use conditional spreads; `installedTransactionBinding` returns only JSON scalars, `transactional-execution-binding.ts:85–90`), but the plan does not pin that property.
*Consequence:* a later shape change produces a false `evidence-mismatch`, which under F3 can abort the TX positive callback.
*Smallest correction:* specify the comparison as equality of `canonicalJson(JSON.parse(JSON.stringify(preHook)))` against `canonicalJson(parsed.result/.sessions/.baseline)`, not raw structural deep-equality.

**F5 — Low. `copySourceBytes`/`parseBoundedJson` cannot be reused for report wrappers without naming a `kind`.**
`input-schema.json:24,26` and `budgets-and-secrecy.json:18,21` require reusing these helpers for a 4 MiB report wrapper, but both take `kind: keyof ConformanceArtifactBundleSources` = `"catalog"|"manifest"|"fixture"` (`artifact-bundle.ts:393,430`); there is no report kind, and the 4 MiB allowance exists only as `CUMULATIVE_MANIFEST_MAX_BYTES` (`:19`). The `kind`/label also appears verbatim in the thrown `ConformanceArtifactBundleError` message (`:405,409,438,442`).
*Consequence:* an implementer either widens `packages/conformance/src/artifact-bundle.ts` — a fifth file outside `footprint.json`'s four owned paths — or passes a misleading `kind` whose text can leak through an error path that `error-contract.json:15` forbids echoing.
*Smallest correction:* state in `input-schema.json` that report wrappers reuse `copySourceBytes(source,"manifest",4194304)` and `parseBoundedJson(bytes,"manifest",label)` unchanged, and that the carrier catches `ConformanceArtifactBundleError` and re-raises `ProfileEvidenceError` `capacity`/`invalid-source` without the message.

**F6 — Low. `maxWorkers 2` is stated as if it were an existing default.**

*Smallest correction:* in `validation-plan.json:11`, state that `--maxWorkers=2` is a command-line flag for the source-validation invocation only and that `vitest.config.ts` remains unmodified.
