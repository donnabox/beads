## Verdict

**No confirmed code blocker.** The implementation changes are defensible as written. One **confirmed test defect** (an assertion that cannot fail on the thing it claims to guard), one **conditional correctness risk** that becomes a blocker only if `types.Issue` cloning is shallow, and one **classification/doc consistency** issue worth resolving before landing. Runtime evidence is pending for all of it — nothing below assumes a test ran or passed.

Review was diff-only: no repo traversal, no tools, no files modified, no tests. Claims about code outside the diff (clone depth, JSON tags, exit-code constants, wrapper classification) are marked as unverified, not asserted.

---

### 1. MEDIUM (confirmed) — label-dedup test cannot detect caller aliasing, the exact invariant it asserts
`internal/storage/graphstore/legacy_import_test.go:77` (`TestLegacyImportLabelSetAndInternalState`)

**Defect.** Input is `{"two","one","two"}` — the duplicate is the *last* element. If `prepared`'s `Labels` shares a backing array with the caller's slice (see finding 2), the in-place filter writes `A[0]="two"`, `A[1]="one"`, skips index 2. The array is byte-identical to the original, so `reflect.DeepEqual(issue.Labels, []string{"two","one","two"})` passes **whether or not the caller was aliased**. The assertion is a tautology for this input.

**Impact.** The "preserving source caller" guarantee is untested. A shallow clone — now or after a future refactor of the clone helper — ships silently.

**Fix.** Use an input where dedup shifts a later distinct element forward, e.g. `{"one","two","one","three"}` → expect prepared `{"one","two","three"}` and caller unchanged at `{"one","two","one","three"}`. Under aliasing the caller's slice becomes `{"one","two","three","three"}` and the test fails as intended.

### 2. MEDIUM (conditional) — in-place `issue.Labels[:0]` filter is only safe if the clone deep-copied the slice
`internal/storage/graphstore/legacy_import.go:306` (`labels := issue.Labels[:0]`)

**Defect.** `[:0]` reuses the backing array. The comment says "normalize the isolated copy," but a struct-level clone (`cloned := *issue`) copies the slice *header*, not the array — the clone and the caller's `Issue` then share storage, and `append` into `labels` overwrites the caller's elements.

**Impact.** If any clone on this path is shallow for `Labels`, a direct SDK caller's input slice is mutated in place (reordered/duplicated elements) by a function documented as non-mutating. Unverifiable from the diff — the clone site is not shown.

**Fix.** Remove the dependency instead of auditing it: `labels := make([]string, 0, len(issue.Labels))`. One allocation per issue, bounded by the existing 1000-resource ceiling, and the aliasing question disappears permanently. (Also note the dedup runs *before* `issue.SetDefaults()` — if `SetDefaults` ever normalizes label case or trims, re-introduced duplicates bypass the set. Ordering it after `SetDefaults` is the safer position.)

### 3. MEDIUM — `sql.ErrTxDone` classified as `outcome_unknown` contradicts the invariant the same test asserts
`internal/storage/graphstore/legacy_import_test.go:362` + `docs/reference/graph-legacy-import.md:76`

**Defect.** The docs now tell users that "cancellation after the driver has ended the transaction" is `outcome_unknown` (exit 6) and that they must "inspect the destination." But `sql.ErrTxDone` means the transaction was already closed — and in this flow nothing closes it with a *successful* commit, so the destination is provably unwritten. The same test asserts exactly that: `reflect.DeepEqual(before, legacyImportState(t, ctx, s))`.

**Impact.** Users get the most alarming exit code and a manual-inspection directive for a case the test proves is clean. That trains people to ignore exit 6, which devalues the genuinely uncertain commit case.

**Fix.** Either (a) narrow the uncertainty to `ErrTxDone`/errors observed from the **commit** call and classify driver-side rollback cleanup as a definite canceled failure, or (b) if Dolt can leave an engine-level partial commit visible before the driver reports `ErrTxDone`, say so explicitly in the doc sentence — right now the doc asserts uncertainty without the reason, and the reason is what makes it credible.

### 4. MEDIUM — `unknown != alreadyDone` over-constrains the test against driver error variance
`internal/storage/graphstore/legacy_import_test.go:362`

**Defect.** The biconditional demands `outcome_unknown` ⟺ `sql.ErrTxDone`. The reverse direction is the problem: any other uncertain cleanup error (a driver "connection closed", a `Rollback` returning `context.Canceled`, a Dolt-specific sentinel) yields `unknown=true, alreadyDone=false` and fails the test even though the classification is correct. It also pins user-facing error identity to a `database/sql` sentinel, which cuts against the storage-boundary rule in `CLAUDE.md` (no public return types leaking driver internals).

Secondarily, if the production classifier's rule *is* literally "`ErrTxDone` → `outcome_unknown`", the assertion restates the implementation's own branch predicate and can only fail if the error chain drops a sentinel — little independent signal for the cost.

**Fix.** Assert the one-way implication that matters (`alreadyDone` ⟹ `unknown`) plus the behavioral consequence already present (state unchanged, cancellation identity retained). Drop the `unknown ⟹ alreadyDone` half, or gate it behind the beads-level sentinel rather than `sql.ErrTxDone`.

Also: the `Fatalf` message is now wrong for this clause — a classification mismatch prints "late context cancellation/deadline did not roll back," which points the reader at rollback when rollback was fine. Add `unknown=%v alreadyDone=%v` to the message. And note this test now requires a **three-sentinel chain** (`ErrOutcomeUnknown` + `context.Canceled`/`DeadlineExceeded` + `sql.ErrTxDone`) in the uncertain branch; the message names none of them, so a missing wrap is a slow debug.

### 5. MEDIUM — nonserialized-field refusal is a hard regression if any of the five fields decodes from legacy JSON
`internal/storage/graphstore/legacy_import.go:249`

**Defect.** The check rejects `WispPlaneOverride`, `IDPrefix`, `PrefixOverride`, `SourceRepo`, `IsLitePartial`. Its safety rests entirely on those fields being unreachable from `encoding/json` (tagged `json:"-"`) — unverified here. `SourceRepo` in particular reads like a federation field that a real export could plausibly carry.

**Impact.** If even one has a live JSON tag, previously importable legacy export files now fail validation with a message that mentions none of the five field names, and the user has no path forward. The new test only exercises the direct-SDK path, so the decode path has no guard either way.

**Fix.** Add a decode-path test: unmarshal a legacy record containing `wisp_plane_override`/`id_prefix`/`prefix_override`/`source_repo`/`is_lite_partial` keys and assert the decoded `Issue` has them zero. That both documents the assumption and fails loudly if a tag changes. Also name the offending field in the error — `invalid("Issue %s sets unsupported in-memory field %s", issue.ID, field)` — since a caller cannot act on the current generic message. (`issue.ID` may be empty here, yielding "Issue  has unsupported…"; the per-field form fixes that too.)

### 6. LOW–MEDIUM — dry-run summary claims a workspace prefix that was not adopted
`cmd/bd/graph_preview_import.go:59`

**Defect.** The disclosure string is unconditional on `importDryRun`: a dry run with a prefix prints `Would import … Workspace Issue prefix: web-app.` "Workspace Issue prefix" states a property of the workspace, but the dry run rolled back and adopted nothing.

**Impact.** The one new summary assertion that *does* involve dry-run ("Would import") passes a result with no prefix, so the dry-run + prefix combination is untested and the wording slipped through.

**Fix.** Branch the phrasing — `Would adopt Issue prefix: %s.` vs `Workspace Issue prefix: %s.` — and add that case to `TestGraphPreviewLegacyImportSummaryPrefix`.

### 7. LOW — internal-state test accepts any error, not the validation error
`internal/storage/graphstore/legacy_import_test.go:83`

**Defect.** `if _, err := prepareLegacyImport(...); err == nil` only asserts non-nil. Any unrelated refusal (prefix admission, a future required-field check) satisfies it, and all five cases would still pass if the new block were deleted and replaced by some other failure.

**Fix.** Assert `errors.Is(err, storage.ErrValidation)` and that the message names the field under test. Cheap, and it pairs with the per-field message in finding 5.

### 8. LOW — docs: formatting drift and two unverified specifics
`docs/reference/graph-legacy-import.md:76-78`

- The replacement paragraph's lines run well past the ~78-column wrap the surrounding prose uses (the `transaction, import reports …` line is ~150 chars). Rewrap to match; `make check-docs` aside, it is visible in the diff.
- `(exit 6)` is new in the user docs — confirm it against the exit-code constant rather than the prompt's `outcome_unknown6` shorthand.
- The old text named "Engine errors and timeout" explicitly; "Definite failures and dry-runs" is correct but vaguer. Consider keeping "engine errors" named, since that is the case readers arrive with.

### 9. LOW — set-normalization applied to labels only
`internal/storage/graphstore/legacy_import.go:301-312`

**Defect.** The rationale "labels are a set in native storage" applies equally to dependency edges. Duplicate edges in a legacy export presumably still reach the writer and surface as a duplicate-key engine error (or, worse, land in the uncertain path) instead of a clean validation refusal. Relatedly, the label dedup is exact-string: if storage normalizes case or whitespace, `["Bug","bug"]` still arrives as two labels and hits the same duplicate-key path the dedup was meant to prevent.

**Fix.** Either extend the same normalization to dependencies and match storage's label-key normalization, or add a sentence to the doc stating that duplicate dependency edges and case-variant labels are the caller's responsibility. Unverified which applies — depends on the native label/dependency uniqueness rules.

### 10. LOW — strict infra-type error returned unwrapped
`internal/storage/graphstore/legacy_import.go:86`

Adopting the strict read is the right call — the old silent-default behavior could admit an infra-typed issue on a config read failure. But `return err` gives the user no origin. Wrap it (`fmt.Errorf("resolve infrastructure Issue types: %w", err)`) per `engdocs/ERROR_HANDLING.md`, and confirm it classifies as a definite pre-commit engine failure rather than falling into `outcome_unknown` — note this read sits *after* the preceding in-transaction write loop, so the refusal path depends on rollback.
