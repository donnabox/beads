## Findings

**1. MEDIUM — clause-1's root `next` conjunct has no declared oracle or coverage binding, and its only detection path misclassifies target non-conformance as a harness defect**

- *Location:* `packages/conformance/test-support/transactional/manifest-v1.json:8690` (`p-update` assertions) and the mirrored `coverage-v1.json` `p-update:*` block; detection path `packages/conformance/src/transactional-observation.ts:231-232` → `packages/conformance/src/runner.ts:716`.
- *Issue:* The row credits "the response contains the first page and an absolute `next` URL for another immutable page of the same receipt", but `p-update` declares no assertion touching `/next`. The sole enforcement is the `/next` capture reaching `register()`, which raises `TransactionalHarnessError("source receipt page unavailable")` when `body.next === null`; the runner maps that class to `state:"harness-error"`. (`captureValue`'s `ScenarioObservationFailure`, which *is* mapped to `fail`, never runs — `register` is called first in the capture loop, runner.ts:1489.)
- *Impact:* A target that inlines all 33 entries — exactly the non-conformance this row exists to detect — is reported as a harness defect rather than a target failure, contrary to the approval's "classify target-observation failures separately from harness defects". None of the 307 coverage bindings attests the root-side `next`, and no control discriminates it. (No false pass: the installed positive demands `state:"pass"`, so it still fails loudly.)
- *Fix:* (a) In the helper lane, throw `TransactionalReceiptFailure` instead of `TransactionalHarnessError` at transactional-observation.ts:232 (a completed root that advertised no page is a target fact, not a harness fault). (b) Add a declared `p-update` assertion `{"id":"next-page","kind":"json-pointer","pointer":"/next","exists":true}` with its coverage binding, and a sixth control row `["root next", "p-update", "next-page", null]` — flipping it to `equals:null` fails against the real URL, which is what proves the root advertised a continuation.

**2. LOW — the new authoring test pins the final-state literal but none of the 32+1 boundary oracles it is named for**

- *Issue:* `it("pins the one-page matched-plus-updated witness …")` pins `p-final:exact-later-items`, the reopen count, `p-later-state.captures === []` and three reason substrings — but nothing pins `p-update:matched` (`count:32`), `p-update:outcomes` (32 ordered tuples, index 0 `matched`), `p-update:no-extra` (`/results/32` absent), or `p-page-read`'s single-entry page (`/body/results/1` absent plus the four p31 literals). - *Impact:* A regenerated manifest that weakened or dropped those four assertions would pass every static test, pass the coverage mirror (which is derived from the manifest), stay inside the byte/node fences, and still pass the installed run — fewer oracles means fewer ways to fail — silently hollowing out the row's only strong positive oracle ("matched consumes a slot").
