## Findings

### 1. Low — efficiency regression on the inherited Event path from the helper extraction
**File/line:** `packages/server/src/transaction-store.ts:543-555` (callers `:1313`, `:1394`)

The extracted `retainedGroupAtOrAfter` calls `db.prepare(...)` on **every invocation** for both statements. The code it replaced hoisted `rowAt` and `bodyAt` once, above `readEvents`'s group-walk loop (`8569b85:1282-1287`).

**Impact:** `readEvents` for a Resource source (`?view=events`) walks and parses *every* group from the cursor to head, because most groups project zero visible events for one subject (`:1312-1351`). That loop now compiles 1–2 SQLite statements per group walked instead of 2 per request, and leaks that many un-finalized `StatementSync` handles until GC. No behavioral change — `report.md:11`'s "preserves Event framing and cursor behavior" is accurate — but the per-row cost is new and is not mentioned. The changefeed path itself is unaffected (bounded at ≤2 helper calls plus 2 inline probes per request, `:1391`, `:1402`).

**Fix:** hoist both statements into lazily-prepared closure constants inside `openTransactionStore` (alongside the existing pattern) and have `retainedGroupAtOrAfter` reuse them. Note that `transaction-events.test.ts:467-499` spies on `DatabaseSync.prototype.prepare` and attaches per-statement `get` mocks, so it keeps passing either way.

### 2. Low — `position` tampering is in the plan's done-when but has no test anywhere
**File/line:** `packages/server/src/transaction-changefeed.test.ts:366-373`

Done-when #10 enumerates "Tampered position/previousPosition/eventCount/ordinal fails closed." The corruption table covers `previousPosition`, `projectionAdvance`, all-empty arrays, shifted `ordinal`, and `eventCount:100`, plus one end-to-end DB tamper of `previousPosition` (`:374-382`). Tampered `position`, `checkpoint`, `scopeEpoch` and `authorizationView` are **not** exercised — and `grep` finds no equivalent in `transaction-events.test.ts` or `transaction-store.test.ts` either, so there is no inherited coverage to lean on.

**Impact:** evidence only. The code does fail closed, via `transaction-events.ts:182-192` (`group.position !== \`pos-${expectedPosition}\``, `group.checkpoint !== group.position`, epoch/view equality), reached unconditionally from `projectTransactionChangeGroup` (`transaction-changefeed.ts:138-144`). So this is an unproven-but-correct branch, not a hole.

**Fix:** add `{ position: "pos-99" }`, `{ checkpoint: "cg_x" }`, `{ scopeEpoch: "foreign" }` to the existing `for (const change of [...])` table — one line each, no new fixture.

### 3. Low — "replaying from the unchanged durable cursor" is asserted more strongly than the test shows
**File/line:** `packages/server/src/transaction-changefeed.test.ts:272-274` (claim at `report.md:22`, plan done-when #3)

After `client.apply(seed, true)` throws and state is confirmed unchanged at `{graph: Map{}, checkpoint: "genesis", position: "pos-0"}`, the retry is `client.apply(seed)` — the **same in-memory group object**, not a re-read of the feed keyed by the oracle's unchanged durable checkpoint (`page(owner, client.state().checkpoint)`).

**Impact:** evidence precision. The composed claim does hold, because test 1 (`:258-260`) separately proves that re-reading the same cursors — across `reopen()` — yields byte-identical pages. But no single test demonstrates "reconnect from old checkpoint replays whole group, applies once," which is what done-when #3 words.

**Fix:** replace `client.apply(seed)` with `client.apply(page(f.owner, client.state().checkpoint).groups[0]!)`, which closes the loop without new scaffolding.

## Deliberate behaviors I checked and am not flagging

- `start > head` → 400 `invalid-parameter` rather than a minimum wait or 410 (`transaction-store.ts:1389`). This is the plan's explicit ruling for future/never-issued tokens, and under a single owner with a stable epoch no legitimately issued checkpoint can exceed head. Rolling a store file back to an older copy would preserve the epoch and reach this branch, but no restore path exists in this slice.
- A corrupt row at `start+2` makes the otherwise-servable page at `start+1` fail 500 (`:1402`). Strictly more conservative than required; nothing is skipped either way.
- `service.changes` spends an owner entry on `captureChangesStart()` before discovering `minimum === "unsupported"`, and `readChanges` spends an `enter()` to return `{kind:"unsupported"}`. Only an extra metadata read; the gap is still bodyless and after authentication.
- `request.signal` is never aborted (the runtime builds `new Request(url, {method, headers})` with no signal), matching "no new cancellation subsystem."
- `url.hash` is unreachable over HTTP (Fetch strips the fragment from `request.url`); it is live for the direct API.
