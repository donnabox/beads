## Open findings

### A — LOW · `empty()`-emitted 405s still lack the non-attesting marker, and the marker is now inconsistent across 405s

`packages/server/src/development-runtime.ts:111-119` (`empty()`), vs. the fix at `:334`.

Finding 6 was fixed at one call site instead of in the shared helper. Live matrix against a real candidate:

```
204 HAS  probe GET            405 MISS service-desc OPTIONS   (allow=GET, HEAD)
200 HAS  service-desc GET     405 MISS operations dir OPTIONS (allow=GET, HEAD)
200 HAS  operations dir GET   405 MISS createBead OPTIONS     (allow=POST)
200 HAS  type inventory GET   405 MISS createBead GET         (allow=POST)
401 HAS  unauthenticated      400 HAS  malformed
404 HAS  unknown resource     406 HAS  not-acceptable
```

Impact: four live routes serve responses indistinguishable from an attesting deployment. Before `39a7674` all 405s were uniformly unmarked; now the schema route's 405 carries the marker (via `setHeader` merge) and the other four do not, so the fix *introduced* the asymmetry. Same applies to 500: a fault originating inside the schema route reaches `empty(response, 500)` with the marker already set, while every other 500 has none. `installed-reference.test.ts` asserts the schema-route headers only; nothing asserts the others. review.md §6 is literally accurate but reads as if the marker class is closed.

Fix: set `"x-bdp-development": "non-attesting"` inside `empty()` alongside `cache-control`, then drop the now-redundant `setHeader` at `:334`, and extend the header assertions to one `empty()`-emitted 405.

### B — LOW · `payloadIdentity` silently skips symlinked module files (fails open)

`packages/server/src/installed-reference.ts:26-36`.

`bindFiles` branches on `entry.isDirectory()` / `entry.isFile()`, and a `readdir` Dirent reports a symlink as neither. Probe:

```
linked.js   isFile:false isDirectory:false isSymbolicLink:true  => SKIP
linkeddir   isFile:false isDirectory:false isSymbolicLink:true  => SKIP
real        isFile:false isDirectory:true  isSymbolicLink:false => RECURSE
```

A symlinked `.js`/`.json`/`.node`/`.wasm` inside a bound package is loadable (resolution follows symlinks) but excluded from the hash, and a symlinked subdirectory is skipped whole. This is finding 7's original failure mode in narrower form, and it fails **open** rather than closed. Not reachable in the pnpm/npm layouts exercised here — package contents are regular files or hardlinks, and `node_modules` is skipped — but this candidate's own fixture builds symlinked package layouts (`installed-reference.test.ts:370` `symlinkSync` for `@bdp/protocol`; it works only because that symlink is the package root reached by path, not an entry inside a scanned directory).

Fix: handle `entry.isSymbolicLink()` explicitly — `stat` and hash/recurse the target, or refuse with `unsupported runtime dependency` so it fails closed.

### C — LOW · the payload traversal walks only `dependencies`, and resolves with CJS semantics

`installed-reference.ts:46-47`.

Two coupled consequences:

1. `Object.keys(manifest.dependencies ?? {})` ignores `optionalDependencies` and peer-only dependencies. The current closure is complete *by luck*: `ajv-formats@3.0.1` declares `ajv` in **both** `dependencies` and optional `peerDependencies`, so the ajv subtree is reached. A future runtime dependency declared peer- or optional-only would be silently excluded while loading — again finding 7's exact shape.
2. `createRequire(manifestPath).resolve(dependency)` is CJS resolution, while the bytes are loaded by ESM resolution. Probe against a synthetic `"exports": { ".": { "import": "./index.js" } }`:

```
require.resolve THREW: ERR_PACKAGE_PATH_NOT_EXPORTED - No "exports" main defined
ESM import      -> OK, x = 1
```

That error is raised outside the walk-up `try` and is not ENOENT, so it propagates: declaring any ESM-only runtime dependency makes `startInstalledReferenceCandidate` reject before the listener or store opens. Fail-closed, but it means `payloadIdentity` constrains which dependencies the candidate may ever declare.

Fix: resolve with `import.meta.resolve` (matching how modules are actually loaded), traverse optional/peer edges, and — the cheap structural guard — assert at startup that every loaded non-builtin `file:` URL lies inside the bound closure, which is the check I ran externally and which would have caught the original `fast-uri` gap directly.

### D — LOW · the depth-32 cap bounds traversal depth, not traversal work

`installed-reference.ts:18`.

`ancestors.includes(root)` only prevents revisiting a package on the *current* path, so diamonds re-traverse. Measured: 6 distinct packages → **14 package visits**, ajv hashed twice and fast-uri three times, 454 file hashes, ~40 ms. Work is exponential in the number of chained diamonds, capped only at depth 32, and it runs on every startup before the listener opens — so a wider future closure degrades startup rather than refusing. Harmless for this fixed two-dependency closure; the hash stays deterministic because labels are path-qualified.

Fix: memoize traversal by resolved root while keeping per-path labels, or add an explicit total-files/bytes bound next to the depth cap.

### B′ — LOW · the reference-closure guard misses protocol-relative and relative URI values

`installed-reference-configuration.ts:64-74`.

The guard only inspects strings matching `/^[A-Za-z][A-Za-z0-9+.-]*:/`. Replicated-guard probe:

```
PASS (accepted)  PROTOCOL-RELATIVE foreign => "//foreign.invalid/types/one"
PASS (accepted)  RELATIVE parent escape    => "../../outside/type"
PASS (accepted)  RELATIVE plain            => "types/other"
```

accepted in array-element and object-key positions too. A descriptor is served from `${scope}types/<name>`, so a client resolving `//foreign.invalid/types/one` against the retrieval URI reaches a **foreign authority** — the exact leak finding 8 asked to close, via a reference form the guard does not classify as a URI. Same hypothetical-future reachability as the original finding (today's 13 descriptors contain no such value), and the author's closure test exercises only scheme-prefixed extensions.

Fix: also refuse values starting with `//`, and for URI-reference-shaped strings check `new URL(value, canonical).href.startsWith(canonical)` rather than only the absolute form.

### C′ — LOW · the same guard over-refuses, and can make every installed candidate unstartable

`installed-reference-configuration.ts:65-67`.

```
REFUSE  urn                   => "urn:example:thing"
REFUSE  mailto                => "mailto:a@b.invalid"
REFUSE  prose with colon      => "Link: outgoing endpoints"
REFUSE  prose word-colon      => "note:see-spec"
THROW TypeError: Invalid URL  => "http://"
```

`referenceTypeArtifacts` runs inside `captureInstalledReferenceConfiguration` whenever `descriptors` is empty — the shipped default. So if a future protocol-side `REFERENCE_TYPE_DESCRIPTORS` gains any field holding a `urn:`/`mailto:` identifier or ordinary prose containing a word followed by a colon (`"description": "Link: connects two beads"`), **every** installed candidate refuses to start, before any filesystem work. Fail-closed, but the failure is a startup outage and the message (`reference artifact is not Scope-local`, or a bare `TypeError: Invalid URL` for malformed input) misdirects. The author's test never exercises a non-URI string.

Fix: gate on URI-reference shape (scheme-with-hierarchical-part, or `//`-prefixed, or containing `/`) rather than any scheme-like prefix, and wrap `new URL` so parse failures report the intended message.

### E — LOW · finding 5's listener-retry path is unexercised against reachable Node behaviour (verification limit, not a defect)

`development-runtime.ts:496-501` and `installed-reference-startup.test.ts:251-289`.

Real Node semantics, probed:

```
before close():            listening = true
immediately after close(): listening = false   <-- synchronously
after 'close' event:       callback error = no error
second close() on a closed server -> ERR_SERVER_NOT_RUNNING
```

`Server.prototype.close` nulls `_handle` synchronously, so `listening` is already false by the time any first attempt could fail. The new `if (!server.listening) return resolve()` guard therefore makes every real retry an immediate no-op resolve — which is *correct* (the handle is closed), but it means a reachable failed listener close is never actually re-closed. The test's injected failure stubs `Server.prototype.close` to invoke the callback with an error while leaving `_handle` intact, so `listening` stays true — a state real Node cannot produce after `close()` is called. review.md §5's "inject a first listener failure that leaves the actual listener open … finish listener cleanup" describes a property of the mock.

The substantive claims are independently sound and do not depend on it: owner close invoked exactly once across retries, terminal owner failure preserved verbatim, store lock genuinely released (the reopen under the same Scope — unchanged because installed mode takes `scope` from `transport.scope`, not the port — is real). Worth recording alongside: once owner close rejects, `close()` rejects **permanently**, so cleanup-path callers must `.catch()`, as the author's own `finally` does.

### F — LOW · `authenticationIdentity` is order-sensitive while every adjacent identity in the same digest is canonical

`installed-reference-configuration.ts:170-172`.

```
ordered   authenticationIdentity: 5c9670674585977adcdee4f9…
reordered authenticationIdentity: 43fb3dcd69eb4b4324eca444…
order-sensitive: true | configurationIdentity differs: true
policyIdentity stable under policy key reordering: true
```

Credential array order has **no observable effect** in the installed path: `development-runtime.ts:240-261` ignores `options.token` entirely when a deployment is configured (so `installed-reference.ts:67-70`'s `credentials[0]` only satisfies the `:178` regex), tokens are unique so `credentials.find` is order-free, and duplicate principals collapse to one `principalViews` entry. Meanwhile `policy.identity()` sorts its snapshots and `captureDevelopmentAggregatePolicy` dedupes-and-sorts (the A3 fix) — both inside the same `identity` digest. So two observably identical authentication bindings get different `authenticationIdentity` and `configurationIdentity` values, which reads as "configuration changed" to anything comparing witnesses.

Disclosed — review.md §33 says "exact ordered captured mapping" — so this is a design-choice flag rather than an undisclosed defect, and it is **not a regression** (the pre-`39a7674` digest was order-sensitive too). It is worth deciding deliberately now that the value is promoted to a named identity on the wire. Fix if undesired: sort by `{principal, tokenDigest}`, matching `policy.identity()`.
