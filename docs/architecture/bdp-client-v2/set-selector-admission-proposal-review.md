**Verdict: coherent recommendation, requiring a ruling; no contradiction with an existing explicit Selector-phase rule found.** The current text leaves that phase unresolved. The proposal correctly distinguishes that gap from authority to implement the selected behavior. Add the client-visible qualifications below before presenting the choice.

## Existing law versus proposed law

- The grammar is defined (`bdp.md:849–863`), but `selector` schema currently checks only nonempty string (`schemas/bdp-v0.schema.json:3218–3221`). Malformed/out-of-profile embedded grammar is not expressly included in Transactional carrier step2 (`bdp.md:4496–4503`). Classifying it there is a sensible clarification, not a consequence mechanically proved by schema validity or the existing closed carrier list.
- Static Selector limits exist (`bdp.md:1065–1066`, `4275–4278`), but neither admission step5 nor failed-receipt limit prose currently enumerates them. Step5 currently names transaction.operations/rate/capacity (`4515–4518`); receipt prose names examined/matched/mutated/Events/duration (`5317–5319`). Both proposed placements therefore need normative edits. The recommendation does not violate “fails the operation without changing anything”: a whole-carrier refusal is a no-effect failure, although its scope should be made explicit.
- Equal-key comparison before fresh capacity is explicit (`4506–4527`). The proposed fresh-only placement preserves it, including pending/terminal/compacted receipts. Grammar is still checked first; malformed text cannot use a key to bypass syntax validation. Current principal authorization and response negotiation still apply. Request target/body bounds remain step1 and can still reject an old request after those bounds change; narrow “outcomes remain retrievable if limits change” to the proposed **Selector operational limits**, not every limit.
- Execution limits after durable admission remain failed receipts. Do not reuse Read's invalid-parameter mapping inside a receipt: the receipt code union excludes it and malformed-request (`receiptProblemCode`, schema4162 onward). No new union variant is needed for either option.

## Missing customer-visible tradeoffs to state

1. **Whole-carrier precedence changes what failure the client sees.** Under the recommendation, any valid over-complex Selector anywhere in a fresh batch causes direct413 before execution, even if an earlier operation would fail identity/authorization/cardinality or the set would match zero Resources. Example: operation0 creates an already-taken ID; operation1 contains an over-limit valid Selector. Recommended result: no receipt/key and413. Execution alternative: admit, reach operation0 and retain its identity-taken failure; operation1 is never evaluated. Neither option partially commits. Invalid grammar remains whole-carrier400 under both options.
2. **No binding is not an automatic-retry promise.** Existing `limit-exceeded` is size/413 with `retry: never` (`schema:262–282`; existing Read/Transactional problem mapping). Recommendation leaves the key unused, but clients should change/split the request or deliberately retry after configuration changes; they must not interpret it as429/503 backoff. State that mapping explicitly rather than introducing a new retry disposition accidentally. It also provides no durable failure receipt to retrieve after a lost refusal; identical submissions repeat validation.
3. **The alternative spends receipt/storage capacity and pins the failure while retained.** A changed configuration does not rerun the same retained key. Say “use a new key while the failed receipt remains retained,” not an unqualified permanent consumption claim: after failed receipt forgetting, the same key is unknown and may execute anew (`bdp.md:4029–4044`). Completed receipts have different lifetime rules.
4. **Pre-principal grammar has a bounded cost.** This choice intentionally validates complete embedded grammar before authentication/key lookup, including retries and inputs that exceed current Selector caps. The body bound limits that work; stack-safe grammar validation and full-input validity checking are essential. This is the main implementation cost of making grammar win over complexity, already recognized by the memo; no new general language mechanism follows.

## Schema/code compatibility and parser precedence

Existing direct Problem schema accepts malformed-request/limit-exceeded, pointer and a dotted `limit` string; selector.bytes/depth/nodes fit. Receipt problems likewise accept limit-exceeded and these names. Required mapping is413/size/never. Adding Selector limits to normative placement/pointer prose does not inherently require widening the error-code schema. For operation-local failures, explicitly define `/selector` versus `/operations/N/selector`; the alternative should identify the reached operation's outer index. In the recommended direct refusal the pointer can identify the operation without inventing receipt-only operationIndex semantics. If several fresh-capacity bounds are violated, retain the existing step5 latitude or state a deterministic tie rule; do not accidentally infer one from parser order.

Current code is not already an implementation of either option. `transaction-batch.ts:64–67` explicitly refuses set operations as a private development gap; submission does preparation before principal/key (`transaction-submission.ts:65–113`) and already has an operation-limit receiving result. This is a compatible integration shape, not proof that Selector timing is settled.

`read-selector.ts:163–183` enforces UTF-8 byte length before parsing. The tokenizer then scans input, while makePath/group/operator reductions enforce depth/nodes during parse (`199–350`, `353–399`). Consequently it can report complexity before discovering a later syntactic/unsupported-grammar fault; some lexical faults arise earlier during tokenization. Calling this API with current operational limits during carrier preparation and relabeling its exceptions cannot implement the proposed grammar-first law. Separate complete bounded syntax validation from the fresh-key operational decision; preserve the existing Read path's behavior. Do not remove all parser bounds or use recursive unbounded parsing merely to defer limit errors.

The proposed byte clarification is correct: count UTF-8 of the decoded JSON string in body carriers, percent-decoded query value for Read, and never decode percent text within a JSON string. Preserve exact Selector literal spelling for semantic request identity; parsing is validation, not permission to canonicalize JSONPath literals or identifiers.

## Concrete decision wording

“Approve whole-carrier malformed-request for invalid set Selector grammar before principal/key lookup; for valid grammar, enforce selector.bytes/depth/nodes as direct413 limit-exceeded, retry:never, only after unknown-key comparison and before negotiation/admission, with no receipt/key/effects. This includes a later set operation that execution would never reach. Equal retained/pending outcomes bypass these operational Selector caps, while existing request bounds/authentication/negotiation still apply. Data-dependent limits remain execution failures.”

The memo's failed-receipt alternative remains valid if preferred, with the retention and earlier-operation precedence differences above. This review selects neither option and does not authorize implementation. Valid-input staged-set work can continue independently.
