## Findings

**MEDIUM 1 — Insertion position unspecified; catalog order is pinned.** Plan §"Files and authority" (87) / action-ledger §. `transactional.receipt.pagination` is catalog index **25**; the manifest is in strict catalog order (4, 6, 17, 18, 19, 20, 24, 50), and `transactional-cumulative.test.ts:91–94` pins manifest ids to the catalog-order filter while `:100–102` pins coverage row ids to manifest order. The new row must be **inserted at position 8 of 9**, between `receipt.readable` (24) and `idempotency.failed-retained` (50), in *both* `manifest-v1.json` and `coverage-v1.json`. The plan says "canonical 9-row" and never says this. *Impact:* appending fails both pinned equalities. *Fix:* state the insertion index for both files explicitly.

**MEDIUM 2 — "Two new reopen witnesses" contradicts the plan's own table.** Plan line 81 vs. table rows 15/16/17. `transactional-matrix.test.ts:359–370` asserts an exact sorted 9-element `reopened-*` list; all 9 current post-reopen reads are GET (the 3 existing HEAD reads are all pre-reopen). Rows 15, 16 **and 17** are post-reopen private reads. *Impact:* the pinned list must become 12, not 11; the stated budget is one short, and this silently introduces the first post-reopen HEAD. *Fix:* enumerate 12 ids, or name row 17 outside the `reopened-` convention and say so.

**MEDIUM 3 — Entry-counting partiality understated.** Plan line 22 attributes partiality *only* to the advertised-limit branch, but requirement 2 (catalog:433, spec 5167–5170) reads "every entry counting as one **whatever its outcome**." The fixture observes only `matched` + homogeneous `updated`, with a homogeneous boundary (p30|p31). *Impact:* the coverage reason would imply broader entry-counting credit than earned. *Fix:* record in the plan and the new coverage `reason` that counting is witnessed only for one `matched` entry plus `updated` entries, with no `created`/`deleted`/`withheld` entry at the boundary. Worth stating the claim actually earned: because 32 `updated` + 1 `matched` = 33 is precisely what forces the spill, the design *does* prove `matched` consumes a slot — that is the strongest part of the oracle and should be named as such.

**MEDIUM 4 — Proposed byte fences collide with already-pinned app bounds.** Plan line 97 ("max 16KiB raw seed request", "max 64KiB finite response") vs. `transactional-matrix.test.ts:385–388`, which pins for the set rows POST `bodyOctets <= 2048` and every `decodedBodyBytes <= 32768`. A 32-create seed POST cannot fit 2048 bytes. *Impact:* if the new row enters that `newRows` filter it fails outright; and 64KiB silently doubles the established 32KiB response discipline with no stated reason. *Fix:* state that the new row is excluded from the existing `newRows` checks (or extend them with row-specific bounds), and justify 64KiB against the 32KiB precedent.

**LOW 5 — `next !== null` is enforced at two sites; only one is cited by line.** Besides `transactional-observation.ts:180–181`, `runner.ts:957` rejects `body.status === "completed" && body.next !== null` on *every* root GET — gating actions 2/5/12/15. Line 37 notes the runner forces `next:null` and lists the file, but line 47 states the relaxation generically. *Fix:* name `runner.ts:957` as the second required relaxation site.

**LOW 6 — Page-URL validator has no accept-form.** Plan line 44 lists only rejections. `receiptUrl` (actual **56–77**) enforces a whitelist: length ≤ 8192, `url.href === value`, prefix match, `/^[A-Za-z0-9_-]+$/` remainder, empty search/hash/username/password. *Impact:* a blacklist is the wrong shape for the one check standing between this seam and arbitrary URL following. *Fix:* require `value === \`${source.receipt}/pages/${token}\`` with `/^[A-Za-z0-9_-]{1,256}$/` (matching transaction-store.ts:768) plus all five `receiptUrl` guards and the length cap.

**LOW 7 — Citation drift in five harness/runtime ranges.** `receiptUrl:59–81`→**56–77**; `register:132–205`→**129–201**; `runner.ts:884–982`→**876–978**; `transaction-service.ts:320–363`→**320–360**; `transaction-store.ts:1937–2021`→**1937–2019**. Catalog/spec/schema/config citations are exact. *Impact:* reviewers reconciling a citation-authority document against the frozen tree hit off-by-3 ranges. *Fix:* correct to frozen-tree ranges.

**LOW 8 — No precedent for the cache/validator assertions rows 6/7/8/17 need.** `cache-control` occurs **0** times in `manifest-v1.json`; no private receipt-read asserts it. The mechanism does exist — `normalizeHeaders` (runner.ts:3325–3331) passes every header through lowercased, and `json-pointer` supports `exists:false` (15 uses) — so it is authorable, but the plan never states the shape. Separately, "missing validator" in line 95 means the `SchemaValidator`, colliding with *HTTP* validators in rows 7/17. *Fix:* give the concrete forms (`/headers/cache-control` equals `private, no-store`; `/headers/etag`, `/headers/last-modified` with `exists:false`) and disambiguate the word "validator."

**LOW 9 — Ledger mechanism for two pointers from one response is unstated.** `register` is per-capture; its non-`/id` branch **deletes** the binding, and `ledger.has(binding)` throws on reuse. So root and page cannot share a binding name, and a `/next` capture under its own name self-deletes today. Line 44 asserts the invariant ("independent capture order must not alter authority") without the mechanism. *Fix:* specify that both ledger entries are derived inside the single `/id` registration from one validated response — the page entry keyed to its own binding and carrying the parent root id — rather than by a second `register` call on a `/next` capture.

**LOW 10 — The load-bearing "32" is never cited to its controlling source.** Every 32 in the design traces to `TRANSACTION_RUNTIME_LIMITS` (transaction-batch.ts:62–72: `maximumOperations:32`, `matchedResources:32`, `requestBodyBytes:64KiB`); the plan cites only `transaction-runtime-configuration.ts:338`. The 32-match selection sits exactly at `matchedResources` with **zero headroom** (admissible only because line 865 uses `>`). *Fix:* cite transaction-batch.ts:62–72 and record the zero-headroom fact so a later limit change invalidates the row knowingly.

---

No finding contradicts the plan's core recommendation. Its scope discipline is sound and, where I could check it, honest: the refusal to credit `page-restart` (1973), `page-expiry` (438) or `validator-omission` (2017); the refusal to borrow the existing custom oracle's pass; and the explicit note that a privately configured bound cannot prove the "when advertised" branch all hold up against the frozen text. The 2048-byte and catalog-order collisions (#4, #1) are the two that would stop an implementation on contact.
