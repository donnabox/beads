## Concrete path and existing groundwork

* `apps/bdptest/src/main.ts:59` always calls `createConfiguredBdptestReadServer`; `server-composition.ts:22` always builds the in-memory Read port and Read controls. Config already parses all three profile tokens (`packages/config/src/index.ts:376,759`), but `packages/server/src/index.ts:288` refuses every non-Read token before listening. The opaque admission type and WeakSet are Read-only. Adding a config token is therefore not the fix. The ordinary executable does not consume the mutable candidate's trusted storage, credentials, contracts or policy configuration. `bdptest.fixture` is stored but not resolved. Existing Read admission is backed by `read-conformance-capability.ts` and the historical two-target Read cohort, not write evidence.
* **RU discovery already works privately.** `installed-reference.ts:8` captures the actual installed configuration, binds the shipped payload, and passes `createDevelopmentComposition` into the mutable runtime. `development-composition.ts:23–87` observes the real authority, emits closed RU discovery, serves the nine-target Directory and gates reads through that owner. `development-runtime.ts:380–401` performs trusted receiving before composed routing. `read-update-matrix.test.ts:2524` already navigates all nine discovered operations with a cold client. The generic development path without this composition is a different lane. Thus the ledger's “Scope/descriptor/directory HTTP still refuses” is accurate for TX, not for this installed RU candidate.
* **TX assembly already exists, wire delivery does not.** `transaction-service.ts:267–293` captures one owner context and assembles discovery after releasing the entry; `transaction-discovery.ts:8–66` has the actual twelve operation targets, current epoch/view/head, replay minimum and enforced limits. `transaction-http.ts:212,245,627–634` deliberately rejects Scope/descriptor/Directory; the Scope probe callback is unreachable through that final fence. `transactional-discovery-installed.test.ts:80,189` explicitly tests that refusal while the same owner writes, reads and replays. This test is a preservation fence to deliberately supersede when the full candidate can honestly describe its profile, not success evidence for discovery.
* Installed factories, configuration capture, compiled schema/Type artifacts, canonical authority, payload identity, trusted credentials, IPC startup/shutdown and separate RU/TX execution already exist. `transaction-installed.ts`, `installed-reference.ts` and their process modules are private candidate machinery; ordinary package exports/startup do not select them. The public server exports root and development only. Preserve these boundaries until reviewed profile-specific evidence authorizes activation; do not simply export an unguarded candidate factory or relax the Read proof.
* The shipped `BdpReadUpdateClient` already follows Scope Link → descriptor → Directory (`packages/client/src/read-update.ts:650–738`) and rejects incompatible closed discovery. It cannot be assumed to accept TX. The sole design explicitly permits a cold conformance HTTP executor for TX; use real protocol parsers and followed references rather than demanding a new full SDK. Setup may know Scope/credentials and canonical dial mapping, but may not hand the cold navigation oracle operation/receipt/feed URLs or fake discovery responses.

## D5: what the existing carriers do and do not prove

`profile-contract-selection.ts` already loads/deduplicates the canonical core and companion catalogs and applies cumulative retirements. `test-support/profile-contract-plan.ts:335–366` records unplanned, unsupported, unresolved-applicability/setup/prerequisite states honestly. The RU artifact-set associates two immutable manifests with one installed configuration; `read-update-artifact-execution.ts` binds actual returned rows and leaves missing observations null. TX's branded bundle/private runner, exact transport and session binding preserve real receipt/reopen/source/configuration provenance. These are useful groundwork, not disposable scaffolding.

The static inventory in `manifest-gap-inventory.json` derives **130 selected normative RU IDs / 56 distinct manifest rows / 74 IDs absent** from the two current RU manifests and **251 selected normative TX IDs / 17 manifest rows / 234 IDs absent** from the current TX manifest. This is a JSON membership calculation before fixture applicability, not a runner result, functionality percentage, or count of missing implementations. In particular, TX's 234 absent IDs are unrelated to the separately observed 234 HTTP exchanges of its historical matrix. Coverage files also deliberately mark partial contracts; a present ID or `wholeContract` author annotation is not fresh execution evidence.

Concrete absent groups include TX discovery, inherited Read navigation/collections/conditions/Type inventory, Update singleton/sequence/alias behavior under TX, replication/Snapshot/Events, and erasure/recovery. RU still has missing cumulative bindings for disclosure/alias/pagination/owned closure and authorization/retry/recovery variants. Existing runtime implementations and standalone tests must be reconciled against these IDs before deciding whether each needs code, a reused executable oracle, a fresh installed fixture, or an explicit applicable/conditional disposition. This audit does not infer that all unplanned IDs are implementation defects.

The required dependency map is: **D1 required serving + D2 explicit semantic resolutions + D4 installed configuration/applicability → complete same-target RU/TX candidates and real cold discovery → U3/T4 fresh cumulative execution → P profile-specific evidence/admission + combined exact CI**. Discovery receiver/startup/evidence authoring and mapping existing oracles can progress independently now; public activation waits for their complete contract. No separate feature roadmap, additional product question, main merge, optional History, or full SDK is introduced here.
