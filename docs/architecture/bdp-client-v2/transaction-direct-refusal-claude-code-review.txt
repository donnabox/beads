## Findings

**1. MEDIUM — label-suppressing matcher in the installed header-presence assertion**
`apps/bdptest/src/transactional-direct-refusal-installed.test.ts:223-226`
`expect(response.headers[name]?.length, "direct refusal context presence: …").toBeGreaterThan(0)` evaluates `undefined` when the header is absent. Vitest's `assertTypes` (`@vitest/utils/dist/helpers.js:56`) throws a bare `TypeError: actual value must be number or bigint, received "undefined"` *before* the chai assertion is constructed, so the custom message is never attached. The matcher works for present-but-empty (`"".length === 0` fails with the label) and breaks only for **absent** — exactly the case the negative control exercises. Note this pattern was inherited verbatim from the adjacent convention at `transactional-alias-installed.test.ts:236`, which the plan instructed the author to reuse and leave unchanged; the source-level equivalent at `packages/server/src/transaction-http.test.ts:2522` uses the safe `expect(headers.has(name), label).toBe(true)` form and did emit its published label.
*Impact:* the installed negative cannot be identified by assertion label, only by file:line + request index; any label-matching postprocessor fails on a correct, intended discrimination.
*Repair (REQUIRED, test-only, needs root disposition + one re-run of the installed negative — not authorized now):* replace line 223-226 with a label-preserving form, e.g. `expect(typeof response.headers[name], \`direct refusal context presence: ${name}\`).toBe("string");`. Leave line 227 as-is — it already covers the empty-string case because every expected value is non-empty. Do not touch `transactional-alias-installed.test.ts`.

**2. MEDIUM — the exclusion boundary is asserted nowhere**
`packages/server/src/transaction-http.test.ts:218-245`, `:834-837`, `:2006-2013`, and the new test at `:2505-2581`
The plan requires the shared fallback "remain unwrapped" for malformed-request (400), unauthenticated (401), forbidden (403), request-too-large (413), unsupported-media-type (415) and comparison temporarily-unavailable (503). Every one of those direct-POST paths is exercised, but only for status and Problem `code` — none asserts that the three context headers are **absent**. The new test asserts presence on the three selected paths and absence nowhere, and none of the four controls is an over-wrapping counterfactual.
*Impact:* a later change that wrapped the shared fallback, or that passed an observation into `transactionHttpProblem` on the POST route, would emit context on auth/malformed/generic-413/503 and still pass all 362 tests. The exclusion half of the accepted scope is unprotected.
*Repair (RECOMMENDED, test-only; optional under the plan's named four-control set):* inside the new HTTP test, add a loop over the excluded direct-POST refusals (`{authorization: ""}` → 401, read-token → 403, `"{"` → 400, oversized body → 413/request-too-large, non-JSON content-type → 415) asserting `expect(response.headers.has(h)).toBe(false)` for all three fields; optionally add a fifth control `over-wrapped-exclusion` that wraps the fallback and must fail those names. Append to the new test rather than editing the existing assertion bodies at `:218-245`.
