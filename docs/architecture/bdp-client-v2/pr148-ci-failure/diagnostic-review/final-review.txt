# Findings

**No blockers.** All items below are optional; 1–3 materially affect whether the diagnostic can actually discriminate the diagnosis's ranked hypotheses.

1. **Medium — `cleanupFailed` mislabels "cleanup skipped", collapsing hypothesis 1 and 3.** `:2999` (`cleanupFailed: row.cleanupError !== undefined`). `runner.ts:790-797` sets `cleanupError` to *"cleanup skipped because fixture preparation did not settle"* / *"…an HTTP exchange did not settle"* — a preparation/execution anomaly, not a cleanup failure — and `:803-805` adds *"cleanup budget exhausted…"*. A preparation deadline (`category: "deadline"`, cleanup skipped) and a true cleanup timeout (`runner.ts:816-824`, `category: "deadline"`, `cleanupError: "cleanup timed out"`) both project as `{category:"deadline", cleanupFailed:true}`, distinguishable only indirectly via `exchanges`. Impact: the projection would name "cleanup" for a setup fault, which is exactly the setup/cleanup split the review asks for. Smallest correction: project the string itself — `cleanupError: row.cleanupError` — it is a closed runner vocabulary (6 literals, worst case embedding only `"HTTP exchange"`/`"action execution"`), so this adds no leak surface and removes the ambiguity.

2. **Medium — category-less harness errors stay indistinguishable, which is the leading hypothesis.** `:2998` projects `category` only. The runner leaves `category` undefined for the plan/catalog mismatch (`runner.ts:528-534`), missing capabilities (`:606-613`), `TransactionalHarnessError` (`:716-717`), transport `configuration` (`:761-768`), generic `ConformanceRunnerError` (`:784-785`) and the final catch-all *"scenario harness failed"* (`:786-787`). A failing `expect` inside the test's own prepare callback (`:1488-1495`) lands in that catch-all. So the most likely projection for the observed failure is `{state:"harness-error", exchanges:[]}` with no category — i.e. still "cause unknown", just one level finer. Also omitted: `prerequisiteFailure` (`runner.ts:217-230`, `:3012-3020`, `:3047-3053`), so a `category:"not-run"` row does not say which prerequisite or which phase. Smallest correction, both bounded: add `genericHarnessReason: row.reason === "scenario harness failed"` (one boolean, zero arbitrary text) and `prerequisitePhase: row.prerequisiteFailure?.phase`, `prerequisiteCategory: row.prerequisiteFailure?.category`, `prerequisiteId: row.prerequisiteFailure?.id` (closed unions plus a catalog ID). Do **not** project `row.reason` generally — several branches carry `error.message`.

3. **Low-Medium — the three counts are run-wide, so `nativeReadObservations` can read as target progress when it is the prerequisite's.** `:2991-2993`. # Verdict

The patch is a sound diagnostic-only change: it is strictly additive, allowlisted, size-bounded (worst case tens of KB), credential-redacted, and it leaves the negative control's expected state, failed-assertion list, request content, run selection, cleanup and deadlines exactly as before. It does separate the three phases at a coarse level — empty `exchanges` plus low `sessions`/`seedObservations` indicates preparation, populated `exchanges` with per-exchange categories indicates execution, `cleanupError`/`cleanupComplete` plus `category` indicates cleanup — but findings 1 and 2 mean the two highest-ranked hypotheses can still project identically or namelessly, so I would apply those two small changes before spending a run on it.
