## Verdict

Proceed with U1/T1. Their separation is sensible and their completion predicates are necessary. The important correction is sequencing: start the cumulative executable evidence/admission work alongside the runtime slices, and explicitly assign the remaining set-mutation and Event-serving work. “HTTP mutations work” and “durable transaction core works” are intermediate results, not full profile delivery. Each selected profile must demonstrate its cumulative applicable contract on the **same installed bdptest SQLite service configuration** that advertises it. Existing qualified Read servers and private diagnostic runners cannot confer that claim on a different owner or listener. [Cumulative profiles](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L73) [Transactional acceptance](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L6587)

No unavoidable product decision blocks the next implementation slices. The current spec already determines the required wire behavior. Static trusted credentials, administratively installed pinned contracts, bounded retention and a single-authority SQLite deployment are implementation/configuration choices within this task; none requires a Types lifecycle API or a new IAM product. Optional History, optional CORS, optional retry hints and arbitrary remote Type installation are not baseline prerequisites.

## Actionable findings

### 1. Bring cumulative qualification infrastructure forward

**High, delivery dependency.** The current artifact bundle deliberately admits the ordinary Read lane or a separate non-attesting diagnostic Update lane. The Transactional catalog test explicitly asserts that its rows have no executable manifest/fixture/runner. Public listener admission accepts only Read. These are honest safeguards, but they make U3/T4 substantial implementation work rather than final command invocations. Define the actual cumulative manifest, fixture/configuration identity, evidence binding, applicability and reviewed admission transition while U1/T1 proceed. Replace the old metadata-only assertions deliberately when real executable coverage arrives; do not simply delete their safety rationale. [Artifact guard](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/conformance/src/artifact-bundle.ts#L115) [Metadata-only assertion](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/conformance/src/transactional-catalog.test.ts#L17) [Read-only admission](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/index.ts#L270)

The checked catalogs currently contain 49 Read rows, 81 Update rows and 133 Transactional rows. Deduplicating numeric/owned companion catalogs adds five Update obligations, making 135 cumulative Read+Update identifiers. Transactional explicitly retires twelve conflicting Update identifiers, giving 256 distinct cumulative identifiers before configuration applicability and optional History. These are **inventory sizes, not progress scores or required scenario counts**; one scenario may observe several requirements and one requirement may need several counterfactuals. The inherited Read companion rows are already present in the Read catalog. Use the existing selection/retirement semantics and preserve citations. Optional History has its own catalog and is not silently included in baseline counts. [Twelve retirements](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/conformance/src/transactional-catalog.test.ts#L38) [Delta-only claim rejection](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/conformance/src/transactional-catalog.test.ts#L100)

The retired Update expectations concern discovery document/limits/directory, singleton result headers and retry, in-progress keys, retained authorization view, retention/expiry/failure expiry, restore namespace and sequence internal faults. Transactional replacements must run instead. Blindly requiring both would introduce false failures or pressure to weaken the spec.

### 2. Name set mutations and Event serving as concrete required slices

**High, scope gap in the work breakdown.** T2 broadly says carriers and T3 broadly says serving semantics. Explicitly assign `updateWhere`/`deleteWhere`, their singleton targets and batch use, staged selector evaluation, cardinality, provenance fanout, and authorization. The private transaction parser deliberately rejects set operations today; they are mandatory Transactional operations, not a later query-language proposal. [Set mutations](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L4215) [Transactional directory](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L4305) [Explicit set rejection](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-batch.ts#L56)

Also explicitly assign finite and SSE **Scope and Resource Event Sources**. A replication changefeed is not a substitute. Internal persisted groups and ordered facts are useful inputs, but Events have distinct source-local cursors, graph facts, retention and disclosure behavior. Snapshot manifest/pages, finite/SSE changefeed and their rendezvous are separate required serving surfaces. [Events](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5350) [Snapshots](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5825) [Changefeed](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5959) [Event Source HTTP](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L6130)

### 3. Share the authority contract; do not stitch two stores into one service

**High, correctness/integration risk.** The current development Update service already reads and mutates through its own SQLite authority. The private Transactional store is explicitly an incompatible independent format; it has durable resources, receipts, identities, positions and groups, but no public authority-read composition in this pinned source. T1 should add reads to that owner, not make Transactional writes visible through the separate Update store. Share route/representation/evaluation code where appropriate, while retaining one actual owner for an advertised Scope. [Update read lifecycle](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/development-authority.ts#L160) [Independent Transactional owner](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-store.ts#L1) [Transactional atomic boundary](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-store.ts#L126)

Capture rows, revisions, epoch/view and observed Scope position in the same immutable read. Current `ReadObservation` and retained pagination entries do not carry a Scope position. A receipt's `requiredPosition` is a mutation barrier, not proof of a later read's observation. A retained page's source snapshot context must remain distinct from the current serving observation. Test mutation between first page/continuation and between body capture/header emission; reject old-view/epoch handles before conditional handling. Do not expose internal Read/Update pagination epoch state as Transactional wire fields. [Read observation](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/authority-read.ts#L123) [Retained pagination inputs](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/read-pagination.ts#L31) [Response context](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5766) [Conditional ordering](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5800)

### 4. U2 needs actual installed configurations, not hypothetical policy callbacks

**Medium, evidence and implementation scope.** Current development configuration is a fixed principal, allow-all policy, empty aggregate constraints and two schema-free/unowned Types. The private Transactional store rejects schema-bearing or owned Types entirely. Evaluator support elsewhere does not establish that either served configuration composes those contracts correctly. Use a bounded administratively installed fixture with pinned schema bytes/closure, ownership and an aggregate policy; use distinct trusted credentials and actual policy changes for principal/view/reauthorization cases. Carry this configuration support into Transactional evaluation and receipts. [Fixed development configuration](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/development-authority.ts#L26) [Private policy and Type restriction](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-store.ts#L129) [Installed contracts](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L2532) [Authorization](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L2628)

Distinguish deployment applicability from product support. An all-visible single-principal schema-free Scope is not obliged to invent hidden Resources or dynamic policy changes. But it cannot qualify claims about schema-backed, owned or restrictive configurations by marking all difficult behavior inapplicable. Record exact installed contracts, policy and supported recovery operations in evidence. `actor`/`revisionProvenance` are attribution, never transport identity. No public Type installation, arbitrary network schema fetch or Types redesign is needed.

### 5. The Transactional receiver needs a real HTTP boundary and receipt reader

**High, next T2 work.** The existing raw submission helper is not a socket server. Its trusted authorization input and raw-body/control precedence need an actual transport composition; reusing Update's authentication-before-body ordering without checking Transactional admission precedence can change which refusal occurs and whether a key is captured. Verify body bounds/syntax, trusted principal, idempotency key, media/accept controls and method precedence using malformed combinations, corrected-key retry and direct after-state. [Private receiver](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-submission.ts#L1) [Admission and atomicity](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L3835) [Transactional Problems](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L5274)

`store.receipt(principal,id)` is not the required receipt service: implement canonical navigable root and pages, GET/HEAD/status/cache rules, current Resource reauthorization, whole-receipt withholding, immutable continuation/restart, retention and pending recovery. Existing durable admission and commit/retract machinery should be reused, with real process interruption at owned boundaries and no fabricated response/outcome fixtures. [Private receipt accessor](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/transaction-store.ts#L1068) [Receipt contract](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L4945) [Receipt responses](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L4982)

### 6. Keep applicability honest without discarding recovery/erasure obligations

**Medium, qualification policy.** Current Transactional erasure rules are independently binding where applicable, even with optional History disabled. Every snapshot still needs its projected `erasures` array, including `[]`. If the supported authority can perform administrative erasure, observe digest-before-erasure, atomic successor/tombstone, Event/receipt withholding, snapshot/feed invalidation and live publication fences. A row involving erasure is not automatically optional History, nor does the protocol require inventing a public erasure command. Explicitly document which supported administrative paths can trigger these conditions; do not silently waive a mandatory row because the test fixture cannot trigger it. If the applicability policy cannot justify exclusion, retain a qualification gap. [Independent erasure obligations](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L6289) [Live successor/deletion rules](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L6380)

Likewise, ordinary restart must preserve the epoch/view, canonical Scope and durable key/receipt state. Restores that replace/discard history have different fencing rules. The current development listener derives Scope from its bound port; restart evidence must retain a stable canonical configured URL rather than accidentally create a different Scope at a new ephemeral port. An administrative restore endpoint, HA deployment and power-loss guarantee are not implied merely by a restart test. [History and recovery identity](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/docs/specs/bdp.md#L3648) [Listener-derived Scope](https://github.com/gastownhall/bdp/blob/caf5ca75a4e9b9c7865e61e97f849ab736c21e64/packages/server/src/development-runtime.ts#L282)

## Minimal sequence after U1/T1

1. **Start evidence composition now:** define cumulative required-ID selection with retirements, actual installation identity and fixture applicability; keep experimental configurations non-attesting while requirements remain uncovered. Add the four still-useful whole-carrier rejection observations from the older audit: duplicate keys, duplicate names, unknown labels and forward labels, proving neither effects nor key capture.
2. **U2 installed-contract/auth slice:** serve actual pinned schema/owned/aggregate contracts and trusted identity/policy variants through the same mutable owner. Exercise hidden/forbidden behavior, guarded owned-source revisions, no-op/provenance retention and diagnostic bounds. Reuse evaluator semantics; no new normative design.
3. **T2 serving slice:** adapt T1's actual owner to canonical discovery, the complete operation directory and singleton/batch/sequence transport; serve durable receipts and restart-safe receipt pages. Make set mutations and owned transitions an explicit adjoining evaluator/serialization slice, not an untracked omission. Profile still non-attesting.
4. **T3 bootstrap/stream slice:** atomic observed read context and minimum barriers, snapshot/page lifecycle, changefeed finite/SSE and Event Source finite/SSE, epoch/view invalidation, conditional/HEAD ordering; replica bootstrap plus subsequent groups must reconstruct the configured visible graph. Include mandatory empty erasure framing and test supported erasure/recovery paths rather than treating them as History.
5. **U3/T4 qualify and activate independently:** finish each profile's applicable executable requirements, meaningful negative controls, packaged cold-client navigation and restart/disconnect/fault observations; generate fresh evidence bound to that exact configuration/source, then broaden production admission only for the completed profile. Update need not wait for Transactional. Existing bdpbd Read remains separately qualified.

Root should own the shared authority/configuration interfaces, evaluator fixes, diagnostic/limit wiring and catalog/admission integration. U1/T1 can merge independently only while their shared-interface changes remain compatible; neither worker should repurpose the other's store or publish claims before cumulative evidence.

## Validation gates

- **Entry:** exact clean source; pinned Node/pnpm; bounded isolated stores and stable canonical URLs; installed bytes, credentials/policy identifiers and retention/bounds recorded without secrets. No old target's evidence transferred.
- **Per slice:** typecheck/build, focused parser/evaluator/store tests and actual HTTP/client observations with after-state and corrected-key discriminators. Mutating one expected guard/context/cursor/identity condition must fail the observation. Tests of authored fixtures alone do not prove server behavior.
- **Cumulative qualification:** required current catalogs plus companion obligations, explicit retirements and justified applicability, all on the same advertised configuration. Test Read behavior after mutations and restarts, not only on a separate static Read fixture. Include metadata and full revision-provenance retention across reads, retries, receipts and replication.
- **Publication gate:** full relevant serial suite, boundaries/schema/catalog/citation/fixtures checks, packaged smoke/preflight and fresh evidence verification. Keep source and direct-successor evidence commits distinct where the sealed-evidence policy requires it. Do not regenerate unrelated existing Read evidence merely to disguise changed write-target coverage; follow the actual artifact dependency policy.

No product question needs to interrupt U1/T1/U2 or the cumulative evidence work. A later proposal to relax a required contract, introduce optional capabilities, or support an incompatible administrative recovery model would require an explicit ruling; implementation difficulty alone is not such a ruling.
