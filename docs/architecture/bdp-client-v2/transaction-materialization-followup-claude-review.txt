**3. MEDIUM — The decisive stress fixture spends 33 of the 64 proof units; the reachable operations-plus-matches shape is unmeasured and not in the disclosure list**
`bdp-integration-logs/transaction-materialization-followup/stress.mjs:45-56`; report.md §"Result and scope"; doc:1071

The proof's per-unit budget is `K = M + maximumOperations = 32 + 32 = 64` (`transaction-events.ts:27`, doc:1071). `matchedResources` is incremented only inside the set-operation branch (`transaction-batch.ts:833`), so one admitted transaction may carry 32 matched set members **plus 31 explicit owned resource operations** — 63 of 64 units. The measured fixture submits exactly one operation (the `updateWhere` built at `stress.mjs:45`) against 32 matches, i.e. 33 units; `assert.equal(resultCount, count+1)` at :56 confirms it. Each added explicit owned update contributes two ≤R upserts (~524 KB of group) and one ~262 KB receipt entry *without* drawing more from the single 65,536-byte Q, so the reachable shape is group ≈51 MB against the measured 35,207,784, over a seeded graph of 63 full-R source/Link pairs instead of 32 — a seeded baseline essentially equal to the killed M64 run's (`293056` KiB at seed end there vs `279584` KiB here at 32 pairs). The F2 disposition closes the prior finding with a per-record feasibility argument ("owned source embeds the Link, so two independently exact-R records are impossible for this shape"), which is correct but addresses record size only, not unit count. The disclosure list names collection scans, accumulated history and "other graph shapes"; it never names this combination, while §"Result and scope" says the tuple "completed the stronger workload."

*Failure scenario:* an admitted transaction of 31 explicit owned `updateLink`s plus one 32-match `updateWhere` lands in the same RSS band as the M64 run the supervisor killed — i.e. the measurement that rejected M64 has not been applied to M32's own reachable shape, so "measured headroom" at M32 rests on a workload at roughly half the serialized budget.
*Remedy:* one additional supervised dense variant seeding 31 extra `n≠0` pairs and submitting 31 explicit `updateLink` operations alongside the `updateWhere`; **or**, if no new run, one sentence in report.md §"Result and scope" and in doc §"Stronger owned materialization measurement" stating that the measured workload spends 1 of 32 permitted explicit operations and that a single transaction combining the full operation budget with the full match budget is reachable and unmeasured.

**4. MEDIUM — No emitted-process artifact records which tuple the stress and the prior-store probe actually measured**
`stress.mjs:5-6,19,56`; `compatibility.mjs:8,14`; `build.log` / `build-m32.log`

`stress.mjs` imports only `openTransactionStore` and `prepareTransactionSetCore` from `dist/`, and takes its match count from `BDP_STRESS_MATCHES`; it never imports `TRANSACTION_RUNTIME_LIMITS`. A 32-member workload therefore runs identically on an M32 and an M64 `dist/` — and that is not hypothetical: `preliminary-dense-m32-on-m64.*` is precisely that run. `assert.equal(resultCount, count+1)` only proves 32 matches were *accepted*, which both builds do; there is no negative probe (33 matches must refuse). `build.log` and `build-m32.log` are byte-identical (`$ pnpm clean && tsc -b` / `$ tsc -b --clean && node scripts/clean-build.mjs`), so the only thing separating `stress-dense-m32.*` from `preliminary-dense-m32-on-m64.*` is file mtime. The companion probe asserts the **old** build's `matchedResources === 64` at `compatibility.mjs:8` but never asserts the current build's value, then prints `newMatched:32` and `refusalBeforeMaintenance:true` as hardcoded literals in the PASS line (:14). What the probe actually establishes is "the current tuple *differs* from the frozen M64 tuple" (via `assert.throws`) and "no bytes were written" (via `deepEqual`); "is 32" and "before maintenance" are asserted by fiat in the output.

*Failure scenario:* a partial or stale `tsc -b` leaves `dist/` at the previous tuple; the dense run completes at `540304` KiB and is filed as the M32 qualification with nothing in the package contradicting it. The report's "the actual emitted M32/E256 tuple completed the stronger workload" then rests on unrecorded build state rather than on evidence — the same gap F11's exit-code discipline was adopted to remove.
*Remedy:* in `stress.mjs`, import `TRANSACTION_RUNTIME_LIMITS` from the same `dist/transaction-batch.js` and `assert.equal(TRANSACTION_RUNTIME_LIMITS.matchedResources, matchMaximum)`, logging the full tuple in the `open` stage; in `compatibility.mjs`, import the current build's tuple, assert `matchedResources === 32`, and derive the logged `newMatched` from it instead of writing the literal.

**6. LOW — The upsert-wrapper closure has no cardinality assertion and compares `resource` to itself**
`packages/server/src/transaction-owned.test.ts:209-214`

The F3 deliverable is `for (const change of f.group().changes) expect(change).toEqual({operation:"upsert", resourceKind: "source" in change.resource ? "link" : "bead", resource: change.resource})`. Both derived fields are read off the object under test: `resource: change.resource` is a tautology (the body is pinned only in the separate test at :641), and the loop has no length assertion, so a group with zero changes satisfies this specific check vacuously. The sibling-rejection property F3 asked for does hold; the resource-content and presence properties do not come from this assertion.

*Failure scenario:* a change that drops the source upsert from an owned update leaves this wrapper assertion passing (it would be caught indirectly by the revision-chain assertions later in the test, but not by the check added to guard the premise).

**7. LOW — Only `1e20` is pinned exactly; the other three numeric witnesses have 1.3×–7× slack**
`packages/server/src/transaction-materialization.test.ts:299-302`

`expect(Buffer.byteLength(literal)).toBeLessThanOrEqual(7 * Buffer.byteLength(token))` is the only constraint on `-9e20`, `9e9` and `-0.0000010000000000000002`, whose observed ratios are 4.4, 3.33 and 1.0 — a normalization change that pushed any of them to just under 7× would pass. The tight guard is `if (token === "1e20") expect(literal).toBe("100000000000000000000")`, applied to one of four cases. Note also that both sides of `expect(stringifyJsonValue(change.slice(0,2))).toBe(normalized)` run through `stringifyJsonValue`, so that assertion correctly proves the stored Event holds normalized values rather than retained lexical/lossless tokens (its stated purpose) but cannot by itself detect a serializer change. F4's requested `<=7` witness is delivered; this is about its resolution.

*Failure scenario:* a V8 or `stringifyJsonValue` change that alters small/negative-exponent spelling (e.g. widening `-0.0000010000000000000002`) passes both the per-token bound and the document-level bound, and the `E*N` term silently loses margin with no failing test.
*Remedy:* pin the expected normalized output for all four tokens the way `1e20` is pinned — four added string literals in the `it.each` body — so the witness fails on any expansion change rather than only above 7×.
