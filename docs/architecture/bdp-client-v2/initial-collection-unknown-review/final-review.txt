## Blockers

### BLOCKER‑1 — Formatter violation: new line exceeds `lineWidth: 100`
**File/line:** `packages/server/src/transaction-read.test.ts:618`

```ts
      { operation: "createLink", id: "links/out", type: link, source: "beads/a", target: "beads/b" },
```

**Issue:** This line is **101 characters**, over `biome.json:14` (`"lineWidth": 100`). Biome/Prettier counts the trailing array separator in its fits check — confirmed empirically by `packages/server/src/transaction-dependencies.test.ts:404`, which sits at *exactly* 100 **including** its trailing comma and stays flat. The object is breakable, so the formatter will expand it. It is also the only breakable `>100` line in any of the four changed files (every other `>100` line in all four is an atomic `it("…")` title or template literal, which the formatter cannot break).

**Impact:** `pnpm format:check` (`biome format .`, `package.json:19`) exits non‑zero, failing the planned static/build gate. No behavioral impact. The report's "Source diff whitespace check passed" does not cover print width, and the report explicitly states the formatter was not executed.

**Smallest correction:** either accept the formatter's expansion

```ts
      {
        operation: "createLink",
        id: "links/out",
        type: link,
        source: "beads/a",
        target: "beads/b",
      },
```

or shorten the identifier to keep one line (`id: "links/b"` → 99 characters).

### BLOCKER‑2 — Inline comment misattributes the mechanism for two of its four cases
**File/line:** `packages/server/src/transaction-http.test.ts:4899` (comment) covering the loop at `4900–4911`

```ts
  // Parser failures still hit the early unknown-token gap; this is an excluded residual.
  for (const suffix of ["types/", "beads/a?view=links", "beads/?limit=0", "beads/?limit=1&limit=2"]) {
```

**Issue:** Only two of the four suffixes are parser failures at the early gate:

| suffix | actual mechanism |
|---|---|
| `beads/?limit=0`, `beads/?limit=1&limit=2` | `requestFromUrl` → `invalidParameter()` (`read-request.ts:260`, `read-request.ts:310`) → early gate `transaction-http.ts:583–587` → `developmentGap("minimum-position")` |
| `types/` | **not** a parser failure — parses to `{kind:"collection",collection:"types"}`, classified `"strict"` by `currentReadMinimumKind`, so it hits the *same* early gate via the second disjunct |
| `beads/a?view=links` | **not the early gate at all** — parses to `{kind:"bead-links",…}`, classified `"missing"`, passes `transaction-http.ts:583–591`, **enters the owner**, and fails *late* with `TransactionMinimumUnsupported` from `checkCurrentReadMinimum(…, waitable=false)`, rendered by the handler catch at `transaction-http.ts:647–648` |

The assertions themselves are all correct (500 / `minimum-position` / no `bdp-scope-position` / empty body / no added wait — I traced each). It is the stated cause that is wrong, in a repo whose accepted plan and disposition both insist on naming residual mechanisms precisely ("add two **named** parser residual checks"; "Keep `minimum-position` and `minimum-position-route` distinct").

**Impact:** Misleading record of which residual each case proves; an unchanged‑behavior claim ("still hit the early gap") that is false for `beads/a?view=links`, which actually reaches the owner and is refused after classification.

**Smallest correction:** reword to cover both mechanisms, e.g.
```ts
  // Excluded residuals: strict/parser-rejected routes stop at the early unknown-token gap,
  // and the incident-Link route is refused after classification. Both keep the private label.
```

## Optional improvements

**OPT‑1 — `expect(allocations).toBe(0)` is an unanchored oracle** (`transaction-read.test.ts:694`, `718`).
Nothing in the new callback ever invokes `generateOpaqueToken`, so a mis‑wired pagination seam would make the assertion vacuously true. This matters specifically here because `createTransactionService` rebinds and freezes a *copy* of `pagination` (`transaction-service.ts:84–99`), i.e. the seam is not the object the test handed in. The 2‑beads/2‑links + `limit: 1` setup exists precisely so a successful page *would* allocate, but no successful page is ever read. Compare the existing `818–873` callback, which does anchor its count. Smallest correction — append after `expect(ownerChecks).toBe(13)` (adds 1 entry, 0 waits, after every count assertion):

```ts
      const served = await service
        .readAtMinimum(principal, { ...minimum, minimumPosition: "pos-1" })
        .perform(request);
      expect(served).toMatchObject({ kind: "success" });
      expect(allocations).toBeGreaterThan(0);
```

**OPT‑2 — uneven 503‑rendering oracle for the two alternate tokens** (`transaction-http.test.ts:4886–4897`). The four collection pairs assert `content-type` and `content-length`; the `pos-01` / `pos-9007199254740992` requests assert neither. The plan only required body/context for these, so this is discretionary; adding `expect(response.headers.get("content-type")).toBe("application/problem+json")` makes the eight timeout responses uniformly oracled at zero cost.

**OPT‑3 — `toBeLessThan(5000)` is effectively dead** (installed test `:515`). `requestTimeoutMs: 5000` (`:257`) aborts the exchange before a 5000 ms response can be observed, so a slow server surfaces as a transport throw rather than this assertion. If you want a diagnosable upper bound, use a value inside the executor budget (e.g. `toBeLessThan(4000)`); otherwise it is harmless documentation of the existing ceiling.

**OPT‑4 — installed evidence covers only the filtered target.** All four added exchanges reuse `target` from `:420` (`?limit=32&type=…`). The plan sanctioned this, and the direct/HTTP callbacks cover the unfiltered form, but swapping one of the four to `${scope}${collection}/` would give an unfiltered installed witness at no extra exchange.
