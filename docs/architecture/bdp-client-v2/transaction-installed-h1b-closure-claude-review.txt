## Findings

### 1. MEDIUM — Non-enumerated harness refusals still publish as target failures with the cause erased

`packages/conformance/src/runner.ts:1069-1075`, `runner.ts:954`, `packages/conformance/src/transactional-observation.ts:171,173,222,234-262`

External F1's fix (b) had two halves: pass the typed error through `runProgrammaticAction`, **and** "record `failure.cause` message in `executionError.message`". Only the first half shipped:

```ts
: error instanceof ScenarioDeadlineError || error instanceof TransactionalHarnessError
  ? error
  : new ScenarioActionExecutionFailure("action execution failed", { cause: error });
```

Anything in the private receipt lane that is not a `TransactionalHarnessError` still collapses to `state: "fail"`, `reason: "action execution failed"`, `executionError.message: "action execution failed"`. Reachable cases, all on a real 200 receipt GET (so all after `observe()` runs — assertions are thrown first, which is why the new 401 witness never reaches them):

- `runner.ts:954` `retained receipt schema or identity mismatch`
- `transactional-observation.ts:222` `retained receipt differs from original wire facts`
- `validateReceiptWire` :234/:237/:240/:244/:247/:253/:262 — seven plain `Error`s

The `validateReceiptWire` family compares the harness's own wire capture against its own parsed response. A mismatch there is a harness-evidence defect, and it is now published as **negative target evidence** — the exact contradiction of plan item 7 that F1 raised, in a lane the closure did not enumerate.

Symmetric residue in the register lane: `transactional-observation.ts:173` (`source receipt schema invalid`) and the `validateReceiptWire(response, "GET")` call at :188 are plain `Error`s, so they fall to `runner.ts:783`'s final `else` → `harness-error` with reason **`"scenario harness failed"`**. Right lane, reason gone.

Net: `receipt wire headers mismatch` reports as `harness-error`/"scenario harness failed" if it fires during registration, and `fail`/"action execution failed" if it fires during the read. Neither report names the refusal, so the new countercontrol discipline at `transactional-matrix.test.ts:352-360` cannot be extended to these.

**Fix:** make `validateReceiptWire`'s throws and `transactional-observation.ts:173` `TransactionalHarnessError`. For the two genuine target-misbehaviour cases (`runner.ts:954`, `transactional-observation.ts:222`) keep `fail` but carry the reason — throw `ScenarioObservationFailure` (already mapped to `fail` with `error.message` at `runner.ts:726`) and add it to the passthrough list at `runner.ts:1072`. Then pin one wire-evidence reason in the matrix countercontrol the way `binding`/`method`/`credential` now are.

### 2. LOW — F4's reader was removed but the writer was kept: `entry.wire` is dead retained state

`transactional-observation.ts:84` (`wire: Buffer`), `:199` (`wire: Buffer.from(response.wireResponseBytes)`)

Grep over `packages/conformance/src` returns **zero** reads of `entry.wire` after the `resolve()` self-rehash was dropped. `responseDigest` is likewise write-only (`:194` writes it; nothing re-derives it — it is report provenance, which is the accepted disposition). So each ledger entry retains a full defensive copy of the receipt-producing response wire — ceiling 2,097,152 bytes, up to `maximum` = scenario action count entries — that nothing can read. The actual read-time check is `validate()` at `:221`, which compares parsed JSON bodies, not bytes.

F4 offered "drop the branch as dead defensive code, **or** make it meaningful". The closure did the first and left the state.

**Fix:** drop `wire` from the ledger entry type and the `Buffer.from(...)` at `:199`. If the retained wire should instead be meaningful, compare it against the subsequent read's `response.wireResponseBytes` inside `validate()` — that is a real check, unlike the removed self-rehash.

### 3. LOW — Reopen's close phase still inherits `requestTimeoutMs`, so the documented 10-second lifecycle budget is not uniform

`runner.ts:983` → `transactional-observation.ts:114` → `transactional-execution-binding.ts:202` → `raw-http-scenario-target.ts:61,87`

The reopen *action* now gets `prepareTimeoutMs` (10 s in the matrix) — that part is correct and is what the new synthetic unit proves. But `context.reopen` first does `await target.close(signal)`, and `createRawHttpScenarioTarget` computes `cleanupTimeoutMs = snapshot.requestTimeoutMs ?? 30_000` = **5000** (`transactional-execution-binding.ts:187`), then bounds cleanup with `AbortSignal.any([signal, AbortSignal.timeout(cleanupTimeoutMs)])`. So the shutdown half of reopen — `controller.abort()`, `Promise.allSettled([...pending])`, then `child.close()` whose own launcher bound is **10 s** (`scripts/transaction-installed-observation.mjs:31`) — is capped at 5 s, inside which a 10 s child close cannot complete. On expiry `settleCleanup` (`raw-http-scenario-target.ts:292`) rejects → `TransactionalHarnessError("transaction session reopen failed")`: the same flaky-harness-error outcome F6 described, from a different trigger.

`docs/design/transaction-harness-review-closure.md:25` ("Preparation/reopen retains its 10-second lifecycle budget") overstates this, and `transactional-cumulative.test.ts:408-487` uses a synthetic context that bypasses `target.close()` entirely, so it cannot see it.

**Fix:** add an explicit `cleanupTimeoutMs` option to `createRawHttpScenarioTarget` (defaulting to today's `requestTimeoutMs`) and set it to `10000` beside `requestTimeoutMs: 5000` at `transactional-execution-binding.ts:185-190`, so the nesting is monotone with the launcher's 10 s `bounded()`. Then state the actual nesting in the design doc.

### 4. LOW — The new `retainedSource` authority branch is unreachable, untested, and widens the documented model

`transactional-observation.ts:158-161, :170`

`retainedSource` needs `register()` called with `method === "GET"` on a URL already in the ledger. `register()` is only reached from runRequest's capture loop under `transactional && served` (`runner.ts:1458`), and every receipt GET goes through the dynamic lane, which calls `runRequest` with `captures: []` and `transactional: undefined` (`runner.ts:916-920, 937, 943`). An ordinary exact GET to a receipt URL is refused earlier because receipt routes are absent from the base exact route table. And no manifest row captures `/id` from a receipt GET — all four rows' receipt-read captures use `/body/...`. The branch cannot fire, and no unit test drives it (the new observation tests cover the POST-mutation and ordinary-resource routes only).

This matters because the branch *grants* authority, its guard at `:170` is a plain `Error` (finding 1), and both `dispositions.md:6` and `docs/.../closure.md:27` assert authority may come from "an already authorized receipt read" — prose the code cannot currently honour. The native P2 repair was explicitly motivated by reusing this runner for inherited Read/Update rows, which is exactly the change that would make it live.

**Fix:** either drop `retainedSource` and the `|| retainedSource` disjunct and align both documents to "canonical mutation response only", or add a unit test that calls `register()` with a receipt-GET request and pins both the accept and a typed `isDeepStrictEqual` reject.

### 7. LOW — `observe()`'s cleanup wrapper can mask the cohort deadline reason

`transactional-matrix.test.ts:236-247`. When the run fails *and* `target.close()` fails, `failure` becomes `AggregateError(..., "installed cohort cleanup failed")`, whose `.message` no longer contains the deadline reason — and the new cohort witness at `:541` asserts `rejects.toThrow("installed cohort deadline")`, so it depends on cleanup succeeding. ### 8. INFORMATIONAL — abort-path drain ordering is no longer strictly "drain, then close child"
