# Findings

### 1. Low–Medium — `maximumGroupsPerObservation` is hashed into configuration identity but no code enforces it
**Where:** `packages/server/src/transaction-events.ts:20-23`; consumed at `transaction-runtime-configuration.ts:114` (into `settings` → `transactionRuntimeDigest` at `:378-388`); asserted at `transaction-runtime-configuration.test.ts:572,613` and `apps/bdptest/src/transactional-event-sse-installed.test.ts:271`.

**Impact:** The owner's one-group bound is implicit in `eventPacket` — exactly one `retainedGroupReader()(at, head)` call and a single `at++` (`transaction-store.ts:661-698`). Only `packetBytes` is actually read (`transaction-store.ts:683`). Plan §127 requires the group-step limit be "consumed by owner **and** runtime configuration metadata rather than duplicated." Today the configuration digest and the installed witness attest a mechanic that nothing honors: changing the constant to `2` would change `runtimeConfigurationIdentity` and the installed report while the owner keeps stepping one group, and the reverse (relaxing the owner loop) would not trip any assertion. This is advertised-vs-actual drift in the one artifact the plan designates as evidence, not a current misbehavior.

**Fix:** make the bound load-bearing in `eventPacket`, e.g. `for (let groups = 0; groups < TRANSACTION_EVENT_STREAM.maximumGroupsPerObservation && at <= head; groups++) { … }` with the existing body (and keep the byte/item break as the inner exit), or — if the one-group shape is meant to stay structural — add a module-scope guard in `transaction-store.ts` next to the import: `if (TRANSACTION_EVENT_STREAM.maximumGroupsPerObservation !== 1) throw new Error("owner scan implements exactly one group per entry")`.

**Missing discriminating test:** none of the three assertion sites would fail if owner behavior and the constant diverged. Add a store-level test that derives the expectation from the constant rather than from the literal `1` — e.g. seed `k` consecutive relevant groups and assert `packets.length` / body-GET counts are a function of `TRANSACTION_EVENT_STREAM.maximumGroupsPerObservation`, so the metadata and the behavior cannot drift silently.

### 2. Low — `settings.eventStream` contains no timers; the Event stream's cadence and live-slot gate come only from `changefeedStream`
**Where:** `transaction-runtime.ts:210-216` passes `settings.changefeedStream` to `pumpTransactionEvents`; `transaction-runtime-configuration.ts:300-306` validates and gates `liveStreamsAvailable` off `changefeedStream` alone.

**Impact:** Functionally this is the reuse the plan asks for (§92, §127: "preserve poll/heartbeat/live-slot settings"), and it is why the finite-only short-timer seam correctly refuses live Event streams. But the captured settings now expose a sibling key named `eventStream` that governs neither poll nor heartbeat nor the live gate, so a future reader (or a future timer change) can reasonably mis-attribute Event-stream cadence to it. The installed report at `transactional-event-sse-installed.test.ts:270-273` prints `eventStream` next to `deadlines`, reinforcing the misreading.

**Fix:** no behavior change needed. Either rename to something scope-accurate (`eventScan`) or add a one-line comment at `transaction-runtime-configuration.ts:114` stating these are owner scan/packet mechanics only and that Event stream timers are `changefeedStream`.

**Missing discriminating test:** nothing asserts that the Event pump uses `changefeedStream`'s poll/heartbeat. The installed idle test (`:243-252`) observes ≥2 comments over 15.1 s, which is consistent with the 5 s default but does not bind the Event path to that settings key. A source test passing a distinguishable `{pollMilliseconds, heartbeatMilliseconds}` through the runtime seam and observing Event comment cadence would pin it.

### 3. Low (test coverage) — a valid `Last-Event-ID` overriding a *valid* query `after` is never observed on delivery
**Where:** `transaction-http.ts:478-487`, specifically `fields.length === 1 ? fields[0] : eventRequest.after` at `:483`. Tests: `transaction-event-sse.test.ts:424-429` and `:341-346`.

**Impact:** The implementation is correct (header wins; the query value is syntax-checked by `transactionEventRequest` but never looked up). But every override case in the suite uses a query cursor that would independently *fail* (stale / foreign / unissued) and is probed with `HEAD`, so only "no error" is proven. The only delivery-observing reconnect (`:341`) has no query `after` at all. Plan predicate 2 asks for "Last-Event-ID override **with/without query**"; the "with query" half is unpinned for the suffix actually streamed. An inverted precedence (`eventRequest.after ?? fields[0]`) would still pass the whole suite for the both-valid case.

**Fix (test only):** add a GET case with two *valid, differently positioned* cursors — e.g. `events/?after=<first event id>` plus `Last-Event-ID: <last event id>` — and assert zero event frames (header wins). The mirror case (`?after=<last>` + `Last-Event-ID: <first>`) should deliver the full later suffix. Both are sharp: header-vs-query precedence flips the frame count.

### 4. Low (test coverage) — the runtime's initial-packet release is asserted by nothing
**Where:** `transaction-runtime.ts:217-219` (`selected = undefined;` after the pump is constructed).

**Impact:** Plan predicate 8 requires "The actual calling chain releases obsolete/initial packets rather than retaining them in a closure." The line is present and correct, but deleting it would not fail any test — the pump's internal release (`transaction-sse.ts:106-107`, `:116`) is also untested for reachability. There is no `WeakRef`/`gc` instrumentation anywhere in the four relevant suites. This is the one predicate-8 clause with no executable witness.

**Fix (test only):** in the source-level HTTP/pump test, hold a `WeakRef` to the `event-stream` result (and to the first `TransactionEventPacket`), drive one successful advance, then assert `deref() === undefined` under `--expose-gc`. If the repo does not want a GC-dependent test, at minimum spy the runtime seam to assert the pump's `next` adapter closure does not capture the initial result object.

# Notes (verified clean / no action)

- **Immutable owner-local continuation:** `advanceEventScan` accepts only the opaque token; state lives in a per-owner `WeakMap` with no enumerable registry; fabricated / foreign-owner / reopened / closed / fenced / head-regressed / context-changed are all refused (`transaction-store.ts:1624-1637`, tests `transaction-events.test.ts:860-878`, `:936-964`). No SQLite handle, iterator, statement or parsed group is retained. Replay of an older genuine continuation is side-effect-free.
- **One group per pull, zero historical body reads at idle:** `retainedGroupReader()` is constructed strictly inside `if (at <= head)` (`transaction-store.ts:661-662`), so a caught-up advance performs zero `FROM groups` prepares and zero body GETs; the 13-group oracle at `transaction-events.test.ts:794-859` pins exactly 1 body GET and 2 group prepares per inspecting advance and 0/0 when caught up. I confirmed `groups.position` is contiguous `1..head` (single insert site `transaction-store.ts:1259-1262`, atomic with the position bump), so `at <= head` can never raise the gap fault spuriously.
- **Ordinal / same-group pagination and byte parity:** `eventCandidateBytes` is now the single charge used by both finite and stream collectors, with byte-for-byte identical arithmetic to the pre-change inline computation (envelope − 4, comma accounting, `json(event)`, reserved `eventContinuation`), and `json` is `stringifyJsonValue` (`transaction-batch.ts:956`), so the frame-bound proof holds. A bound break keeps `at` and advances `ordinal` only to the last included Event; `complete` is the only path that moves to the next group with `ordinal = -1`, and `complete === false` implies `events.length ≥ 1`, so no livelock and no skipped ordinal. Finite lookahead and `next`-null behavior are untouched.
- **Shared pump:** continuation is read after the frame loop and adopted only after `next()` returns; `packet = undefined` before the heartbeat/idle wait, so at most one packet plus one pending frame is live. Heartbeat is evaluated at every next-pull boundary including empty backlog packets, through the same `write`/drain barrier, with `caughtUp ? delay(poll) : setImmediate` — matching plan §88 exactly. The changefeed adapter is behaviour-preserving (`continuation = groups.at(-1)?.checkpoint ?? page.after` equals the old per-group `after` tracking; the new heartbeat check cannot fire because `lastWrite` was just set).
- **Capacity and context:** the stream slot is the single global `maximumStreams` map shared by both kinds; `streamContext` is captured before `activeService.stream` so `TransactionStreamCapacityError` projects `503` with the *initial* observation tuple, and `TransactionEventParameterError.context` carries the entry tuple for known-source `400`. The entry-pairing test at `transaction-event-sse.test.ts:609-670` commits between observation and projection and pins `pos-1` / `pos-2` against a later `pos-3`.
- **HTTP ordering:** unchanged — raw target/method → auth `401` → query grammar `400` (pre-owner, contextless) → unknown source `404` → minimum (`behind` → one non-renewing deadline → `503 catch-up-timeout`) → reconnect validity `400`. `waitForTransactionMinimum` retries only `behind`, so `invalidReconnect` cannot shortcut a pending minimum. Empty header is not absent; `genesis` is rejected; JSON ignores all reconnect values. `406/304/412/HEAD` retain all three context headers and create no slot (`streamResponse` returns a `kind`-less response that falls through `applyReadHttpSemantics`), and `Content-Length`/`ETag`/`Last-Modified` are absent on successful SSE.
- **Scope/bead/link semantics, retained deletion, projection gap:** source identity, membership, self-Link double endpoint facts and ordinal preservation are unchanged in `projectTransactionEventGroup`; `identities` rows survive `deleteResource`, so retained deleted Sources stream while canonical GET is `404`. The metadata-only incident gap is refused pre-header when it lands in the first scanned group and post-header otherwise, closing without a second status — and because the initial entry reads only one group, reconnect-at-the-last-complete-ID deterministically returns `200` and then faults at the same group, which is what `transaction-event-sse.test.ts:531-557` asserts.
- **No new public admission:** `index.ts`, the testing barrel and `package.json` are untouched; all new exports are intra-package.
- One deliberate test repurposing worth recording in the freeze notes: `transaction-events.test.ts:474` changed the finite-suite `406` probe from `Accept: text/event-stream` to `text/plain`. That is required (the route now serves SSE) and the new suite covers negotiation, but the finite suite no longer pins anything about `text/event-stream`. Relatedly, a negotiation failure on the Event route still runs the *unbounded* finite scan to obtain its context (`transaction-http.ts:467-476`) before returning the bodyless `406` — correct per §99 and identical to the pre-existing finite/changefeed behavior, just not the bounded one-group path.
