## Findings

**1. Blocker — `apps/bdptest/src/transactional-event-missing-context-installed.test.ts` (`finally`, ~L332‑345): `controller.abort()` runs before `await child.close()`, risking a double close.**
The same `controller.signal` is handed to `launchInstalledTransaction(entry, config, controller.signal)` (~L148‑158), and the supplied launcher contract states "abort triggers close … It removes abort listeners". Unlike `runtime.close`, the launcher's `close` is *not* documented as memoized. So the unconditional `controller.abort()` starts a close, and the explicit `await child.close()` then re-runs the sequence against an exiting/exited child: the `close` command is sent on a dead IPC channel (throw) or the 10 000 ms clean-exit wait elapses and the child is killed. Either outcome pushes into `failures`, so a fully successful 11-exchange observation reports `outcome:"failed"`, `closed:false` and throws `AggregateError`. The source HTTP test is immune only because nothing wires the runtime to that controller. This file has never executed, so this would surface on the first installed run.
*Smallest fix:* move `controller.abort()` to after the `child.close()` try/catch (the deadline timer already aborts; no exchange is in flight at `finally`, since all are awaited), or make the launcher's `close` idempotent.

**2. Blocker — owner `missing` shape change is observable to every caller, and only a 9-case selector ran.**
`transaction-store.ts:1553` / `1636‑1639` widen both `missing` members, and `:1565‑1566` / `:1652‑1653` now return `context`. Two concrete break classes are *not* covered by the reported evidence (7 stages + 9 selected callbacks + 1 emitted control): (a) any remaining `toEqual({ kind: "missing" })` / `toStrictEqual({ kind: "missing" })` on `readEvents`/`beginEventScan` outside the two patched test files now fails on the extra `context` key (`toEqual` rejects extra defined properties); (b) any conformance rule or snapshot pinning the exact header set of a `view=events` `404` now sees three new `BDP-*` headers — note `docs/specs/bdp.md:5661‑5668` mandates only that unknown and out-of-projection identities return *the same* `404`, which this preserves, but it does not mandate context on problem responses, so a nondisclosure-style rule would flag it.
*Smallest fix:* run `packages/server` and `packages/conformance` unfiltered before merge; do not rely on a `-t` selector for this change.

**3. Major — `docs/design/transaction-implementation-progress.md` (new section, ~L1852): "These tests have not yet been executed at this draft checkpoint" is false for the source tests.**
Per the supplied disposition, four owner cases, the reconciled SSE case and the emitted-runtime HTTP case have each passed once, and the emitted-only control reproduced 8 named context failures. The progress doc is the evidence ledger, so this sentence misstates the record (understating, but still wrong) and will be read against the run artifacts.
*Smallest fix:* replace with the actual disposition — nine source callbacks passed once under a corrected selector; one emitted-only control run with 8 named context failures and 11 completed responses; the installed witness remains unexecuted.

**4. Major — installed file ~L77‑80: `validProblem` compiles `$defs/transactionalProblem` at module scope in a file that has never been imported.**
`mutationReceipt` and `eventPage` are proven by the executed source run; `transactionalProblem` is not. If that `$def` is absent or differently named, `ajv.compile` throws during collection: zero observations, no cleanup JSON, no indication of which assertion was at fault. If it exists but requires more than the four fields the source run proved (`type`, `code`, `retry`, `status`), the two GET assertions fail on a body already known correct — and `validProblem` adds nothing there, since `toStrictEqual(problem)` is strictly stronger. Same collection-abort exposure applies to `realpathSync(entry)` (~L59) and the two module-scope `execFileSync("git", …)` calls (~L62, ~L64).
*Smallest fix:* confirm `$defs.transactionalProblem` exists in `schemas/bdp-v0.schema.json` with exactly those required fields; otherwise drop `validProblem` from the 404 path and keep it only for the 401 body.

**5. Major — installed file ~L54‑66 + log `declaredSourceCommit`: the binding attributes uncommitted code to the parent commit.**
`sourceCommit = git rev-parse HEAD` resolves to `88c9408`, which provably does not contain the six-path draft under test. `workspaceDirty` is computed but never asserted and never folded into `installedTransactionBinding(child.ready, sourceCommit, fixture)`, so the emitted JSON reads as commit-attributed installed evidence. The existing guard is one-directional: overriding `BDP_TRANSACTIONAL_INSTALLED_ENTRY` requires a declared commit, but a declared commit requires neither a clean tree nor agreement with `entrySha256`.
*Smallest fix:* when `workspaceDirty` and no `BDP_TRANSACTIONAL_SOURCE_COMMIT`, pass a non-commit label (e.g. `${sourceCommit}+dirty-${entrySha256.slice(0, 12)}`) or throw, so the binding cannot be mistaken for a commit attestation.

**6. Medium — `packages/server/src/transaction-http.ts:495‑500` (finite branch) is pinned only through `dist`.**
The new HTTP test (`transaction-events.test.ts` ~L1090) imports `../dist/transaction-runtime.js` with no freshness check against `src`, so a stale `dist` yields a false pass. Per the supplied SSE dispatch breakdown (10 rows × GET/HEAD under `text/event-stream`, with `finitepage` and `JSON` counted separately), the source-executed SSE case exercises only the `beginEvents` branch at `:510‑515`. Consequently the finite `view=events` `404` header projection has no source-executed assertion. Secondary effect: a `src` unit-test file now hard-requires a prior build (`ERR_MODULE_NOT_FOUND` in a clean checkout or watch run, surfaced as the single thrown failure).
*Smallest fix:* add one source-handler assertion of the finite `404` context tuple (or compare the `dist/transaction-http.js` digest against a `src` build before importing).

**7. Medium — `transaction-events.test.ts` ~L1230 (`expect.soft` tuple block): the emitted log reports `failureCount: 0` on a failing run.**
Soft failures never reach the `catch`, so `failures.length === 0` and the JSON records `failureCount: 0`; the control run demonstrated exactly this (8 named assertion failures, `failureCount` 0). `verdict: "see-final-vitest-result"` mitigates only for a reader who knows to ignore `failureCount`, and the installed file uses a different key (`outcome`, computed the same unsound way) for the same pipeline.
*Smallest fix:* collect the three-header tuples into an array inside the loop and add one hard `expect(tuples).toStrictEqual(Array(8).fill(expected))` after the loop — this keeps the "collect all eight" intent while routing failures into `failures`/`failureCount`.

**8. Medium — `transaction-events.test.ts` ~L1010: `it.each` object titles interpolate with quotes, which already caused silent non-execution.**
`$mode`/`$kind` expand quoted in the actual Vitest names, which is why the first selector run reported 4 pass / 29 skip and did not qualify the eight intended checks. A selector that matches zero cases reports success, so this is a recurring evidence hazard rather than a cosmetic issue.
*Smallest fix:* use the array form with positional `%s` substitution — `it.each([["finite", "Bead", "beads/missing"], …])("captures immutable current context for missing %s %s Event source", (mode, kind, id) => …)` — which does not quote strings.

**9. Minor — the newly introduced fault path is asserted only in prose.**
`docs/…progress.md` claims "A missing or corrupt Scope metadata value follows the existing internal-fault path rather than fabricating context or silently returning a contextless 404." That is code-true (`transaction-store.ts:590‑599` throws on a non-canonical position), but it is a behavior change with no test: an unknown-id `view=events` read was previously infallible and now returns an internal fault when `metadata("position")` is corrupt.
*Smallest fix:* one owner case that corrupts the stored `position` row and expects `readEvents(`${scope}beads/missing?view=events`)` to throw.

**10. Minor — installed file, log `binding: binding ?? null`.**
The adjacent comment promises "never credential headers", but that constraint is enforced only for `responses` via `retainedHeaders`; the binding object is serialized wholesale to stdout, so whatever `bindServedProfileConfiguration` stores in its "auth identities" fields lands in CI logs. The operator token itself is safe here (the binding is derived from `child.ready`, and the contract verifies `listenUrl` carries no credentials), so this is a hygiene exposure, not a current leak.
*Smallest fix:* log an explicit field allowlist from `binding` (or a digest of it) instead of the whole object.

## Focus areas checked, no finding
- **Same-entry timing:** both new `readContext()` calls are inside the same `enter(() => …)` as `eventSourceKnown(source)` (`:1565‑1566`, `:1652‑1653`); `enter` is synchronous with a `busy` re-entrancy fence, and `eventSource`/`snapshotTransactionMinimum` remain outside it — so no second read, and malformed-source `400` stays contextless as claimed.
- **Privacy/auth:** `epoch`/`view` are store-scoped closures, not per-principal, and `scopePosition` is already disclosed by any authorized read, so the `404` discloses nothing new; HTTP `:389` still rejects unauthenticated before Event routing, and both tests assert the `401` carries no `BDP-*` headers plus the exact bearer challenge.
- **HEAD framing:** `read-http.ts:40‑48` sets `content-length` from the serialized body before removal and `transaction-runtime.ts:87‑95` leaves it alone when `selected.body === undefined`, so the GET/HEAD `content-length` equality assertions are sound; `response.body` is null for HEAD under undici, which the `reader`-guarded path handles to `""`.
- **Bounds and vacuity:** 1 + 1 + 8 + 1 = 11 matches both dispatch caps; the 32 768-byte reader cap precedes retention, and the reader `cancel()`/`releaseLock()` path aggregates cleanup errors with the primary rather than replacing it. `expect(Buffer.byteLength(body)).toBe(152)` is correct for the installed seed, and `expected[0]/[1]` truthiness plus `expected[2] === "pos-1"` prevent the all-`undefined` vacuous pass in both tuple comparisons.
