## Laws that need no administrative trigger

Canonical Resource identity may never be reassigned, including across deletion/authority replacement; retaining an old version preserves its address-to-state binding (I1–I2). A restore that loses the non-reuse guarantee creates a new logical Scope at a new canonical URL.

RU mutation, semantic identity, allocated IDs and terminal disposition are one durable member unit. Restart clears abandoned claims; committed sequence members remain retained, in-flight work is abandoned and unstarted members are not executed by recovery. These are RU continuity/partial-sequence laws, not TX atomic batch or exposed epoch behavior (RU1).

TX ordinary restart preserving identical committed history preserves its epoch (TX1). Every wire change group includes `changes`, `erasures`, `events`; projection advances have three empty arrays, no transaction and eventCount0, while a visible group has a nonempty payload class. Every snapshot manifest carries its projected erasure ledger, empty if no records have been committed (G1,E7). Current `erasures: []` and snapshot `readonly never[]` establish the no-record implementation shape only. They do not establish that an erasure was applied or survived recovery.

## Triggered laws remain mandatory when triggered

Erasure differs from local retention aging. Every obligated holder applies it; within a view receiving the record, the obligation is unconditional (E1). Historyfalse excludes optional History feature surfaces, not independent TX framing, permanent-ledger or controlled-retained-copy duties (H1,E7). No API absence is classified N/A.

An erasure is an administrative act outside BDP operations, so it has no MutationReceipt. The authority still mints a transaction identity and ordinary visible group at a position. It does not rotate the epoch. Historical-only erasure has empty changes/events. The digest scheme is exactly `sha-256-jcs`, over the original complete served version record including metadata, revisionProvenance and inline ownedLinks, excluding the links aggregate. Pre-metadata original digests stay bound to the original representation. A serialization escape is reported out of band and never delays cleanup; recovery/configuration identity hashes are not substitutes (E1–E3).

Erasing an owned Link version erases each retained containing source version in the same group. A live erased version needs its successor upsert or tombstone in that group. Direct property/metadata correction uses full root replacements; an owning source induced by an owned-Link correction carries only the ownedLink form. Incident-Link safety and agreement between first-class Links and complete inline owned sets remain mandatory (E3–E4).

For a receiving view at P, advance replay floor and expire pre-P checkpoints/snapshots. Stream eligibility, floor advance and complete erasure-group publication form one ordered step. Once any erasure is committed, its identity-level ledger persists for the logical Scope lifetime across restore, epoch and view changes, is projected in every snapshot, and reaches previous consumer generations. Retained addresses still cannot be rebound. Content whose erasure status cannot be established is discarded (TX1,E7). ## Why current interfaces cannot supply the witness

The RU owner has explicit new-logical-Scope creation, normal member/key lifecycle methods and startup inventory visitors. Its own recovery contract says it provides no logical import/export API, and opening a partial restore does not certify it (RU-API,RU-RESTORE). A direct member deletion or row edit is not erasure.

The TX owner creates an epoch only on new-store provisioning; ordinary same-configuration reopen reads the stored epoch and retracts pending receipts. Its options have no erase/import/restore or epoch-reset capability, and its schema has no erasure ledger. Ordinary group and snapshot constructors hardcode empty erasures (TX-OPTIONS,TX-STORAGE,TX-REOPEN,TX-GROUP,TX-SNAPSHOT). Creating a fresh store at an old URL cannot replace the missing restore contract.

Existing private administration is the bounded all-visible→empty authorization replacement. It drains mutation work through the owner, but hiding a view does not discard retained bytes or supply an erasure record. Its ordering pattern is relevant to a future design, not a generic administrative entry point to reuse unchanged (TX-ADMIN,TX-SERVICE). The installed TX bootstrap accepts only close after trusted configuration. The fdd public loader returns an inert immutable summary, holds prepared data in a private registry, and neither opens a store nor grants an administrative capability (TX-IPC,FDD-CAPTURE,FDD-REGISTRY). The explicit public export allowlist remains unchanged.

The existing copied hot-journal test exercises SQLite crash-image recovery with fault/clock/cache fixtures, including a recovered copy and installation refusal. It demonstrates neither history-changing logical restore, epoch rotation nor ledger survival. No new claim is made about power-loss behavior (TX-RECOVERY).
