## 1. [High] The prepared result carries the private TX runtime capture and plaintext RU credentials through a newly public package subpath

**Where:** plan.md §"Loader algorithm and return boundary" step 5 (`plan.md:49`), footprint row `packages/server/package.json` (`plan.md:63`).
**Source:** `packages/server/src/transaction-runtime-configuration.ts:310–403` — the capture's frozen return exposes `authenticate(supplied: Buffer)` (line 321), `readOptions(scope)` (333) and `metadata(actual, scope)` (353). `packages/server/src/installed-reference-configuration.ts:187–202` returns `credentials` holding plaintext `token`. Against this, `scripts/smoke-executables.mjs:535–536` and `549–550` deliberately assert that `@bdp/server/transaction-runtime-configuration` and `@bdp/server/installed-reference-configuration` resolve to `ERR_PACKAGE_PATH_NOT_EXPORTED`.

**Issue:** the plan describes the loader as "data/compilation only, never a start/admit factory" (`plan.md:41`) and the subpath as having "no start/admit operation" (`plan.md:94`), but step 5 says the frozen object contains "compiled/preflight data needed by later internal startup." For TX that is the capture object itself. `authenticate` is a bearer-credential oracle whose length check (`c.credential.length === supplied.length` before `timingSafeEqual`, line 323) is not constant-time, and `metadata` is the TX live-identity producer. Shipping either inside the returned value makes them reachable from any installed consumer of `@bdp/server/reference-configuration`, bypassing the existing specifier-level tripwires by value rather than by path, and pulls private runtime types (`TransactionHttpAuthorization`, `TransactionReadOptions`, `ReturnType<ReturnType<typeof openTransactionStore>["readConfiguration"]>`) into the emitted `reference-deployment.d.ts`.

**Impact:** this is not a secret-disclosure escalation — the caller supplied the tokens — but it directly contradicts the plan's own "No candidate/runtime/admission export" constraint (`plan.md:63`) and makes the new "data-only" surface non-inert. The plan frames the declaration leak as a type-ergonomics footnote (`plan.md:70`), not as capability exposure.

**Fix:** return only inert data (format, profile, canonicalScope, intended listener, matched limit tuple, artifact identity, RU configuration/artifact/policy/authentication identities, frozen projected input, file digest). Hold the live RU/TX capture objects in a module-private `WeakMap` keyed by the prepared handle (or an unexported brand) and reach them only from an internal accessor absent from `package.json#exports`. D3c loses nothing: `startInstalledReferenceCandidate` (`installed-reference.ts:8`) and `startInstalledTransactionCandidate` (`transaction-installed.ts:5`) already accept the raw projected input, and the plan already accepts deterministic re-capture (`plan.md:52`). Add negative assertions in `reference-deployment.test.ts` and `smoke-safety.test.mjs` that the prepared object has no `authenticate` / `metadata` / `readOptions` / `credentials` key.

## 2. [Medium] The envelope depth/node bounds are enforced after decode, so bytes are the only pre-decode bound

**Where:** plan.md step 2–3 (`plan.md:46–47`), contract.md §"Supported effective Read tuples" closing line (`contract.md:74`).
**Source:** `packages/protocol/src/json-admission.ts:98–193`. The decoder is documented to impose "no hidden nesting/wire limit" (lines 3–6) and pushes one `Frame` with its own `Set` per container (line 138); `admitJsonNumbers` → `mapLosslessJson` (231–291) then materializes a second full tree.

**Issue:** the plan says "require the successful value, then enforce envelope max depth 16 and 100000 nodes using a finite iterative traversal." Both bounds therefore run *after* a 32 MiB document has been fully decoded. A file of `[[[[…` or of millions of two-byte members is materialized first; the advertised depth/node protection describes post-decode validation, not parser work. Separately, the plan calls `admitJsonNumbers` without a diagnostic budget, and the API documents that omitting both bounds "explicitly requests the full list" (`json-admission.ts:45–46`): a document of inadmissible literals builds one frozen occurrence plus one formatted diagnostic per number, and those occurrences carry `pointer` (file-derived key names) and `literal`, which step 6 forbids from reaching the error.

**Impact:** robustness, not privilege escalation — the file is operator-supplied and trusted. But the plan's "safe bounded" framing overstates what the 32 MiB ceiling buys, and the planned negative test for "depth/node/32MiB bounds" (`plan.md:80`) will exercise only the benign small-document case.

**Fix:** before decoding, reject the text on a cheap structural pre-scan (count of `{`/`[`/`,` outside strings exceeding the 100 000-node budget, or running `{`/`[` nesting exceeding 16); pass `{ diagnostics: 1, diagnostic: () => ({ message: "unsupported number" }) }` to `admitJsonNumbers` so refusal is O(1) and carries no pointer or literal; if the pre-scan is not adopted, state in `contract.md` that the only pre-decode bound is bytes.

## 3. [Medium] The TX enforced Read tuple is a store-persisted value, so step 4's "actual fixed readOptions tuple" is a preflight claim the loader cannot settle

**Where:** plan.md step 4 (`plan.md:48`), contract.md §"Supported effective Read tuples" (`contract.md:67–74`) and §"Binding and limitations" (`contract.md:80`).
**Source:** `packages/server/src/transaction-service.ts:111–116` compares `capturedRead.advertisedLimits.page.maximumItems` against `owner.readConfiguration().receiptMaximumItems` and throws "receipt page maximum differs from installed owner". `packages/server/src/transaction-store.ts:317–330` serializes `receiptMaximumItems`, `snapshotLimits`, `snapshotTokenPolicy`, `runtimeLimits`, `contractIdentity`, `scope` and the sorted Type set into `metadata.configuration`, and line 599 refuses a reopen whose stored configuration matches neither the current nor the legacy serialization.

**Issue:** contract.md's deferred-check list names "Storage existence, compatible private store format, persisted Scope, installed live Type inventory, current policy/view and recovery" but omits the persisted `receiptMaximumItems` / snapshot-limit / runtime-limit / contract-identity equality that actually decides whether the matched tuple holds. Verified correct: the code constants are page 2/32, selector 4096/32/256, cursor 1000 ms (`transaction-runtime-configuration.ts:96–99,334–341` with `transaction-batch.ts:62` and `transaction-store.ts:251`), and RU is 20/100, 4096/32/256, 60 000 ms (`development-authority.ts:50–52`, consumed as `advertisedLimits` at `development-authority.ts:260–268`). The defect is the claim's strength, not the numbers.

**Impact:** a later composition or reviewer could treat the prepared "enforced Read limits" as settled and advertise them, while an existing store provisioned under different constants still fails at open — today *after* `listen` (`transaction-runtime.ts:316` precedes `326`, which the plan correctly flags at `plan.md:93`).

**Fix:** add persisted `receiptMaximumItems`, snapshot limits/token policy, runtime limits, contract identity and Type set to contract.md's explicit later-owner validation list; name the prepared field `preflightReadLimits` (or equivalent) and have the safe summary label the tuple as matched against code constants only.

## 4. [Medium] Two existing tripwires are not extended to the new module, leaving the plan's own guarantees unenforced

**Where:** footprint rows `scripts/smoke-executables.mjs` (`plan.md:64`) and `packages/server/src/transaction-snapshot.test.ts` (`plan.md:67`).
**Source:** `scripts/smoke-executables.mjs:509–520` filters deep-specifier refusals to names starting `installed-schema-` or `transaction-`, so `reference-deployment.js` is outside it; `522–559` is the explicit refusal list; `packages/server/src/transaction-snapshot.test.ts:678–680` scans only `["index.ts", "development.ts"]` for `transaction-snapshot` / `json-value-equality`.

**Issue:** (a) nothing will assert that `@bdp/server/reference-deployment` and `@bdp/server/dist/reference-deployment.js` still fail with `ERR_PACKAGE_PATH_NOT_EXPORTED` — that is precisely the tripwire that would catch an accidental `./dist/*` or bare-name broadening of the new export. (b) `reference-deployment.ts` becomes a third public entry file, but the plan says to change "only the exact package export key assertion" at the privacy test, so the private-module scan the plan promises to "preserve" will not cover it. That matters concretely: step 4 requires checking "compatible stream defaults", which an author could implement by importing `TRANSACTION_SSE_DEFAULTS` / `TRANSACTION_SNAPSHOT_LIMITS` into the new public entry.

**Fix:** add both deep specifiers to the `smoke-executables.mjs:522` refusal list; add `reference-deployment.ts` to the `transaction-snapshot.test.ts:678` file list; satisfy the stream-defaults check from the capture's own `liveStreamsAvailable` / `settings` (`transaction-runtime-configuration.ts:306–320`) rather than importing `transaction-sse.js` or `transaction-snapshot.js`.

## 5. [Medium] The new config field's refusal and diagnostic discipline is under-specified against the repository's stated no-echo rule

**Where:** plan.md §"Chosen input contract" (`plan.md:21`), §"Prospective tests" Config bullet (`plan.md:76`, "diagnostic output without payload"), contract.md projection row (`contract.md:58`).
**Source:** `packages/config/src/index.ts:901–929` (`readHost`), `981–1036` (`readScopeUrl`), `785–800` (`readFixture`) all name field and rule and never echo the value; `docs/design/startup-configuration.md:506–515` makes that an explicit contract. `redactStartupConfig` (`index.ts:1045–1049`) replaces only `auth.token`, so the resolved `bdptest.deploymentFile` is emitted verbatim in `startup.config` via `apps/bdptest/src/main.ts:117`.

**Issue:** "without payload" is ambiguous between "no file contents" and "no echoed path." The plan never states that the validator message must not echo the supplied value, nor that the resolved path is logged unredacted. Given the doc's rationale — a credential can be pasted into any `BDP_*` variable — the omission is material for a brand-new `BDP_BDPTEST_DEPLOYMENT_FILE`.

**Fix:** specify a fixed message naming `bdptest.deploymentFile` and its rule only; add an `index.test.ts` assertion that no issue message contains the rejected value, mirroring the existing host/Scope tests; record in the doc's Fields and Redaction sections that the resolved path is emitted like `bd.workspace` and must not carry secrets.

## 6. [Low] The 32 MiB outer ceiling derates the 16 MiB inner artifact budget by roughly half, unquantified

**Where:** plan.md step 2 (`plan.md:46`), contract.md `:74`.
**Source:** `packages/server/src/installed-contract-artifact.ts:19–24` — `artifactBytes` 1 048 576, `totalBytes` 16 777 216.

**Issue:** descriptors and schemas are themselves JSON, so embedding them as `utf8` strings at minimum doubles every `"` and `\`; control characters expand 6× as `\uXXXX`. A bundle near the 16 MiB inner total will commonly exceed 32 MiB once escaped. The plan calls this "an honest local input refusal," which it is, but it does not quantify the effective capacity.

**Impact:** the supported configuration is materially smaller than the inner ceilings advertise, and a negative test written at exactly 16 MiB inner would trip the transport bound rather than the bound it means to isolate.

**Fix:** either raise the transport ceiling to ≥ 2× `totalBytes` plus envelope overhead, or state the derated effective inner capacity in `contract.md` and choose the 32 MiB negative-test input so it isolates the transport bound alone.
