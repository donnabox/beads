## Concrete recommendation from caller inventory

Prefer a **principal-bound immutable owner authorization snapshot**, with empty projection as the first policy fixture, over a permanent Scope-global revoke boolean. Existing `authority-read` already accepts ReadPrincipal and invokes captureReadAuthorization(reader, principal, intent) inside the owner entry (authority-read.ts70–71,120–124,460–501,970–981). It validates/captures policy callbacks and view. Preserve that public-shaped interface; build the trusted bridge in the private Transactional composition.

The important implementation requirement is a principal-bound owner entry/facade: one entry captures that principal's policy and source context together, then supplies both to existing authority-read. Do not call a second reentrant owner method from captureReadAuthorization, or change only observation.authorizationView while sourceContext still records the global view. A private `withReadFor(principal, ...)`/equivalent facet can close over the trusted principal; a bound read-plane facade can reuse authority-read without adding arbitrary policy callbacks to wire requests. The exact caching/lifetime strategy must be bounded and owned by the service, not an unbounded principal→plane map. Runtime credential capture already has a32-entry installation bound, but that is not automatically a persistent policy-registry capacity: root must measure/choose its explicit private bound, never silently grow it or call it normative.

The proposed administration operation replaces an immutable policy binding for a trusted principal. It does not accept credentials or client policy fields. Durable identity must be determined from actual semantic policy plus a retained generation, not token digests. Same projection/token rotation preserves the view; changed grants/revocation allocate a new view; reusing an older policy must not resurrect old handles accidentally. Even if the first supported transition is monotonic all→empty, keep stored binding separate from retained authority fact format so partial policies can be added without rewriting the log. This recommendation does not claim generic partial projection is currently implementable from every retained fact.

## Transition atomicity and delivery correction

The frozen plan's blanket statement that failed commit leaves old leases active needs correction. Storeatomic373–403 deliberately fences on uncertain COMMIT, unclean rollback, or nonconstraint SQLite fault. **Only a confirmed precommit failure with clean rollback can preserve old policy/leases.** Uncertain outcome must fence the owner and abort/stop all delivery; reopen determines durable policy. Never compensate by reverting to an assumed old policy. The transition should publish replacement and cancel old-generation leases synchronously only after confirmed commit; any postcommit publication fault also fails closed. The existing stream catch/destroy behavior is reusable, but no asynchronous gap may register an old packet under the new generation.

Already accepted socket writes are irrevocable. Tests must distinguish a frame accepted before transition from an attempted subsequent frame. The deterministic backpressure test uses an actual multi-Event initial packet and write(false), transitions while blocked, then releases drain; cancellation prevents the second frame and owner pull. This proves more than caught-up polling. Transition cancellation, listener removal and no later enqueue are deterministic facts, not an elapsed-time silence assertion.

Existing tests intentionally reject mismatched configuration (recovery85, receipt-pages219, snapshot422/435), different stored view and prior-format9 (snapshot891–924), and changed identity codec (dependencies574/611). Those protections cannot become a generic best-effort upgrade.

Recommended exact migration boundary for council: support only the exact current format10 configuration synthesized from the same supplied options/artifacts and current identity codec, plus one new explicitly versioned authorization-storage format. No prior-format9, foreign authorizationView, changed receipt/page/snapshot/runtime bounds, Type/schema/capture mismatch or key identity mismatch is eligible. Construct legacy expected bytes using the existing field order/serializer, compare exact bytes, validate retained capture, then add the initial all-visible policy binding and replace configuration format/authorization-storage marker atomically **before recovery/maintenance**. Preserve epoch/position and all retained graph/group/receipt/page bytes. New creation writes the new format and policy record together. New-format open requires a valid complete policy record; missing/corrupt state is a fault, never defaults all-visible. The old binary's exact configuration check rejects the new format, preventing downgrade re-exposure. No exposed migration switch or general-purpose storage framework is needed.

The actual new format literal, bounded policy-record schema and default/override identity preimages are still implementation decisions pending council; the frozen packet did not settle them. Do not claim migration implemented or inspect any shared database to infer its safety. Optionally shipping only newly provisioned new-format disposable stores would be smaller, but it must refuse existing stores unchanged and cannot claim stable old-key/retained-handle compatibility. The recommended exact current-format migration gives a meaningful stable-generation reopen test without rewriting facts.

Snapshot maintenance needs particular care: liveLedger/disposition currently validates each retained handle against the current context view, including a global sweep. With multiple principal views, validating storage integrity must use the handle's own retained view; authorize a **request** separately against the requesting principal's current view. Otherwise opening or maintaining one principal's empty view can fence another principal's valid handle. Known issued same-Scope handle versus unknown token classification must precede a semantic foreign-view response without disclosing other principals' handles; freeze the explicit visibility policy for Snapshot handles in the corrected plan.

## Ready decision, not release

There is a useful reusable seam, and an empty policy can exercise it without an arbitrary historical projection engine. The minimal safe slice is more than changing a token: principal threading, per-entry immutable snapshot, durable versioned policy binding, current projection at all data exits, and expected-view delivery leases are inseparable for the selected principal. A bounded partial implementation may remain inaccessible under the existing development gate, but cannot be advertised as actual complete narrowing if receipts/sequence/snapshots still disclose old data. No new operator ruling is needed for these architecture/fault choices. Wait for the running actual review and final native findings, then let root freeze the corrected concrete ownership, migration and total test ledger before authoring.
