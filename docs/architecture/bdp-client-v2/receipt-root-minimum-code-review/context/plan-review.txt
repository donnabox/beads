## Blockers (must be fixed in the plan before authoring)

**1. Severity: High — `checkCurrentReadMinimum`'s third argument is load-bearing and the plan never states it.**
*Plan location:* "Use existing current-minimum check for lexical tuples: matching unknown is Unproved… foreign unknown remains private unsupported." *Source location:* `packages/server/src/transaction-store.ts:970–971`; helper `transaction-consistency.ts:115–132`.
*Issue:* `checkCurrentReadMinimum(minimum, context, waitable)` branches entirely on `waitable`: `false` ⇒ `TransactionMinimumUnsupported` (private 500) for **every** unknown position, `true` ⇒ `TransactionMinimumUnproved`. The plan names neither the call site nor the literal, and the adjacent sentence about "private unsupported" invites the wrong value. The existing precedents are conditional (`transaction-store.ts:1588`, `:1705` pass `true` only under a classifier; `transaction-read.ts:218` passes `false`), so "existing check" alone does not determine it.
*Impact:* An author following the plan literally could emit `false`, which still satisfies the plan's "own unsupported" language while contradicting D rows 2–4, A, both R-opaque rows and E — i.e. the entire deliverable inverts with one boolean.
*Smallest correction:* State the two store edits exactly: at `:959–962` replace `snapshotTransactionMinimum(minimum)` with `snapshotCurrentReadMinimum(minimum)`; at `:970–971` replace `checkTransactionMinimum(condition, context)` with `checkCurrentReadMinimum(condition, context, true)`, with the one-line justification that `true` is unconditional here because `receiptAtMinimum` is the only minimum-bearing caller and it always wraps a finite waiter.

**2. Severity: High — the HTTP root and page branches currently share one computed `minimum` constant; the plan's "only root uses `currentReadMinimumHeaders`" does not say it must be split.**
*Plan location:* "Only root branch uses currentReadMinimumHeaders, retaining undefined/has-controls fence. Page branch stays strict, including its unsupported sentinel." *Source location:* `packages/server/src/transaction-http.ts:551–553` (single `const minimum`), consumed by the page branch at `:559` and the root branch at `:575`.
*Issue:* The one-line edit a reader would make (`transactionMinimumHeaders` → `currentReadMinimumHeaders` at `:552`) relaxes **both** branches. A lexical tuple would then reach `service.receiptPage` → `snapshotTransactionMinimum` (`transaction-service.ts:586`) → `TypeError` → rejected → the generic `else response = empty(500)` at `transaction-http.ts:664`, i.e. a 500 **without** `x-bdp-development-limit`.
*Impact:* Silently destroys the page unsupported sentinel and breaks the installed historical page assertion the plan promises to keep (`transactional-minimum-receiving-installed.test.ts:503`, `expect(headers["x-bdp-development-limit"]).toBe("minimum-position")`) — a failure in the one file the plan says only changes its owned-root assertion.
*Smallest correction:* Add one sentence: the shared `const minimum` at `transaction-http.ts:551–553` must be split into a per-branch computation — page keeps `transactionMinimumHeaders(...) ?? "unsupported"`, root alone uses `currentReadMinimumHeaders(...)`.

**3. Severity: Medium-High — the R row table as specified cannot preserve the two historical titles.**
*Plan location:* "Preserve final historical titles (false)/(true)… Row-label/forget/minimumPosition table is enough." *Selection location:* `R-false` / `R-true` entries with `"new": false`. *Source location:* `packages/server/src/transaction-service.test.ts:894–896` — `it.each([false, true])("… receipts (%s)", async (forget) => …)`.
*Issue:* The current titles are produced by `%s` interpolating a bare boolean. A three-field row table whose rows are objects renders the object, not `false`/`true`, so both "unchanged" evidence identifiers change.
*Impact:* The selection's `"new": false` claim for the two historical rows becomes false, which is exactly the kind of relabeling the plan forbids elsewhere ("Do not… relabel historical evidence").
*Smallest correction:* Specify a **label-first tuple** table (`[["false", false, "pos-1"], ["true", true, "pos-1"], ["opaque false", false, "unknown"], ["opaque true", true, "unknown"]]`) keeping the `%s` format string, or `$label` object interpolation — either renders the first two titles byte-identically.

**4. Severity: Medium — "foreign" is overloaded across the plan in a way that contradicts the plan's own precedence list.**
*Plan locations:* store paragraph "foreign unknown remains private unsupported" vs the same paragraph's ordering "missing/foreign absence; semantic minimum", vs R's "foreign principal/foreign epoch lookup" (asserted 404) and A's "foreign/missing404".
*Source location:* `transaction-store.ts:969` (`if (!stored) return {receipt: undefined, context}`) precedes `:970–971`.
*Issue:* A foreign-**principal** read with an unknown tuple returns 404-with-context because absence precedes the check; only a foreign **epoch/view** with an unknown position reaches `checkCurrentReadMinimum` and yields the private 500. The single word "foreign" is used for both, in adjacent sentences that demand opposite assertions.
*Impact:* The R-opaque rows and D rows 5/6 are written from the same paragraph; a reader applying the "unsupported" reading to the R foreign row (or the "404" reading to D 5/6) authors assertions that fail.
*Smallest correction:* Disambiguate once: "foreign **principal** (and missing) identities return 404 with current context before any minimum comparison; only a foreign **epoch or view** paired with an unrecognized position yields the private unsupported 500."

## Optional suggestions (non-blocking)

**5. Severity: Low — D rows 7 and 10 are route-independent fences, not receipt-root observations.**
`transaction-http.ts:403` (401) and `:404–405` (400 malformed, no context) fire before the receipt route at `:550`, so both rows pass identically today and for any target. Correction: label them in the D table as preserved shared receiving/auth fences so the 10-request total is not read as 10 receipt-branch observations.

**6. Severity: Low — D row 3 / E row 3 would be stronger as content-length parity rather than "503 empty".**
`read-http.ts:42–45` sets HEAD `content-length` from the serialized problem body while dropping it, which is exactly the oracle the installed callback already uses (`transactional-minimum-receiving-installed.test.ts:433–436`, `malformedLength`). Correction: assert HEAD 503 `content-length` equals the paired GET 503 `content-length` with a zero-octet body.

**7. Severity: Low — the receipt minimum wait is the only minimum-bearing path that ignores `request.signal`; say so where the plan declines to add one.**
`transaction-service.ts:631` calls `waitForTransactionMinimum(attempt, minimumReads)` with no signal, and `transaction-http.ts:575` passes none, whereas `snapshot`/`events`/`changes`/`readAtMinimum` all forward one (`:291, :402, :462, :486, :530`). The plan's "No new AbortSignal API; the finite registered lifetime drains on close" is a defensible minimal choice, but as written it reads as an oversight. Correction: add the explicit note that this asymmetry is pre-existing and deliberately retained, so B's "no invented AbortSignal/disconnect claim" is understood as scope, not as a gap to be closed for symmetry.

**8. Severity: Low — D rows 5/6 encode a declared gap as an expectation; tie them to the stated exclusion.**
Under the general law the plan relies on (5841–5843), a foreign view/epoch enumerates 409 foreign-view / 410 cursor-expired; the reference instead emits the private 500 because `checkCurrentReadMinimum` classifies the unknown position first. The plan already excludes "foreign opaque policies", so this is consistent — but the new callback will be the written record. Correction: one sentence in the D description marking rows 5/6 as a preserved, excluded-scope private gap rather than a conformance position.

**9. Severity: Low — B should state that the post-close probe calls the raw owner, not the counting delegate.**
`separatePostCloseOwnerProbes: 1` only reconciles with `rootAttempts: 2` if the probe bypasses the wrapper, as the absence callback's shape permits (`transaction-service.test.ts:2278–2286` wraps only the object handed to `createTransactionService`). Correction: "probe `f.owner.readReceipt` directly (uncounted), expecting the closed-store throw".

**10. Severity: Low — the "120 s outer supervisor" bound has no in-repo enforcement point.**
`vitest.config.ts` sets no `testTimeout`/`hookTimeout`/`teardownTimeout`, and the installed file encodes only 5 s/45 s/10 s/60 s. Correction: name the stage that enforces 120 s (runner/CI), or drop it from the plan's bound list so it is not read as a code-level guarantee.

**11. Severity: Low — cite 5850–5851 explicitly in the behavior section.**
That sentence ("This rule does not establish precedence for retained continuations or Snapshots, nor extend unrecognized-position waiting to successful incident-Link lists") is the actual textual basis for treating the 5844 MUST as non-extending, and its silence about receipts is why the choice is permitted rather than mandated. Correction: add the line range beside the existing 5841–5851 citation.

`context/` was not readable; the 679-byte equality, tree `9b6f50b9a6b9eea953a6407599090c259cf97331`, and CI `39012707852` could not be checked with read-only tools. The plan's own gate already requires a release-time recheck of those pins, which is the correct place for them — no change requested, but this review's "frozen base" verification rests on the clean worktree source I read, not on those artifacts.

Substantively, the plan is feasible on this exact base: the six-file boundary needs no new imports or helper changes, the stated precedence matches `transaction-store.ts:956–974` / `transaction-service.ts:616–632` / `transaction-http.ts:403–586` line for line, every counter I could derive independently (absence 4/4/0/5/2; R 3/1/4 and 3/1/3; A 10/4/11/2; B 2/1/3; D 3 waits; 36 HTTP with POST 6/GET 21/HEAD 9; installed 22) reproduces, the budget-2 seam is genuinely forced by the 5 s vitest default plus the real 1100 ms isolation, the retention oracle survives because the minimum check precedes `expireRow`, and no test outside the six files depends on the behavior being changed.
