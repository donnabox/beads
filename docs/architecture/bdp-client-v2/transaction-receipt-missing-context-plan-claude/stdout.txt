# PLAN REVIEW — receipt-root/page missing-context serving slice

Independent review only. No files read or written, no commands, no delegation. Line references below are to the snippets you supplied; I did not re-read the tree.

## Verdict

The core repair is sound and correctly scoped. The five-branch split in `readReceiptPage` (two namespace defenses contextless, three genuine misses context-bearing) is the right cut, the precedence claims hold against the quoted code, and the nondisclosure argument is correct — the tuple is the *current* all-visible head, so it cannot discriminate unknown/foreign/prior-epoch/retracted/forgotten.

The defects are concentrated in three places: (a) unenumerated exact-equality assertions outside the 14-case selection, (b) the installed witness's unproven preconditions (second credential, receipts-root prefix, position model), and (c) an under-specified hard/soft partition that the exactly-8 control gate depends on.

## Critical

**1. [DEFECT] Exact-equality assertions outside the selection will break, and the stated gate provably cannot detect it.**
*Plan*: "Complete ownership and caller/expectation fanout"; "Existing page tests that inspect `.kind` on missing remain valid"; "Typecheck plus exact selected regressions below address fanout".
*Source*: `transaction-store.ts:2008-2089` missing variant; `transaction-receipt-pages.test.ts:280-290` is the only exact `toEqual({kind:"missing"})` the plan quotes.
Adding `context` to the three genuine missing branches makes any `toEqual({kind:"missing"})` / `toStrictEqual` fail (Vitest `toEqual` fails on an extra *defined* key). The same applies to `toEqual({kind:"refused",status:404,code:"resource-not-found"})` for the root. The plan selects 3 of N cases in `transaction-receipt-pages.test.ts`, 5 of N in `transaction-service.test.ts`, 6 of N in `transaction-http.test.ts`, and asserts without enumeration that service `227-246` is "the sole exact hidden404 object" and that `transaction-owned.test.ts:482/491`, `transaction-set.test.ts:328/341/443/621`, `recovery.test.ts:110` touch only success paths. Typecheck does not see runtime matchers, and the three bounded selectors do not run the unselected cases.
*Impact*: green local gate, red full CI at the root landing gate; unknown blast radius; done-when "all selected precedence/retention tests pass" is satisfiable while the suite is broken.
*Fix (smallest)*: in the measured draft, enumerate every exact-equality assertion against a missing/refused result across the six files (grep `kind: "missing"`, `"resource-not-found"`, `toStrictEqual`), and either amend them or add their callbacks to the selection. Note `280-290` is genuinely safe: `${scope}receipts/pages/token` yields `parentId === ${scope}receipts`, which fails `startsWith(`${scope}receipts/`)` → defense branch, contextless.

**2. [PROOF GAP] The installed witness needs a second authenticated principal, and no non-owned path may be edited to add one.**
*Plan*: ledger ordinals 6–9 and 11–12 use `credential: "other"`; "No spec/catalog/schema/runner/fixture/installed launcher/runtime/exports edit"; `ownedPaths` contains only the new `apps/bdptest` test file.
The plan explicitly audited one installed-entry limitation ("Existing installed entry offers no page-size override; do not add one") but never establishes that the installed `configuration` accepts a *second, non-owner* credential. Six of fourteen dispatches — the entire foreign-principal arm, which is the headline evidence — depend on it. An anonymous fallback yields 401, not 404, so it is not substitutable.
*Impact*: if absent, the witness is unissuable without editing the installed launcher/entry, i.e. a scope violation; the plan would need re-scoping, not re-measurement.
*Fix*: cite the installed configuration's credential field (shape and arity) alongside the existing page-size finding. If it is single-credential, replace the foreign-principal arm with unknown-token + prior-head probes and restate the ledger (14 → fewer dispatches, combined 95 → lower).

## High

**3. [PROOF GAP] The `pos-1`/`pos-2`/`pos-3` model is unproven and drives 14 pinned ledger fields.**

**4. [DEFECT] `receipts/unknown` hardcodes a discovered prefix; the smallest fix removes the assumption entirely.**

*Source*: `bdp.md:5116-5133` — receipt URLs live "beneath the **discovered** `receipts` root"; `transaction-http.ts:481-485` keys `receiptRoute` off `${scopeUrl.pathname}receipts/`. The plan forbids a collection/discovery fetch.

*Impact*: the unknown-token arm (2 of 14 dispatches, 2 of 8 named mutant failures) rests on a literal the plan is not allowed to verify by request.

**5. [DEFECT] `$root` has no servability control, so its 404s are not distinguishable from a misderived URL.**
*Plan*: ledger ordinals 6, 7, 11 (and 13) use `$root` with `urlAuthority: "exact response2 receipt.id or receipt.next"`; the witness never GETs `$root` at 200.
`$page` *does* have this control — ordinal 3 is a 200 for the same URL. `$root` does not. A root URL that was truncated, re-encoded, or taken from the wrong field produces exactly the expected 404s with exactly the expected context, so the foreign-principal nondisclosure claim is unfalsifiable at the installed layer.
*Fix (zero extra requests)*: `readReceiptPage` builds `page = { receipt: parentId, ... }` (`transaction-store.ts:2080-2085`), so the ordinal-3 200 body already echoes the authority's own root URL. Assert `page.receipt === response2.receipt.id` and bind `$root` to that. This also resolves the loose `urlAuthority` in #16.

**6. [DEFECT/GAP] The hard/soft partition is under-specified relative to the exactly-8 gate.**
*Plan*: "Each404 GET has complete transactionalProblem schema/exact body and cache/absence headers **before** the named tuple assertion"; control expects "one failed case/eight specific assertion errors".
If "absence headers" includes *presence* of `bdp-scope-epoch` / `bdp-authorization-view` / `bdp-scope-position` as a hard prerequisite, the mutant aborts at the first 404 with one hard failure, not eight soft ones — the control silently degrades to a weaker witness that still "fails", so the gate reads as satisfied.
*Impact*: the discriminating property of the whole counterfactual (8 named, projection-attributable failures) is lost.
*Fix*: enumerate the hard prerequisite header set explicitly (`cache-control`, `content-type`, `x-bdp-development`, `content-length`, plus the no-`etag`/no-`last-modified` checks) and state that all three `bdp-scope-*` presence **and** value checks live inside the single `expect.soft` named tuple assertion per request. Also state the structural rule (all hard assertions precede all soft ones, or per-request hard-then-soft) since the count is a gate.
