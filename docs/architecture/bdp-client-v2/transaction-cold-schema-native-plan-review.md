# Native plan review: cold-client local schema serving

## Finding

**P2 — Make the runtime adapter's gate placement executable within the seven-file scope.** Audit lines35–39 require authentication and the existing generic minimum gate before successful schema serving, but the proposed owned files omit `transaction-http.ts`, where both of those gates actually run. In the reviewed source, `transaction-runtime.ts:145` computes authorization but does not reject an unauthenticated principal. Its ordinary nonmutation authentication rejection is inside `transaction-http.ts:378`; the generic minimum handling is at538–548. A schema response intercepted before `handler.handle` at runtime165 therefore does not inherit either gate merely by running after credential parsing. Running the full existing handler first is not the answer either: a valid schema URL already becomes a404, not a continuation into a new route. The intended semantics are clear, but the final plan needs this placement spelled out so its footprint does not force a gate bypass or unplanned HTTP refactor.

**Smallest correction:** keep the seven-file ceiling. At the runtime dispatch point after its existing raw target/Host/method, body/closing and Origin checks, let the private adapter handle only an authenticated GET/HEAD exact captured schema hit with **none** of `bdp-minimum-scope-position`, `bdp-scope-epoch`, or `bdp-authorization-view` present. Return an explicit not-handled result for unauthenticated or minimum-bearing requests, then call the unchanged existing handler. Use header **presence**, including empty/malformed/partial tuples; do not parse a tuple and let failed parsing fall through to success. Unknown/uninstalled/alternate targets also use the existing handler. This preserves its actual401/minimum refusal/404 behavior and method-before-auth/Origin precedence, rather than inventing a new ordering. The adapter's successful branch then obtains its own fresh authorized context and applies shared HTTP selection once. A new helper/export from the HTTP module is unnecessary for a fixed three-header routing exclusion.

Add source cases for a known root schema with each minimum header alone, empty header, complete supported-looking tuple, and malformed tuple combined with a conditional shortcut; all must reach the existing refusal rather than200/304/412. Also check unauthenticated schema plus conditional/Accept, and Origin/method precedence. These are bounded source observations, not added installed exchanges. The audit already requests the broad classes; this correction makes their actual dispatch seam and expected preservation explicit.

No other material blocker found in the bounded proposal. This finding concerns implementation feasibility/gate integrity, not a new product ruling or a requirement to broaden minimum support.

## Accepted boundaries and source-grounded feasibility

1. **Local deployment obligation, not universal hosting law.** Spec `docs/specs/bdp.md:1091–1098` supports schema-preloading tooling;1198 gives propertiesSchema its absolute URL role;1234–1243 preserves ordinary retrieval and JSON Schema reference semantics.2533–2584 requires exact immutable local validation closure, not universal proxying of arbitrary external URLs. The accepted cold-client objective justifies serving this deployment's named local artifacts. Preserve external/offline schemas and the explicit non-advertising discovery boundary. No schema/catalog/profile amendment is needed for this slice.

2. **Exact root/transitive capture exists.** `development-contracts.ts:53–96,149–159` retains the immutable captured artifact entries and reconstructs compilation only from their bytes. `installed-contract-artifact.ts:305–405` captures kind, canonical retrieval URI, copied UTF8 bytes, length and SHA256, deduplicates identity, and freezes entries. The adapter can build an exact-URI map over schema entries in the chosen local namespace. Prefix matching alone is insufficient; it must not publish descriptors, embedded schema IDs as invented retrieval aliases, external resources, arbitrary files or normalized alternate targets. Installed positive fixtures should make the two dereferenced document retrieval identities explicit (root `$id`/retrieval and resolved `$ref`), while any fragment is a client-side within-document reference. This does not require new installation rejection or reference-resolution machinery.

3. **Raw delivery is necessary and feasible privately.** `transaction-runtime.ts:86–93` serializes selected.body, which cannot preserve original whitespace and number spelling. `development-runtime.ts:333–365` is a usable bounded precedent: shared HTTP selection followed by original-byte delivery. The new adapter can keep bytes separate from HttpResponse without widening public types. `read-http.ts:10–50` computes HEAD length from serialized body and strips body for HEAD; therefore overwrite successful200 GET/HEAD Content-Length using the exact captured byte length **after** selection. Do not reattach raw bytes after304/412/406, or invent zero-length304 metadata. No public validator/digest is required; valid no-ETag preconditions already exist in `conditionalReadStatus`.

4. **Current context must be an owner observation, not installed metadata.** General Transactional Scope response law5768–5774 applies to the selected local deployment's responses;304/412/406 do not excuse stale context. `transaction-service.ts:130–145` already tracks finite work, and `sequenceObserved:528–544` shows a same-entry current tuple. Final sequence source may supply a narrowly reusable private observation method; otherwise one small service method within the listed inventory suffices. Copy/freeze context in the owner entry; perform byte selection/delivery outside it. Never execute a sequence, discover, or read an unrelated Resource just to obtain context. Preserve runtime closing503 and sanitized observation-fault500; do not claim all owner faults are unreachable. Source controls should establish one entry, no receipt/admission/Event effect, and returned earlier context immutability after a write.

5. **Installed proposal is feasible without hidden discovery.** The14 requests sum correctly: two Type reads, two schema GETs, one HEAD, three selection refusals, three routing/auth/method cases, one withheld discovery request, one write, one post-write schema GET. An explicitly configured inventory URL and validated observed descriptor/schema URLs are honest cold descriptor/schema traversal, not complete cold discovery. Root and transitive bytes/hashes must come from independent fixture constants, not from response-provided digests. Use a single-page Type fixture, a direct local referenced document and a simple valid write so neither pagination nor a receipt-follow request is silently added.
