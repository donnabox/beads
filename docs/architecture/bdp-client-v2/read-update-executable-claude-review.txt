### F‑B — MEDIUM — `update-bead` is marked whole-contract, but half of one citation is unobserved on a target that supports it
**File** `packages/conformance/test-support/read-update-coverage-v1.json` (`read-update.singleton.update-bead`, `wholeContract: true`, boilerplate reason); `packages/conformance/matrices/read-update-v1.json` (same row)
Citation `#property-change-values`: *"Applying the properties patch must yield a JSON object satisfying every effective Type schema. **The metadata patch must yield a JSON object.**"* Observed legs are `update` and `noop`, both `propertiesChange` only. **No `metadataChange` patch is ever sent, and no Type-schema-violating patch is refused.**
The target supports both: `packages/server/src/resource-evaluator.ts:807-808,1030-1034` applies `metadataChange`, and the server's own tests exercise schema-violating patches (`member-executor.test.ts:2432`, `member-identity.test.ts:1212`). So this is a skipped leg, not an inapplicable one.
**Impact** Under the slice's own whole-contract rule, 4 of the 5 `wholeContract: true` rows are defensible, not 5. The other four check out: `create-bead` (allocated + honored id, both read back), `delete-bead` (incident-Link refusal, unchanged GET, no minted version, three 404 views), `expected-revision` (matching guard, stale update **and** stale delete with unchanged afterstate, omitted-guard leg, guarded delete), `idempotency-conflict` (conflict, unchanged afterstate, retained disposition re-returned).
**Fix** Either add a `metadataChange` leg plus a schema-violating refusal leg, or set `wholeContract: false` with reason "metadata patch and Type-schema refusal legs unobserved" — which moves the uncovered count to 125.

### F‑C — LOW — `noop-rev`/`noop-record` are captured and never asserted; the no-op *result*'s retained revision is unverified

### F‑D — LOW — `guard-wire` re-reads the harness's own request echo, not the serialized bytes
**File** `apps/bdptest/test-support/read-update-exact-client.ts:105-156`; assertions `update.guard-wire`, `noop.guard-wire`
The client sets `body[field] = string(execution.bindings[binding])` (`:114`), serializes that object (`:137`), and embeds **the same object** in `output.request.body` (`:156`). The runner then compares `/request/body/expectedRevision` against `bindings.get("a-rev")` — identical by construction. The assertion can only fail if the manifest's `bodyBindings` name and the assertion's `equalsBinding` name disagree (which the `old-revision` negative control does exercise, at `read-update-matrix.test.ts:271`). It cannot detect the client failing to put the guard on the wire.
**Impact** The inventory lists `update.guard-wire` / `noop.guard-wire` among the row's assertion bindings as evidence the guard reached the wire; it evidences manifest↔harness binding agreement instead.
**Mitigation I confirmed** `observation.bodyDigest`/`bodyOctets` are genuine serializer output and reproducible from the recorded body (verified above), so a reviewer *can* close the loop by hand — but no assertion does.
**Fix** Assert `observation.bodyDigest` against a fixture oracle, or use the existing `request-authored-body` assertion kind (`runner.ts:1805`) over the exact bytes.
