## Confirmed design corrections

**Actual configuration, not a parallel defaults description.** The runtime presently repeats selector values and pagination/advertised-limit values (`transaction-runtime.ts:294–316`) and owns explicit listener settings separately (`:237,252–255`). Mandatory extraction into values actually supplied to these consumers fixes H1 F5. Importing the existing mutation tuple preserves the current M32/E256 distinction. Resolving receipt maximum once preserves the existing three-consumer agreement. Passing the captured maintenance and wait budgets explicitly is a valid way to stop depending on unobserved fallback literals: the existing store fallback is 1000 ms (`transaction-store.ts:242`), comparison uses `options.budgetMs ?? 1000` (`transaction-comparison.ts:40` vicinity), and minimum wait does likewise (`transaction-consistency.ts:90`). Algorithm details remain bound by installed payload; the logical digest does not purport to describe all Node internals.

**The retention seam is genuinely export-only.** `transaction-store.ts:158` already defines `day = 86400000`, consumed by receipt expiry and clock bounds. Export that binding under a private alias. No new duration source, policy parameter, compatibility format or expiry rule is necessary. The runtime can bind its numeric value without advertising retention. A changed store compatibility record would be outside M1 and should fail review.

**Three identity concepts remain distinct.** The store constructs compatibility JSON at `transaction-store.ts:232–240`; the owner returns that JSON alongside the literal view name at `:517–527`. Neither is a served configuration hash. The proposed `runtimeConfigurationIdentity`, hashed policy identity and separate physical binding close H1 F4 without renaming persisted fields or extending the shared closed conformance record. Dynamic epoch/head/time/port must stay out of the logical configuration digest. Store compatibility and live authentication have different lifetimes: reopening with changed credentials can legitimately preserve the former and change the latter.

**Per-credential authorization is retained.** Authentication dispatch actually forwards the matched credential's principal and canMutate (`transaction-runtime.ts:188–201`). Hashing the same detached records, sorted by token digest, closes H1 F3; a principal-to-permission map would be wrong. A same-principal permission swap must change both relevant digests and real mutation behavior. Actor/revision attribution cannot supply transport permission. Token ordering should remain irrelevant. Captured authentication buffers must remain private, even if their containing object is frozen.

**Installed contracts bind exact capture, not regenerated fixtures.** The existing compiler ingests/detaches artifacts, compiles them and returns a branded closure. Its identity includes captured artifact digest plus artifact, graph and evaluator ceilings (`development-contracts.ts:138–154`). Reusing that exact closure and existing identity is sufficient; a second compile/digest scheme would weaken rather than improve the evidence. Validate the actual owner's installed Types and fixed aggregate/view facts before returning metadata. This remains the actual installed-contract path even though the runtime metadata is non-attesting.

**Canonical identity and a physical loopback endpoint can coexist.** Existing Host checking is against the allocated listener at `transaction-runtime.ts:172`; the listener itself binds 127.0.0.1 and obtains its actual address before deriving Scope (`:271–275`). The explicit canonical mode is therefore a real necessary change. It can compare the incoming Host with the configured canonical Scope authority while keeping port 0 physical binding separate. The plan correctly preserves default listener mode and requires explicit Scope for canonical mode. Tests must dial the actual address, send canonical Host and exercise actual authenticated operations. Merely testing URL construction would not close this dependency. This private dial mapping is not TLS qualification, ordinary cold discovery or inherited Read completeness.

**No test-seam qualification.** Withholding metadata for injected clocks, schedulers, waits and numeric/cadence overrides is appropriate. Arbitrary callback names or function text must not acquire the default behavior identity. Post-start metadata must describe the same owner/service/handler that served requests, with readiness only after successful construction. The plan correctly distinguishes real coupled configuration changes from injected digest mismatch controls (H1 F6).

## Two bounded acceptance clarifications

1. **Define seam-presence capture before the first await.** At plan line 35, “any behavior seam is supplied” should be implemented with detached own-data inspection of the seam record, not a late check of mutable fields, truthiness, or the caller's object. Conservatively suppress metadata for any recognized explicitly supplied seam key, including an explicitly undefined value; an omitted/empty seam record can retain the normal path. Reject proxy/accessor/unknown seam properties without evaluating getters. Add a control that mutates a supplied seam object immediately after startup is called. This is an implementation detail of the accepted no-test-seams guarantee, not a new feature or blocker.
2. **Describe the new administrative limits accurately.** Plan line 29 adds a credential count ceiling of 32 and a 16 KiB principal ceiling; d907 does not have those bounds. They are reasonable private capture bounds, but the extraction is therefore not wholly behavior-preserving for all historically accepted private inputs. Measure principal size as UTF-8 bytes if the unit is KiB, keep valid non-ASCII spelling unchanged and add exact-boundary/one-over refusal checks before provisioning. Record this small private input restriction in the implementation report. No protocol principal limit or public configuration contract follows from it.

Neither clarification requires a product decision or a new mechanism.

## Safe implementation slice and acceptance gates

Proceed with the proposed new private configuration module, runtime wiring, export-only day alias, focused tests and private packaging inventory. A coherent first checkpoint can extract/capture the actual settings and credentials plus digest construction; the following checkpoint wires canonical Host and actual post-start owner metadata. Do not publish an intermediate digest as actual runtime configuration before its consumers have been wired.

Done means: detached administrative inputs; exact compiled closure forwarded; actual per-token permission discrimination; actual canonical Host GET and mutation with no-effects wrong-Host refusals; unchanged listener-mode behavior; real close/reopen with stable logical identity and rebound actual endpoint; immutable metadata absent on all seam paths; unchanged store compatibility behavior; cleanup releases the owner after failed startup; private module inventory and bare/dist import denials; the focused regressions and toolchain checks listed in the plan pass with exact logs. Pure leaf-perturbation tests establish digest dependencies only; real consumer/HTTP checks remain required.

**H1b remains blocked pending its own work**, not M1 design: exact executor Transactional profile acceptance, required dynamic original-wire observation recorder, profile/bundle binding negatives, private installed process/payload binding and before-first-request comparison. M1 returns captured metadata; it does not enforce the conformance adapter's binding or prove a fresh packed process uses it. Collections, retention advertisement, receipt pagination, snapshots, full cumulative Read/Origin/absolute-target behavior and public profile activation remain outside this slice. In particular, preserving current Origin/absolute-form refusals is preservation of the private target, not qualification of those inherited Read clauses.
