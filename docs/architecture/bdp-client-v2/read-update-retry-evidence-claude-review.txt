## Findings

### 1. Retained-Problem equality is not closed — `title`/`instance`/`retryAfter` unconstrained
**Severity** Low (latent; no live gap) · **Location** `packages/conformance/matrices/read-update-v1.json` (every `problem-*`/`absent-*` group in both rows); `schemas/bdp-v0.schema.json` `$defs.readUpdateProblem`, `$defs.sequenceMemberProblem`

`readUpdateProblem` and `sequenceMemberProblem` carry **no** `additionalProperties`/`unevaluatedProperties: false` — unlike `mutationResult` and `sequenceMemberResult`, which are closed. The rows pin 4 present fields (`status`/`type`/`code`/`retry`) and 5 absences (`detail`, `outcome`, `resource`, `diagnostics`, `diagnosticsTruncated`), but never constrain `title`, `instance`, or `retryAfter`.

**Impact** Today this is latent only: `packages/server/src/member-executor.ts:116-133` and `read-request.ts:265` emit exactly `{type, code, status, retry}` (+ diagnostics), and the recorded wire in `positive.json` contains precisely `('code','retry','status','type')` — so the plan's "every **actual** non-positional field" is satisfied. But a retained failure that gained a `title` or `instance` on replay would pass every assertion in both rows *and* the open schema. The report's "full Problem tuple" and F2's "every normative Problem field" overstate what is pinned. Note the new rows are already strictly richer than the neighbour `sequence.member-problem-shape`, which pins only code/status/type/retry/no-outcome.

**Fix** Add `absent-title-*`, `absent-instance-*`, `absent-retryafter-*` to each Problem group (cheap, no schema change), and narrow the report wording to "four pinned fields plus five pinned absences".

### 2. Three oracles have no negative control; one control is status-only
**Severity** Low · **Location** `apps/bdptest/src/read-update-matrix.test.ts:1612-1617`

"changed record is not a conflict" corrupts only `status → 200` on `b-conflict`, leaving the Problem body intact, so it validates the `status` assertion's wiring, not the body-level conflict oracle. Unguarded entirely: `a-replay.name-0` (cross-carrier name projection — the row-A analogue of the clause row B does control), `reordered-again.same-results` (repeat-replay stability), `d-after` (fresh member actually committed).

**Impact** 13 controls over 491 assertions is thin by design and the report doesn't overclaim, but the name-projection oracle is controlled in only one of the two rows that depend on it.

**Fix** Corrupt `body/code` together with `body/status` in the b-conflict control; add controls for the three uncovered oracles.

### 3. Control targeting is positional where this file's own idiom is content-based
**Severity** Low (maintainability) · **Location** `apps/bdptest/src/read-update-matrix.test.ts:387-392`

`...actions.filter(a => a.family === "client")[retryClientIndex++]` matches the target by position in the filtered client-action list. The adjacent `patchControl` mechanism (same function, lines 412-461) instead matches on observable input — `w1Input.idempotencyKey`, `method`. `ScenarioActionExecution` (`packages/conformance/src/scenario-action.ts:55-62`) carries no action `id`, so a runner-supplied id isn't available and the plan forbids a runner seam — the positional counter is a consequence of the interface, not a free choice.

**Impact** Self-validating today: `counterfactualApplications === 1` plus the per-action failing-assertion lookup both fail loudly on drift. But inserting any client action ahead of a target silently retargets the corruption, and `status`/`postimage`/`indices`/`name-0` repeat across actions, so the failure mode is a confusing miss rather than an obvious one. The alignment invariant (one `actionExecutor` call per client action, in manifest order) is undocumented and unasserted.

**Fix** In-slice, no runner change: before applying, assert the matched `clientAction.input` deep-equals `execution.input`. Or match on `idempotencyKey`/`method`+`targetBinding` like the neighbouring control layer.

### 4. The singleton→sequence retained-success replay changes carrier *and* name at once
**Severity** Low · **Location** matrix row `read-update.idempotency.cross-carrier`, action `a-replay`

`a-replay` presents `retry-cross-a` as a sequence member **with** `name: "renamed"`, where `a-initial` was a singleton with no name. Both are lawful — `bdp.md:3209` excludes `idempotencyKey` and `name` from semantic identity — but there is no singleton→sequence retained-success replay with a byte-identical record. The cited carrier-equivalence clause is therefore observed in its cleanest form only in the sequence→singleton direction (`b-replay`, where a singleton *cannot* carry a name).

**Impact** A regression in the `name` exclusion and a regression in carrier equivalence both surface as the same single failure; the two cannot be distinguished from the row.

**Fix** Add one unnamed sequence member replaying `retry-cross-a`, or move the name projection onto a separate key.

### 5. Dead `a-disposition` capture reads as a stronger comparison than is performed
**Severity** Low · **Location** `packages/conformance/matrices/read-update-v1.json:66092`

`a-initial` captures the full singleton disposition `/body` as `a-disposition`; nothing references it. The plan anticipated a "full original-disposition comparison … within the same carrier", but `a-final-replay` compares only `/body/resource` to `a-original`.

**Impact** Nothing is actually unasserted — `mutationResult` is closed via `unevaluatedProperties: false`, and for a bead postimage `source`/`sourceRevision`/`deleted` are forbidden, so `{outcome, resource}` fully pins the body. This is dead weight, not an evidence gap.

**Fix** Either drop the capture or add `a-final-replay.disposition` with `equalsBinding: "a-disposition"`.

### 6. Residual limit: no state-side oracle against a spurious extra allocation
**Severity** Low (residual limit, not a defect) · **Location** both rows

Re-execution of the allocated creator *is* excluded at response level — `reordered.retained-body-results-3` deep-equals `position-a-original` including the allocated id and revision, so a fresh execution (new id) fails. Row A's explicit-id replays are excluded a second way, since a fresh execution would be `identity-taken`. The one uncovered shape is "returned the correct retained disposition **and additionally** created a bead": neither row reads the bead collection.

**Fix (optional, priced)** One `GET beads/` with an identity-set assertion after `reordered`. Note this is *not* free: `clientReadRoutes` precedes `readRoutes` and dedupe keeps the first position, so adding a client GET on the `beads` binding reorders the closed allowlist and moves `exactConfigurationDigest` even though the route set is unchanged.
