### 1. Medium — teardown can retain an ordinary cancellation as the "first genuine fault", so `close()` rejects on a clean shutdown

**Source:** F2 repair. `packages/server/src/transaction-runtime.ts:196-197` (capture predicate), `:339` (close aggregation); `packages/server/src/transaction-sse.ts:48-50` and `:73-74` (the two non-abort `"stream transport closed"` throws).

The capture predicate is `response.headersSent && !streamSignal.aborted && !firstStreamFault`. `streamSignal` is linked to the disconnect signal only through `supplied.addEventListener("abort", …)` in `transaction-service.ts:208-210`, and that abort originates from `response.once("close")` in `node-http-disconnect.ts:18-20`. Node sets `response.destroyed` **synchronously** on `socket.destroy()` but emits `'close'` on `nextTick`. So there is a window in which `sink.destroyed === true` and `streamSignal.aborted === false`. Both `write()` entry points fail non-abort in that window: `transaction-sse.ts:49` (`throw new Error("stream transport closed")`) and `:73` (`else if (sink.destroyed) closed()`).

The backpressured-drain path is safe — `createNodeHttpDisconnectSignal` registers its `response` `'close'` listener before `write()` registers its own, so `aborted` rejects first and `closed()` lands on an already-settled promise. The unguarded path is the `pumpTransactionChanges` loop re-entering `write()` from a queued microtask.

**Failure scenario:** `runtime.close()` is called with a live stream. `closeListener()` runs `server.closeAllConnections()` synchronously inside the async IIFE prologue (`transaction-runtime.ts:260-264`), i.e. inside a microtask drain; `emitCloseNT` queues on `nextTick`. If the pump has an already-resolved continuation in that same microtask drain (reachable whenever groups are flowing, since `node:sqlite` reads resolve without a macrotask), it re-enters `write()`, sees `destroyed`, throws `Error("stream transport closed")` with `streamSignal.aborted` still false → captured as `firstStreamFault` → unshifted at `:339` → `close()` rejects with `AggregateError("transaction runtime shutdown failed")`. `transaction-sse.test.ts:249-254` exercises exactly this (`const again = f.stream("changes/?start=now")` left open across `await f.runtime.close()`), with no `shutdownFailure` callback, so it becomes intermittently red; in the installed launcher the same window turns a normal shutdown into a reported shutdown failure. Root's disposition 2 explicitly requires that "ordinary pre-abort, client disconnect and service cancellation must remain clean".

Note the native 321-test pass does not disconfirm this: the pump's duty cycle is ~99% inside `delay(pollMilliseconds)`, so the window is narrow, and every `f.stream()` recorder is closed *before* `runtime.close()` in `afterEach`'s reversed cleanup — except at `:254`.

**Minimal remedy:** one added conjunct at `:196`:

```ts
if (response.headersSent && !streamSignal.aborted && !response.destroyed && !firstStreamFault)
```

`finally { response.destroy() }` at `:199-200` runs *after* the catch, so at capture time `response.destroyed` is true only if the transport already went away — genuine store/owner faults (`next()` throwing) leave it false and remain captured. This is the same already-accepted narrowing tradeoff as `!streamSignal.aborted`. No wire, protocol, or test-expectation change; the F2 test at `:527-547` still passes because the injected `prepare` throw leaves the response alive.

### 2. Low — the accepted heartbeat/idle validation is wired to module constants, so it cannot fail for any caller input; effective pump timers are validated only after headers

**Source:** F1 repair. `packages/server/src/transaction-runtime-configuration.ts:296-302`; `packages/server/src/transaction-sse.ts:88`.

```ts
validateTransactionStreamTimers(
  TRANSACTION_RUNTIME_DEFAULTS.changefeedStream,
  TRANSACTION_RUNTIME_DEFAULTS.transport.timeout,
);
```

Both arguments are frozen module constants with zero dependence on `input` or `rawSeams`. The one line that does read effective configuration — `liveStreamsAvailable = settings.changefeedStream.heartbeatMilliseconds < settings.transport.timeout` (`:303-304`) — degrades to a capability refusal rather than validating. Net: the rule root accepted ("heartbeat strictly below socket idle timeout") is enforced as a constant assertion plus a refusal, never as validation of the effective settings object. Separately, `settings.changefeedStream` is not seam-overridable today (`:287-293` overrides only `transport`, `receiptMaximumItems`, `maintenanceIntervalMs`), and the pump's own `validateTransactionStreamTimers(settings)` at `transaction-sse.ts:88` runs **after** `writeHead`/`flushHeaders` at `transaction-runtime.ts:180-181`.

**Failure scenario:** conditional, not reachable at this commit. Add a `changefeedStream` seam (the natural next step for G2b stream tuning) with `pollMilliseconds: 0`: capture accepts it (the validator saw constants), `liveStreamsAvailable` stays true (it inspects only heartbeat), the client receives `200` + `text/event-stream` headers, the pump then throws `"invalid transaction stream timer"` post-header, which finding 1's predicate retains as a genuine fault and `close()` rejects — a misconfiguration surfaces as a successful stream that dies plus a shutdown AggregateError, instead of a startup `TypeError`.

**Minimal remedy:** pass the effective object — `validateTransactionStreamTimers(settings.changefeedStream, settings.transport.timeout)` — and gate the refusal on the result rather than re-deriving the comparison. Identical behavior and identical test expectations today (`settings.changefeedStream` *is* `TRANSACTION_SSE_DEFAULTS`), and the invariant then holds under any future seam. The existing `:294-295` `headersTimeout`/`requestTimeout` check is already written against `settings`, so this also makes the two cross-timer checks consistent.

### 3. Low — the new raw-byte oracle couples SSE frame index to finite page index without pinning one group per page

**Source:** F5 repair. `packages/server/src/transaction-sse.test.ts:177-178`.

```ts
for (const [index, rawFinite] of [firstBytes, secondBytes].entries())
  expect(rawFinite).toContain(groups(stream)[index]!.split("\ndata: ")[1]!);
```

`groups(stream)[0]` is asserted against `firstBytes` and `groups(stream)[1]` against `secondBytes`, which is only correct while each page carries exactly one group. Nothing in the test pins that; the preceding `stream.until(() => groups(stream).length === 2)` constrains only the total.

**Failure scenario:** a page-default or grouping change that puts both groups on the first page leaves `second.groups` empty. The preceding `toEqual` at `:174-176` still passes (2 frames vs 2 frames), while the new loop compares frame 1 against an empty-groups page body and fails with a diff that reads as a serialization mismatch rather than a paging change. Fails loud, not silent — this is a diagnosability/robustness defect, not a soundness hole in the oracle.

**Minimal remedy:** one line before the loop — `expect([first.groups, second.groups].map((g) => g.length)).toEqual([1, 1]);` — using data already fetched. No production change.

### 5. Informational — the installed F5 witness has no numeric-like property keys

**Source:** F5 repair. `apps/bdptest/src/transactional-sse-installed.test.ts:156`, `:175`.

Root's disposition 5 said "add numeric-like keys if needed to prove sensitivity"; the source test does so (`properties: { "10": "ten", "2": "two", n: 100, … }` at `transaction-sse.test.ts:149-154`), and that is what makes the *pair* of assertions sensitive — authored `"10","2"` order would fail the round-trip `toEqual`, while a reserialization divergence fails the raw `toContain`. Inside root's wording. Flagged so the installed assertion is not later cited as independent byte-ordering evidence.

## Static limits of this review

- **Not executed:** no test run, no installed/native evidence, no socket-level timing experiment. Native closure and the fresh installed evidence run independently, per the brief. The only commands I ran were the dependency-boundary checker and the no-emit typecheck, both read-only, both exit 0 at `b14fb28`.
- **Finding 1 is an ordering argument, not an observed failure.** It rests on Node's documented `destroy()`-then-`nextTick('close')` sequence and on `processTicksAndRejections` draining all microtasks inside `runMicrotasks()` before returning to the `nextTick` queue. A targeted repro would need to force a pump continuation to be queued at the instant `closeAllConnections()` runs. The native pass is consistent with the window being narrow, not with its absence.
- **Spy efficacy in the new pre-abort test is assumed, not proven statically.** `vi.spyOn` on the ESM namespaces of `../dist/node-http-disconnect.js` and `../dist/transaction-service.js` depends on Vite transforming those `dist` files into settable export bindings, and on `createTransactionService` returning a plain own-property object (spread at `:751-759` would drop prototype methods otherwise). Both failure modes surface as a test failure or a 5 s recorder-deadline stall rather than a silent pass, so the test is fail-safe — but I did not confirm the transform.
- **Unchanged-by-this-diff areas were not re-derived.** The prior review's "verified clean" set (group-loss/duplication, backpressure and listener cleanup, lifecycle ordering, representation selection, HEAD/304/412, frame safety, `TRANSACTION_CHANGEFEED_BYTES` arithmetic, settings-hash key order, raw bridge) was taken as established for `b64`; I re-derived only the parts the repair touches — the service abort wiring at `transaction-service.ts:208-214`, `deliver` at `transaction-runtime.ts:81-88`, the recorder's chunked decoder, and the close-path ordering at `:328-342`.
- **Also unchanged and untouched:** erasure publication fencing, mutable views, Event Source SSE, set HTTP admission, real-socket backpressure against `server.timeout`. G2b was not read and is not in scope. No deferred `start=now`/header semantics were reopened and no new protocol was proposed.
- **Type coverage asymmetry is pre-existing:** `apps/*/test-support/**/*.ts` remains outside `tsconfig.check.json` `include`, so `apps/bdptest/test-support/transactional-execution-binding.ts` is still only transitively checked. The recorder move removed the one file this mattered for; the general gap is out of scope.
