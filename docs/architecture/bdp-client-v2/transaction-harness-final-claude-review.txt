## Findings

### 1. MEDIUM — Any harness cleanup failure now discards the whole cohort observation; the doc only claims the both-fail case

**Location** `apps/bdptest/src/transactional-matrix.test.ts:226-233`, `:259-262`; `docs/design/transaction-harness-review-closure.md:38`; `packages/conformance/src/runner.ts:814-824`

**Evidence** The runner already attributes a failed `harness.cleanup`: `runner.ts:819` converts `state: "pass"` → `"harness-error"` and `:823` records `cleanupError: "cleanup failed"`. The new wrapper additionally retains the cause, then `:259-262` throws unconditionally whenever `cleanupFailures.length` — including when `failure === undefined` and the run produced a complete 255-row result. The doc says only "If abort and cleanup both fail, the final AggregateError preserves the original abort and the actual cleanup cause."

**Impact** A single unclean child exit on any one of five sessions converts a row-level diagnostic into a whole-run throw with no `result` returned. Concretely, the witnesses that assert on `observed.result` and are *indifferent* to cleanup today — `:373` (`harness-error`/reason), `:575` (ordinary `/id` not followed), `:681-688` (401 dynamic linkage), `:322-324` (changed installed identity) — all become coupled to every session closing cleanly, and they fail with `"installed cohort cleanup failed"` instead of their own evidence. The supplement's own new test proves the aggregating path fires in practice.

**Bounded fix** Aggregate only when `failure !== undefined`; otherwise return `{ ...observed, cleanupFailures }` and leave the runner's `cleanupError`/`harness-error` row as the publication gate. If the unconditional refusal is intended, say so at `docs:38` ("any cleanup failure refuses publication") rather than describing it as the both-fail case.

**Bounded fix** Apply the same `Number.isSafeInteger / >0 / ≤2_147_483_647` predicate to `snapshot.requestTimeoutMs` when it is defined, independently of the cleanup bound, and add `{ requestTimeoutMs: 0, cleanupTimeoutMs: 10000 }` to the existing `it.each`.

### 3. LOW, reachable only off the current four rows — moving `validateReceiptWire` ahead of the status guard reports a non-200 mutation response as evidence self-disagreement

**Location** `packages/conformance/src/transactional-observation.ts:165` (moved call) vs `:180-185` (status/wire guard), `:248`

**Evidence** `validateReceiptWire` asserts `HTTP/1.1 ${response.status} OK` (`:248`, pre-existing hardcoded reason phrase). It now runs before the explicit `response.status !== 200` refusal. A real `201 Created` / `202 Accepted` canonical mutation response therefore throws `TransactionalHarnessError("receipt wire status mismatch")` rather than `"source receipt wire unavailable"`, even though wire and parsed response agree exactly.

**Impact** Category is unaffected (both are `harness-error`, so no false *target* evidence), but the reason contradicts the classification the supplement just documented — `docs:36` defines wire mismatch as "receipt evidence self-disagreement". Not reachable in the four rows: `register` runs only after all assertions pass (`runner.ts:1455-1461`) and every mutation action asserts status 200, so only a 200-with-`OK` response reaches it. It becomes live for any row or target that does not assert 200.

**Bounded fix** Keep the `response.status !== 200 || !response.wireResponseBytes || length > 2097152` guard immediately before `validateReceiptWire(response, "GET")`, preserving the new schema/identity ordering below it.

### 4. LOW, unreachable-defensive — the read lane still classifies a missing validator as a target failure

**Location** `packages/conformance/src/runner.ts:951-955`

**Evidence**
```ts
input.method === "GET" &&
(!schemaValidator ||
  schemaValidator.validate("#/$defs/mutationReceipt", body).length ||
  body.id !== source.receipt || ...)
  → throw new TransactionalReceiptFailure("retained receipt schema or identity mismatch")
```
The register lane was split exactly as directed (`transactional-observation.ts:166` harness for the absent validator, `:168` receipt failure for a real invalid schema), but the read lane keeps `!schemaValidator` inside the same disjunction that now yields `state: "fail"`.

**Impact** Unreachable today: `resolve()` requires a ledger entry, and `register` refuses with `TransactionalHarnessError("source receipt validator unavailable")` when no validator exists, so a receipt read cannot occur without one. The new `transactional-cumulative.test.ts` `"validator"` case confirms this — it asserts `reads === 0`. So this is dead code that states the opposite classification from the one the supplement documents, not a live misattribution.

**Bounded fix** Hoist it: `if (!schemaValidator) throw new TransactionalHarnessError("receipt validator unavailable");` before the disjunction, leaving schema/identity as the target-failure arm.

### 7. INFORMATIONAL — cleanup and child-close bounds are now equal, so the nesting is not strictly monotone

**Location** `apps/bdptest/test-support/transactional-execution-binding.ts:188` (`cleanupTimeoutMs: 10000`); `scripts/transaction-installed-observation.mjs:31` (`bounded()` = 10000); `apps/bdptest/src/transactional-matrix.test.ts:611`

**Evidence** `close()` bounds cleanup with `AbortSignal.any([signal, AbortSignal.timeout(10000)])` (`raw-http-scenario-target.ts:94`), and that cleanup contains `controller.abort()` → `allSettled(pending)` → `child.close()`, whose own launcher bound is also 10 s. A child close that consumes its full bound still trips the cleanup bound, yielding `TransactionalHarnessError("transaction session reopen failed")`. In the reopen path the effective bound is the *remaining* `prepareTimeoutMs`, which is strictly less.

**Impact** Not a defect, and the documentation is honest about it — `docs:29` explicitly declines the per-phase claim ("Close and reopen do not each receive a fresh additional 10 seconds") as disposition 3 required, and the previous hard 5 s cap is gone. Two second-order notes: the emergency `closeStarted()` path (`raw-http-scenario-target.ts:128`) now runs on a 10 s rather than 5 s bound that is not joined to the aggregate signal, and the cohort abort witness's `performance.now() - started < 15000` assertion at `:611` consequently has ~3 s of worst-case slack instead of ~8 s.

**Bounded fix (optional)** Make the launcher's child-close `bounded()` strictly smaller than the raw cleanup bound (e.g. 8000), or raise `:611` to accommodate the new worst case.
