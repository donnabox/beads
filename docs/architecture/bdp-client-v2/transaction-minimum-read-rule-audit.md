## What the normative text actually settles

| Case | Current law and implication |
| --- | --- |
| Invalid token characters | `docs/specs/bdp.md:6602–6625` expressly requires `[A-Za-z0-9_-]{1,256}` for serialized epochs, Authorization Views and Scope positions, including HTTP fields. Empty values, commas, internal whitespace, percent signs and non-ASCII are outside that profile. This is **settled syntax**, not merely an implementation preference or schema inference. HTTP field framing/OWS is separate from the decoded token value. |
| Missing or repeated minimum fields | `:5800–5817` shows epoch+view+minimum together but does not specify all-or-nothing presence, cardinality or what an isolated epoch/view means. In contrast, repeated/absent Idempotency-Key has an explicit rejection rule at3909/4521–4525, and repeated query parameters have an explicit invalid-parameter rule at1552–1555. Neither rule can be transplanted silently to these fields. |
| Which400 code | `:1897–1898` assigns status/family/retry to malformed-request and invalid-parameter, but does not define these minimum failures. The “invalid request string/object syntax” sentence at901 is within **BDP JSON and HTTP Protocol's JSON scalar/I-JSON paragraph** (890–904), covering invalid JSON strings/object member syntax; it is not an express all-header receiving rule. Generic HTTP syntax failures and ordinary field/body limits remain enforced separately. |
| Well-formed unknown position | `:3689–3699` makes positions opaque to clients and ordered by the authority; `:6602–6625` permits counters, hashes, UUIDs and other encodings. A token matching the alphabet need not have been issued or identify a position. There is no universal pos-N grammar, unknown-position code, or statement equating unknown with expired. Valid recognized future positions already use the finite wait path. |
| Compatible disclosed read | `:5788–5817` requires a current prefix at/after the minimum or a real wait/route/foreign-view/cursor-expired/catch-up-timeout result. `:5323–5326` defines the bounded wait failure. `:5841–5843` orders checks before304/412. | Missing/hidden target with compatible satisfied tuple | `:1440–1453` requires unknown/deleted/non-visible Resource uniform404; alias nondisclosure is also explicit. | Missing/hidden target plus behind/foreign tuple | Nondisclosure requires unknown and hidden identities to behave alike. | Receipt/page exception | `:4648–4654` expressly orders authentication → principal/epoch nondisclosure → minimum/wait → page expiry → representation. This is already implemented. It cannot be generalized to every Resource/alias read simply because it is a convenient model. |

## Smallest next decision, without bundling unrelated semantics

There is **one narrow receiving decision worth resolving first**, rather than requiring a decision on every simultaneous failure:

> On an otherwise authorized current read, should any presence of the three minimum-control fields require exactly one nonempty checkpoint-profile value for each field, with a missing, repeated or lexically invalid tuple rejected before owner observation as400 `malformed-request`? All three absent would mean no minimum. This would leave well-formed but unrecognized position identities and missing/hidden-target collisions unchanged pending their own disposition.

**Recommendation, not existing law:** adopt that closed tuple rule and malformed-request, after normal method/transport/authentication checks; keep response context absent if no owner was entered. It is consistent with the existing strict receiver and distinguishes receiving from an owner-observed inability to satisfy a valid minimum. The equally viable naming alternative is400 `invalid-parameter` with the same phase and privacy rules. An alternative applicability rule could ignore incomplete fields unless Minimum-Scope-Position is present, but that risks silently discarding an intended fence; the present text does not expressly choose between those policies. Do not infer approval from this recommendation or present it as a new answer to S1/G2.

Unknown positions are deliberately outside this first decision: alphabet-valid but unrecognized is not “lexically malformed.” Extending the rule to them would require saying whether an unknown identity is invalid-parameter, cursor-expired based on actual expiry evidence, or another expressly defined outcome. Likewise, minimum-first and nondisclosure-first both can preserve missing/hidden equivalence; either needs explicit selection before changing the visibility-gap branch. No need to ask those questions merely to implement the first closed receiving increment once ruled.

After an actual receiving ruling, the smallest serving proposal would update the normative receiving sentence and the existing consistency/HTTP receiver, preserving recognized-position comparison/wait and all current resource/alias behavior. Tests should use actual raw single/duplicate fields, absent-all versus partial/empty/illegal tokens, authenticated/anonymous precedence, no owner entry/conditional shortcut on receiving failure, GET/HEAD body rules and a valid satisfied/future control. Inventory the existing route-specific Snapshot/feed/Event/receipt branches before assigning paths; some parse controls separately and must share the same decision without changing their target/nondisclosure ordering. This is a concrete subsequent bounded plan, not authorization now. No transport limit, arbitrary token interpretation, public admission change or test-only bypass is required.
