## 2. Front-load the small set of semantic decisions

The default working recommendations, subject to Donna's review, are:

1. Keep task-management commands Issue-only (`ready`, `blocked`, claim/lease, close/reopen/defer, epic/children, comments/todo) unless a Memory or other Bead meaning is intentionally designed. Generic Bead/Link commands remain the common surface.
2. Make shipping-product Issue JSON and exit/error behavior the compatibility baseline where feasible. Preserve intentional graph-only complete-record formats; log exceptions rather than silently rewriting golden files. Human wording may change with documented intent.
3. Keep `bd dep` Dependency-only and `bd link` all-Link. Keep Link query/search deferred until its semantics and index contract are approved. Current `bd link list/count` are collection filters, not substitutes for a general query language.
4. Keep Dependency metadata/property update refusals until Trish's Type/constraint design defines the writer contract. Do not enable `gate`, `state set`, label writers or duplicate/supersede by changing only the admission allowlist; their atomicity/row-isolation constraints need independent decisions.
5. Let Polly's accepted shared History/Provenance V2 contract determine whether `bd history` remains a local versions alias or becomes an event/attribution view. Do not implement a second History model in the CLI lane.
6. Treat `remember`/`memories`/`recall`/`forget` as Memory-specific convenience commands over the canonical Bead operations until Melinda's record/identity contract is settled; then decide which wrappers remain.

Capture each accepted choice in a short decision/exception ledger keyed to matrix rows. Unresolved choices block only dependent waves, not independent baseline work.

## 4. Scheduling and stop conditions

Wave 0 (baseline) and decision ledger can run while the fork/upstream CI/Bazel merge is being reconciled; they do not require product-source edits or another Dolt runner. A and the safe parts of C can proceed once the integration base is qualified. B waits for the Type/Link-constraint contract; D waits for Melinda/Polly's relevant accepted slices. E is a rolling backlog, not a Preview 3 release gate by default. Any command that cannot satisfy its whole journey and qualification remains explicitly refused and is recorded for a later preview.

The first concrete delivery should be the row-complete, evidence-labeled Preview 2 matrix plus corrected versions of the two inventories. The second should be Donna's short decision ledger and a prioritized PR queue, with each item naming the exact rows and acceptance scenarios it will close. Only then start implementation PRs. This avoids treating either source-only report, an old help page, or a broad test-suite pass as proof of command-level completeness.
